## 요약

| 항목 | 결론 |
|---|---|
| 용도 | 맞다. 만든 사람이 팀에 내놓기 전에 직접 돌려 보는 기능이다. 지금은 저장하는 순간 팀 전체가 쓰는 상태가 되어 그 단계가 없다 |
| 공개 상태 | 새 칸을 만들지 않는다. **게시됨** = 활성 release가 있다. **미게시** = 없다. 미게시 에이전트는 그 에이전트의 관리자와 워크스페이스 `owner`·`admin`에게만 보인다. 게시되면 지금 규칙대로 보인다 |
| 미리보기 | 켜지 않은 release로 관리자가 혼자 돌리는 세션. 세션 만들기 요청의 `preview: true`. 웹 로그인만, 개인 key·에이전트 key·Slack은 안 된다. 공유 범위는 만든 사람 하나로 고정되고, 턴마다 지금도 관리자인지 다시 본다 |
| 게시 | 시험한 release를 지금의 활성화(`POST /v1/agents/{id}/activate`)로 켠다. 버전·롤백 흐름은 그대로다 |
| 저장과 게시 분리 | 저장 요청에 `activate: false`를 더한다. 지금의 저장 대기(draft) 상태로 남기고 release를 만들되 켜지 않는다. 기본값은 지금처럼 켠다 |
| 콘솔 | 새 에이전트 화면을 다시 만든다. 이름 → 하는 일 → **미리 써 보기** → 채널 연결. 게시된 에이전트는 설정 저장 옆에 "저장만 하고 미리 써 보기", release 탭의 켜지 않은 release에 "미리 써 보기" |

## 결정 1: 공개 상태는 활성 release로 정한다

- **게시됨**: `active_release_id`가 있다. **미게시**: 없다. 새 칸(`published_at`, `visibility`)을 만들지 않는다. 활성 release를 비우는 동작이 없으므로, 한 번 게시된 에이전트는 계속 게시됨이다. 그래서 미게시 에이전트에는 승인된 release가 없고, 그 에이전트의 세션은 미리보기 세션뿐이다.
- 미게시 에이전트에서는 담당 팀 구성원과 사용 범위 팀을 안쪽·사용 근거에서 뺀다. 남는 것은 그 에이전트의 관리자(개인 관리자, 관리자 팀 구성원, 담당 팀 `lead`)와 워크스페이스 `owner`·`admin`이다. 담당 팀 `member`에게는 지금 바깥쪽이 받는 답과 같다. 목록과 counts에 없고, 상세는 `404`다.
- **같은 판정을 하는 모든 곳을 함께 바꾼다.** 한 곳만 바꾸면 경로마다 답이 달라진다. 바꾸는 곳은 넷이다.
  1. SQL 안쪽 판정 `insideAgent`(`administers.ts:130`). 목록·counts·상세·세션 공유 가시성(`session-shares.ts:131`)이 이것을 쓴다. SQL 사용 판정 `agentUsable`(`administers.ts:175-220`)은 `insideAgent` 말고도 갈래가 셋 더 있다. 공개(`workspace` 범위), 사용 범위 팀, 에이전트 key. 미게시면 공개와 사용 범위 팀 갈래도 막는다. 에이전트 key 갈래는 아래 규칙대로 둔다.
  2. 잠금 아래 다시 맞추는 안쪽 판정(`requester-locks.ts:192-200`, `:510-520`). 담당 팀 구성원을 따로 다시 세므로 같은 조건을 넣는다.
  3. 사용 판정의 사실 모으기. 미게시면 `managingMember`와 `usageTeams`를 비우고, `scope: workspace`의 `public` 근거도 쓰지 않는다(`agent-usage-decision.ts:58-86`의 입력을 만드는 쪽).
  4. 정책의 `isInside`(`agent-authority.ts:148`)는 1을 부르므로 따로 바꿀 것이 없음을 시험으로 확인한다.
  - 판정식 하나("게시됐거나, 관리자이거나, 워크스페이스 관리자")를 SQL 조각으로 두고 1·2·3이 같이 쓴다. 미게시 에이전트, `workspace` 공유 세션, 사람 지정 공유, 에이전트 key 각각에 대해 네 경로가 같은 답을 내는지 맞춤 시험을 두고, 목록·상세·`GET /v1/usable-agents`·세션 만들기 endpoint 시험도 둔다.
- **에이전트 key.** 에이전트 key는 지금처럼 자기 에이전트 행 하나를 읽는다(`keysOwnAgent`, `agent-service.ts:399-438`). 그 key는 그 에이전트의 관리자가 발급했고, 사람에게 에이전트를 보여 주는 길이 아니다. 미게시 에이전트에서는 `active_release_id`가 `null`이라 key로 시작할 세션이 없고, 미리보기는 웹 로그인만 하므로 key로 켜지 않은 release를 돌릴 길도 없다. 그래서 이 경로는 막지 않고, 이 동작을 endpoint 시험으로 고정한다.
- 게시된 뒤의 "권한 있는 사용자"는 지금 규칙 그대로다. 사용 판정은 근거의 합집합이고(사용 범위가 `private`이면 그 팀들에 워크스페이스 관리자·관리자·담당 팀 구성원이 더해진다), 세션 시작은 거기에 안쪽 조건을 더한다. 사용 범위 설정을 공개 상태로 쓰지 않는 이유: 사용 범위는 게시된 에이전트를 누가 쓰는지를 정하는 것이고, `private`도 팀을 하나 이상 골라야 해서 "관리자만"을 표현하지 못한다.
- 활성화 실패로 활성 release가 아직 없는 에이전트(counts `draft`)도 미게시다. 지금도 담당 팀 구성원은 이 에이전트를 쓰지 못한다. 바뀌는 것은 목록과 설정 읽기(카드, 버전, release, `agents.ts:251-260`)다. 담당 팀 `member`는 첫 게시 전까지 이것도 보지 못한다.
- 게시를 되돌리는 "비공개로 돌리기"는 만들지 않는다. 쓰던 사람의 Slack·API 경로가 한꺼번에 끊긴다. 멈추는 것은 지금의 일시 정지(`paused`)로 한다.

## 결정 2: 미리보기는 켜지 않은 release로 관리자가 혼자 돌리는 세션이다

- 세션 만들기(`POST /v1/sessions`)에 `preview: true`를 더한다. 이때만 승인되지 않은 release로 시작할 수 있다.
- **조건.**
  1. 요청자가 웹 로그인한 사람이다. 개인 key, 에이전트 key, Slack은 `preview`를 보내면 `400`이다. 관리 action은 지금 사람 아닌 주체를 모두 거절한다(`packages/platform/src/musterrolle/policy.ts:724-725`). 개인 key까지 열려면 key의 만든 사람을 관리자로 보는 판정을 새로 만들어야 하는데, 그만한 필요가 아직 없다.
  2. 그 release의 에이전트를 관리한다(`agent.manage`, 워크스페이스 관리자 포함).
  3. release가 그 에이전트의 것이고 연결·모델이 지금 쓸 수 있다(`RELEASE_SPEC_UNAVAILABLE`은 그대로).
  4. 에이전트가 `active`다. 소유자 없음으로 막힌 에이전트도 미리보기는 된다. 승계하려는 사람이 확인할 길이 있어야 하기 때문이다(관리자가 없으면 워크스페이스 관리자만 해당한다).
- **거절의 모양.** 바깥쪽(그 에이전트를 볼 수 없는 사람)은 지금처럼 release를 찾기 전에 `404`로 숨긴다(`packages/platform/src/sessions/session-service.ts:528`, `:644`). 미리보기라고 해서 승인·연결·모델 진단을 먼저 보여 주지 않는다. 안쪽이지만 관리자가 아닌 사람(게시된 에이전트의 담당 팀 `member`)이 `preview: true`를 보내면 `403 FORBIDDEN`(`reason_code: role`)이다. 이 사람은 이미 설정 화면에서 release를 읽으므로 감출 것이 없다. `preview` 없이 승인 안 된 release를 보내면 지금처럼 `release_unapproved`다.
- **턴마다 다시 본다.** 미리보기 세션에 입력을 더하거나 이어 가는 모든 요청(턴 제출, 재개)은 그 순간에도 2를 만족해야 한다. 관리자에서 빠진 뒤에는 자기가 만든 미리보기 세션이라도 새 턴을 돌리지 못하고 `403`(`reason_code: role`)이다. 판정은 입력을 받아들이는 transaction 안에서, 사용 판정을 잠금 아래 다시 하는 자리(`requester-locks.ts`)에서 한다.
- **대기 요청 답변도 같다.** 미리보기 세션의 질문·권한 요청에 답하거나 push·PR을 승인하는 것도 멈춘 턴을 이어 가게 한다(`packages/platform/src/decision/pending-service.ts:82-86`, 잠금 아래 재판정 `packages/db/src/sessions/pending-requests.ts:747-750`, 재개 `:928-946`). 지금은 세션을 만든 사람이면 관리자가 아니어도 답할 수 있다(`policy.ts:545-550`). 미리보기 세션에서는 답하는 사람이 웹 로그인한 사람이고 지금도 그 에이전트를 관리해야 한다. 같은 쓰기 transaction 안에서 본다. 관리자에서 빠진 뒤 멈춘 요청에 답하는 시험을 둔다.
- transcript 읽기는 이 조건과 따로이고 지금의 세션 공유 규칙을 따른다.
- 승인된 release(활성 또는 옛 release)에도 `preview: true`를 보낼 수 있다. 같은 표시와 같은 조건이 붙을 뿐이다.
- 세션 행에 `preview boolean NOT NULL DEFAULT false`를 둔다. 상세·목록에 `preview`로 나온다. release가 나중에 게시돼도 이 값은 바뀌지 않는다.
- **공유 범위는 만든 사람 하나로 고정한다.** 미리보기 세션의 공유를 넓히는 요청은 `409`다. 아직 팀에 내놓지 않은 동작과 그 transcript가 담당 팀에 보이지 않게 하려는 것이다. 워크스페이스 관리자의 감사 읽기(`session.audit_read`)는 지금처럼 된다.
- 미리보기 세션도 진짜 세션이다. 같은 worker, 같은 도구·권한 모드·GitHub 설정·자격 증명 연결·호출자 상한으로 돈다. 사용량과 비용도 그대로 센다. 따로 sandbox를 만들지 않는 이유: 다르게 돌면 게시 뒤의 동작을 시험한 것이 아니다. push 승인 같은 외부 쓰기 확인은 release 설정대로 사람에게 묻는다.
- **Slack.** Slack 세션은 에이전트의 활성 release로만 시작하고, 미리보기 세션은 Slack 링크를 갖지 않는다. 미게시 에이전트에 Slack 앱을 붙이는 것은 지금처럼 된다(설치 준비). 멘션과 DM은 지금처럼 요청자를 먼저 판정한다(`packages/adapters/chat/slack/src/slack-session-handler.ts:335-345`). 그 판정을 통과하는 사람(관리자, 워크스페이스 관리자)만 "아직 게시되지 않은 에이전트" 안내를 받고, 나머지는 지금의 숨김 답을 그대로 받는다. 안내를 판정보다 앞에 두지 않는다.
- 성과 판정(achievements)에서는 미리보기 세션을 뺀다. 시험 실행이 팀 성과로 세어지지 않게 한다.

## 결정 3: 저장과 게시를 나눈다

- `POST /v1/agents`와 `PATCH /v1/agents/{id}`의 저장 요청에 `activate`(기본 `true`)를 더한다. 기본값을 `true`로 두는 이유: 지금의 API 사용자와 SDK는 저장이 곧 적용이라고 믿고 있다. 콘솔이 `false`를 보낸다.
- **`activate: false`의 상태 전이.** 지금의 저장 기계를 그대로 쓰고, 마지막 활성화만 하지 않는다.
  1. 지금처럼 `behavior_revision`을 하나 올리고 draft(`draft_version_id`, `draft_connection_id`)를 채운다. `draft_failure`는 비운다. 이 revision이 오르므로 앞서 진행 중이던 저장의 활성화는 지금처럼 `superseded`로 끝난다. 그래서 더 오래된 저장이 나중에 켜지는 일이 없다.
  2. 그 버전과 연결로 release를 만든다(`createRelease`와 같은 검사). 켜지 않는다. release를 만들지 못하면(연결이 꺼짐, 모델이 목록에 없음, 확장 거절 등, `agent-service.ts:491-531`) 지금의 저장 실패와 같이 처리한다. draft는 남기고, 그 revision이 아직 지금 것일 때만 `draft_failure`를 적고 `failed`(이유 포함)를 답한다. 더 새 저장이 있으면 `superseded`다(`agent-service.ts:812-836`과 같은 규칙). 콘솔은 이유를 보여 주고 같은 저장을 다시 하게 한다.
  3. release를 만든 뒤, 에이전트 행을 잠그고 그 저장의 `behavior_revision`과 `draft_version_id`가 아직 그대로인지 본다(활성화가 `agents.ts:1130-1135`에서 하는 것과 같은 검사). 그 사이 더 새 저장이 들어왔으면 `superseded`를 답한다. 만든 release는 켜지 않은 release로 남을 뿐이다. 그대로이면 응답의 `release.status`는 새 값 `saved`이고 `release_id`가 있다. draft는 남는다. 즉 draft의 뜻을 "저장했지만 아직 켜지 않은 변경"으로 그대로 쓰고, `draft_failure`가 없으면 "켜기를 기다린다", 있으면 "켜기에 실패했다"다.
  4. 저장한 카드와 연결이 지금 활성 release와 같으면 지금처럼 draft를 비우고 `unchanged`다.
- **다음 저장.** draft가 있으면, 카드나 연결을 생략한 부분 저장은 활성 release가 아니라 draft의 카드와 연결을 바탕으로 한다(지금은 활성 release가 먼저다, `agent-service.ts:700-712`). 그래야 저장만 해 둔 변경 위에 이어서 고칠 수 있다. 실패한 draft 위의 저장도 같은 규칙이다.
- **게시(활성화)와 draft.** 게시는 지금의 활성화다(`POST /v1/agents/{id}/activate` `{"release_id", "expected_revision"}`). 화면에서 본 `activation_revision`을 보내고, 경합이면(`REVISION_CONFLICT`) 새로 읽고 사람이 다시 누른다. 자격 증명 연결 확인(`CREDENTIAL_UNBOUND`)도 그대로다. 켠 release의 버전과 연결이 draft와 같으면 활성화 transaction에서 draft를 비운다. 다르면(예: 이전 release로 롤백) draft는 남고, 콘솔은 "켜지 않은 변경이 있습니다"를 계속 보여 준다.
- 게시된 에이전트에서 `activate: false`로 저장한 변경은 활성 release를 건드리지 않는다. 팀은 계속 이전 release를 쓰고, 관리자는 새 release를 미리 써 본 뒤 release 탭에서 켠다.
- **설정 읽기는 지금 그대로다.** 저장만 한 버전과 release는 설정을 읽는 사람(게시된 에이전트의 담당 팀 구성원 포함)에게 지금처럼 보인다. 이 설계가 팀에 감추는 것은 켜지 않은 동작을 돌린 결과(미리보기 transcript)와 미게시 에이전트 자체다. 저장만 한 설정까지 감추려면 버전·release 읽기를 관리자 여부로 거르는 일이 따로 필요하고, 지금 요청에는 없다.
- 첫 게시로 활성 release가 생기면 [결정 1](#결정-1-공개-상태는-활성-release로-정한다)에 따라 팀에 보인다.

## 콘솔

시안: 오케스트레이터가 게시한 HTML 시안. 오너가 시안을 승인하며 지금의 새 에이전트 화면을 다시 만들라고 했다.

1. **새 에이전트 화면(재설계).** 이름 → 하는 일 → 미리 써 보기 → 채널 연결.
   - 지금 넓은 화면에서 보이는 문제와 고칠 점: 입력 칸이 화면 끝까지 늘어난다(폼 폭을 640–720px로 제한). 오른쪽이 비어 있다(만드는 에이전트의 요약과 다음에 일어날 일을 보여 주는 패널로 쓴다. 좁은 화면에서는 폼 아래로 내린다). 페이지 제목에 focus ring 상자가 그려진다(단계 이동 때 제목에 focus를 옮기되 상자를 그리지 않는다). 식별자 도움말이 한 줄로 길다(짧게 줄이고 이름에서 만든 값을 바로 옆에 보여 준다). "다음" 버튼이 작게 홀로 있다(모든 단계에 뒤로·다음이 같은 자리에 있는 하단 줄).
   - `packages/ui` 부품을 쓰고, 단계 이동 때 제목 focus, 오류 연결(`aria-describedby`), 키보드 순서를 지킨다.
   - "하는 일"의 버튼은 "저장하고 미리 써 보기"다(`activate: false`).
   - "미리 써 보기" 단계: 위에 "아직 게시하지 않았습니다. 이 에이전트의 관리자와 워크스페이스 관리자만 이 에이전트를 봅니다." 알림. 메시지를 보내면 미리보기 세션이 시작되고, 답과 세션 링크가 보인다. 같은 세션에 이어 보낼 수 있다. "설정 고치기"는 이전 단계로 돌아가 새 release를 만들고, 다음 메시지는 새 미리보기 세션으로 간다.
   - "게시" 버튼: 확인 창 "게시하면 담당 팀 {팀}이 이 에이전트를 쓸 수 있습니다." → 활성화. "나중에 게시"를 누르면 미게시 상태로 에이전트 상세로 간다.
   - 채널 연결은 게시 뒤에만 연다.
2. **에이전트 목록.** 미게시 에이전트는 상태 칸에 "미게시"로 보인다(관리자에게만 보이는 행이다).
3. **에이전트 상세(미게시).** 위에 알림 "아직 게시하지 않았습니다"와 "미리 써 보기", "게시" 버튼.
4. **release 탭.** 켜지 않은 release의 행에 "미리 써 보기"(미리보기 세션 시작)와 지금의 "켜기"(=게시). 설정 저장 버튼 옆에 "저장만 하고 미리 써 보기". draft가 있으면 위에 "켜지 않은 변경이 있습니다"를 보여 준다.
- 미리보기 세션은 세션 목록과 상세에 "미리보기" 표시가 붙는다.

## 하지 않는 것

- 별도 sandbox 실행 환경, 가짜 도구, 외부 쓰기를 막는 모드. 미리보기는 진짜 실행이다.
- 공개 상태 칸, 게시 취소, 게시 예약.
- 개인 key로 하는 미리보기.
- 저장만 한 버전·release를 담당 팀 구성원에게서 감추기.
- 다른 사람에게 미리보기를 보여 주는 공유(검토자 초대). 필요해지면 미리보기 세션의 공유를 지정한 사람까지 여는 것으로 연다.
- 미리보기용 비용 상한. 지금의 세션 상한과 호출자 상한이 그대로 적용된다.

## 오너 확인이 필요한 것

아래는 이 문서가 정한 기본값이다. 바뀌면 후속 PR로 고친다.

- 공개 상태는 활성 release 유무로 정하고 별도 칸을 두지 않는다.
- 미게시 에이전트는 담당 팀 `member`에게도 보이지 않는다.
- 미리보기는 진짜 실행이다(sandbox 없음). 비용·외부 쓰기도 실제와 같다.
- 미리보기는 웹 로그인만 한다(개인 key 없음).
- 저장만 한 설정은 지금처럼 설정을 읽는 사람에게 보인다.
