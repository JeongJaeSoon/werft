| 今あるもの | API | 誰が |
| --- | --- | --- |
| 自分の Slack アカウントを Web アカウントに連携 | `POST /v1/linked-accounts/slack/start`, `…/callback`, `GET /v1/linked-accounts`, `DELETE /v1/linked-accounts/{id}` | ログインした本人 |
| エージェントに Slack アプリ(bot)を接続 | `POST`·`GET /v1/agents/{id}/identities`, `DELETE …/identities/{identity_id}` | owner·admin·そのエージェントの管理者 |
| guest のエージェント利用を許可 | `POST /v1/workspaces/{id}/slack-guest` | owner·admin |

三つとも Web ログインの cookie でのみ呼び出せる。API キーでは 403 になる。以下の例は[作成](/agents/create#ログイン)の `WEB` ヘッダーと `WS` を使う。

## guest の利用設定

Slack guest(マルチチャンネル·シングルチャンネル guest)がエージェントを使えるかどうかを決める。デフォルトはオフである。

```bash
WS=$(curl -sS "$API/v1/auth/me" "${WEB[@]}" | jq -r .workspace.id)
curl -sS "$API/v1/workspaces/$WS/slack-guest" "${WEB[@]}" \
  -d '{"slack_guest_enabled": true}' | jq .
```

```text
{
  "slack_guest_enabled": true
}
```

オンにしても、guest は自分の Slack アカウントを連携しないと使えない。Slack Connect で参加した他社のユーザーは、この設定に関係なく使えない。

## Slack アカウントの連携

Sign in with Slack(OpenID Connect)で連携する。運用者がコンソールの公開アドレス `CONSOLE_ORIGIN` を設定し、ワークスペースのアドミンが設定 > ワークスペース > 連携 > Slack に App Configuration Token を入れてアカウント連携用アプリを作れるようにし、そのワークスペースに確認済みの Slack インストールがある必要がある。ローカルスタックには `CONSOLE_ORIGIN` がないため、開始リクエストは 503 になる。API が Slack に送る要求と id_token の検査はログインプロバイダーと同じである。Slack のアドレスは https でなければならず、loopback・link-local・reserved アドレスに解決される名前には送らず 503 で終わる。id_token には `exp`・`iat`・`sub` が必要で、`iat` は 60 秒先から 11 分前までだけを受け付ける。

```bash
curl -sS -o /dev/null -w '%{http_code}\n' -X POST "$API/v1/linked-accounts/slack/start" "${WEB[@]}"
```

```text
503
```

設定済みのインストールでは、開始リクエストが `authorize_url` を返す。その URL の Slack の認可画面で同意すると、Web の連携画面が `code` と `state` を callback に渡し、連携が完了する。開始したブラウザで 10 分以内に終える。時間が過ぎたか別のブラウザで続けると `400` になり、最初からやり直す。連携の状態は `active`·`stale`·`revoked` である。

連携の応答と `GET /v1/linked-accounts` の各項目には、連携時に Slack が返した名前も入る。`external_user_name` は Slack の表示名（id_token の `name`）、`external_tenant_name` は Slack ワークスペース名（`https://slack.com/team_name`）である。もう一度連携すると新しい名前に置き換わる。名前を保存する前に作った連携や、Slack が名前を返さなかった連携は `null` で、Web 画面はそのとき ID を表示する。Slack のトークンは保存しない。そのため provider トークンの有効期限である `expires_at` は、Slack 連携では常に `null` である。開始応答の `expires_at` は連携リクエストの有効期限で、別の値である。

| レスポンス | 意味 |
| --- | --- |
| 409 `SLACK_NOT_INSTALLED` | このワークスペースに確認済みの Slack インストールがない |
| 409 `LINK_TEAM_MISMATCH` | インストールされていない Slack チームのアカウントである |
| 409 `LINK_TAKEN` | その Slack アカウントは別の人に連携されている |
| 409 `LINK_EXISTS` | 同じチームに自分の連携がすでにある |

アカウント連携用アプリがなければ、最初の連携開始がその場でアプリを作る。Slack の作成応答を失うと（タイムアウト、接続切れ、保存失敗）アプリは作成中のまま残り、その後の連携開始はすべて `409 SLACK_APP_CREATING` になる。60 秒を過ぎると `details.uncertain: true` が付く。そのとき api.slack.com/apps でその時刻に作られたアプリを確認して削除し、API コンテナーで次を実行して([運用者コマンドの実行](#運用者コマンドの実行))、失われた作成をあきらめて新しく作る。出力は JSON 一行である。終了コード `6` は、アプリがまだ作成中（60 秒前）か削除中であることを示す。

```bash
bun run apps/control-host/src/api/slack-app.ts create --kind link --workspace "$WORKSPACE_ID" --replace-uncertain
```

## 通知の言語

プラットフォームが Slack に書く案内文(拒否の案内、失敗・回答待ちの案内、`Webで開く` リンク、Web・API から送った指示の `(Webコンソール)` 表示)は、ユーザーが Web コンソールの **言語・テーマ** で選んだ言語(한국어・日本語・English)に従います。コンソールは選んだ言語をサーバーに保存します(`PATCH /v1/auth/me`)。保存した言語がないままコンソールが英語以外の言語で開いた場合(ブラウザーの言語など)は、その言語を保存してコンソールと Slack の言語をそろえます。

- 本人にだけ見える拒否の案内は、その Slack アカウントに連携したユーザーの言語で書きます。
- スレッドに投稿する案内と指示の表示は、セッションを開始したユーザーの言語で書きます。スレッドは複数の人が見るため、1つの言語にそろえます。
- 言語を保存したことがないユーザーと、連携していない Slack アカウントには英語で届きます。

モデルの回答とユーザーが入力した内容は翻訳しません。デプロイの歓迎メッセージは受け取る人が決まらないため、韓国語で送ります。

## 承認と回答

Slack のスレッドから始めたセッションが人を待つと、待っている要求ごとにそのスレッドへカードが 1 枚投稿される。カードはセッションを始めた人をメンションし、Web で同じ要求を開くリンクと有効期限を示す。カードは投稿するときにセッションを始めた人の言語([通知の言語](#通知の言語))で書き、処理したあともその言語のままにする。

ツール権限のカードは、何をしようとしているかを 1 行に要約して示す。たとえば `コマンド実行: bun test`、`ファイル編集: src/app.ts`、`PR作成: タイトル (ブランチ)` のようになる。ファイルを書いたり編集したりするツールは、要約の下に書き込む内容の最初の 3 行も示す。モデルが渡した入力の原文は **入力の原文** の下に折りたたまれ、開いたときだけ見える。原文はフィールドごとに `名前: 値` で示し、値の中の改行は `\n` ではなく実際の改行で示す。長い原文は切り詰められるため、全体は **Webで開く** で見る。push 承認のカードもリポジトリ・ブランチ・コミットを先に示し、残りは **詳細** の下に折りたたむ。モデルが書いた文はカードのどこでもメンションやリンクにならない。

| 要求 | カードでできること |
| --- | --- |
| ツール権限 | **許可**・**指示を付けて許可**・**拒否**。**指示を付けて許可** は指示を書くフォームを開く。送信すると許可され、その指示がモデルに渡される。指示は 8 KiB までで、空のときはフォームにエラーが表示される。セッションが指示をモデルに渡せない場合は許可しない。その理由は押した人だけに見えるメッセージで伝え、リクエストは開いたまま残る。処理されたカードは普通の許可と同じで、指示の内容はスレッドに表示されない。エンジンが繰り返し確認するルールを提案した場合は **このセッション中は許可** が加わる。ルールはカードと確認ダイアログに表示される。リダイレクト・パイプ・複合コマンドなど、提案されたルールがその呼び出しに合わない可能性がある Bash 呼び出しにはボタンを出さない。押すと、このセッションが終わるまでそのルールに合う呼び出しを確認しなくなる。この許可は押した人に結び付き、その人が答えられなくなると(プライベートチャンネルを抜けたなど)カードがまた出る。処理済みのカードは `セッション中は許可` になる。push 承認とサーバーの許可リストはこのボタンでは変わらない。ボタンは、エンジンがその呼び出しを覆うルールを提案したときだけ付く。`auto` モードの release(新しく作った Claude モデルの release)はルール外の呼び出しを分類器が判定するため、カードはたいてい確認一覧にかかった呼び出しで、今そのカードにはこのボタンは出ない。確認一覧の呼び出しは毎回人が答えるものとしている。このルールより前に作った Claude モデルの release と、`auto` release のセッションが Claude 以外のモデルに移った場合は `default` で動く。`default` モードでワークスペースのルール外の呼び出しを確認するときはボタンが出ることがある。Codex 接続の release には出ない([権限モード](/agents/permissions#権限モード)) |
| 質問 | 質問が 1 つで選択肢が 5 個以下なら選択肢ボタン、自由入力できるなら **直接入力**。それ以外は **回答する** で開くフォームで答える。質問が 10 個を超えるか 1 つの質問の選択肢が 100 個を超えると Slack のフォームに収まらないため、カードは「このリクエストはWebで回答してください」と **Webで開く** ボタンだけを示す |
| push 承認 | リポジトリ・ブランチ・コミットを確認して **承認**(もう一度確認する)・**却下** |

押した人は Slack アカウントが Web アカウントに連携されていて([Slack アカウントの連携](#slack-アカウントの連携))、Web でそのセッションの要求に答えられる人でなければならない。Web と同じ規則で判断する。連携していないアカウントには連携ページのリンクを、権限のない人には拒否の案内をその人にだけ表示し、何も処理しない。

処理するとカードからボタンが消え、結果が残る。Slack で押しても Web で答えても同じである。Web で答えたとき、要求が期限切れになったとき、セッションが終わって要求が閉じたときは、control-host 内の action-broker が少しあとに Slack のカードを同じ形に直す。1 行目は結果と処理した人で、どこで処理したかも示す。Slack で処理したなら `許可済み · @名前`、Web で処理したなら `Webで許可済み · @名前` になる。処理した人の Slack アカウントが連携されていなければ、名前なしで結果だけを示す。ツール権限と push のカードは、この結果に要求の要約と Web のリンクを付けた 1 行になる。質問のカードは質問の全文をそのまま残し、その下に選んだ答えを `<選択肢>を選択`(Web で答えたなら `Webで<選択肢>を選択`)で示す。直接入力した文は内容を出さず `直接入力` とだけ表示する。スレッドは複数の人が見るためである。期限切れやセッション終了で閉じた要求は誰もメンションしない。質問のカードは質問を残したまま、期限切れなら `期限切れ`、セッションが終わって閉じたなら `もう回答できません` を示す。Slack がカードの更新を断ったら少しあとにやり直し、メッセージが削除されたかチャンネルがアーカイブされていればそのままにする。カードは押されたメッセージではなく、保存された要求から描き直す。Web や他の人がすでに処理した要求を押しても再び処理せず、カードを現在の結果に更新する。Slack で push を承認・却下すると、その結果をセッションに伝える指示が続き、セッションが PR を開くか却下を伝える。承認したときにセッションのターンが動いていれば、その指示はそのターンが終わるまで待ち、そのターンがすでに PR を開いていれば入れない。そのブランチに PR がすでにある場合も入れない。そのため同じ PR を二度開いたり、同じ返事を二度したりしない。

ボタンとフォームはエージェントアプリの Interactivity アドレス `/v1/slack/interactions/{agent_id}` に届く。イベントと同じく、そのアプリの signing secret による署名と 300 秒以内の時刻を確認する。インストールの finalize が Event Subscriptions のアドレスと一緒に manifest に入れる。この機能より前に作ったアプリは **再確認**(`POST /v1/agents/{id}/slack/app/events/recheck`)で manifest を送り直すと登録される。

セッションのスレッドにエージェントが投稿するメッセージ（回答、失敗・待機の案内、カード）の送信者名は `エージェント名 [セッションのタイトル]` になる。タイトルがまだなければエージェント名だけが表示される。Slack は名前を 80 文字で切るので、その中に収め、長いタイトルは `…` で縮める。セッションのスレッド外のメッセージ（デプロイの歓迎など）はエージェント名で投稿される。`chat:write.customize` 権限のないアプリは名前を変えず、これまでどおりアプリ名で投稿する。一人にだけ見える拒否の案内もアプリ名のままだ。

エージェントのアプリは bot scope `reactions:write` を持つ。エージェントが答えるメッセージに 👀 を一つ付けるための scope で、一つのメッセージには一度だけ付ける。会話 rollout が `on` のエージェントがメンションを返信・新しいタスクの作成・開いているタスクへの引き継ぎで終えると、そのメッセージに付け、黙っている場合は付けない。scope がないアプリは付けず、回答はそのまま送られる。人が付けた絵文字は読まず、`reaction_added` イベントも受け取らない。この scope ができる前にインストールしたアプリはそのまま動き、コンソールの Slack タブのアプリ欄に「Slack の再承認が必要」が出る。**再承認**でアプリをインストールし直すとこの scope を受け取る（[コンソールで Slack に接続する](/integrations/slack-console)）。

会話 rollout が `on` のエージェントでメンション・DM のターンが決定なしに終わると（モデルのエラー、時間切れ、ターンの上限）、そのスレッドに `今はお答えできませんでした。もう一度やってみます` を一度だけ残し、同じメッセージでもう一度試す。2 回目はすぐに、3 回目は 2 回目が終わってから 10 秒後に試す。試すたびにモデル呼び出しを別に予約する。3 回とも決定なしに終わると `3回試しましたが、お答えできませんでした。しばらくしてからもう一度呼んでください` を残す。その間スレッドは処理中と表示され、終わると元に戻る。次の場合はもう一度試さない。

- 予算アカウントが呼び出しを拒否したら、予算の案内を一行だけ残す。
- その試行がすでに Slack に何かを送ったか、送るために残していたら（回答、👀、案内）、同じことを二度しないようにすぐ失敗の文を残す。その試行のモデル呼び出しが終わったという報告が、試行の終了から 30 秒以内に来ないときも同じ。
- 管理者が緊急停止したか、会話 rollout が `on` でなくなったか、メンションのメッセージが削除されたら、何も残さない。

## 作業を止める

会話 rollout が `on` のエージェントでは、開いている作業（セッション）に結びついたスレッド（チャンネル・DM）に `그만`、`그만해`、`멈춰`、`멈춰줘`、`중지`、`止めて`、`やめて`、`ストップ`、`停止`、`stop` のどれか一つだけを書くと、その作業を止める。エージェントへのメンション、前後の空白、大文字・小文字、末尾の `.`・`!`・`。` はあってもよい。ほかの言葉が混じると（`止めてください、でも …`）通常のメッセージとして作業に入る。チャンネルの聞き取り設定とは関係ない。

- いま動いているターンを中断し、止めるメッセージより前に入って待っていたメッセージは処理しない。止めるメッセージの後に書いたメッセージはそのまま処理する（下のように作業を閉じたときを除く）。ただし止めるメッセージと1秒以内に書いたメッセージは、Slack が届ける順序が入れ替わることがあり、前後が逆に処理されることがある。
- セッションは閉じない。同じスレッドにもう一度書くと続きから作業する。ただし最初のターンが始まる前で、止めることで待っていたメッセージを一つ以上取り消した作業は続けるものがないのですぐに閉じ（作業は取り消しで終わる）、その後スレッドに書いたメッセージは作業に入らない。このときスレッドに `ご依頼どおり、作業を始める前に止めて閉じました。もう一度行うには、新しく依頼してください。` を残す。依頼の後に待っていたメッセージがあればその件数も書く。閉じた作業は会話・エージェントの開いている作業の数に入らない。
- スレッドに一行を残す（`ご依頼どおり作業を止めました。続けるにはこのスレッドにもう一度書いてください。`）。待っていたメッセージを処理しなかったときはその件数も書く。動いているターンも待っていたメッセージもなければ `今進めている作業はありません。` だけを残す。
- 止めるメッセージ自体は作業の入力にならない。
- 止められるのは、そのセッションを制御できる人（Web の **このターンを停止** と同じ権限）だ。作業を依頼した人と、そのセッションに書けるメンバーがこれにあたる。チャンネルの上限からセッション制御を外したチャンネルでは、Slack からは誰も止められない。止められない人が書いた止める言葉は、その人にだけ `作業を依頼した人だけが止められます` を見せ、通常のメッセージとして作業に入る。

## 元の Slack メッセージへのリンク

Slack のメンション·DM·スレッドの返信で始めた、または送った指示は、その Slack メッセージの場所(チーム·チャンネル·`ts`、返信なら `thread_ts`)と Slack が返したリンクを一緒に残す。リンクは `chat.getPermalink` で受け取り、この呼び出しに追加の scope は要らない。Web のセッション画面は、ヘッダーの始めた人·経路の横と、会話の Slack からの指示の吹き出しに **Slack で表示** リンクを出し、押すと新しいタブで開く。API ではセッションの `slack_permalink`(セッションを始めたメッセージ)と turn の `slack_permalink`(その指示を送ったメッセージ)で読む。

プライベートチャンネルと DM もリンクだけを残し、メッセージ本文はそれ以上保存しない(指示として受け取った文はこれまでどおり turn の `message` にある)。リンクは Slack でそのメッセージを読める人にだけ開く。リンクを残す前に作ったセッション·指示と、Slack がリンクを返さなかった指示は `null` で、画面にリンクは出ない。

## 運用者コマンドの実行

このページの運用者コマンド(`slack-app.ts`、`slack-install.ts`)は api イメージの中にあり、api コンテナーの DB 設定でその設置の DB に接続する。ホストにリポジトリの checkout や Bun は要らない。設置方法ごとに api コンテナーで次のように実行する。例は `list-bots` である。

[単一サーバー設置](/run-server/self-hosting/single-server)(test-ops バンドル)では、この設置の compose project label で api コンテナーを探す。`werft-test-ops` は `TEST_OPS_PROJECT` の既定値なので、別の値で設置した場合はその値に置き換える。コンテナー id が一行出力されなければならない。

```bash
API_CONTAINER="$(docker ps -q --filter label=com.docker.compose.project=werft-test-ops --filter label=com.docker.compose.service=api)"
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/slack-app.ts list-bots --agent <agent_id>
```

[Kubernetes](/run-server/self-hosting/kubernetes) では、まず[設置の context・namespace・fullname の確認](/run-server/self-hosting/kubernetes#준비물)に従う。下の `werft` はその例の設置名である。

```bash
kubectl -n werft exec deploy/werft-api -c api -- bun run apps/control-host/src/api/slack-app.ts list-bots --agent <agent_id>
```

リポジトリ checkout のローカルスタックでは、checkout で実行する。

```bash
docker compose --profile apps exec -T api bun run apps/control-host/src/api/slack-app.ts list-bots --agent <agent_id>
```

## Slack インストールの登録

普通はこの登録は要らない。コンソールの **Slack アプリを作成してインストール**([コンソールで Slack に接続する](/integrations/slack-console))がエージェントのアプリを作り、Slack の同意が終わると確認済み(`verified`)のインストールを残す。この CLI は、Slack で手作業で作ってワークスペースにインストールしたアプリを、運用者がターミナルで登録する経路である。そのアプリの bot token でインストールを登録する。CLI が Slack の `auth.test`·`bots.info` でチーム、bot ユーザー、アプリを確認し、確認済みのインストールを残す。アプリには bot scope `users:read` が必要である。token は環境変数 `SLACK_BOT_TOKEN` でのみ渡す。CLI は token を引数で受け取らず、出力もしない。下のコマンドは token を画面に出さずに読み、コマンド引数に入れずに api コンテナーへ渡す。

単一サーバー設置(test-ops バンドル)では、[運用者コマンドの実行](#運用者コマンドの実行)のように api コンテナーを探し、`docker exec -e` でシェルの値を渡す。

```bash
API_CONTAINER="$(docker ps -q --filter label=com.docker.compose.project=werft-test-ops --filter label=com.docker.compose.service=api)"
read -rs SLACK_BOT_TOKEN && export SLACK_BOT_TOKEN
docker exec -e SLACK_BOT_TOKEN "$API_CONTAINER" \
  bun run apps/control-host/src/api/slack-install.ts register --workspace "$WS" --app-id A0123ABCD
unset SLACK_BOT_TOKEN
```

Kubernetes では `kubectl exec` に環境変数を渡すオプションがないので、token を stdin で渡し、コンテナー内のシェルがその行を `SLACK_BOT_TOKEN` として読む。

```bash
read -rs SLACK_BOT_TOKEN
printf '%s\n' "$SLACK_BOT_TOKEN" | kubectl -n werft exec -i deploy/werft-api -c api -- sh -c \
  'IFS= read -r SLACK_BOT_TOKEN && export SLACK_BOT_TOKEN && exec bun run apps/control-host/src/api/slack-install.ts register --workspace "$1" --app-id "$2"' \
  sh "$WS" A0123ABCD
unset SLACK_BOT_TOKEN
```

ローカルスタックでは checkout の package script を使う。

```bash
read -rs SLACK_BOT_TOKEN && export SLACK_BOT_TOKEN
bun run slack-install register --workspace "$WS" --app-id A0123ABCD
unset SLACK_BOT_TOKEN
```

```text
{"outcome":"verified","registration":"registered","installation_id":"…","workspace_id":"…","app_id":"A0123ABCD","team_id":"T0123ABCD","bot_user_id":"U0123ABCD"}
```

同じコマンドをもう一度実行すると、同じインストールを確認し直す(`registration: existing`)。失敗すると stderr に 1 行を書き、次の終了コードで終わる。

| 終了コード | 意味 |
| --- | --- |
| 0 | 確認済みのインストールがある |
| 2 | 引数または環境変数が正しくない |
| 3 | Slack が token を拒否した、または Slack に届かない |
| 4 | そのアプリとチームは別のワークスペースのものである(`workspace_conflict`)。そこで解除されていても、そのワークスペースだけが再登録できる |
| 5 | 登録中にインストールが解除された(`revoked`)。もう一度実行すると再び開く |
| 6 | ワークスペースが存在しない(`workspace_not_found`) |
| 7 | token が `--app-id` とは別のアプリのものである(`app_mismatch`) |
| 1 | その他のエラー |

## エージェントの Slack アプリ

### アプリ設定の読み取り

owner・admin を含むエージェント管理者が Web セッションで呼び出す。`GET /v1/agents/{id}/slack/app` は `event_url` と `events` を返す。イベント URL は、サーバーがコンソールの公開アドレス(`CONSOLE_ORIGIN`)から計算した https アドレスに `/v1/slack/events/{agent_id}` を付けた絶対 URL である。イベントの入口をコンソールと別にしているサーバーは、owner が **設定 > 連携 > Slack** の「イベントの入口アドレス」に保存したアドレス(`PUT /v1/slack-settings`)を使う。計算できなければ null になる。owner がイベントの入口アドレスを変えて保存すると(空にして `CONSOLE_ORIGIN` のアドレスに戻るときも)、すべてのワークスペースの `created` のエージェントアプリに、新しいアドレスを入れた manifest を再確認と同じように送る。すべてのアプリに一度に送り、Slack の `Retry-After` は待たず、応答は 20 秒までしか待たない。応答の `updates` がアプリごとに `updated`(新しい権限も受け取ったら `reinstall_required: true`)、`sending`(待つ間に Slack が応答しなかった。結果は応答が来たあとそのアプリの `manifest_sync` に残る)、または `failed` と理由(`config_token_inactive`・`events_url_unset`・`slack_refused`・`no_answer`)を返し、同じ理由がそのアプリの `manifest_sync` に残って Slack タブに「更新が必要」と出る。送れなかったアプリは前のアドレスのままで、`POST /v1/slack-settings/retry`(コンソールの **送れなかったアプリにもう一度送る**)で送り直す。`events.state` は `pending`・`verified`・`failed` である。インストール finalize が manifest にこのアドレスを Request URL として入れると `pending` になり、`events.url` に送ったアドレスが残る(送る前は null)。すでに `verified` のアプリは、アドレスをもう一度入れても、アドレスが変わっても `verified` のままである。Slack は manifest 更新で変わった Request URL を確認し直さず、確認済みのまま扱うためである。変わったアドレスへの更新を Slack が拒否すると `failed` になる。そのアプリの signing secret で署名されたリクエスト(`url_verification` またはイベント)が初めて届くと `verified` になる。`url_verification` には署名と時刻を確認したうえで challenge の値だけを返す。manifest 登録に失敗すると `failed` になり、秘密値を含まない `error` コードを返す。`checked_at` は状態が最後に変わった時刻(まだなければ null)である。

finalize 後も `pending` なら、Slack はまだこのアドレスを確認できていない。公開 DNS がまだアドレスを解決できないこともあれば、Slack が manifest で入れた URL を確認していないこともある。`POST /v1/agents/{id}/slack/app/events/recheck`(コンソールの Slack タブ **Slack アプリに入れるアドレス** の **再確認**)は manifest を Request URL とともにもう一度送る。それでも `pending` なら、Slack アプリ設定の Event Subscriptions 画面で Request URL の Verify(または Retry)を押す。コンソールの Slack タブは、アドレスを送った後 `pending` の間、同じ案内とその画面へのリンクを表示する。ローカルスタックで `scripts/slack-funnel.sh on` でアドレスを公開した場合は、最後の行の公開 DNS チェック(dns.google・cloudflare-dns.com)の警告が消えるまで待ってから Slack アプリを作成する。単一サーバーや Kubernetes の設置では、[アクセス経路](/run-server/self-hosting/access)で開いた公開 https アドレスが公開 DNS で解決できてから作成する。

`GET /v1/agents/{id}/slack/app/manifest` は現在のエージェントとサーバー設定から生成した `manifest_yaml` を返す。秘密値は含まない。

`GET /v1/agents/{id}/slack-channels?ids=C1,C2` は最大 50 個の ID の名前を返す。各 item は `id`・`name`・`state` を持ち、Slack が存在しないかアクセスできないと答えた ID だけ名前と状態が `unknown` になる。通信失敗・上位サーバーのエラーはキャッシュせずリクエスト全体が 503 になり、失効したか無効な bot token は 409 `SLACK_NOT_INSTALLED` になる。cursor と全件走査はない。アプリ・チャンネルごとに 60 秒キャッシュし、Slack 429 は `Retry-After` 付きの 503 になる。

`GET`・`PUT /v1/agents/{id}/slack/app/settings` は `{ "mention_only": true }` を読み書きする。`true` なら @メンションされたときだけ、`false` ならメンションがなくてもチャンネルへの投稿に応答する。どちらの値でも、エージェントがすでに会話中のスレッド(セッションにつながったスレッド)の返信は、メンションなしでそのセッションに続く。接続済みのチャンネルを含め、使用中のすべてのチャンネルに適用され、DM には適用されない。初期値は `true` で、アプリ作成前にも保存できる。アプリ全体のオン・オフは提供しない。

binding の `mode` は `off`(このチャンネルでは使わない)・`on`(使用中)である。`mention_only` が `false` なら、使用中のチャンネルで人がメンションなしでチャンネルに直接書いた投稿にもセッションを開く。エージェントが参加していないスレッドの返信には応答しない。

binding には聞く設定 `listen` もある。`free`(チャンネルのすべての投稿)・`mention`(メンションとエージェントが参加したスレッド)・`off`(聞かない)のいずれかである。今は保存と読み取りだけで、エージェントが何に応答するかは上の `mode` と `mention_only` が決める。新しく接続したチャンネルは `free` で始まる。この設定ができる前からあったチャンネルは、そのときのエージェントの `mention_only` に従い、`true` なら `mention`、`false` なら `free` になった。`PUT` で `listen` を省くと、そのチャンネルの値はそのまま残る。ほかの組織と共有したチャンネル(Slack Connect)は `listen` を `free` で保存できない(400、`external_shared_channel`)。`mention` と `off` は保存される。同じ Enterprise 内のワークスペース同士だけで共有したチャンネルはこれに当たらない。

binding の `m1_judgments_per_hour` は、そのチャンネルで 1 時間に判断できる数である。会話層の最初の判断(M1)はチャンネルの投稿をまとめて、エージェントが割り込むかを判断する。1 時間以内の判断がこの数に達したチャンネルの次のまとまりは、M1 を呼ばずに `rate_limited` として記録される。1 から 60 までの整数で、新しいチャンネルとこの設定ができる前からあったチャンネルは 12 で始まる。変えた値はそのチャンネルの次のまとまりから適用される。`PUT` で省くと、そのチャンネルの値はそのまま残る。コンソールでは Slack タブの**チャンネル**の**1時間の判断数**列で変える。

エージェントごとに自分の Slack アプリを持つ。接続には、アプリ id、チーム id、bot token が入った認証情報への参照の名前(`credential_ref`、値ではない)を送る。

```sh
curl -sS "$API/v1/agents/$AID/identities" "${WEB[@]}" \
  -d '{"provider": "slack_bot", "app_id": "A0APP", "team_id": "T0TEAM", "credential_ref": "slack/research-bot-token"}'
```

確認済みの Slack インストールがない場合は 409 `SLACK_NOT_INSTALLED` になる。インストールはコンソールの **Slack アプリを作成してインストール** が Slack の同意の後に作成する。手作業で作ったアプリは、運用者が[Slack インストールの登録](#slack-インストールの登録)で作成する。

Slack でアプリを削除すると連携は解除される。`app_uninstalled` イベント、または bot token を含む `tokens_revoked` イベントを受け取ると、インストールが `revoked` になり、そのインストール上の有効な連携も一緒に `revoked` になる(`revoked_at` が入る)。連携のチャンネル binding と認証情報の名前も解放される。コンソールの Slack タブは「接続済み」ではなく「再インストールが必要」を表示する。同じイベントが再度届いても、再インストールの後に遅れて届いても、状態は変わらない。再度インストールすると新しい有効な連携が作られ、以前の連携は解除済みの記録として残る。

Werft が作ったアプリを `DELETE /v1/workspaces/{id}/slack/apps/{app_id}`（コンソール: Slack タブの**危険な操作**の**アプリを削除**）で削除すると、Slack のイベントを待たずに Werft 側を 1 つの transaction ですべて閉じる。アプリのインストールとその有効な連携、チャンネル binding、まだ送っていない Slack メッセージ（`app_deleted` で取り消し）、そのエージェントが聞いていたチャンネルの判断バッファがまとめて閉じられ、保存済みの secret が削除される。1 つでも閉じられなければ何も閉じずにエラーで応答する。アプリは `deleting` のまま残り、同じリクエストでもう一度削除する。実行中のセッションは止めないが、そのセッションがこのアプリに送ろうとするメッセージは `app_deleted` で拒否される。セッションとターンの記録は残る。この削除は `delete_slack_app` receipt に、誰がどのアプリを削除したか、閉じた数、Slack 側の後片付けの結果を残す。トークンの値は残らない。

Werft 側がコミットされた後、Slack に bot token の失効（`auth.revoke`）とアプリの削除（`apps.manifest.delete`）を 1 回ずつだけ依頼する。Slack にもうないトークンやアプリは完了とみなす。どちらかが失敗しても削除は成功（`200`）で、応答の `slack_cleanup` が `failed` と失敗した手順（`failed_steps`）を知らせる。再試行はしないので、Slack のアプリ管理画面（api.slack.com/apps）でアプリを自分で削除する。その後 Slack が `app_uninstalled` や `tokens_revoked` を送っても何も変わらない。署名 secret はアプリと一緒に削除されるので、署名を確認できないリクエストには `401` で応答し、Slack が何度再送しても閉じた状態はそのままである。

イベントが届かない削除もある。bot token で Slack を呼ぶリクエスト(チャンネル一覧、名前の取得、チャンネル binding)が `token_revoked` または `account_inactive` で拒否された場合も、同じ解除を行う。応答は引き続き 409 `SLACK_NOT_INSTALLED` である。削除以外でも起こり得るエラー(`invalid_auth`、`not_authed`、`token_expired`)、429、5xx、通信失敗では状態を変えない。

### 判断の記録

`GET /v1/agents/{id}/slack/judgments`(コンソール: Slack タブの**判断の記録**)は、直近 7 日間に M1 がこのエージェントのチャンネルで判断した記録を表示する。今の M1 は shadow で判断するだけで、Slack には投稿しない。チャンネルごとに判断の数、そのうち `speak`(割り込む)の数、理由コードごとの数(`rate_limited` と `budget_refused` を含む)を数え、最新の判断 50 件を理由コードと Slack の投稿へのリンクで表示する。投稿の本文は Werft に残らないので、リンクを開いて Slack で読む。コンソールは判断に使ったエージェント指示も表示する。有効なリリースを作ったときにリポジトリから読んだ指示ファイルのリリースと commit で、リポジトリやファイルがない場合はその旨を知らせる。画面を開いたときにリポジトリの branch の先頭 commit を GitHub から読み(`GET /v1/agents/{id}/slack/instructions-head`)、その commit と違えば「リポジトリにより新しい指示があります。新しいリリースを作ると反映されます。」を添える。リリースを自動では作らず、GitHub を読めないときはこの案内だけを出さない。

見られるのはワークスペースの owner・admin とそのエージェントの管理者だけで、API キーでは読めない。非公開チャンネルの記録も、数・一覧・メッセージのリンクまで、そのチャンネルのメンバーかどうかに関係なく見える。どのチャンネルもメッセージ本文はなく、リンクは Slack でそのメッセージを読める人にだけ開く。

判断が多すぎたり少なすぎたりするときは、チャンネルの聞く設定、1 時間あたりの判断の上限、リポジトリのエージェント指示(AGENTS.md)で調整する。

## ほかのボットのメンション

エージェントは人だけでなく、ほかのボットのメンションにも応答できる。受け付けるのは、エージェント管理者がコンソールの Slack タブの **基本 > 応答するボット** で選んだボットだけだ。初期値は空のリストで、空のあいだは従来どおりすべてのボットのメッセージを無視する。

- 選べるのは、エージェントをインストールした Slack ワークスペースのボットだけで、最大 20 件。エージェント自身のボット、同じ Werft にあるほかのエージェントのボット、Slack Connect で入ってきたほかのチームのボットは選べない。エージェント同士は Slack のメンションで呼び合わない。
- ワークスペースが大きく Slack の一覧を最後まで読めなかったときは、選択画面にその案内と **Slack ユーザー ID で追加** 欄が出る。入れた ID はそのワークスペースの有効なボットのときだけすぐ保存され、そうでなければ理由を 1 行で示す。
- 選んだボットがチャンネルやスレッドでエージェントを直接 @メンションしたときだけ応答する。メンションのないボットの投稿と DM は常に無視する。エージェント自身のアプリの投稿(エージェントの返答、Web コンソールから人の名前で送った指示)は、許可リストにかかわらず最初に捨てる(捨てた理由 `own_bot_user`)。Slackbot(`USLACK`)の投稿は DM でもチャンネルでも捨てる(捨てた理由 `slackbot`)。同じ Werft のほかのエージェントのボットの投稿は、リストに残っていても捨てる(捨てた理由 `werft_agent_bot`)。それ以外のボットの投稿を捨てた理由は、許可リストが空なら `bot_allowlist_empty`、送ったボットがリストにないなら `bot_not_allowed`、リストのボットでも DM か直接のメンションでなければ `bot_message` である。
- 選んだあとで Slack から削除・無効化されたボットは、リストに **Slack から削除済み** として残り、そのメンションは無視する。リストから外すことはできるが、選び直すことはできない。
- ボットが始めたセッションには開始した人がいない。エージェントの API キーで始めたセッションと同じだ。人がそのスレッドで続けてもセッションの持ち主は変わらず、セッションの記録には始めたボットの Slack ユーザー ID が残る(`requester_kind` が `slack_bot`)。ボットが始めたターンはエージェントとワークスペースの接続だけを使い、個人の接続は使わない。セッションのコスト上限にも数える。
- 1 つの Slack スレッドで、人を挟まずにボットが始めたターンが 5 回続くと止まる。6 回目のメンションを受けたエージェントがそのスレッドに `人を挟まずにボット同士で5回やり取りしたため、ここで止まります。続きは人が進めてください` を 1 回だけ残し、その後のボットのメンションは何も言わずに無視する。回数はスレッドごとに数え、どのエージェントが応答したかにかかわらず合算する。人がそのスレッドに書き込むと 0 に戻る。時間が経っても戻らない。

`GET /v1/agents/{id}/slack/app/bots` は `items` と `truncated` を返す。各項目に `user_id`・`name`・`state`(`active`・`gone`)・`allowed` があり、`truncated` が `true` なら Slack の一覧を最後まで読めなかったことを示す。`PUT` は `{ "allowed_user_ids": ["U0..."] }` でリスト全体を置き換え、エージェント管理者が Web セッションで呼ぶ。新しく加える ID を受け付けられなければ 400 で、`details.reason_code` が理由を示す: `slack_bot_own`(エージェント自身のボット)、`slack_bot_werft_agent`(同じ Werft のほかのエージェントのボット)、`slack_bot_other_team`(ほかのチームのボット)、`slack_bot_unknown`(有効なボットではない)。`details.user_ids` にその理由で拒否した ID が入る。アプリがインストールされていなければ 409 `SLACK_NOT_INSTALLED`、Slack の 429 は `Retry-After` 付きの 503 になる。

テストと復旧では、データベースに触れる運用者が API コンテナーで([運用者コマンドの実行](#運用者コマンドの実行)) `bun run apps/control-host/src/api/slack-app.ts list-bots --agent <agent_id>`、`allow-bot --agent <agent_id> --bot <bot_user_id>`、`disallow-bot --agent <agent_id> --bot <bot_user_id>` を使える。普段はコンソールで変更する。`allow-bot` は上と同じ検査(`slack_bot_own`・`slack_bot_werft_agent`・`slack_bot_other_team`・`slack_bot_unknown`)を通し、拒否すると終了コード 10 で終わる。リストが変わると `by` が `operator_cli` の receipt `set_slack_allowed_bots` が残る（コンソールで変えた場合は `by` が `web` で、`actor` が変えたユーザー）。すでに許可した Bot をもう一度許可しても、許可していない Bot を外しても、何も変わらず receipt も残らない。API は引き続き Web セッション専用で、API キーでは開かない。

## チャンネル参加とデプロイの歓迎メッセージ

エージェントのチャンネル(`PUT /v1/agents/{id}/slack-bindings`)を保存すると、サーバーが bot をそのチャンネルに入れる。公開チャンネルには bot が自分で参加する。非公開チャンネルは Slack が bot の自己参加を許さないので、チャンネルで `/invite @<bot>` で招待する。招待されるとサーバーが検知して続きを進める。結果は binding の `membership.state` に出る。保存していないチャンネルに bot を招待した場合も、サーバーがそのチャンネルを使用中(`on`)で接続する。保存済みのチャンネルは設定を変えない(オフにしたチャンネルはオフのまま)。

エージェントがチャンネルに書いた返信は、そのチャンネルの全員が読む。担当チーム外の人も、ワークスペース設定でそのセッションをコンソールで見られない人も含まれる。コンソールのチャンネル欄にもそう書いてある。

| `membership.state` | 意味 |
| --- | --- |
| `joined` | bot がチャンネルにいる |
| `awaiting_invite` | 非公開チャンネルで、招待を待っている |
| `config_error` | Slack が token か scope を拒否した(`error` に Slack のエラーコード)。アプリを再インストールする |
| `join_failed` | アーカイブ済みのチャンネルか、ワークスペースのポリシーが拒否した(`error`) |

release が初めてデプロイされると、home チャンネルに`안녕하세요, <エージェント名>입니다. 이 채널에 연결됐어요. 멘션하면 답할게요`(既定は韓国語)が届く。この挨拶はエージェントごとに、チャンネルあたり一度だけ。新しい release のデプロイ、同じ定義の再提出、前の release へのロールバック、Slack 連携の切断と再接続のどれでも、挨拶済みのチャンネルには送らない。home をまだ挨拶していないチャンネルに移すと、そのチャンネルに一度届く。bot が home にまだいなければ、入るまで待つ。歓迎メッセージや参加が失敗してもデプロイは失敗しない。

## チャンネルのアーカイブ・名前変更・削除

エージェントのアプリは、チャンネルのアーカイブ(`channel_archive`・`group_archive`)、アーカイブ解除(`channel_unarchive`・`group_unarchive`)、名前変更(`channel_rename`・`group_rename`)、削除(`channel_deleted`・`group_deleted`)のイベントを受け取る。`channel_*` は公開チャンネル、`group_*` は非公開チャンネルのものだ。アプリがすでに持つ scope で届くイベントなので、新しい scope はない。Slack のドキュメントでは、すでに持つ scope のイベントを追加するのに再インストールは要らない。これらのイベントより前に作ったアプリには、API の起動時に manifest を自動で送り直す。起動のたびに各アプリの manifest を Slack から読み(`apps.manifest.export`)、bot イベントだけが違えば manifest 全体を送り、bot scope が違うか、アプリに user scope があれば送らない。結果は `GET /v1/agents/{id}/slack/app` の `manifest_sync` に残る。`error` が null でなければ、コンソールの Slack タブのアプリ欄に「更新が必要」と理由が出る。理由は `config_token_inactive`(有効な App Configuration Token がなく、読みも送りもしない)、`events_url_unset`、`slack_refused`、`no_answer` だ。次の起動か **再確認**(`POST /v1/agents/{id}/slack/app/events/recheck`)がもう一度試し、その間に自動の再試行はない。複数の API レプリカが同時に起動しても、1 つのアプリは 10 分以内に 1 回だけ確認する。コンソールを使わずに送るには、API コンテナーで([運用者コマンドの実行](#運用者コマンドの実行)) `bun run apps/control-host/src/api/slack-app.ts finalize --agent <agent_id>` を実行する。送り直した manifest がインストールにない scope を求め、Slack が権限が変わったと答えた場合は、再確認の応答(`reinstall_required: true`)とコンソールの案内がアプリの再インストールを求める。

チャンネルがほかの組織と共有されたとき、共有が終わったときに届く `channel_shared`・`channel_unshared` も受け取る。アプリがすでに持つ `channels:read`・`groups:read` で届くイベントなので再インストールは要らず、これらのイベントより前に作ったアプリは上と同じく再確認で受け取るようになる。イベントが届く前でも、共有されているかはチャンネルの投稿が届いたときに Slack に問い合わせて知る。

- アーカイブ・アーカイブ解除・名前変更は、そのチャンネルの会話に状態(`active`・`archived`)と新しい名前だけを記録する。チャンネルの binding と、受け取り・返答は変わらない。
- チャンネルが削除されると、その binding は `gone` になる。binding は消さずに残し、そのチャンネルの投稿は受け取らず、そのチャンネルへは何も送らない。home だった場合は home が外れ、承認も消える。会話には `deleted` が記録される。コンソールのチャンネル一覧には「削除済み」と表示される。そのチャンネルのチャンネル要約も、すべてのバージョンの履歴と一緒に削除する。要約はチャンネルにいるエージェントが共有する一つだけなので、エージェントごとに届く削除イベントのうち最初のものが削除し、残りは削除するものがない。関与記録と会話はセッションの保持に従って残る。アーカイブでは要約を削除しない。
- 削除イベントを取りこぼしても、投稿やチャンネルの参照に Slack が `channel_not_found` を返せば、公開チャンネルの binding は `gone` になる。Slack は bot がいない非公開チャンネルにも `channel_not_found` を返し、削除と bot の除外を区別できないため、bot が入っていた非公開チャンネルは `left` にする(`group_left` を取りこぼした場合と同じ)。招待待ちや承認待ちの非公開チャンネルはそのままにする。429、Slack の障害、token のエラーでは状態は変わらない。`channel_not_found` ではチャンネル要約を削除しない。bot が再び参加すれば戻る判定だからだ。
- `gone` のチャンネルに bot が再び参加すると(`member_joined_channel`)、公開チャンネルは使用中に、非公開チャンネルは承認待ちに戻る。その間に非公開へ変わった公開チャンネルは、非公開チャンネルとして承認を待つ。
- 4 種類とも、そのチャンネルのメンバー確認キャッシュを消す。

## Slack で削除されたメッセージ

Slack で削除されたメッセージ（返信のあるメッセージを削除した墓標を含む）が指示のターンは、Web コンソールと API で隠れる。そのターンの指示、エージェントの返答、ツールが読んで返した文は「Slack で削除済み」と表示され、ツールの名前と削除された時刻は残る。監査閲覧でも同じである。最初のメッセージから切り出した・生成したセッションのタイトルも隠れ、人が付けたタイトルはそのまま残る。同じセッションの後のターンのように、そのメッセージを引き継いだだけのターンは隠さない。保存された内容は消さず、読むときに隠す。
