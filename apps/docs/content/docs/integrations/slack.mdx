| 지금 있는 것 | API | 누가 |
| --- | --- | --- |
| 내 Slack 계정을 웹 계정에 연결 | `POST /v1/linked-accounts/slack/start`, `…/callback`, `GET /v1/linked-accounts`, `DELETE /v1/linked-accounts/{id}` | 로그인한 본인 |
| 에이전트에 Slack 앱(bot) 연결 | `POST`·`GET /v1/agents/{id}/identities`, `DELETE …/identities/{identity_id}` | owner·admin·그 에이전트 관리자 |
| guest의 에이전트 사용 허용 | `POST /v1/workspaces/{id}/slack-guest` | owner·admin |

셋 다 웹 로그인 cookie로만 부른다. API key는 403이다. 아래 예제는 [만들기](/agents/create#로그인)의 `WEB` 헤더와 `WS`를 쓴다.

## guest 사용 설정

Slack guest(멀티·단일 채널 guest)가 에이전트를 쓸 수 있는지 정한다. 기본은 꺼짐이다.

```bash
WS=$(curl -sS "$API/v1/auth/me" "${WEB[@]}" | jq -r .workspace.id)
curl -sS "$API/v1/workspaces/$WS/slack-guest" "${WEB[@]}" \
  -d '{"slack_guest_enabled": true}' | jq .
```

```text
{
  "slack_guest_enabled": true
}
```

켜도 guest는 자기 Slack 계정을 연결해야 쓴다. Slack Connect로 들어온 다른 회사 사용자는 이 설정과 상관없이 쓸 수 없다.

## Slack 계정 연결

Sign in with Slack(OpenID Connect)으로 연결한다. 운영자가 콘솔의 공개 주소 `CONSOLE_ORIGIN`을 설정하고, 워크스페이스 어드민이 설정 > 워크스페이스 > 연동 > Slack에 App Configuration Token을 넣어 계정 연결용 앱을 만들 수 있게 하며, 그 워크스페이스에 확인된 Slack 설치가 있어야 한다. 로컬 스택에는 `CONSOLE_ORIGIN`이 없어서 시작 요청이 503이다. API가 Slack에 보내는 요청과 id_token 검사는 로그인 공급자와 같다. Slack 주소는 https여야 하고, loopback·link-local·reserved 주소로 풀리면 보내지 않고 503으로 끝난다. id_token은 `exp`·`iat`·`sub`가 있어야 하고, `iat`는 앞으로 60초, 뒤로 11분까지만 받는다.

```bash
curl -sS -o /dev/null -w '%{http_code}\n' -X POST "$API/v1/linked-accounts/slack/start" "${WEB[@]}"
```

```text
503
```

설정된 설치에서는 시작 요청이 `authorize_url`을 돌려준다. 그 주소에서 Slack에 동의하면 웹의 연결 화면이 `code`와 `state`를 callback에 넘기고 연결이 끝난다. 시작한 브라우저에서 10분 안에 끝내야 한다. 시간이 지났거나 다른 브라우저에서 이어 가면 `400`이고, 처음부터 다시 시작한다. 연결 상태는 `active`·`stale`·`revoked`다.

연결 응답과 `GET /v1/linked-accounts`의 각 항목에는 Slack이 연결 때 알려 준 이름도 있다. `external_user_name`은 Slack 표시 이름(id_token의 `name`), `external_tenant_name`은 Slack 워크스페이스 이름(`https://slack.com/team_name`)이다. 다시 연결하면 새 이름으로 바뀐다. 이름을 저장하기 전에 만든 연결이나 Slack이 이름을 주지 않은 연결은 `null`이고, 웹 화면은 그때 ID를 보인다. Slack 토큰은 저장하지 않는다. 그래서 provider 토큰의 만료 시각인 `expires_at`은 Slack 연결에서 늘 `null`이다. 시작 응답의 `expires_at`은 연결 요청이 유효한 시각이라 이 값과 다르다.

| 응답 | 뜻 |
| --- | --- |
| 409 `SLACK_NOT_INSTALLED` | 이 워크스페이스에 확인된 Slack 설치가 없다 |
| 409 `LINK_TEAM_MISMATCH` | 설치되지 않은 Slack 팀의 계정이다 |
| 409 `LINK_TAKEN` | 그 Slack 계정이 다른 사람에게 연결돼 있다 |
| 409 `LINK_EXISTS` | 같은 팀에 내 연결이 이미 있다 |

계정 연결용 앱이 없으면 첫 연결 시작이 그 자리에서 앱을 만든다. Slack의 생성 응답을 잃으면(시간 초과, 연결 끊김, 저장 실패) 앱이 만드는 중으로 남고, 그 뒤의 연결 시작은 모두 `409 SLACK_APP_CREATING`이다. 60초가 지나면 `details.uncertain: true`가 붙는다. 그때 api.slack.com/apps에서 그 시각에 만들어진 앱을 확인해 지우고, API 컨테이너에서 다음을 실행해([운영자 명령 실행](#운영자-명령-실행)) 잃어버린 생성을 포기하고 새로 만든다. 출력은 JSON 한 줄이다. 종료 코드 `6`은 앱이 아직 만드는 중(60초 전)이거나 지우는 중이라는 뜻이다.

```bash
bun run apps/control-host/src/api/slack-app.ts create --kind link --workspace "$WORKSPACE_ID" --replace-uncertain
```

## 알림 언어

플랫폼이 Slack에 쓰는 안내 문구(거절 안내, 실패·답변 대기 안내, `웹에서 열기` 링크, 웹·API로 보낸 지시의 `(웹 콘솔)` 표시)는 사용자가 웹 콘솔의 **언어·테마**에서 고른 언어(한국어·日本語·English)를 따른다. 콘솔이 고른 언어를 서버에 저장한다(`PATCH /v1/auth/me`). 저장한 언어가 없는데 콘솔이 영어가 아닌 언어로 열리면(브라우저 언어 등) 그 언어를 저장해, 콘솔과 Slack의 언어를 맞춘다.

- 한 사람에게만 보이는 거절 안내는 그 Slack 계정에 연결된 사용자의 언어로 쓴다.
- 스레드에 올라가는 안내와 지시 표시는 세션을 시작한 사용자의 언어로 쓴다. 스레드는 여러 사람이 함께 보므로 한 언어로 맞춘다.
- 언어를 저장한 적 없는 사용자와 연결되지 않은 Slack 계정은 영어로 받는다.

모델이 쓴 답변과 사용자가 입력한 내용은 번역하지 않는다. 배포 환영 메시지는 받는 사람이 정해지지 않아 한국어로 보낸다.

## 승인과 답변

Slack 스레드에서 시작한 세션이 사람을 기다리면, 기다리는 요청마다 그 스레드에 카드가 하나 올라온다. 세션을 시작한 사람을 멘션하고, 웹에서 같은 요청을 여는 링크와 만료 시각을 함께 보인다. 카드는 게시할 때 세션을 시작한 사람의 언어([알림 언어](#알림-언어))로 쓰고, 처리한 뒤에도 그 언어를 유지한다.

도구 권한 카드는 무엇을 하려는지 한 줄로 요약해 보인다. 예를 들어 `명령 실행: bun test`, `파일 수정: src/app.ts`, `PR 열기: 제목 (브랜치)` 같은 식이다. 파일을 쓰거나 고치는 도구는 요약 아래에 쓸 내용의 앞 세 줄을 함께 보인다. 모델이 넘긴 입력 원본은 **입력 원본** 아래에 접혀 있어, 펼쳐야 보인다. 원본은 필드마다 `이름: 값`으로 보이고, 값 안의 줄바꿈은 `\n`이 아니라 실제 줄바꿈으로 보인다. 긴 원본은 잘리므로 전체는 **웹에서 열기**로 본다. push 승인 카드도 저장소·브랜치·커밋을 먼저 보이고, 나머지는 **자세히** 아래에 접어 둔다. 모델이 쓴 글은 어디에서도 멘션이나 링크가 되지 않는다.

| 요청 | 카드에서 하는 일 |
| --- | --- |
| 도구 권한 | **허용**·**지시와 함께 허용**·**거부**. **지시와 함께 허용**은 지시를 적는 창을 연다. 보내면 허용과 함께 그 지시가 모델에 전해진다. 지시는 8 KiB까지이고, 비어 있으면 창에 오류가 보인다. 세션이 지시를 모델에 전할 수 없으면 허용하지 않는다. 그 이유는 누른 사람에게만 보이는 메시지로 알리고, 요청은 열린 채 남는다. 처리된 카드는 그냥 허용한 카드와 같고, 지시 내용은 스레드에 보이지 않는다. 엔진이 되풀이해서 묻는 규칙을 제안했으면 **이 세션 동안 허용**이 더해진다. 규칙은 카드와 확인 창에 보인다. 리다이렉션·파이프·복합 명령처럼 제안된 규칙이 그 호출을 덮지 못할 수 있는 Bash 호출에는 버튼을 내지 않는다. 누르면 이 세션이 끝날 때까지 그 규칙에 맞는 호출을 묻지 않는다. 처리된 카드는 `이 세션 동안 허용됨`이 된다. push 승인과 서버 허용 목록은 이 버튼으로 바뀌지 않는다. 버튼은 엔진이 그 호출을 덮는 규칙을 제안할 때만 붙는다. `auto` 모드 release(새로 만든 Claude 모델 release)는 규칙 밖 호출을 분류기가 판정하므로 카드는 대개 묻기 목록에 걸린 호출이고, 지금 그런 카드에는 이 버튼이 나오지 않는다. 묻기 목록의 호출은 매번 사람이 답하는 것으로 둔다. 이 규칙 전에 만든 Claude 모델 release와, `auto` release의 세션이 Claude가 아닌 모델로 옮긴 경우는 `default`로 돈다. `default` 모드에서 작업 공간 규칙 밖의 호출을 물을 때는 버튼이 나올 수 있다. Codex 연결의 release에는 나오지 않는다([권한 모드](/agents/permissions#권한-모드)) |
| 질문 | 질문 하나에 선택지가 5개 이하면 선택지 버튼, 직접 입력할 수 있으면 **직접 입력**. 그 밖에는 **답하기**를 눌러 열리는 창에서 답한다. 질문이 10개를 넘거나 한 질문의 선택지가 100개를 넘으면 Slack 창에 담을 수 없어, 카드는 "이 요청은 웹에서 답해 주세요"와 **웹에서 열기** 버튼만 보인다 |
| push 승인 | 저장소·브랜치·커밋을 보고 **승인**(한 번 더 확인)·**거절** |

누른 사람은 Slack 계정이 웹 계정에 연결돼 있어야 하고([Slack 계정 연결](#slack-계정-연결)), 웹에서 그 세션의 요청에 답할 수 있는 사람이어야 한다. 웹과 같은 규칙으로 판단한다. 연결되지 않은 계정에는 연결 페이지 링크를, 권한이 없는 사람에게는 거절 안내를 그 사람에게만 보이고 아무것도 처리하지 않는다.

처리되면 카드에서 버튼이 사라지고 결과가 남는다. Slack에서 누르든 웹에서 답하든 같다. 웹에서 답했거나, 요청이 만료됐거나, 세션이 끝나 요청이 닫혔으면 control-host 안의 action-broker가 잠시 뒤 Slack 카드를 같은 모양으로 고친다. 첫 줄은 결과와 처리한 사람이다. Slack에서 처리했으면 `허용됨 · @이름`, 웹에서 처리했으면 `웹에서 허용됨 · @이름`처럼 어디서 처리했는지가 함께 보인다. 처리한 사람의 Slack 계정이 연결되지 않았으면 이름 없이 결과만 보인다. 도구 권한과 push 카드는 이 결과에 요청 요약과 웹 링크를 붙인 한 줄이 된다. 질문 카드는 질문 전문을 그대로 두고, 그 아래에 고른 답을 `<선택지> 선택됨`(웹에서 답했으면 `웹에서 <선택지> 선택됨`)으로 보인다. 직접 입력한 글은 내용 없이 `직접 입력`으로만 표시한다. 스레드는 여러 사람이 보기 때문이다. 만료됐거나 세션이 끝나 닫힌 요청은 아무도 멘션하지 않는다. 질문 카드는 질문을 남긴 채, 만료됐으면 `만료됨`을, 세션이 끝나 닫혔으면 `더 이상 답할 수 없어요`를 보인다. Slack이 카드를 고치지 못하면 잠시 뒤 다시 시도하고, 메시지가 지워졌거나 채널이 보관됐으면 그대로 둔다. 카드는 누른 메시지가 아니라 저장된 요청에서 다시 그린다. 웹이나 다른 사람이 먼저 처리한 요청을 누르면 다시 처리하지 않고 지금 결과로 카드를 바꾼다. push를 Slack에서 승인·거절하면 그 결과를 세션에 알리는 지시가 이어져, 세션이 PR을 열거나 거절을 알린다. 승인할 때 세션의 턴이 돌고 있으면 그 지시는 그 턴이 끝날 때까지 기다리고, 그 턴이 PR을 이미 열었으면 넣지 않는다. 그 브랜치에 PR이 이미 있어도 넣지 않는다. 그래서 같은 PR을 두 번 열거나 같은 답을 두 번 하지 않는다.

버튼과 창은 에이전트 앱의 Interactivity 주소 `/v1/slack/interactions/{agent_id}`로 온다. 요청은 이벤트와 같이 그 앱의 signing secret 서명과 300초 안의 시각을 확인한다. 설치 finalize가 Event Subscriptions 주소와 함께 manifest에 넣는다. 이 기능 전에 만든 앱은 **다시 확인**(`POST /v1/agents/{id}/slack/app/events/recheck`)으로 manifest를 다시 보내면 등록된다.

## 원래 Slack 메시지 링크

Slack 멘션·DM·스레드 답글로 시작하거나 보낸 지시는 그 Slack 메시지의 위치(팀·채널·`ts`, 답글이면 `thread_ts`)와 Slack이 준 링크를 함께 남긴다. 링크는 `chat.getPermalink`로 받고, 이 호출에는 scope가 더 필요 없다. 웹 세션 화면은 머리의 시작한 사람·경로 옆과 대화의 Slack 지시 말풍선에 **Slack에서 보기** 링크를 보이고, 누르면 새 탭에서 열린다. API에서는 세션의 `slack_permalink`(세션을 시작한 메시지)와 turn의 `slack_permalink`(그 지시를 보낸 메시지)로 읽는다.

비공개 채널과 DM도 링크만 남기고 메시지 본문을 더 저장하지 않는다(지시로 받은 글은 원래대로 turn의 `message`에 있다). 링크는 Slack에서 그 메시지를 읽을 수 있는 사람에게만 열린다. 링크를 남기기 전에 만든 세션·지시, Slack이 링크를 주지 않은 지시는 `null`이고 화면에 링크가 없다.

## 운영자 명령 실행

이 페이지의 운영자 명령(`slack-app.ts`, `slack-install.ts`)은 api 이미지 안에 있고, api 컨테이너의 DB 설정으로 그 설치의 DB에 붙는다. 호스트에 저장소 checkout이나 Bun은 필요 없다. 설치 방식마다 api 컨테이너에서 이렇게 실행한다. 예시는 `list-bots`다.

[단일 서버 설치](/run-server/self-hosting/single-server)(test-ops 번들)에서는 이 설치의 compose project label로 api 컨테이너를 찾는다. `werft-test-ops`는 `TEST_OPS_PROJECT`의 기본값이니, 다른 값으로 설치했으면 그 값으로 바꾼다. 컨테이너 id가 한 줄 나와야 한다.

```bash
API_CONTAINER="$(docker ps -q --filter label=com.docker.compose.project=werft-test-ops --filter label=com.docker.compose.service=api)"
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/slack-app.ts list-bots --agent <agent_id>
```

## Slack 설치 등록

보통은 이 등록이 필요 없다. 콘솔의 **Slack 앱 만들고 설치**([콘솔에서 Slack 연결](/integrations/slack-console))가 에이전트의 앱을 만들고, Slack 동의가 끝나면 확인된(`verified`) 설치를 남긴다. 이 CLI는 Slack에서 손으로 만들어 워크스페이스에 설치한 앱을 운영자가 터미널에서 등록하는 경로다. 그 앱의 bot token으로 설치를 등록한다. CLI가 Slack의 `auth.test`·`bots.info`로 팀, bot 사용자, 앱을 확인하고 확인된 설치를 남긴다. 앱에는 bot scope `users:read`가 있어야 한다. token은 환경 변수 `SLACK_BOT_TOKEN`으로만 넘긴다. CLI는 token을 인자로 받지 않고 출력하지도 않는다. 아래 명령은 token을 화면에 보이지 않게 읽고, 명령 인자에 넣지 않은 채 api 컨테이너에 넘긴다.

단일 서버 설치(test-ops 번들)에서는 [운영자 명령 실행](#운영자-명령-실행)처럼 api 컨테이너를 찾고, `docker exec -e`로 셸의 값을 넘긴다.

```bash
API_CONTAINER="$(docker ps -q --filter label=com.docker.compose.project=werft-test-ops --filter label=com.docker.compose.service=api)"
read -rs SLACK_BOT_TOKEN && export SLACK_BOT_TOKEN
docker exec -e SLACK_BOT_TOKEN "$API_CONTAINER" \
  bun run apps/control-host/src/api/slack-install.ts register --workspace "$WS" --app-id A0123ABCD
unset SLACK_BOT_TOKEN
```

Kubernetes에서는 `kubectl exec`에 환경 변수를 넘기는 옵션이 없으니 token을 stdin으로 넘기고, 컨테이너 안의 셸이 그 줄을 `SLACK_BOT_TOKEN`으로 읽는다.

```bash
read -rs SLACK_BOT_TOKEN
printf '%s\n' "$SLACK_BOT_TOKEN" | kubectl -n werft exec -i deploy/werft-api -c api -- sh -c \
  'IFS= read -r SLACK_BOT_TOKEN && export SLACK_BOT_TOKEN && exec bun run apps/control-host/src/api/slack-install.ts register --workspace "$1" --app-id "$2"' \
  sh "$WS" A0123ABCD
unset SLACK_BOT_TOKEN
```

로컬 스택에서는 checkout의 package script를 쓴다.

```bash
read -rs SLACK_BOT_TOKEN && export SLACK_BOT_TOKEN
bun run slack-install register --workspace "$WS" --app-id A0123ABCD
unset SLACK_BOT_TOKEN
```

## 에이전트의 Slack 앱

### 앱 설정 읽기

에이전트 관리자(owner·admin 포함)가 웹 세션으로 호출한다. `GET /v1/agents/{id}/slack/app`은 앱과 함께 `event_url`과 `events`를 반환한다. `event_url`은 서버가 콘솔의 공개 주소 `CONSOLE_ORIGIN`에서 계산한 https 주소에 `/v1/slack/events/{agent_id}`를 붙인 절대 주소이며, 이벤트 입구를 콘솔과 따로 둔 서버는 owner가 **설정 > 연동 > Slack**의 "이벤트 입구 주소"에 저장한 주소(`PUT /v1/slack-settings`)를 쓴다. 계산할 수 없으면 null이다. owner가 이벤트 입구 주소를 바꿔 저장하면(비워서 `CONSOLE_ORIGIN` 주소로 돌아갈 때도) 모든 워크스페이스의 `created` 에이전트 앱에 새 주소를 넣은 manifest를 다시 확인처럼 보낸다. 한 워크스페이스의 앱은 하나씩 보내고, Slack의 `Retry-After`는 기다리지 않는다. 응답의 `updates`가 앱마다 `updated`(새 권한까지 받았으면 `reinstall_required: true`)나 `failed`와 이유(`config_token_inactive`·`events_url_unset`·`slack_refused`·`no_answer`)를 알리고, 같은 이유가 그 앱의 `manifest_sync`에 남아 Slack 탭에 "갱신 필요"로 보인다. 보내지 못한 앱은 예전 주소를 그대로 쓰고, `POST /v1/slack-settings/retry`(콘솔의 **보내지 못한 앱 다시 보내기**)로 다시 보낸다. `events.state`는 `pending`·`verified`·`failed`다. 설치 finalize가 manifest에 이 주소를 Request URL로 넣으면 `pending`이 되고 `events.url`에 보낸 주소가 남는다(보내기 전에는 null). 이미 `verified`인 앱은 주소를 다시 넣어도, 주소가 바뀌어도 `verified`를 유지한다. Slack은 manifest 갱신으로 바뀐 Request URL을 다시 확인하지 않고 확인된 상태로 두기 때문이다. 바뀐 주소의 갱신을 Slack이 거절하면 `failed`가 된다. 그 앱의 signing secret으로 서명된 요청(`url_verification` 또는 이벤트)이 처음 도착하면 `verified`가 된다. `url_verification`에는 서명과 시각을 확인한 뒤 challenge 값만 돌려준다. manifest 등록이 실패하면 `failed`가 되고 비밀 값 없는 `error` 코드가 온다. `checked_at`은 상태가 마지막으로 바뀐 시각(아직 없으면 null)이다.

finalize 뒤에도 `pending`이면 Slack이 아직 이 주소를 확인하지 못한 것이다. 공개 DNS가 주소를 아직 풀지 못했을 수도 있고, Slack이 manifest로 넣은 URL을 확인하지 않았을 수도 있다. `POST /v1/agents/{id}/slack/app/events/recheck`(콘솔 Slack 탭 **Slack 앱에 넣을 주소**의 **다시 확인**)는 manifest를 Request URL과 함께 다시 보낸다. 그래도 `pending`이면 Slack 앱 설정의 Event Subscriptions 화면에서 Request URL의 Verify(또는 Retry)를 누른다. 콘솔의 Slack 탭은 주소를 보낸 뒤 `pending`인 동안 같은 안내와 그 화면 링크를 보여 준다. 로컬 스택에서 `scripts/slack-funnel.sh on`으로 주소를 열었다면, 마지막 줄의 공개 DNS 점검(dns.google·cloudflare-dns.com)에서 경고가 사라질 때까지 기다린 뒤 Slack 앱을 만든다. 단일 서버나 Kubernetes 설치에서는 [접속 경로](/run-server/self-hosting/access)로 연 공개 https 주소가 공개 DNS에서 풀린 뒤 만든다.

`GET /v1/agents/{id}/slack/app/manifest`는 현재 에이전트와 서버 설정으로 만든 manifest를 `manifest_yaml`로 반환한다. 비밀 값은 포함하지 않는다.

`GET /v1/agents/{id}/slack-channels?ids=C1,C2`는 최대 50개 ID의 이름을 조회한다. `items`에는 `id`·`name`·`state`가 있고 Slack이 없거나 접근할 수 없다고 답한 ID만 이름과 상태가 `unknown`이다. 통신 실패·상위 서버 오류는 캐시하지 않고 요청 전체가 503이며, 회수됐거나 유효하지 않은 bot token은 409 `SLACK_NOT_INSTALLED`다. cursor와 전체 스캔은 없다. 앱·채널별 60초 캐시를 쓰며 Slack 429는 `Retry-After`를 포함한 503이다.

`GET`·`PUT /v1/agents/{id}/slack/app/settings`는 `{ "mention_only": true }`를 읽고 저장한다. `true`면 @멘션했을 때만, `false`면 멘션 없이 채널에 쓴 글에도 반응한다. 어느 값이든 에이전트가 이미 대화 중인 스레드(세션이 연결된 스레드)의 답글은 멘션 없이도 그 세션으로 이어진다. 이미 연결된 채널을 포함해 사용 중인 모든 채널에 적용되고, DM에는 적용되지 않는다. 초기값은 `true`이며 앱 생성 전에도 저장할 수 있다. 앱 전체 켜기·끄기는 제공하지 않는다.

binding의 `mode`는 `off`(이 채널에서 쓰지 않음)·`on`(사용)이다. `mention_only`가 `false`면 사용 중인 채널에서 사람이 멘션 없이 채널에 바로 쓴 글에도 세션을 연다. 에이전트가 참여하지 않은 스레드의 답글에는 반응하지 않는다.

binding에는 듣기 설정 `listen`도 있다. `free`(채널의 모든 글)·`mention`(멘션과 에이전트가 참여한 스레드)·`off`(듣지 않음) 가운데 하나다. 지금은 저장하고 읽기만 하며, 에이전트가 무엇에 반응하는지는 위의 `mode`와 `mention_only`가 정한다. 새로 연결한 채널은 `free`로 시작한다. 이 값이 생기기 전부터 있던 채널은 그때 에이전트의 `mention_only`를 따라 `true`면 `mention`, `false`면 `free`가 됐다. `PUT`에서 `listen`을 빼면 그 채널의 값을 그대로 둔다. 다른 조직과 공유한 채널(Slack Connect)은 `listen`을 `free`로 저장할 수 없다(400, `external_shared_channel`). `mention`과 `off`는 저장된다. 같은 Enterprise 안의 워크스페이스끼리만 공유한 채널은 여기에 들지 않는다.

binding의 `m1_judgments_per_hour`는 그 채널에서 한 시간에 판단할 수 있는 수다. 대화 계층의 첫 판단(M1)이 채널 글을 묶어 에이전트가 끼어들지 판단하는데, 한 시간 안의 판단이 이 수에 닿은 채널의 다음 묶음은 M1을 부르지 않고 `rate_limited`로 기록된다. 1에서 60 사이의 정수이고, 새 채널과 이 값이 생기기 전부터 있던 채널은 12로 시작한다. 바꾼 값은 그 채널의 다음 묶음부터 적용된다. `PUT`에서 빼면 그 채널의 값을 그대로 둔다. 콘솔에서는 Slack 탭 **채널**의 **시간당 판단** 칸에서 바꾼다.

에이전트마다 자기 Slack 앱을 갖는다. 연결에는 앱 id, 팀 id, bot token이 든 자격 참조의 이름(`credential_ref`, 값이 아니다)을 보낸다.

```sh
curl -sS "$API/v1/agents/$AID/identities" "${WEB[@]}" \
  -d '{"provider": "slack_bot", "app_id": "A0APP", "team_id": "T0TEAM", "credential_ref": "slack/research-bot-token"}'
```

확인된 Slack 설치가 없으면 409 `SLACK_NOT_INSTALLED`다. 설치는 콘솔의 **Slack 앱 만들고 설치**가 Slack 동의 뒤에 만든다. 손으로 만든 앱은 운영자가 [Slack 설치 등록](#slack-설치-등록)으로 만든다.

Slack에서 앱을 제거하면 연결이 해제된다. `app_uninstalled`나 bot token이 든 `tokens_revoked` 이벤트가 오면 설치가 `revoked`가 되고, 그 설치의 활성 연결도 같이 `revoked`가 된다(`revoked_at`이 채워진다). 그 연결의 채널 binding과 자격 참조 이름도 풀린다. 콘솔의 Slack 탭은 "연결됨" 대신 "재설치 필요"를 보인다. 같은 이벤트가 다시 오거나 재설치 뒤에 늦게 도착해도 상태는 그대로다. 다시 설치하면 새 활성 연결이 만들어지고, 이전 연결은 해제된 기록으로 남는다.

Werft가 만든 앱을 `DELETE /v1/workspaces/{id}/slack/apps/{app_id}`(콘솔: Slack 탭 **위험 구역**의 **앱 삭제**)로 지우면, Slack의 이벤트를 기다리지 않고 한 transaction에서 Werft 쪽을 모두 닫는다. 앱의 설치와 그 설치의 활성 연결, 채널 binding, 아직 보내지 않은 Slack 메시지(`app_deleted`로 취소), 그 에이전트가 듣던 채널의 판단 버퍼가 함께 닫히고, 저장된 secret이 지워진다. 하나라도 닫지 못하면 아무것도 닫지 않고 오류로 답한다. 앱은 `deleting`으로 남고, 같은 요청으로 다시 지운다. 도는 세션은 멈추지 않지만, 그 세션이 이 앱으로 보내려는 글은 `app_deleted`로 거절된다. 세션과 턴 기록은 남는다. 이 삭제는 `delete_slack_app` receipt에 누가 어떤 앱을 지웠는지, 닫은 수, Slack 쪽 정리 결과를 남긴다. 토큰 값은 남지 않는다.

Werft 쪽이 커밋된 뒤 Slack에 bot token 회수(`auth.revoke`)와 앱 삭제(`apps.manifest.delete`)를 한 번씩만 요청한다. Slack에 이미 없는 토큰이나 앱은 끝난 것으로 본다. 둘 중 하나라도 실패해도 삭제는 성공(`200`)이고, 응답의 `slack_cleanup`이 `failed`와 실패한 단계(`failed_steps`)를 알린다. 다시 시도하지 않으니 Slack 앱 관리 화면(api.slack.com/apps)에서 앱을 직접 지운다. 그 뒤 Slack이 `app_uninstalled`나 `tokens_revoked`를 보내도 바뀌는 것은 없다. 서명 secret이 앱과 함께 지워져 서명을 확인할 수 없는 요청에는 `401`로 답하고, Slack이 몇 번 다시 보내도 닫힌 상태는 그대로다.

이벤트가 오지 않는 제거도 있다. 채널 목록·이름 조회·채널 binding처럼 bot token으로 Slack을 부른 요청이 `token_revoked`나 `account_inactive`로 거절되면 같은 해제를 한다. 이때도 응답은 409 `SLACK_NOT_INSTALLED`다. `invalid_auth`·`not_authed`·`token_expired`처럼 제거 말고도 나올 수 있는 오류, 429·5xx·통신 실패는 상태를 바꾸지 않는다.

### 판단 기록

`GET /v1/agents/{id}/slack/judgments`(콘솔: Slack 탭 **판단 기록**)는 최근 7일 동안 M1이 이 에이전트의 채널에서 판단한 기록을 보인다. 지금 M1은 shadow로 판단만 하고 Slack에 글을 올리지 않는다. 채널마다 판단 수, 그 가운데 `speak`(끼어들기)의 수, 이유 코드별 수(`rate_limited`와 `budget_refused` 포함)를 세고, 가장 최근 판단 50건을 이유 코드와 Slack 글 링크로 보인다. 글 본문은 Werft에 남지 않으므로 링크를 눌러 Slack에서 읽는다. 콘솔은 판단에 쓴 에이전트 지침도 함께 보인다: 활성 릴리스를 만들 때 저장소에서 읽은 지침 파일의 릴리스와 commit이고, 저장소가 없거나 파일이 없으면 그렇다고 알린다. 화면을 열 때 저장소 branch의 끝 commit을 GitHub에서 읽어(`GET /v1/agents/{id}/slack/instructions-head`) 그 commit과 다르면 "저장소에 더 새 지침이 있습니다. 새 릴리스를 만들면 반영됩니다"를 덧붙인다. 릴리스를 저절로 만들지는 않고, GitHub을 읽지 못하면 이 안내만 빠진다.

워크스페이스 owner·admin과 그 에이전트의 관리자만 볼 수 있다. API 키로는 읽을 수 없다. 비공개 채널(살아 있는 binding이 공개 채널이라고 하지 않는 채널 포함)의 기록은 숫자까지 지금 그 채널의 멤버에게만 보인다. Slack에 멤버인지 묻고(최대 5분 캐시), 확인하지 못하면 그 채널을 뺀다. owner나 admin이라도 멤버가 아니면 그 채널은 목록과 합계 어디에도 나오지 않는다.

판단이 너무 잦거나 드물면 채널의 듣기 설정, 시간당 판단 상한, 저장소의 에이전트 지침(AGENTS.md)으로 맞춘다.

## 다른 봇의 멘션

에이전트는 사람이 아닌 다른 봇의 멘션에도 답할 수 있다. 에이전트 관리자가 콘솔 Slack 탭의 **기본 > 답할 봇**에서 고른 봇만 받는다. 초기값은 빈 목록이고, 비어 있으면 지금처럼 모든 봇 메시지를 무시한다.

- 고를 수 있는 봇은 에이전트를 설치한 Slack 워크스페이스의 봇뿐이고, 최대 20개다. 에이전트 자신의 봇, 같은 Werft에 있는 다른 에이전트의 봇, Slack Connect로 들어온 다른 팀의 봇은 고를 수 없다. 에이전트끼리는 Slack 멘션으로 부르지 않는다.
- 워크스페이스가 커서 Slack의 목록을 끝까지 읽지 못하면 고르기 창에 그 안내와 **Slack 사용자 ID로 추가** 칸이 보인다. 넣은 ID는 그 워크스페이스의 살아 있는 봇일 때만 바로 저장되고, 아니면 이유를 한 줄로 보인다.
- 고른 봇이 채널이나 스레드에서 에이전트를 직접 @멘션했을 때만 답한다. 멘션 없는 봇 글과 DM은 늘 무시한다. 에이전트 자신의 앱이 쓴 글(에이전트의 답, 웹 콘솔에서 보낸 사람 이름으로 올린 지시)은 허용 목록과 상관없이 맨 먼저 버린다(버린 이유 `own_bot_user`). Slackbot(`USLACK`)의 글은 DM이든 채널이든 버린다(버린 이유 `slackbot`). 같은 Werft의 다른 에이전트 봇이 쓴 글은 목록에 남아 있더라도 버린다(버린 이유 `werft_agent_bot`). 그 밖의 봇 글을 버린 이유는 허용 목록이 비어 있으면 `bot_allowlist_empty`, 보낸 봇이 목록에 없으면 `bot_not_allowed`, 목록의 봇이지만 DM이거나 직접 멘션이 아니면 `bot_message`다.
- 고른 뒤 Slack에서 지워지거나 비활성이 된 봇은 목록에 **Slack에서 사라짐**으로 남고, 그 봇의 멘션은 무시한다. 목록에서 뺄 수는 있지만 다시 고를 수는 없다.
- 봇이 연 세션에는 시작한 사람이 없다. 에이전트 API 키로 연 세션과 같다. 사람이 그 스레드에서 이어 써도 세션 주인은 바뀌지 않고, 세션 기록에는 연 봇의 Slack 사용자 ID가 남는다(`requester_kind`가 `slack_bot`). 봇이 시작한 턴은 에이전트와 워크스페이스 연결만 쓰고 개인 연결은 쓰지 않는다. 세션 비용 한도에도 함께 센다.
- 한 Slack 스레드에서 사람 없이 봇이 시작한 턴이 5번 이어지면 멈춘다. 6번째 멘션을 받은 에이전트가 그 스레드에 `사람 없이 봇끼리 5번 주고받아 여기서 멈춰요. 사람이 이어 가야 해요`를 한 번 남기고, 그 뒤의 봇 멘션은 말없이 무시한다. 수는 스레드마다 세고, 어느 에이전트가 답했든 합친다. 사람이 그 스레드에 글을 쓰면 0으로 돌아간다. 시간이 지나도 돌아가지 않는다.

`GET /v1/agents/{id}/slack/app/bots`는 `items`와 `truncated`를 반환한다. 항목마다 `user_id`·`name`·`state`(`active`·`gone`)·`allowed`가 있고, `truncated`가 `true`면 Slack 목록을 끝까지 읽지 못했다는 뜻이다. `PUT`은 `{ "allowed_user_ids": ["U0..."] }`로 목록 전체를 바꾸며, 에이전트 관리자가 웹 세션으로 호출한다. 새로 넣는 ID를 받을 수 없으면 400이고, `details.reason_code`가 이유를 말한다: `slack_bot_own`(에이전트 자신의 봇), `slack_bot_werft_agent`(같은 Werft의 다른 에이전트 봇), `slack_bot_other_team`(다른 팀의 봇), `slack_bot_unknown`(살아 있는 봇이 아님). `details.user_ids`가 그 이유로 거절된 ID를 담는다. 앱이 설치되지 않았으면 409 `SLACK_NOT_INSTALLED`, Slack 429는 `Retry-After`를 포함한 503이다.

시험과 복구에는 DB에 접근할 수 있는 운영자가 API 컨테이너에서([운영자 명령 실행](#운영자-명령-실행)) `bun run apps/control-host/src/api/slack-app.ts list-bots --agent <agent_id>`, `allow-bot --agent <agent_id> --bot <bot_user_id>`, `disallow-bot --agent <agent_id> --bot <bot_user_id>`를 쓸 수 있다. 평소에는 콘솔에서 바꾼다. `allow-bot`은 위와 같은 검사(`slack_bot_own`·`slack_bot_werft_agent`·`slack_bot_other_team`·`slack_bot_unknown`)를 거치고, 거절하면 종료 코드 10으로 끝난다. 목록이 바뀌면 `by`가 `operator_cli`인 receipt `set_slack_allowed_bots`가 남는다(콘솔에서 바꾸면 `by`가 `web`이고 `actor`가 바꾼 사용자다). 이미 허용한 봇을 다시 허용하거나 허용하지 않은 봇을 빼면 아무것도 바뀌지 않고 receipt도 없다. API는 계속 웹 세션 전용이고 API 키로는 열리지 않는다.

## 채널 참가와 배포 환영

에이전트의 채널(`PUT /v1/agents/{id}/slack-bindings`)을 저장하면 서버가 bot을 그 채널에 넣는다. 공개 채널은 bot이 스스로 들어간다. 비공개 채널은 Slack이 막으니 채널에서 `/invite @<bot>`으로 초대한다. 초대되면 서버가 알아채고 이어 간다. 결과는 binding의 `membership.state`로 보인다. 저장한 적 없는 채널에 bot을 초대해도 서버가 그 채널을 사용(`on`)으로 연결한다. 이미 저장한 채널은 설정을 바꾸지 않는다(꺼 둔 채널은 꺼진 채로 둔다).

에이전트가 채널에 쓴 답은 그 채널의 모든 사람이 읽는다. 담당 팀 밖 사람도, 워크스페이스 설정으로 그 세션을 콘솔에서 못 보는 사람도 포함된다. 콘솔의 채널 칸도 이 점을 적는다.

| `membership.state` | 뜻 |
| --- | --- |
| `joined` | bot이 채널에 있다 |
| `awaiting_invite` | 비공개 채널이라 초대를 기다린다 |
| `config_error` | Slack이 token이나 scope를 거절했다(`error`에 Slack 오류 코드). 앱을 다시 설치한다 |
| `join_failed` | 보관된 채널이거나 워크스페이스 정책이 막았다(`error`) |

release가 처음 배포되면 home 채널에 `안녕하세요, <에이전트 이름>입니다. 이 채널에 연결됐어요. 멘션하면 답할게요`가 간다. 이 인사는 에이전트마다 채널당 한 번이다. 새 release를 배포하거나, 같은 정의를 다시 제출하거나, 이전 release로 되돌리거나, Slack 연결을 끊었다가 다시 이어도 이미 인사한 채널에는 다시 보내지 않는다. home을 아직 인사하지 않은 채널로 옮기면 그 채널에 한 번 간다. bot이 home에 없으면 들어올 때까지 기다린다. 환영이나 참가가 실패해도 배포는 실패하지 않는다.

## 채널 보관·이름 변경·삭제

에이전트 앱은 채널의 보관(`channel_archive`·`group_archive`), 보관 해제(`channel_unarchive`·`group_unarchive`), 이름 변경(`channel_rename`·`group_rename`), 삭제(`channel_deleted`·`group_deleted`) 이벤트를 받는다. `channel_*`은 공개 채널, `group_*`은 비공개 채널의 것이다. 앱이 이미 가진 scope로 오는 이벤트라 새 scope는 없다. Slack 문서로는 이미 가진 scope의 이벤트를 더하는 데 재설치가 필요 없다. 이 이벤트가 생기기 전에 만든 앱에는 API가 시작할 때 manifest를 저절로 다시 보낸다. 시작할 때마다 앱마다 Slack의 manifest를 읽어(`apps.manifest.export`) bot 이벤트만 다르면 manifest 전체를 보내고, bot scope가 다르거나 앱에 user scope가 있으면 보내지 않는다. 그 결과는 `GET /v1/agents/{id}/slack/app`의 `manifest_sync`에 남는다. `error`가 null이 아니면 콘솔 Slack 탭의 앱 칸에 "갱신 필요"와 이유가 나온다. 이유는 `config_token_inactive`(활성 App Configuration Token이 없어 읽지도 보내지도 않음), `events_url_unset`, `slack_refused`, `no_answer`다. 다음 시작이나 **다시 확인**(`POST /v1/agents/{id}/slack/app/events/recheck`)이 다시 시도하고, 따로 도는 재시도는 없다. 여러 API replica가 함께 떠도 한 앱은 10분 안에 한 번만 확인한다. 콘솔 없이 보내려면 API 컨테이너에서([운영자 명령 실행](#운영자-명령-실행)) `bun run apps/control-host/src/api/slack-app.ts finalize --agent <agent_id>`를 실행한다. 다시 보낸 manifest가 설치에 없는 scope를 요청해 Slack이 권한이 바뀌었다고 답하면, 다시 확인의 응답(`reinstall_required: true`)과 콘솔 안내가 앱을 다시 설치하라고 알린다.

채널이 다른 조직과 공유되거나 공유가 끝날 때 오는 `channel_shared`·`channel_unshared`도 받는다. 앱이 이미 가진 `channels:read`·`groups:read`로 오는 이벤트라 재설치는 필요 없고, 이 이벤트가 생기기 전에 만든 앱은 위와 같이 다시 확인으로 받는다. 이벤트를 받기 전에도 공유 여부는 채널 글이 올 때 Slack에 물어 안다.

- 보관·보관 해제·이름 변경은 그 채널의 대화에 상태(`active`·`archived`)와 새 이름만 적는다. 채널의 binding과 받기·답하기는 그대로다.
- 채널이 삭제되면 그 채널의 binding이 `gone`이 된다. binding은 지우지 않고 남기며, 그 채널의 글을 받지 않고 그 채널로 아무것도 보내지 않는다. home이었으면 home이 풀리고 승인도 지워진다. 대화에는 `deleted`가 적힌다. 콘솔의 채널 목록에는 "삭제됨"으로 보인다. 그 채널의 채널 요약도 모든 버전의 이력과 함께 지운다. 요약은 채널에 든 에이전트가 같이 쓰는 한 벌이라, 에이전트마다 오는 삭제 이벤트 중 첫 것이 지우고 나머지는 지울 것이 없다. 관여 기록과 대화는 세션의 보존을 따라 남는다. 보관으로는 요약을 지우지 않는다.
- 삭제 이벤트를 놓쳐도 게시나 채널 조회에 Slack이 `channel_not_found`로 답하면 공개 채널의 binding은 `gone`이 된다. Slack은 bot이 없는 비공개 채널에도 `channel_not_found`로 답해 삭제와 bot 제거를 가를 수 없으므로, bot이 들어가 있던 비공개 채널은 `left`로 둔다(`group_left`를 놓친 것과 같다). 초대를 기다리거나 승인을 기다리는 비공개 채널은 그대로 둔다. 429, Slack 장애, token 오류로는 상태가 바뀌지 않는다. `channel_not_found`로는 채널 요약을 지우지 않는다. bot이 다시 들어오면 되돌아가는 판정이기 때문이다.
- `gone`인 채널에 bot이 다시 들어오면(`member_joined_channel`) 공개 채널은 사용 중으로, 비공개 채널은 승인 대기로 돌아온다. 공개였다가 그사이 비공개로 바뀐 채널은 비공개 채널로 승인을 기다린다.
- 네 종류 모두 그 채널의 멤버 확인 캐시를 지운다.

## Slack에서 지운 글

Slack에서 지운 글(답이 달린 글을 지운 묘비 포함)이 지시인 턴은 웹 콘솔과 API에서 가려진다. 그 턴의 지시, 에이전트의 답, 도구가 읽고 돌려준 글이 "Slack에서 삭제됨"으로 보이고, 도구의 이름과 지운 시각은 남는다. 감사 열람에서도 같다. 첫 글에서 따오거나 만든 세션 제목도 가려지고, 사람이 붙인 제목은 그대로다. 같은 세션의 뒤 턴처럼 그 글을 물려받기만 한 턴은 가리지 않는다. 저장된 글은 지우지 않고 읽을 때 가린다.
