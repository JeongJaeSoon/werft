GitHub との間でやることは三つある。開始リポジトリがあるセッションは開始時に、ないセッションはエージェントが attach したときにリポジトリを clone する。人が承認した commit を `agent/<session-id>` ブランチへ push する。そのブランチで PR を開き、コメントを付ける。clone は worker が API のプロキシ経由で行い、push と PR はプラットフォーム(API)が直接行う。どちらの場合も、リポジトリの認証情報は worker に渡らない。

## 運用者がやること

認証情報は GitHub App で、owner か admin がコンソールの **設定 > ワークスペース > 連携 > GitHub** で扱う。

- **App を追加**: GitHub で新しい App を作成する(コンソールが App ID と鍵を受け取って保存する)か、既存の App を App ID と private key(PEM ファイル)で接続する。作成用 App とレビュー承認用 App を複数置けて、一覧では役割のバッジで見分ける。鍵は暗号化して保存し、画面にも API の応答にも二度と出ない。鍵を替えるときは App の行の ⋯ メニューの **新しい鍵を登録** を使う。
- **組織を追加**: App を組織か個人アカウントにインストールする。インストールの表にアカウントごとの種類・リポジトリの範囲・App・接続した人・状態が出て、行の ⋯ メニューの **GitHub で管理** がそのインストールの設定画面を開く。
- **リポジトリを管理**: エージェントが選んだリポジトリをインストールごとに見て、デフォルトブランチとそのリポジトリを担当する App を変える。リポジトリはエージェントの GitHub タブで選ぶとでき、別に登録はしない。
- **エージェントが使える機能**: ワークスペース全体の上限である。スイッチを変えるとすぐに保存される。有効にした機能に App の権限が足りないと、その App の行に必要な権限と **GitHub で権限を追加** が出る。権限を追加すると GitHub がインストール先のアカウントごとに owner へ承認を依頼し、再インストールは要らない。
- **自分の PR のマージ**: 既定はオフである。オンにすると、人がマージを指示したとき、エージェントは自分のセッションが開いた PR を squash でマージする。必須チェックとレビューは GitHub が判断し、マージ要求は ruleset の回避をオフにして送る。変更できるのは owner と admin だけで、ワークスペースの GitHub 設定 API(`PUT /v1/workspaces/{id}/github-settings` の `ceiling.merge`)で行う。オンにしても新しいリリースは要らず、次の呼び出しから効く。

コンソールで新しい App を作るには、API に `CONSOLE_ORIGIN`(ブラウザがコンソールを開く origin。例: `https://werft.internal.example`)が必要です。GitHub が App を作った後、このアドレスにブラウザを戻すためです。ないと、**GitHub App を作成** から開く **新しい App を作成** 画面で **GitHub で作成** ボタンが無効になり、「CONSOLE_ORIGIN が設定されていないため、GitHub がコンソールに戻る先がありません」という案内が出ます。運用者に値の設定を頼むか、**既存の App を接続** を使います。単一サーバーでは env ファイルに入れて `upgrade` で再適用します([単一サーバー](/run-server/self-hosting/single-server))。GitHub が passkey の確認(sudo mode)を求めたときは、その画面で App が作られず、空の App フォームに移ることがあります。確認を済ませてコンソールに戻り、**GitHub で作成** をもう一度押します。

| 方式 | 必要な権限 |
| --- | --- |
| GitHub App | Repository permissions: Contents Read and write, Pull requests Read and write |

`Workflows` 権限は「ワークフローファイルの変更」機能を有効にするときだけ App に加える。push される commit はエージェントが書いたものなので、この権限があるとエージェントが書き換えた `.github/workflows/` のファイルも push され、CI で実行される。デフォルトブランチはリポジトリの ruleset でも保護しておく([デフォルトブランチの保護](#기본-브랜치-보호))。

### App の Setup URL

コンソールで作った App は、Setup URL が `<CONSOLE_ORIGIN>/settings/workspace/integrations/github` で入る。すでにあった App を連携した場合は、GitHub の App 設定（Developer settings > GitHub Apps > その App > General）で **Setup URL** をこの住所に合わせる。組織を追加すると GitHub がブラウザーをこの住所へ戻し、コンソールは戻ってきた値でインストールを記録する。すでにインストール済みのアカウントで、インストールの設定を保存したあとコンソールへ戻るのは、App の **Redirect on update** がオンのときだけである。

<a id="기본-브랜치-보호" />
### デフォルトブランチの保護

プラットフォームはそのセッションの `agent/<session-id>` ブランチ（リクエスト本文で `branch` を渡すと `agent/<session-id>-<suffix>`）にだけ push し、デフォルトブランチは拒否する。GitHub でももう一度防ぐ。

1. リポジトリの Settings → Rules → Rulesets → New branch ruleset で、Target を `Include default branch` にする。
2. **Restrict updates**、**Restrict deletions**、**Block force pushes** をオンにする。人のレビューを経たマージだけを受け付けるなら、**Require a pull request before merging** もオンにする。
3. Bypass list に App を入れない。

- `agent/*` ブランチに **Block force pushes** だけを掛ける ruleset を別に置くと、プラットフォーム以外の誰かがそのブランチを巻き戻すことも防げる。
- `agent/*` の push で CI が要らなければ、workflow の `on.push.branches-ignore` に `agent/**` を入れる。変更されていない workflow にだけ効くため、`Workflows` 権限を与えないことと併せて使う。
- 保護ブランチの自動承認は、ブランチの ruleset(**Require a pull request before merging**、承認レビュー 1 件以上)を作成用 App で読む。旧来の branch protection rule は **Administration: Read-only** 権限を持つ App にしか見えないため、その権限なしで branch protection だけを置いたリポジトリでは自動承認を有効にできない(`protection_missing`)。
- 自動承認の前に、新しいバージョンを前の承認済みバージョンと比べて固定ルールで検査する。scripts・実行ファイルの追加、300 行を超える変更、新しい URL ホスト、見えない Unicode、指示のような文、`description` の変更のどれかに当たると、そのスキルのバージョンだけが承認待ち(`checks_failed`)に残り、同じ push の他のスキルはそのまま自動承認される。当たったルールとファイルはスキルの詳細とレビュー画面に表示される。検査は承認を止めるだけで、代わりに承認はしない。新しい URL ホストは、Markdown ファイルは CommonMark で描画した結果から、HTML ファイルはブラウザーと同じように解析した結果から読む(すべての属性値の URL と本文・コメントの URL、使われていないリンク定義を含む)。その他のファイルは書かれたまま読む。256 KiB を超える、または描画できない Markdown・HTML ファイルは判定できないため、新しい URL のルールに当たる。スクリプトが組み立てる URL、base64 などのエンコード、行末で切れた平文の URL は読まず、平文の URL は空白で終わるものとして読むため、何も当たらなくても変更行を読む。

<a id="git-스킬-webhook" />
### Git スキルの webhook

GitHub から登録したスキルは、push webhook、一日一回の確認、コンソールの「今すぐ確認」で新しいバージョンを探す。webhook は GitHub がこの API に届くときだけ使う。届かない設置は残りの二つで動く。

| 変数 | 既定値 | 許容範囲 |
| --- | --- | --- |
| `GITHUB_WEBHOOK_BASE_URL` | なし(webhook なし) | GitHub がインターネットから届くこの API の `https` アドレス。query・fragment・ユーザー情報があると API は起動しない。webhook のアドレスは `<この値>/v1/github/webhook` である |

- この値があると、コンソールで新しく作る作成用 App の manifest に webhook アドレスと `push` イベントが入り、GitHub が返した webhook secret は App キーと同じく暗号化して保存される。
- 既存の App は、GitHub の App 設定(General → Webhook)で **Active** をオンにして **Webhook URL** と **Secret** を入れ、Permissions & events で **Push** イベントをオンにする。同じ secret を owner か admin が `PUT /v1/workspaces/{id}/github-apps/{role}/webhook-secret` で入れる。
- 受け取る経路は認証なしの `POST /v1/github/webhook` で、本文の `X-Hub-Signature-256` の署名を検証したあとでだけイベントを処理する。署名がないか誤っていれば `401`、本文が 64 KiB を超えれば `413`、App ごとの毎分の上限を超えれば `429` である。

<a id="토큰-발급이-실패할-때" />
### トークンの発行に失敗したとき

clone・push・PR は、API が App キーで受け取った installation token を使う。発行に失敗すると(キーやインストールの誤り、App のアンインストール、GitHub の障害)リポジトリ route が `503` で閉じ、clone が開始段階で失敗してセッションの attention が `STARTUP_FAILED` になる。API ログの `GitHub request failed`(`request: installation token request`)の行で `status` を見る。

| status | 確認すること |
| --- | --- |
| `401` | App ID と private key が対になっているか |
| `404` | そのインストールにリポジトリが含まれているか |
| `422` | リポジトリ名 |

- コンソールの App がそのリポジトリにインストールされていなければ、`GitHub App is not installed on <owner>/<repo>` で同じ `503` になる。
- ログインなしで読めないリポジトリ(存在しないリポジトリ、インストールに含まれない非公開リポジトリ)は、clone が `could not read Username` で失敗する。`http://` URL のように GitHub が redirect するアドレスは `upstream redirected` で失敗するため、カタログの URL を `https://` に直す。
- API コンテナから `api.github.com:443` へ、egress proxy から `github.com:443`(`EGRESS_CREDENTIAL_ALLOWLIST`)へ出られる必要がある。`github.com` を forward 一覧(`EGRESS_ALLOWLIST`)に入れると proxy は起動を拒否する。

<a id="github-enterprise-server" />
### GitHub Enterprise Server

コンソールの App は github.com だけを使う。GHES のリポジトリは、設定文書に App を直接書いてインポートする([設定文書のインポートとエクスポート](/run-server/self-hosting/reference/configuration#설정-문서-가져오기내보내기))。

```json
{
  "version": 1,
  "connections": {},
  "repositories": {
    "ghes-app": {
      "url": "https://<ghes-host>/<owner>/<repo>.git",
      "branch": "main",
      "auth": {
        "kind": "github_app",
        "app_id": 123456,
        "installation_id": 7890123,
        "stored": true,
        "api_base": "https://<ghes-host>/api/v3"
      }
    }
  }
}
```

- インポート後に owner か admin が `POST /v1/installation/settings/repositories/{id}/credential` で RSA private key PEM を入れる(コンソール画面はない)。入れるまでそのリポジトリは `needs_value` で、セッションは動かない。キーを変えるときも同じ経路を使う。
- `api_base` は `https` だけを受け付ける。運用者のネットワーク内のプライベートな host だけは `http` も受け付ける。`app_id`・`installation_id`・`api_base` を変えると binding が変わり、そのリポジトリの既存セッションは `CATALOG_MISMATCH` になる。
- API から `<ghes-host>:443` へ出る経路を開け、proxy の `EGRESS_CREDENTIAL_ALLOWLIST`(プライベートアドレスなら `EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST`)に `<ghes-host>:443` を加える。

## ユーザーがやること

GitHub を使うには、まず管理者がエージェントの GitHub タブでリポジトリをオンにする。スイッチは切り替えるとすぐ保存される。新しいエージェント(リリースにも GitHub 設定がないエージェント)は、このタブで最初に保存するまでセッションに GitHub ツールがなく、ふつうはリポジトリをオンにすることが最初の保存になる。このとき push 承認の既定値(push 前の人の承認はオフ、追加リポジトリへの push は許可)も一緒に保存されるため、その後に始まるセッションからエージェントは人の承認なしで push する。承認を求めるには、同じタブの push 承認の項目を変えて保存バーで保存する。

1. そのリポジトリの `repository_id` でセッションを作る([開始](/sessions/start))。
2. 結果を[リクエスト](/approvals/request)し、[承認](/approvals/approve)する。リクエストが `pushed` になると、リポジトリに `agent/<session-id>` ブランチができる。
3. PR を開く。`sessions:approve` が必要である。下の例は[リクエスト](/approvals/request)と[承認](/approvals/approve)の `sessionId` と `push`(HTTP API は `SID`、`PUSH_ID`)を使う。

4. コメントを付ける。同じ `marker`(デフォルトは `status`)のコメントがすでにある場合は、新しく付けずにそのコメントを書き換える。

タイトル・本文・コメントは GitHub に送る前に整形される。秘密情報に見える行は伏せ、`@メンション` や `Closes #N` のような close キーワードは、通知や自動クローズが起きないように置き換える。

PR 本文の末尾には、プラットフォームが書く末尾ブロックが付く。セッション id とコミット、セッションのアドレス、エージェントとリリース、誰がどの経路で開始したか、その push を依頼した人(`Requested by`。通知が飛ばないよう `@` なしで login だけを書く)が入る。そのブランチにもう一度 push して PR をもう一度要求すると、末尾ブロックだけが新しいコミットに変わり、その上に人が書いた本文はそのまま残る。

セッションの中のエージェントは、組み込み MCP ツールで同じことをする。`open_pull_request` で開き、`update_pull_request` でタイトルと本文を直し、`comment_pull_request` でコメントする。`close_pull_request` と `reopen_pull_request` で、このセッションの push 要求が開いた PR をマージせずに閉じ、また開く。人の承認は受けない。ほかのセッションの PR や、許可されていないリポジトリの PR は閉じられない。閉じた PR を閉じたり、開いている PR を再オープンしたりすると、何も変えずに `changed: false` で答える。マージ済みの PR は `PULL_REQUEST_MERGED` で拒否する。閉じても `agent/<session-id>` ブランチは消さない。そのため再オープンできる。

`get_pull_request` は、このセッションの push 要求が開いた PR のタイトル、本文、状態、head を読む。プラットフォームの末尾は除き、秘密値に見える行は `[REDACTED]` で隠す。末尾を除き秘密値を隠した本文が 64 KiB を超えると先頭だけを返し、`body_truncated: true` と `body_sha256: null` で知らせる。本文は人が書いた文章なので `untrusted: true` が付く。一緒に返る `body_sha256` を `update_pull_request` の `expected_body_sha256` に渡すと、読んだあとに誰かが本文を直していた場合は何も書かずに `body_changed` で拒否する。この値と一緒に送った本文が長くて切れてしまう場合は、切らずに `body_too_long` で拒否する。切れて読まれた本文にはハッシュがないので、エージェントは書き直せない(`body_unverified`)。タイトルだけの変更はできる。読み取りも GitHub の利用スイッチとリポジトリの範囲に従う。

ワークスペースが許可していれば、`merge_pull_request` でその PR を squash でマージする。許可していなければ、GitHub を呼ぶ前に `GITHUB_REFUSED`(`merge_off`)で拒否する。マージは push 要求が push した commit に固定する。PR の head がその commit でなければ `head_moved` で、必須チェックの待ち・レビュー待ち・未解決の会話・競合など GitHub が今はマージしない PR は `merge_blocked` で拒否する。この拒否の `details` には、GitHub が返した状態(`mergeable_state`、`mergeable`、`draft`)と、どの条件が満たされなかったかを述べる `reason` の文が載る。`reason` は状態を述べるだけで、どの必須チェックやレビューかまでは述べない。開いたときと別の base に移された PR、または base が別の開いている PR の head である PR(積まれた PR)も `merge_blocked` である。GitHub の非同期マージは、その PR が積まれている下の PR も一緒にマージするためである。マージ要求を GitHub が受け付けても待つ間に終わらなければ `forge_failed` で答える。マージはあとから終わることがあるので、PR を確かめてからもう一度呼べばよい。すでにマージ済みの PR は、同じ commit なら `changed: false` で答え、別の commit なら `head_moved` で拒否する。マージされずに閉じられた PR は `pull_request_closed` で拒否する。管理者による回避、自動マージ、ほかのマージ方式は使わない。権限確認のないモード(`bypassPermissions`)のセッションは、オンの間は指示がなくてもマージできる。マージ要求はルールの回避をオフにして(`bypass_rules: false`)GitHub の非同期マージ API に送るため、作成用 App がルールセットの回避対象でも、その権限で必須チェックとレビューを飛ばせない。それでもマージ用の App は回避対象に入れないほうが安全である。エージェントの Actions 許可リストに PR をマージするワークフローを入れると、このスイッチはそのマージを止められない。

<a id="push가-거절되는-경우" />
## push が拒否される場合

承認されたリクエストは、API が数秒以内に push する。リクエストが固定した commit 一つをそのリポジトリのそのブランチ（`refs/heads/agent/<session-id>` または `refs/heads/agent/<session-id>-<suffix>`）に送り、force push はしない。同じ commit がすでにあれば、そのまま `pushed` になる。失敗すると、`push` receipt の `refusal` が理由になる。

| `refusal` | エラーコード | 意味 |
| --- | --- | --- |
| `non_fast_forward` | `REVISION_CONFLICT` | リモートブランチの commit が、push する commit の祖先ではない |
| `target_refused` | `FORBIDDEN` | ブランチが `agent/<session-id>` でも `agent/<session-id>-<suffix>` でもない |
| `default_branch` | `FORBIDDEN` | カタログのブランチか、リモートのデフォルトブランチである |
| `no_push_credential` | `FORBIDDEN` | そのリポジトリに push する資格情報がない |
| `catalog_changed` | `CATALOG_MISMATCH` | リクエストの後にリポジトリの URL か認証が変わったか、項目が削除された。リモートには何も送らない。新しくリクエストして承認を受け直す |
| `checkpoint_unavailable` | `CHECKPOINT_UNAVAILABLE` | 固定した checkpoint を読めないか、検証できなかった |
| `lease_expired` | `LEASE_EXPIRED` | push が終わらないまま lease を何度も超えた。新しくリクエストできる |
| `push_failed` | `BACKEND_UNAVAILABLE` | トークン発行の失敗、リモートの拒否、ネットワーク。`Workflows` 権限なしで workflow ファイルを変える push もここに入る |

リモートが送ったメッセージは receipt に入れない。API ログの `Push refused`・`Push failed` の行に `push_request_id` と理由がある。push は API が直接行うため、API コンテナからリポジトリの host へ出られる必要がある。

## push の後に PR が作られる仕組み

push リクエストに PR のリクエストが付いていると、push が `pushed` で終わった後に control-host が PR を作成します。エージェントが続きのターンで `open_pull_request` をもう一度呼ぶ必要はありません。control-host を再起動しても、すでに始まっている PR の段階は最後まで処理されます。REST では、push が終わる前に `POST /v1/sessions/{id}/push-requests/{push_request_id}/pull-request?schedule=true` を呼ぶと、409 `PUSH_NOT_PUSHED` の代わりに 202 と `status: "scheduled"` が返り、push が終わり次第 PR が作成されます。`schedule` クエリがない場合や、`flow = legacy` で作成した push リクエストの場合は 409 です。

PR の段階は push リクエストごとに 1 つで、状態は次のように変わります。

| 状態 | 意味 |
| --- | --- |
| `due` | push が終わり、PR を作る番です。作成に失敗すると間隔を空けて再試行します(最大 3 回) |
| `opening` | control-host の 1 つが作成中です。その処理が止まると別の replica が引き継ぎます |
| `opened` | PR が作成され、記録されました。番号とリンクは PR の行にあります |
| `closed_unrecorded` | この push リクエストの PR が、プラットフォームが記録する前にクローズまたはマージされました。新しい PR は作りません |
| `uncertain` | PR があるかどうかを確認できませんでした(照会が 3 回失敗したか、最初の照会が上限の 10 件で埋まり、次のページにまだあるかもしれません)。または当てはまる PR が複数あります。プラットフォームは選びません |
| `failed` | PR を作成できませんでした。理由は `pr_error` に残ります |
| `cancelled` | push が失敗したため、作成する PR がありません。理由は `pr_error` に残ります |

作成の前に、プラットフォームはブランチをすべての状態(オープン・クローズ・マージ済み)で先に探します。応答を失った後で再試行しても PR がもう 1 つ増えないのはこのためです。すでにオープンの PR があればそれを使い、末尾だけを新しい commit に書き換えます。見つけた PR や新しく作った PR の head が push した commit と違えば、何も記録せず `head_moved` で終わります。ただし GitHub は push 直後にしばらく古い head を返すことがあるため、その head が push した commit の祖先であれば終わらせず、次の試行まで待ちます。祖先でない場合や比較が失敗した場合は、その場で終わります。作られた PR は閉じないので、人が確認します。PR 本文の目印は誰でも書けるため、同じリポジトリ・head・base の PR だけを候補にします。

結果はセッションのスレッドに通知として届きます(作成した、作成できなかった、すでにクローズ済み、確認できなかった)。文言はセッションを始めた人の言語に合わせ(依頼した人ではありません)、結果ごとに 1 回だけ作られます。通知は、セッションが Slack のスレッドにつながっていて、ミュートや権限の制限がないときだけ作られます。そうでなければ状態だけが変わり、通知は届きません。

既知の制限があります。プロセスが呼び出しの直前に長く止まり、すでに送ったリクエストが遅れて届くと、同じブランチに PR がもう 1 つできることがあり、プラットフォームは作成後にそれを探しません。GitHub には条件付き作成がないため、プラットフォームは呼び出しの直前に再確認し、作成の前にブランチを探すところまでしかしません。作成時に当てはまる PR が複数あれば、新しく作らず `uncertain` のままにして通知します。自動ではクローズしないので、GitHub で人が選びます。

## セッションの途中でリポジトリを付ける

GitHub 設定があるエージェントのセッションはリポジトリなしで始まる(GitHub 設定がないエージェントはリリースのリポジトリで始まる)。エージェントは作業の途中で、タスクが読むか変更するリポジトリだけを、内蔵 MCP ツール `attach_repository({ repository_id })` で付ける。付けられるのは、エージェントのリリースの GitHub 設定（`github.repositories`）にあり、ワークスペースの上限が許可するリポジトリだけだ。人の承認は受けない。そのリポジトリへの書き込みは push 要求の承認を通り、付けたリポジトリへの push が人の承認なしで進むのは、push 承認を切り、付けたリポジトリの push ポリシーも `allow` にしたエージェントだけである(どのリポジトリにも同じルール)。付けられるリポジトリはエージェントが `list_repositories` で見る(付けたもの `attached`、取得中か失敗したもの `pending`・`failed`、まだ付けていないもの `not_attached`。セッションを作るときに `repository_id` で指定したリポジトリは `attached` と表示される)。セッションは始めたときのリリースを使い続ける。そのため、あとで有効なリリースにだけ加えたリポジトリは `allowed_in_newer_release` として別に表示され、`attach_repository` も `repository_not_allowed` ではなく `allowed_in_newer_release` で拒否する。もう一度許可する必要はなく、新しいセッション(Slack では新しいスレッド)で付けられる。エージェントの設定で動き、付けたリポジトリの一覧を持つセッションは異なる。開始後にエージェントが一覧でオンにしたリポジトリはすぐに付けられ、一覧から外すか GitHub をオフにすると、付けていたリポジトリ(セッションを作るときに指定したリポジトリを含む)は `revoked` と表示され、プラットフォームはエージェントによるそのリポジトリへの GitHub 操作と、他のリポジトリの新しい attach を拒否する。セッションを作るときに指定したリポジトリへの attach は何もせず、すでに付いているものとして答え、プラットフォームが記録済みの PR を読む処理は続く。作業領域のコピーは削除せず、再びオンにすればそのまま使える。

セッションを作るときに `attached_repository_ids` を送らなければ、何も付けずに始まる(`repository_id` を送ったセッションにはそのリポジトリだけがある)。最初から必要なリポジトリはその一覧に入れ、残りはエージェントが必要なときに付ける。push 要求は 1 つのリポジトリを送り出すので、リポジトリが複数あるときはリポジトリごとに 1 回ずつ出す。

attach が接続エラー(`upstream connection failed` の応答、または HTTP 502・503)で失敗した場合、それは一時的な失敗で、リポジトリについては何も示していない。同じ引数でやり直しても安全である。`repository_not_allowed` は接続エラーではなくエージェント設定による拒否なので、やり直しても同じ答えになる。

- 付けたリポジトリは、作業スペースで名前が `repository_id` の git リモートになり、デフォルトブランチを `<repository_id>/<branch>` に取得する。エージェントはトークンを見ない。
- 同じリポジトリをもう一度付けても何も変えずに成功する。取得中なら `pending` と `final: false` をすぐ返す。`wait_seconds`（0〜7 秒、既定 0）を渡すと、取得が終わるかその秒数が過ぎるまで待ってから答え、終わっていれば `final: true` になる。
- 取得には 300 秒と 2 GiB の上限がある。超えると付けるのは失敗で終わり、`failure` に理由（`fetch_timeout`、`fetch_too_large`）が残る。
- 付けるたびに `attach_repository` の[レシート](/approvals/receipt)が残る。要求した人と attempt、リポジトリ、リリース、取得したコミット、拒否の理由（`repository_not_allowed`・`allowed_in_newer_release`）が入る。
- セッションが別の worker で再開すると（restore）、付けたリポジトリのリモートをもう一度付ける。このときブランチの今の先端ではなく、そのセッションが最初に取得した commit を取得する。その間にリモートのブランチが進んだり書き換えられたりしても、セッションが読むコードは変わらない。付けたリポジトリの CLAUDE.md は指示として読まない。
- その commit がリモートから消えてもう一度取得できないと、そのリポジトリは付いていない扱いになる。セッションイベントに `system` イベント（`subtype: "repository_restore_failed"`、`repository_id`、`commit`）が一度残り、`list_repositories` はそのリポジトリを `failed`（`failure: restore_failed`、記録した `commit`）として示す。エージェントが付け直すと、ブランチの今の先端を取得する。

## 自分の GitHub アカウントを連携する

コミットの作成者は常に GitHub App の bot アカウント(`<App slug>[bot]`)だ。自分の GitHub アカウントを連携しておくと、自分が依頼したターンのコミットに `Co-authored-by:` トレーラーで自分の名前も入り、GitHub でそのコミットが自分の貢献としても表示される。

1. owner か admin が **設定 > ワークスペース > 連携 > GitHub** の「メンバーの GitHub アカウント連携」の行で、連携に使う作成用 App を選び(App が複数あるとき)、⋯ メニューの callback URL をその App の Callback URL に入れ、その App で作った client secret を入力する。この準備がないと連携ボタンは無効になっている。
2. **個人設定 > 連携アカウント** の GitHub の行で「連携」を押し、GitHub の同意画面で承認する。プラットフォームは GitHub アカウントの id と login だけを読み、GitHub のトークンは保管しない。
3. 連携した行に、コミットに入る行(`Co-authored-by: <login> <<id>+<login>@users.noreply.github.com>`)が表示される。連携を解除すると、それ以降に依頼するターンからは入らない。

Web コンソール、個人 API キー、Slack から依頼したターンは、そのターンを依頼した人の連携に従う。一つのセッションで複数の人が続けて依頼した場合、コミットごとにそのターンの依頼者が入る。エージェントキーや運用者キーで依頼したターンには依頼した人がいないため、共同作成者は入らない。どちらの場合も、コミットには `Agent-Session:` トレーラーが付く。運用者がコンソールのアドレスを設定した環境ならセッションのアドレス、そうでなければセッション id だ。セッション詳細の成果物タブの最後の行で、そのセッションがどちらかを確認できる。

GitHub アカウント1つは1人にだけ連携される。他の人がすでに連携したアカウントは連携できない。

## ローカルスタックでは

ローカルの `sample-app` はスタック内の Git サーバーに GitHub App として登録されているため、承認した push は `pushed` になり、PR も開ける。push されていないリクエスト(拒否したものなど)に PR を要求すると 409 `PUSH_NOT_PUSHED` になる。[承認](/approvals/approve)で `rejected` として終わったリクエストで確認する。

import { isApiError } from "@werft-ai/sdk";

const requests = await werft.sessions.pushRequests.list(sessionId);
const rejected = requests.find((request) => request.state === "rejected");
if (rejected) {
  try {
    await werft.sessions.pushRequests.openPullRequest(sessionId, rejected.id, {
      title: "Add release notes",
    });
  } catch (error) {
    if (!isApiError(error)) throw error;
    console.log(error.status, error.code);
  }
}

| レスポンス | 意味 |
| --- | --- |
| 409 `PUSH_NOT_PUSHED` | リクエストがまだ `pushed` ではない |
