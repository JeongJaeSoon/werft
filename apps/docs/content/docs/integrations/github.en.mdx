title: "GitHub"
description: Run sessions on a GitHub repository, push approved results to a branch, and open a PR from that branch

Werft does three things with GitHub. It clones the repository when a session starts with one, or when the agent attaches it otherwise. It pushes the commits a person approved to the `agent/<session-id>` branch. It opens a PR from that branch and adds comments to it. The worker clones through the API's proxy, while the platform (API) pushes and handles the PR itself. In either case, the repository credentials never reach the worker.

## What the operator does

The credential is a GitHub App, which an owner or admin handles in the console under **Settings > Workspace > Integrations > GitHub**.

- **Add App**: create a new App on GitHub (the console receives and stores its App ID and key), or connect an existing one with its App ID and private key (the PEM file). A workspace can hold several author Apps and reviewer Apps; a role badge tells them apart in the list. The key is stored encrypted and never shown again on the screen or in an API response. To change a key, use **Register a new key** in the App row's ⋯ menu.
- **Add organization**: install an App on an organization or a personal account. The installation table shows, for each account, its type, repository scope, App, who connected it and its status; **Manage on GitHub** in the row's ⋯ menu opens that installation's settings.
- **Manage repositories**: see the repositories agents picked, by installation, and change their default branch and the App that handles each. A repository appears once it is picked in an agent's GitHub tab; there is nothing to register.
- **Features agents may use**: the workspace's ceiling. A switch saves at once. When an App lacks a permission a feature that is on needs, that App's row says which and offers **Add permissions on GitHub**. Once added, GitHub asks the owner of each account it is installed on to approve; no reinstall is needed.
- **Merging its own pull requests**: off by default. When on, an agent squash-merges a pull request its session opened when a person tells it to. GitHub still decides on required checks and reviews, and the merge request is sent with ruleset bypass off. Only owners and admins change it, through the workspace GitHub settings API (`ceiling.merge` of `PUT /v1/workspaces/{id}/github-settings`). Turning it on needs no new release and applies from the next call. The agent's GitHub tab must have **Merge its own pull requests** on as well. With either side off the merge is refused with `merge_off`, and the refusal's `off_in` names the side that is off (`agent`, `ceiling` or `both`).

To create a new App in the console, the API needs `CONSOLE_ORIGIN`, the origin where browsers open the console (for example `https://werft.internal.example`), because GitHub sends the browser back to that address after it creates the App. Without it the **Create on GitHub** button on the **Create a new App** screen, which opens from **Create a GitHub App**, is disabled and the console says `CONSOLE_ORIGIN is not set`. Ask the operator to set it, or use **Connect an existing App**. On a single server, put it in the env file and re-apply with `upgrade` ([Single server](/run-server/self-hosting/single-server)). If GitHub asks for a passkey check (sudo mode), the App may not be created on that screen and you land on an empty App form. Finish the check, return to the console and click **Create on GitHub** again.

| Method | Required permissions |
| --- | --- |
| GitHub App | Repository permissions: Contents Read and write, Pull requests Read and write |

An author App made in the console also always asks for Workflows write and Actions and Checks read, since editing workflow files and seeing CI results is on by default. Checking **Also ask to run workflows directly** asks for Actions write instead. An App made before that may lack them. With an App that lacks Actions and Checks read, a CI read is refused with `github_refused` (`reason_code` `app_permission_missing`), and no person is asked to approve it. In the App's settings on GitHub, under **Permissions & events**, raise Actions and Checks to Read-only, and Workflows to Read and write for pushes that edit workflow files, then approve the permission request on each account the App is installed on.

Two switches cover workflows. The workspace ceiling and the agent's GitHub tab have the same two, and a switch the ceiling turns off is off even where the agent turns it on.

| Switch | Default | Permissions the token asks for |
| --- | --- | --- |
| **Edit workflow files and see CI results** | On | `workflows: write` on a push; `actions: read` and `checks: read` to read CI results |
| **Run workflows directly (run, rerun, cancel)** | Off | `actions: write` to dispatch and rerun |

**Edit workflow files and see CI results**: When on, the agent edits and pushes workflow files and reads CI results on its own. Reading CI asks no person to approve. CI is read with `get_ci_status` (a summary of the check runs and workflow runs of a pull request's head, or of a commit sha) and `get_workflow_run` (one run). Both take the repository to read as `repository` (`owner/name`, github.com repositories only). They read the session's repository, or one the agent's GitHub settings list that the session attached, and refuse any other (one `list_repositories` shows as `not_attached` included) with `github_refused` (`reason_code` `repository_not_allowed`). A session that keeps no list of attached repositories reads, without attaching it, any repository the GitHub settings in force for the session and the workspace's repository ceiling allow. Without it they read the session's repository, so in a Slack DM, where a session has no repository of its own, the agent gives `repository`. Each read gets a read token for that one repository (`actions: read` and `checks: read`, and, when it reads by pull request number, a separate `pull_requests: read` token to find the head); the session's token is not widened. The tool descriptions have the agent, after it pushes and opens a pull request, read the CI again until it is done and report the result in its reply once. A pull request still `scheduled` has no number yet. When `request_push` answered `deferred`, the push runs after the reply, so the agent reports the push and the pull request as scheduled and reads the CI in a later turn. Otherwise `get_push_request` gives the push state and, once the pull request is open, its number; meanwhile the pushed commit is read by sha. When a few reads with the longest wait are still not done, it reports what it read: each run's status, no runs when both lists are empty, and a `truncated` list as partial. That is a description the agent follows: the platform does not watch CI or write to the thread on its own, so when CI outlasts the turn or no run appears, the result may go unreported. While the switch is off, both tools are refused with `feature_off` (`workflows_off`), and the refusal's `details` name where it is off (the agent's settings, the workspace ceiling, or both) and who turns it on. The ceiling is read on every call, so a change to it applies from the next call. An agent switch that was off when the session started stays off in that session; a new session takes the change. Only a workspace owner or admin changes the ceiling.

**Run workflows directly (run, rerun, cancel)**: When on, the agent runs and reruns workflows on its own. CI that runs on push and pull requests is run by GitHub whatever this switch says. While it is off, dispatch and rerun are refused with `actions_off` before GitHub is called (`feature_off` from the MCP tools, `GITHUB_REFUSED` from the REST API), never passed to a person to approve, and no token asks for `actions: write`. The MCP tools' refusal `details` also name where it is off and who turns it on. When the agent turns it on but the workspace ceiling turns it off, the MCP tools refuse with the same `actions_off` and the REST API with `over_workspace_ceiling`. There is no cancel tool yet, so turning it on allows runs and reruns only.

An agent whose GitHub tab was never saved follows the settings its release pinned. Their old Actions (`actions: true`) reads as editing workflow files and seeing CI results, and direct runs count as off; turn direct runs on in the GitHub tab. When the workspace ceiling turns off workflow file edits, workflow file pushes are blocked too.

Three permissions start off in an agent's GitHub tab. Each can be turned on only where the workspace ceiling allows it, and a token is asked for only for one that is on. One that is off is refused with a reason code, never handed to a person to approve.

| Permission | Refusal when off | What the token asks for when on |
| --- | --- | --- |
| **Merge its own pull requests** | `github_refused` (`reason_code` `merge_off`) from the MCP tool, with `details.off_in` naming the side that is off | the author App's `contents: write` and `pull_requests: read` |
| **Approve reviews** | `feature_off` (`review_off`) from the MCP tool, `GITHUB_REFUSED` (`review_off`) from the REST API; on for the agent but off in the ceiling, the REST API answers `over_workspace_ceiling` | the reviewer App's `contents: read` and `pull_requests: write` |
| **Run workflows directly (run, rerun, cancel)** | `actions_off` | the author App's `actions: write` |

With **Approve reviews** on, the agent leaves and approves reviews on its own. With **Merge its own pull requests** on, the agent merges its own pull requests on its own. The repository's rules decide on required checks and reviews. A repository with no such rules waits for no check or review. A pull request GitHub cannot merge now (a conflict, a draft) is still refused with `merge_blocked`. Merging is not part of the settings a release pins, so only an agent whose GitHub tab was saved uses it. A session that started before it was turned on keeps it off; a new session takes the change. Only an old session that recorded no settings at its start reads the settings as they are now.

When GitHub refuses a `workflows: write` token, the installation's granted permissions are read with the App's key. If they lack `Workflows` write (the App lacks it, or the installation has not approved it), a push goes with `contents: write` alone even with the first switch on; if they cannot be read, the push is refused with `app_permission_missing`. With `contents: write` alone, GitHub then refuses only a push that changes `.github/workflows/` files. The commits that get pushed are written by the agent, so with this permission a `.github/workflows/` file the agent edited would also be pushed and run in CI. Also protect the default branch with a repository ruleset ([Protecting the default branch](#기본-브랜치-보호)).

### The App's Setup URL

An App made in the console gets its Setup URL filled in as `<CONSOLE_ORIGIN>/settings/workspace/integrations/github`. If you connected an App that already existed, set **Setup URL** to this address in the App's settings on GitHub (Developer settings > GitHub Apps > the App > General). After you add an organization, GitHub sends the browser back to this address, and the console records the installation from what comes back. For an account that already has the App installed, GitHub returns to the console after you save the installation's settings only when the App's **Redirect on update** is on.

<a id="기본-브랜치-보호" />
### Protecting the default branch

The platform pushes only to the session's `agent/<session-id>` branch (`agent/<session-id>-<suffix>` when the request body gives `branch`) and refuses the default branch. Block it once more on GitHub.

1. In the repository's Settings → Rules → Rulesets → New branch ruleset, set Target to `Include default branch`.
2. Turn on **Restrict updates**, **Restrict deletions** and **Block force pushes**. To accept only merges a person reviewed, also turn on **Require a pull request before merging**.
3. Do not put the App in the Bypass list.

- A separate ruleset that only applies **Block force pushes** to `agent/*` branches also stops anyone other than the platform from rewinding those branches.
- If `agent/*` pushes need no CI, add `agent/**` to the workflow's `on.push.branches-ignore`. It only affects workflows that were not changed, so use it together with not granting the `Workflows` permission.
- A skill's auto-sync does not read GitHub's branch protection rules or pull request reviews. As long as the source is a branch, one owner or admin turns it on in the GitHub sync section of the skill's page (a tag or a commit is refused with `not_branch`). Once on, a version that passes the fixed-rule checks is approved with no person's review and becomes the current version. So whoever can push to that branch, a person or an App, can change the skill. Decide who can push with GitHub's rulesets. Automatic approval turned on in an earlier version is turned off by the upgrade; turn it on again per skill to use it.
- With auto-sync on, fixed-rule checks compare a version with the approved one before it. With no approved version, every file counts as added. If it adds a script or executable file, changes more than 300 lines, names a new URL host, adds invisible Unicode or an instruction-like sentence, or changes `description`, only that skill's version stays pending (`checks_failed`) and a person approves it; the other skills of the same push are still approved. Turning it on checks once too, and approves a version that was waiting when it passes the rules. The rules caught and their files show on the skill's page and in the review. New URL hosts are read from a Markdown file as CommonMark renders it and from an HTML file as a browser parses it (URLs in every attribute value and in text and comments, unused link definitions included); any other file is read as written. A Markdown or HTML file over 256 KiB, or one that cannot be rendered, cannot be judged and fails the new URL rule. URLs a script assembles, other encodings such as base64, and plain-text URLs broken across lines are not read, and a plain-text URL is read as ending at whitespace. Such content is approved without being caught, so turn auto-sync on only for a branch whose pushers you trust.

### Git skill webhook

A skill registered from GitHub finds new versions through a push webhook, a check once a day and the console's "Check now". The webhook works only when GitHub can reach this API. An installation GitHub cannot reach works with the other two.

An owner saves this API's `https` address that GitHub reaches from the internet as the webhook entrance under **Settings > Integrations > GitHub** (`PUT /v1/github-webhook-settings`, audit record `update_github_webhook_settings`). It takes no query, fragment or account details, and a path prefix is kept. The webhook address is `<saved address>/v1/github/webhook`, one for the whole installation. Left empty, there is no webhook. `GITHUB_WEBHOOK_BASE_URL` is only the first default, carried in once on the first start while nothing is saved ([upgrade](/run-server/self-hosting/upgrade-compose#웹으로-옮긴-github-webhook-입구-주소)).

- With an address saved, a writer App newly created in the console gets the webhook address and the `push` event in its manifest, and the webhook secret GitHub returns is stored encrypted like the App key. If the address changed while it was being made, completing sets that App's webhook URL to the address saved now. If GitHub refuses, the completion screen does not move on to the install screen and shows why (`webhook_update` in the response). The owner retries there or goes on to install.
- When a changed address is saved, Werft sets the webhook URL of every App whose webhook secret is stored, once per App and in other workspaces too: it makes an App JWT with that App's key and calls `PATCH /app/hook/config` with the URL only. The secret and content type stay. Before saving, the screen shows which Apps change and which are also connected in other workspaces. After saving, an App GitHub did not take stays listed with its reason (`github_rejected`, `url_refused`, `github_unreachable` or `key_unreadable`) and **Retry** (`POST /v1/github-webhook-settings/retry`). The address stays saved either way, and a failed App keeps its old URL on GitHub. Clearing the address changes no App.
- Werft does not change an App added with its key and no webhook secret. For such an App, turn on **Active** in the App settings on GitHub (General → Webhook), enter **Webhook URL** and **Secret**, then turn on the **Push** event under Permissions & events. An owner or admin enters the same secret with `PUT /v1/workspaces/{id}/github-apps/{role}/webhook-secret`. From then on, a changed address changes this App too.
- The receiving path is the unauthenticated `POST /v1/github/webhook`, and an event is handled only after the body's `X-Hub-Signature-256` signature is verified. A missing or wrong signature is `401`, a body over 64 KiB is `413`, and going over the per-App per-minute limit is `429`.

<a id="토큰-발급이-실패할-때" />
### When token issuance fails

Clone, push and pull requests use installation tokens the API gets with the App key. When issuance fails (wrong key or installation, the App uninstalled, a GitHub outage), the repository route closes with `503`, and clone fails at startup with the session attention `STARTUP_FAILED`. Read `status` on the `GitHub request failed` line (`request: installation token request`) in the API log.

| status | What to check |
| --- | --- |
| `401` | Whether the App ID and the private key are a pair |
| `404` | Whether the installation includes the repository |
| `422` | The repository name |

- If the console App is not installed on the repository, the same `503` comes with `GitHub App is not installed on <owner>/<repo>`.
- For a repository that cannot be read without a login (a repository that does not exist, a private repository outside the installation), clone fails with `could not read Username`. An address GitHub redirects, such as an `http://` URL, fails with `upstream redirected`, so change the catalog URL to `https://`.
- The API container must reach `api.github.com:443`, and the egress proxy must reach `github.com:443` (`EGRESS_CREDENTIAL_ALLOWLIST`). Putting `github.com` in the forward list (`EGRESS_ALLOWLIST`) makes the proxy refuse to start.

<a id="github-enterprise-server" />
### GitHub Enterprise Server

Console Apps use github.com only. For a GHES repository, write the App directly in a settings document and import it ([Settings document import and export](/run-server/self-hosting/reference/configuration#설정-문서-가져오기내보내기)).

```json
{
  "version": 1,
  "connections": {},
  "repositories": {
    "ghes-app": {
      "url": "https://<ghes-host>/<owner>/<repo>.git",
      "branch": "main",
      "auth": {
        "kind": "github_app",
        "app_id": 123456,
        "installation_id": 7890123,
        "stored": true,
        "api_base": "https://<ghes-host>/api/v3"
      }
    }
  }
}
```

- After the import, an owner or admin enters the RSA private key PEM with `POST /v1/installation/settings/repositories/{id}/credential` (there is no console screen). Until then the repository is `needs_value` and sessions do not run. Use the same path to change the key.
- `api_base` accepts `https` only, except that a private host inside the operator's network may use `http`. Changing `app_id`, `installation_id` or `api_base` changes the binding, and existing sessions of that repository become `CATALOG_MISMATCH`.
- Open the API's way out to `<ghes-host>:443`, and add `<ghes-host>:443` to the proxy's `EGRESS_CREDENTIAL_ALLOWLIST` (`EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST` for a private address).

## What the user does

To use GitHub, an admin first turns on repositories in the agent's GitHub tab. A switch saves as soon as it is flipped. A new agent (one whose release has no GitHub settings either) has no GitHub tools in its sessions until this tab is first saved, and turning on a repository is usually that first save. When that first save is a repository switch, it also saves the push approval defaults (Approve before push off, Push to attached repositories allowed), so sessions that start after it push without human approval. To require approval, change the push approval section in the same tab and save it in the save bar.

1. Create a session with that repository's `repository_id` ([Start](/sessions/start)).
2. [Request](/approvals/request) and [approve](/approvals/approve) the result. When the request becomes `pushed`, the `agent/<session-id>` branch exists in the repository.
3. Open the PR. This needs `sessions:approve`. The examples below use the `sessionId` and `push` from [Request](/approvals/request) and [Approve](/approvals/approve) (`SID` and `PUSH_ID` in the HTTP API).

If a PR from that branch is already open, no new one is opened and that PR is returned (`created: false`). This call does not approve or merge PRs, and it does not choose reviewers or labels.

4. Add a comment. If a comment with the same `marker` (default `status`) already exists, it is edited instead of adding a new one.

Titles, bodies, and comments are sanitized before they are sent to GitHub. Lines that look like secrets are masked, and `@mentions` and closing keywords such as `Closes #N` are rewritten so they trigger no notification or automatic close.

The platform adds a tail to the end of the PR body: the session id and commit, the session's address, the agent and release, who started the session and how, and who requested the push (`Requested by`, the login without `@` so nobody is notified). Push to the branch again and ask for the PR again, and only the tail changes to the new commit; the text a person wrote above it stays.

The agent in a session does the same work with built-in MCP tools: `open_pull_request` opens the PR, `update_pull_request` changes its title and body, and `comment_pull_request` comments on it. `close_pull_request` and `reopen_pull_request` close a PR that a push request of this session opened, without merging it, and reopen it. No person approves these. The agent cannot close a PR from another session, or one in a repository it is not allowed. Closing a closed PR, or reopening an open one, changes nothing and answers `changed: false`. A merged PR is refused with `PULL_REQUEST_MERGED`. Closing does not delete the `agent/<session-id>` branch, so the PR can be reopened.

`get_pull_request` reads the title, body, state and head of the PR that a push request of this session opened. It leaves out the platform tail and replaces lines that look like secrets with `[REDACTED]`. When the body, with the tail left out and secrets hidden, is over 64 KiB, it comes back cut, with `body_truncated: true` and `body_sha256: null`. The body is text people wrote, so the answer carries `untrusted: true`. Pass its `body_sha256` to `update_pull_request` as `expected_body_sha256`: if someone edited the body after the read, nothing is written and the call is refused with `body_changed`. A body sent with that value that would have to be cut is refused with `body_too_long` instead. A body read cut has no hash, so the agent cannot rewrite it (`body_unverified`); changing only the title still works. Reading follows the GitHub switch and the repository scope too.

When both the agent's GitHub tab and the workspace ceiling have **Merge its own pull requests** on, `merge_pull_request` squash-merges that PR. With either off, the call is refused with `github_refused` (`reason_code` `merge_off`) before GitHub is called, and `details.off_in` names the side that is off. A repository the session attached merges under the same switches, but the PR merged must be one the platform opened on GitHub for a push request of this session. A PR the platform did not open, such as one it found on the branch and adopted, is refused with `github_refused` (`reason_code` `not_own_pull_request`). Another session's push request is `not_found`, and a push request with no PR recorded is `no_pull_request`. In an attached repository the switches are read before the repository lists: with a switch off it is `merge_off` even for a repository outside the lists, and with both on such a repository is `repository_not_allowed`. With the agent's GitHub off it is `github_disabled` whatever the switches. The platform reads no check to decide for GitHub, and does not send a merge GitHub refused a second time. The merge is pinned to the commit the push request pushed: a PR whose head is another commit is refused with `head_moved`, and a PR GitHub will not merge now (a required check pending, a review needed, an open conversation, a conflict) is refused with `merge_blocked`. That refusal's `details` state what GitHub reported (`mergeable_state`, `mergeable`, `draft`) and a `reason` sentence saying which condition failed; the reason names the state, it does not name which required check or review. So is a PR moved to another base than the one it was opened against, or one whose base is another open PR's head (a stacked PR), because GitHub's asynchronous merge also merges the pull requests it is stacked on. When GitHub accepted the merge but it has not finished within the wait, the call answers `forge_failed`; the merge may still complete, so check the PR and call again. A PR already merged on the same commit is answered with `changed: false`; one merged on another commit is refused with `head_moved`. A PR closed without a merge is refused with `pull_request_closed`. There is no admin bypass, no auto-merge and no other merge method. The merge request is sent with rule bypass off (`bypass_rules: false`) to GitHub's asynchronous merge API, so even if the author App is on a ruleset's bypass list it cannot skip required checks and reviews with that permission. Keeping the merging App off bypass lists is still the safer setup. A workflow that merges PRs, put on an agent's Actions allow list, is outside this switch.

<a id="push가-거절되는-경우" />
## When a push is refused

The API pushes an approved request within a few seconds. It sends the one commit the request pinned to that branch (`refs/heads/agent/<session-id>` or `refs/heads/agent/<session-id>-<suffix>`) of that repository and never force-pushes. If the same commit is already there, the request is simply `pushed`. On failure, `refusal` in the `push` receipt gives the reason.

| `refusal` | Error code | Meaning |
| --- | --- | --- |
| `non_fast_forward` | `REVISION_CONFLICT` | The remote branch's commit is not an ancestor of the commit to push |
| `target_refused` | `FORBIDDEN` | The branch is neither `agent/<session-id>` nor `agent/<session-id>-<suffix>` |
| `default_branch` | `FORBIDDEN` | The branch is the catalog's branch or the remote's default branch |
| `no_push_credential` | `FORBIDDEN` | There is no credential to push to that repository |
| `catalog_changed` | `CATALOG_MISMATCH` | The repository's URL or auth changed after the request, or the entry was removed. Nothing is sent to the remote. Request again and get a new approval |
| `checkpoint_unavailable` | `CHECKPOINT_UNAVAILABLE` | The pinned checkpoint could not be read or verified |
| `lease_expired` | `LEASE_EXPIRED` | The push went past its lease several times without finishing. A new request can be made |
| `push_failed` | `BACKEND_UNAVAILABLE` | Token issuance failed, the remote refused, or the network failed. A push that changes workflow files without the `Workflows` permission also lands here |

Messages from the remote are not put in the receipt. The `Push refused` and `Push failed` lines in the API log carry the `push_request_id` and the reason. The API pushes directly, so the API container must reach the repository host.

## How the pull request opens after a push

When a push request carries a pull request request, the control-host opens the pull request once the push ends as `pushed`. The agent does not have to call `open_pull_request` in a follow-up turn. A stage that was already started is finished even if you restart the control-host. Over REST, calling `POST /v1/sessions/{id}/push-requests/{push_request_id}/pull-request?schedule=true` before the push ends returns 202 with `status: "scheduled"` instead of 409 `PUSH_NOT_PUSHED`, and the pull request opens as soon as the push ends. Without the `schedule` query, or on a push request made with `flow = legacy`, the call answers 409.

There is one pull request stage per push request, and its state moves like this.

| State | Meaning |
| --- | --- |
| `due` | The push is done and it is time to open the pull request. A failed attempt is tried again after a delay (up to 3 times) |
| `opening` | One control-host is opening it. If that one stops, another replica takes over |
| `opened` | The pull request is open and recorded. Its number and link are on the pull request row |
| `closed_unrecorded` | This push request's pull request was closed or merged before the platform recorded it. No new one is created |
| `uncertain` | The platform could not confirm whether a pull request exists (the lookup failed three times, or the first lookup returned a full page of 10 and more may be on the next), or more than one fits. The platform does not choose |
| `failed` | The pull request could not be opened. The reason is in `pr_error` |
| `cancelled` | The push failed, so there is no pull request to open. The reason is in `pr_error` |

Before opening, the platform looks the branch up in every state (open, closed, merged). That is why a retry after a lost answer does not create a second pull request. If a pull request is already open it is reused, and only its tail changes to the new commit. If the head of a pull request it found or created is not the pushed commit, nothing is recorded and the stage ends as `head_moved`. GitHub can show the old head for a moment after a push, so when that head is an ancestor of the pushed commit the stage waits for its next attempt instead. A head that is not an ancestor, or a compare that fails, ends it at once. The pull request that was created is not closed, so a person checks it. A marker in a pull request body can be written by anyone, so only pull requests with the same repository, head and base count as candidates.

The result arrives as a notice in the session thread (opened, could not open, already closed, could not confirm). The text follows the language of the person who started the session (not the requester) and is created once per result. A notice is created only when the session is tied to a Slack thread that is not muted or restricted; otherwise only the state changes and no notice arrives.

There is a known limit. If a process stops for a long time just before the call and wakes up so that an already sent request arrives late, one more pull request can appear on the same branch, and the platform does not look for it after opening. GitHub has no conditional create, so the platform only checks again right before the call and looks the branch up before opening. If more than one pull request fits at open time, it creates none, leaves the stage `uncertain` and notifies. It never closes one automatically; a person chooses on GitHub.

## Attaching a repository mid-session

A session of an agent with GitHub settings starts without a repository (an agent with no GitHub settings starts on its release's repository). While it works, the agent attaches only the repositories the task reads or changes, with the built-in MCP tool `attach_repository({ repository_id })`. It can attach only repositories listed in the agent release's GitHub settings (`github.repositories`) that the workspace ceiling allows. No person approves it; writing to that repository goes through push request approval, and a push to an attached repository goes without a person's approval only for an agent with push approval off and the attached-repository push policy on `allow` (one rule for every repository). The agent sees which repositories it can attach with `list_repositories` (attached ones `attached`, ones being fetched or that failed `pending` or `failed`, and ones not attached yet `not_attached`; a repository named by `repository_id` when the session was created is listed as `attached`). A session keeps the release it started with, so a repository added only to a later active release is listed apart as `allowed_in_newer_release`, and `attach_repository` refuses it with `allowed_in_newer_release` instead of `repository_not_allowed`. It does not need to be allowed again: a new session (in Slack, a new thread) can attach it. A session that runs on the agent's settings and keeps its own attached-repository list is different. A repository the agent turns on after the session started can be attached right away; if the agent takes one off the list, or turns GitHub off, the repositories it had attached (one named when the session was created included) are listed as `revoked`, and the platform refuses the agent's GitHub actions on them and a new attach of another repository. An attach of the repository named when the session was created does nothing and is answered as already attached, and the platform's own reading of recorded pull requests continues. The working copy is not deleted, and turning the repository back on makes it usable again.

A session created without `attached_repository_ids` starts with no repository attached (a session created with `repository_id` has only that one). Put the repositories it needs from the start in that list; the agent attaches the rest when it needs them. A push request sends one repository, so with several repositories you make one push request per repository.

If an attach fails on a connection error (an `upstream connection failed` answer, or HTTP 502 or 503), the failure is transient and says nothing about the repository. Trying again with the same arguments is safe. `repository_not_allowed` is a refusal by the agent's settings, not a connection failure, so trying again gets the same answer.

- The attached repository becomes a git remote named `repository_id` in the workspace, with its default branch fetched to `<repository_id>/<branch>`. The agent never sees a token.
- To change an attached repository, the agent makes a branch in the workspace with `git switch -c <branch> <repository_id>/<branch>` and commits there. `git worktree` asks a person, inside the workspace or outside it, in any permission mode that asks. A worktree or clone outside the workspace is not part of a checkpoint or a push. One inside it that git does not ignore is a nested repository the checkpoint refuses, and that turn's push is cancelled as `turn_ended_without_checkpoint`.
- Attaching the same repository again changes nothing and succeeds. While the fetch is running the tool answers `pending` with `final: false` at once. With `wait_seconds` (0 to 7, default 0) it holds the answer until the fetch ends or the seconds have passed; `final` is true once the fetch has ended.
- The fetch is limited to 300 seconds and 2 GiB. Past either, the attachment fails with the reason in `failure` (`fetch_timeout`, `fetch_too_large`).
- Each attachment leaves an `attach_repository` [receipt](/approvals/receipt): who asked and from which attempt, the repository, the release, the commit fetched, and the refusal reason (`repository_not_allowed` or `allowed_in_newer_release`).
- When the session restarts on another worker (a restore), the attached repositories' remotes are added again, at the commit the session first fetched rather than the branch's current tip. The code the session reads does not change when the remote branch moves or is rewritten in between. A CLAUDE.md in an attached repository is not read as instructions.
- When that commit is gone from the remote and cannot be fetched again, the repository is no longer attached. A `system` event (`subtype: "repository_restore_failed"`, `repository_id`, `commit`) is recorded once in the session events, and `list_repositories` shows it as `failed` (`failure: restore_failed`, with the recorded `commit`). Attaching it again fetches the branch's current tip.

## Link your GitHub account

The GitHub App's bot account (`<App slug>[bot]`) is always the commit author. Link your GitHub account and the commits of turns you request also carry your name in a `Co-authored-by:` trailer, so GitHub shows the commit as your contribution too.

1. On the "Member GitHub accounts" line under **Settings > Workspace > Integrations > GitHub**, an owner or admin picks the author App to link with (when there are several), puts the callback URL from the ⋯ menu in that App's Callback URL, and enters a client secret made in that App. Until then the link button is off.
2. In the GitHub row of **Personal settings > Linked accounts**, choose "Link" and approve on GitHub's consent screen. The platform reads only the GitHub account's id and login and keeps no GitHub token.
3. The linked row shows the line commits get (`Co-authored-by: <login> <<id>+<login>@users.noreply.github.com>`). After you unlink, turns requested from then on leave it out.

Turns requested from the web console, a personal API key, or Slack follow the link of the person who requested that turn. When several people ask in one session, each commit carries the requester of its own turn. A turn requested with an agent key or an operator key has no requesting person, so no co-author is added. Either way, commits carry an `Agent-Session:` trailer: the session's address where the operator has set the console's address, else the session's id. The last line of the Outputs tab in session details shows which case a session is.

A GitHub account links to one person only. Linking an account someone else already linked is refused.

## On the local stack

The local `sample-app` is registered with a GitHub App on the stack's own Git server, so an approved push becomes `pushed` and a PR can be opened. A PR request on a request that was never pushed, such as a rejected one, returns 409 `PUSH_NOT_PUSHED`. Check this with a request that ended as `rejected` in [Approve](/approvals/approve).
