## What you will do

Preserve the previous worker pin and support window, read upgrade-check results, then replace the published chart.

<a id="준비물" />
## Before you begin

Read target-version operator actions in the [changelog](https://github.com/JeongJaeSoon/werft/blob/main/CHANGELOG.md).

You need installation values, jq/helm/kubectl, the current deployed revision and worker-previous.json, and database/S3 backups. On kind, with one session waiting for an approval and one paused with a checkpoint, a `helm upgrade` and a `helm rollback` that kept the images and the schema and changed only `extraEnv` to restart the Pods (migrate had nothing to do) were run, and the hook order and the sessions' state, events and checkpoint continuity were checked (`deploy/kind/upgrade.sh`). Steps 1 and 2 of this page were also followed as written on kind: an upgrade that changes the control-host image, starting from the schema of the previous release's commit (the migrate Job completed and the new build's `/readyz` answered `schema: ok`), one that changes the worker image, sessions resuming on the previous image, and the approval of affected sessions. The chart was a file packaged in the form of a published chart. A `helm rollback` that takes the control-host image or the worker image back (a new schema under old code after a rollback) has not been verified by execution; only the direct check before a rollback was run. The [order for the profile-removal release](/run-server/self-hosting/upgrade-compose#프로필-제거-릴리스의-업그레이드-순서) (step 2 once, without step 1) was also followed on kind, starting from an installation of the published `v0.1.3` chart. The upgrade check answered `proceed`, `0270` emptied the sessions of `v0.1.3`, and a new session finished turn 1 on the new control-host and the new worker. With only the worker set back to the `v0.1.3` image on the same installation, a new session stopped with `STARTUP_FAILED` after three launches. Distinguish fixture rendering from published-chart installation.

Check activation order and rollback floors in the [shared gates](/run-server/self-hosting/upgrade-compose#실행-전-게이트). Use the Helm hooks and direct checks below instead of Compose-only commands.

Confirm [context, namespace, and fullname](/run-server/self-hosting/kubernetes#준비물). Test new control-host with the previous worker: complete turn 1 → remove worker Pod → complete turn 2 from checkpoint, with no API worker-request 400s. Look at turn 1 first: when the previous worker cannot read the new API's response, the API answers no 400, the worker exits right after it starts, and the session stops with `STARTUP_FAILED`. The profile removal release does not support this combination, so when you upgrade to it, check that turn 1 completes with the new control-host and the new worker ([Upgrade order of the profile removal release](/run-server/self-hosting/upgrade-compose#프로필-제거-릴리스의-업그레이드-순서)). `deploy/kind/up.sh` overrides `images.worker` through `--set`; use direct `helm upgrade`, not EXTRA_VALUES, to test previous workers.

## Steps

<a id="1-대상-chart와-제어-영역-우선-교체" />
### 1. Target chart and control plane first

Set VERSION to the exact chart version. Pass installation-specific values without `--reuse-values`. For protocol/manifest/usage changes, do not replace control-host and worker in one upgrade.

Skip this step when you upgrade to the profile removal release. Old workers cannot read that release's control-host answers, so no new session starts between step 1 and step 2. Replace the control-host and the worker together in one upgrade with step 2 ([Upgrade order of the profile removal release](/run-server/self-hosting/upgrade-compose#프로필-제거-릴리스의-업그레이드-순서)).

When you upgrade to the release that moves credentials named by env into the database (migration `0285_credential_carried_auth`), stop every old api before this step with `kubectl -n werft scale deploy/werft-api --replicas=0`, and wait for its pods to end with `kubectl -n werft wait --for=delete pod -l app.kubernetes.io/instance=werft,app.kubernetes.io/component=api --timeout=120s`. Once `kubectl -n werft get pods -l app.kubernetes.io/instance=werft,app.kubernetes.io/component=api -o name` prints nothing, run the `helm upgrade` below with `--set api.replicas=1` added. Scaling does not wait for the pods to end, and an api that is ending still runs its push executor while it drains requests (up to 35 seconds). The chart runs several api replicas by default, and one that has not read the move yet may fail a moved push request with `catalog_changed` or refuse a token reissue. After the api log shows the move (`… took its credential from …`), step 2 puts the replica count back to your values ([Credentials named by env move into the database once](/run-server/self-hosting/upgrade-compose#env로-가리키던-자격-증명은-db로-한-번-옮긴다)).

```bash
VERSION=<new-version>
DEPLOYED="$(helm -n werft history werft -o json | jq '[.[] | select(.status == "deployed")] | last.revision')"
TARGET_VALUES="$(helm show values oci://ghcr.io/jeongjaesoon/werft --version "$VERSION")" \
  && TARGET_RUNTIME="$(printf '%s\n' "$TARGET_VALUES" \
    | awk '/^  worker:/ {found = 1; next} found && /^  [^ ]/ {exit} found && /^    runtime: / {sub(/^    runtime: /, ""); print; exit}')" \
  && helm -n werft get values werft --all --revision "$DEPLOYED" -o json \
  | jq -e --argjson target "$TARGET_RUNTIME" '.images
      | .worker.runtime |= (($target | if type == "object" then map_values(null) else error("target runtime is not a JSON object") end) + .)
      | {images: {worker, workerPrevious, egressProxy}}' \
  > control-phase.json \
  && helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
    --namespace werft -f values-<installation>.yaml -f control-phase.json \
    --set-json 'upgrade.approvedSessions=[]' --timeout 10m \
  && kubectl -n werft rollout status deploy/werft-api --timeout=600s
```

This intermediate upgrade applies the new chart's control-host while retaining current worker/egress proxy. Verify migration, replacement of **all** APIs, and readiness before proceeding. Image changes do not replace already-running workers; new images apply at the next launch.

`TARGET_RUNTIME` is the `images.worker.runtime` the target chart carries, and `jq` lays every key of it down as `null` and puts the deployed runtime on top, because Helm merges the maps in values key by key. The target chart carries the runtime of its own worker image. A key the deployed runtime does not have keeps the target chart's value, which then sits on the worker image you run now. `null` removes a key the chart carries. A `null` for a key the chart does not carry stays as a value and the render fails, so the keys are read from the target chart, not written by hand. The commands are joined with `&&`: when `helm show values` fails, when the runtime line of the worker entry is not a single-line JSON object, or when the deployed values cannot be read, the commands after it do not run. An installation made without a runtime loses all of the chart's keys and stays without one, as it is now; an installation made from a published chart keeps exactly its deployed runtime. Without these `null`s, an installation made without a runtime gets the current worker image configured with the target chart's runtime: the upgrade check passes, but the scheduler refuses that image and no new session launches ([Troubleshooting](/run-server/self-hosting/upgrade-kubernetes#자주-막히는-곳)).

<a id="2-최종-worker와-proxy-교체" />
### 2. Final worker and proxy replacement

Published charts include `images.worker.runtime` and leave `images.workerPrevious` empty, because previous images vary per installation. A worker-digest change is `refused` unless target images.workerPrevious equals the currently deployed worker; approval cannot bypass this ([checks](/run-server/self-hosting/upgrade-kubernetes#3-검사-결과와-예외)). Save the current image in a file and pass it too. Pass this file unchanged also when you upgrade to the profile removal release. The image in it (a worker built before the profile removal) is outside the support window, but no session launches on it ([Upgrade order of the profile removal release](/run-server/self-hosting/upgrade-compose#프로필-제거-릴리스의-업그레이드-순서)).

```bash
VERSION=<new version>
DEPLOYED="$(helm -n werft history werft -o json | jq '[.[] | select(.status == "deployed")] | last.revision')"
CURRENT="$(helm -n werft get values werft --all --revision "$DEPLOYED" -o json | jq -r '.images.worker.digest')"
TARGET="$(helm show values oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  | awk '/^  worker:/ {found = 1} found && /digest:/ {print $2; exit}')"
echo "deployed ${CURRENT}"
echo "target   ${TARGET}"
PREVIOUS=worker-previous.json
if [ -n "$TARGET" ] && [ "$CURRENT" != "$TARGET" ]; then
  PREVIOUS=worker-previous.next.json
  helm -n werft get values werft --all --revision "$DEPLOYED" -o json \
    | jq '{images: {workerPrevious: .images.worker}}' > "$PREVIOUS"
fi
set -- -f values-<installation>.yaml
if [ -f "$PREVIOUS" ]; then set -- "$@" -f "$PREVIOUS"; fi
if helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  --namespace werft "$@" --timeout 10m; then
  if [ "$PREVIOUS" != worker-previous.json ]; then mv "$PREVIOUS" worker-previous.json; fi
fi
```

Without `--revision`, a failed upgrade makes get values return that attempted revision's candidate image. When digests differ, save current into a candidate file, replacing worker-previous.json only after successful upgrade. Failed upgrades leave the preserved file untouched. With identical digests, pass the existing file unchanged. An upgrade retaining the first installation's worker may have no file yet; that is valid.

An installation that deploys the Codex worker (one that copies the chart's `images.workerCodex` values into `images.worker`) reads `TARGET` from that entry: change `/^  worker:/` in the `awk` to `/^  workerCodex:/`. Left as it is, the script compares against the digest of the Claude image the installation does not deploy, and picks the wrong previous-image file. On kind, an upgrade from the Claude worker to the Codex worker run that way passed the old `worker-previous.json` and stopped as `refused` (not approvable).

- Keep `worker-previous.json` beside installation files and pass it on subsequent upgrades. Omitting it when the worker digest is unchanged drops the deployed previous image. Checks then compare sessions and refuse if any match neither target current/previous combination or lack recorded combinations (approval can bypass this). If omitted accidentally, restore the file rather than approving. With no affected sessions and empty upgrade.approvedSessions, checks pass; stale approvals cause refused. See “What checks do not cover” below. Main charts merged the same day can share worker digests.
- Do not use `--reuse-values`: old chart defaults can leave old images under a new chart version.
- Do not pass all of `helm get values --all` as values; old digests override the new chart. Extract only .images.worker.
- Charts published from `v*` tags follow the same procedure.

Do not pass control-phase.json to the final upgrade. Replace worker-previous.json only on success and retain it for future upgrades. Clear approvals each upgrade and inspect the new affected list.

<a id="이미지-목록-설치의-upgrade" />
#### Upgrading an image-list installation

An installation that sets its worker images with `images.workers` (one that runs Claude and Codex together) builds its values file with the target chart's `files/next-workers.jq` instead of the `images.worker` commands above. Converting a single-image installation to a list for the first time uses the same procedure. The target release's two worker image entries are in the same chart's `files/release-images.json`. Do not upgrade a list installation with a chart that lacks these two files (a release from before this procedure).

```bash
VERSION=<new version>
rm -rf target-chart \
  && helm pull oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" --untar --untardir target-chart
# deployed_values: the values of the deployed revision; next_workers <control|final>: the values file
deployed_values() {
  DEPLOYED="$(helm -n werft history werft -o json | jq '[.[] | select(.status == "deployed")] | last.revision')" \
    && helm -n werft get values werft --all --revision "$DEPLOYED" -o json > deployed-values.json
}
next_workers() {
  jq -n -f target-chart/werft/files/next-workers.jq --arg phase "$1" \
    --slurpfile deployed deployed-values.json \
    --slurpfile release target-chart/werft/files/release-images.json \
    --argjson known "$KNOWN"
}
```

**Step 1 (control plane).** A list installation passes the deployed list as it is. Helm replaces a list whole instead of merging it key by key, so there is no `null` overlay for runtime keys. Instead the digest and runtime of `images.worker` and `images.workerPrevious` are cleared: a published chart fills `images.worker`, and the chart refuses single values beside a list. When converting a single-image installation for the first time, do step 1 above unchanged (`next_workers control` refuses a single-image installation).

```bash
KNOWN='{}'
deployed_values && next_workers control > control-phase.json \
  && helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
    --namespace werft -f values-<installation>.yaml -f control-phase.json \
    --set-json 'upgrade.approvedSessions=[]' --timeout 10m \
  && kubectl -n werft rollout status deploy/werft-api --timeout=600s
```

**Step 2 (final list).** The target release's two images are added to the deployed images: the deployed list for a list installation, or the deployed `images.worker` and (if set) `images.workerPrevious` for a single-image installation. Do not pass `worker-previous.json`; the previous image is read from the deployed values.

```bash
deployed_values && next_workers final > workers.json \
  && helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
    --namespace werft -f values-<installation>.yaml -f workers.json \
    --set-json 'upgrade.approvedSessions=[]' --timeout 10m
```

When converting a single-image installation for the first time, put each deployed image's `releasedAt` in `KNOWN` by digest, and its runtime too if it was deployed without one. The program does not read `images.worker.releasedAt` from single values: it is the chart default and may not match the digest the installation set. Take the values from the deployed release's manifest; `releasedAt` is the committer time of that release's commit. If the Codex image was deployed as `images.worker`, change the `IMAGE=` line to `IMAGE=worker-codex RUNTIME=workerCodexRuntime RELEASED=workerCodexReleasedAt`. If `images.workerPrevious` is set, build one more entry from its release's manifest and merge the two.

```bash
TAG=<the deployed release, e.g. v0.2.0>
IMAGE=worker RUNTIME=workerRuntime RELEASED=workerReleasedAt
mkdir -p "$TAG" && curl -fsSL -o "$TAG/release-manifest.json" \
  "https://github.com/JeongJaeSoon/werft/releases/download/$TAG/release-manifest.json" \
  && AT="$(curl -fsS "https://api.github.com/repos/JeongJaeSoon/werft/commits/$(jq -r .commit "$TAG/release-manifest.json")" | jq -er .commit.committer.date)" \
  && KNOWN="$(jq -c --arg at "$AT" --arg i "$IMAGE" --arg r "$RUNTIME" --arg t "$RELEASED" '{(.images[$i].digest): {runtime: .[$r], releasedAt: (.[$t] // $at)}}' "$TAG/release-manifest.json")"
```

The program builds the list like this:

- Each engine's images go newest `releasedAt` first, and up to two unretracted images are kept; a third is dropped. The [pre-upgrade check](#3-검사-결과와-예외) judges the sessions that need a dropped image: if the images left cannot restore the checkpoint of a launch holding a slot on it, the result is `refused` with no approval possible, and a session with only a checkpoint is listed as affected.
- A digest is listed once. A deployed retracted image stays retracted even when the target release names the same digest. A retracted image is kept only when it is newer than the oldest image kept; an engine with no unretracted image keeps all its retracted images (which is not the same as the engine leaving the list). Once an old retracted image is dropped, checkpoints of its combination stop as `incompatible_checkpoint` instead of `runtime_retired`.
- It fails without writing a values file when a deployed image has no runtime or `releasedAt`, when a target image is not newer than every deployed image of its engine, when one digest is given with another runtime, time or repository, and when two images of one engine have the same time. `releasedAt` is a commit time and can differ from the publishing order: a chart of a tag on a commit older than the deployed image, and a chart that rebuilt by tag push a commit main had already published (another digest, the same time), stop here. Upgrade with a newer release's chart instead.

The commands are joined by `&&`, so `helm upgrade` does not run when the program fails. A failed upgrade, run again, gives the same file from the same deployed revision, so there is no file to keep. Clear the approval list every time as above. An engine you do not use may be deleted from `workers.json` before passing it; deleting an engine the deployed images had makes the upgrade one that drops an engine (see "An upgrade that drops an engine" below).

This procedure was followed on kind (the `list` and `next-list` steps of `deploy/kind/upgrade.sh`). A single image A installed without a runtime became [B, A, C] (B is A rebuilt, C the Codex image), and after a control phase that list became [D, B, C]. Both upgrades were `proceed` with no approval. A session waiting for an approval on A went on in the same Pod and finished after A left the list; a paused session resumed from its checkpoint on B, then on D. No Codex session ran on kind.

### 3. Check results and exceptions

<a id="업그레이드-전-검사" />
#### Pre-upgrade check

Before migrate (hook weight -5), helm upgrade runs upgrade-check using the target release's api image. It reads combinations from every session's uncollected checkpoint pointer and selects sessions resumable on neither target images.worker nor images.workerPrevious. Pointers committed before combination recording are also selected. It also reads the images of launches still holding a slot (unclaimed ones included). Job logs contain one JSON result line.

```bash
kubectl -n werft logs job/werft-upgrade-check
```

| `verdict` | Exit | Upgrade | Meaning |
|---|---|---|---|
| `proceed` | 0 | Continues | upgrade.approvedSessions exactly matches affected sessionId values. Approvals must be empty if none are selected, if worker is unchanged and every deployed image stays under the same runtime, or if never deployed |
| `refused` | 2 | Stops | Any approval mismatch, including stale values. With unchanged worker but removed/changed previous, sessions matching neither target combination or lacking recorded combinations are selected. Also returned when no target image restores the checkpoints sealed by the deployed worker or by a launch holding a slot (a rebuild with the same combination restores them; an image deployed or a launch reserved without a runtime needs the same digest in the target); that case cannot be approved. A retracted target image does not count as one that restores them. When a launch on the image being retracted holds a slot, list a fixed image of the same combination beside it, or upgrade once that slot is free |
| `check_failed` | 1 | Stops | Database unreadable, runtime combinations unreadable/missing when required below, or deployed worker unknown. Also if a deployed worker exists without UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS (pass empty if none), or scheduler Deployment is absent but database has sessions/partial schema. No bypass exists |

images.worker.runtime is optional for first installation; upgrade requirements depend on deployed/target state.

| Deployed state | Target | Without runtime |
|---|---|---|
| No scheduler Deployment; database empty or without sessions (first-install retry) | Any worker, no images.workerPrevious | `proceed` |
| One worker image without runtime/previous | Same worker, no images.workerPrevious | `proceed` |
| One worker image without runtime/previous | Different worker | `check_failed`; supply images.worker.runtime and images.workerPrevious containing current image |
| Runtime or previous exists | images.worker.runtime omitted | `check_failed`; combinations are needed to compare sessions |

See [API configuration](/run-server/self-hosting/reference/configuration) for extracting runtime. Minimal values can start without it; the first worker-changing upgrade adds runtime for both images.

An unchanged images.worker with removed/changed images.workerPrevious compares sessions. Unmatched or unrecorded combinations cause refused; exact approval passes. Unrecorded sessions are always selected as on image-changing upgrades. With absent deployed previous, or one unchanged under the same runtime, no session comparison occurs: empty approvals proceed, stale approvals refuse. The same digest declared under another runtime is compared like a removed image. Rebuilds with different image references but identical combinations can drop previous without affecting sessions, since current still resumes them.

If selected sessions may fail to resume, put exactly that list in values and rerun. Approval does not change session state. `no_image` sessions stop as recovery_required on resume, with no worker launched. The session's `attention` says `RESTORE_FAILED`, `incompatible_checkpoint`, so after resuming an approved session look at its `admission_state` and `attention`. `unrecorded` sessions launch current, then restoration either succeeds or stops as recovery_required.

```bash
helm upgrade --install ... --set-json 'upgrade.approvedSessions=["<sessionId>", ...]'
```

Approvals remain in release values. Clear them every upgrade with `--set-json 'upgrade.approvedSessions=[]'`, then reread and approve that upgrade's list. Leftover approvals refuse if different from affected, but still pass if identical and support-window requirements hold.

**Each engine is judged on its own.** When the deployed and target images span more than one engine, as in an installation that runs Claude and Codex from one image list, the check above runs per engine. An engine stays when the target lists any image of it, even only retracted ones. If no target image restores what that engine's deployed newest image seals, the verdict is `refused`, which no approval passes. A deployment of one engine, or one with an image deployed without a runtime, is judged as one group, as before.

**An upgrade that drops an engine.** When the target lists no image of an engine, the upgrade drops that engine. The check then stops protecting that engine's newest image. Instead it lists every session of that engine that is not closed as `no_engine_image`, checkpoint or not. An open session whose runtime kind this host does not know, or that has none, is `no_engine_image` too. A session with a checkpoint is judged by its checkpoint first, so it is listed as `no_image` or `unrecorded`. Each session is listed once, with one reason. A launch of that engine still holding a slot, claimed or not, is `refused`, which no approval passes. Run the upgrade again once its slot is released. Approved sessions end up like this:

- A session without a checkpoint waits without taking a slot. The API shows it with attention `CATALOG_MISMATCH`.
- A session with a recorded checkpoint stops before launch as `recovery_required` (attention `RESTORE_FAILED`, reason `incompatible_checkpoint`).
- A session whose checkpoint has no recorded runtime waits.
- New sessions of that engine cannot be created, from the API or from Slack (`UNSUPPORTED_CAPABILITY`). An engine left with only retracted images is not dropped, so that refusal does not apply to it.

Dropping an engine does not itself delete a session or retire its restore point. Ordinary retention still applies, such as checkpoint GC and the workspace TTL of stopped sessions.

**A race between the check and the rollout.** The check sees only the launches holding a slot when it runs. After the check and before the rollout, the old scheduler may still reserve a launch of the dropped engine. Its worker finds no session to claim from the new control-host and exits. The scheduler does not count that exit as a failed launch, and gives the launch back instead of building it again (as it does for a launch on a retracted image). The session then waits or stops as above. A worker that claimed after the check and is already running is not stopped by this setting alone.

**Bringing an engine back.** To run the dropped engine's sessions again, upgrade with an unretracted image of that engine back in the list. The image must ship the session's runtime version. Clear the approval list. Waiting sessions then launch on that image on the next pass. Sessions stopped with `incompatible_checkpoint` are retried with `retry_restore`.

The Job receives JSON `UPGRADE_APPROVED_SESSIONS`, deployed `UPGRADE_DEPLOYED_WORKER_IMAGE`, `UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS` (empty if absent), and their runtimes as `UPGRADE_DEPLOYED_WORKER_IMAGE_RUNTIME` and `UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS_RUNTIME`. A deployed scheduler running an image list (`WORKER_IMAGES`) passes it as `UPGRADE_DEPLOYED_WORKER_IMAGES`. Chart lookup reads these from the scheduler Deployment and prefixes each name with `UPGRADE_DEPLOYED_`. A deployed image without a runtime is compared by digest alone. On kind, real `helm upgrade` runs verified the following. `lookup` reads the deployed worker image and the deployed previous image. An upgrade that removes the previous image selects the sessions sealed on it as `no_image` and stops as `refused`; approving exactly that list gives `proceed`. An upgrade that changes the worker image and makes the current worker image the previous one gives `proceed`. An upgrade that keeps the worker image and replaces only the previous image with another one, image lists, and the judgement of launches holding a slot have not been verified by execution (only by tests). Chart-provided `UPGRADE_DEPLOYED_STATE` alone permits runtime-table exceptions. `absent` means scheduler Deployment missing but namespace default ServiceAccount readable, requiring get permission on it. `unpinned` means Deployment without runtime/previous. `helm template`/client dry-run lookup reads nothing, leaving every deployed value empty and making such Jobs check_failed. Server dry-run reads the cluster but executes no hooks, so cannot establish a verdict.

Checks trust DATABASE_URL to point to this installation; another empty database can pass absent. No Job is created for first installation (pre-install) or scheduler.enabled: false. To keep Job/scheduler image inputs aligned, WORKER_IMAGE, WORKER_IMAGE_PREVIOUS, WORKER_IMAGE_RUNTIME, and WORKER_IMAGE_PREVIOUS_RUNTIME cannot be supplied through *.extraEnv, config.limits, or secrets.catalogEnv; rendering rejects them. Use images.worker/images.workerPrevious.

**Before `helm rollback`**, run the check directly in the api Pod because rollback does not run the hook. Supply target revision values from `helm get values --revision <revision>`.

```bash
kubectl -n werft exec deploy/werft-api -- env \
  UPGRADE_DEPLOYED_WORKER_IMAGE='<WORKER_IMAGE of the running scheduler>' \
  UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS='<WORKER_IMAGE_PREVIOUS of the running scheduler, empty if none>' \
  UPGRADE_DEPLOYED_WORKER_IMAGE_RUNTIME='<WORKER_IMAGE_RUNTIME of the running scheduler, empty if none>' \
  UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS_RUNTIME='<WORKER_IMAGE_PREVIOUS_RUNTIME of the running scheduler, empty if none>' \
  WORKER_IMAGE='<worker image of the target revision>' WORKER_IMAGE_RUNTIME='<its runtime JSON>' \
  WORKER_IMAGE_PREVIOUS='<workerPrevious of that revision>' WORKER_IMAGE_PREVIOUS_RUNTIME='<its runtime JSON>' \
  bun run apps/control-host/src/api/upgrade-check.ts
```

A typical worker-image rollback returns refused: when the current image carries a newer SDK/CLI, no image of the target revision restores the checkpoints it seals. A rollback to a rebuild with the same combination compares sessions. Unreadable settings/database return check_failed. Current-image workers keep producing that combination's checkpoints after rollback until they exit, beyond the check's view. affected lists only sessions selected at check time. Prefer roll-forward. If rolling back anyway, scheduler matches runtime combinations on resume; sessions matching neither target current nor previous stop as recovery_required, including newer SDK/CLI checkpoints made by surviving current workers during rollback.

With unchanged worker, rollback proceeds with empty approvals only if deployed previous remains identical in the target revision; stale approvals refuse. Removed/changed previous triggers session comparison as above. This direct command does not block rollback automatically. On refused, read affected and decide. Omitting deployed-previous env when deployed worker exists yields check_failed.

**What checks do not cover.** Unlike [Compose checks](/run-server/self-hosting/upgrade-compose), target images are not executed. Only pointer engine/SDK/CLI/profile digest scheme combinations are compared; actual profile digests are judged at restore. Writers are not stopped and rechecked afterward. Instead, the check passes only when a target image restores the checkpoints sealed by the deployed worker image and by the images of launches holding a slot at check time, so what those workers write afterward stays inside the target window. Sessions before their first checkpoint count when their launch holds a slot. Launches the deployed scheduler starts on the previous image after the check are not seen, so run an upgrade that drops or changes previous when no launch runs on it. Workers of older images that no deployed image restores either are not stranded by this upgrade and do not block it; their sessions are selected if existing pointers already record that combination, and are absent before their first checkpoint. Registry pullability is not tested; failures surface as launch failures. Whether `images.worker.runtime` is the value that image itself prints is not tested either: the upgrade passes when it is wrong. When the engine, SDK, CLI or profile digest scheme differs from what the worker writes in its claim, the scheduler refuses the image the first time a worker on it starts ([Troubleshooting](/run-server/self-hosting/upgrade-kubernetes#자주-막히는-곳)). Whether `restorableSchemes` matches what the image can really restore is not compared then either.

<a id="4-파일-카탈로그-설치에서-오는-경우" />
### 4. Migrate file-catalog installations

The old chart's catalog ConfigMap no longer exists in the new chart. Helm deletes old resources only after hooks, so pre-upgrade migrate optionally mounts it at /legacy-config and runs `settings seed --from-dir /legacy-config`. It imports nothing when the database already holds a connection or an MCP server, and once decided it never imports again, even with the ConfigMap still there. Change settings in the console after that. Partial files or invalid values fail the Job without changing Deployments.

1. Add PLATFORM_SECRET_KEY to the Secret first; preserve the same value if already present.
2. Remove catalog from values, then helm upgrade. Remove PLATFORM_CONFIG_DIR from api.extraEnv if present.
3. With an installed-version checkout and host Bun/kubectl, run `bun run settings:k8s export` to inspect additions. See procedure/rollback floors in [api-server.md](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md#설정-문서-가져오기내보내기).

## Troubleshooting

workerPrevious differing from the deployed image is an unapprovable refused. Omitting get values revision can read failed-upgrade candidates. helm template/client dry-run without lookup cannot substitute for actual upgrade checks.

When new sessions stay `queued` after an upgrade and the scheduler logs `Worker image refused: a worker on it claimed under another runtime than configured`, `images.worker.runtime` is not that worker image's value. An upgrade that removes the runtime again is stopped as `check_failed` (`WORKER_IMAGE_RUNTIME is not set`). Put the runtime the image prints ([API settings in the configuration reference](/run-server/self-hosting/reference/configuration)) in `images.worker.runtime`, write only the keys the chart carries but the image does not print (for example `restorableSchemes`) as `null`, and upgrade again. The sessions that waited launch after that.

An upgrade stopped as `refused` or `check_failed` still uses one Helm revision. Helm keeps 10 revisions by default, so after several stopped attempts the revision to roll back to is gone from the history. On kind, after eight stopped upgrades and two successful ones, the deployed revision before them answered `release: not found`. `helm rollback` cannot go to a revision that left the history, and saving its values does not change that. When you expect several attempts, give `helm upgrade` a larger `--history-max` (`0` is no limit). An upgrade with that option has not been verified by execution.

<a id="되돌리기" />
## Roll back

```bash
helm -n werft history werft
helm -n werft rollback werft <revision> --wait --timeout 10m
```

Rollback does not run migrate hooks (they are not pre-rollback). Database schema stays new; old builds can still report ready on later schemas because readyz checks only that their migration list is a prefix of applied migrations. Do not deploy irreversible migrations. A migration that can be reversed only down to some image (for example `0243`) has that floor written per image in the [Compose upgrade table](/run-server/self-hosting/upgrade-compose); do not roll back below it. Before reverting workers, read [incremental checkpoint rollback](/run-server/self-hosting/upgrade-compose#workercontrol-host-롤백과-incremental-checkpoint).

Roll back only after shared gates and the direct check establish viability. Without hooks, rollback does not automatically enforce checks. Prefer roll-forward.
