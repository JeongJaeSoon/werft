## What you will do

Preserve the previous worker pin and support window, read upgrade-check results, then replace the published chart.

> **Do this first: the Codex sandbox.** This chart changes the default of `codexSandbox`. Earlier charts created the installer DaemonSet and a ClusterRole by default; now the default (`codexSandbox.provider: disabled`) creates no cluster-scoped object. Upgraded as is, helm upgrade deletes the ClusterRole and the installer DaemonSet, and a Codex agent's input fails with `CODEX_SANDBOX_NOT_INSTALLED`. **If you use the Codex sandbox, put `codexSandbox.provider: installer` in your values before you upgrade.** An installation that places the profile through the Security Profiles Operator or a node image puts `external`. The old `codexSandbox.installer.enabled` is not accepted, and the render stops while it is set (`installer.enabled=true` is `provider: installer`, `false` is `external`).

<a id="준비물" />
## Before you begin

Read target-version operator actions in the [changelog](https://github.com/JeongJaeSoon/werft/blob/main/CHANGELOG.md).

You need installation values, jq/helm/kubectl, the current deployed revision and worker-previous.json, and database/S3 backups.

Check activation order and rollback floors in the [shared gates](/run-server/self-hosting/upgrade-compose#실행-전-게이트). Use the Helm hooks and direct checks below instead of Compose-only commands.

Confirm [context, namespace, and fullname](/run-server/self-hosting/kubernetes#준비물). Test new control-host with the previous worker: complete turn 1 → remove worker Pod → complete turn 2 from checkpoint, with no API worker-request 400s. Look at turn 1 first: when the previous worker cannot read the new API's response, the API answers no 400, the worker exits right after it starts, and the session stops with `STARTUP_FAILED`. The profile removal release does not support this combination, so when you upgrade to it, check that turn 1 completes with the new control-host and the new worker ([Upgrade order of the profile removal release](/run-server/self-hosting/upgrade-compose#프로필-제거-릴리스의-업그레이드-순서)).

## Steps

<a id="1-대상-chart와-제어-영역-우선-교체" />
### 1. Target chart and control plane first

Set VERSION to the exact chart version. Pass installation-specific values without `--reuse-values`. For protocol/manifest/usage changes, do not replace control-host and worker in one upgrade.

Skip this step when you upgrade to the profile removal release. Old workers cannot read that release's control-host answers, so no new session starts between step 1 and step 2. Replace the control-host and the worker together in one upgrade with step 2 ([Upgrade order of the profile removal release](/run-server/self-hosting/upgrade-compose#프로필-제거-릴리스의-업그레이드-순서)).

When you upgrade to the release that moves credentials named by env into the database (migration `0285_credential_carried_auth`), stop every old api before this step with `kubectl -n werft scale deploy/werft-api --replicas=0`, and wait for its pods to end with `kubectl -n werft wait --for=delete pod -l app.kubernetes.io/instance=werft,app.kubernetes.io/component=api --timeout=120s`. Once `kubectl -n werft get pods -l app.kubernetes.io/instance=werft,app.kubernetes.io/component=api -o name` prints nothing, run the `helm upgrade` below with `--set api.replicas=1` added. Scaling does not wait for the pods to end, and an api that is ending still runs its push executor while it drains requests (up to 35 seconds). The chart runs several api replicas by default, and one that has not read the move yet may fail a moved push request with `catalog_changed` or refuse a token reissue. After the api log shows the move (`… took its credential from …`), step 2 puts the replica count back to your values ([Credentials named by env move into the database once](/run-server/self-hosting/upgrade-compose#env로-가리키던-자격-증명은-db로-한-번-옮긴다)).

When you upgrade to the release that removes external credential sources (migration `0288_remove_external_credentials`), delete `secrets.catalogEnv` and `config.aws.secretsManagerEndpointUrl` from your values. While either is set the render stops (`secrets.catalogEnv is removed: credentials are entered in the console…`, `config.aws.secretsManagerEndpointUrl is removed…`). Model keys in the Secret no longer reach the api, so enter them in the console before upgrading. For disabled rows, `needs_value` and the settings document, follow [The release that removes external credential sources](/run-server/self-hosting/upgrade-compose#외부-자격-증명-출처를-없앤-릴리스).

When you upgrade to the release that makes the first owner from a one-time setup link, delete `secrets.bootstrapToken` from your values and `BOOTSTRAP_TOKEN` from the Secret. While the value is set the render stops (`secrets.bootstrapToken is removed…`). Nothing else changes for an installation that has an owner. Recovering after every owner is lost also goes through a setup link (`admin bootstrap-owner` in [Create the first owner](/run-server/self-hosting/users-and-keys#1-첫-owner-만들기)).

When you upgrade to the release that moves twelve settings (execution limits, session event archive, and workspace retention) to the web, pass your installation values as they are. `QUEUED_INPUT_LIMIT_PER_SESSION`, `STORAGE_LIMIT_BYTES`, `SESSION_COST_LIMIT_USD`, `SESSION_TOKEN_LIMIT`, `MAX_TURN_SECONDS`, and `PROVIDER_MAX_RETRIES` left in `config.limits`, and `api.workspaceEnforce` now go to the migrate Job only. The chart's `config.limits` default keeps only `EXECUTION_SLOT_LIMIT`. The same names or `PENDING_REQUEST_TTL_SEC` in `api.extraEnv` go to the migrate Job too; they also stay in the api pod, which does not read them. When a name is set twice, `api.extraEnv` wins. `MAX_TURN_SECONDS` and `PROVIDER_MAX_RETRIES` alone are picked as the scheduler, which started the workers, read them: the same name in `scheduler.extraEnv` wins over `config.limits`, and the two names in `api.extraEnv` are not carried. The workspace retention times, `EXECUTION_WORKSPACE_STOPPED_TTL_SEC` and `EXECUTION_WORKSPACE_PAUSED_TTL_SEC`, are picked the same way. A value left in `scheduler.extraEnv` still reaches the scheduler pod, which does not read it. An empty string there was a value the earlier scheduler refused to start on, so it is not carried and blocks the key. The archive's `sessionArchive.afterDays` and `dryRun` lose their chart defaults (180, `true`), and only a value set in your installation values goes to the migrate Job, as `SESSION_ARCHIVE_AFTER_DAYS` and `SESSION_ARCHIVE_DRY_RUN`; a `0` or `false` you set is carried as a value. The archive CronJob no longer gets either and reads them from the database on each run. Unlike the earlier chart, a value out of range no longer stops the render: migrate blocks that key instead. The Job is a `pre-upgrade` hook, so before any role starts it carries each value in once, for a key with nothing saved. Once the Job log shows `note: … was carried into Settings > Workspace > Execution limits`, delete that key from your values. A value outside the range is not carried in and blocks the key (`note: … was not carried in`) until a value is saved in the console. An installation that set none of them runs on the same defaults as the earlier chart ([Execution limits moved to the web](/run-server/self-hosting/upgrade-compose#웹으로-옮긴-실행-한도)).

When you upgrade to the release that takes the object store settings from one place, the render stops if any role's `extraEnv`, `config.limits` or `secrets.catalogEnv` holds a name starting with `AWS_` or `CHECKPOINT_OBJECT_` (`… must not be set through extraEnv, config.limits or secrets.catalogEnv`). No hook runs and no Deployment changes. The earlier chart put an `extraEnv` into that role alone, so a value in `api.extraEnv` won on the api only, while the checkpoint GC and session archive CronJobs and the scheduler ran on the chart's values. Move the values as follows: `S3_BUCKET` → `config.checkpoints.bucket`, `CHECKPOINT_OBJECT_STORE` → `config.checkpoints.objectStore` (`s3` or `disabled`), `CHECKPOINT_OBJECT_PROTECTION` → `config.checkpoints.protection`, `CHECKPOINT_OBJECT_ENCRYPTION_CHECK` → `config.checkpoints.encryptionCheck` (`enforce` or `warn`), `AWS_REGION` → `config.aws.region`, `AWS_ENDPOINT_URL` → `config.aws.endpointUrl`, `AWS_ENDPOINT_URL_SECRETS_MANAGER` → `config.aws.secretsManagerEndpointUrl` (delete it from the release that removes external credential sources on), and the two static keys → `secrets.objectStoreKeys` and the same names in the Secret. Other `AWS_` names (`AWS_ENDPOINT_URL_S3`, `AWS_ROLE_ARN`, `AWS_PROFILE` and so on) have no chart route; delete them. Give an IRSA role as an annotation on the api ServiceAccount, which both CronJobs use too. If moving the names leaves the values the pods get unchanged, that is all there is to do.

Before moving them, check whether the earlier chart ran split. If `api.extraEnv` holds one of these names with a value other than the chart's (`config.*`, defaults included), the session archive job may have moved events into a store the api does not read and deleted their database rows. An archive record holds the object key and version, not the bucket, so once the settings agree those events can no longer be read. Copying the bucket does not stand in for this, because version IDs change. Keep the api's value: the api wrote the checkpoints into its store. If `S3_BUCKET` or `AWS_REGION` in `scheduler.extraEnv` differed from the api's, aligning them changes the isolation stamp that carries them, and each worker is replaced once ([Upgrade compatibility](/run-server/self-hosting/explanation/compatibility)). Before upgrading:

1. Suspend the archive CronJob: `kubectl -n werft patch cronjob werft-session-archive -p '{"spec":{"suspend":true}}'`. `suspend` does not stop a Job already created. After suspending, wait until the command below prints nothing. It prints each Job this CronJob created that is neither `Complete` nor `Failed`, including one whose pod is still `Pending`. The CronJob's `status.active` is not used: it misses a Job when the controller fails to record it right after creating it. A list taken earlier misses the sessions an unfinished Job archives after it.

```bash
UID_=$(kubectl -n werft get cronjob werft-session-archive -o jsonpath='{.metadata.uid}')
kubectl -n werft get jobs -o json | jq -r --arg uid "$UID_" '.items[]
  | select(any(.metadata.ownerReferences[]?; .uid == $uid))
  | select(any(.status.conditions[]?; (.type == "Complete" or .type == "Failed") and .status == "True") | not)
  | .metadata.name'
```

2. Run `SELECT DISTINCT session_id FROM session_event_archives;` from your database client to list the archived sessions. With no rows, go to 4.
3. For each session, create a restore Job from the earlier chart's CronJob. It runs on the same store settings as the CronJob. Every Job must succeed, with `Session archive restored` in its log. Then `SELECT count(*) FROM session_event_archives;` must return `0` (a restore deletes those rows). Do not go on to 4 until it does.

```bash
kubectl -n werft create job "werft-archive-restore-$N" --from=cronjob/werft-session-archive --dry-run=client -o json \
  | jq --arg id "$SESSION_ID" '.spec.template.spec.containers[0].args += ["restore", $id]' \
  | kubectl -n werft apply -f -
```

4. Move the names in your values as above and run this step's `helm upgrade`. Then resume the CronJob with `kubectl -n werft patch cronjob werft-session-archive -p '{"spec":{"suspend":false}}'`. Helm does not manage `suspend`, so the CronJob stays suspended after the upgrade. The next archive run moves the restored events into the api's store again.

Pull the target chart and define the two functions used through step 2. The target release's two worker image entries are in the chart's `files/release-images.json`, and the program that builds the next values file is `files/next-workers.jq`.

```bash
VERSION=<new-version>
rm -rf target-chart \
  && helm pull oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" --untar --untardir target-chart
# deployed_values: the values of the deployed revision; next_workers <control|final>: the values file
deployed_values() {
  DEPLOYED="$(helm -n werft history werft -o json | jq '[.[] | select(.status == "deployed")] | last.revision')" \
    && helm -n werft get values werft --all --revision "$DEPLOYED" -o json > deployed-values.json
}
next_workers() {
  jq -n -f target-chart/werft/files/next-workers.jq --arg phase "$1" \
    --slurpfile deployed deployed-values.json \
    --slurpfile release target-chart/werft/files/release-images.json \
    --argjson known "$KNOWN"
}
# Drop the runtime the values files before them set, which Helm would merge with the next one
echo '{"images": {"worker": {"runtime": null}}}' > worker-reset.json
echo '{"images": {"workerPrevious": {"runtime": null}}}' > worker-previous-reset.json
```

```bash
KNOWN='{}'
deployed_values && next_workers control > control-phase.json \
  && helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
    --namespace werft -f values-<installation>.yaml \
    -f worker-reset.json -f worker-previous-reset.json -f control-phase.json \
    --set-json 'upgrade.approvedSessions=[]' --timeout 10m \
  && kubectl -n werft rollout status deploy/werft-api --timeout=600s
```

This intermediate upgrade applies the new chart's control-host while retaining current worker/egress proxy. What it retains is the images. The chart is applied as a whole, so the egress proxy's settings (the allowlist is an env value of its Deployment) take the new chart's values and the proxy Pods restart in this upgrade. An installation that sets `config.egress.privateAllowlist` itself reads [The release that moves the worker gateway to port 3200](/run-server/self-hosting/upgrade-compose#worker-gateway를-3200-포트로-옮긴-릴리스) first. Verify migration, replacement of **all** APIs, and readiness before proceeding. Image changes do not replace already-running workers; new images apply at the next launch.

`next_workers control` writes the deployed worker images and egress proxy as they are. For a single-image installation it writes the deployed `images.worker` and `images.workerPrevious` with `images.workers: []`. The published chart defaults to a list of the target release's two images, so without `images.workers: []` this upgrade would replace the worker images too. The target chart's `images.worker.runtime` is empty, so the deployed runtime stays as it is, and an installation deployed without a runtime stays without one. For a list installation it writes the deployed list ([Upgrading an image-list installation](#이미지-목록-설치의-upgrade)). The commands are joined with `&&`: when the chart cannot be pulled or the deployed values cannot be read, `helm upgrade` does not run.

When you upgrade to the release that checks workspace MCP servers by address, the proxy image is still the current one between steps 1 and 2, so a session's calls to a server on neither credential list get 403 (`egress_proxy_outdated`). They work again when step 2 finishes. See [the same section in the Compose page](/run-server/self-hosting/upgrade-compose#워크스페이스-mcp-서버를-주소로-검사하는-릴리스).

### 2. Final worker and proxy replacement

Published charts default to the target release's Claude and Codex images in `images.workers` and leave `images.worker` and `images.workerPrevious` empty. A single-image installation takes the entry of the engine it deploys from the target release's `files/release-images.json` into `images.worker` and passes it with `images.workers: []` (`worker.json`). The chart cannot know the previous image, which varies per installation. A worker-digest change is `refused` unless target images.workerPrevious equals the currently deployed worker; approval cannot bypass this ([checks](/run-server/self-hosting/upgrade-kubernetes#3-검사-결과와-예외)). Save the current image in a file and pass it too. Pass this file unchanged also when you upgrade to the profile removal release. The image in it (a worker built before the profile removal) is outside the support window, but no session launches on it ([Upgrade order of the profile removal release](/run-server/self-hosting/upgrade-compose#프로필-제거-릴리스의-업그레이드-순서)).

```bash
ENGINE=claude
if deployed_values \
  && CURRENT="$(jq -er '.images.worker.digest' deployed-values.json)" \
  && jq -e --arg e "$ENGINE" '[.[] | select(.runtime.engine == $e)]
      | if length == 1 then {images: {workers: [], worker: (.[0] | {repository, digest, runtime})}}
        else error("the release has no single \($e) image") end' \
    target-chart/werft/files/release-images.json > worker.json \
  && TARGET="$(jq -er '.images.worker.digest' worker.json)"; then
  echo "deployed ${CURRENT}"
  echo "target   ${TARGET}"
  PREVIOUS=worker-previous.json
  if [ "$CURRENT" != "$TARGET" ]; then
    PREVIOUS=worker-previous.next.json
    jq '{images: {workerPrevious: (.images.worker | {repository, digest, runtime})}}' \
      deployed-values.json > "$PREVIOUS"
  fi
  set -- -f values-<installation>.yaml -f worker-reset.json -f worker.json
  if [ -f "$PREVIOUS" ]; then set -- "$@" -f worker-previous-reset.json -f "$PREVIOUS"; fi
  if helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
    --namespace werft "$@" --timeout 10m; then
    if [ "$PREVIOUS" != worker-previous.json ]; then mv "$PREVIOUS" worker-previous.json; fi
  fi
fi
```

`ENGINE` is the engine this installation deploys; an installation that deploys the Codex worker sets `ENGINE=codex`. Left as it is, the worker becomes the Claude image, and the previous-image file is chosen against an image the installation does not deploy. `deployed_values` reads the values of the deployed revision. Without the revision, a failed upgrade makes get values return that attempted revision's candidate image. When digests differ, save current into a candidate file, replacing worker-previous.json only after successful upgrade. Failed upgrades leave the preserved file untouched. With identical digests, pass the existing file unchanged. An upgrade retaining the first installation's worker may have no file yet; that is valid. When any command before it fails, `helm upgrade` does not run. Helm merges a values file's runtime key by key into the runtime of the files before it, so a file that clears that runtime (`worker-reset.json`, `worker-previous-reset.json`) goes before each image file. Without it, a key of the last image that your installation values still hold, such as `restorableSchemes`, sticks to the new image, which then claims to restore checkpoints it cannot.

- An upgrade without `worker.json` applies the published chart's list of two images. An installation whose values set `images.worker` fails at render (`set images.workers: [] to deploy images.worker alone`). One whose values do not becomes a list installation and does not keep the current image as the previous one. When no image of the target list restores the current image's checkpoints (another engine, SDK or CLI, or an image deployed without a runtime), the pre-upgrade check stops with a `refused` that no approval covers.
- Keep `worker-previous.json` beside installation files and pass it on subsequent upgrades. Omitting it when the worker digest is unchanged drops the deployed previous image. Checks then compare sessions and refuse if any match neither target current/previous combination or lack recorded combinations (approval can bypass this). If omitted accidentally, restore the file rather than approving. With no affected sessions and empty upgrade.approvedSessions, checks pass; stale approvals cause refused. See “What checks do not cover” below. Main charts merged the same day can share worker digests.
- Do not use `--reuse-values`: old chart defaults can leave old images under a new chart version.
- Do not pass all of `helm get values --all` as values; old digests override the new chart. Extract only .images.worker.
- Charts published from `v*` tags follow the same procedure.

Do not pass control-phase.json to the final upgrade. Replace worker-previous.json only on success and retain it for future upgrades. Clear approvals each upgrade and inspect the new affected list.

<a id="이미지-목록-설치의-upgrade" />
#### Upgrading an image-list installation

An installation that sets its worker images with `images.workers` (one that runs Claude and Codex together, including one installed with the published chart's defaults) builds its values file with `next_workers final` instead of the `worker.json` above. Converting a single-image installation to a list for the first time uses the same procedure. Helm replaces a list as a whole instead of merging it, so the list in your values or from the last upgrade never gets a new release's images by itself: build the list with this procedure for every release. Do not upgrade a list installation with a chart that lacks `files/next-workers.jq` and `files/release-images.json` (a release from before this procedure).

**Step 1 (control plane).** Do step 1 above unchanged. For a list installation, `next_workers control` passes the deployed list and clears the digest and runtime of `images.worker` and `images.workerPrevious`, since the chart refuses single values beside a list even when the installation's values still set them. When converting a single-image installation for the first time, this step keeps the single image.

**Step 2 (final list).** The target release's two images are added to the deployed images: the deployed list for a list installation, or the deployed `images.worker` and (if set) `images.workerPrevious` for a single-image installation. Do not pass `worker-previous.json`; the previous image is read from the deployed values.

```bash
deployed_values && next_workers final > workers.json \
  && helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
    --namespace werft -f values-<installation>.yaml -f workers.json \
    --set-json 'upgrade.approvedSessions=[]' --timeout 10m
```

When converting a single-image installation for the first time, put each deployed image's `releasedAt` in `KNOWN` by digest, and its runtime too if it was deployed without one. The program does not read `images.worker.releasedAt` from the deployed single values: that key is an old chart's default and may not match the digest the installation set, and this chart's `images.worker` has no such key. Take the values from the deployed release's manifest; `releasedAt` is the committer time of that release's commit. If the Codex image was deployed as `images.worker`, change the `IMAGE=` line to `IMAGE=worker-codex RUNTIME=workerCodexRuntime RELEASED=workerCodexReleasedAt`. If `images.workerPrevious` is set, build one more entry from its release's manifest and merge the two.

```bash
TAG=<the deployed release, e.g. v0.2.0>
IMAGE=worker RUNTIME=workerRuntime RELEASED=workerReleasedAt
mkdir -p "$TAG" && curl -fsSL -o "$TAG/release-manifest.json" \
  "https://github.com/JeongJaeSoon/werft/releases/download/$TAG/release-manifest.json" \
  && AT="$(curl -fsS "https://api.github.com/repos/JeongJaeSoon/werft/commits/$(jq -r .commit "$TAG/release-manifest.json")" | jq -er .commit.committer.date)" \
  && KNOWN="$(jq -c --arg at "$AT" --arg i "$IMAGE" --arg r "$RUNTIME" --arg t "$RELEASED" '{(.images[$i].digest): {runtime: .[$r], releasedAt: (.[$t] // $at)}}' "$TAG/release-manifest.json")"
```

The program builds the list like this:

- Each engine's images go newest `releasedAt` first, and up to two unretracted images are kept; a third is dropped. The [pre-upgrade check](#3-검사-결과와-예외) judges the sessions that need a dropped image: if the images left cannot restore the checkpoint of a launch holding a slot on it, the result is `refused` with no approval possible, and a session with only a checkpoint is listed as affected. A launch started on a single image deployed without a runtime has no runtime on record. The check judges such a launch by the runtime the deployed list declares for the same digest, the value set in `KNOWN` when switching to a list. So an upgrade that drops that image (usually the one after the switch to a list) passes while the launch holds its slot, as long as a rebuild of the same runtime is in the target. When the deployed list has no runtime for that digest, or declares it under two runtimes, only that image itself is taken to restore what it seals, and the upgrade is `refused` until the launch lets go of its slot. Whether the declared runtime is what that image really carries is beyond what the check can tell.
- A digest is listed once. A deployed retracted image stays retracted even when the target release names the same digest. A retracted image is kept only when it is newer than the oldest image kept; an engine with no unretracted image keeps all its retracted images (which is not the same as the engine leaving the list). Once an old retracted image is dropped, checkpoints of its combination stop as `incompatible_checkpoint` instead of `runtime_retired`.
- It fails without writing a values file when a deployed image has no runtime or `releasedAt`, when a target image is not newer than every deployed image of its engine, when one digest is given with another runtime, time or repository, and when two images of one engine have the same time. `releasedAt` is a commit time and can differ from the publishing order: a chart of a tag on a commit older than the deployed image, and a chart that rebuilt by tag push a commit main had already published (another digest, the same time), stop here. Upgrade with a newer release's chart instead.

The commands are joined by `&&`, so `helm upgrade` does not run when the program fails. A failed upgrade, run again, gives the same file from the same deployed revision, so there is no file to keep. Clear the approval list every time as above. An engine you do not use may be deleted from `workers.json` before passing it; deleting an engine the deployed images had makes the upgrade one that drops an engine (see "An upgrade that drops an engine" below).

<a id="3-검사-결과와-예외" />
### 3. Check results and exceptions

<a id="업그레이드-전-검사" />
#### Pre-upgrade check

Before migrate (hook weight -5), helm upgrade runs upgrade-check using the target release's api image. It reads combinations from every session's uncollected checkpoint pointer and selects sessions resumable on neither target images.worker nor images.workerPrevious. Pointers committed before combination recording are also selected. It also reads the images of launches still holding a slot (unclaimed ones included). It reads the session of every launch a worker claimed that still holds its slot too, and selects the workers this upgrade ends (see "Workers this upgrade ends" below). Job logs contain one JSON result line.

```bash
kubectl -n werft logs job/werft-upgrade-check
```

| `verdict` | Exit | Upgrade | Meaning |
|---|---|---|---|
| `proceed` | 0 | Continues | upgrade.approvedSessions exactly matches affected sessionId values. Approvals must be empty if none are selected, if worker is unchanged and every deployed image stays under the same runtime, or if never deployed. Sessions selected as `worker_ends` are in the list even when the worker image is unchanged |
| `refused` | 2 | Stops | Any approval mismatch, including stale values. With unchanged worker but removed/changed previous, sessions matching neither target combination or lacking recorded combinations are selected. Also returned when no target image restores the checkpoints sealed by the deployed worker or by a launch holding a slot (a rebuild with the same combination restores them; an image deployed without a runtime needs the same digest in the target; a launch reserved without a runtime is taken to run what the deployed list declares for its digest, and needs the same digest in the target when nothing is declared or the declarations disagree); that case cannot be approved. A retracted target image does not count as one that restores them. When a launch on the image being retracted holds a slot, list a fixed image of the same combination beside it, or upgrade once that slot is free |
| `check_failed` | 1 | Stops | Database unreadable, runtime combinations unreadable/missing when required below, or deployed worker unknown. Also if a deployed worker exists without UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS (pass empty if none), or scheduler Deployment is absent but database has sessions/partial schema. Also if a deployed worker exists and either gateway address, `WORKER_GATEWAY_URL` or `UPGRADE_DEPLOYED_WORKER_GATEWAY_URL`, is missing or not a URL. No bypass exists |

images.worker.runtime is optional for first installation; upgrade requirements depend on deployed/target state.

| Deployed state | Target | Without runtime |
|---|---|---|
| No scheduler Deployment; database empty or without sessions (first-install retry) | Any worker, no images.workerPrevious | `proceed` |
| One worker image without runtime/previous | Same worker, no images.workerPrevious | `proceed` |
| One worker image without runtime/previous | Different worker | `check_failed`; supply images.worker.runtime and images.workerPrevious containing current image |
| Runtime or previous exists | images.worker.runtime omitted | `check_failed`; combinations are needed to compare sessions |

See [API configuration](/run-server/self-hosting/reference/configuration) for extracting runtime. Minimal values can start without it; the first worker-changing upgrade adds runtime for both images.

An unchanged images.worker with removed/changed images.workerPrevious compares sessions. Unmatched or unrecorded combinations cause refused; exact approval passes. Unrecorded sessions are always selected as on image-changing upgrades. With absent deployed previous, or one unchanged under the same runtime, no session comparison occurs: empty approvals proceed, stale approvals refuse. The same digest declared under another runtime is compared like a removed image. Rebuilds with different image references but identical combinations can drop previous without affecting sessions, since current still resumes them.

If selected sessions may fail to resume, put exactly that list in values and rerun. Approval does not change session state. `no_image` sessions stop as recovery_required on resume, with no worker launched. The session's `attention` says `RESTORE_FAILED`, `incompatible_checkpoint`, so after resuming an approved session look at its `admission_state` and `attention`. `unrecorded` sessions launch current, then restoration either succeeds or stops as recovery_required.

```bash
helm upgrade --install ... --set-json 'upgrade.approvedSessions=["<sessionId>", ...]'
```

Approvals remain in release values. Clear them every upgrade with `--set-json 'upgrade.approvedSessions=[]'`, then reread and approve that upgrade's list. Leftover approvals refuse if different from affected, but still pass if identical and support-window requirements hold.

**Workers this upgrade ends.** A worker only knows the gateway address it was created with (`WORKER_GATEWAY_URL`). When the target release's scheduler gives workers another address than the running scheduler does, a worker that is running has its heartbeat refused at the old address after the upgrade, gives its lease up and exits. The check then selects the session of every launch a worker claimed that still holds its slot as `worker_ends`. It selects idle workers and workers running a turn alike, and it does so on an upgrade that keeps the worker image too. With the same address it selects none. It does not select an unclaimed launch: the new scheduler builds that launch again with the new address. A session already selected for its checkpoint is listed under that reason only. These sessions belong to the same approval list. Run the upgrade again once the slots are released (the session closed, or the idle worker stopped) and they leave the list. If the workers may end, approve the list as it is. The workers of approved sessions exit after the upgrade. The session of an idle worker launches on a new worker at its next input, and a turn that was running is cut off ([Recover sessions](/run-server/self-hosting/recover-sessions)).

**Each engine is judged on its own.** When the deployed and target images span more than one engine, as in an installation that runs Claude and Codex from one image list, the check above runs per engine. An engine stays when the target lists any image of it, even only retracted ones. If no target image restores what that engine's deployed newest image seals, the verdict is `refused`, which no approval passes. A deployment of one engine, or one with an image deployed without a runtime, is judged as one group, as before.

**An upgrade that drops an engine.** When the target lists no image of an engine, the upgrade drops that engine. The check then stops protecting that engine's newest image. Instead it lists every session of that engine that is not closed as `no_engine_image`, checkpoint or not. An open session whose runtime kind this host does not know, or that has none, is `no_engine_image` too. A session with a checkpoint is judged by its checkpoint first, so it is listed as `no_image` or `unrecorded`. Each session is listed once, with one reason. A launch of that engine still holding a slot, claimed or not, is `refused`, which no approval passes. Run the upgrade again once its slot is released. Approved sessions end up like this:

- A session without a checkpoint waits without taking a slot. The API shows it with attention `CATALOG_MISMATCH`.
- A session with a recorded checkpoint stops before launch as `recovery_required` (attention `RESTORE_FAILED`, reason `incompatible_checkpoint`).
- A session whose checkpoint has no recorded runtime waits.
- New sessions of that engine cannot be created, from the API or from Slack (`UNSUPPORTED_CAPABILITY`). An engine left with only retracted images is not dropped, so that refusal does not apply to it.

Dropping an engine does not itself delete a session or retire its restore point. Ordinary retention still applies, such as checkpoint GC and the workspace TTL of stopped sessions.

**A race between the check and the rollout.** The check sees only the launches holding a slot when it runs. After the check and before the rollout, the old scheduler may still reserve a launch of the dropped engine. Its worker finds no session to claim from the new control-host and exits. The scheduler does not count that exit as a failed launch, and gives the launch back instead of building it again (as it does for a launch on a retracted image). The session then waits or stops as above. A worker that claimed after the check and is already running is not stopped by this setting alone.

**Bringing an engine back.** To run the dropped engine's sessions again, upgrade with an unretracted image of that engine back in the list. The image must ship the session's runtime version. Clear the approval list. Waiting sessions then launch on that image on the next pass. Sessions stopped with `incompatible_checkpoint` are retried with `retry_restore`.

The Job receives JSON `UPGRADE_APPROVED_SESSIONS`, deployed `UPGRADE_DEPLOYED_WORKER_IMAGE`, `UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS` (empty if absent), and their runtimes as `UPGRADE_DEPLOYED_WORKER_IMAGE_RUNTIME` and `UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS_RUNTIME`. A deployed scheduler running an image list (`WORKER_IMAGES`) passes it as `UPGRADE_DEPLOYED_WORKER_IMAGES`. Chart lookup reads these from the scheduler Deployment and prefixes each name with `UPGRADE_DEPLOYED_`. It passes the gateway address the running scheduler gives workers the same way, as `UPGRADE_DEPLOYED_WORKER_GATEWAY_URL`, and the address the target scheduler will give as `WORKER_GATEWAY_URL`. A deployed image without a runtime is compared by digest alone. Chart-provided `UPGRADE_DEPLOYED_STATE` alone permits runtime-table exceptions. `absent` means scheduler Deployment missing but namespace default ServiceAccount readable, requiring get permission on it. `unpinned` means Deployment without runtime/previous. `helm template`/client dry-run lookup reads nothing, leaving every deployed value empty and making such Jobs check_failed. Server dry-run reads the cluster but executes no hooks, so cannot establish a verdict.

Checks trust DATABASE_URL to point to this installation; another empty database can pass absent. No Job is created for first installation (pre-install) or scheduler.enabled: false. To keep Job/scheduler image inputs aligned, WORKER_IMAGE, WORKER_IMAGE_PREVIOUS, WORKER_IMAGE_RUNTIME, and WORKER_IMAGE_PREVIOUS_RUNTIME cannot be supplied through *.extraEnv or config.limits; rendering rejects them. Use images.worker/images.workerPrevious.

**Before `helm rollback`**, run the check directly in the api Pod because rollback does not run the hook. Supply target revision values from `helm get values --revision <revision>`.

```bash
kubectl -n werft exec deploy/werft-api -- env \
  UPGRADE_DEPLOYED_WORKER_IMAGE='<WORKER_IMAGE of the running scheduler>' \
  UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS='<WORKER_IMAGE_PREVIOUS of the running scheduler, empty if none>' \
  UPGRADE_DEPLOYED_WORKER_IMAGE_RUNTIME='<WORKER_IMAGE_RUNTIME of the running scheduler, empty if none>' \
  UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS_RUNTIME='<WORKER_IMAGE_PREVIOUS_RUNTIME of the running scheduler, empty if none>' \
  UPGRADE_DEPLOYED_WORKER_GATEWAY_URL='<WORKER_GATEWAY_URL of the running scheduler>' \
  WORKER_GATEWAY_URL='<WORKER_GATEWAY_URL of the scheduler of the target revision>' \
  WORKER_IMAGE='<worker image of the target revision>' WORKER_IMAGE_RUNTIME='<its runtime JSON>' \
  WORKER_IMAGE_PREVIOUS='<workerPrevious of that revision>' WORKER_IMAGE_PREVIOUS_RUNTIME='<its runtime JSON>' \
  bun run apps/control-host/src/api/upgrade-check.ts
```

Both gateway addresses are the `WORKER_GATEWAY_URL` of a scheduler Deployment. The target revision's is in `helm get manifest --revision <revision>`. When the two differ, the sessions of workers holding a slot are listed as `worker_ends`. When the deployed scheduler runs an image list, pass that scheduler's `WORKER_IMAGES` as `UPGRADE_DEPLOYED_WORKER_IMAGES` instead of the four values starting with `UPGRADE_DEPLOYED_WORKER_IMAGE`. The api Pod of that installation carries `WORKER_IMAGES` too, so a check for a rollback to a single-image revision drops it with `env -u WORKER_IMAGES`. Left in, the command returns `check_failed` with `WORKER_IMAGES replaces WORKER_IMAGE`. When the target revision was deployed without a runtime, take `WORKER_IMAGE_RUNTIME` from the `workerRuntime` of that release's manifest (as `KNOWN` does in [Upgrading an image-list installation](#이미지-목록-설치의-upgrade)). Left empty, it returns `check_failed`. When the target revision is a list as well, pass the `WORKER_IMAGES` its scheduler received instead of the four values starting with `WORKER_IMAGE` (it is in `helm get manifest --revision <revision>`).

A typical worker-image rollback returns refused: when the current image carries a newer SDK/CLI, no image of the target revision restores the checkpoints it seals. A rollback to a rebuild with the same combination compares sessions. Unreadable settings/database return check_failed. Current-image workers keep producing that combination's checkpoints after rollback until they exit, beyond the check's view. affected lists only sessions selected at check time. Prefer roll-forward. If rolling back anyway, scheduler matches runtime combinations on resume; sessions matching neither target current nor previous stop as recovery_required, including newer SDK/CLI checkpoints made by surviving current workers during rollback.

With unchanged worker, rollback proceeds with empty approvals only if deployed previous remains identical in the target revision; stale approvals refuse. Removed/changed previous triggers session comparison as above. This direct command does not block rollback automatically. On refused, read affected and decide. Omitting deployed-previous env when deployed worker exists yields check_failed.

**What checks do not cover.** Unlike [Compose checks](/run-server/self-hosting/upgrade-compose), target images are not executed. Only pointer engine/SDK/CLI/profile digest scheme combinations are compared; actual profile digests are judged at restore. Writers are not stopped and rechecked afterward. Instead, the check passes only when a target image restores the checkpoints sealed by the deployed worker image and by the images of launches holding a slot at check time, so what those workers write afterward stays inside the target window. Sessions before their first checkpoint count when their launch holds a slot. Launches the deployed scheduler starts on the previous image after the check are not seen, so run an upgrade that drops or changes previous when no launch runs on it. Workers of older images that no deployed image restores either are not stranded by this upgrade and do not block it; their sessions are selected if existing pointers already record that combination, and are absent before their first checkpoint. Registry pullability is not tested; failures surface as launch failures. Whether `images.worker.runtime` is the value that image itself prints is not tested either: the upgrade passes when it is wrong. When the engine, SDK, CLI or profile digest scheme differs from what the worker writes in its claim, the scheduler refuses the image the first time a worker on it starts ([Troubleshooting](/run-server/self-hosting/upgrade-kubernetes#자주-막히는-곳)). Whether `restorableSchemes` matches what the image can really restore is not compared then either. Of the ways an upgrade ends a worker, the check reads only a changed gateway address. A worker the new scheduler stops after its turn and builds again because its isolation contract (the `werft.isolation` label) changed, and a worker on an image the target retracts, stopped after its turn, are not listed as `worker_ends`.

<a id="자주-막히는-곳" />
## Troubleshooting

workerPrevious differing from the deployed image is an unapprovable refused. Omitting get values revision can read failed-upgrade candidates. helm template/client dry-run without lookup cannot substitute for actual upgrade checks.

When new sessions stay `queued` after an upgrade and the scheduler logs `Worker image refused: a worker on it claimed under another runtime than configured`, `images.worker.runtime` is not that worker image's value. An upgrade that removes the runtime again is stopped as `check_failed` (`WORKER_IMAGE_RUNTIME is not set`). Put the runtime the image prints ([API settings in the configuration reference](/run-server/self-hosting/reference/configuration)) in `images.worker.runtime` as it is, and upgrade again. The single-image procedure's `worker.json` takes this value from the target release's `files/release-images.json`. The sessions that waited launch after that.

An upgrade stopped as `refused` or `check_failed` still uses one Helm revision. Helm keeps 10 revisions by default, so after several stopped attempts the revision to roll back to is gone from the history. `helm rollback` cannot go to a revision that left the history, and saving its values does not change that. When you expect several attempts, give `helm upgrade` a larger `--history-max` (`0` is no limit).

<a id="되돌리기" />
## Roll back

```bash
helm -n werft history werft
helm -n werft rollback werft <revision> --wait --timeout 10m
```

Rollback does not run migrate hooks (they are not pre-rollback). Database schema stays new; old builds can still report ready on later schemas because readyz checks only that their migration list is a prefix of applied migrations. Do not roll back below a release the [changelog](https://github.com/JeongJaeSoon/werft/blob/main/CHANGELOG.md) marks as irreversible ([Pre-upgrade gates](/run-server/self-hosting/upgrade-compose#실행-전-게이트)).

Roll back only after shared gates and the direct check establish viability. Without hooks, rollback does not automatically enforce checks. Prefer roll-forward.

<a id="옛-worker-이미지-지우기" />
## Delete old worker images

Sessions resume on a runtime combination, not on an image. An old worker image may therefore be deleted from the registry once the checks below pass, in order. The deletion happens in the registry; werft does not delete images. When the image must not run again, such as for a vulnerability that cannot be rebuilt away, [retract](/run-server/self-hosting/reference/configuration) it in the list before deleting it.

1. Remove it from the list. On a list install (`images.workers`, `WORKER_IMAGES`), the program in [Upgrading an image-list installation](#이미지-목록-설치의-upgrade) keeps at most two unretracted images per engine, so the image drops out by itself once you upgrade to two newer releases of that engine. A retracted image drops out once it is older than the oldest kept unretracted image, and never on an engine with no unretracted image. To remove it sooner, delete its entry from the generated `workers.json` before passing the file. The program adds the target chart's `release-images.json` to the deployed list, so a removed image does not come back at the next upgrade unless the target chart lists its digest. If it does, delete the entry from that upgrade's `workers.json` too. On an install with single values, keep it out of both `images.worker` and `images.workerPrevious` and upgrade as in the steps above. When a session still needs the removed image, the [pre-upgrade check](#3-검사-결과와-예외) judges that upgrade. From then on no new launch chooses that image. What happens to a session whose combination has no image left in the list is described under the image list in the [configuration reference](/run-server/self-hosting/reference/configuration).
2. Wait until the series `werft_sessions_by_worker_image{image="<repository>@sha256:<digest>"}` is gone. The gauge counts sessions that have not ended, by the image of their newest launch ([metrics reference](/run-server/self-hosting/reference/metrics), [collect metrics](/run-server/self-hosting/collect-metrics)). While the series exists, a session whose newest launch is on that image is still open. An open session at rest stays in the series too, so wait until such sessions end or launch again on another image. The gauge does not count `stopped` sessions, so do not skip step 3 when the series is gone.
3. Check in the database that no launch on that image holds a slot. Run the query below with your own database client; it must return no rows. Those rows cover a worker the scheduler manages on that image and a launch that, rebuilt before a worker binds it, is rebuilt on its stored image, the one you are about to delete. A slot is released only after the scheduler confirms the resource is gone. An orphan Pod, which has left the records and which the scheduler cleans up on its own, does not appear here. An orphan is never rebuilt and runs on the image its node already pulled, so deleting the image from the registry does not affect that Pod.

```sql
SELECT session_id, generation, claimed_attempt_id IS NOT NULL AS claimed
FROM worker_launches
WHERE image = '<repository>@sha256:<digest>'
  AND slot_released_at IS NULL;
```

When all three hold, delete it from the registry. Rolling back afterwards to a Helm revision whose list holds that image makes that revision's scheduler fail to pull it on any node without a cached copy when it launches on it (worker Pods pull with `IfNotPresent`). Keep the images held by any revision you want to be able to roll back to.
