<a id="무엇을-하게-되나" />
## 作業内容

最初の owner と workspace を作成し、利用者ごとに API key を発行します。API key の廃止とセッション実行権限の取り消しを区別します。

<a id="준비물" />
## 準備

[設置](/run-server/self-hosting)と[アクセス経路](/run-server/self-hosting/access)の準備が必要です。設定リンクは運用者だけが受け取り、扱います。

<a id="단계" />
## 手順

<a id="1-첫-owner-만들기" />
### 1. 最初の owner の作成

運用者が設置側で一回限りの設定リンクを受け取ります。test-ops 単一サーバーでは `scripts/test-ops.sh setup-link`、Kubernetes では `kubectl -n werft exec deploy/werft-api -- bun run apps/control-host/src/api/setup-link.ts`、それ以外の compose 構成では `docker compose --profile apps exec -T api bun run apps/control-host/src/api/setup-link.ts` です。コマンドは live owner がいないときだけリンクを stdout に一度出力し、ログやファイルには残しません。`CONSOLE_ORIGIN` があればそのアドレスを付けた URL、なければ `/bootstrap#setup=…` のパスだけが出るので、コンソールのアドレスの後ろに付けます。リンクをブラウザで開き、owner 情報と workspace 名を入力します。リンクは一度使うとすぐ無効になり、24 時間で期限切れになります。再実行すると前のリンクは無効になり、新しいリンクが出力されます。owner がいればコマンドはリンクを作らず、終了コード 1 で終わります。`/login` でログインします。

<a id="2-사용자별-key-발급" />
### 2. 利用者ごとの key 発行

```bash
KEY="$(scripts/test-ops.sh key create <owner_id> \
  --scopes sessions:read,sessions:write,sessions:approve,sessions:control,sessions:recover)"
```

`<owner_id>` は、この key のセッションをまとめる名前です。利用者ごとに異なる値を決めます。Web コンソールのアカウントとは別であり、workspace id は使いません。

SDK と HTTP API はこのサーバーアドレスと key で接続します（[SDK のインストール](/getting-started/install)）。

Kubernetes では次を使います。

先に[設置環境の context・namespace・fullname の確認](/run-server/self-hosting/kubernetes#준비물)に従います。次の `werft` はその設置例の名前です。

```bash
kubectl -n werft exec deploy/werft-api -c api -- \
  bun run apps/control-host/src/api/keys.ts create <owner_id> \
  --scopes sessions:read,sessions:write,sessions:approve,sessions:control,sessions:recover
```

stdout には平文 key が一度だけ、stderr には key id が出力されます。平文は公開ログに保存せず、対象の利用者へ安全に渡します。利用者ごとの key 所有者識別子と Web コンソールのアカウントは別です。API key の scope は作業に必要な範囲に絞ります。

<a id="3-폐기-연락과-실행-권한" />
### 3. 廃止時の連絡と実行権限

key を廃止する際の連絡先を利用者に案内します。checkout の運用者 CLI は次のとおりです。

```bash
scripts/test-ops.sh key revoke <key_id>
API_CONTAINER='<api-container-id-from-this-installation>'
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/grants.ts revoke <session_id> --reason <text>
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/grants.ts restore <session_id> --reason <text>
```

API_CONTAINER は、この環境の status と Docker project label で確認した API コンテナ id に置き換えます。Kubernetes では設置バージョンのリポジトリ checkout とホストの Bun・kubectl を準備し、`keys:k8s` と `grants:k8s` を使います。`NAMESPACE` と `RELEASE` の既定値はいずれも werft です。

| 操作 | 効果 |
| --- | --- |
| key revoke | その key による以後の API 認証を拒否します。開始済みのセッション実行を停止するコマンドではありません |
| grants revoke | 指定セッションの実行権限と資格情報を取り消し、実行の終了を要求します |
| grants restore | execution が存在しないことの確認後に実行権限を戻します。廃止した API key は復活させません |

<a id="4-개인-key" />
### 4. 個人 key

`keys create <owner_id>` で作った key は運用者 key です。Web コンソールの workspace の外で、その owner をまとまりとして使います。メンバーが Web で作ったセッションを API でも同じ一覧で見るには、そのメンバーの個人 key を作ります。

```bash
scripts/test-ops.sh key create --workspace <workspace_id> --personal <user_id> \
  --scopes sessions:read,sessions:write
```

- 個人 key は、key の scope と作成者の現在の役割が許す scope の共通部分だけを持ちます。その人のアカウントか membership が無効になると、次のリクエストから `401` です。
- API key は scope に関係なく管理操作（メンバー管理、セッションの引き継ぎ、key の発行）を行えません（`403`）。管理操作は人のログインセッションで行います。
- 個人 key とエージェント key は、その key が始めたセッションの承認リクエストに回答できません（`403`、`reason_code: self_approval`）。

<a id="5-멤버-내보내기와-인수" />
### 5. メンバーの除外と引き継ぎ

owner か admin がログインセッションで `POST /v1/members/{user_id}/disable`（本文 `{}` または `{"reason": "…"}`）を呼びます。owner を無効にできるのは owner だけで（`403 OWNER_PROTECTED`）、自分自身と最後の owner は無効にできません（`409 LAST_OWNER`）。

- 一度に membership を無効にし、その人のログインセッションすべてとその workspace の個人 key を失効させ、連携した Slack アカウントを回収します。エージェント key には触れません。
- その人がリクエストした閉じていないセッションは引き継ぎ待ちになります。実行中の turn だけを終え、新しいメッセージは `409 TAKEOVER_REQUIRED` で拒否されます。owner が `GET /v1/takeovers` で一覧を見て `POST /v1/sessions/{id}/takeover` で引き継ぐと、その owner がリクエスト者になります。
- `POST /v1/members/{user_id}/enable` は membership だけを戻します。失効したログインセッション、個人 key、Slack 連携は戻らないため、再ログインして key を新しく受け取ります。まだ誰も引き継いでいないセッションはその人に戻ります。
- アカウント全体を止めるには `POST /v1/users/{user_id}/disable`・`/enable` を使います。対象が、呼び出した人が owner か admin である workspace にだけ属するときに許可されます。
- 外部ディレクトリ（SCIM）とは同期しません。社内 SSO から人を外してもここには反映されないため、この API を別途呼びます。

<a id="6-감사-기록과-보존-기간" />
### 6. 監査記録と保持期間

権限判定は、拒否と、管理操作・承認・Slack 入力の許可を監査記録に残します。記録は変更できません。行の `request_id` は応答の `X-Request-Id` で、そのリクエストが残した receipt と同じです。

- **読み取り.** owner はコンソールの設定 > ワークスペース > 監査記録で、期間・種類・人で絞り込み、同じリクエストの行をつなげて見て、NDJSON ファイルにエクスポートします。同じ内容をログインセッションで `GET /v1/audit/events`（`limit` 既定 50、最大 200）で読みます。admin・member と API key は `403` です。
- **エクスポート.** `Accept: application/x-ndjson` を付けると、絞り込んだ行すべてを一行ずつ送り、最後の行は `{"kind":"end",…}` です。一度に 100,000 行までで、超えたら終わりの行の `next_cursor` で続けて受け取ります。一つの workspace で同時に一つだけ動き（二つ目は `429`）、10 分を過ぎると打ち切ります。終わりの行がないファイルは完全ではないため、受け取った最後の行の `cursor` で呼び直します。
- **保持期間.** 既定 90 日です。owner がログインセッションで `POST /v1/workspaces/{id}/audit-retention`（`{"audit_retention_days": …}`、30〜3650）で変えます。現在の値は `GET /v1/auth/me` の `workspace.settings` にあります。期間を過ぎた判定行は reconciler が削除します。receipt は削除しませんが、監査記録には保持期間内のものだけが出ます。

<a id="확인" />
## 確認

各利用者の key で `/v1/sessions` を読むと許可範囲の応答が返り、key なしなら 401 になる必要があります。廃止した key は認証されないことを確認します。grants 出力の receipt と execution 状態を確認し、受理と実際の終了を区別します。

<a id="자주-막히는-곳" />
## よくある問題

リンクが「この設定リンクは使えません」で開く場合は、すでに使ったか、24 時間が過ぎたか、コマンドの再実行で置き換わっています。owner がいなければ、コマンドを再実行して新しいリンクを受け取ります。CLI の owner id に workspace id を指定しないでください。

<a id="되돌리기" />
## 元に戻す

作成済みの最初の owner を削除する目的で環境を reset しないでください。誤って発行した key を revoke し、正しい scope で新しい key を作成します。grants restore は以前の実行が消えた後だけ行います。
