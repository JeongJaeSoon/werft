<a id="무엇을-하게-되나" />
## 作業内容

最初の owner と workspace を作成し、利用者ごとに API key を発行します。API key の廃止とセッション実行権限の取り消しを区別します。

<a id="준비물" />
## 準備

[設置](/run-server/self-hosting)と[アクセス経路](/run-server/self-hosting/access)の準備が必要です。設定リンクは運用者だけが受け取り、扱います。

<a id="단계" />
## 手順

<a id="1-첫-owner-만들기" />
### 1. 最初の owner の作成

運用者は設置側のコマンドで、最初の owner の一回限りの設定リンクをファイルとして受け取ります。コマンドは api イメージの中にあり、owner になる人のメールアドレスだけを受け取ります。パスワードはコマンドの引数や環境変数では渡さず、リンクを開いた人が決めます。リンクは画面に出ません。画面にはファイルのパスと期限だけが出ます。

test-ops 単一サーバーでは、ホストの新しいファイルに直接受け取ります。`DEPLOYMENT_DIR` は[単一サーバーへのインストール](/run-server/self-hosting/single-server)で決めたインストールごとのディレクトリで、バンドルのディレクトリの中は拒否されます。

```bash
scripts/test-ops.sh setup-link --email <owner-email> --out "$DEPLOYMENT_DIR/owner-link.json"
```

それ以外の compose 構成では、api コンテナの中にファイルを作り、ホストへ移してから、コンテナ側のファイルを削除します。

```bash
docker compose --profile apps exec -T api \
  bun run apps/control-host/src/main.ts admin bootstrap-owner \
  --email <owner-email> --out /tmp/owner-link.json
(umask 077 && set -C && docker compose --profile apps exec -T api cat /tmp/owner-link.json >owner-link.json)
docker compose --profile apps exec -T api rm -f /tmp/owner-link.json
```

Kubernetes では、まず[設置の context・namespace・fullname の確認](/run-server/self-hosting/kubernetes#준비물)に従います。下の `werft` はその例の設置名です。3 つのコマンドが同じ Pod に届くよう、先に Pod を 1 つ選びます。

```bash
POD="$(kubectl -n werft get pod -l app.kubernetes.io/instance=werft,app.kubernetes.io/component=api -o name | head -n 1)"
kubectl -n werft exec "$POD" -c api -- \
  bun run apps/control-host/src/main.ts admin bootstrap-owner \
  --email <owner-email> --out /tmp/owner-link.json
(umask 077 && set -C && kubectl -n werft exec "$POD" -c api -- cat /tmp/owner-link.json >owner-link.json)
kubectl -n werft exec "$POD" -c api -- rm -f /tmp/owner-link.json
```

ファイルは 0600 で新しく作られます。同じ名前のファイルがあれば、コマンドは上書きせずに拒否します。ファイルには[メンバー招待](/members#api-응답)の応答と同じ項目が JSON で入っています。

| 項目 | 内容 |
| --- | --- |
| `accept_path` | 設定画面のパス。`/bootstrap#setup=<setup_token>` の形です |
| `accept_url` | `CONSOLE_ORIGIN` の後ろに `accept_path` を付けたリンク。`CONSOLE_ORIGIN` がなければ `null` です |
| `expires_at` | 期限 |

ブラウザがあれば `accept_url`（なければコンソールの origin の直後に `accept_path`）を開き、owner 情報と workspace 名を入力します。メールアドレスはコマンドに渡したアドレスでなければなりません。別のアドレスは `403` で拒否され、リンクはそのまま残ります。そのあと `/login` でログインし、リンクのファイルを削除します。ブラウザがなければ、下の[ブラウザなしで作る](#브라우저-없이-만들기)に従います。

リンクは一度使うとすぐ無効になり、24 時間で期限切れになります。再実行すると前のリンクは無効になり、新しいリンクが発行されます。owner がいれば、コマンドはリンクもファイルも作らず、終了コード 1 で終わります。実行するたびに、api コンテナのログ（`docker compose logs api`、`kubectl logs`）に `setup_link_issued` の行が 1 行残ります。その行にはリンク id、メールアドレス、期限だけがあり、トークンとリンクはありません。リンクで最初の workspace が作られると、その workspace の最初の receipt（`bootstrap_owner`）が、使ったリンクの id と作成時刻を残します。

<a id="브라우저-없이-만들기" />
#### ブラウザなしで作る

コンソールを開くブラウザがないホスト（設置をエージェントに任せた場合など）では、リンクのファイルの値で `POST /v1/auth/bootstrap` を直接呼びます。設定画面が呼ぶものと同じ API です。`curl` と `jq` が必要です。下のコマンドは、api に届くホストの、`owner-link.json` があるディレクトリで実行します。`API` はコンソールに届くアドレスです。test-ops 単一サーバーではそのサーバー内の `http://127.0.0.1:<TEST_OPS_API_PORT>`（既定は `3000`）、AWS 外の Kubernetes では[コンソールへの接続](/run-server/self-hosting/kubernetes#5-aws-밖-클러스터의-콘솔-접속)の port-forward のアドレス `http://127.0.0.1:3000` です。

まず owner のパスワード（12 文字以上、1024 バイト以下）を 0600 のファイル `owner-password` に 1 行で置きます。パスワードはコマンドの引数、環境変数、画面に置きません。下の例は `openssl` でランダムな値を作ります。自分で決めた値を使うなら、エディタで同じファイルを作ります。

```bash
API=http://127.0.0.1:3000
(umask 077 && set -C && openssl rand -base64 24 >owner-password)
```

リンクのファイルの `accept_path` から、`#setup=` の後ろの値（`setup_token`）を 0600 のファイルに取り出します。

```bash
(umask 077 && set -C && jq -j '.accept_path | sub("^/bootstrap#setup="; "")' owner-link.json >owner-setup-token)
```

リクエスト本文を 0600 のファイルとして作ります。`<owner-email>` はリンクのコマンドに渡したアドレス、`<owner-name>` は画面に表示する名前（64 文字まで）、`<workspace-name>` は workspace 名、`<workspace-slug>` は workspace の識別子（英小文字・数字・`-`。`-` で始めず 64 文字まで）です。

```bash
(umask 077 && set -C && jq -n \
  --rawfile token owner-setup-token \
  --rawfile password owner-password \
  --arg email '<owner-email>' \
  --arg name '<owner-name>' \
  --arg workspace '<workspace-name>' \
  --arg slug '<workspace-slug>' \
  '{setup_token: ($token | rtrimstr("\n")), email: $email,
    password: ($password | rtrimstr("\n")), display_name: $name,
    workspace_name: $workspace, workspace_slug: $slug}' >owner-bootstrap.json)
```

`set -C` のため、同じ名前のファイルがあれば作りません。コマンドが失敗して空のファイルが残ったら、そのファイルを削除して再実行します。

本文を送ります。

```bash
curl --max-time 10 -sS -w '\n%{http_code}\n' "$API/v1/auth/bootstrap" \
  -H 'content-type: application/json' -H 'x-requested-with: werft-web' \
  --data-binary @owner-bootstrap.json
```

最後の行が `201` で、本文の `role` が `owner`、`workspace` に作った workspace があれば、owner はできています。応答にはパスワードもトークンもありません。ほかの状態は次のとおりです。

| 状態 | 意味と対処 |
| --- | --- |
| `400` | 本文の項目が正しくありません（パスワードの長さ、slug の形など）。リンクは残るので、`owner-bootstrap.json` を削除して本文の作成からやり直します |
| `401` | リンクはすでに使われたか、24 時間が過ぎたか、コマンドの再実行で置き換わっています。owner がいなければ、`owner-link.json` と `owner-setup-token` を削除し、リンクのコマンドからやり直します |
| `403` | メールアドレスがリンクのコマンドに渡したアドレスと違います。リンクは残ります |
| `409` | 同じリンクで先に届いたリクエストが owner を作りました |
| `429` | リクエストが多すぎます。少し待って送り直します |

最後に、そのメールアドレスとパスワードでログインできることを確かめ、リンク・トークン・本文のファイルを削除します。

```bash
(umask 077 && set -C && jq '{email, password}' owner-bootstrap.json >owner-login.json)
curl --max-time 10 -sS -o /dev/null -w '%{http_code}\n' "$API/v1/auth/login" \
  -H 'content-type: application/json' -H 'x-requested-with: werft-web' \
  --data-binary @owner-login.json
rm -f owner-link.json owner-setup-token owner-bootstrap.json owner-login.json
```

`200` が出れば完了です。この確認は、応答が渡したログインセッションを捨てます。`owner-password` はパスワードマネージャーなど安全な場所に移してから削除します。コンソールの外で owner のログインセッションを使って管理 API を呼ぶ方法（`cookieSession`）は、設置が提供する API リファレンス（`/docs`）にあります。

<a id="2-사용자별-key-발급" />
### 2. 利用者ごとの key 発行

```bash
KEY="$(scripts/test-ops.sh key create <owner_id> \
  --scopes sessions:read,sessions:write,sessions:approve,sessions:control,sessions:recover)"
```

`<owner_id>` は、この key のセッションをまとめる名前です。利用者ごとに異なる値を決めます。Web コンソールのアカウントとは別であり、workspace id は使いません。

SDK と HTTP API はこのサーバーアドレスと key で接続します（[SDK のインストール](/getting-started/install)）。

Kubernetes では次を使います。

先に[設置環境の context・namespace・fullname の確認](/run-server/self-hosting/kubernetes#준비물)に従います。次の `werft` はその設置例の名前です。

```bash
kubectl -n werft exec deploy/werft-api -c api -- \
  bun run apps/control-host/src/api/keys.ts create <owner_id> \
  --scopes sessions:read,sessions:write,sessions:approve,sessions:control,sessions:recover
```

stdout には平文 key が一度だけ、stderr には key id が出力されます。平文は公開ログに保存せず、対象の利用者へ安全に渡します。利用者ごとの key 所有者識別子と Web コンソールのアカウントは別です。API key の scope は作業に必要な範囲に絞ります。

<a id="3-폐기-연락과-실행-권한" />
### 3. 廃止時の連絡と実行権限

key を廃止する際の連絡先を利用者に案内します。checkout の運用者 CLI は次のとおりです。

```bash
scripts/test-ops.sh key revoke <key_id>
API_CONTAINER='<api-container-id-from-this-installation>'
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/grants.ts revoke <session_id> --reason <text>
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/grants.ts restore <session_id> --reason <text>
```

API_CONTAINER は、この環境の status と Docker project label で確認した API コンテナ id に置き換えます。Kubernetes では設置バージョンのリポジトリ checkout とホストの Bun・kubectl を準備し、`keys:k8s` と `grants:k8s` を使います。`NAMESPACE` と `RELEASE` の既定値はいずれも werft です。

| 操作 | 効果 |
| --- | --- |
| key revoke | その key による以後の API 認証を拒否します。開始済みのセッション実行を停止するコマンドではありません |
| grants revoke | 指定セッションの実行権限と資格情報を取り消し、実行の終了を要求します |
| grants restore | execution が存在しないことの確認後に実行権限を戻します。廃止した API key は復活させません |

<a id="4-개인-key" />
### 4. 個人 key

`keys create <owner_id>` で作った key は運用者 key です。Web コンソールの workspace の外で、その owner をまとまりとして使います。メンバーが Web で作ったセッションを API でも同じ一覧で見るには、そのメンバーの個人 key を作ります。

```bash
scripts/test-ops.sh key create --workspace <workspace_id> --personal <user_id> \
  --scopes sessions:read,sessions:write
```

- 個人 key は、key の scope と作成者の現在の役割が許す scope の共通部分だけを持ちます。その人のアカウントか membership が無効になると、次のリクエストから `401` です。
- API key は scope に関係なく管理操作（メンバー管理、セッションの引き継ぎ、key の発行）を行えません（`403`）。管理操作は人のログインセッションで行います。
- 個人 key とエージェント key は、その key が始めたセッションの承認リクエストに回答できません（`403`、`reason_code: self_approval`）。

<a id="5-멤버-내보내기와-인수" />
### 5. メンバーの除外と引き継ぎ

owner か admin がログインセッションで `POST /v1/members/{user_id}/disable`（本文 `{}` または `{"reason": "…"}`）を呼びます。owner を無効にできるのは owner だけで（`403 OWNER_PROTECTED`）、自分自身は無効にできず（`403 SELF_PROTECTED`）、最後の owner も無効にできません（`409 LAST_OWNER`）。

- 一度に membership を無効にし、その人のログインセッションすべてとその workspace の個人 key を失効させ、連携した Slack アカウントを回収します。エージェント key には触れません。
- その人がリクエストした閉じていないセッションは引き継ぎ待ちになります。実行中の turn だけを終え、新しいメッセージは `409 TAKEOVER_REQUIRED` で拒否されます。owner が `GET /v1/takeovers` で一覧を見て `POST /v1/sessions/{id}/takeover` で引き継ぐと、その owner がリクエスト者になります。
- `POST /v1/members/{user_id}/enable` は membership だけを戻します。失効したログインセッション、個人 key、Slack 連携は戻らないため、再ログインして key を新しく受け取ります。まだ誰も引き継いでいないセッションはその人に戻ります。
- アカウント全体を止めるには `POST /v1/users/{user_id}/disable`・`/enable` を使います。対象が、呼び出した人が owner か admin である workspace にだけ属するときに許可されます。
- 外部ディレクトリ（SCIM）とは同期しません。社内 SSO から人を外してもここには反映されないため、この API を別途呼びます。

<a id="6-감사-기록과-보존-기간" />
### 6. 監査記録と保持期間

権限判定は、拒否と、管理操作・承認・Slack 入力の許可を監査記録に残します。記録は変更できません。行の `request_id` は応答の `X-Request-Id` で、そのリクエストが残した receipt と同じです。

- **読み取り.** owner はコンソールの設定 > ワークスペース > 監査記録で、期間・種類・人で絞り込み、同じリクエストの行をつなげて見て、NDJSON ファイルにエクスポートします。同じ内容をログインセッションで `GET /v1/audit/events`（`limit` 既定 50、最大 200）で読みます。admin・member と API key は `403` です。
- **エクスポート.** `Accept: application/x-ndjson` を付けると、絞り込んだ行すべてを一行ずつ送り、最後の行は `{"kind":"end",…}` です。一度に 100,000 行までで、超えたら終わりの行の `next_cursor` で続けて受け取ります。API プロセスごとに一つの workspace で同時に一つだけ動き（同じプロセスの二つ目は `429`）、10 分を過ぎると打ち切ります。終わりの行がないファイルは完全ではないため、受け取った最後の行の `cursor` で呼び直します。
- **保持期間.** 既定 90 日です。owner がログインセッションで `POST /v1/workspaces/{id}/audit-retention`（`{"audit_retention_days": …}`、30〜3650）で変えます。現在の値は `GET /v1/auth/me` の `workspace.settings` にあります。期間を過ぎた判定行は reconciler が削除します。receipt は削除しませんが、監査記録には保持期間内のものだけが出ます。

<a id="7-공유-범위-밖의-세션" />
### 7. 共有範囲外のセッション

owner・admin でも、共有範囲外のセッションは一覧・詳細・turn に表示されません（`404`）。そのようなセッションは次の経路でだけ扱います。理由（`justification`、1000 文字まで）は判定記録に残ります。

- **管理一覧.** `GET /v1/admin/sessions` で、owner・admin は範囲に関係なく workspace のセッションを新しい順に見ます。項目は作成者、agent release、状態、共有範囲などのメタデータだけで、メッセージ・タイトル・要約はありません。
- **監査閲覧.** `POST /v1/sessions/{id}/audit-read`（`{"justification": "…"}`）はセッション詳細と turn の 1 ページ（`cursor`・`limit`）を返し、読むたびに監査記録が一つ残ります。読むだけなので、その後もメッセージ・回答・終了は `404` です。
- **管理終了.** `POST /v1/admin/sessions/{id}/terminate`（`{"expected_revision": …, "justification": "…"}`）で、owner・admin は範囲に関係なくセッションを止めます。理由が停止理由になります。
- **管理復旧.** `POST /v1/admin/sessions/{id}/recovery-decisions` で、owner だけが範囲に関係なく復旧の決定を出します。本文は[セッションの復旧](/run-server/self-hosting/recover-sessions)の復旧決定と同じで、その `reason` が理由です。
- **引き継ぎ.** 離れたメンバーのセッションが引き継ぐ人に見えない範囲なら、`POST /v1/sessions/{id}/takeover` に `{"justification": "…"}` を渡します。なければ `403`（`reason_code: justification_required`）です。
- **プライベートチャンネルのセッションの引き継ぎ.** `private_channel` セッションは、そのチャンネルの現在のメンバーでセッションに書き込める人が同じ経路で引き継ぎ、理由は求めません。owner・admin もチャンネルのメンバーでなければ `404` です。

<a id="확인" />
## 確認

各利用者の key で `/v1/sessions` を読むと許可範囲の応答が返り、key なしなら 401 になる必要があります。廃止した key は認証されないことを確認します。grants 出力の receipt と execution 状態を確認し、受理と実際の終了を区別します。

<a id="자주-막히는-곳" />
## よくある問題

リンクが「この設定リンクは使えません」で開く場合は、すでに使ったか、24 時間が過ぎたか、コマンドの再実行で置き換わっています。owner がいなければ、コマンドを再実行して新しいリンクを受け取ります。CLI の owner id に workspace id を指定しないでください。

`admin bootstrap-owner` が `usage: bun run src/main.ts <api|metrics> | …(got admin)` で終わるか、`scripts/test-ops.sh setup-link --email …` が使い方だけを出力する場合、そのイメージはこのコマンドがない以前のリリース（`v0.4.0` まで）のものです。そのイメージでは、`bun run apps/control-host/src/api/setup-link.ts`（test-ops 単一サーバーでは引数なしの `scripts/test-ops.sh setup-link`）がリンクを stdout に一度だけ出力し、ファイルは作りません。リンクはメールアドレスに結び付きません。ブラウザなしで作るには、出力を画面に出さずにトークンのファイルに受け取り、[ブラウザなしで作る](#브라우저-없이-만들기)のトークンの取り出しだけを飛ばして進めます。

```bash
(umask 077 && set -C && scripts/test-ops.sh setup-link | sed -n 's/.*#setup=//p' >owner-setup-token)
(umask 077 && set -C && kubectl -n werft exec deploy/werft-api -c api -- \
  bun run apps/control-host/src/api/setup-link.ts | sed -n 's/.*#setup=//p' >owner-setup-token)
```

最初の行は test-ops 単一サーバー用、その下の 2 行は Kubernetes 用の 1 つのコマンドです。設置に合うものを 1 つだけ実行します。`owner-setup-token` が空なら、リンクは出ていません（owner がすでにいる場合など）。ファイルを削除し、コマンドのエラーを確かめます。

<a id="되돌리기" />
## 元に戻す

作成済みの最初の owner を削除する目的で環境を reset しないでください。誤って発行した key を revoke し、正しい scope で新しい key を作成します。grants restore は以前の実行が消えた後だけ行います。
