## 무엇을 하게 되나

회사 IdP(Google Workspace, OneLogin, Microsoft Entra ID, Okta, Keycloak 같은 OpenID Connect 공급자)로 콘솔에 로그인하게 한다. 공급자를 더하고, 테스트 로그인으로 확인하고, 켠다. 누가 가입할 수 있는지 정하고, 원하면 비밀번호 로그인을 닫는다.

werft의 로그인 수단은 두 가지다.

| 수단 | 설명 |
| --- | --- |
| 비밀번호 | 이메일과 비밀번호. 첫 owner는 항상 비밀번호로 만든다. 설치 전체에서 닫을 수 있고, 닫아도 비상 관리자 한 명은 비밀번호로 들어온다 |
| OIDC 공급자 | owner가 콘솔에서 등록한 IdP. 공급자는 여러 개 둘 수 있고, issuer마다 하나다 |

알아 둘 규칙:

- 공급자 설정은 콘솔의 화면에서만 한다. SSO용 환경 변수는 없다. 공급자와 client secret은 DB에 저장된다.
- 사람은 공급자의 `(issuer, subject)`로 찾는다. 이메일 주소로 기존 계정에 자동으로 붙이지 않는다. 같은 주소의 계정이 이미 있으면 그 사람이 로그인한 뒤 직접 연결하거나, 초대 링크로 가입한다.
- 공급자를 끄면 그 공급자로 로그인한 세션이 그 자리에서 끊긴다.
- IdP 그룹을 역할로 옮기는 기능, SCIM 동기화, SAML, IdP 쪽 로그아웃 전파는 없다. IdP에서 사람을 지워도 werft의 세션과 계정은 남으므로 [구성원을 비활성화](#되돌리기)한다.

이 기능은 `v0.1.3` 다음 릴리스에 들어 있다. `v0.1.3`까지는 Google 로그인만 환경 변수로 켤 수 있었다. 그 설치를 올린다면 [환경 변수 Google 로그인에서 옮기기](#9-환경-변수-google-로그인에서-옮기기)를 먼저 읽는다.

## 준비물

| 무엇 | 왜 |
| --- | --- |
| owner 계정 | 공급자 화면은 owner만 연다. admin과 member는 볼 수 없다 |
| `CONSOLE_ORIGIN` | 사람이 브라우저로 콘솔을 여는 공개 주소(`scheme://host[:port]`). 공급자에 등록하는 redirect URI를 이 값에서 만든다. 없으면 공급자를 만들 수 없다. 단일 서버는 [env 파일](/run-server/self-hosting/single-server#2-비밀과-설정-문서)에, Kubernetes는 values의 `api.extraEnv`에 둔다 |
| `PLATFORM_SECRET_KEY` | 설치에 이미 있는 값이다. client secret을 이 키로 봉인해 저장한다. 바꾸거나 잃으면 저장한 secret을 읽지 못한다 |
| `https` 주소의 IdP | issuer와 IdP의 모든 endpoint는 `https`여야 한다. `http`는 IdP와 `CONSOLE_ORIGIN`이 모두 `localhost`·`127.0.0.1`일 때만 받는다(로컬 시험용) |
| API에서 IdP로 가는 길 | API 서버가 IdP의 discovery·token·JWKS·UserInfo 주소에 직접 요청한다. 사설 주소의 IdP도 된다. link-local(`169.254.0.0/16` 등)로 풀리는 이름은 거절한다 |
| IdP 관리자 권한 | IdP에 앱(client)을 만들고 redirect URI를 등록할 수 있어야 한다 |

콘솔은 `CONSOLE_ORIGIN`과 같은 주소로 연다. 로그인 흐름의 cookie는 `__Host-` cookie라 `https`나 `localhost`·`127.0.0.1`에서만 남고, 다른 host 이름으로 연 콘솔에서는 IdP에서 돌아왔을 때 로그인이 거절된다.

## 단계

### 1. 공급자 만들기

1. owner로 로그인해 **설정 > 워크스페이스 > 로그인**을 연다.
2. **공급자 추가**를 누르고 **이름**과 **Issuer**를 넣는다. 이름은 로그인 화면의 버튼 글자다(64자까지). Issuer는 IdP가 알려 주는 주소를 글자 그대로 넣는다. 끝의 `/`도 IdP가 쓰는 대로 둔다.
3. **만들기**를 누르면 서버가 그 자리에서 IdP의 설정 문서(`<issuer>/.well-known/openid-configuration`)를 읽는다. 문제가 있으면 아무것도 만들지 않고 이유를 보인다([설정 문서의 문제](/run-server/self-hosting/reference/sso-providers#설정-문서의-문제)).
4. 통과하면 꺼진 공급자가 만들어지고 상세 화면으로 간다. 상태는 **초안**이다.

Issuer는 만든 뒤 바꿀 수 없다. issuer가 바뀌면 모든 사람의 신원이 바뀌기 때문이다. 다른 issuer가 필요하면 새 공급자를 만든다. 같은 issuer의 공급자는 하나만 둘 수 있다.

### 2. IdP에 앱 등록하기

상세 화면의 **공급자에 등록할 값**에 두 가지가 있다.

| 화면 | 쓰는 곳 |
| --- | --- |
| **Redirect URI** | `<CONSOLE_ORIGIN>/auth/callback/<공급자 id>`. IdP 앱의 redirect(callback) URI에 글자 그대로 등록한다. 공급자마다 다르다 |
| **서버가 요청을 보내는 곳** | 로그인할 때 API 서버가 요청을 보내는 host. 방화벽이나 egress 규칙이 있으면 이 host를 연다 |

IdP에서 웹 애플리케이션(confidential client, authorization code 흐름)을 만들고 이 redirect URI를 넣는다. werft가 요청하는 scope는 `openid email profile`로 고정이다. werft는 언제나 PKCE(S256)를 보낸다. client secret이 없는 client(public client)는 지원하지 않는다. IdP마다 무엇을 만들고 어떤 값을 가져오는지는 [공급자별 값](/run-server/self-hosting/reference/sso-providers#공급자별-값)에 있다.

### 3. client 값 넣기

**Client** 구역에서 IdP가 준 값을 넣는다.

1. **Client ID**의 **바꾸기**에서 client ID와 **Client 인증 방식**을 고른다. `HTTP Basic (client_secret_basic)`과 `POST 본문 (client_secret_post)` 가운데 IdP 앱에 설정한 방식과 같은 것을 고른다. 처음 값은 IdP가 알린 방식 가운데 Basic, 없으면 POST다.
2. **Client secret**의 **값 넣기**에 secret을 붙여 넣는다. 저장한 값은 다시 보이지 않고 끝 네 글자만 남는다.

둘을 다 넣으면 상태가 **테스트 필요**가 된다.

### 4. 테스트 로그인

**테스트와 켜기** 구역의 **테스트 로그인**을 누른다. 브라우저가 IdP의 로그인 화면으로 갔다가 돌아와 **테스트 로그인 결과**를 보인다. 테스트는 계정도 세션도 만들지 않는다.

| 결과 화면 | 뜻 |
| --- | --- |
| Subject (sub) | IdP가 이 계정에 준 식별자. werft는 issuer와 이 값으로 사람을 찾는다 |
| 이메일, `email_verified` | IdP가 보낸 주소와 검증 여부. IdP가 보내지 않으면 "보내지 않음" |
| 주소 증명 | werft가 이 주소를 이 계정의 것으로 믿는지. 믿지 않는 주소로는 계정을 찾지도, 가입시키지도 않는다 |
| 이 계정이 로그인하면 | 지금 규칙에서 이 계정이 실제로 로그인했을 때의 결과 |

실패하면 **이유 코드**가 나온다. 코드별 원인과 조치는 [테스트 로그인의 이유 코드](/run-server/self-hosting/reference/sso-providers#테스트-로그인의-이유-코드)에 있다. 테스트하는 동안 설정이 바뀌면 통과로 기록하지 않으니 다시 테스트한다.

### 5. 켜기

테스트가 통과하면 상태가 **켤 수 있음**이 되고 **켜기**가 열린다. 켜면 로그인 화면에 공급자 이름이 든 버튼(예: **Keycloak 계정으로 로그인**)이 나온다.

| 상태 | 뜻 |
| --- | --- |
| 초안 | client ID나 client secret이 없다 |
| 테스트 필요 | 지금 설정으로 통과한 테스트가 없다. 꺼진 공급자의 설정을 바꾸면 이 상태로 돌아간다. 켠 채로 규칙을 바꾼 공급자도 끄면 이 상태다 |
| 켤 수 있음 | 통과했고 꺼져 있다 |
| 켜짐 | 로그인 화면에 버튼이 나온다 |
| 켜짐 · 새 secret 대기 | 켜져 있고, 새로 넣은 client secret이 테스트를 기다린다 |

### 6. 누가 들어올 수 있나

상세 화면의 **누가 들어올 수 있나**에서 **규칙 바꾸기**를 누른다. 켜진 공급자에는 바로 적용된다. 꺼진 공급자는 바꾼 뒤 다시 테스트해야 켤 수 있다. 규칙도 설정이라, 켠 채로 바꾼 공급자를 나중에 끄면 다시 켤 때 테스트가 필요하다.

| 규칙 | 값 |
| --- | --- |
| **허용 도메인** | 이메일 도메인이 목록에 있는 계정만 로그인한다. 쉼표나 공백으로 나눠 50개까지. 비우면 제한하지 않는다. 목록이 있으면 werft가 믿는 주소가 없는 계정은 거절된다 |
| **초대 없이 가입** | **받지 않음**(기본) 또는 **member로 가입**. 켜면 IdP가 주소를 증명한 사람은 초대 없이 member로 계정이 생긴다 |
| **검증된 이메일** | **요구함**(기본) 또는 **요구하지 않음**. 요구하지 않으면 `email_verified`를 보내지 않는 IdP의 계정도 로그인한다. 그 주소는 믿지 않으므로 그런 계정은 초대 링크로만 가입한다 |

"주소 증명"은 IdP가 `email_verified: true`를 보낸 경우다. Google은 여기에 더해 주소가 `gmail.com`이거나 Workspace 도메인(`hd`)과 같아야 한다. IdP가 `email_verified: false`를 보낸 계정은 어느 설정에서도 로그인하지 못한다.

공급자 버튼으로 들어오는 계정은 위에서부터 이 순서로 판정한다.

1. 허용 도메인과 **검증된 이메일** 규칙을 먼저 본다. 맞지 않으면 이미 연결된 계정이라도 거절한다. 허용 도메인 밖은 `403`, 검증 규칙에 걸리면 `401`이다.
2. 이 공급자의 계정이 이미 werft 사용자에 연결돼 있다 → 그 사용자로 로그인한다. 계정을 찾을 때 이메일은 보지 않는다. 사용자나 멤버십이 꺼져 있으면 거절한다.
3. 증명된 주소의 werft 계정이 이미 있다 → 붙이지 않고 거절한다(`409 LOGIN_LINK_REQUIRED`). 그 사람은 원래 수단으로 로그인해 [계정을 연결](#8-계정-연결과-끊기)한다.
4. 증명된 주소 앞으로 살아 있는 초대가 있다 → 초대의 역할로 계정을 만든다.
5. **초대 없이 가입**이 **member로 가입**이고 주소가 증명됐다 → member로 계정을 만든다.
6. 그 밖에는 거절한다(`401`). 화면은 이유를 구분하지 않는다.

공급자로 만든 계정에는 비밀번호가 없다. Google 공급자는 **검증된 이메일**을 끌 수 없고, 허용 도메인 없이 **초대 없이 가입**을 켤 수 없다. 누구나 Google 계정을 만들 수 있기 때문이다.

### 7. 초대로 가입

**구성원** 화면에서 보낸 초대 링크를 연 사람에게, 켜진 공급자가 있으면 그 공급자의 버튼이 함께 보인다. 버튼으로 가입하면 계정의 이메일은 초대받은 주소가 되고 역할은 초대의 역할이다. 근거는 초대 링크라서 IdP가 보낸 주소는 보지 않는다. `email_verified`를 보내지 않는 IdP의 사람은 이 길로 가입한다.

허용 도메인과 **검증된 이메일**은 초대 가입에도 적용된다. 이 공급자 계정이 이미 다른 사용자에 연결돼 있거나, 초대 주소의 계정이 이미 있으면 가입하지 않고 초대도 쓰지 않는다.

### 8. 계정 연결과 끊기

이미 계정이 있는 사람은 로그인한 뒤 **설정 > 로그인 수단**에서 공급자 계정을 직접 연결한다.

- **연결할 수 있는 공급자**의 **연결**을 누르면 IdP에서 로그인하고 돌아온다. IdP에서 로그인한 계정이 연결된다. 이메일 주소가 werft 계정과 달라도 된다. 그 공급자의 허용 도메인과 **검증된 이메일** 규칙은 연결에도 적용된다.
- 연결과 끊기는 로그인한 지 10분 안에만 된다. 지났으면 로그아웃하고 다시 로그인한다.
- 한 공급자 계정은 한 사용자에게만, 한 사용자는 한 공급자에 계정 하나만 연결한다.
- 쓸 수 있는 수단이 하나만 남으면 끊을 수 없다. 꺼진 공급자의 계정은 쓸 수 있는 수단으로 세지 않는다.
- 비밀번호를 끊으면 비밀번호가 지워진다. 그 사람이 스스로 다시 정할 수는 없다. owner라면 운영자가 [로그인 복구](/run-server/self-hosting/recover-sign-in)의 `reset-password`로 다시 줄 수 있다.
- 끊으면 그 수단으로 로그인한 세션이 모두 끊긴다.

### 9. 환경 변수 Google 로그인에서 옮기기

`GOOGLE_OIDC_*` 환경 변수로 Google 로그인을 쓰던 설치는 옛 설정이 자동으로 옮겨지지 않는다. 올리면 Google 로그인이 꺼지고 로그인 화면에는 비밀번호만 남는다. Google로만 로그인하던 사람은 owner가 공급자를 다시 등록할 때까지 새로 로그인하지 못한다.

1. 옛 버전 API 프로세스를 모두 내린 뒤 새 버전을 올린다. 옛 프로세스가 남아 있으면 그 프로세스의 Google 로그인은 실패한다.
2. env 파일이나 values에서 `GOOGLE_OIDC_CLIENT_ID`·`GOOGLE_OIDC_CLIENT_SECRET`·`GOOGLE_OIDC_REDIRECT_URI`·`GOOGLE_OIDC_ISSUER`·`GOOGLE_OIDC_ALLOWED_DOMAINS`·`GOOGLE_OIDC_JIT`를 지운다. 남아 있어도 읽지 않는다. `CONSOLE_ORIGIN`이 없으면 넣는다.
3. 비밀번호가 있는 owner로 로그인해 [1단계](#1-공급자-만들기)부터 Google을 공급자로 다시 등록한다. Issuer는 `https://accounts.google.com`이다.
4. Google Cloud 콘솔의 OAuth client에서 승인된 리디렉션 URI를 화면의 새 redirect URI로 바꾼다. 옛 주소(`…/auth/google/callback`)는 지운다. 같은 OAuth client를 계속 써도 된다.
5. 옛 `GOOGLE_OIDC_ALLOWED_DOMAINS`·`GOOGLE_OIDC_JIT`에 넣었던 규칙을 [6단계](#6-누가-들어올-수-있나)에서 다시 정하고, 테스트하고, 켠다.

전에 Google로 로그인하던 사람은 같은 issuer(`https://accounts.google.com`)의 공급자가 켜지면 전과 같은 werft 계정으로 들어온다. 사람과 Google 계정의 연결은 DB에 남아 있고, Google은 같은 Google 계정에 같은 `sub`를 준다. 다른 issuer로 등록하면 다른 사람으로 본다.

Google 수단이 있는 사람은 올린 뒤 한 번 다시 로그인한다. 올리기 전에 만든 세션은 어느 수단으로 만들었는지 기록이 없어서, 외부 로그인 수단이 있는 사람의 그런 세션은 받지 않는다. 비밀번호만 쓰는 사람의 세션은 그대로다.

### 10. 비밀번호 로그인 닫기와 비상 관리자

모두가 공급자로 로그인하게 하려면 **설정 > 워크스페이스 > 로그인**의 **비밀번호 로그인** 구역에서 **닫기**를 누른다. 닫아도 **비상 관리자** 한 명은 비밀번호로 로그인한다. 공급자가 고장 났을 때 들어올 길이다.

비상 관리자는 켜져 있고 비밀번호가 있는 owner 한 명이다. 새 설치는 첫 owner가, 올린 설치는 그런 owner 가운데 멤버십이 가장 오래된 사람이 처음 비상 관리자다. 그런 owner가 없는 설치는 비어 있다. **비상 관리자**의 **바꾸기**로 다른 owner를 고른다. 비울 수는 없다.

닫기는 셋이 모두 맞아야 된다. 화면은 맞지 않으면 버튼을 막고 까닭을 보인다.

| 조건 | 맞지 않을 때 API의 `details.reason_code` |
| --- | --- |
| 켜진 공급자가 하나 이상 있다 | `no_provider` |
| 비상 관리자가 지정돼 있고 지금도 비밀번호로 로그인할 수 있다 | `no_emergency_admin` |
| 닫는 owner가 비상 관리자이거나, 켜진 공급자의 계정을 자기 로그인 수단에 연결해 뒀다 | `locks_out_actor` |

닫으면 비상 관리자를 뺀 모든 사람의 비밀번호 세션이 끊긴다. 닫혀 있는 동안은 이렇게 된다.

| 동작 | 결과 |
| --- | --- |
| 비상 관리자가 아닌 사람의 비밀번호 로그인 | 비밀번호가 맞아도 틀린 비밀번호와 같은 `401` |
| 로그인 화면 | 공급자 버튼이 먼저 나오고, 비밀번호 칸은 **비상 관리자 로그인**을 누르면 나온다 |
| 초대 수락 | 비밀번호 단계 없이 공급자 버튼만 나온다. 비밀번호 수락 요청은 `403`(`password_login_closed`) |
| 비상 관리자가 아닌 사람 앞으로 owner가 API로 내는 비밀번호 재설정 링크(콘솔에는 이 화면이 없다) | 발급은 `409`(`password_login_closed`), 이미 낸 링크의 사용은 `401` |
| 켜진 마지막 공급자 끄기 | `409`(`last_provider`). 먼저 비밀번호 로그인을 연다 |

비상 관리자로 지정된 사람은 끄거나(멤버십, 계정), owner가 아니게 바꾸거나, 그 비밀번호를 끊을 수 없다(`409`, `emergency_admin`). 비밀번호 로그인을 닫지 않은 설치도 같다. 먼저 다른 owner를 비상 관리자로 바꾼다. 비밀번호가 있는 다른 owner가 없으면 [로그인 복구](/run-server/self-hosting/recover-sign-in)의 `reset-password`로 한 명에게 비밀번호를 준다. 닫혀 있는 동안 비상 관리자를 바꾸면 옛 비상 관리자의 비밀번호 세션이 끊긴다.

## 확인

- 로그아웃한 브라우저로 `/login`을 열면 공급자 이름이 든 로그인 버튼이 있다. 버튼으로 IdP에 로그인하면 콘솔로 돌아온다.
- 로그인 화면이 쓰는 공개 API가 켜진 공급자를 보인다.

```bash
curl -s "$CONSOLE_ORIGIN/v1/auth/login-methods"
```

기대 응답은 `{"password":"on","providers":[{"id":"<공급자 id>","display_name":"<이름>"}]}`이다. 비밀번호 로그인을 닫았으면 `password`가 `emergency_only`다.

- 공급자 상세의 상태가 **켜짐**이고 **마지막으로 통과한 테스트** 시각이 있다.

## 자주 막히는 곳

| 증상 | 원인과 조치 |
| --- | --- |
| "콘솔의 공개 주소(CONSOLE_ORIGIN)가 설정되지 않아 공급자를 만들 수 없습니다. …" | API에 `CONSOLE_ORIGIN`이 없다. 넣고 API를 다시 띄운다 |
| 만들 때 "https가 아닌 주소는 쓸 수 없습니다." | issuer나 IdP의 endpoint가 `http`다. 운영 설치는 `https` IdP만 쓴다 |
| 만들 때 "설정 문서의 issuer가 넣은 주소와 다릅니다. …" | issuer를 IdP가 알린 글자 그대로 넣지 않았다(끝의 `/`, tenant 자리 등). [공급자별 값](/run-server/self-hosting/reference/sso-providers#공급자별-값)을 본다 |
| IdP가 "redirect URI가 맞지 않는다"고 거절한다 | IdP 앱의 redirect URI가 화면의 **Redirect URI**와 다르다. 공급자를 지우고 다시 만들면 id가 바뀌어 주소도 바뀐다 |
| 테스트의 이유 코드 `code_refused` | IdP의 token endpoint가 code 교환을 거절했다. client ID와 client secret, **Client 인증 방식**, IdP 앱의 redirect URI가 맞는지 본다. IdP 쪽 로그에 거절 이유가 남는다 |
| 로그인 화면 "이 계정으로 로그인하지 못했습니다 — …" | `401`. 연결된 계정도, 초대도, 가입 규칙도 맞지 않거나 IdP 응답 검증에 실패했다. owner가 같은 계정으로 테스트 로그인을 해 보면 "이 계정이 로그인하면"과 이유 코드가 나온다 |
| 로그인 화면 "이 계정으로는 로그인할 수 없습니다 — …" | `403`. 허용 도메인 밖이다 |
| 공급자 로그인 뒤 "서버가 응답하지 않습니다 — 잠시 뒤 다시 시도하세요." | `503`. 서버가 IdP에 닿지 못했거나, IdP가 오류로 답했거나, IdP 주소가 허용되지 않았다. owner가 테스트 로그인을 해 보면 이유 코드(`provider_`로 시작)가 나온다 |
| "이미 이 이메일로 만든 계정이 있습니다 — …" | 같은 주소의 계정이 있어 붙이지 않았다(`409 LOGIN_LINK_REQUIRED`). 그 사람이 원래 쓰던 수단(비밀번호나 다른 공급자)으로 로그인해 **설정 > 로그인 수단**에서 [계정을 연결](#8-계정-연결과-끊기)한다. 비밀번호 로그인이 닫혀 있고 그 사람에게 비밀번호밖에 없으면 로그인하지 못하므로, 화면의 안내대로 owner에게 요청한다. owner는 [비밀번호 로그인을 다시 열고](#되돌리기), 그 사람이 연결하면 다시 닫는다 |
| **설정 > 로그인 수단**에서 연결·끊기가 막힌다 | 로그인한 지 10분이 지났다(`session_too_old`). 다시 로그인한다 |
| IdP 앞에서 돌아왔는데 거절된다 | 콘솔을 `CONSOLE_ORIGIN`과 다른 host 이름으로 열었다. cookie가 다른 host에 묶여 있다 |

이유 코드 전체는 [SSO 공급자별 값과 이유 코드](/run-server/self-hosting/reference/sso-providers)에 있다. 로그인이 망가져 아무도 들어오지 못하면 [로그인 복구](/run-server/self-hosting/recover-sign-in)를 따른다.

## 되돌리기

| 하려는 것 | 방법 |
| --- | --- |
| 공급자를 잠시 멈춘다 | 상세 화면의 **끄기**. 로그인 화면에서 빠지고, 그 공급자로 로그인한 세션이 모두 끊긴다. 내가 그 공급자로 로그인했다면 내 세션도 끊긴다. 마지막으로 통과한 테스트 뒤에 규칙을 포함한 설정을 바꾸지 않았다면 다시 켤 때 테스트를 다시 하지 않아도 된다 |
| 켜진 공급자의 client ID·인증 방식·설정 문서를 바꾼다 | 끄고, 바꾸고, 테스트하고, 켠다. 이름과 **누가 들어올 수 있나**의 규칙은 켠 채로 바꾼다 |
| client secret을 바꾼다 | 켠 채로 **값 바꾸기**. 새 값은 교체 후보로 들어가고 테스트 로그인이 그 값으로 통과하면 쓰인다. 그때까지 로그인은 지금 값을 쓴다. 후보를 거두려면 지금 쓰는 값을 다시 넣는다 |
| 공급자를 없앤다 | 끈 뒤 **삭제**. 설정과 client secret이 지워진다. 사람들의 계정과 그 공급자 계정의 연결은 남아, 같은 issuer로 다시 만들면 같은 사람으로 들어온다 |
| 비밀번호 로그인을 다시 연다 | **비밀번호 로그인**의 **열기**. 비밀번호가 있는 사람은 다시 비밀번호로 로그인한다 |
| IdP에서 지운 사람을 내보낸다 | werft는 IdP의 삭제를 모른다. **구성원** 화면에서 그 사람을 **비활성화**하면 세션과 개인 key가 폐기된다 |

## 보안 참고

- client secret은 DB의 secret 저장소에 `PLATFORM_SECRET_KEY`로 봉인한다. 화면과 API는 끝 네 글자와 바꾼 시각만 돌려준다. 로그에도 남기지 않는다.
- 공급자의 만들기, 바꾸기, secret 넣기, 테스트, 켜기, 끄기, 삭제, 비밀번호 로그인 열기·닫기, 비상 관리자 바꾸기, 계정 연결·끊기는 DB의 `receipts` 테이블에 감사 기록을 남긴다. 기록의 `operation` 이름은 [감사 기록](/run-server/self-hosting/reference/sso-providers#감사-기록)에 있다.
- 공급자를 끄면 세션 만료를 기다리지 않고 그 공급자의 세션이 끊긴다.
- 서버는 IdP의 서명 키(JWKS)를 로그인마다 새로 읽는다. IdP가 키를 돌리거나 지우면 다음 로그인부터 따른다.
- 로그인은 만들 때 확인해 둔 endpoint만 쓴다. IdP의 endpoint가 바뀌었으면 공급자를 끄고 **설정 문서**의 **다시 읽기**를 누른다.
- `http` IdP는 IdP와 `CONSOLE_ORIGIN`이 모두 loopback일 때만 받는다. 운영 설치는 평문으로 secret이나 code를 보내지 않는다.
