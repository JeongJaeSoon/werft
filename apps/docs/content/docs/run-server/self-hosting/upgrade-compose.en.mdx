## What you will do

Upgrade Compose after backup and compatibility checks. Approve checkpoint loss only after identifying the exact affected sessions.

<a id="준비물" />
## Before you begin

Read the target version's operator actions in the [changelog](https://github.com/JeongJaeSoon/werft/blob/main/CHANGELOG.md).

You need current/target source commits, release inputs, settings digests, and image digests. Check a recent successful backup and restoration drill, and notify users of downtime.

Check the [shared pre-upgrade gates](#실행-전-게이트) first.

<a id="단계" />
## Steps

<a id="1-대상-입력과-백업" />
### 1. Target input and backup

Select the tag from the [package contract](/run-server/self-hosting/reference/packages). Generate release-new.json outside the checkout as in [installation release generation](/run-server/self-hosting/single-server#3-release-입력-생성). First check out the target source commit and run `bun install --frozen-lockfile`. Release `source_commit` must equal checkout HEAD. Perform a [backup](/run-server/self-hosting/backup-and-restore) first.

<a id="2-api--proxy--worker-순서" />
### 2. API → proxy → worker order

For protocol or [gate](#실행-전-게이트) field changes, do not replace every image together. Check out the new source commit and install dependencies. Create an intermediate release changing only control_host to the target image while retaining current worker and egress_proxy images. Meet the same settings digest and source_commit requirements. Upgrade with it, then confirm readiness and that every API instance runs the new version.

Next upgrade to the final release with target egress proxy and worker digests. This prevents proxy/workers from sending new fields before the API is ready. Apply intermediate and final test-ops inputs separately through `scripts/test-ops.sh upgrade`.

Do not follow this order when you upgrade to the profile removal release. Upgrade straight to the final release, with no intermediate release, because an old worker cannot read the new control-host's answer ([Upgrade order of the profile removal release](#프로필-제거-릴리스의-업그레이드-순서)).

<a id="3-upgrade와-영향-세션" />
### 3. Upgrade and affected sessions

Run `upgrade` with step 1's `release-new.json`. A worker image change checks current checkpoints with the new image and refuses with exit 3 if sessions are incompatible. Affected ids are written to `$TEST_OPS_STATE_DIR/upgrade-<timestamp>.sessions`. Review them and notify users, then rerun `scripts/test-ops.sh upgrade release-new.json --approve-sessions approved.txt` with exactly those ids. Any difference is rejected; accepted approvals are recorded in the state directory. Recovering an incompatible session with `start_fresh` discards its checkpoint context. No approval is needed if none are affected.

Take a [backup](/run-server/self-hosting/backup-and-restore) immediately before upgrading. Reverting means running `upgrade` with the previous release file; the same rules apply because the worker image changes again.

If upgrade stops before the new release starts (for example, scheduler quota check failure), the installation remains stopped with `pending.json`. Only `status`, `reset`, and `upgrade` with a release identical to pending are allowed. Other commands, including upgrade to the previous release, are rejected. Fix the cause and rerun upgrade with the same target release.

If the installation merely went down through `compose down` or reboot, use `scripts/test-ops.sh start` to reuse the same volumes, rather than upgrade/deploy ([lifecycle](/run-server/self-hosting/stop-compose)). `start` rejects `pending.json`.

```bash
scripts/test-ops.sh upgrade release-new.json
```

Pass actual absolute paths outside the checkout for `release-new.json` and approval files. Target checkout HEAD must match release source_commit.

<a id="확인" />
## Verify

Check applied release, service health, and ready in status. Resume an existing session on a new worker; compare context, final checkpoint, and turn completion. For metric renames, update Datadog definitions/queries/filters and Prometheus rules, then verify actual series.

Compare overridden CSS names with changelog operator actions and update them too. Do not assume aliases exist for old metric/CSS names.

<a id="자주-막히는-곳" />
## Troubleshooting

With pending.json, start and upgrade to the previous release are rejected. Fix the cause and upgrade to the identical pending target. Do not reuse old approval files if the affected list changes. start_fresh discards prior context.

<a id="되돌리기" />
## Roll back

Applying a previous release still follows upgrade checks and [gate](#실행-전-게이트) rollback floors. Do not simply revert image tags to builds unaware of new schemas/checkpoints. A pending failure before the new release starts rejects the previous release; recover using the same target.

## Pre-upgrade gates

Before upgrading, read every [changelog](https://github.com/JeongJaeSoon/werft/blob/main/CHANGELOG.md) entry between the deployed version and the target. When a release in that range has steps under [Per-release tasks](#릴리스별-작업) below, follow them too. When deploying, check the commit and the three digests of the [release manifest](/run-server/self-hosting/reference/packages#릴리스-manifest-읽기) together.

The current rollback floor is `v0.2.0`. Its migration `0270` deletes the profile data, so do not go back to older images ([Rollback floor of profile removal](#프로필-제거의-롤백-하한)). If the changelog marks a later release as irreversible, that release is the floor. To go back further than the floor, restore the database from the backup taken before the upgrade. Before considering a rollback, count the affected sessions with read-only SQL and decide first whether you can roll forward without losing data.

Test new control-host with the previous worker before deployment: complete session turn 1 → remove worker → complete turn 2 from checkpoint, with no 400 BAD_REQUEST in API worker requests. Empty-installation ready 200 does not substitute. Look at turn 1 first. When the previous worker cannot read the new control-host's answer, the API answers 200 and the worker exits right after it starts, so the absence of 400s does not catch this failure. The profile removal release does not support this combination. When you upgrade to it, check that turn 1 completes with the new control-host and the new worker ([Upgrade order of the profile removal release](#프로필-제거-릴리스의-업그레이드-순서)).

<a id="compose-전용-checkpoint-검사" />
### Compose checkpoint checks

When worker images change, Compose upgrade checks calculate restoration plans for every current checkpoint using the new image's engine/SDK/CLI/profile digest. Sessions matching all four continue without approval; notify users and approve the exact `INCOMPATIBLE_CHECKPOINT` list. If checking cannot complete or other validation failures occur, fail closed: include every session with uncollected checkpoints and log this. Recheck after stopping writers. `start_fresh` discards incompatible checkpoint context. Kubernetes pre-upgrade hooks make equivalent decisions from pointer combinations without executing images ([Kubernetes checks](/run-server/self-hosting/upgrade-kubernetes#3-검사-결과와-예외)).

On a worker image change, upgrade retains the old image in the state directory's `previous-worker` file. For each session, the scheduler matches checkpoint engine/SDK/CLI/profile digest scheme against current/previous images, preferring current if both match ([configuration](/run-server/self-hosting/reference/configuration)). The affected list therefore includes sessions restorable by neither image. If either image check fails closed, retain the new-image list unchanged. For rebuilt images with the same combination, the scheduler selects current: do not remove sessions unverified on current merely because previous can restore them. If either is too old to report its combination (a build without combination reporting), previous is not used and the gate retains the new-image list. The support window is one release: another upgrade can affect sessions left on the older image. In the profile removal release, no session launches on the previous image ([Upgrade order of the profile removal release](#프로필-제거-릴리스의-업그레이드-순서)).

<a id="runtime-버전의-공통-준비" />
### Shared runtime version preparation

An SDK upgrade release changes the runtime version the image ships. A release pins the runtime version its image shipped when it was made, and its sessions run that version. A new session on a release whose version neither the current nor the previous image ships is refused with `UNSUPPORTED_CAPABILITY`; release that agent again. Checkpoints resume only on images with the same engine/SDK/CLI combination they were made with, regardless of this check. For Kubernetes (helm) rollback steps and cautions, see [Kubernetes upgrade § Rollback](/run-server/self-hosting/upgrade-kubernetes#되돌리기).

## Per-release tasks

Steps for particular releases that the changelog points to. Follow only the sections for releases between the deployed version and the target.

<a id="프로필-제거의-롤백-하한" />
### Rollback floor of the profile removal

The release that removes run profiles runs migration `0270_remove_profiles`, which drops the profile tables and columns and deletes the releases made on profiles, their sessions, and the records under those sessions (turns, events, checkpoint rows and so on; 45 tables). Slack outbox rows that name no session (welcome notices and the like) are kept. Of the usage tables only `provider_usage`, which hangs off sessions, is emptied; `agent_usage` stays. Agents and their card versions, teams, keys and the installation settings stay. From then on every session runs the spec its release pinned (connection, model, runtime, tools), and an agent runs again once it is released on a connection. Each connection needs the model list (`models`) agents may pick from, and a release cannot use a model its connection does not list. `0270` fills only connections whose list is empty, with the models of the profiles that mapped to that connection. A connection no profile mapped to keeps an empty list, and a connection that already had a list gets nothing added. After the upgrade, check that every connection lists all the models its agents use, and add the missing ones. In the settings document, delete the top-level `profiles` key and the `profiles` of each repository entry. `settings import` (CLI and API) refuses a document with the top-level key. The CLI drops a repository entry's `profiles`, but the API refuses it. **You cannot roll back to a build older than this release.** To go back, restore the database from the backup taken before the upgrade.

<a id="프로필-제거-릴리스의-업그레이드-순서" />
### Upgrade order of the profile removal release

Upgrade the control-host and worker images together, in one upgrade, to the profile removal release. Its control-host leaves `runtime.profile_id` and `profile_fingerprint` out of the `bootstrap-claim` answer. A worker built before the profile removal (`v0.1.3` included) requires both fields. So that worker logs `POST /bootstrap-claim answered a body this worker cannot read` as soon as the answer arrives and exits with code 1. The session is launched three times and then stops as `recovery_required` (`STARTUP_FAILED`, `execution_gone`). The API answers this request with 200, so looking for 400s on worker requests in the API log does not find this failure. Whether the session's turn 1 completes does.

- Do not do the intermediate release of [2. API → proxy → worker order](#2-api--proxy--worker-순서) or [step 1 of the Kubernetes upgrade](/run-server/self-hosting/upgrade-kubernetes#1-대상-chart와-제어-영역-우선-교체) for this release. While the new control-host runs with old workers, no new session starts. On Compose, `upgrade` straight to the final release. On Kubernetes, upgrade straight with the step 2 commands.
- A worker image built before the profile removal is outside this release's support window. Do not put such an image in `images.workerPrevious` on purpose. But the Kubernetes [pre-upgrade check](/run-server/self-hosting/upgrade-kubernetes#3-검사-결과와-예외) requires `images.workerPrevious` to be the deployed image in an upgrade that changes the worker image, and approval cannot bypass this. So pass the `worker-previous.json` that the step 2 script makes (the deployed worker image) unchanged in this upgrade. The `previous-worker` file that the Compose `upgrade` keeps is the same. No session launches on that image: `0270` empties the sessions, new sessions always start on the current image, and the current image seals the checkpoints after that. The next upgrade that changes the worker image replaces the previous image with this release's image.
- After the upgrade, check that one new session completes turn 1.

<a id="지운-slack-연결-env" />
### Removed Slack linking variables

From this release on, the API and the slack role no longer read `SLACK_OIDC_REDIRECT_URI`, `SLACK_OIDC_CLIENT_ID` or `SLACK_OIDC_CLIENT_SECRET`. The Slack account linking redirect is `CONSOLE_ORIGIN` with the fixed path `/settings/linked-accounts/slack`. The client ID and secret come only from each workspace's link app, made in Settings > Workspace > Integrations > Slack.

- Before you upgrade, check that the API and the slack role have `CONSOLE_ORIGIN`. Earlier releases used the origin of `SLACK_OIDC_REDIRECT_URI` when `CONSOLE_ORIGIN` was unset. In this release, Slack account linking then answers `503`, Slack apps cannot be created, and, unless an events entrance is saved (below), no event subscription is registered (`events_url_unset`).
- Remove the three variables. On Compose, `infra/compose.core.yml` no longer passes them, so delete the lines from your env file. On Kubernetes, delete them from `api.extraEnv` and `slack.extraEnv`. If one is still set, the API logs the warning `Ignored removed settings: <names>` once at startup. It prints no value and does not use it.
- This release cannot be rolled back to an earlier build ([Rollback floor of the profile removal](#프로필-제거의-롤백-하한)), so no line needs to stay for a rollback.

<a id="웹으로-옮긴-slack-이벤트-입구-주소" />
### Slack events entrance moved to the web

From this release on, the API no longer reads `SLACK_EVENTS_PUBLIC_URL`. When events enter apart from the console, an owner saves an https address without a query, fragment or credentials as the events entrance under **Settings > Integrations > Slack** (`PUT /v1/slack-settings`, audit record `update_slack_settings`). Left empty, the address computed from `CONSOLE_ORIGIN` applies. Before saving, the screen shows the computed address and the URL Slack will be sent. The value is one for the whole installation.

- Migration `0278_slack_settings` adds the `slack_settings` table. When the new API first starts with that table empty and `SLACK_EVENTS_PUBLIC_URL` actually present in the API container, it carries the value in once and logs a warning without the value. The carry-over is recorded as an audit record without an author (`by: "env_import"`). Compose's `infra/compose.core.yml` does not pass this variable to the API, so it is carried in only if you passed it yourself through an overlay of your installation or `api.extraEnv` (Kubernetes). Otherwise, save it on the screen after the upgrade.
- After the carry-over, delete the line from your env. While it stays, every start logs `Ignored removed settings: SLACK_EVENTS_PUBLIC_URL`. A value that is not https or has a query is not carried in, and the warning says so. Unlike earlier releases, startup does not stop.
- Changing the saved address does not send it to apps already made. Press Recheck on the agent's Slack tab, or run `slack-app finalize`.
- Keep the `slack_settings` table when rolling back. Earlier builds do not read it.

<a id="웹으로-옮긴-실행-한도" />
### Execution limits moved to the web

An owner saves twelve installation-wide settings (execution limits, session event archive, and workspace retention) under **Settings > Workspace > Execution limits** instead of env (`GET`/`PATCH /v1/installation-config`, audit record `update_installation_config`). No role reads the env below. A save applies at once on that API and within 10 seconds on other replicas and on the scheduler, slack, and metrics roles. A request already waiting keeps the wait it was given. The turn time and model request retries reach launches reserved after the save, and a worker started with other values stops once its current turn ends ([changing the turn time and retries](/run-server/self-hosting/explanation/isolation#turn-시간과-재시도를-바꿀-때)). The archive job reads its two settings each time it runs, and the scheduler the two workspace retention times each time it reclaims workspaces. Ranges and defaults are in [execution limits set on the web](/run-server/self-hosting/reference/configuration#웹에서-정하는-실행-한도).

| Section on the screen | Env carried in |
|---|---|
| Human answers | `PENDING_REQUEST_TTL_SEC` |
| Session cost | `SESSION_COST_LIMIT_USD` |
| Session tokens | `SESSION_TOKEN_LIMIT` |
| Waiting messages | `QUEUED_INPUT_LIMIT_PER_SESSION` |
| Kept input | `STORAGE_LIMIT_BYTES` |
| Workspace size | `WORKSPACE_ENFORCE` |
| Turn time | `MAX_TURN_SECONDS` |
| Model request retries | `PROVIDER_MAX_RETRIES` |
| Session event archive: idle before archiving | `SESSION_ARCHIVE_AFTER_DAYS` |
| Session event archive: what the archive job does | `SESSION_ARCHIVE_DRY_RUN` |
| Stopped sessions' workspaces | `EXECUTION_WORKSPACE_STOPPED_TTL_SEC` |
| Paused sessions' workspaces | `EXECUTION_WORKSPACE_PAUSED_TTL_SEC` |

- Migration `0281_installation_config` adds the `installation_config` table, one row per key. Migrate then carries the values in before any role starts. For a key with nothing saved and an env value present, it carries the value in once and logs `note: <env> was carried into Settings > Workspace > Execution limits and is no longer read; remove it`, without the value. With a workspace, the carry-over is recorded as an audit record without an author (`by: "env_import"`). A blank value counts as unset.
- `infra/compose.core.yml` takes the twelve variables from the host env or `.env` and passes them to migrate only. A value you kept in `.env`, as earlier releases read it, is carried in as is. A value you passed to api, scheduler or maintenance through an overlay is not: move it to `.env` before upgrading, or save it on the screen after. With nothing set, the defaults apply; they are the defaults earlier Compose files used (a turn time of 3600 seconds, 2 retries, archiving after 180 days, count only, 86400 seconds for each workspace retention time). While the workspace retention times cannot be read (a blocked key, a database outage), the scheduler does not stop; it only reclaims no new `stopped` or `paused` session's workspace. When the carried turn time and retries equal a running worker's, that worker keeps running after the upgrade.
- After the carry-over, delete the line from your env. While it stays, every migrate run logs `note: Ignored removed settings: <env>`. The env never changes a saved value.
- A value outside the range is not carried in (`note: <env> was not carried in`). Unlike earlier releases, startup does not stop, and the default does not apply either. That key is blocked until a value is saved on the screen, and so is a saved value outside this version's range. Only the work that reads a blocked key is refused, and the screen marks the field. What is refused is under "With no usable value" in [execution limits set on the web](/run-server/self-hosting/reference/configuration#웹에서-정하는-실행-한도). For example, with the session cost blocked, new sessions and messages are refused with `503 BACKEND_UNAVAILABLE` and the scheduler skips launches.
- Workers no longer read `QUESTION_TIMEOUT_SEC`. No launcher ever passed it, so nothing changes (30 minutes until the gateway registers the request).
- Keep the `installation_config` table when rolling back. Earlier builds do not read it and read the env instead (the Compose defaults when unset). To keep a value changed on the screen under the rolled-back build, put it back in `.env`.

<a id="설정-문서는-빈-설치에-한-번만-들어간다" />
### The settings document seeds an empty installation once

From this release on, migrate imports the settings document (`SETTINGS_DOCUMENT`, `PLATFORM_SETTINGS_DOCUMENT` in test-ops) only into an empty installation, once (`settings seed`). After that, connections, repositories and MCP servers are changed in the console (Settings > Agent connections). Editing the document and deploying again does not import it.

- Migration `0282_settings_seed_decided` adds the column `settings_generation.seed_decided_at`. The first migrate after the upgrade that is given a settings document records that time. Without `SETTINGS_DOCUMENT`, migrate runs no seed, so neither the time nor the log line appears. An installation that already holds a connection or an MCP server (disabled ones included) imports nothing and only records the time. An installation holding repository rows alone counts as empty and is seeded once.
- When nothing is imported, migrate logs one line without values: `note: the settings document <file> (SETTINGS_DOCUMENT) not imported: the installation already holds settings. It seeds an empty installation only; change settings in the console`. Once the time is recorded, it reads `the automatic seed ran on <time>`. This line is not a failure.
- To import the document's content again on purpose, an owner runs `settings import` by hand. That command is unchanged.
- test-ops `upgrade` neither imports a changed document nor compares it with the database. When the document's digest changes, it logs `upgrade: the settings document changed; it is not imported into a deployed installation, so change settings in the console`. The check in `deploy` is unchanged.
- After a rollback, the earlier release's migrate imports the document on every deploy again. When an item changed in the console differs from the same id in the document, that import is refused, migrate fails and the API does not start. Before rolling back, remove such items from the document or match them to the console. Keep the `seed_decided_at` column. Earlier builds do not read it.

<a id="env로-가리키던-자격-증명은-db로-한-번-옮긴다" />
### Credentials named by env move into the database once

From this release the api no longer reads a setting's `value_env` (a connection, a repository naming its own GitHub App, an MCP server) from env. When it reads the settings it seals the value in the database as that row's own stored value, once. `secret_id` stays as it is.

- Migration `0285_credential_carried_auth` adds a `carried_auth` column to `provider_connections`, `catalog_repositories` and `mcp_servers` and a `carried_binding` column to `catalog_repositories`, and changes `catalog_repositories_credential_check` so an explicit App repository may hold a stored value. It adds an INSERT trigger (`…_carried_binding`) to `push_requests` and `worker_credentials`.
- After the upgrade the api logs, once per moved row, `<kind>:<id> took its credential from <name> into the database and no longer reads it; remove <name>`. The name can then go from env. No value is in the log or the receipt: the `set_settings_credential` receipt carries the variable's name and `by: env_import` only.
- With no workspace yet (before bootstrap) the value is read from env until then, and moved on the first settings read after the workspace exists (within 10 seconds).
- A row whose variable has no value is left out, with one warning: `<kind>:<id> names <name>, which the API does not have, so it is left out. …`. Set the variable and restart the api. A connection can also take its key from the console's "Enter key on screen".
- A value the run path would refuse (a key shorter than 8 bytes or with surrounding whitespace or a control character, an App key that is not an RSA private key PEM), and a key shorter than 8 characters (a stored value shows its last four), is not moved. The row is left out, with one warning: `<kind>:<id> is left out and not carried into the database: <reason>. Correct <name> and restart the API`. The reason names the variable only.
- Moving an explicit App repository changes its credential reference and so its repository binding. In the same transaction, the push requests and running sessions' repository tokens that hold exactly the old binding move to the new one. So a push made before the move still opens and merges a pull request, and a running session gets its token again. The counts are in the log (`… (N push requests and M worker credentials moved to its new binding)`) and in the receipt's `rebound`. A row written later with the old binding, by a replica that has not read the move yet (each reads again every 10 seconds) or by a previous build, is stored with the new binding as it is written (the trigger above). Once the rollback SQL clears `carried_binding`, the trigger changes nothing. The moving transaction locks both tables, so requests that write push requests or worker tokens wait meanwhile. When it cannot lock them within 5 seconds it moves nothing and tries again on the next read. Afterwards change that App's key with `POST /v1/installation/settings/repositories/{id}/credential` (owners and admins, an RSA private key PEM). Changing env is no longer read.
- **Upgrade to this release with one api, or start the new build only after every old replica is down.** Each replica reads the settings again every 10 seconds on its own, so one that has not read the move yet may meanwhile fail a moved push request with `catalog_changed` or refuse a running session's token reissue. Compose runs one api, so upgrade it as usual. With Helm, follow step 1 of the [Kubernetes upgrade](/run-server/self-hosting/upgrade-kubernetes). A push failed that way is pushed with the new binding when requested again.
- Importing the old document by hand with `settings import` after the move stops at `conflicts` for the moved items: same id, other content. Remove them from the document, or use one from `settings export`.
- A URL repository (`auth` `basic` or `bearer`) is not used to run anything, so it is not moved.
- Rollback: earlier builds read a stored value on connections and MCP servers, but refuse one on an explicit App repository, which drops out as `invalid`. Roll back in this order:
  1. Stop every api replica of this release. One left running moves the rows back on its next settings read (within 10 seconds).
  2. Run the SQL below as one transaction. It puts the rows' env references back, and the bindings the move changed on push requests and worker tokens.
  3. Give the api those variables again and start the earlier build. If a key was changed in the console after the move, the row goes back to the env value, so put the new value in env.

  Keep the `carried_auth` and `carried_binding` columns and the sealed values.

```sql
BEGIN;
UPDATE push_requests p SET repository_binding = r.carried_binding->>'from' FROM catalog_repositories r WHERE r.carried_binding IS NOT NULL AND p.repository_binding = r.carried_binding->>'to';
UPDATE worker_credentials w SET binding = r.carried_binding->>'from' FROM catalog_repositories r WHERE r.carried_binding IS NOT NULL AND w.purpose = 'repository' AND w.binding = r.carried_binding->>'to';
UPDATE provider_connections SET definition = jsonb_set(definition, '{auth}', carried_auth), credential_source = 'external', carried_auth = NULL WHERE carried_auth IS NOT NULL;
UPDATE catalog_repositories SET auth = carried_auth, credential_source = 'external', carried_auth = NULL, carried_binding = NULL, version = version + 1 WHERE carried_auth IS NOT NULL;
UPDATE mcp_servers SET auth = carried_auth, credential_source = 'external', carried_auth = NULL WHERE carried_auth IS NOT NULL;
COMMIT;
```

<a id="외부-자격-증명-출처를-없앤-릴리스" />
### The release that removes external credential sources

From this release model connections, MCP servers and repository GitHub App keys use only values stored in the database. The settings' `value_env` (the api's env) and `secret_id` (AWS Secrets Manager) are gone, and the api uses Secrets Manager nowhere. Enter a value in the console (Settings > Model connections or MCP servers) or with `POST /v1/installation/settings/{connections|mcp-servers|repositories}/{id}/credential` under an owner session; it is encrypted with `PLATFORM_SECRET_KEY` and kept in the database. A repository App key has no web screen and goes through this API only (the GitHub App RSA private key PEM). `PLATFORM_SECRET_KEY`, `DATABASE_URL`, `EGRESS_AUTHORIZER_TOKEN`, the object store keys, the Slack and IdP secrets (already kept in the database) and repository `auth` `none` stay as they are.

- Before upgrading, enter the key of each model connection that names env or Secrets Manager with **Enter key on screen** in the current release's console. Its sessions then keep running after the upgrade. You can also enter it after the upgrade. The current release has no way to move an MCP server's key or a repository App key, so enter those right after the upgrade (below).
- A disabled connection or MCP server that still names env or Secrets Manager cannot be enabled again after the upgrade: the console takes no key for a disabled row and does not enable a row without a key. To keep such a connection, enable it and enter its key with **Enter key on screen** before upgrading. Enable such an MCP server before upgrading and enter its key after. Otherwise, after the upgrade, make a new connection or server under a new id; ids are never reused.
- Migration `0288_remove_external_credentials` turns each row that named env or Secrets Manager into a stored row without a value. It is `needs_value` (**Needs a value** on screen) until its key is entered, and sessions that use it do not run. Enter a connection's key with **Set API key**, an MCP server's with **Replace value**, and a repository App key through the API above. The old `auth` stays in `carried_auth` as history only and is never read. An explicit App repository's binding changes, so the same migration moves that repository's worker credential bindings to the new value. Its push requests' binding moves when its App key is entered, so a pull request cannot be opened from a push made before the upgrade until then. A key taken by an older api replica moves no push, so enter repository App keys after every api runs the new build (enter one again if it went in earlier).
- Change the settings document's `value_env` and `secret_id` entries to `"stored": true` before importing it again. Otherwise `settings import` (API, CLI) refuses it with 400 `invalid_document`, and the CLI names the field.
- After the upgrade, remove the key variables connections named (for example `ANTHROPIC_API_KEY`) and `AWS_ENDPOINT_URL_SECRETS_MANAGER` from the api's env; the api reads none of them. For Helm, follow the [Kubernetes upgrade](/run-server/self-hosting/upgrade-kubernetes).
- A connection or MCP server made in the console is saved only with its key. The web keeps the save button off until 8 or more characters are typed; the API refuses with 400 a missing key, one shorter than 8 bytes, or one with control characters or surrounding whitespace; the database refuses a console-made row without its value in the same transaction. The console's "Enter key on screen" button, which turned an external connection into a stored one, and the `POST …/connections/{id}/convert` route are gone.
- The 0285 rollback SQL above no longer applies after this release: `credential_source` allows `stored` only.

<a id="쓰지-않는-표-셋을-지운-릴리스" />
### The release that drops three unused tables

Migration `0305_drop_unused_tables` drops the `catalog_authority`, `owner_workspace_map` and `push_continuations` tables with their rows. No release since `v0.1.0` reads or writes the first two, and the last release that used `push_continuations` is `v0.1.1`. Rolling back to an image inside the support window is therefore unaffected.

- The tables may still hold rows. `catalog_authority` may hold one revision activated in the days of the file catalog, `owner_workspace_map` owner-to-workspace mappings an operator inserted by hand, and `push_continuations` follow-up turn records made by `v0.1.1` or earlier. When there are rows, the migrate log `db.migrate.notice` records how many each table lost (`0305: dropped rows: …`). The values of the rows stay out of the log.
- If you need those rows, back them up before the upgrade. Rolling the schema below 0305 does not bring them back.

<a id="slack-글을-입력-접수-표에-적는-릴리스" />
### The release that records Slack posts in the input table

Migration `0314_conversation_inputs` adds the input table `conversation_inputs`. The slack role still turns a mention, a DM or a post in a linked thread into a session turn as before, and in the transaction that marks its inbox row processed it records the post as one input row. From this release it also fills `conversations` and `conversation_topics` from 0310. The upgrade needs nothing from you, and Slack and sessions behave as before.

- An input row keeps the post's place (team, channel, ts), its number within the topic (the thread), the requester (a Werft user id, or the Slack user id of an allowed bot) and the turn it became. It keeps no message text.
- A post that arrives as both a `message` and an `app_mention` event, or that Slack sends again, is one row per agent. A post that became no turn (refused or ignored) is not recorded.
- Numbers follow the order the server took the posts in. A late event gets the later number even when its Slack ts is earlier.
- The reconciler no longer removes the delete and edit marks (`deleted_sources`, `edited_sources`) of a post with an input row after 70 minutes.
- Rolling back to an image inside the support window makes turns as before, with no input rows for the posts in between.

<a id="대화-층의-빈-표-셋을-더한-릴리스" />
### The release that adds three empty conversation tables

Migration `0310_conversation_scopes` creates the `channel_contexts` (channel objects), `conversations` (an agent's main conversations) and `conversation_topics` (a conversation's topics) tables, empty. No code in this release reads or writes them yet, so the upgrade needs nothing from you, and Slack and sessions behave as before.

- Rolling back to an image inside the support window is unaffected. Older code does not know these tables.

<a id="처리한-slack-이벤트-원문을-지우는-릴리스" />
### The release that clears the body of processed Slack events

Migration `0308_slack_inbound_payload_check` changes the CHECK on `slack_inbound_events`: a processed or failed row may go without its body (`payload`). This release's slack role clears the body when it finishes processing, and the reconciler clears it on failed rows received more than 7 days ago. The retention is in [Retention by data](/run-server/self-hosting/reference/storage#데이터별-보존).

- The new CHECK is looser than the old one. It accepts an earlier slack role that keeps the body, so rolling back to an image inside the support window is fine.
- Once any row has lost its body, the old CHECK (`slack_inbound_events_dropped_check`) cannot be put back. Do not roll the schema below 0308. A cleared body does not come back.

<a id="사람에게-바로-가는-slack-글을-막는-릴리스" />
### The release that stops Slack posts aimed straight at a person

Migration `0309_slack_outbox_channel` adds the CHECK `slack_outbox_channel_check` to `slack_outbox`. Only a model notice (`model_notice`) may have a Slack user id (`U…`, or `W…` on Enterprise Grid) as its channel. This keeps the agent from opening a direct message with a person first. No release so far wrote such a row, so there is usually nothing to do.

- If such rows remain, the migrate log `db.migrate.notice` records how many (`0309: … slack_outbox rows name a Slack user as their channel`) and migrate stops at `VALIDATE CONSTRAINT`. The constraint then stays `NOT VALID` and still refuses new rows. You can check before the upgrade with this query:

```sql
SELECT kind, status, count(*) FROM slack_outbox
WHERE channel_id ~ '^[UW]' AND kind <> 'model_notice'
GROUP BY 1, 2;
```

- Rows it finds are rows that must not be sent. Delete them and run migrate again; every statement may run again.
- The sender also never posts such a row to Slack: it ends `failed` with the `error_code` `user_channel`.
- Earlier images write no such row either, so rolling back with the constraint in place is safe.

<a id="예산-계정-표를-더하는-릴리스" />
### The release that adds the budget account tables

Migration `0314_budget_accounts` creates three empty tables: `budget_limits` (the workspace's limit for every person, a person's own limit, an agent team's limit), `budget_accounts` (what a person's or a team's account spent and holds reserved each month, months cut in UTC), and `budget_reservations` (the reservation and settlement of each call). Nothing to do.

- In this release no call reads or writes these tables. The session cost and token limits work as before, and there is no screen, API or operator command that sets a budget limit yet.
- The migration only adds tables, so rolling back to an image inside the support window is fine.

<a id="slack-글의-수정삭제-표식" />
### Marks of edited and deleted Slack messages

Migration `0312_slack_source_marks` creates two tables, `deleted_sources` and `edited_sources`. From this release, an event for a deleted or edited Slack message (`message_deleted`, the tombstone `message_changed` that comes when a message with replies is deleted, and a `message_changed` for a person's edit) is no longer dropped: it leaves a mark with only where the message was (team, channel, ts) and when. Neither the message text nor the event body is stored anywhere, and the inbox row stays `processed` without its body. There is nothing to do.

- Werft keeps no record that points at a message yet, so the reconciler removes every mark 70 minutes after it was made (the 10-minute judgment buffer and an hour). The log `Unknown Slack source marks purged` records how many it removed. The retention is in [Retention by data](/run-server/self-hosting/reference/storage#데이터별-보존).
- Queries that count the drop reason `message_subtype` see fewer rows, without the edits and deletes. A `message_changed` no person made, such as a link preview, is still dropped.
- The migration only adds tables, so rolling back to an image inside the support window is fine. The earlier image does not use them and drops edits and deletes again.

<a id="slack-스레드의-link-이력-칸을-더한-릴리스" />
### The release that adds link history columns for Slack threads

Migration `0313_session_link_history` adds the columns `closed_at` and `closed_reason` to `session_links`, with two partial uniques that cover only links not closed (`session_links_open_surface_ref_uniq`, `session_links_open_session_uniq`), and adds the column `session_link_id` to `slack_outbox`. Code in this release does not read or write the new columns yet, so there is nothing to do and behavior is unchanged. Every existing row stays an open link.

- The two old uniques (`session_links_surface_ref_key`, `session_links_session_uniq`) stay. A later release drops them.
- Indexes are built `CONCURRENTLY`, and the CHECKs and the foreign key are added `NOT VALID` and validated on their own, so writes are not blocked while they validate or build (adding the columns and constraints takes a brief lock).
- Every statement may run again. If an index build is cut short, run migrate again: it drops the leftover INVALID index and builds it again.
- Earlier images write without the new columns and resolve conflicts on the old uniques, so they keep working. Rolling back to an image in the support window is safe.

### Mock Slack variable names

`SLACK_API_URL` and `SLACK_OIDC_ISSUER`, used by the mock Slack test stack (`infra/compose.mock-slack.yml`), are now `MOCK_SLACK_API_URL` and `MOCK_SLACK_OIDC_ISSUER`. <a id="성과-판정-연결과-되돌리기" />
### Achievement judge connections and rollback

Once an `openai_decisions` connection (for the Luna achievement judge) exists, a build that does not know this kind fails the whole Settings > Agent connections > Model connections list and `GET /v1/installation/settings/connections`, other connections included. Disabled connections are still read for the list, so disabling does not help. Agent runs and releases skip the connection and are not affected. Before rolling back, delete those connection rows in the database.

```sql
DELETE FROM provider_connections WHERE definition->>'kind' = 'openai_decisions';
```

The stored key value stays. The connection id saved in the judge settings stays too, and the rolled-back build does not judge Luna rules. After upgrading again, create the connection again and pick it in the judge settings. Rolling back by restoring the pre-upgrade database backup needs no extra step.
