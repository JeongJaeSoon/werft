## What you will do

Create a Compose installation using LocalStack on a Linux test server. This is a non-persistent test path: objects can disappear when the host or Docker restarts.

<a id="준비물" />
## Before you begin

| Item | Requirement |
| --- | --- |
| Operating system | Linux, both `x86_64` and `arm64` |
| Docker Engine | 28 or later |
| Docker Compose | 2.24.6 or later |
| Disk | Docker data-root on XFS mounted with `prjquota`. `preflight` checks this with the quota probe and stops otherwise. Complete [XFS disk preparation](/run-server/self-hosting/prepare-xfs) first on ext4 servers. Docker Desktop is unsupported |
| Time | NTP synchronized. Docker starts automatically after reboot |
| Tools | For a checkout installation, `git`, `jq`, `curl`, `openssl`, Bun 1.3.14, and the Docker Buildx plugin. For a release bundle installation, `jq`, `curl`, `openssl`, `sha256sum`, and `tar` (with gzip). Both need an account with Docker daemon access |
| External access | Download images from `ghcr.io` and Docker Hub without signing in. Sessions connect to `api.anthropic.com` and `github.com` |

As in [single-server installation](/run-server/self-hosting/single-server), there are two ways to install. A repository checkout works for every published tag, and a `v*` release can also be installed from its bundle with no checkout and no host Bun. Either way, the Compose files and `scripts/test-ops.sh` are read from the downloaded directory, and no image is built.

Complete [XFS preparation](/run-server/self-hosting/prepare-xfs) on a Linux server separate from production data. Choose a test-only project, installation id, ports, and state/secret directories. test-ops defaults to project `werft-test-ops`; override it with `TEST_OPS_PROJECT`. If the default paths below belong to an existing installation, choose different paths and `TEST_OPS_*` values.

## Steps

<a id="1-이미지와-소스" />
### 1. Images and source

```bash
TAG='<published-image-tag>'
SOURCE_REF='<matching-source-commit-or-release-tag>'
for app in control-host worker egress-proxy; do
  echo "$app $(docker buildx imagetools inspect "ghcr.io/jeongjaesoon/werft-$app:$TAG" --format '{{.Manifest.Digest}}')"
done
```

```bash
git clone https://github.com/JeongJaeSoon/werft.git
cd werft
git checkout "$SOURCE_REF"
bun install --frozen-lockfile
```

Confirm all three images return digests and that you checked out the matching source commit.

To install a `v*` release without a checkout, follow [Get the release bundle in single-server installation](/run-server/self-hosting/single-server#릴리스-번들로-받기) instead of the two blocks above. Run the later steps from the bundle directory. The bundle refuses `backup` and `reseed`, so run the planned-restart procedure under "Troubleshooting" below from a repository checked out at the release's `source_commit`, with the same env file and state directory.

<a id="2-시험-설정" />
### 2. Test configuration

Keep secrets only in the env file `/etc/werft/test-ops.env`, outside the repository. The following block makes the settings directory and the state directory the operator's, and `init-config` makes this file anew from the example. The file is created `0600`, readable by the operator alone, and the random secrets are not shown on screen. If the file already exists, it is refused, never replaced. Put the origin of the console as the browser opens it in `<console-origin>`; for an SSH tunnel it is `http://127.0.0.1:<tunnel port>`.

```bash
sudo install -d -m 755 -o "$USER" /etc/werft
sudo install -d -m 700 -o "$USER" /var/lib/werft/test-ops
TEST_OPS_OBJECT_STORE=localstack scripts/test-ops.sh init-config --console-origin '<console-origin>'
```

A line starting with `init-config: wrote /etc/werft/test-ops.env` must appear. The arguments and the values filled in are those of [step 2 of the single-server installation](/run-server/self-hosting/single-server#2-비밀과-설정-문서); instead of the S3 arguments, `--localstack-port` moves the LocalStack host port. The example's `EXECUTION_INSTALLATION_ID=test-ops`, `PLATFORM_SETTINGS_DOCUMENT=/etc/werft/settings.json`, `EXECUTION_WORKSPACE_QUOTA=on` and private credential allowlist `localstack:4566` stay, and the AWS key, region, and bucket variables stay empty.

To write the env file yourself, copy `infra/test-ops.env.example` to `/etc/werft/test-ops.env`, owned by the operator with mode `0600`, and fill in the following in an editor.

| Variable | Value |
| --- | --- |
| `POSTGRES_PASSWORD` | Random value using only letters, digits, `.`, `_`, `~`, and `-` |
| `EGRESS_AUTHORIZER_TOKEN` | Random value of at least 32 characters |
| `PLATFORM_SECRET_KEY` | 64-character hex from `openssl rand -hex 32`. Losing it prevents reading stored credentials |

Add `CONSOLE_ORIGIN` yourself. Use `EXECUTION_INSTALLATION_ID=test-ops`, `PLATFORM_SETTINGS_DOCUMENT=/etc/werft/settings.json`, and `EXECUTION_WORKSPACE_QUOTA=on`. Set the credential allowlist to `api.anthropic.com:443,github.com:443` and the private credential allowlist to `localstack:4566`. Leave AWS key, region, and bucket variables empty as in the example. LocalStack uses fixed test keys and the `claude-sessions` bucket.

Put the settings document in `/etc/werft/settings.json` and list the GitHub repositories sessions will use. The first `deploy` puts it into the empty installation once; after that, edits to the document are not imported, so change settings in the console. It contains no secrets. Replace only the repository URL with your actual value. This example assumes a public repository. Each repository entry must contain `"auth": { "kind": "github_app" }`; otherwise `preflight` refuses the whole document and blocks installation. For a private repository, install the GitHub App on it ([GitHub](/integrations/github)).

The migrate container must read this file, so use `0644`. Create an empty file first, then fill it with the following content using an editor.

```bash
sudo install -m 644 -o "$USER" /dev/null /etc/werft/settings.json
```

```json
{
  "version": 1,
  "connections": {},
  "repositories": {
    "sample-app": {
      "url": "https://github.com/<owner>/<repo>.git",
      "branch": "main",
      "auth": { "kind": "github_app" }
    }
  }
}
```

<a id="3-release-입력과-설치" />
### 3. Release input and installation

Generate the release as in [single-server step 3](/run-server/self-hosting/single-server#3-release-입력-생성). If you downloaded the bundle, use that step's `manifest` command for bundles. Write it outside the checkout at `/var/lib/werft/test-ops/release.json`. Do not run the S3 preflight at this stage; use:

```bash
TEST_OPS_OBJECT_STORE=localstack scripts/test-ops.sh preflight /var/lib/werft/test-ops/release.json
TEST_OPS_OBJECT_STORE=localstack scripts/test-ops.sh deploy /var/lib/werft/test-ops/release.json
```

The quota check and service health must succeed. Add the model key through the console after installation.

<a id="확인" />
## Verify

Check `scripts/test-ops.sh status`, the ready response body and 200, and docs 200. Verify authentication under [First owner and keys](/run-server/self-hosting/users-and-keys). This trial does not prove production AWS S3 permissions or restoration with data.

## Troubleshooting

If the first `deploy` fails, started containers remain and `stop` is unavailable because `current.json` does not exist. Inspect failure logs for quota, network, or Secret issues. Confirm this installation's project name and bring it down as follows, without `-v`.

```bash
PROJECT='<this-installation-project>'
printf '%s\n' '{"services":{"x":{"image":"alpine:3"}},"networks":{"default":{}}}' \
  | docker compose --project-name "$PROJECT" -f - down --remove-orphans
```

After fixing the cause, rerun `deploy` with the same release file and environment. Use `start` to restart an installation that has already succeeded.

If `preflight` stops with `path(s) the containers mount cannot be read by the user their container runs as`, the container user in parentheses cannot read the listed path. Postgres (uid 999) and migrate (uid 1000) do not run as the host user, so this comes from a checkout or bundle made under a restrictive umask (`077`, `027`), or from a settings document other users cannot read. Run `chmod -R o+rX` on the checkout or bundle directory and `chmod o+r` on the settings document, or fetch it again under umask `022`. An installation whose postgres volume is already initialized does not read the init SQL again, so even if nothing showed before, it may first stop here at `upgrade` or `start` on a version with this check.

An upgrade that recreates the LocalStack container may lose objects. Postpone the upgrade unless `status` confirms 0 uncollected checkpoints. If API startup failure coincides with `pending.json`, `reseed` is also rejected; `reset` discards all data. `backup --stop` does not remove this block.

LocalStack loses its in-memory objects whenever its container restarts (a host reboot, a Docker restart, a recreated container). The bucket is made again on every start, but empty. The API of this trial installation does not refuse to start in that state: it gives up the uncollected checkpoints the database still has and starts. After an unplanned reboot there is nothing to do, and `reset` is not the answer.

- The owner, keys, settings and the session list stay.
- Sessions whose restore point was one of those checkpoints, closed ones aside, move to `recovery_required`. Decide whether each goes on without its earlier context (`start_fresh`) or is closed (`close`); see the recovery decision in the [API guide](/reference/api-guide).
- One warning line in the API log, starting with `The object store came back empty`, names the number of sessions and their ids.
- `/readyz` still answers 200, and `detail.checkpoints_forgotten_on_boot` in its body carries that number of sessions.

Do not restart the LocalStack container on its own. The API cleans up only when it starts, not while it runs. If a new checkpoint is written in between, the bucket is no longer empty, so the next start cleans up nothing either, and the sessions that lost their objects fail when they restore. If that happened, restart the whole installation at once with `scripts/test-ops.sh stop` and then `start`.

Releases up to `v0.4.0` do not clean up. Their API logs `Checkpoint bucket claude-sessions holds no object version` and refuses to start; unless you took `backup --stop` beforehand, only `reset` is left. For automatic and manual start conditions, see the [Compose lifecycle](/run-server/self-hosting/stop-compose).

To keep the sessions' context, back up and stop the writers before a planned restart. After the restart use `reseed`, not `start`. `start` brings the API up on the empty bucket, which gives the checkpoints up, and putting the objects back afterwards does not bring those checkpoints back.

```bash
# Back up, leave the writers stopped, restart the host, then restore the objects
scripts/test-ops.sh backup --stop
sudo reboot
scripts/test-ops.sh reseed /var/lib/werft/test-ops/backups/backup-<timestamp>
```

`reseed` checks the source project/bucket/checksum, an empty bucket, and absence of checkpoint changes since the last backup. It rejects unmet conditions. After object loss, with API startup failure and a pending upgrade, `reseed` is rejected. Even a backup made with `backup --stop` does not remove that block. Choosing `reset` in this state discards the database, sessions, and checkpoints. Do not use it as a routine reboot recovery command.

<a id="되돌리기" />
## Roll back

Follow [Stop and remove Compose](/run-server/self-hosting/stop-compose). For a successful installation, `scripts/test-ops.sh stop` brings down this project and retains volumes. For a failed first deploy, use the explicit-project cleanup with the Compose model on stdin above. A checkpoint-free trial does not authorize cleaning production buckets or other installations. reset is a separate choice requiring a deletion-scope check.
