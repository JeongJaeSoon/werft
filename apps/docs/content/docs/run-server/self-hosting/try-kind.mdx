## 무엇을 하게 되나

노트북의 격리된 kind 클러스터에서 chart와 API 준비 상태를 시험한 뒤 제거한다. 이 PostgreSQL·LocalStack은 운영 데이터 저장소가 아니다.

## 준비물

Docker, kind, Helm 3, kubectl이 필요하다. 1단계의 harness는 git, Bun 1.3.14와 저장소 checkout도 쓴다. 2단계의 게시 chart 시험은 checkout 대신 `curl`, `openssl`과 [chart 시험용 DB와 object store](/run-server/self-hosting/try-chart-dependencies#준비물)의 준비물을 쓴다. 설치·제거할 클러스터 이름과 registry 포트가 다른 작업과 겹치지 않아야 한다. NetworkPolicy를 강제하는 kind 버전을 사용한다.

## 단계

### 1. checkout의 시험 harness

```bash
git clone https://github.com/JeongJaeSoon/werft.git
cd werft
CLUSTER_NAME=werft-try REGISTRY_PORT=15001 deploy/kind/up.sh
export KUBECONFIG=~/.cache/werft/kind/werft-try/kubeconfig
```

스크립트는 cluster·registry·이미지·namespace·DB·LocalStack·Secret·chart를 준비하고 rollout과 ready/docs를 확인한다. 생성된 kubeconfig만 사용한다. `EXTRA_VALUES`로 설치별 값을 덮을 수 있지만 harness의 worker 이미지 `--set` 값은 바뀌지 않는다.

### 2. 게시 chart를 직접 시험하는 경우

harness 대신 게시 chart를 시험할 때는 저장소 checkout이 필요 없다. 별도의 kind 클러스터를 만들고, 이 클러스터만 가리키는 kubeconfig를 쓴다.

```bash
kind create cluster --name werft-try --kubeconfig "$HOME/.kube/werft-try"
export KUBECONFIG="$HOME/.kube/werft-try"
kubectl config current-context
```

마지막 명령이 `kind-werft-try`를 출력해야 한다. 이어서 같은 셸에서 [chart 시험용 DB와 object store](/run-server/self-hosting/try-chart-dependencies)의 1~4단계를 따른다. 그 페이지가 게시 chart의 `examples/`에 든 의존성 manifest와 최소 values를 꺼내 쓰고 Secret을 만들며, 4단계에서 게시 chart를 설치한다. LocalStack 초기화 스크립트는 그 manifest의 ConfigMap `localstack-init`에 들어 있으며, 릴리스 번들(`werft-test-ops-<tag>.tar.gz`)의 `infra/localstack/init/10-create-resources.sh`와 같은 파일이다.

첫 owner는 아래 [첫 owner 만들기](#첫-owner-만들기)에서 만든다. 링크는 DB에 있으므로 replica 2개 중 어디에 닿아도 통한다. 모델 key는 Secret에 넣지 않는다. key는 첫 owner가 콘솔에서 넣어 DB에 저장하는 값뿐이고, 이 시험은 key를 넣지 않는다. 실제 운영 자격 증명을 이 시험에 넣지 않는다.

## 확인

```bash
kubectl -n werft get job werft-migrate
for d in api egress-proxy reconciler scheduler; do
  kubectl -n werft rollout status deploy/werft-$d --timeout=600s
done
```

```bash
kubectl -n werft port-forward svc/werft-api 13000:3000 &
PF=$!
trap 'kill "$PF" 2>/dev/null || true' EXIT INT TERM
READY=0
for attempt in $(seq 1 30); do
  if curl --max-time 2 -fsS -o /dev/null http://127.0.0.1:13000/readyz; then READY=1; break; fi
  sleep 1
done
if [ "$READY" != 1 ]; then
  kill "$PF" 2>/dev/null || true
  trap - EXIT INT TERM
  false
else
  STATUS=0
  curl --max-time 10 -fsS -w '\n%{http_code}\n' http://127.0.0.1:13000/readyz || STATUS=1
  curl --max-time 10 -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:13000/docs || STATUS=1
  kill "$PF" 2>/dev/null || true
  trap - EXIT INT TERM
  [ "$STATUS" = 0 ]
fi
```

ready 200과 docs 200은 빈 설치의 준비 상태다. 세션과 worker Pod를 시작해 checkpoint 복원까지 확인한 결과가 아니다. kind의 PVC Bound만으로 byte 상한 강제를 증명하지 않는다.

### 첫 owner 만들기

위 블록은 끝에서 port-forward를 끈다. 링크는 port-forward 주소로 열므로, 먼저 port-forward를 다시 띄우고 api가 답할 때까지 기다린다.

```bash
kubectl -n werft port-forward svc/werft-api 13000:3000 &
PF=$!
until curl --max-time 2 -fsS -o /dev/null http://127.0.0.1:13000/readyz; do sleep 1; done
```

그 셸에서 [첫 owner 만들기](/run-server/self-hosting/users-and-keys#1-첫-owner-만들기)의 Kubernetes 명령으로 링크 파일을 받는다. `accept_url`이 `null`이면 `http://127.0.0.1:13000` 뒤에 `accept_path`를 붙여 열고, 명령에 준 이메일 주소로 owner를 만든다. 다 만들었으면 `kill "$PF"`로 port-forward를 끄고 링크 파일을 지운다.

## 자주 막히는 곳

직접 설치에서 Secret의 필수 키가 빠지면 Pod가 시작하지 않는다. 게시 chart를 못 받으면 fixture 렌더로 성공 처리하지 말고 해당 게시 패키지 설치 실패로 남긴다. 클러스터 밖 DB·S3 주소와 시험 의존성 주소를 섞지 않는다.

## 되돌리기

harness로 만든 경우:

```bash
CLUSTER_NAME=werft-try deploy/kind/up.sh down
```

직접 만든 `werft-try` 클러스터는 `kind delete cluster --name werft-try --kubeconfig "$HOME/.kube/werft-try"`로 제거한다. 실패했을 때도 이번 시험 클러스터만 정리하고 다른 context의 리소스는 건드리지 않는다.
