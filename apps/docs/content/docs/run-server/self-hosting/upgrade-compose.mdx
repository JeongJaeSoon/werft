## 무엇을 하게 되나

백업과 호환성 검사를 거쳐 Compose 설치를 새 release로 올린다. checkpoint를 잃는 승인은 영향 세션을 정확히 확인한 뒤에만 한다.

## 준비물

[변경 기록](https://github.com/JeongJaeSoon/werft/blob/main/CHANGELOG.md)에서 대상 버전의 운영자 작업을 먼저 읽는다.

현재와 대상의 source commit·release 입력·settings digest·이미지 digest가 필요하다. 최근 성공 백업과 복원 훈련을 확인하고 사용자에게 중단을 알린다.

[공통 실행 전 게이트](#실행-전-게이트)를 먼저 확인한다.

## 단계

### 1. 대상 입력과 백업

[패키지 계약](/run-server/self-hosting/reference/packages)에서 대상 태그를 고르고 [설치의 release 생성](/run-server/self-hosting/single-server#3-release-입력-생성)과 같은 방식으로 checkout 밖에 release-new.json을 만든다. 생성 전에 대상 source commit을 checkout하고 `bun install --frozen-lockfile`을 실행한다. release의 `source_commit`은 이 checkout의 HEAD여야 한다. 먼저 [백업](/run-server/self-hosting/backup-and-restore)을 수행한다.

### 2. API → proxy → worker 순서

protocol 또는 [실행 전 게이트](#실행-전-게이트)의 필드 변경이 있으면 한 번에 모든 이미지를 바꾸지 않는다. 먼저 새 source commit으로 checkout하고 의존성을 설치한 뒤, 대상 release에서 control_host만 새 이미지로 바꾸고 worker와 egress_proxy는 현재 이미지를 유지한 중간 release 파일을 만든다. 중간 release도 새 source commit의 compose 파일로 적용하므로, egress proxy는 이미지만 현재 것이고 설정(allowlist 등)은 새 release의 값으로 다시 뜬다. 동일한 settings digest와 source_commit 조건을 지킨다. 이 중간 release로 upgrade한 뒤 API가 ready이고 모든 API 인스턴스가 새 버전임을 확인한다.

그 다음 egress proxy와 worker를 대상 digest로 바꾼 최종 release로 upgrade한다. 이 순서가 API보다 proxy·worker가 먼저 새 필드를 보내는 것을 막는다. test-ops 설치는 중간·최종 release 입력을 각각 `scripts/test-ops.sh upgrade`로 적용한다.

프로필 제거 릴리스로 올릴 때는 이 순서를 따르지 않는다. 중간 release 없이 최종 release로 바로 올린다. 옛 worker가 새 control-host의 응답을 읽지 못하기 때문이다([프로필 제거 릴리스의 업그레이드 순서](#프로필-제거-릴리스의-업그레이드-순서)).

### 3. upgrade와 영향 세션

1단계에서 대상 source commit과 digest로 만든 `release-new.json`을 사용해 `upgrade`를 부른다. worker 이미지가 바뀌었으면 새 이미지로 현재 checkpoint를 검사하고, 호환되지 않는 세션이 있으면 종료 코드 3으로 거부한다. 이때 영향을 받는 세션 id가 `$TEST_OPS_STATE_DIR/upgrade-<시각>.sessions`에 적힌다. 목록을 검토하고 사용자에게 알린 뒤, 정확히 그 id를 담은 파일로 `scripts/test-ops.sh upgrade release-new.json --approve-sessions approved.txt`를 다시 부른다. 목록이 하나라도 다르면 거부하고, 진행하면 승인 기록을 상태 디렉터리에 남긴다. 호환되지 않는 세션을 `start_fresh`로 복구하면 이전 checkpoint의 context를 잃는다. 영향받는 세션이 없으면 승인 없이 진행한다.

업그레이드 직전에 [백업](/run-server/self-hosting/backup-and-restore)을 한 번 받는다. 되돌리기는 이전 release 파일로 `upgrade`를 다시 부르는 것이고, worker 이미지가 다시 바뀌므로 같은 규칙이 적용된다.

업그레이드가 새 release가 뜨기 전에(예: scheduler의 quota 검사 실패) 멈추면 설치가 멈춘 채로 남고, 상태 디렉터리의 `pending.json`이 남는다. 이 상태에서는 `status`, `reset`, `pending.json`과 내용이 같은 release 파일을 쓰는 `upgrade`만 허용하고, 이전 release로 되돌리는 `upgrade`를 포함한 다른 명령은 거부한다. 원인을 고친 뒤 같은 대상 release 파일로 `upgrade`를 다시 부르면 풀린다.

업그레이드가 아니라 `compose down`이나 호스트 재부팅으로 설치가 내려갔을 뿐이면 `upgrade`나 `deploy`가 아니라 `scripts/test-ops.sh start`로 같은 volume 그대로 다시 올린다([내리기](/run-server/self-hosting/stop-compose)). `pending.json`이 있으면 `start`는 거부한다.

```bash
scripts/test-ops.sh upgrade release-new.json
```

`release-new.json`과 승인 파일은 checkout 밖의 실제 절대 경로로 넘긴다. 대상 checkout의 HEAD는 release의 source_commit과 일치해야 한다.

## 확인

status의 적용 release·서비스 health·ready를 확인한다. 기존 세션을 새 worker에서 재개하고 context·최종 checkpoint·turn 완료를 대조한다. 지표 이름 변경이 있으면 Datadog 정의·쿼리·필터와 Prometheus 규칙을 새 이름으로 바꿔 실제 series를 확인한다.

덮어쓴 CSS 이름도 변경 기록의 운영자 작업과 대조해 새 이름으로 바꾼다. 옛 지표·CSS 이름의 별칭이 있다고 가정하지 않는다.

## 자주 막히는 곳

pending.json이 남으면 start와 이전 release로의 upgrade가 거부된다. 원인을 고친 뒤 pending과 동일한 대상 release로 다시 upgrade한다. 영향 세션 목록이 바뀌면 예전 승인 파일을 재사용하지 않는다. start_fresh는 이전 context를 버린다.

## 되돌리기

이전 release를 적용하는 일도 upgrade 검사와 [실행 전 게이트](#실행-전-게이트)의 rollback 하한을 따른다. 새 schema·checkpoint를 모르는 빌드로 단순히 이미지 태그만 되돌리지 않는다. 아직 새 release가 뜨지 않은 pending 실패에서는 이전 release 적용이 거부되므로 같은 대상으로 복구한다.

## 실행 전 게이트

올리기 전에 지금 배포한 버전과 대상 버전 사이의 [변경 기록](https://github.com/JeongJaeSoon/werft/blob/main/CHANGELOG.md)을 모두 읽는다. 그 사이에 든 릴리스의 절차가 아래 [릴리스별 작업](#릴리스별-작업)에 있으면 그 절차도 따른다. 배포할 때는 [release manifest](/run-server/self-hosting/reference/packages#릴리스-manifest-읽기)의 commit과 세 digest를 함께 확인한다.

지금 롤백 하한은 `v0.2.0`이다. 그 릴리스의 migration `0270`이 프로필 데이터를 지우므로 그보다 앞선 이미지로는 돌아가지 않는다([프로필 제거의 롤백 하한](#프로필-제거의-롤백-하한)). 그 뒤에 변경 기록이 되돌릴 수 없다고 적은 릴리스가 있으면 그 릴리스가 하한이다. 하한보다 앞선 버전으로 돌아가야 하면 업그레이드 전 백업으로 DB를 복원한다. rollback을 생각하기 전에 영향 세션을 읽기 SQL로 세고, 데이터 손실 없이 roll-forward할 수 있는지 먼저 판단한다.

GitHub skill 출처에 `access` 열이 생긴 버전부터, `access = 'public'`인 출처(App이 설치되지 않은 공개 저장소에서 읽는 skill)가 있으면 그 버전보다 앞선 이미지로 되돌리기 전에 그 출처를 지운다. 앞선 이미지는 저장소가 아직 공개인지 확인하지 않고 읽는다.

**워크스페이스 설정의 모르는 키.** 이 수정이 든 판보다 앞선 판(`v0.5.0` 포함)은 `workspaces.settings`에 자기가 모르는 키가 하나라도 있으면 그 워크스페이스의 `GET /v1/auth/me`가 실패한다. 이 수정이 든 판부터는 모르는 키를 응답에서 빼고 저장된 값은 그대로 둔다. 출시된 판은 모두 `achievement_judge`와 그 안의 필드를 알고(`v0.4.0`·`v0.5.0`은 `dispatch_model`, `kill_switch`, `daily_cost_limit_usd`, `idle_pause_minutes`, `audit_retention_days`, `slack_guest_enabled`, `achievement_judge`로 지금과 키 목록이 같다), 이 수정 이전에 저장할 수 있던 설정은 어느 출시 판으로 돌아가도 읽힌다. 돌아갈 수 있는 판은 설정 키와 따로 위의 롤백 하한을 따른다. 이 수정 뒤에 설정 키를 더한 판을 쓴 설치가 이 수정이 없는 판으로 돌아갈 때는, 돌아가기 전에 그 키를 지운다.

**에이전트 GitHub 권한 스위치의 모르는 키.** 이 수정이 든 판보다 앞선 판은 에이전트 GitHub 설정(`agent_github_settings.features`), release pin(`policy_pins.github.features`), 세션 시작 snapshot(`sessions.github_policy_start`)의 권한 스위치에 자기가 모르는 키가 하나라도 있으면 그 설정을 읽지 못한다. 그러면 그 에이전트와 세션의 GitHub 작업이 막히고(gate는 `github_settings_unsupported`로 거절한다), 그런 pin을 가진 release는 조회 응답도 실패한다. 이 수정이 든 판부터는 권한을 판정할 때 권한 스위치의 모르는 키를 빼고 읽고, 저장된 값은 그대로 둔다. release는 ID가 저장된 pin 그대로를 해시하므로 release를 읽을 때는 그 키를 남겨 두고, 권한 판정에서만 뺀다. 알려진 스위치의 값이 잘못되었거나 스위치 밖(GitHub 설정의 다른 최상위 키, workflow 허용 목록 항목의 키)에 모르는 키가 있으면 전처럼 읽지 못한다. 스위치 밖의 키는 범위를 좁히는 조건일 수 있어 빼고 읽으면 넓어지기 때문이다. 이 판이 다시 쓰는 값(세션 시작 snapshot, 첫 저장으로 만드는 설정, 앞선 release의 pin을 물려받아 만드는 release, 에이전트 GitHub 설정 조회 응답)에는 모르는 키를 넣지 않으므로 앞선 판으로 돌아가도 이 판이 만든 값은 읽힌다. release 조회 응답은 저장된 pin을 그대로 돌려준다. 이 수정 뒤에 권한 스위치를 더한 판을 쓴 설치는 그 판이 쓴 값이 남아 있으므로 이 수정이 든 판보다 앞으로 돌아가지 않는다.

새 control-host와 직전 worker의 조합은 배포 전 시험 설치에서 확인한다. 세션 turn 1 완료 → worker 제거 → checkpoint에서 turn 2 완료를 보고 API의 worker 요청에 400 BAD_REQUEST가 없어야 한다. 빈 설치 ready 200으로 이를 대신하지 않는다. turn 1 완료를 먼저 본다. 직전 worker가 새 control-host의 응답을 읽지 못하면 API는 200을 주고 worker가 시작 직후 끝나므로, 400이 없다는 것만으로는 이 실패를 잡지 못한다. 프로필 제거 릴리스는 이 조합을 지원하지 않는다. 그 릴리스로 올릴 때는 새 control-host와 새 worker로 turn 1 완료를 본다([프로필 제거 릴리스의 업그레이드 순서](#프로필-제거-릴리스의-업그레이드-순서)).

### Compose 전용 checkpoint 검사

단일 서버(compose) 설치의 업그레이드 검사에서 worker 이미지가 바뀌면 새 이미지의 engine·SDK·CLI·profile digest로 각 현재 checkpoint의 restore plan을 계산한다. 네 값이 모두 같아 호환되는 세션은 승인 없이 이어지고, `INCOMPATIBLE_CHECKPOINT`인 세션만 사용자에게 알리고 정확한 목록을 승인받는다. 검사를 끝까지 돌릴 수 없거나 다른 검증 실패가 섞이면 미수거 checkpoint가 있는 세션 전부를 영향 목록으로 삼는 fail-closed 동작을 하고 로그에 남긴다. writer를 멈춘 뒤에도 같은 검사를 다시 한다. 불호환 세션에 `start_fresh`를 선택하면 이전 checkpoint의 context를 버린다. Kubernetes(helm) 설치에서는 pre-upgrade hook이 같은 판정을 이미지를 실행하지 않고 포인터의 조합으로 한다([Kubernetes 업그레이드 § 3. 검사 결과와 예외 — 업그레이드 전 검사](/run-server/self-hosting/upgrade-kubernetes#3-검사-결과와-예외)).

worker 이미지가 바뀌면 upgrade는 바뀌기 전 이미지를 직전 이미지로 남긴다(upgrade 스크립트의 상태 디렉터리에 `previous-worker` 파일로 둔다). scheduler는 세션마다 checkpoint 포인터의 조합(engine·SDK·CLI·profile digest scheme)과 같은 이미지를 현재·직전 중에서 고르고, 둘 다 맞으면 현재 이미지를 쓴다([설정 레퍼런스 § scheduler·worker 컨테이너·egress 설정](/run-server/self-hosting/reference/configuration)). 그래서 게이트는 새 이미지로 복원할 수 없는 세션 가운데 직전 이미지로도 복원할 수 없는 세션만 영향 목록에 올린다. 새 이미지와 직전 이미지 가운데 어느 한쪽의 검사라도 fail-closed로 끝나면 새 이미지 기준 목록을 그대로 쓴다. 같은 조합으로 다시 빌드한 이미지라면 scheduler는 새 이미지로 띄우므로, 새 이미지로 복원된다고 확인하지 못한 세션은 직전 이미지가 복원하더라도 목록에서 빼지 않는다. 어느 한쪽이 자기 조합을 출력하지 못하는 옛 이미지면(조합 출력 기능이 없는 빌드) 직전 이미지를 쓰지 않고, 게이트도 새 이미지 기준 목록을 그대로 쓴다. 지원 창은 한 릴리스다. 한 번 더 업그레이드하면 그 전 이미지에 남은 세션이 다시 영향 목록에 오른다. 프로필 제거 릴리스에서는 직전 이미지로 뜨는 세션이 없다([프로필 제거 릴리스의 업그레이드 순서](#프로필-제거-릴리스의-업그레이드-순서)).

### runtime 버전의 공통 준비

SDK를 올리는 릴리스는 이미지가 싣는 런타임 버전을 바꾼다. release는 만들 때 이미지가 싣던 런타임 버전을 고정하고, 세션은 그 release의 버전으로 돈다. 현재·직전 이미지 어느 쪽도 싣지 않는 버전의 release로는 새 세션이 `UNSUPPORTED_CAPABILITY`로 거절되므로, 그 에이전트를 다시 release한다. 체크포인트는 이 판정과 무관하게 만든 빌드와 같은 엔진·SDK·CLI 조합의 이미지에서만 재개된다. Kubernetes(helm) 설치의 되돌리기 절차와 주의사항은 [Kubernetes 업그레이드 § 되돌리기](/run-server/self-hosting/upgrade-kubernetes#되돌리기)에 있다.

## 릴리스별 작업

변경 기록이 가리키는 릴리스별 절차다. 지금 버전과 대상 버전 사이에 든 릴리스의 절만 따른다.

### 프로필 제거의 롤백 하한

실행 프로필을 지운 릴리스는 migration `0270_remove_profiles`가 프로필 표와 열을 지우고, 프로필로 만든 release와 그 세션, 세션에 딸린 기록(turn·이벤트·checkpoint 행 등 45개 표)을 지운다. 세션이 없는 `slack_outbox` 행(환영 알림 등)은 남기고, 사용량은 `provider_usage`(세션에 딸림)만 지우며 `agent_usage`는 남는다. 에이전트와 카드 버전, 팀, key, 설치 설정은 남는다. 그 뒤로는 모든 세션이 release가 고정한 spec(연결·모델·런타임·도구)으로 돌고, 에이전트는 연결을 골라 다시 release해야 돈다. 연결에는 에이전트가 고를 모델 목록(`models`)이 있어야 하고, 목록에 없는 모델로는 release를 만들 수 없다. `0270`은 목록이 빈 연결에만 그 연결에 대응하던 프로필의 모델을 채운다. 대응하던 프로필이 없으면 목록은 빈 채로 남고, 목록이 이미 있던 연결에는 아무것도 더하지 않는다. 올린 뒤 연결마다 에이전트가 쓸 모델이 목록에 모두 있는지 확인하고, 빠진 모델을 넣는다. 설정 문서에서는 최상위 `profiles` 키와 저장소 항목의 `profiles`를 지운다. 최상위 키가 있으면 `settings import`(CLI와 API)가 문서를 거절한다. 저장소 항목의 `profiles`는 CLI가 버리지만 API는 거절한다. **이 릴리스보다 이전 빌드로는 롤백할 수 없다.** 되돌리려면 업그레이드 전 백업으로 DB를 복원한다.

### 프로필 제거 릴리스의 업그레이드 순서

프로필 제거 릴리스는 control-host와 worker 이미지를 한 upgrade로 함께 올린다. 이 릴리스의 control-host는 `bootstrap-claim` 응답에서 `runtime.profile_id`와 `profile_fingerprint`를 뺐다. 프로필 제거 전에 빌드한 worker(`v0.1.3` 포함)는 이 두 칸을 필수로 읽는다. 그래서 그 worker는 응답을 받자마자 `POST /bootstrap-claim answered a body this worker cannot read`를 남기고 exit 1로 끝난다. 세션은 세 번 launch한 뒤 `recovery_required`(`STARTUP_FAILED`, `execution_gone`)로 멈춘다. API는 이 요청에 200을 주므로 API 로그에서 worker 요청의 400을 찾는 것으로는 이 실패를 알 수 없다. 세션의 turn 1이 끝나는지로 안다.

- 위 [2. API → proxy → worker 순서](#2-api--proxy--worker-순서)의 중간 release와 [Kubernetes 업그레이드의 1단계](/run-server/self-hosting/upgrade-kubernetes#1-대상-chart와-제어-영역-우선-교체)를 이 릴리스에서는 하지 않는다. 새 control-host와 옛 worker가 함께 도는 동안에는 새 세션이 하나도 뜨지 않기 때문이다. Compose는 최종 release로 바로 `upgrade`하고, Kubernetes는 2단계의 명령으로 바로 올린다.
- 프로필 제거 전에 빌드한 worker 이미지는 이 릴리스의 지원 창에 들지 않는다. 그런 이미지를 `images.workerPrevious`에 따로 넣지 않는다. 다만 Kubernetes의 [업그레이드 전 검사](/run-server/self-hosting/upgrade-kubernetes#3-검사-결과와-예외)는 worker 이미지가 바뀌는 upgrade의 `images.workerPrevious`가 지금 배포된 이미지이기를 요구하고, 이 조건은 승인으로 넘길 수 없다. 그래서 이 upgrade에는 2단계 스크립트가 만든 `worker-previous.json`(지금 배포된 worker 이미지)을 그대로 넘긴다. Compose의 `upgrade`가 남기는 `previous-worker` 파일도 같다. 그 이미지로 뜨는 세션은 없다. `0270`이 세션을 비우고, 새 세션은 언제나 현재 이미지로 뜨며, 그 뒤의 checkpoint는 현재 이미지가 남긴다. 다음 worker 이미지 upgrade에서 직전 이미지는 이 릴리스의 이미지로 바뀐다.
- 올린 뒤에는 새 세션 하나가 turn 1을 끝내는지 본다.

### 지운 Slack 연결 env

이 릴리스부터 API와 slack 역할은 `SLACK_OIDC_REDIRECT_URI`·`SLACK_OIDC_CLIENT_ID`·`SLACK_OIDC_CLIENT_SECRET`을 읽지 않는다. Slack 계정 연결의 redirect는 `CONSOLE_ORIGIN`에 고정 경로 `/settings/linked-accounts/slack`을 붙여 계산한다. client id와 secret은 워크스페이스마다 설정 > 워크스페이스 > 연동 > Slack에서 만든 link 앱의 것만 쓴다.

- 올리기 전에 API와 slack 역할에 `CONSOLE_ORIGIN`이 있는지 본다. 앞선 릴리스는 `CONSOLE_ORIGIN`이 없으면 `SLACK_OIDC_REDIRECT_URI`의 origin을 대신 썼다. 이 릴리스에서는 그때 Slack 계정 연결이 `503`이 되고, Slack 앱을 만들 수 없고, 저장한 이벤트 입구 주소(아래)도 없으면 이벤트 구독이 등록되지 않는다(`events_url_unset`).
- 세 값을 지운다. Compose는 `infra/compose.core.yml`이 더는 넘기지 않으므로 설치의 env 파일에서 줄만 지운다. Kubernetes는 `api.extraEnv`와 `slack.extraEnv`에서 지운다. 값이 남아 있으면 API가 시작할 때 `Ignored removed settings: <이름>` 경고를 한 번 남긴다. 값은 출력하지 않고 동작에도 쓰지 않는다.
- 이 릴리스는 앞선 빌드로 되돌릴 수 없으므로([프로필 제거의 롤백 하한](#프로필-제거의-롤백-하한)), 되돌릴 때를 위해 남겨 둘 줄은 없다.

### 웹으로 옮긴 Slack 이벤트 입구 주소

이 릴리스부터 API는 `SLACK_EVENTS_PUBLIC_URL`을 읽지 않는다. 이벤트 입구를 콘솔과 따로 둘 때는 owner가 **설정 > 연동 > Slack**의 "이벤트 입구 주소"에 query·fragment·계정 정보 없는 https 주소를 저장한다(`PUT /v1/slack-settings`, 감사 기록 `update_slack_settings`). 비워 두면 `CONSOLE_ORIGIN`에서 계산한 주소를 쓴다. 저장 전에 화면이 계산한 주소와 Slack에 보낼 URL을 보여 준다. 이 값은 설치 전체에 하나다.

- migration `0278_slack_settings`가 `slack_settings` 표를 더한다. 새 API가 처음 뜰 때 이 표가 비어 있고 API 컨테이너에 `SLACK_EVENTS_PUBLIC_URL`이 실제로 들어와 있으면 그 값을 한 번 옮겨 담고, 값 없이 경고를 남긴다. 옮긴 기록은 작성자 없는 감사 기록(`by: "env_import"`)으로 남는다. Compose의 `infra/compose.core.yml`은 이 값을 API에 넘기지 않으므로, 설치 쪽 overlay나 `api.extraEnv`(Kubernetes)로 직접 넘긴 경우에만 옮겨진다. 그 밖에는 올린 뒤 화면에서 저장한다.
- 옮긴 뒤 env의 줄을 지운다. 남아 있으면 시작할 때마다 `Ignored removed settings: SLACK_EVENTS_PUBLIC_URL` 경고가 남는다. 값이 https가 아니거나 query가 있으면 옮기지 않고 그렇다고 경고한다. 앞선 릴리스와 달리 시작은 멈추지 않는다.
- 저장한 주소를 바꿔도 이미 만든 앱에는 바로 보내지 않는다. 에이전트의 Slack 탭에서 "다시 확인"을 누르거나 `slack-app finalize`를 실행한다.
- `slack_settings` 표는 되돌릴 때 지우지 않는다. 앞선 빌드는 이 표를 읽지 않는다.

### 웹으로 옮긴 GitHub webhook 입구 주소

이 릴리스부터 API는 `GITHUB_WEBHOOK_BASE_URL`을 읽지 않는다. GitHub가 인터넷에서 닿는 이 API의 https 주소는 owner가 **설정 > 연동 > GitHub**의 "웹훅 입구 주소"에 저장한다(`PUT /v1/github-webhook-settings`, 감사 기록 `update_github_webhook_settings`). 주소를 바꿔 저장하면 webhook secret이 저장된 GitHub App의 webhook URL도 GitHub에서 함께 바뀐다([Git 스킬 webhook](/integrations/github#git-스킬-webhook)). 이 값은 설치 전체에 하나다.

- migration `0360_github_webhook_settings`가 `github_webhook_settings` 표를 더한다. 새 API가 처음 뜰 때 이 표가 비어 있고 API 컨테이너에 `GITHUB_WEBHOOK_BASE_URL`이 들어와 있으면 그 값을 한 번 옮겨 담고, 값 없이 경고를 남긴다. 옮긴 기록은 작성자 없는 감사 기록(`by: "env_import"`)으로 남는다. 옮길 때는 GitHub App을 바꾸지 않는다. App은 이미 그 주소로 만들어졌다.
- 옮긴 뒤 env의 줄을 지운다. 남아 있으면 시작할 때마다 `Ignored removed settings: GITHUB_WEBHOOK_BASE_URL` 경고가 남는다. 값이 https가 아니거나 query가 있으면 옮기지 않고 그렇다고 경고한다. 앞선 릴리스와 달리 시작은 멈추지 않는다.
- `github_webhook_settings` 표는 되돌릴 때 지우지 않는다. 앞선 빌드는 이 표를 읽지 않고 env를 읽는다. 화면에서 바꾼 주소를 되돌린 빌드에서도 쓰려면 그 값을 env에 다시 넣는다. GitHub App의 webhook URL은 화면에서 마지막으로 저장한 주소로 남아 있다.

### Slack 채널 이벤트와 manifest 다시 보내기

업그레이드한 API가 처음 뜰 때, 이미 만든 에이전트 앱의 manifest를 Slack에서 읽어 새 이미지의 것과 견준다. bot 이벤트만 다르면 manifest를 저절로 다시 보낸다. 이벤트만 더하는 데는 재설치가 필요 없다. 그래서 이미 만든 앱이 채널 삭제·보관·이름 변경 이벤트를 사람 손 없이 받는다. App Configuration Token이 활성 상태가 아니거나 Slack이 갱신을 거절하면 그 앱의 Slack 탭 앱 칸에 "갱신 필요"와 이유가 나온다. 그때는 콘솔 Slack 탭의 "다시 확인"을 누르거나 API 컨테이너에서 `bun run apps/control-host/src/api/slack-app.ts finalize --agent <agent_id>`를 실행한다. 누르지 않아도 다음 업그레이드나 API 재시작 때 다시 시도한다. 갱신되기 전에는 삭제된 채널의 처리가 게시나 채널 조회가 `channel_not_found`를 받을 때만 동작한다. bot scope가 다른 manifest는 저절로 보내지 않는다. 손으로 다시 보낸 manifest가 설치에 없는 scope를 요청하면 "다시 확인"의 안내와 명령의 `warnings`(`reinstall_required`)가 앱을 다시 설치하라고 알린다.

### 웹으로 옮긴 실행 한도

설치 전체에 걸린 실행 한도, 세션 기록 보관, 작업 공간 보존 설정 열두 개를 env 대신 owner가 **설정 > 워크스페이스 > 실행 한도**에서 저장한다(`GET`·`PATCH /v1/installation-config`, 감사 기록 `update_installation_config`). 어느 role도 아래 env를 읽지 않는다. 저장하면 그 API는 바로, 다른 replica와 scheduler·slack·metrics role은 10초 안에 따른다. 이미 기다리는 요청은 처음 받은 시간을 그대로 쓴다. 턴 시간·모델 요청 재시도는 그 뒤에 예약되는 launch부터 받고, 다른 값으로 뜬 worker는 지금 turn을 마친 뒤 내려간다([turn 시간과 재시도를 바꿀 때](/run-server/self-hosting/explanation/isolation#turn-시간과-재시도를-바꿀-때)). 세션 기록 보관 두 값은 보관 job이 돌 때마다, 작업 공간 보존 두 값은 scheduler가 workspace를 회수할 때마다 읽는다. 범위와 기본값은 [웹에서 정하는 실행 한도](/run-server/self-hosting/reference/configuration#웹에서-정하는-실행-한도)에 있다.

| 화면의 항목 | 옮겨 오는 env |
|---|---|
| 사람 응답 | `PENDING_REQUEST_TTL_SEC` |
| 세션 비용 | `SESSION_COST_LIMIT_USD` |
| 세션 토큰 | `SESSION_TOKEN_LIMIT` |
| 대기 메시지 | `QUEUED_INPUT_LIMIT_PER_SESSION` |
| 입력 보관 | `STORAGE_LIMIT_BYTES` |
| 작업 공간 용량 | `WORKSPACE_ENFORCE` |
| 턴 시간 | `MAX_TURN_SECONDS` |
| 모델 요청 재시도 | `PROVIDER_MAX_RETRIES` |
| 세션 기록 보관: 보관까지 쉰 기간 | `SESSION_ARCHIVE_AFTER_DAYS` |
| 세션 기록 보관: 보관 작업이 할 일 | `SESSION_ARCHIVE_DRY_RUN` |
| 멈춘 세션의 작업 공간 | `EXECUTION_WORKSPACE_STOPPED_TTL_SEC` |
| 일시 정지한 세션의 작업 공간 | `EXECUTION_WORKSPACE_PAUSED_TTL_SEC` |

- migration `0281_installation_config`가 키마다 한 행인 `installation_config` 표를 더한다. 이어서 migrate가 어느 role보다 먼저 값을 옮긴다. 저장한 값이 없는 키에 env 값이 들어와 있으면 한 번 옮겨 담고, 값 없이 `note: <env> was carried into Settings > Workspace > Execution limits and is no longer read; remove it`을 남긴다. 워크스페이스가 있으면 작성자 없는 감사 기록(`by: "env_import"`)을 남긴다. 빈 값은 넣지 않은 것으로 본다.
- `infra/compose.core.yml`은 위 열두 env를 호스트 env나 `.env`에서 받아 migrate에만 넘긴다. 앞선 릴리스처럼 `.env`에 적어 둔 값은 그대로 옮겨진다. api·scheduler·maintenance에 overlay로 넘기던 값은 옮겨지지 않으니, 올리기 전에 `.env`로 옮기거나 올린 뒤 화면에서 저장한다. 아무것도 넣지 않았으면 기본값을 쓴다. 기본값은 앞선 compose의 기본값과 같다(턴 시간 3600초, 재시도 2회, 보관 180일, 세기만 함, 작업 공간 보존 각 86400초). 작업 공간 보존 시간을 읽지 못하는 동안(막힌 키, DB 장애) scheduler는 멈추지 않고 `stopped`·`paused` 세션의 workspace만 새로 회수하지 않는다. 옮겨 온 턴 시간·재시도가 떠 있는 worker의 값과 같으면 올린 뒤에도 그 worker는 그대로 돈다.
- 옮긴 뒤 env 줄을 지운다. 남아 있으면 migrate가 돌 때마다 `note: Ignored removed settings: <env>`가 나온다. 이미 저장한 값은 env가 바꾸지 않는다.
- 범위를 벗어난 값은 옮기지 않는다(`note: <env> was not carried in`). 앞선 릴리스처럼 시작을 멈추지도, 기본값으로 돌지도 않는다. 그 키는 화면에서 값을 저장할 때까지 막힌다. 저장한 값이 이 버전의 범위를 벗어나도 같다. 막힌 키를 읽는 일만 거절되고, 화면은 그 칸에 안내를 띄운다. 무엇이 거절되는지는 [웹에서 정하는 실행 한도](/run-server/self-hosting/reference/configuration#웹에서-정하는-실행-한도)의 "쓸 수 있는 값이 없을 때"에 있다. 예를 들어 세션 비용이 막히면 새 세션과 메시지가 `503 BACKEND_UNAVAILABLE`로 거절되고 scheduler는 launch를 건너뛴다.
- worker는 `QUESTION_TIMEOUT_SEC`를 읽지 않는다. launcher가 넘긴 적 없는 값이라 동작은 같다(gateway가 등록하기 전까지 30분).
- `installation_config` 표는 되돌릴 때 지우지 않는다. 앞선 빌드는 이 표를 읽지 않고 env를 읽는다(없으면 compose 기본값). 화면에서 바꾼 값을 되돌린 빌드에서도 쓰려면 그 값을 `.env`에 다시 넣는다.

### 설정 문서는 빈 설치에 한 번만 들어간다

이 릴리스부터 migrate는 설정 문서(`SETTINGS_DOCUMENT`, test-ops는 `PLATFORM_SETTINGS_DOCUMENT`)를 빈 설치에만 한 번 넣는다(`settings seed`). 그 뒤 연결·저장소·MCP 서버는 콘솔(설정 > 에이전트 연결)에서 바꾼다. 문서를 고쳐 다시 배포해도 들어가지 않는다.

- migration `0282_settings_seed_decided`가 `settings_generation.seed_decided_at` 열을 더한다. 올린 뒤 설정 문서를 받은 첫 migrate가 이 시각을 적는다. `SETTINGS_DOCUMENT`가 없으면 migrate는 seed를 돌지 않으므로 시각도 로그도 남지 않는다. 연결이나 MCP 서버가 이미 있는 설치(사용 중지한 것 포함)는 아무것도 가져오지 않고 그 시각만 적는다. 저장소 행만 있는 설치는 빈 설치로 보고 한 번 넣는다.
- 가져오지 않을 때 migrate 로그에 값 없이 한 줄이 남는다: `note: the settings document <파일> (SETTINGS_DOCUMENT) not imported: the installation already holds settings. It seeds an empty installation only; change settings in the console`. 시각을 적은 뒤에는 `the automatic seed ran on <시각>`으로 나온다. 이 줄은 실패가 아니다.
- 문서의 내용을 일부러 다시 넣을 때는 owner가 손으로 `settings import`를 돌린다. 이 명령은 바뀌지 않았다.
- test-ops `upgrade`는 바뀐 문서를 넣지도, DB와 비교하지도 않는다. 문서의 digest가 바뀌면 `upgrade: the settings document changed; it is not imported into a deployed installation, so change settings in the console`을 남긴다. `deploy`의 확인은 그대로다.
- 되돌리면 앞선 release의 migrate가 배포마다 문서를 다시 가져온다. 콘솔에서 바꾼 항목이 문서의 같은 id와 다르면 그 가져오기가 거절되고 migrate가 실패해 API가 뜨지 않는다. 되돌리기 전에 그런 항목을 문서에서 빼거나 콘솔의 값에 맞춘다. `seed_decided_at` 열은 지우지 않는다. 앞선 빌드는 이 열을 읽지 않는다.

### env로 가리키던 자격 증명은 DB로 한 번 옮긴다

이 릴리스부터 api는 설정의 `value_env`(연결, 자기 GitHub App을 적은 저장소, MCP 서버)를 env에서 읽지 않는다. 설정을 읽을 때 그 값을 DB에 봉인해 그 행의 저장값으로 한 번 옮긴다. `secret_id`는 그대로다.

- migration `0285_credential_carried_auth`가 `provider_connections`·`catalog_repositories`·`mcp_servers`에 `carried_auth` 열을, `catalog_repositories`에 `carried_binding` 열을 더하고, 명시적 App 저장소도 저장값을 갖도록 `catalog_repositories_credential_check`를 바꾼다. `push_requests`·`worker_credentials`에는 INSERT trigger(`…_carried_binding`)를 단다.
- 올린 뒤 api 로그에 옮긴 행마다 `<kind>:<id> took its credential from <이름> into the database and no longer reads it; remove <이름>`이 한 번 나온다. 그 뒤 env에서 그 이름을 빼도 된다. 값은 로그와 receipt에 나오지 않는다. receipt `set_settings_credential`에는 변수 이름과 `by: env_import`만 남는다.
- 첫 워크스페이스가 없으면(bootstrap 전) 그때까지는 env에서 읽고, 워크스페이스가 생긴 뒤 첫 설정 읽기(10초 안)에 옮긴다.
- env에 값이 없는 행은 빠지고 경고가 한 번 남는다: `<kind>:<id> names <이름>, which the API does not have, so it is left out. …`. 변수를 넣고 api를 다시 띄운다. 연결이면 콘솔의 "화면에서 키 넣기"로도 된다.
- 실행 경로가 거절할 값(8바이트보다 짧거나 앞뒤 공백·제어 문자가 있는 키, RSA 개인 키 PEM이 아닌 App 키)과 8자보다 짧은 키(저장값은 끝 네 글자를 보여 준다)는 옮기지 않는다. 그 행은 빠지고 `<kind>:<id> is left out and not carried into the database: <이유>. Correct <이름> and restart the API`가 한 번 남는다. 이유에는 변수 이름만 나온다.
- 명시적 App 저장소를 옮기면 자격 참조가 바뀌어 저장소 binding도 바뀐다. 같은 트랜잭션에서 그 저장소의 옛 binding을 그대로 가진 push 요청과 실행 중 세션의 저장소 토큰을 새 binding으로 옮긴다. 그래서 옮기기 전에 만든 push로 PR을 열고 병합할 수 있고, 실행 중 세션도 토큰을 다시 받는다. 옮긴 행 수는 로그(`… (N push requests and M worker credentials moved to its new binding)`)와 receipt의 `rebound`에 남는다. 아직 옮김을 읽지 않은 replica(10초마다 다시 읽는다)나 앞선 빌드가 그 뒤 옛 binding으로 쓰는 행은 DB가 쓰는 순간 새 binding으로 적는다(위 trigger). 되돌리기 SQL이 `carried_binding`을 비우면 trigger는 아무것도 바꾸지 않는다. 옮기는 트랜잭션은 두 표를 잠가 그동안 push 요청과 worker 토큰을 쓰는 요청이 기다린다. 5초 안에 잠그지 못하면 옮기지 않고 다음 읽기에서 다시 한다. 옮긴 뒤 그 App 키는 `POST /v1/installation/settings/repositories/{id}/credential`(owner·admin, RSA 개인 키 PEM)로 바꾼다. env를 바꿔도 읽지 않는다.
- **이 릴리스로 올릴 때는 api를 하나로 줄이거나 옛 replica를 모두 내린 뒤 새 빌드를 띄운다.** replica는 저마다 10초마다 설정을 다시 읽으므로, 아직 옮김을 읽지 않은 replica가 그 사이 옮겨진 push 요청을 `catalog_changed`로 실패시키거나 실행 중 세션의 토큰 재발급을 거절할 수 있다. Compose의 api는 하나라 그대로 올리면 된다. Helm은 [Kubernetes 업그레이드](/run-server/self-hosting/upgrade-kubernetes)의 1단계를 따른다. 그렇게 실패한 push는 다시 요청하면 새 binding으로 push된다.
- 옮긴 뒤 옛 문서를 손으로 `settings import`하면 옮긴 항목은 같은 id에 다른 내용이라 `conflicts`로 멈춘다. 그 항목을 문서에서 빼거나 `settings export`로 받은 문서를 쓴다.
- URL 저장소(`auth`가 `basic`·`bearer`)는 실행에 쓰이지 않으므로 옮기지 않는다.
- 되돌리기: 앞선 빌드는 연결·MCP 서버의 저장값은 읽지만 명시적 App 저장소의 저장값은 거절해 그 저장소가 `invalid`로 빠진다. 되돌릴 때는 이 순서를 지킨다.
  1. 이 릴리스의 api replica를 모두 내린다. 하나라도 살아 있으면 다음 설정 읽기(10초 안)에 되돌린 행을 다시 옮긴다.
  2. 아래 SQL을 한 트랜잭션으로 실행한다. 행의 env 참조를 되돌리고, 옮길 때 바꾼 push 요청과 worker 토큰의 binding도 옛 값으로 되돌린다.
  3. 그 변수들을 api env에 다시 넣고 앞선 빌드를 띄운다. 옮긴 뒤 콘솔에서 키를 바꿨다면 env의 값으로 돌아가므로 env에 새 값을 넣는다.

  `carried_auth`·`carried_binding` 열과 봉인한 값은 남겨 둔다.

```sql
BEGIN;
UPDATE push_requests p SET repository_binding = r.carried_binding->>'from' FROM catalog_repositories r WHERE r.carried_binding IS NOT NULL AND p.repository_binding = r.carried_binding->>'to';
UPDATE worker_credentials w SET binding = r.carried_binding->>'from' FROM catalog_repositories r WHERE r.carried_binding IS NOT NULL AND w.purpose = 'repository' AND w.binding = r.carried_binding->>'to';
UPDATE provider_connections SET definition = jsonb_set(definition, '{auth}', carried_auth), credential_source = 'external', carried_auth = NULL WHERE carried_auth IS NOT NULL;
UPDATE catalog_repositories SET auth = carried_auth, credential_source = 'external', carried_auth = NULL, carried_binding = NULL, version = version + 1 WHERE carried_auth IS NOT NULL;
UPDATE mcp_servers SET auth = carried_auth, credential_source = 'external', carried_auth = NULL WHERE carried_auth IS NOT NULL;
COMMIT;
```

### 외부 자격 증명 출처를 없앤 릴리스

이 릴리스부터 모델 연결과 저장소의 GitHub App key는 DB에 저장된 값만 쓴다. 설정의 `value_env`(api의 env)와 `secret_id`(AWS Secrets Manager)는 없어졌고, api는 Secrets Manager를 어디서도 쓰지 않는다. 값은 콘솔(설정 > 모델 연결)이나 owner 세션의 `POST /v1/installation/settings/{connections|repositories}/{id}/credential`로 넣고, `PLATFORM_SECRET_KEY`로 암호화돼 DB에 저장된다. 저장소 App key는 웹 화면이 없어 이 API로만 넣는다(GitHub App RSA 개인 키 PEM). `PLATFORM_SECRET_KEY`, `DATABASE_URL`, `EGRESS_AUTHORIZER_TOKEN`, object store key, 이미 DB에 저장되는 Slack·IdP 비밀, 저장소 `auth` `none`은 그대로다. 설치 카탈로그 MCP 서버는 같은 릴리스의 migration `0304_retire_catalog_mcp`가 저장값과 함께 지우므로 넣을 key가 없다. 계속 쓸 서버는 올린 뒤 워크스페이스 MCP 서버로 등록한다.

- 올리기 전에 env나 Secrets Manager를 가리키는 모델 연결마다 지금 릴리스 콘솔의 **화면에서 키 넣기**로 key를 넣어 둔다. 그러면 올린 뒤에도 그 연결의 세션이 멈추지 않는다. 올린 뒤에 넣어도 된다. 저장소 App key는 지금 릴리스에서 옮길 길이 없으니 올린 뒤 바로 넣는다(아래).
- 사용 중지한 연결이 env나 Secrets Manager를 가리키면 올린 뒤에는 다시 켤 수 없다. 콘솔은 사용 중지한 행에 key를 받지 않고, key가 없는 행을 켜지 않는다. 그 연결을 계속 쓰려면 올리기 전에 켜고 **화면에서 키 넣기**로 key를 넣는다. 그러지 않았다면 올린 뒤 새 id로 연결을 만든다. id는 다시 쓰지 않는다.
- migration `0288_remove_external_credentials`는 env나 Secrets Manager를 가리키던 행을 값 없는 저장형 행으로 바꾼다. 그 행은 key가 들어갈 때까지 `needs_value`(화면에서 **값 필요**)이고, 그 행을 쓰는 세션은 돌지 않는다. 연결은 **API 키 설정**, 저장소 App key는 위 API로 넣는다. 옛 `auth`는 `carried_auth`에 기록으로만 남고 읽지 않는다. 명시적 App 저장소의 binding이 바뀌므로, 같은 migration이 그 저장소의 worker 자격 증명 binding을 새 값으로 옮긴다. push 요청의 binding은 그 저장소의 App key를 넣을 때 옮기므로, key를 넣기 전에는 올리기 전에 만든 push에서 PR을 열 수 없다. 앞선 api replica가 받은 key는 push를 옮기지 않으므로, 저장소 App key는 모든 api가 새 빌드로 바뀐 뒤 넣는다(먼저 넣었다면 한 번 더 넣는다).
- 설정 문서의 `value_env`·`secret_id` 항목은 `"stored": true`로 바꾼 뒤 가져온다. 남아 있으면 `settings import`(API, CLI)가 400 `invalid_document`로 거절하고, CLI는 그 필드 이름을 오류에 적는다.
- 올린 뒤 api의 env에서 연결이 가리키던 key 변수(예: `ANTHROPIC_API_KEY`)와 `AWS_ENDPOINT_URL_SECRETS_MANAGER`를 지운다. api는 이 값을 읽지 않는다. Helm은 [Kubernetes 업그레이드](/run-server/self-hosting/upgrade-kubernetes)를 따른다.
- 콘솔에서 만드는 연결은 key가 있어야 저장된다. 웹은 8자 이상을 넣기 전에 저장 버튼을 끄고, API는 key가 없거나 8바이트보다 짧거나 제어 문자·앞뒤 공백이 있으면 400으로 거절하며, DB는 값 없이 콘솔에서 만든 행을 같은 트랜잭션에서 거절한다. 외부 출처 연결을 저장형으로 바꾸던 콘솔의 "화면에서 키 넣기" 버튼과 `POST …/connections/{id}/convert` 경로는 없어졌다.
- 위 0285 되돌리기 SQL은 이 릴리스 뒤에는 쓸 수 없다. `credential_source`는 `stored`만 허용된다.

### 대화 기록의 관리자 삭제를 더하는 릴리스

migration `0337_conversation_records_deleted`가 `conversations`에 `records_deleted_at`·`records_deleted_by_user_id`(nullable)를, `deleted_sources`에 `reason`(기본값 `slack_deleted`)을 더한다. 올릴 때 할 일은 없고, Slack과 세션의 동작은 그대로다.

- 운영자 명령 `conversation-records.ts delete`가 들어온다([대화 기록의 관리자 삭제](/run-server/self-hosting/reference/storage#대화-기록의-관리자-삭제)). 부르지 않으면 아무것도 바뀌지 않는다.
- 있던 삭제 표식은 모두 `slack_deleted`가 된다. 관리자 삭제가 다는 표식은 `admin_deleted`이고, 그 글이 나중에 Slack에서 지워지면 `slack_deleted`로 바뀐다. 검사는 둘을 똑같이 본다.
- 칸은 nullable이거나 상수 기본값이라 표를 다시 쓰지 않는다. `conversations`의 CHECK·외래 키와 `deleted_sources`의 CHECK는 `NOT VALID`로 더한 뒤 따로 검증하므로 쓰기를 오래 막지 않는다.
- 지원 창 안의 이미지로 되돌려도 된다. 옛 이미지는 새 칸을 읽지 않고, 관리자 삭제가 단 표식도 Slack의 삭제 표식처럼 본다.

### 비공개 채널의 옛 세션을 옮기는 릴리스

migration은 없다. 비공개 Slack 채널에서 이 릴리스 전에 만든 세션은 공유 범위 줄이 없어 범위 값이 `workspace`로 남는다. 운영자 명령 `private-channel-sessions.ts`가 그 범위를 `private_channel`로 옮긴다. 비공개 채널의 세션에 채널 확인을 먼저 거는 릴리스부터는 명령을 돌리기 전에도 그런 세션이 그 에이전트를 쓸 수 있는 지금 채널 멤버에게만 보이고, 명령은 남은 범위 값을 바로잡는다.

- 돌리는 때: 비공개 채널에서 만든 사람이 범위를 `private`로 좁혀 둔 세션에도 채널 확인을 먼저 거는 릴리스에 올린 뒤에 돌린다. 그 전에 돌리면 그런 세션은 채널을 나간 만든 사람과 그 사람의 key에 계속 닿는다.
- 먼저 `plan`으로 본다. 아무것도 바꾸지 않는다.

```sh
docker compose --profile apps exec -T api bun run apps/control-host/src/api/private-channel-sessions.ts plan
```

세션마다 `from`·`to`, 못 보게 될 사람 수 `people_losing`, API key로 만든 턴 수 `key_turns`가 나온다. 못 보게 되는 사람은 채널 멤버가 아닌 사람(owner·admin·에이전트 관리자 포함), Slack을 연결하지 않은 멤버, 채널을 나간 만든 사람, 이름으로 공유받은 사람이다. `key_turns`가 0이 아닌 세션을 key로 폴링하던 연동은 옮긴 뒤 `404`를 받는다.
- 그다음 `apply`로 옮긴다. 다시 돌려도 더 옮기는 것이 없다(`outcome: unchanged`). `--workspace <id>`나 `--agent <id>`로 하나만 고를 수 있다.

```sh
docker compose --profile apps exec -T api bun run apps/control-host/src/api/private-channel-sessions.ts apply --agent <agent_id>
```

- 결과는 한 줄 JSON이다. `outcome`은 세션이나 binding을 하나라도 바꿨으면 `moved`, 바꾼 것이 없으면 `unchanged`이고 둘 다 종료 코드 `0`이다. 아래의 `unconfirmed_channels`나 `skipped`가 있으면 `incomplete`, 종료 코드 `3`이다. `run_id`는 이 실행의 id이고, 옮긴 세션 수 `sessions_moved`와 바뀐 binding 수 `bindings_changed`가 따로 나와 binding만 바뀐 실행도 읽힌다. 만든 사람이 `private`로 좁혀 둔 세션은 넓히지 않고 `kept_private`로 센다. 공개 채널 세션은 그대로다(`unchanged`).
- 옮긴 세션마다 그 세션의 receipt 목록에 `share_session` receipt가 하나 남는다. `result`에는 이전 범위 `previous_scope`, 새 범위 `scope`, 사유 `reason: "operator_private_channel_migration"`, Slack 설치가 없어 binding의 종류로 정했는지 `no_install`, 그 세션을 더 못 보게 된 사람 수 `people_losing`(명단은 없다. `no_install`이면 `null`), 출력의 `run_id`, `by: "operator_cli"`가 들고, 세션 본문은 들지 않는다. 같은 실행에서 바뀐 binding의 receipt도 같은 `run_id`를 단다. receipt를 쓰지 못하면 그 채널의 세션과 binding도 옮기지 않고 종료 코드 `1`로 멈춘다. 앞 채널에서 옮긴 것은 남으니 고친 뒤 다시 돌린다. 이 릴리스 전 명령으로 옮긴 세션에는 이 receipt가 없다.
- 명령은 채널마다 에이전트의 bot token으로 Slack에 채널 종류를 묻는다. 종류를 확인하지 못한 채널은 `unconfirmed_channels`, 옮기지 못한 세션은 `skipped`(`no_channel_conversation`·`no_workspace`, 옮기는 사이 범위가 바뀌면 `share_changed`)에 남고 그대로 둔다. 하나라도 있으면 종료 코드 `3`이다. 고친 뒤 다시 돌린다. 공개로 묶였지만 지금 비공개인 채널의 binding은 `private_channel`이 되고 다시 승인을 기다린다(`bindings`에 `now_private`).
- `unconfirmed_channels`의 `reason`이 `master_key_mismatch`면 명령이 받은 master key로 저장된 bot token이 열리지 않은 것이고, stderr에 `master_key_mismatch` 한 줄이 함께 나온다. 명령은 API가 쓰는 키를 받아야 한다. `docker compose exec`로 띄운 명령은 컨테이너에 설정된 env만 받는다. 그래서 entrypoint가 서버 프로세스에만 키를 넘기는 구성에서는 서비스 env에 `PLATFORM_SECRET_KEY_FILE`을 두거나([설정](/run-server/self-hosting/reference/configuration)의 "Secret과 AWS values"), 그 실행에만 `-e PLATFORM_SECRET_KEY= -e PLATFORM_SECRET_KEY_FILE=<컨테이너 안의 키 파일 경로>`를 넘긴다. 앞의 것은 컨테이너 env에 남은 다른 키를 비운다.
- Slack 앱 설치가 없는 에이전트(`SLACK_NOT_INSTALLED`)의 채널은 `unconfirmed_channels`가 아니라 `no_install`에 따로 센다(`channel_count`·`session_count`). 종료 코드 `3`의 이유가 아니다. Slack에 물을 수 없으므로 binding에 적힌 종류를 쓴다. 비공개 binding이거나 종류를 아는 binding이 없는 채널(`kind_unknown_as_private`)의 세션은 `private_channel`로 옮기고, 공개 binding이면 그대로 둔다. 멤버를 읽을 수 없어 못 보게 될 사람 수는 확인할 수 없다(`people_losing: "unconfirmed_no_install"`). 옮긴 세션은 재설치 전까지 에이전트 말고는 아무도 보지 못한다. 앱을 다시 설치하면 지금 채널 멤버에게 다시 보이고, 그 뒤 `plan`과 `apply`를 다시 돌리면 Slack이 답한 종류로 바로잡힌다.
- 봇이 빠진 채널은 멤버 목록을 읽지 못해 `members_unconfirmed: true`다. 옮기면 그 채널의 세션은 모두에게 숨는다. 남길 채널이면 명령 전에 봇을 다시 초대한다.
- `members_unconfirmed: true`인 세션에는 이유 칸 `members_unconfirmed_reason`이 붙는다. `slack_error:<Slack 오류 코드>`(예: `slack_error:missing_scope`, `slack_error:ratelimited`), `http_<상태>`·`unreachable`·`timeout`·`unexpected_answer`(Slack이 오류 코드를 주지 못한 호출), `too_many_members`(멤버가 10,000명을 넘음), `no_bot_token`, `master_key_mismatch`, `exception:<오류 이름>` 중 하나다. 코드와 분류만 적고 token·헤더·응답 원문은 없다. 같은 이유가 stderr에 구조화 로그 한 줄(`private_channel_sessions.member_check.unconfirmed`)로 남는다. 판정과 종료 코드는 그대로다.
- 올린 뒤 채널을 공개↔비공개로 바꾸면 binding과 그 채널의 세션이 같이 옮겨진다. 옮긴 세션마다 같은 `share_session` receipt가 남되 `reason: "slack_channel_converted"`, `by: "slack_event"`이고, `run_id` 대신 Slack 이벤트 id `event_id`를 단다. 이때는 멤버를 읽지 않아 `people_losing`이 `null`이다. 비공개 채널을 공개로 바꾸면 그 채널의 `private_channel` 세션은 워크스페이스에 보인다.
- 지원 창 안의 이미지로 되돌려도 된다. 옛 이미지는 `private_channel` 세션을 만든 사람에게만 보인다.

### 처리를 마친 Slack 이벤트의 옛 원문을 지우는 릴리스

migration은 없다. migration 0308 전의 slack 역할은 이벤트 처리를 마쳐도 inbox 행에 원문(`payload`)을 남겼다. 운영자 명령 `slack-inbound-payloads.ts`가 그 원문을 지운다. 돌리기 전에는 그 원문이 남아 있을 뿐이고 동작은 같다.

- 돌리는 때: 모든 slack 역할이 처리 뒤 원문을 지우는 이미지(0308 이후)로 돈 뒤에 한 번 돌린다. 앞선 이미지의 slack 역할이 남아 있으면 처리한 행에 원문을 다시 남긴다.

```sh
docker compose --profile apps exec -T api bun run apps/control-host/src/api/slack-inbound-payloads.ts
```

- 처리를 마친 행(`processed`)의 원문만 지운다. 처리 중인 행(`received`)과 실패한 행(`failed`, 받은 지 7일이 지나면 reconciler가 지운다)은 그대로다. 행 자체(이벤트 종류·상태·시도 횟수)는 남는다.
- 기본키 순서로 1000행씩 한 문장으로 지우고, 문장마다 따로 커밋한다. 행 잠금은 그 묶음의 처리된 행에만 잡히고, 표에는 보통의 쓰기와 같은 `ROW EXCLUSIVE` 잠금만 잡혀 읽기·쓰기를 막지 않는다. `--batch-size <n>`(1~10000)으로 묶음 크기를 바꾼다.
- 결과는 한 줄 JSON이다. 상태별로 원문이 있는 행 수(`before`·`after`), 지운 행 수 `cleared`, 묶음 수 `batches`, `batch_size`, 걸린 시간 `duration_ms`가 나온다. 다시 돌려도 더 지우는 것이 없다(`cleared: 0`).
- 끝난 뒤에도 원문이 남은 처리된 행이 있으면 `outcome: incomplete`, 종료 코드 `3`이다. 앞선 이미지의 slack 역할이 아직 돈다는 뜻이다. 그 컨테이너를 내린 뒤 다시 돌린다. 수는 묶음마다 따로 읽은 값이라 종료 코드 `0`이 앞선 이미지가 없다는 증거는 아니다. 돌리기 전에 모든 컨테이너의 이미지를 확인한다.
- 지운 원문은 돌아오지 않는다. 비운 자리는 autovacuum 뒤 새 행이 다시 쓰고, 파일 크기는 줄지 않는다. 되돌리기 하한은 0308 그대로다.

### 지운 Slack 글이 든 세션을 멈추는 릴리스

migration `0333_source_deleted`가 `sessions`에 `source_deleted_at`(timestamptz, nullable)을 더한다. 올릴 때 할 일은 없다. 지운 글이 없는 세션의 동작은 그대로다.

- Slack에서 글이 삭제되면(답이 달린 부모 글의 묘비 포함), 그 글을 출처로 가진 턴이 하나라도 있는 열린 세션을 멈춘다. 그 턴의 직접 출처든 앞 턴에서 물려받은 출처든 같다. 글의 수정으로는 멈추지 않는다.
- 실행 중인 턴은 끊지 않는다. worker가 그 턴을 끝내고 pause처럼 checkpoint를 남긴 뒤 내려가며, 세션은 `paused`가 된다. 대기 중인 입력은 내보내지 않는다. 이 pause의 receipt는 요청한 사람이 없어 `actor`가 비어 있다.
- 멈춘 세션은 `GET /v1/sessions/{id}`의 `attention.code`가 `SOURCE_DELETED`다. 메시지 보내기와 재개, 복구 결정의 `start_fresh`·`retry_restore`는 `409 SOURCE_DELETED`로 거절된다. 닫기만 된다.
- 멈춘 이유는 세션 이벤트 stream의 `system` 이벤트 `source_deleted`(지운 글의 자리와 바뀐 admission)로 남는다. 닫힌 세션은 건드리지 않는다.
- 칸은 기본값 없이 더하므로 표를 다시 쓰지 않는다. 지원 창 안의 이미지로 되돌려도 된다. 옛 이미지는 칸을 읽지 않으므로 멈춘 세션을 재개할 수 있게 된다.

### 쓰지 않는 표 셋을 지운 릴리스

migration `0305_drop_unused_tables`가 `catalog_authority`·`owner_workspace_map`·`push_continuations` 표를 행째 지운다. `v0.1.0` 이후 어느 릴리스도 앞의 두 표를 읽거나 쓰지 않았고, `push_continuations`를 쓴 마지막 릴리스는 `v0.1.1`이다. 그래서 지원 창 안의 이미지로 되돌려도 영향이 없다.

- 표에 행이 남아 있을 수 있다. `catalog_authority`에는 설정 파일 카탈로그 시절에 활성화한 revision 한 행, `owner_workspace_map`에는 운영자가 손으로 넣은 owner와 워크스페이스의 매핑, `push_continuations`에는 `v0.1.1` 이하가 만든 이어 턴 기록이 있을 수 있다. 행이 있으면 migrate 로그 `db.migrate.notice`에 표마다 지운 행 수가 남는다(`0305: dropped rows: …`). 행의 값은 로그에 남지 않는다.
- 그 행이 필요하면 올리기 전에 백업한다. 0305 아래로 스키마를 내려도 행은 돌아오지 않는다.

### 엔진 설정 표 둘을 지운 릴리스

migration `0357_drop_engine_settings`가 `agent_engine_settings`·`workspace_engine_settings` 표를 행째 지운다. 두 표에는 워크스페이스·에이전트의 실행 규칙(묻기·패턴 막기·자동 모드 규칙)이 들어 있었다. `v0.4.0`부터 어느 릴리스도 두 표를 읽거나 쓰지 않았고, 마지막으로 읽은 릴리스는 `v0.3.0`이다. 그래서 지원 창 안의 이미지로 되돌려도 영향이 없다.

- 표에 행이 남아 있을 수 있다. `v0.3.0` 이하에서 저장한 실행 규칙이다. 행이 있으면 migrate 로그 `db.migrate.notice`에 표마다 지운 행 수가 남는다(`0357: dropped rows: …`). 행의 값은 로그에 남지 않는다.
- 그 행이 필요하면 올리기 전에 백업한다. 0357 아래로 스키마를 내려도 행은 돌아오지 않는다.

### 대화 턴 기록 표를 더하는 릴리스

migration `0345_conversation_turns`가 대화 턴 기록 표 `conversation_turns`를 더하고, `conversation_engagements`·`conversation_calls`·`conversation_inputs`에 그 표를 가리키는 칸 `conversation_turn_id`를, `conversation_inputs`에 `body_sha256`을 더한다. 외래 키와 검사는 `NOT VALID`로 더한 뒤 따로 검증하고, 인덱스는 `CONCURRENTLY`로 만들므로 표를 오래 잠그지 않는다. 올릴 때 할 일은 없다. 이 릴리스에는 사람의 글로 대화 턴을 돌리는 길이 없어서, Slack 멘션과 답, 웹·API 세션의 동작은 그대로다.

migration `0351_conversation_turn_limits`는 `conversation_turns`에 상한에 닿아 끝난 턴의 상한(`limit_reached`)과 그 상한을 지킨 쪽(`limit_reached_by`) 두 칸을 더한다. 기본값 없는 빈 칸이라 줄을 다시 쓰지 않고, 검사는 `NOT VALID`로 더한 뒤 따로 검증한다. 올릴 때 할 일은 없다.

- 웹 입력의 본문은 이제 그 입력의 대화 턴 줄(종류 `web_input`, 상태 `received`)에서 읽는다. 입력 접수 줄은 그 줄을 가리키고 본문의 SHA-256을 갖는다. 같은 메시지 키의 재전송은 이 해시로 비교한다. 지원 창 안의 이전 이미지가 읽을 수 있도록 입력 접수 줄도 본문을 그대로 갖고, 뒤의 릴리스가 지운다.
- 이전 릴리스(올리는 동안 함께 도는 이전 이미지 포함)가 받은 웹 입력은 api가 기동할 때마다 도는 정리가 하나씩 턴 줄을 만들어 준다. 그 수는 로그 `Web inputs given their turn rows`에 남는다. 만들지 못한 입력은 입력 id와 함께 경고로 남고 다음 기동에서 다시 시도한다. 할 줄이 없으면 아무것도 쓰지 않는다.
- [관리자 삭제](/run-server/self-hosting/reference/storage#대화-기록의-관리자-삭제)는 그 대화의 대화 턴 기록도 지우고, 출력과 receipt에 지운 수 `turns`를 더한다. 웹 입력의 턴 줄은 지우지 않는다.
- 지원 창 안의 이전 이미지로 되돌려도 된다. 이전 이미지는 입력 접수 줄의 본문을 읽고 새 칸과 대화 턴 표를 읽지 않는다. 그동안 받은 웹 입력은 다시 올린 뒤 기동 때 턴 줄을 받는다.

### Slack 글의 관여 기록을 남기는 릴리스

migration `0323_conversation_engagements`가 관여 기록 표 `conversation_engagements`를 더한다. slack 역할은 멘션·DM·묶인 스레드의 글을 지금처럼 세션의 턴으로 넣고, 입력 접수 줄을 적는 같은 transaction에서 "에이전트가 이 글에 관여했다"를 한 줄 적는다. 올릴 때 할 일은 없고, Slack과 세션의 동작은 그대로다.

- 관여 기록에는 에이전트, 글의 자리(team, 채널, ts), 종류, 그 글이 든 세션만 남는다. 본문, 스레드 ts, Slack 링크는 남지 않는다. 스레드는 세션의 link가 갖는다.
- 종류는 세션을 연 글이 `mention`(멘션이나 DM), 멘션 없는 맨 위 글로 연 세션이면 `reply`, 이미 열린 세션에 들어간 글이 `bound`다(멘션이 있어도 `bound`).
- 한 글이 두 이벤트로 와도, 다시 처리돼도 에이전트마다 한 줄이다. 턴이 되지 않은 글(거절, 무시)은 적지 않는다. 있던 세션은 채우지 않는다.
- 관여 기록이 있는 글의 삭제·수정 표식은 70분이 지나도 reconciler가 지우지 않는다.
- 새 표만 만들므로 지원 창 안의 이미지로 되돌려도 된다. 그동안의 글에는 관여 기록이 생기지 않는다.

### 세션에 부모 대화를 채우는 릴리스

migration `0320_session_parent_conversation`이 `sessions.parent_conversation_id`(nullable, `conversations`의 외래 키)를 더한다. 외래 키는 `NOT VALID`로 더한 뒤 따로 검증하므로 표를 오래 잠그지 않는다. 올릴 때 할 일은 없고, Slack·웹·세션 API의 동작은 그대로다.

- 새 Slack 세션은 만들 때 부모 대화를 받는다. 채널 스레드의 세션은 그 채널의 메인 대화, DM 세션은 그 사람의 DM 메인 대화다. link가 없는 세션(웹의 "새 세션", 세션 API)은 비어 있다.
- 있던 세션은 api가 기동할 때마다 도는 정리가 묶음으로 채운다. 닫히거나 폐기된 link의 세션도 채운다. 세션마다 비어 있을 때만 채우므로 여러 번 기동해도, 여러 api가 함께 기동해도 결과가 같고, 중간에 멈추면 다음 기동이 남은 세션부터 잇는다.
- DM 세션의 사람은 그 세션을 연 사람이고, 없거나 워크스페이스 멤버가 아니면 link를 만든 사람이다. 새 세션이 만들 때 고르는 사람과 같다. 둘 다 없으면 부모를 비워 두고, 그 세션은 link가 없는 세션처럼 동작한다. 그 수는 이유별로 로그 `Linked DM sessions left without a parent conversation`(`no_person`·`no_membership`)에 남는다. 그 사람이 다시 멤버가 되면 다음 기동이 채운다.
- 채운 수는 로그 `Parent conversations filled`에 남는다. 채우지 못한 세션은 세션 id와 함께 경고로 남고 다음 기동에서 다시 시도한다.
- 지원 창 안의 이미지로 되돌려도 된다. 그동안 만든 Slack 세션은 부모 없이 생기고, 다시 올리면 기동 때 채워진다.

### 웹 입력의 Slack 글 위치를 기다리는 줄을 보류하는 릴리스

migration `0335_input_hold`가 `slack_outbox`에 칸 `correlation_id`와 `held_for_input_id`를 더하고, `conversation_inputs.slack_mirror`에 값 `unconfirmed`를 더한다. 올릴 때 할 일은 없다. 이 릴리스에는 웹 입력을 적는 route가 없어서 새 칸이 채워지는 줄은 생기지 않고, Slack 멘션과 답, 웹·API 세션의 동작은 그대로다.

- 웹 입력의 Slack 글이 아직 위치(ts)를 받기 전에는, 그 글의 스레드로 가야 할 Slack 줄을 종류와 상관없이 보류한다. 글이 올라가면 위치를 적는 같은 트랜잭션에서 그 스레드로 풀려 나간다. 이미 위치가 있는 스레드로 가는 줄은 그대로다.
- 웹 입력의 Slack 글에는 요청마다 새로 만든 상관값을 message metadata(`event_type` `werft_input_mirror`)로 싣는다. 다른 줄의 글에는 metadata가 없다.
- 게시가 `uncertain`으로 끝나면 다시 보내지 않고, 새 스레드나 채널 맨 위 글을 만들지 않는다. 입력은 `unconfirmed`("Slack 반영을 확인하지 못했어요")가 되고, 같은 주제의 다음 입력도 기다린다.
- Slack이 돌려보낸 자기 앱의 글이 metadata의 상관값으로 `uncertain`인 거울 하나를 정확히 가리키면, 그 글을 거울의 게시로 보고 입력의 별칭으로 잇는다. 후보가 없거나 둘 이상이면 잇지 않는다. 본문이 같다는 것으로는 잇지 않는다.
- 문에서 버린 이벤트의 기록(`drop_fields`)에 `metadata`(`event_type`과 거울의 `correlation_id`)를 더한다. `event_payload`의 나머지는 남기지 않는다.
- "다시 보내기"는 사람이 부를 때만 같은 입력의 거울을 새 상관값으로 보낸다. 입력 줄은 하나 그대로다. 자동으로 다시 보내지 않는다. 이 릴리스에는 그 버튼이나 route가 없다.
- 거울 게시가 끝내 실패하면 보류된 줄은 보내지 않고 `failed`(`input_unplaced`)로 닫는다. 위치가 정해지지 않은 채 `SLACK_ROLE_INPUT_HOLD_SEC`(기본 3600초, Helm `slack.inputHoldSec`)가 지나도 같이 닫고 입력을 `unconfirmed`로 둔다. slack 역할이 `warn` 로그 `Slack rows held for a web input's post closed unsent; Slack never confirmed the post`를 남긴다.
- CHECK와 외래 키는 `NOT VALID`로 더하고 따로 검증하며, 색인은 `CONCURRENTLY`로 만든다. 기존 줄은 고치지 않는다. 이 릴리스에는 보류된 줄을 만드는 길이 없어서 지원 창 안의 이미지로 되돌려도 된다.

### Slack에서 지운 글이 든 턴을 가리는 릴리스

migration은 없고 올릴 때 할 일도 없다. 저장된 글은 지우지 않고 API가 읽을 때 가린다. 지운 글이 없는 세션은 지금처럼 읽힌다.

- Slack에서 지운 글(답이 달린 부모 글의 묘비 포함)이 입력인 턴은 턴 목록·상세(`GET /v1/sessions/{id}/turns`, `…/turns/{turn_id}`)와 감사 열람(`POST /v1/sessions/{id}/audit-read`)에서 `message`가 빈 문자열, `result`가 null이 되고, 새 칸 `source_deleted_at`에 지운 시각이 담긴다. `usage`는 그대로다.
- 그 턴의 이벤트(`GET /v1/sessions/{id}/events`와 SSE, 보관소로 옮긴 이벤트 포함)는 envelope에 `source_deleted_at`이 붙고 글이 빠진다. 답의 글과 생각, 도구 호출의 입력, 도구 결과의 글, 질문의 입력, result의 답이 빠지고, 도구의 이름과 id, 턴의 끝과 토큰 수는 남는다. 이미 스트림으로 받은 클라이언트는 다시 읽어야 가려진다.
- 그 턴의 대기 요청은 `GET /v1/sessions/{id}/pending-requests`에 나오지 않는다.
- 첫 글에서 따오거나 만든 제목(`title_source`가 `derived`·`generated`)은 첫 턴이 가려지면 세션 목록·상세에서 `title`이 null이 되고 새 칸 `title_deleted_at`에 지운 시각이 담긴다. 그 제목의 글로는 검색되지 않는다. 사용량 화면의 도구 호출과 성과 목록에서도 세션 제목이 비어 보인다. 사람이 붙인 제목은 그대로다.
- 웹 입력은 그 입력이 Slack에 비친 글이 지워지면 같은 방식으로 가린다.
- 같은 세션의 뒤 턴처럼 그 글을 물려받기만 한 턴은 가리지 않는다.
- 웹 콘솔은 가려진 자리에 "Slack에서 삭제됨"을 보인다.
- 지원 창 안의 이미지로 되돌리면 저장된 값이 그대로라 가린 글이 다시 읽힌다.

### 웹 입력을 Slack 거울과 잇는 릴리스

migration `0334_input_mirror`가 `slack_outbox`에 종류 `input_mirror`와 그 줄이 비추는 웹 입력의 칸 `input_id`를 더하고, 아직 Slack에 비치지 않은 웹 입력을 찾는 부분 색인을 `conversation_inputs`에 `CONCURRENTLY`로 만든다. 올릴 때 할 일은 없다. 이 릴리스에는 웹 입력을 적는 route가 없어서 새 종류의 줄은 생기지 않고, Slack 멘션과 답, 웹·API 세션의 동작은 그대로다.

- 웹 입력은 `instruction`과 같은 모양(보낸 사람 이름 뒤에 "(웹 콘솔)")으로 Slack에 올라간다. 새 주제의 첫 입력은 채널(DM이면 그 사람의 DM)의 맨 위 글이 되고, 나머지는 그 주제의 스레드에 올라간다.
- 게시가 성공하면 같은 트랜잭션에서 그 글의 (team, 채널, ts)가 입력의 Slack 별칭이 되고, 새 주제면 주제의 Slack 위치도 된다. 같은 스레드의 사람 답글은 그 주제의 다음 순번으로 접수된다.
- Slack이 돌려보내는 그 글의 이벤트는 지금처럼 자기 앱의 글(`own_bot_user`)로 문에서 버리고, 새 입력이나 턴을 만들지 않는다.
- 별칭이 생긴 뒤 그 Slack 글을 지우면, 그 웹 입력을 출처로 가진 outbox 줄이 `voided_by_delete`로 멈춘다. 별칭보다 먼저 온 삭제 표식도 별칭이 생기는 순간 그 입력의 것이 된다.
- 사람 답글이 게시 결과보다 먼저 처리되어 그 스레드가 이미 다른 주제가 된 드문 경우, 두 주제를 합치지 않는다. slack 역할이 `warn` 로그 `Slack mirror opened a thread another topic already holds; the topics stay apart`를 남긴다.
- DM의 새 주제는 그 사람의 DM 채널을 아는 주제가 있을 때만 올라간다. 없으면 입력은 Slack에 비치지 않은 채로 기다린다.
- CHECK와 외래 키는 `NOT VALID`로 더하고 따로 검증한다. 지원 창 안의 이미지로 되돌려도 된다.

### 끝난 턴의 끝을 모르는 예약을 추정으로 정산하는 릴리스

migration `0373_budget_reservation_estimated`가 `budget_reservations`의 `resolution` CHECK에 값 `estimated`를 더한다. 칸은 바뀌지 않는다. CHECK는 `NOT VALID`로 다시 더한 뒤 따로 검증하므로 표를 오래 잠그지 않는다. 올릴 때 할 일은 없다.

- reconciler가 매 pass 배치 크기만큼, 끝을 모르는 예약 가운데 호출이 더는 돌 수 없는 것을 정산한다. 조건과 그 밖의 줄을 푸는 법은 [끝을 모르는 예산 예약 풀기](/run-server/self-hosting/reference/storage#끝을-모르는-예산-예약-풀기)에 있다.
- 정산은 묶인 만큼을 쓴 것으로 확정한다(`resolution: "estimated"`). 계정의 쓴 것과 예약을 합한 값은 그대로라 예산 한도 판정은 바뀌지 않는다. 그 호출은 진행 중으로 세지 않는다. 대화 호출은 `resolved`가 되어 동시 호출 상한에서 빠지고, 세션 호출은 원장 줄이 해제되어 세션 한도에서 빠진다.
- 늦은 보고가 오면 운영자가 푼 줄과 같이 차이를 조정 줄 하나로 더한다.
- 정산마다 receipt `resolve_unknown_budget`(행위자 없음, `by: "reconciler"`)과 `warn` 로그 `Budget reservation of unknown end settled as estimated`가 남는다. `RECONCILER_DRY_RUN`이면 로그만 남긴다.
- 사용량 화면의 수는 바뀌지 않는다. 세션 비용은 사용량 보고만 세고, 보고 없이 끝난 턴은 지금처럼 비용을 완전하지 않은 것으로 보인다.
- 지원 창 안의 이미지로 되돌려도 된다. 옛 이미지는 이 정산을 하지 않고, 정산된 줄은 운영자가 푼 줄처럼 다룬다.

### 끝을 모르는 예약을 운영자가 푸는 릴리스

migration `0350_unknown_budget_resolution`이 `budget_reservations`에 nullable 칸 `resolution`과 상태 값 `resolved`를, `conversation_calls`에 상태 값 `resolved`를 더하고, 늦은 보고의 조정 줄을 두는 빈 표 `budget_adjustments`를 만든다. 바뀐 CHECK는 `NOT VALID`로 다시 더한 뒤 따로 검증하므로 표를 오래 잠그지 않는다. 올릴 때 할 일은 없고, 운영자가 명령으로 풀기 전에는 동작이 그대로다.

- 운영자 명령 `budget-unknown.ts`(`list`·`resolve`)가 들어온다. 사용법은 [끝을 모르는 예산 예약 풀기](/run-server/self-hosting/reference/storage#끝을-모르는-예산-예약-풀기)에 있다. 푼 예약마다 receipt `resolve_unknown_budget`이 남는다.
- 지원 창 안의 이미지로 되돌려도 된다. 다만 푼 예약에 늦은 보고가 오면 옛 이미지는 그 보고를 저장하지 못하고 실패로 답하며, 보고는 다시 시도된다. 되돌린 동안은 명령으로 풀지 않는다.

### 끝을 모르는 호출을 표시하고 에이전트 스스로 하는 일을 먼저 멈추는 릴리스

migration `0332_unknown_budget_end`가 `budget_reservations`와 `conversation_calls`에 끝을 모르는 호출을 적는 칸 `unknown_at`(nullable)을 더하고, reconciler가 읽는 부분 인덱스 둘을 만든다. 올릴 때 할 일은 없다. 예산 한도가 없는 설치에서는 사람, key, 에이전트의 호출이 지금처럼 돈다.

- 쓰인 provider 호출에 lease(5분) 안에 사용량 보고가 오지 않으면 reconciler가 그 예약의 `unknown_at`을 적는다. 상태는 `reserved`(대화 호출은 `in_flight`) 그대로다. 예약은 풀지 않고, 한도 계산에서 계속 쓴 것으로 센다. 늦게 보고가 오면 실제 값으로 정산하고 예약을 뺀다. lease가 다시 갱신되거나 호출이 해제되면 표시를 지운다. 세션의 호출과 세션 없는 호출(대화 호출)이 같은 규칙을 따른다.
- reconciler가 끝을 모르는 예약이 많은 계정부터 배치 크기만큼 그 수와 묶인 금액을 `warn` 로그 `Budget reservations of unknown end held`(`unknown_count`, `held_cost_usd`, `held_tokens`)로, 모든 계정의 합계를 로그 `Budget reservations of unknown end reported`로 남긴다. 로그 `Provider exchange ledger reconciled`와 `Conversation call reservations reconciled`에 `unknown_count`가 더해진다. 이 릴리스에는 묶인 예약을 운영자가 푸는 명령이 없다.
- 한도가 있는 예산 계정에서 사람도 key도 없는 실행(root 종류 `none`)의 예약은 한도의 80%에서 거절된다. 사람의 요청과 key, Slack 봇의 요청은 100%까지 돌고, 100%에서는 모두 거절된다. 한도가 없는 계정에는 80% 판정이 걸리지 않는다.
- 상태 값과 CHECK는 바뀌지 않고, 인덱스는 `CONCURRENTLY`로 만든다. 지원 창 안의 이미지로 되돌려도 된다. 옛 이미지는 `unknown_at`을 무시하고 예약을 `reserved`로 정산한다.

### 판단 버퍼를 더하는 릴리스

migration `0330_judgment_buffer`가 입력 접수 표 `conversation_inputs`에 만료 칸 `buffer_expires_at`과 그 색인을 더하고, 줄의 종류를 가리는 CHECK에 '판단 버퍼에 담긴 Slack 글'을 더한다. 줄은 고치지 않고 색인은 `CONCURRENTLY`로 만든다. 올릴 때 할 일은 없고 Slack 동작도 그대로다.

- 버퍼는 에이전트의 대화 층 스위치 `conversation_rollout`이 `shadow`·`on`이고 채널이 `free`로 들을 때만 멘션 없는 글을 담는다. 기본값은 `off`이고 이 릴리스에는 스위치를 바꾸는 API가 없다.
- 담긴 줄은 글의 본문과 쓴 사람의 Slack id를 갖고, 10분 뒤 reconciler가 통째로 지운다. 로그 `Judgment buffer purged`의 `expired_count`가 만료로, `unlistened_count`가 더 듣지 않는 채널로 지운 수다.
- Slack에서 그 글이 지워지면 바로 지우고, 고쳐지면 담긴 본문만 새 본문으로 바꾼다. 지워지거나 고쳐진 뒤에 늦게 온 글은 담지 않는다. 채널 보관·삭제, 봇이 채널을 나감, binding `off`, 에이전트 보관 때도 바로 지운다.
- 지원 창 안의 이미지로 되돌려도 된다. 옛 reconciler는 버퍼 줄을 지우지 않지만, 스위치를 켠 적이 없으면 버퍼 줄은 없다.

### 지운 Slack 글에 걸린 답과 턴을 막는 릴리스

migration `0329_slack_outbox_voided_by_delete`가 `slack_outbox`의 상태 값에 `voided_by_delete`를, 그 줄이 어느 턴의 것인지 적는 칸 `sources_turn`을 더한다. 올릴 때 할 일은 없다. 지운 글이 없는 스레드의 멘션과 답, 웹·API 세션의 동작은 그대로다.

- Slack에서 지운 글(답이 달린 부모 글의 묘비 포함)이 출처에 든 outbox 줄은 보내기 직전에 멈춘다. 답, 실패 알림, 승인 카드, 웹 지시의 거울이 모두 해당하고, 그 세션 앞 턴의 글을 물려받은 출처도 본다. 줄은 상태 `voided_by_delete`, `error_code` `source_deleted`로 끝나고 다시 보내지 않는다. slack 역할이 `warn` 로그 `Slack send voided: a source was deleted`를 남긴다.
- 보내기 시작한 뒤에 온 삭제는 이미 나간 글을 지우지 않는다. 표식 확인과 보내기 시작은 같은 글의 잠금으로 갈린다.
- 글의 수정은 아무것도 막지 않는다.
- 지운 글로 세션을 만들거나 턴을 넣지 않는다. 그 글의 멘션, 앞 글이 지워진 스레드의 다음 글이 해당한다. Slack에는 안내를 올리지 않고, slack 역할이 `warn` 로그 `Slack input refused by the session`(`code` `SOURCE_DELETED`)을 남긴다.
- 그런 세션에 웹이나 API로 메시지를 보내면 새로 409 `SOURCE_DELETED`로 거절된다. 이 릴리스는 세션을 멈추지는 않는다.
- CHECK는 `NOT VALID`로 더하고 따로 검증하므로 표를 쓰는 동안 오래 막지 않는다. 지원 창 안의 이미지로 되돌려도 된다. 옛 이미지는 `voided_by_delete` 줄을 읽지도 보내지도 않는다.

### 세션 없는 호출의 예약 표를 만드는 릴리스

migration `0328_conversation_calls`가 세션 없는 provider 호출(대화 호출)의 표 `conversation_calls`를 더한다. 이 릴리스에는 대화 호출을 내는 경로가 없어서 표는 비어 있다. 올릴 때 할 일은 없다.

- 대화 호출은 토큰을 내기 전에 누구의 요청인지(root)로 고른 예산 계정에 그 호출의 최대 비용을 예약한다. 최대 비용은 요청 본문의 바이트 상한을 입력 토큰으로, `max_tokens`를 출력 토큰으로 셈한다. 계정이 모자라면 토큰도 표의 줄도 생기지 않는다.
- 토큰은 해시로만 저장하고, egress proxy를 지나는 Messages 호출 하나에 묶인다. 그 호출의 경로, 모델, `max_tokens`, 본문 바이트 상한을 넘는 요청은 proxy가 거절한다. 같은 토큰의 두 번째 호출도 거절한다.
- 쓰인 호출은 proxy의 사용량 보고로 계정에 정산된다. 세션의 사용량(`provider_usage`)에는 적지 않는다.
- 2분 안에 쓰이지 않은 토큰의 예약은 reconciler가 풀고 로그 `Conversation call reservations reconciled`(`released_count`)를 남긴다. 쓰였는데 보고가 오지 않은 호출의 예약은 풀지 않는다.
- 세션 제목 짓기 호출과 실행 중인 턴이 없는 세션 호출은 이제 그 세션을 만든 첫 턴의 계정에 잡힌다. 한도가 없는 설치에서는 지금처럼 돈다. 한도를 넣으면 넘는 제목 짓기 호출은 거절되고 첫 메시지에서 자른 제목이 남는다.
- egress proxy가 provider 허가 요청에 헤더 `x-werft-exchange-id`를 붙인다. 앞선 API는 이 헤더를 무시한다. 대화 호출 토큰은 이 헤더가 있어야 허가되므로 api와 egress proxy를 함께 올린다.
- 새 표만 만들므로 지원 창 안의 이미지로 되돌려도 된다.

### Slack 스레드의 게시 설정을 칸 셋으로 나눈 릴리스

migration `0326_link_posting`이 `session_links`에 게시 칸 셋을, 채널 binding에 `report_mode` 기본값을 더한다. 스레드에 무엇이 올라가는지는 이제 `visibility` 대신 이 칸들이 정한다. 올릴 때 할 일은 없고, Slack에 올라가는 글의 종류와 횟수는 그대로다.

- `report_mode`(nullable)는 답·실패·push와 PR 결과 알림을, `mirror_instructions`는 웹·API에서 보낸 지시를 스레드에 비추는 것을, `post_prompts`는 승인 카드와 질문을 정한다. link의 `report_mode`가 비어 있으면 그 채널 binding의 값을 쓴다. binding의 기본값은 `per_step`(지금처럼 턴마다 올림)이다.
- `visibility = 'full'`인 link는 그대로 둔다. 새 칸의 기본값이 `full`과 같은 뜻이다. `summary`인 link는 api가 기동할 때마다 도는 정리가 `report_mode = 'none'`, 나머지 두 칸 `false`로 묶음으로 옮긴다(지금처럼 아무것도 올리지 않음). 옮기기 전에도 outbox는 `summary` link에 아무것도 올리지 않는다. 옮긴 수는 로그 `Summary session links moved`에 남는다. 이 릴리스까지 `summary` link를 만드는 길은 없었으므로 보통 0이다.
- `none`은 옮긴 link에만 있는 값이다. binding의 CHECK는 `notify_only`·`progress`·`per_step`만 받는다. 이 릴리스에는 칸 셋을 바꾸는 화면·API가 없다.
- `session_links`의 CHECK는 `NOT VALID`로 더한 뒤 따로 검증하므로 쓰기를 오래 막지 않는다. `visibility` 칸은 뒤의 릴리스가 지울 때까지 남는다.
- 지원 창 안의 이미지로 되돌려도 된다. 옛 이미지는 `visibility`만 읽고, 새 이미지가 만든 link도 `visibility`가 `full`이라 지금처럼 올린다.

### 채널 요약 표를 만드는 릴리스

migration `0325_channel_summaries`가 채널 요약 표 셋(`channel_summaries`, `channel_summary_lines`, `channel_summary_line_sources`)을 더한다. 이 릴리스에는 요약을 쓰는 길이 없어서 표는 비어 있다. 올릴 때 할 일은 없고, Slack과 세션의 동작은 그대로다.

- 요약은 채널마다 한 벌이고 그 채널의 에이전트가 같이 쓴다. 줄에는 에이전트가 쓴 글, 쓴 에이전트, 시각이 있고, 출처 줄에는 그 줄이 나온 Slack 글의 자리(team, 채널, ts), 입력 접수 줄 id, 화자(그 입력의 요청자)가 있다. Slack 글의 본문은 저장하지 않는다. 화자와 출처는 서버가 입력 접수 줄에서 읽는다.
- 바뀔 때마다 버전이 하나 오르고, 옛 버전은 되돌리기용 이력으로 남는다.
- 출처 글이 Slack에서 지워지거나 고쳐지면 그 줄을 지금 버전과 모든 옛 버전에서 지우고 버전을 올린다. 되돌려도 살아나지 않는다.
- 요약 줄이 출처로 가진 글의 삭제·수정 표식은 70분이 지나도 reconciler가 지우지 않는다.
- 새 표만 만들므로 지원 창 안의 이미지로 되돌려도 된다.

### 턴과 outbox 줄에 출처 집합을 적는 릴리스

migration `0324_source_sets`가 `turns`와 `slack_outbox`에 출처 집합 칸 `sources`(jsonb, nullable)를 더하고, 두 칸에 GIN 색인(`turns_sources_idx`, `slack_outbox_sources_idx`)을 만든다. 올릴 때 할 일은 없고, Slack 멘션의 답과 웹·API 세션의 동작은 그대로다.

- 출처 집합은 그 턴이 어느 Slack 글에서 나왔는지를 글의 자리(team, 채널, ts)와 입력 접수 줄의 id로만 적는다. 본문은 담지 않는다. 그 턴의 입력은 직접 출처(`direct`), 같은 세션의 앞 턴들이 나온 글은 물려받은 출처(`inherited`)로 갈라 적는다.
- Slack 글로 생긴 턴은 그 글을 직접 출처로 갖는다. 같은 세션의 뒤 턴(이어 가는 턴, push 후속 턴, 웹·API로 보낸 지시)은 앞 턴들의 출처를 물려받는다. Slack과 무관한 웹·API 세션의 턴은 칸이 비어 있다.
- 턴의 답, 실패 알림, 승인 카드, 웹 지시의 거울, 전송을 확인하지 못했다는 알림 줄은 그 턴의 출처를 그대로 받는다. 다른 알림 줄은 비어 있다.
- 한 집합은 256개까지 적는다. 넘으면 앞의 것부터 남기고 `overflow`를 표시한다.
- 출처 집합에 든 글의 삭제·수정 표식(`deleted_sources`·`edited_sources`)은 70분이 지나도 reconciler가 지우지 않는다.
- 이 릴리스는 출처를 적기만 한다. 지운 글의 출처로 답을 막거나 세션을 멈추는 동작은 아직 없다.
- 칸은 기본값 없이 더하고 색인은 `CONCURRENTLY`로 만들므로 표를 다시 쓰지 않고 쓰기를 오래 막지 않는다. 있던 턴과 줄은 비어 있는 채로 남는다. 지원 창 안의 이미지로 되돌려도 된다. 옛 이미지는 칸을 읽지 않고, 그동안 만든 턴은 출처 없이 생긴다.

### Slack 글을 입력 접수 표에 적는 릴리스

migration `0316_conversation_inputs`가 입력 접수 표 `conversation_inputs`를 더한다. slack 역할은 멘션·DM·묶인 스레드의 글을 지금처럼 세션의 턴으로 넣고, inbox 행을 처리됨으로 바꾸는 같은 transaction에서 그 글을 접수 줄 하나로 적는다. 0310이 만든 `conversations`·`conversation_topics`도 이때부터 채운다. 올릴 때 할 일은 없고, Slack과 세션의 동작은 그대로다.

- 접수 줄에는 글의 자리(team, 채널, ts), 주제(스레드) 안의 순번, 요청자(Werft 사용자 id, 허용한 봇이면 그 봇의 Slack 사용자 id), 그 글이 된 턴만 남는다. 본문은 남지 않는다.
- 한 글이 `message`와 `app_mention` 두 이벤트로 와도, Slack이 같은 이벤트를 다시 보내도 에이전트마다 한 줄이다. 턴이 되지 않은 글(거절, 무시)은 적지 않는다.
- 순번은 서버가 접수한 순서다. 늦게 온 이벤트는 Slack ts가 앞서도 뒤 번호를 받는다.
- 접수 줄이 있는 글의 삭제·수정 표식(`deleted_sources`·`edited_sources`)은 70분이 지나도 reconciler가 지우지 않는다.
- 지원 창 안의 이미지로 되돌리면 그동안의 글은 접수 줄 없이 지금처럼 턴만 생긴다.

### 웹 입력 칸을 입력 접수 표에 더하는 릴리스

migration `0319_web_inputs`가 입력 접수 표 `conversation_inputs`에 웹 입력의 칸 셋(`client_message_id`, `body`, `slack_mirror`)을 더하고, `turn_id`를 비워 둘 수 있게 한다. 웹에서 들어온 입력을 서버가 받는 즉시 입력 id·주제·요청자·순번을 정해 적는 접수 서비스가 함께 들어오지만, 이 릴리스에는 그 서비스를 부르는 route가 없다. 올릴 때 할 일은 없고, 웹 콘솔과 Slack의 동작은 그대로다.

- 웹 입력 줄은 본문을 갖고, 턴이 생기기 전이라 `turn_id`가 비어 있을 수 있다. Slack 접수 줄은 지금처럼 본문 없이 턴을 가리킨다. CHECK `conversation_inputs_origin_check`가 둘을 가른다.
- 같은 사람이 같은 에이전트에 같은 `client_message_id`로 다시 보내면 앞의 접수 결과가 돌아온다. 본문이 다르면 거절한다.
- 인덱스는 `CONCURRENTLY`로 만들고 CHECK는 `NOT VALID`로 더한 뒤 따로 검증하므로 쓰기를 오래 막지 않는다. 있던 줄은 모두 Slack 접수 줄이라 검증을 통과한다.
- 지원 창 안의 이미지로 되돌려도 된다. 옛 이미지는 새 칸을 읽지 않고 Slack 접수 줄을 지금처럼 적는다.

### 턴에 요청자의 인증 근거를 남기는 릴리스

migration `0315_turn_requester_auth`가 `turns.requester_auth`(jsonb)와 `tool_call_audits.requester_kind`·`requester_id`(text)를 더한다. 셋 다 nullable이고 기본값·색인·backfill이 없어 표를 다시 쓰지 않는다. 올릴 때 할 일은 없다.

- 이 릴리스부터 새 턴에 요청자가 들어온 자격이 남는다: 콘솔 로그인 세션 id, 개인 key id, 에이전트 key의 에이전트, Slack 설치와 연결 계정. key의 비밀, cookie, Slack 사용자 id는 담지 않는다.
- 옛 턴은 고치지 않는다. 턴 읽기 API의 `requester`가 null이거나 `auth_method`가 null로 보인다. `tool_call_audits`의 두 칸은 이 릴리스에서는 비어 있다.
- 지원 창 안의 이미지로 되돌리면 새 칸을 읽지도 쓰지도 않는다. 그 이미지가 넣은 턴은 근거가 비어 있을 뿐이다.

### 대화 층의 빈 표 셋을 더한 릴리스

migration `0310_conversation_scopes`가 `channel_contexts`(채널 개체)·`conversations`(에이전트의 메인 대화)·`conversation_topics`(대화의 주제) 표를 빈 채로 만든다. 이 릴리스의 코드는 아직 이 표를 읽거나 쓰지 않으므로 올릴 때 할 일은 없고, Slack과 세션의 동작도 그대로다.

- 지원 창 안의 이미지로 되돌려도 영향이 없다. 옛 코드는 이 표를 모른다.

### 처리한 Slack 이벤트 원문을 지우는 릴리스

migration `0308_slack_inbound_payload_check`가 `slack_inbound_events`의 CHECK를 바꾼다. 처리를 마친 행과 실패한 행은 원문(`payload`) 없이도 된다. 이 릴리스의 slack 역할은 처리를 마치면 원문을 지우고, reconciler는 받은 지 7일이 지난 실패 행의 원문을 지운다. 보존 기간은 [데이터별 보존](/run-server/self-hosting/reference/storage#데이터별-보존)에 있다.

- 새 CHECK는 옛 CHECK보다 느슨하다. 원문을 남기는 앞선 slack 역할의 쓰기도 받으므로, 지원 창 안의 이미지로 되돌려도 된다.
- 원문을 지운 행이 하나라도 생기면 옛 CHECK(`slack_inbound_events_dropped_check`)를 다시 걸 수 없다. 0308 아래로 스키마를 내리지 않는다. 지운 원문은 돌아오지 않는다.

### 사람에게 바로 가는 Slack 글을 막는 릴리스

migration `0309_slack_outbox_channel`이 `slack_outbox`에 CHECK `slack_outbox_channel_check`를 더한다. Slack 사용자 id(`U…`, Enterprise Grid의 `W…`)를 channel로 가진 줄은 모델 안내(`model_notice`)만 넣을 수 있다. 에이전트가 사람에게 DM을 먼저 열지 않게 하는 방어다. 지금까지 어느 릴리스도 그런 줄을 쓰지 않았으므로 보통은 할 일이 없다.

- 그런 줄이 남아 있으면 migrate 로그 `db.migrate.notice`에 그 수가 남고(`0309: … slack_outbox rows name a Slack user as their channel`), migrate가 `VALIDATE CONSTRAINT`에서 멈춘다. 그때도 제약은 `NOT VALID`로 남아 새 줄을 막는다. 올리기 전에 아래 쿼리로 확인할 수 있다.

```sql
SELECT kind, status, count(*) FROM slack_outbox
WHERE channel_id ~ '^[UW]' AND kind <> 'model_notice'
GROUP BY 1, 2;
```

- 찾은 줄은 보내서는 안 되는 줄이다. 지운 뒤 migrate를 다시 돌린다. 각 문장은 다시 돌려도 된다.
- 보내는 쪽도 그런 줄을 Slack에 보내지 않고 `failed`(`error_code` `user_channel`)로 끝낸다.
- 앞선 이미지도 그런 줄을 쓰지 않으므로 제약을 둔 채 되돌려도 된다.

### 모델 안내를 사람에게 바로 보내지 않는 릴리스

모델 안내(`model_notice`: 세션의 모델이 허용 목록에서 빠짐, 세션 모델 이동, `runtime_retired` 멈춤, worker 이미지 교체)는 이제 사람에게 DM으로 가지 않는다. 세션에 Slack 스레드가 있으면 그 스레드에 한 번 올라가고, 없으면 웹 콘솔의 세션 기록에만 보인다. 음소거한 스레드, 보고를 끈 스레드, 닫힌 스레드에는 가지 않는다. 에이전트 단위의 모델 자동 이동 안내(옮김, 옮기지 못함)는 Slack에 가지 않는다. migration은 없고 따로 할 일도 없다.

- api는 시작할 때마다 앞선 릴리스가 사람에게 쓴 모델 안내 줄을 정리한다. 아직 보내지 않은 줄은 세션 스레드가 있으면 그 스레드로 옮기고(한 안내에 한 줄), 나머지(보낸 줄, 실패한 줄, 스레드가 없는 줄)는 지운다. 정리한 수는 로그 `Model notices taken off people's direct messages`(`moved`, 상태별 `deleted`)에 남는다. 보내는 중인 줄은 다음 시작에 다시 본다.
- 보내는 쪽은 channel이 Slack 사용자 id인 줄을 모델 안내라도 보내지 않는다. 앞선 이미지가 함께 도는 동안 쓴 줄 중 세션의 줄은 다음 시작의 정리를 기다리고, 세션이 없는 줄은 `failed`(`error_code` `user_channel`)로 끝난다.
- CHECK `slack_outbox_channel_check`는 지금처럼 모델 안내를 받는다. 그래서 앞선 이미지로 되돌려도 그 이미지의 모델 안내 쓰기가 막히지 않는다. 이 예외는 다음 릴리스가 지운다.
- 앞선 이미지로 되돌리는 동안이나 두 이미지가 함께 도는 동안, 앞선 이미지는 이 릴리스가 비공개 채널 세션의 스레드에 쓴 모델 안내를 보내지 않고 `failed`(`error_code` `reader_outside_channel`)로 닫는다. 잘못된 곳으로 가지는 않고, 같은 안내는 웹 세션 기록에 남는다.
- 비공개 채널 세션의 DM을 받을 사람이 그 채널 멤버인지 확인하던 일(`error_code` `reader_outside_channel`)은 없어진다. 안내가 세션의 스레드에만 가기 때문이다.

### 호출을 턴의 예산 계정에 매기는 릴리스

이 릴리스부터 provider 호출의 open이 세션 한도와 함께 예산 계정에서도 그 호출을 잡는다. 계정은 실행 중인 턴이 누구의 요청인지(root)로 고른다. migration `0322_budget_root_slack_bot`은 원장의 root 종류에 `slack_bot`을 더한다(`provider_exchanges.budget_root_kind`, `budget_reservations.root_kind`의 CHECK 교체). 따로 할 일은 없다.

- 한도를 정하지 않은 설치(`budget_limits` 행이 없음)에서는 사람·key·Slack 봇의 턴이 지금처럼 돈다. 원장에는 호출마다 root 종류와 계정이 남는다. 사람이 시키지 않은 에이전트 스스로의 일(root `none`)은 한도가 없으면 거절되지만, 이 릴리스에는 그런 턴을 만드는 경로가 없다(push 후속 턴은 앞 턴의 요청자를 따른다).
- 계정 고르기: 사람의 턴과 그 뒤의 이어 가는 턴·push 후속 턴은 그 사람의 계정(`user`)이다. 개인 key의 턴은 만든 사람의 계정(`key`), 사람 없는 key의 턴은 에이전트를 관리하는 팀의 계정(`key`), 허용한 Slack 봇의 턴도 그 팀의 계정(`slack_bot`)이다. 팀이 보관되었으면 계정 없이 root 종류만 남는다.
- 요청자를 읽을 수 없는 턴(요청자 기록이 없는 옛 턴 등), 세션 제목 짓기 호출, 실행 중인 턴이 없는 호출(턴 사이 등), 워크스페이스가 없는 세션은 계정을 잡지 않고 세션 한도만 본다. 지금과 같다.
- `budget_limits`에 한도를 넣으면 그 계정에서 넘는 호출은 세션 한도를 넘었을 때와 같은 `BUDGET_EXCEEDED`로 거절된다. 계정이 거절한 턴은 provider 오류로 끝나고(Claude Code 엔진은 `api_error`) 세션의 주의 표시(`BUDGET_EXCEEDED`)는 세션 한도에만 생긴다. 계정 거절인지는 아래 로그의 `turn_id`로 잇는다. 이 릴리스에는 한도를 정하는 화면이나 API가 없다.
- 거절된 open마다 API가 `info` 로그 `Provider exchange refused for the budget`을 남긴다. 칸은 `session_id`, `attempt_id`, `turn_id`(실행 중인 턴), `refused_by`(`session` 또는 `account`), `budget_root_kind`, `budget_account_id`다.
- CHECK가 값을 넓히기만 하므로 지원 창 안의 이미지로 되돌려도 된다. 이미 열린 호출은 처음 open이 고른 계정(또는 세션 한도만)으로 끝난다.
- 제목 짓기 호출은 egress proxy가 open에 헤더로 알린다. api만 이 버전이고 egress proxy가 앞선 버전인 동안에는 제목 짓기 호출도 실행 중인 턴의 계정에 잡힌다. 한도를 정하지 않은 설치에서는 차이가 없고, 둘을 함께 올리면 된다.

### 원장에 예산 계정 칸을 더하는 릴리스

migration `0318_provider_exchange_budget`이 provider 호출 원장 `provider_exchanges`에 nullable 칸 둘을 더한다. `budget_root_kind`(그 호출을 매긴 root 종류 `user`·`key`·`none`)와 `budget_account_id`(그 호출을 함께 잡은 예산 계정)다. 따로 할 일은 없다.

- 이 릴리스에서는 어떤 호출도 계정을 넘기지 않으므로 두 칸은 비어 있고, 세션 비용 한도와 토큰 한도는 지금처럼 동작한다. 원장이 계정과 세션 한도를 한 번에 잡는 코드는 들어가지만, 호출 경로에 연결하는 것은 뒤의 릴리스다.
- 칸을 더하기만 하므로 지원 창 안의 이미지로 되돌려도 된다.

### 예산 계정 표를 더하는 릴리스

migration `0314_budget_accounts`가 빈 표 셋을 만든다. `budget_limits`(조직 전체 사람당 기본 한도, 사람마다의 한도, 에이전트 팀 한도), `budget_accounts`(사람·팀 계정의 달마다 쓴 것과 예약한 것, UTC 기준 달), `budget_reservations`(호출마다의 예약과 정산 기록)이다. 따로 할 일은 없다.

- 이 릴리스에서는 어떤 호출도 이 표를 읽거나 쓰지 않는다. 세션 비용 한도와 토큰 한도는 지금처럼 동작하고, 한도를 정하는 화면·API·운영자 명령도 없다.
- 새 표만 만들므로 지원 창 안의 이미지로 되돌려도 된다.

### Slack 글의 수정·삭제 표식

migration `0312_slack_source_marks`가 새 표 `deleted_sources`와 `edited_sources`를 만든다. 이 릴리스부터 Slack에서 글을 지우거나 고친 이벤트(`message_deleted`, 답이 달린 글을 지울 때 오는 묘비 `message_changed`, 사람이 고친 `message_changed`)를 버리지 않고, 그 글의 자리(team, 채널, ts)와 시각만 표식으로 남긴다. 글의 본문과 이벤트 원문은 어디에도 저장하지 않고, inbox 행은 원문 없이 `processed`로 남는다. 따로 할 일은 없다.

- 지금은 Werft가 그 글을 가리키는 기록을 두지 않으므로, 모든 표식은 만든 지 70분(판단 버퍼 10분과 1시간)이 지나면 reconciler가 지운다. 로그 `Unknown Slack source marks purged`에 지운 수가 남는다. 보존 기간은 [데이터별 보존](/run-server/self-hosting/reference/storage#데이터별-보존)에 있다.
- 버린 이유 `message_subtype`으로 집계하던 질의는 수정·삭제 이벤트가 빠진 만큼 수가 준다. 링크 미리보기처럼 사람이 고치지 않은 `message_changed`는 지금처럼 버린다.
- 표를 더하기만 하므로 지원 창 안의 이미지로 되돌려도 된다. 앞선 이미지는 이 표를 쓰지 않고 수정·삭제 이벤트를 다시 버린다.

### Slack 스레드의 옛 link unique를 지운 릴리스

migration `0336_session_link_old_uniques`가 `session_links`의 옛 unique 둘(`session_links_surface_ref_key`, `session_links_session_uniq`)을 지운다. 남는 unique는 닫히지 않은 link만 보는 둘(`session_links_open_surface_ref_uniq`, `session_links_open_session_uniq`)이다. 스레드와 세션마다 열린 link는 지금처럼 하나뿐이고, 닫힌 link는 그 옆에 이력으로 남을 수 있다. 올릴 때 할 일은 없고, Slack 스레드의 동작은 그대로다.

- **`v0.3.0` 이하의 이미지로는 되돌릴 수 없다.** 그 이미지는 Slack 스레드의 link를 옛 unique `(installation_id, surface_ref)`를 가리키는 `ON CONFLICT`로 예약하므로, 이 migration 뒤에는 그 예약이 오류로 끝나고 스레드에 세션이 생기지 않는다. 열린 link만 보는 예약으로 옮긴 릴리스부터의 이미지로는 되돌려도 된다. 그보다 앞으로 돌아가야 하면 업그레이드 전 백업으로 DB를 복원한다.
- `v0.3.0`에서 바로 올리면 migrate가 끝난 뒤 옛 slack 역할이 내려갈 때까지 그 역할이 받은 스레드 예약이 실패한다. 실패한 이벤트는 다른 예약 실패처럼 다시 시도되고, 새 slack 역할이 처리한다.
- 행은 고치지 않는다. 제약은 표를 읽지 않는 한 문장으로 지우고(잠깐 잠금을 잡는다), 인덱스는 `CONCURRENTLY`로 지운다. 각 문장은 다시 돌려도 된다.

### Slack 스레드의 link 이력 칸을 더한 릴리스

migration `0313_session_link_history`가 `session_links`에 `closed_at`·`closed_reason` 칸과 닫히지 않은 link만 보는 부분 unique 둘(`session_links_open_surface_ref_uniq`, `session_links_open_session_uniq`)을 더하고, `slack_outbox`에 `session_link_id` 칸을 더한다. 이 릴리스의 코드는 새 칸을 아직 읽거나 쓰지 않으므로 할 일은 없고 동작도 그대로다. 있던 줄은 모두 닫히지 않은 link로 남는다.

- 옛 unique 둘(`session_links_surface_ref_key`, `session_links_session_uniq`)은 그대로 남는다. 뒤의 릴리스가 지운다.
- 인덱스는 `CONCURRENTLY`로 만들고, CHECK와 외래 키는 `NOT VALID`로 더한 뒤 따로 검증한다. 그래서 검증과 인덱스를 만드는 동안 쓰기를 막지 않는다(칸과 제약을 더할 때만 잠깐 잠금을 잡는다).
- 각 문장은 다시 돌려도 된다. 인덱스 만들기가 중간에 끊기면 migrate를 다시 돌린다. 남은 INVALID 인덱스를 지우고 다시 만든다.
- 앞선 이미지는 새 칸 없이 쓰고 옛 unique로 겹침을 가리므로 그대로 돈다. 지원 창 안의 이미지로 되돌려도 된다.

### mock Slack env 이름

mock Slack 시험 스택(`infra/compose.mock-slack.yml`)이 쓰던 `SLACK_API_URL`·`SLACK_OIDC_ISSUER`는 `MOCK_SLACK_API_URL`·`MOCK_SLACK_OIDC_ISSUER`로 바뀌었다. 옛 이름은 읽지 않고, 남아 있으면 `Ignored removed settings` 경고에 이름이 나온다. 새 이름에 값이 있으면 주소와 상관없이 시작할 때 `Mock Slack override in use: <이름>` 경고를 한 줄 남긴다. 운영 설정에는 두 이름 모두 두지 않는다.

### 성과 판정 연결과 되돌리기

`openai_decisions` 연결(성과 판정기 Luna용)을 만든 뒤 이 종류를 모르는 빌드로 되돌리면, 그 빌드의 설정 > 에이전트 연결 > 모델 연결 목록과 `GET /v1/installation/settings/connections`가 다른 연결까지 함께 실패한다. 사용 중지한 연결도 목록에 읽히므로 사용 중지로는 풀리지 않는다. 에이전트 실행과 release는 그 연결을 건너뛰므로 영향이 없다. 되돌리기 전에 DB에서 그 연결 행을 지운다.

```sql
DELETE FROM provider_connections WHERE definition->>'kind' = 'openai_decisions';
```

넣어 둔 key 값은 남는다. 판정 설정에 저장된 연결 id도 남고, 되돌린 빌드에서 Luna 규칙은 판정되지 않는다. 다시 올린 뒤 연결을 다시 만들고 판정 설정에서 고른다. 업그레이드 전 백업으로 DB를 복원해 되돌릴 때는 할 일이 없다.

### worker gateway를 3200 포트로 옮긴 릴리스

이 릴리스부터 api는 `/internal`(worker와 대화 런타임이 부르는 gateway)을 공개 포트 3000이 아니라 3200(`INTERNAL_API_PORT`)에서만 받는다. scheduler가 worker에게 주는 `WORKER_GATEWAY_URL`과 egress proxy의 `EGRESS_PRIVATE_ALLOWLIST`가 같은 주소를 가리켜야 worker가 gateway에 닿는다. migration은 없다.

- release의 compose 파일(Kubernetes는 chart)을 통째로 적용한다. egress proxy의 설정은 control-host와 함께, 또는 그보다 먼저 적용한다. `scripts/test-ops.sh upgrade`는 scheduler가 의존하는 egress proxy도 설정이 바뀌면 다시 만든다. [2. API → proxy → worker 순서](#2-api--proxy--worker-순서)의 중간 release에서도 같다. proxy는 이미지만 현재 것이고 allowlist는 새 값이 된다. Kubernetes chart는 allowlist를 egress proxy Deployment의 env로 넣으므로, 같은 `helm upgrade`가 proxy Pod를 새 값으로 다시 띄운다.
- 기본값을 쓰는 설치는 할 일이 없다. `WORKER_GATEWAY_URL`은 `http://api:3200`, `EGRESS_PRIVATE_ALLOWLIST`는 `api:3200,host.docker.internal:3200`이 기본이다.
- 두 값을 직접 준 설치는 `api:3000`을 `api:3200`으로 바꾼다. Kubernetes에서 `config.egress.privateAllowlist`를 직접 준 설치는 `<fullname>-api:3000`을 `<fullname>-api-internal:3200`으로 바꾼다. proxy 설정을 손으로 고쳐 쓰는 설치도 allowlist에 `api:3200`을 더하고, control-host를 올리기 전에 proxy를 다시 띄운다.
- allowlist가 옛 값으로 남으면 proxy가 worker의 gateway 호출을 403(`egress denied: destination is not allowlisted`)으로 거절하고, worker는 claim 전에 끝난다. 세션은 시작하지 않는다. 이때 남는 기록은 이렇다.
  - proxy 로그: `Egress denied`(`host`, `port` 3200, `reason`).
  - scheduler 로그 `Launch attempt failed; retrying after a backoff`의 `error`: `resource exited before a worker claimed it (exit code 1): the egress proxy refused the worker's bootstrap-claim (destination is not allowlisted): its EGRESS_PRIVATE_ALLOWLIST must name the host and port of WORKER_GATEWAY_URL.` 문장은 이 절의 주소로 끝난다. 앞선 릴리스의 worker는 proxy의 말을 옮기지 않으므로 괄호 안이 `HTTP 403`이다.
  - launch 실패 한도(기본 5회)에 이르면 그 입력은 `LAUNCH_FAILED`로 실패하고, 실패 사유에 같은 문장이 남는다.
- allowlist를 고치고 proxy를 다시 띄우면 backoff 뒤의 다음 launch가 gateway에 닿는다. `LAUNCH_FAILED`로 끝난 입력은 다시 보낸다.
- 올릴 때 돌고 있던 worker는 앞선 주소(3000)로 gateway를 부르므로 호출이 실패한다. 세션이 돌지 않을 때 올린다.
