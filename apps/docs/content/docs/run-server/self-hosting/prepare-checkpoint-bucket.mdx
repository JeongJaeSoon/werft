## 무엇을 하게 되나

기본 보호 모드 locked를 만족하는 영속 bucket과 API 최소 권한을 준비한다. 공통 계약과 AWS 생성 절차를 구분한다.

## 준비물

bucket 생성 권한과 비용 승인이 필요하다. 설치 하나에 bucket 하나, 복원 훈련마다 별도 빈 bucket 하나를 사용한다. AWS 이외 S3 호환 저장소는 [공통 보호 계약](/run-server/self-hosting/reference/storage#공통-object-store-보호)과 조건부 쓰기·legal hold·version 읽기/삭제가 동작하는지 먼저 확인한다. Compose test-ops의 s3 경로는 AWS endpoint를 사용하며 사용자 endpoint를 받는 범용 설치 경로가 아니다.

## 단계

### 1. 공통 계약

- versioning, Object Lock, 기본 SSE-S3(`AES256`)를 켠다.
- public access는 모두 차단한다.
- 기본 retention과 object version을 만료시키는 lifecycle은 두지 않는다.
- 운영 자격 증명에는 bucket 생성 권한을 주지 않는다.

### 2. AWS bucket 만들기

`BUCKET`은 전역에서 유일한 이름으로 바꾼다. 기존 운영 bucket을 덮어쓰는 절차가 아니다.

```bash
BUCKET=<unique-bucket>
AWS_REGION=ap-northeast-1
aws s3api create-bucket --bucket "$BUCKET" --region "$AWS_REGION" \
  --create-bucket-configuration "LocationConstraint=$AWS_REGION" \
  --object-lock-enabled-for-bucket
aws s3api put-bucket-encryption --bucket "$BUCKET" --server-side-encryption-configuration \
  '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}'
aws s3api put-public-access-block --bucket "$BUCKET" --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
```

Object Lock을 켜면 versioning도 켜진다.

### 3. 최소 권한과 경로

- API용 IAM 사용자에게는 이 bucket에 `s3:PutObject`, `s3:GetObject`, `s3:GetObjectVersion`, `s3:GetObjectLegalHold`, `s3:PutObjectLegalHold`, `s3:DeleteObjectVersion`, 그리고 bucket 설정을 읽는 `s3:ListBucket`, `s3:ListBucketVersions`, `s3:GetBucketVersioning`, `s3:GetBucketObjectLockConfiguration`, `s3:GetEncryptionConfiguration`만 준다. bucket을 만드는 권한은 주지 않는다.
- object version을 만료시키는 lifecycle rule을 두지 않는다. 조직 정책이 있으면 이 bucket을 제외한다.
- 복원 훈련은 같은 자격 증명으로 훈련용 bucket에 쓴다. 훈련 bucket 이름을 `<bucket>-drill-*`로 정하고 같은 권한을 그 이름에 준다. 훈련 bucket은 운영자가 자기 권한으로 만든다.

자격 증명은 API와 maintenance 컨테이너에만 간다. worker는 egress proxy를 지나며, 그 요청은 API가 세션 범위로 서명한다. [단일 서버 4단계](/run-server/self-hosting/single-server#4-s3를-명시해-검사설치)의 `TEST_OPS_OBJECT_STORE=s3 preflight`가 업로드, legal hold, version 읽기, hold 해제, scratch version 삭제 왕복을 통과해야 설치할 수 있다.

API용 권한은 bucket의 `s3:ListBucket`, `s3:ListBucketVersions`, `s3:GetBucketVersioning`, `s3:GetBucketObjectLockConfiguration`, `s3:GetEncryptionConfiguration`과 객체의 `s3:PutObject`, `s3:GetObject`, `s3:GetObjectVersion`, `s3:GetObjectLegalHold`, `s3:PutObjectLegalHold`, `s3:DeleteObjectVersion`이다. 리소스 ARN은 이 설치 bucket과 허용된 훈련 bucket 범위로 제한한다. `s3:DeleteObject`는 GC에 필요하지 않다.

`EGRESS_CREDENTIAL_ALLOWLIST` 값은 기본값을 통째로 대체하므로 virtual-hosted bucket endpoint를 넣을 때 provider와 패키지 registry, Git host 등 필요한 항목을 모두 다시 적는다. 점이 든 bucket은 리전의 path-style endpoint를 쓴다. worker에 AWS key를 전달하지 않는다.

## 보호 모드와 기동 검사

API는 `S3_BUCKET`·`AWS_REGION`(선택 `AWS_ENDPOINT_URL`)이 없으면 기동하지 않는다.

- **자격 증명.** `AWS_ACCESS_KEY_ID`·`AWS_SECRET_ACCESS_KEY`는 둘 다 주거나 둘 다 뺀다. 하나만 있으면 기동하지 않는다. 둘 다 빼면 AWS SDK 기본 credential chain이 서명한다. EKS에서는 api ServiceAccount의 IRSA role이 그 자리에 오고, chart는 `secrets.objectStoreKeys: false`로 이 경로를 쓴다. chain이 credential을 찾지 못하면 요청은 서명 없이 나가지 않고 실패한다.
- **보호 모드.** `CHECKPOINT_OBJECT_PROTECTION`의 기본은 `locked`다. versioning이 꺼진 bucket은 `unversioned`를 명시해야 뜬다. 이 모드는 key로만 읽고 hold를 걸지 않으므로 커밋 뒤의 삭제·덮어쓰기를 막지 못하고, 복원 때 digest 불일치로 발견할 뿐이다. checkpoint GC와 세션 이벤트 보관도 아무것도 하지 않는다. `unversioned`에서 `locked`로 바꾸면 그 전 checkpoint는 첫 복원 때 다시 해시하고 hold를 건 뒤에 쓴다.
- **object store 없이.** `CHECKPOINT_OBJECT_STORE=disabled`를 명시하면 모든 checkpoint가 거절되고 worker에는 `409 CHECKPOINT_UNAVAILABLE`로 답한다. 기동 로그에 경고가 남는다.
- **암호화 검사.** API는 기동 때 bucket 기본 암호화를 읽고 `AES256`이 아니면(설정 없음, `aws:kms` 포함) 기동하지 않는다. SSE-KMS는 worker 요청마다 KMS 키 권한이 필요해 받지 않는다. 다른 설정으로 띄워야 하면 `CHECKPOINT_OBJECT_ENCRYPTION_CHECK=warn`을 명시한다. 그러면 경고만 남는다.

### 비워진 bucket

DB에 수거되지 않은 checkpoint 행이 있는데 bucket에 object version이 하나도 없으면(delete marker만 남은 경우 포함) API는 기동하지 않는다. DB만 남고 bucket을 잃었거나, 설정이 다른 빈 bucket을 가리키는 경우다. bucket을 되살리거나 원래 bucket을 가리키게 한다. 미수거 checkpoint가 있는 동안 bucket을 바꾸지 않는다.

시험 설치에만 예외가 있다. `CHECKPOINT_OBJECTS_LOST=forget`(chart는 `config.checkpoints.objectsLost: forget`)이면 API는 이 상태에서 기동을 거부하지 않고, 잃은 checkpoint를 포기한 뒤 뜬다.

- 닫히지 않은 세션은 `recovery_required`가 되어 복구 결정을 기다린다.
- API 로그에 경고 한 줄이 세션 수와 id를 남긴다.
- `/readyz`는 200 그대로이고, 본문의 `detail.checkpoints_forgotten_on_boot`에 그 세션 수를 적는다.

API는 이 설정을 `INSTALLATION_PROFILE=test`(chart는 `config.installation.profile: test`)이고 `AWS_ENDPOINT_URL`의 host 첫 마디가 `localstack`일 때만 받는다(`localstack`, `localstack.<namespace>.svc…`). 그 밖의 설치에서 켜면 기동하지 않는다. 다시 뜰 때마다 비는 LocalStack을 위한 설정이며 운영 bucket에는 쓸 수 없다. object가 일부만 없는 bucket은 이 설정으로도 정리하지 않는다. `v0.4.0` 이하 릴리스에는 이 설정이 없다.

### 저장량

checkpoint가 쓰는 바이트는 실행 한도의 저장량에 세지 않는다. `locked`에서는 모든 version에 hold가 걸려 있어 GC가 hold를 풀고 지우기 전까지 lifecycle 규칙으로도 줄지 않는다. 저장량은 주간 checkpoint GC와 bucket 크기 관찰로 관리한다.

## 확인

단일 서버는 S3를 명시한 preflight가 scratch 객체의 create-only put → hold → hold 확인/version 읽기 → hold 해제 → version 삭제를 모두 성공해야 한다. bucket 설정을 읽는 API 기동 검사만으로 쓰기·hold·삭제 권한을 대신 증명하지 않는다.

## 자주 막히는 곳

기본 retention은 scratch 삭제와 checkpoint GC를 막는다. 암호화·versioning·Object Lock 중 하나가 없으면 API가 기동을 거부한다. allowlist endpoint가 다르면 worker가 checkpoint를 저장하지 못한다.

## 되돌리기

기존 운영 bucket을 삭제하거나 hold를 일괄 해제하지 않는다. 이번에 만든 빈 시험 bucket만 객체 version과 delete marker가 없음을 확인하고 조직의 저장소 정리 절차로 제거한다. 보존 데이터가 있으면 [복원 훈련](/run-server/self-hosting/backup-and-restore)을 먼저 수행한다.
