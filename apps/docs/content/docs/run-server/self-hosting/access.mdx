## 무엇을 하게 되나

원격 bootstrap 전에 SSH tunnel 또는 TLS·제한된 네트워크의 접속 경로를 구성하고 콘솔·API·SSE를 확인한다. Slack을 연결하면 Slack 경로만 여는 공개 입구도 구성한다.

## 준비물

서버 설치, SSH 권한 또는 조직의 TLS 인증서·VPN/IP allowlist가 필요하다. PostgreSQL과 Docker socket을 외부에 열지 않는다. 사설 CA는 클라이언트가 신뢰해야 하며 curl의 `-k`로 우회하지 않는다.

## 단계

### Compose: SSH tunnel

```bash
ssh -N -L 3000:127.0.0.1:3000 <user>@<server>
```

이 터미널을 유지하고 다른 터미널/브라우저에서 `http://127.0.0.1:3000`으로 접속한다.

### Compose: TLS reverse proxy

API(기본 3000)와 PostgreSQL(기본 5432)은 호스트 loopback에만 열린다. 사용자는 SSH tunnel로 들어오고, PostgreSQL은 운영자가 서버 안에서만 쓴다. 방화벽은 SSH와 선택한 TLS endpoint만 허용한다.

내부 DNS 이름으로 API를 내보내려면 reverse proxy를 앞에 둔다. upstream은 계속 `127.0.0.1:3000`이다. 접속 주소는 VPN 대역이나 IP allowlist로 좁히고, TLS 연결은 proxy에서 처리한다. proxy는 브라우저가 보낸 `Host`를 그대로 upstream에 넘긴다. API는 상태를 바꾸는 브라우저 요청에서 `Origin`의 host와 `Host`가 다르면 거부하므로, upstream host로 바꿔 넘기면 웹 콘솔의 변경 요청이 실패한다. 이벤트 스트림(SSE)은 연결을 오래 유지하므로 `proxy_buffering`과 요청 buffering을 끄고 read, send timeout을 1시간처럼 길게 둔다. 어떤 경로를 택해도 PostgreSQL과 Docker socket은 proxy나 방화벽 밖으로 열지 않는다. Docker socket은 scheduler가 worker를 관리할 때만 쓰며 호스트 TCP socket을 켜지 않는다.

인증서 경로, 내부 DNS 이름, 허용 대역은 조직 환경 값으로 정한다. 같은 서버의 시험 요청도 허용하려면 loopback을 명시한다. `Host`와 브라우저 `Origin`을 일치시키고 SSE buffering을 끈다. 설정 예는 아래 [공개 입구](#공개-입구-slack-경로만-열기) 절의 콘솔 입구 `server` 블록이다.

### 공개 입구: Slack 경로만 열기

Slack 이벤트와 버튼·창(interaction)을 받으려면 Slack이 닿는 공개 https 입구가 필요하다. Slack이 부르는 주소는 `POST /v1/slack/events/{agent_id}`와 `POST /v1/slack/interactions/{agent_id}` 둘뿐이고, 둘 다 cookie나 API key 대신 그 에이전트 앱의 signing secret 서명을 확인한다. 공개 입구는 이 두 경로만 api로 보내고 나머지는 proxy에서 404로 답한다. Slack 앱 설치와 계정 연결의 OAuth redirect는 콘솔 주소(`CONSOLE_ORIGIN`)로 브라우저가 돌아오므로 공개 입구에 열지 않는다.

api의 3000번 포트에는 콘솔과 `/v1` API 말고도 worker용 `/internal`이 있다. 터널이나 proxy로 3000을 통째로 공개하면 `/internal`까지 인터넷에 열린다. 그래서 공개 입구(Slack 경로만)와 콘솔 입구(VPN·IP allowlist 안)를 다른 DNS 이름으로 나누고, 콘솔 입구에서도 `/internal`을 막는다. Bun은 백슬래시를 `/`로 바꿔 `/internal` 규칙을 비켜 가게 하므로, 어떤 proxy를 쓰든 경로에 `\`나 `%5C`가 든 요청은 400으로 막는다.

아래는 Compose 서버에서 nginx로 두 입구를 나눈 예다. `<hooks-host>`는 공개 DNS 이름, `<console-host>`는 `CONSOLE_ORIGIN`의 host, `<allowed-cidr>`는 콘솔에 들어올 수 있는 대역이다. 인증서 경로는 조직의 값을 쓴다.

```nginx
# Public entry: only the two request URLs Slack calls reach the API.
server {
    listen 443 ssl;
    server_name <hooks-host>;
    ssl_certificate     <certificate-path>;
    ssl_certificate_key <certificate-key-path>;

    location ~ "^/v1/slack/(events|interactions)/[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$" {
        limit_except POST { deny all; }
        proxy_pass http://127.0.0.1:3000$uri;
        proxy_set_header Host $http_host;
    }

    location / {
        return 404;
    }
}

# Console entry: allowlisted networks only, /internal never forwarded.
server {
    listen 443 ssl;
    server_name <console-host>;
    ssl_certificate     <certificate-path>;
    ssl_certificate_key <certificate-key-path>;

    allow <allowed-cidr>;
    allow 127.0.0.1;
    deny all;

    if ($request_uri ~* "\\\\|%5c") {
        return 400;
    }

    location ^~ /internal {
        return 404;
    }

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $http_host;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_buffering off;
        proxy_request_buffering off;
        proxy_read_timeout 1h;
        proxy_send_timeout 1h;
    }
}
```

- 공개 입구의 `location`은 nginx가 디코드·정리한 경로가 Slack 경로 둘 중 하나에 `agent_id`(소문자 UUID)가 붙은 꼴일 때만 맞는다. api에는 원래 요청 줄이 아니라 그 정리한 경로(`$uri`)를 넘기므로, `..`이나 백슬래시를 섞어도 api에 닿는 것은 Slack 경로뿐이다. 나머지는 404, POST가 아닌 요청은 403이다. query는 넘기지 않는다. Slack에 보내는 주소에는 query가 없다.
- 콘솔 입구는 `/internal`과 그 아래를 404로 답한다. nginx는 `/%69nternal/x`처럼 인코딩한 경로와 `/x/../internal/x`를 디코드·정리한 뒤 `location`을 고르므로 이 경로도 404다. 백슬래시는 nginx가 경로 구분자로 보지 않지만, api 앞의 Bun은 `/`로 바꿔 `/x/..\internal/x`를 `/internal/x`로 만든다. 그래서 요청 줄에 `\`나 `%5C`가 있으면 400으로 거절한다.
- `Host`는 `$http_host`로 브라우저가 보낸 값을 포트까지 그대로 넘긴다. `$host`는 포트를 떼므로 443이 아닌 포트로 콘솔을 열면 변경 요청이 `Origin`과 맞지 않아 거부된다.
- 이벤트 스트림(SSE)이 지나는 콘솔 입구는 buffering을 끄고 read·send timeout을 1시간으로 둔다.

공개 입구의 DNS 이름이 콘솔과 다르면 owner가 **설정 > 연동 > Slack**의 "이벤트 입구 주소"에 `https://<hooks-host>`를 저장한다(`PUT /v1/slack-settings`). 저장한 주소의 경로 prefix는 Slack에 보내는 URL에도 붙는데, 위 예는 prefix를 떼지 않으므로 host만 저장한다. 저장 전에 만든 에이전트 앱은 그 에이전트 Slack 탭의 **다시 확인**으로 새 주소를 보낸다.

터널(예: Cloudflare Tunnel)로 공개 입구를 만들 때도 규칙은 같다. 공개 hostname에는 Slack 경로 둘만 `http://127.0.0.1:3000`으로 보내고 나머지는 404로 답하게 두며, 콘솔은 다른 hostname과 접근 제한 뒤에 둔다. 경로를 어떻게 정리하는지는 터널 제품마다 다르므로 규칙을 쓴 뒤 아래 확인을 공개 주소로 돌린다.

```bash
for p in /v1/slack/events/00000000-0000-0000-0000-000000000000 /v1/auth/login-methods / /internal/x /%69nternal/x /x/../internal/x '/x/..\internal/x'; do
  curl -s --path-as-is -o /dev/null -X POST -w "$p %{http_code} %{content_type}\n" "https://<hooks-host>$p"
done
```

첫 줄만 api의 응답(서명이 없으므로 4xx, `application/json`)이고 나머지는 모두 proxy의 404다(nginx는 `text/html`). 다른 줄에 `application/json`이 오면 그 경로가 api에 닿은 것이므로 공개 입구를 내리고 규칙을 고친다. 콘솔 입구는 [확인](#확인)의 반복문을 `<console-host>`로 돌린다. 위 nginx 예에서는 백슬래시가 든 두 줄이 400, 나머지가 404이고 어느 줄도 `application/json`이 아니다.

### Kubernetes: 내부망 ALB

`values-aws.example.yaml`을 설치별 파일로 복사해 placeholder(account id, ARN, host, digest)를 채우고, `values.yaml` 위에 얹는다. 아래 render는 로컬에서 돌지만, 그 결과를 적용하는 일은 **AWS 전용**이다.

**AWS 예제는 내부망 전용 ALB를 전제로 한다.** 그래서 예제의 Ingress annotation `scheme`은 이미 `internal`이다. 설치별 파일에서도 `internet-facing`으로 바꾸지 않는다. `render-check`가 예제 render에서 `internet-facing`을 거부한다. 적용 뒤에는 ALB가 내부망 subnet에 생겼는지 확인한다(**AWS 전용**).

### 웹 콘솔과 `/internal`

웹 콘솔은 api가 3000번에서 서빙한다. `ingress.console.enabled: true`(기본 `false`)면 Ingress가 `/`(Prefix)를 api Service로 보낸다. 같은 포트에 worker용 `/internal`도 있고, `/` Prefix는 `/internal`까지 맞는다. 그래서 chart는 `/` 앞에 `/internal`(Prefix) 규칙을 두고, 그 규칙은 api가 아니라 annotation `alb.ingress.kubernetes.io/actions.block-internal`의 fixed-response(404, `text/plain`)로 보낸다. AWS Load Balancer Controller는 긴 Prefix를 짧은 Prefix보다 먼저 평가하므로 `/internal`과 그 아래 경로는 ALB가 404로 답한다. `render-check`가 이 규칙이 `/`보다 앞에 있는지, 404 action을 가리키는지, 나머지 경로가 api Service의 `http`(3000) 포트로 가는지 검사한다.

이 규칙은 ALB에서만 효과가 있다. 다른 controller는 `block-internal`이라는 Service가 없는 경로를 건너뛰고 `/`로 `/internal`을 열 수 있으므로, `ingress.className`이 `alb`가 아니면 chart가 render를 거부한다. `/internal` 요청을 404 규칙 밖으로 보낼 수 있는 annotation(`alb.ingress.kubernetes.io/`의 `actions.*`·`conditions.*`·`transforms.*`·`group.*`, `kubernetes.io/ingress.class`)이 `ingress.annotations`에 있어도 render를 거부한다. IngressClass의 `IngressClassParams`가 이 Ingress를 다른 Ingress와 같은 group에 넣으면 앞선 Ingress의 규칙이 먼저 평가되므로, 콘솔을 켤 때는 `alb` IngressClass가 group을 강제하지 않는지 확인한다(**AWS 전용**).

**켜는 조건.** api는 percent-encoding을 디코드한 경로로 route한다. ALB path pattern에는 `%`를 쓸 수 없으므로 `/%69nternal/…`처럼 인코딩한 경로는 `/internal` 규칙에 걸리지 않고 `/` 규칙을 타고 api에 닿는다. api는 디코드하지 않은 경로가 `/internal`로 시작할 때만 worker 라우트로 보내고, 인코딩한 변형에는 404 `NOT_FOUND`로 답한다. 이 동작이 들어간 api 이미지를 쓸 때만 `ingress.console.enabled`를 켠다.

dot segment(`/x/../internal/…`, `/%2e/internal/…`)와 역슬래시(`/internal\…`, `/x/..\internal/…`)는 Bun이 요청을 api에 넘기기 전에 `/internal/…`로 정리하므로, api는 이 경로를 그냥 `/internal/…`과 구분하지 못한다. 이 경로를 막는 것은 ALB다. ALB는 URI를 정규화한 뒤 규칙을 평가하지만, 문서에는 무엇을 정규화하는지 나와 있지 않다. 그래서 콘솔을 켠 뒤에는 내부망에서 아래 요청을 보내 확인한다(**AWS 전용**). `/%69nternal/x`는 api의 404(`application/json`)가 기대값이다(ALB가 이것까지 정규화해 `text/plain` 404로 답해도 안전하다). 나머지 경로는 모두 ALB의 404(`text/plain`)가 기대값이다. api의 `/internal` 라우트는 상태와 상관없이 `application/json`으로 답한다. 그래서 dot segment나 역슬래시 경로에 `application/json` 응답이 오면 ALB가 그 경로를 api로 보낸 것이므로 콘솔을 다시 끈다(ALB가 400 같은 자기 오류로 거절하는 것은 안전하다).

```bash
for p in /internal/x /%69nternal/x /x/../internal/x /%2e/internal/x '/internal\x' '/x/..\internal/x'; do
  curl -s --path-as-is -o /dev/null -w "$p %{http_code} %{content_type}\n" "https://<host>$p"
done
```

켤 때는 설치별 파일에 다음을 둔다. 끄면 `/`와 `/internal` 규칙이 함께 빠지고 `/v1`·`/docs`·`/healthz`·`/readyz`는 그대로다.

```yaml
ingress:
  className: alb
  console:
    enabled: true
```

적용 뒤 내부망에서 확인한다(**AWS 전용**). `curl -s -o /dev/null -w '%{http_code}\n' https://<host>/`는 200이다. `curl -si -X POST https://<host>/internal/worker/x`는 404이고, 응답 헤더가 `content-type: text/plain`이며 api가 붙이는 `x-request-id`가 없어야 한다. api의 404는 `application/json`에 `x-request-id`가 붙으므로, 상태 코드만으로는 ALB가 막았는지 알 수 없다.

```bash
helm lint deploy/helm/werft -f deploy/helm/werft/values-aws.example.yaml   # render only
helm template werft deploy/helm/werft \
  -f deploy/helm/werft/values-aws.example.yaml >/dev/null                          # render only
helm upgrade --install werft deploy/helm/werft \
  --namespace werft -f values-aws-<installation>.yaml --timeout 10m               # requires AWS resources
```

## 확인

```bash
for p in /internal/x /%69nternal/x /x/../internal/x /%2e/internal/x '/internal\x' '/x/..\internal/x'; do
  curl -s --path-as-is -o /dev/null -w "$p %{http_code} %{content_type}\n" "https://<host>$p"
done
```

선택한 경로에서 `/readyz`, `/docs`, `/docs/scalar.js`와 콘솔을 확인한다. 인증한 이벤트 스트림은 `curl -sSN --max-time 5`로 내용이 오는지 보고, 제한 시간 종료는 지속 연결을 관찰한 결과와 구분한다. allowlist 밖에서는 차단돼야 한다. 로그인 cookie와 변경 요청의 Origin 검사도 확인한다. 실제 내부 DNS·VPN·AWS ALB 경로는 이 문서의 로컬 확인으로 증명되지 않는다.

## 자주 막히는 곳

TLS 인증서가 신뢰되지 않으면 브라우저가 연결을 차단한다. Host를 upstream 값으로 바꾸면 콘솔 변경 요청이 거부된다. ALB 정규화 시험에서 내부 경로가 API로 전달되면 콘솔 Ingress를 즉시 끈다.

## 되돌리기

터널은 그 터미널에서 종료한다. reverse proxy의 이번 설정을 백업본으로 되돌린다. 공개 입구는 그 `server` 블록(또는 터널 규칙)을 지운다. 그 뒤로는 Slack 이벤트가 들어오지 않는다. Kubernetes는 설치별 values의 `ingress.console.enabled`를 false로 되돌려 적용하고 `/internal`과 authorizer가 외부에 열리지 않았는지 확인한다.
