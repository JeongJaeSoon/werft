## 무엇을 하게 되나

첫 owner와 workspace를 만들고 사용자별 API key를 발급한다. API key 폐기와 세션 실행 권한 회수를 구분한다.

## 준비물

[설치](/run-server/self-hosting)와 [접속 경로](/run-server/self-hosting/access)가 준비돼 있어야 한다. 설정 링크는 운영자만 받아 다룬다.

## 단계

### 1. 첫 owner 만들기

운영자가 설치 쪽 명령으로 첫 owner의 일회용 설정 링크를 파일로 받는다. 명령은 api 이미지 안에 있고, owner가 될 사람의 이메일 주소만 받는다. 비밀번호는 명령 인자나 환경 변수로 주지 않고, 링크를 연 사람이 정한다. 링크는 화면에 나오지 않는다. 화면에는 파일 경로와 만료 시각만 나온다.

test-ops 단일 서버에서는 호스트의 새 파일에 바로 받는다. `DEPLOYMENT_DIR`는 [단일 서버 설치](/run-server/self-hosting/single-server)에서 정한 설치별 디렉터리이고, 번들 디렉터리 안은 거절된다.

```bash
scripts/test-ops.sh setup-link --email <owner-email> --out "$DEPLOYMENT_DIR/owner-link.json"
```

그 밖의 compose 구성에서는 api 컨테이너 안에 파일을 만든 뒤 호스트로 옮기고 컨테이너 쪽 파일을 지운다.

```bash
docker compose --profile apps exec -T api \
  bun run apps/control-host/src/main.ts admin bootstrap-owner \
  --email <owner-email> --out /tmp/owner-link.json
(umask 077 && set -C && docker compose --profile apps exec -T api cat /tmp/owner-link.json >owner-link.json)
docker compose --profile apps exec -T api rm -f /tmp/owner-link.json
```

Kubernetes에서는 먼저 [설치의 context·namespace·fullname 확인](/run-server/self-hosting/kubernetes#준비물)을 따른다. 아래 `werft`는 그 예시 설치 이름이다. 세 명령이 같은 Pod에 닿도록 Pod 하나를 먼저 고른다.

```bash
POD="$(kubectl -n werft get pod -l app.kubernetes.io/instance=werft,app.kubernetes.io/component=api -o name | head -n 1)"
kubectl -n werft exec "$POD" -c api -- \
  bun run apps/control-host/src/main.ts admin bootstrap-owner \
  --email <owner-email> --out /tmp/owner-link.json
(umask 077 && set -C && kubectl -n werft exec "$POD" -c api -- cat /tmp/owner-link.json >owner-link.json)
kubectl -n werft exec "$POD" -c api -- rm -f /tmp/owner-link.json
```

파일은 0600으로 새로 만들어지고, 같은 이름의 파일이 있으면 명령은 덮어쓰지 않고 거절한다. 파일에는 [구성원 초대](/members#api-응답)의 응답과 같은 칸이 JSON으로 들어 있다.

| 칸 | 내용 |
| --- | --- |
| `accept_path` | 설정 화면의 경로. `/bootstrap#setup=<setup_token>` 꼴이다 |
| `accept_url` | `CONSOLE_ORIGIN` 뒤에 `accept_path`를 붙인 링크. `CONSOLE_ORIGIN`이 없으면 `null`이다 |
| `expires_at` | 만료 시각 |

브라우저가 있으면 `accept_url`(없으면 콘솔 origin 바로 뒤에 `accept_path`)을 열고 owner 정보와 workspace 이름을 넣는다. 브라우저가 없으면 `#setup=` 뒤의 값을 `setup_token`으로 삼아 `POST /v1/auth/bootstrap`에 owner 정보와 함께 보낸다. 요청 본문은 설치가 서빙하는 API 레퍼런스(`/docs`)에 있다. 어느 쪽이든 이메일 주소는 명령에 준 주소여야 한다. 다른 주소는 `403`으로 거절되고 링크는 그대로 남는다. 그다음 `/login`으로 로그인하고, 링크 파일은 지운다.

링크는 한 번 쓰면 바로 무효이고 24시간 뒤 만료된다. 다시 실행하면 앞 링크는 무효가 되고 새 링크가 나온다. owner가 있으면 명령은 링크도 파일도 만들지 않고 종료 코드 1로 끝난다. 명령을 실행할 때마다 api 컨테이너 로그(`docker compose logs api`, `kubectl logs`)에 `setup_link_issued` 한 줄이 남는다. 그 줄에는 링크 id, 이메일 주소, 만료 시각만 있고 토큰과 링크는 없다. 링크로 첫 workspace가 만들어지면 그 workspace의 첫 receipt(`bootstrap_owner`)가 쓴 링크의 id와 만든 시각을 남긴다.

### 2. 사용자별 key 발급

```bash
KEY="$(scripts/test-ops.sh key create <owner_id> \
  --scopes sessions:read,sessions:write,sessions:approve,sessions:control,sessions:recover)"
```

`<owner_id>`는 이 key의 세션을 묶는 이름이다. 사용자마다 다른 값을 정한다. 웹 콘솔 계정과는 별개이며, workspace id는 쓰지 않는다.

SDK와 HTTP API는 이 서버 주소와 key로 붙는다([SDK 설치](/getting-started/install)).

Kubernetes에서는 다음을 사용한다.

먼저 [설치의 context·namespace·fullname 확인](/run-server/self-hosting/kubernetes#준비물)을 따른다. 아래 `werft`는 그 예시 설치 이름이다.

```bash
kubectl -n werft exec deploy/werft-api -c api -- \
  bun run apps/control-host/src/api/keys.ts create <owner_id> \
  --scopes sessions:read,sessions:write,sessions:approve,sessions:control,sessions:recover
```

stdout에 평문 key가 한 번만 나오고 stderr에는 key id가 나온다. 평문은 공개 로그에 저장하지 않고 해당 사용자에게 안전하게 전달한다. 사용자별 key 소유자 식별자와 웹 콘솔 계정은 별개다. API key의 scope를 작업에 필요한 범위로 줄인다.

### 3. 폐기 연락과 실행 권한

사용자에게 key를 폐기할 연락 경로를 전달한다. checkout의 운영자 CLI는 다음과 같다.

```bash
scripts/test-ops.sh key revoke <key_id>
API_CONTAINER='<api-container-id-from-this-installation>'
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/grants.ts revoke <session_id> --reason <text>
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/grants.ts restore <session_id> --reason <text>
```

API_CONTAINER는 이 설치의 status와 Docker project label로 확인한 API 컨테이너 id로 바꾼다. Kubernetes에서는 설치 버전의 저장소 checkout과 호스트 Bun·kubectl을 준비하고 `keys:k8s`와 `grants:k8s`를 사용한다. `NAMESPACE`와 `RELEASE`의 기본값은 둘 다 werft다.

| 작업 | 효과 |
| --- | --- |
| key revoke | 그 key의 후속 API 인증을 막는다. 이미 시작한 세션 실행을 중지하는 명령이 아니다 |
| grants revoke | 지정한 세션의 실행 권한과 자격 증명을 회수하고 실행 종료를 요청한다 |
| grants restore | execution 부재가 확인된 뒤 실행 권한을 복원한다. 폐기한 API key를 되살리지 않는다 |

### 4. 개인 key

`keys create <owner_id>`로 만든 key는 운영자 key다. 웹 콘솔의 workspace 밖에서 그 owner를 묶음으로 쓴다. 멤버가 웹에서 만든 세션을 API에서도 같은 목록으로 보려면 그 멤버의 개인 key를 만든다.

```bash
scripts/test-ops.sh key create --workspace <workspace_id> --personal <user_id> \
  --scopes sessions:read,sessions:write
```

- 개인 key는 key의 scope와 만든 사람의 지금 역할이 허용하는 scope의 교집합만 갖는다. 그 사람의 계정이나 membership이 비활성이 되면 다음 요청부터 `401`이다.
- API key는 scope와 관계없이 관리 동작(멤버 관리, 세션 인수, key 발급)을 하지 못한다(`403`). 관리 동작은 사람의 로그인 세션으로 한다.
- 개인 key와 에이전트 key는 그 key가 시작한 세션의 승인 요청에 답하지 못한다(`403`, `reason_code: self_approval`).

### 5. 멤버 내보내기와 인수

owner나 admin이 로그인 세션으로 `POST /v1/members/{user_id}/disable`(본문 `{}` 또는 `{"reason": "…"}`)을 부른다. owner는 owner만 비활성으로 만들 수 있고(`403 OWNER_PROTECTED`), 자기 자신은 비활성으로 만들 수 없고(`403 SELF_PROTECTED`), 마지막 owner도 비활성으로 만들 수 없다(`409 LAST_OWNER`).

- 한 번에 membership을 비활성으로 만들고, 그 사람의 로그인 세션 전부와 그 workspace의 개인 key를 폐기하고, 연결된 Slack 계정을 회수한다. 에이전트 key는 건드리지 않는다.
- 그 사람이 요청한 닫히지 않은 세션은 인수 대기가 된다. 돌던 turn까지만 마치고, 새 메시지는 `409 TAKEOVER_REQUIRED`로 거절된다. owner가 `GET /v1/takeovers`로 목록을 보고 `POST /v1/sessions/{id}/takeover`로 인수하면 그 owner가 요청자가 된다.
- `POST /v1/members/{user_id}/enable`은 membership만 되살린다. 폐기한 로그인 세션, 개인 key, Slack 연결은 돌아오지 않으므로 다시 로그인하고 key를 새로 받는다. 아직 인수하지 않은 세션은 그 사람에게 돌아간다.
- 계정 전체를 막으려면 `POST /v1/users/{user_id}/disable`·`/enable`을 쓴다. 대상이 호출한 사람이 owner나 admin인 workspace에만 속할 때 허용된다.
- 외부 디렉터리(SCIM)와 동기화하지 않는다. 사내 SSO에서 사람을 내보내도 여기에는 반영되지 않으므로 이 API를 따로 부른다.

### 6. 감사 기록과 보존 기간

권한 판정은 거절과, 관리 동작·승인·Slack 입력의 허용을 감사 기록으로 남긴다. 기록은 고칠 수 없다. 행의 `request_id`는 응답의 `X-Request-Id`이고, 그 요청이 남긴 receipt와 같다.

- **읽기.** owner는 콘솔의 설정 > 워크스페이스 > 감사 기록에서 기간·종류·사람으로 거르고, 같은 요청의 행을 이어 보고, NDJSON 파일로 내보낸다. 같은 내용을 로그인 세션으로 `GET /v1/audit/events`(`limit` 기본 50, 최대 200)로 읽는다. admin·member와 API key는 `403`이다.
- **내보내기.** `Accept: application/x-ndjson`을 주면 거른 행 전체를 한 줄씩 보내고, 마지막 줄은 `{"kind":"end",…}`이다. 한 번에 100,000행까지이고, 넘으면 끝 줄의 `next_cursor`로 이어 받는다. API 프로세스마다 한 workspace에 동시에 하나만 돌고(같은 프로세스의 둘째는 `429`), 10분이 지나면 끊는다. 끝 줄이 없는 파일은 완전하지 않으므로 받은 마지막 줄의 `cursor`로 다시 부른다.
- **보존 기간.** 기본 90일이다. owner가 로그인 세션으로 `POST /v1/workspaces/{id}/audit-retention`(`{"audit_retention_days": …}`, 30~3650)으로 바꾼다. 지금 값은 `GET /v1/auth/me`의 `workspace.settings`에 있다. 기간이 지난 판정 행은 reconciler가 지운다. receipt는 지우지 않지만 감사 기록에는 보존 기간 안의 것만 나온다.

### 7. 공유 범위 밖의 세션

owner·admin에게도 공유 범위 밖 세션은 목록·상세·turn에 보이지 않는다(`404`). 그런 세션은 아래 길로만 다룬다. 사유(`justification`, 1000자까지)는 판정 기록에 남는다.

- **관리 목록.** `GET /v1/admin/sessions`는 owner·admin이 범위와 관계없이 workspace의 세션을 최근 것부터 본다. 항목은 만든 사람, agent release, 상태, 공유 범위 같은 메타데이터뿐이고 메시지·제목·요약은 없다.
- **감사 열람.** `POST /v1/sessions/{id}/audit-read`(`{"justification": "…"}`)는 세션 상세와 turn 한 페이지(`cursor`·`limit`)를 돌려주고, 읽을 때마다 감사 기록이 하나 남는다. 읽기만 하므로 그 뒤에도 메시지·응답·종료는 `404`다.
- **관리 종료.** `POST /v1/admin/sessions/{id}/terminate`(`{"expected_revision": …, "justification": "…"}`)는 owner·admin이 범위와 관계없이 세션을 멈춘다. 사유가 stop 이유가 된다.
- **관리 복구.** `POST /v1/admin/sessions/{id}/recovery-decisions`는 owner만 범위와 관계없이 복구 결정을 내린다. 본문은 [세션 복구](/run-server/self-hosting/recover-sessions)의 복구 결정과 같고, 그 `reason`이 사유다.
- **인수.** 나간 멤버의 세션이 인수하는 사람에게 보이지 않는 범위면 `POST /v1/sessions/{id}/takeover`에 `{"justification": "…"}`를 준다. 없으면 `403`(`reason_code: justification_required`)이다.
- **비공개 채널 세션의 인수.** `private_channel` 세션은 그 채널의 지금 멤버이고 세션에 쓸 수 있는 사람이 같은 경로로 인수하고, 사유는 받지 않는다. owner·admin도 채널 멤버가 아니면 `404`다.

## 확인

각 사용자의 key로 `/v1/sessions`를 읽으면 허용 범위의 응답이 와야 하고, key 없이 요청하면 401이어야 한다. 폐기한 key는 인증되지 않아야 한다. grants 출력의 receipt와 execution 상태를 확인하여 수락과 실제 종료를 구분한다.

## 자주 막히는 곳

링크가 "이 설정 링크는 쓸 수 없습니다"로 열리면 이미 썼거나, 24시간이 지났거나, 명령을 다시 실행해 바뀐 것이다. owner가 없으면 명령을 다시 실행해 새 링크를 받는다. CLI의 owner id에 workspace id를 넣지 않는다.

## 되돌리기

이미 만든 첫 owner를 지우기 위해 설치를 reset하지 않는다. 잘못 발급한 key를 revoke하고 올바른 scope로 새 key를 만든다. grants restore는 옛 실행이 사라진 뒤에만 한다.
