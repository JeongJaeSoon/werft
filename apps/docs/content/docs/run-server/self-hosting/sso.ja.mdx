## 作業内容

会社の IdP（Google Workspace、OneLogin、Microsoft Entra ID、Okta、Keycloak などの OpenID Connect プロバイダー）でコンソールにログインできるようにします。プロバイダーを追加し、テストログインで確認し、オンにします。誰が参加できるかを決め、必要ならパスワードログインを閉じます。

werft のログイン方法は二つです。

| 方法 | 説明 |
| --- | --- |
| パスワード | メールアドレスとパスワード。最初の owner は必ずパスワードで作成します。設置全体で閉じられ、閉じても緊急管理者一人はパスワードでログインします |
| OIDC プロバイダー | owner がコンソールで登録した IdP。プロバイダーは複数置けますが、issuer ごとに一つです |

知っておくルール:

- プロバイダーの設定はコンソールの画面でだけ行います。SSO 用の環境変数はありません。プロバイダーと client secret は DB に保存されます。
- 人はプロバイダーの `(issuer, subject)` で見つけます。メールアドレスで既存アカウントに自動で結び付けることはしません。同じアドレスのアカウントがすでにあれば、その人がログインしてから自分で接続するか、招待リンクで参加します。
- プロバイダーをオフにすると、そのプロバイダーでログインしたセッションはその場で切れます。
- IdP のグループをロールに移す機能、SCIM 同期、SAML、IdP 側のログアウトの伝播はありません。IdP で人を削除しても werft のセッションとアカウントは残るので、[メンバーを無効化](#되돌리기)します。

この機能は `v0.1.3` の次のリリースに含まれます。`v0.1.3` までは Google ログインだけを環境変数でオンにできました。その設置をアップグレードするなら、先に[環境変数の Google ログインからの移行](#9-환경-변수-google-로그인에서-옮기기)を読んでください。

<a id="준비물" />
## 準備

| 何 | なぜ |
| --- | --- |
| owner アカウント | プロバイダーの画面は owner だけが開けます。admin と member には見えません |
| `CONSOLE_ORIGIN` | 人がブラウザーでコンソールを開く公開アドレス（`scheme://host[:port]`）。プロバイダーに登録する redirect URI はこの値から作ります。ないとプロバイダーを作成できません。単一サーバーは [env ファイル](/run-server/self-hosting/single-server#2-비밀과-설정-문서)に、Kubernetes は values の `api.extraEnv` に置きます |
| `PLATFORM_SECRET_KEY` | 設置にすでにある値です。client secret はこのキーで封印して保存します。変えたり失ったりすると、保存した secret を読めなくなります |
| `https` アドレスの IdP | issuer と IdP のすべての endpoint は `https` でなければなりません。`http` は IdP と `CONSOLE_ORIGIN` がどちらも `localhost` または `127.0.0.1` のときだけ受け付けます（ローカルの試用向け） |
| API から IdP への経路 | API サーバーが IdP の discovery・token・JWKS・UserInfo のアドレスに直接リクエストします。プライベートアドレスの IdP も使えます。link-local（`169.254.0.0/16` など）に解決される名前は拒否します |
| IdP の管理者権限 | IdP にアプリ（client）を作成し、redirect URI を登録できる必要があります |

コンソールは `CONSOLE_ORIGIN` と同じアドレスで開きます。ログインの流れの cookie は `__Host-` cookie なので、`https` か `localhost`・`127.0.0.1` でだけ残ります。別のホスト名で開いたコンソールでは、IdP から戻ったときにログインが拒否されます。

<a id="단계" />
## 手順

<a id="1-공급자-만들기" />
### 1. プロバイダーの作成

1. owner でログインし、**設定 > ワークスペース > ログイン**を開きます。
2. **プロバイダーを追加**を押し、**名前**と **Issuer** を入力します。名前はログイン画面のボタンの文字です（64 文字まで）。Issuer は IdP が示すアドレスを文字どおりに入力します。末尾の `/` も IdP の書き方に合わせます。
3. **作成**を押すと、サーバーがその場で IdP の設定ドキュメント（`<issuer>/.well-known/openid-configuration`）を読みます。問題があれば何も作らず、理由を表示します（[設定ドキュメントの問題](/run-server/self-hosting/reference/sso-providers#설정-문서의-문제)）。
4. 通ればオフのプロバイダーが作成され、詳細画面に移ります。状態は**下書き**です。

Issuer は作成後に変更できません。issuer が変わると全員の識別が変わるからです。別の issuer が必要なら新しいプロバイダーを作成します。同じ issuer のプロバイダーは一つだけ置けます。

<a id="2-idp에-앱-등록하기" />
### 2. IdP へのアプリ登録

詳細画面の**プロバイダーに登録する値**に二つあります。

| 画面 | 使う場所 |
| --- | --- |
| **Redirect URI** | `<CONSOLE_ORIGIN>/auth/callback/<provider-id>`。IdP アプリの redirect（callback）URI に文字どおり登録します。プロバイダーごとに異なります |
| **サーバーのリクエスト先** | ログインのときに API サーバーがリクエストを送る host。ファイアウォールや egress のルールがあれば、この host を開けます |

IdP で Web アプリケーション（confidential client、authorization code フロー）を作成し、この redirect URI を入力します。werft が要求する scope は `openid email profile` で固定です。werft は常に PKCE（S256）を送ります。client secret のない client（public client）には対応していません。IdP ごとに何を作り、どの値を持ち帰るかは[プロバイダーごとの値](/run-server/self-hosting/reference/sso-providers#공급자별-값)にあります。

<a id="3-client-값-넣기" />
### 3. client の値の入力

**Client** の区画に IdP から受け取った値を入れます。

1. **Client ID** の**変更**で client ID を入れ、**Client 認証方式**を選びます。`HTTP Basic (client_secret_basic)` と `POST ボディ (client_secret_post)` のうち、IdP アプリに設定した方式と同じものを選びます。初期値は IdP が示す方式のうち Basic、なければ POST です。
2. **Client secret** の**値を入力**に secret を貼り付けます。保存した値は二度と表示されず、末尾の四文字だけが残ります。

両方を入れると、状態は**テストが必要**になります。

<a id="4-테스트-로그인" />
### 4. テストログイン

**テストとオン**の区画の**テストログイン**を押します。ブラウザーは IdP のログイン画面に移って戻り、**テストログインの結果**を表示します。テストはアカウントもセッションも作りません。

| 結果の画面 | 意味 |
| --- | --- |
| Subject (sub) | IdP がこのアカウントに付けた識別子。werft は issuer とこの値で人を見つけます |
| メール、`email_verified` | IdP が送ったアドレスと検証の有無。IdP が送らなければ「送信なし」 |
| アドレスの証明 | werft がこのアドレスをこのアカウントのものと信じるかどうか。信じないアドレスでは、アカウントを探すことも参加させることもしません |
| このアカウントがログインすると | 今のルールでこのアカウントが実際にログインしたときの結果 |

失敗すると**理由コード**が表示されます。コードごとの原因と対処は[テストログインの理由コード](/run-server/self-hosting/reference/sso-providers#테스트-로그인의-이유-코드)にあります。テスト中に設定が変わると合格として記録しないので、もう一度テストします。

<a id="5-켜기" />
### 5. オンにする

テストが通ると状態は**オンにできます**になり、**オンにする**が使えるようになります。オンにすると、ログイン画面にプロバイダー名の入ったボタン（例: **Keycloak でログイン**）が表示されます。

| 状態 | 意味 |
| --- | --- |
| 下書き | client ID か client secret がありません |
| テストが必要 | 今の設定で通ったテストがありません。オフのプロバイダーの設定を変えるとこの状態に戻ります。オンのままルールを変えたプロバイダーも、オフにするとこの状態です |
| オンにできます | 通っていて、オフです |
| オン | ログイン画面にボタンが表示されます |
| オン · 新しい secret 待ち | オンで、新しく入れた client secret がテストを待っています |

<a id="6-누가-들어올-수-있나" />
### 6. 誰が入れるか

詳細画面の**誰が入れるか**で**ルールを変更**を押します。オンのプロバイダーにはすぐ適用されます。オフのプロバイダーは、変更後にもう一度テストを通さないとオンにできません。ルールも設定なので、オンのまま変えたプロバイダーを後でオフにすると、もう一度オンにするときにテストが必要です。

| ルール | 値 |
| --- | --- |
| **許可ドメイン** | メールのドメインがリストにあるアカウントだけがログインします。カンマか空白で区切って 50 個まで。空にすると制限しません。リストがあると、werft が信じるアドレスのないアカウントは拒否されます |
| **招待なしで参加** | **受け入れない**（既定）または **member として参加**。オンにすると、IdP がアドレスを証明した人は招待なしで member のアカウントが作られます |
| **検証済みメール** | **要求する**（既定）または**要求しない**。要求しないと、`email_verified` を送らない IdP のアカウントもログインします。そのアドレスは信じないので、そうしたアカウントは招待リンクでだけ参加します |

「アドレスの証明」は IdP が `email_verified: true` を送った場合です。Google ではさらに、アドレスが `gmail.com` であるか Workspace のドメイン（`hd`）と同じである必要があります。IdP が `email_verified: false` を送ったアカウントは、どの設定でもログインできません。

プロバイダーのボタンで入ってくるアカウントは、上からこの順で判定します。

1. 許可ドメインと**検証済みメール**のルールを先に見ます。合わなければ、すでに接続済みのアカウントでも拒否します。許可ドメインの外は `403`、検証のルールにかかると `401` です。
2. このプロバイダーのアカウントがすでに werft のユーザーに接続されている → そのユーザーでログインします。アカウントを探すときにメールは見ません。ユーザーかメンバーシップが無効なら拒否します。
3. 証明されたアドレスの werft アカウントがすでにある → 結び付けずに拒否します（`409 LOGIN_LINK_REQUIRED`）。その人は元の方法でログインし、[アカウントを接続](#8-계정-연결과-끊기)します。
4. 証明されたアドレス宛ての有効な招待がある → 招待のロールでアカウントを作ります。
5. **招待なしで参加**が **member として参加**で、アドレスが証明されている → member のアカウントを作ります。
6. それ以外は拒否します（`401`）。画面は理由を区別しません。

プロバイダーで作られたアカウントにはパスワードがありません。Google のプロバイダーは**検証済みメール**をオフにできず、許可ドメインなしで**招待なしで参加**をオンにできません。誰でも Google アカウントを作れるからです。

<a id="7-초대로-가입" />
### 7. 招待での参加

**メンバー**画面から送った招待リンクを開いた人には、オンのプロバイダーがあればそのボタンも表示されます。ボタンで参加すると、アカウントのメールは招待されたアドレスになり、ロールは招待のロールです。根拠は招待リンクなので、IdP が送ったアドレスは見ません。`email_verified` を送らない IdP の人はこの方法で参加します。

許可ドメインと**検証済みメール**は招待での参加にも適用されます。このプロバイダーのアカウントがすでに別のユーザーに接続されているか、招待アドレスのアカウントがすでにあれば、参加せず、招待も使いません。

<a id="8-계정-연결과-끊기" />
### 8. アカウントの接続と解除

すでにアカウントがある人は、ログインしてから**設定 > ログイン方法**でプロバイダーのアカウントを自分で接続します。

- **接続できるプロバイダー**の**接続**を押すと、IdP でログインして戻ります。IdP でログインしたアカウントが接続されます。メールアドレスが werft のアカウントと違っても構いません。そのプロバイダーの許可ドメインと**検証済みメール**のルールは接続にも適用されます。
- 接続と解除はログインから 10 分以内にだけできます。過ぎたらログアウトしてログインし直します。
- 一つのプロバイダーアカウントは一人のユーザーにだけ、一人のユーザーは一つのプロバイダーにアカウント一つだけを接続します。
- 使える方法が一つだけ残っているときは解除できません。オフのプロバイダーのアカウントは使える方法に数えません。
- パスワードを解除するとパスワードは消え、もう設定できません。
- 解除すると、その方法でログインしたセッションはすべて切れます。

<a id="9-환경-변수-google-로그인에서-옮기기" />
### 9. 環境変数の Google ログインからの移行

`GOOGLE_OIDC_*` 環境変数で Google ログインを使っていた設置では、古い設定は自動で移りません。アップグレードすると Google ログインはオフになり、ログイン画面にはパスワードだけが残ります。Google だけでログインしていた人は、owner がプロバイダーを登録し直すまで新しくログインできません。

1. 古いバージョンの API プロセスをすべて止めてから新しいバージョンを起動します。古いプロセスが残っていると、そのプロセスでの Google ログインは失敗します。
2. env ファイルや values から `GOOGLE_OIDC_CLIENT_ID`・`GOOGLE_OIDC_CLIENT_SECRET`・`GOOGLE_OIDC_REDIRECT_URI`・`GOOGLE_OIDC_ISSUER`・`GOOGLE_OIDC_ALLOWED_DOMAINS`・`GOOGLE_OIDC_JIT` を削除します。残っていても読みません。`CONSOLE_ORIGIN` がなければ追加します。
3. パスワードのある owner でログインし、[手順 1](#1-공급자-만들기) から Google をプロバイダーとして登録し直します。Issuer は `https://accounts.google.com` です。
4. Google Cloud コンソールの OAuth client で、承認済みのリダイレクト URI を画面の新しい redirect URI に置き換えます。古いアドレス（`…/auth/google/callback`）は削除します。同じ OAuth client を使い続けても構いません。
5. 古い `GOOGLE_OIDC_ALLOWED_DOMAINS`・`GOOGLE_OIDC_JIT` に入れていたルールを[手順 6](#6-누가-들어올-수-있나)で決め直し、テストして、オンにします。

以前 Google でログインしていた人は、同じ issuer（`https://accounts.google.com`）のプロバイダーがオンになれば、以前と同じ werft アカウントで入ります。人と Google アカウントの接続は DB に残っていて、Google は同じ Google アカウントに同じ `sub` を付けるからです。別の issuer で登録すると別の人として扱います。

Google の方法を持つ人は、アップグレード後に一度ログインし直します。アップグレード前に作られたセッションにはどの方法で作ったかの記録がないので、外部のログイン方法を持つ人のそうしたセッションは受け付けません。パスワードだけを使う人のセッションはそのままです。

<a id="10-비밀번호-로그인-닫기와-비상-관리자" />
### 10. パスワードログインを閉じることと緊急管理者

全員がプロバイダーでログインするようにするには、**設定 > ワークスペース > ログイン**の**パスワードログイン**の区画で**閉じる**を押します。閉じても**緊急管理者**一人はパスワードでログインします。プロバイダーが壊れたときに入るための道です。

緊急管理者は、有効でパスワードのある owner 一人です。新しい設置では最初の owner が、アップグレードした設置ではそうした owner のうちメンバーシップが最も古い人が、最初の緊急管理者です。そうした owner がいない設置では空です。**緊急管理者**の**変更**で別の owner を選びます。空にはできません。

閉じるには三つすべてを満たす必要があります。満たさないと、画面はボタンを止めて理由を示します。

| 条件 | 満たさないときの API の `details.reason_code` |
| --- | --- |
| オンのプロバイダーが一つ以上ある | `no_provider` |
| 緊急管理者が指定されていて、今もパスワードでログインできる | `no_emergency_admin` |
| 閉じる owner が緊急管理者であるか、オンのプロバイダーのアカウントを自分のログイン方法に接続している | `locks_out_actor` |

閉じると、緊急管理者を除く全員のパスワードセッションが切れます。閉じている間はこうなります。

| 動作 | 結果 |
| --- | --- |
| 緊急管理者以外の人のパスワードログイン | パスワードが正しくても、誤ったパスワードと同じ `401` |
| ログイン画面 | プロバイダーのボタンが先に表示され、パスワードの欄は**緊急管理者ログイン**を押すと表示されます |
| 招待の承諾 | パスワードの段階なしでプロバイダーのボタンだけが表示されます。パスワードでの承諾リクエストは `403`（`password_login_closed`） |
| 緊急管理者以外の人宛てに owner が API で発行するパスワード再設定リンク（コンソールにはこの画面がありません） | 発行は `409`（`password_login_closed`）、発行済みのリンクの使用は `401` |
| オンの最後のプロバイダーをオフにする | `409`（`last_provider`）。先にパスワードログインを開きます |

緊急管理者に指定された人は、無効化すること（メンバーシップ、アカウント）、owner でなくすること、そのパスワードを解除することができません（`409`、`emergency_admin`）。パスワードログインを閉じていない設置でも同じです。先に別の owner を緊急管理者に変えます。パスワードのある別の owner がいなければ、[ログインの復旧](/run-server/self-hosting/recover-sign-in)の `reset-password` で一人にパスワードを与えます。閉じている間に緊急管理者を変えると、前の緊急管理者のパスワードセッションが切れます。

<a id="확인" />
## 確認

- ログアウトしたブラウザーで `/login` を開くと、プロバイダー名の入ったログインボタンがあります。そのボタンで IdP にログインするとコンソールに戻ります。
- ログイン画面が使う公開 API が、オンのプロバイダーを示します。

```bash
curl -s "$CONSOLE_ORIGIN/v1/auth/login-methods"
```

期待する応答は `{"password":"on","providers":[{"id":"<provider-id>","display_name":"<name>"}]}` です。パスワードログインを閉じていれば、`password` は `emergency_only` です。

- プロバイダーの詳細画面の状態が**オン**で、**最後に通ったテスト**の時刻があります。

<a id="자주-막히는-곳" />
## よくある問題

| 症状 | 原因と対処 |
| --- | --- |
| 「コンソールの公開アドレス（CONSOLE_ORIGIN）が設定されていないため、プロバイダーを作成できません。」 | API に `CONSOLE_ORIGIN` がありません。追加して API を起動し直します |
| 作成時に「https ではないアドレスは使えません。」 | issuer か IdP の endpoint が `http` です。運用の設置では `https` の IdP だけを使います |
| 作成時に「設定ドキュメントの issuer が入力したアドレスと異なります。」 | issuer を IdP が示す文字どおりに入れていません（末尾の `/`、テナントの部分など）。[プロバイダーごとの値](/run-server/self-hosting/reference/sso-providers#공급자별-값)を見ます |
| IdP が「redirect URI が合わない」と拒否する | IdP アプリの redirect URI が画面の **Redirect URI** と違います。プロバイダーを削除して作り直すと id が変わり、アドレスも変わります |
| テストの理由コード `code_refused` | IdP の token endpoint が code の交換を拒否しました。client ID と client secret、**Client 認証方式**、IdP アプリの redirect URI が合っているか見ます。IdP 側のログに拒否の理由が残ります |
| ログイン画面「このアカウントでログインできませんでした」 | `401`。接続済みのアカウントも、招待も、参加ルールも合わないか、IdP の応答の検証に失敗しました。owner が同じアカウントでテストログインすると、「このアカウントがログインすると」と理由コードが表示されます |
| ログイン画面「このアカウントではログインできません」 | `403`。許可ドメインの外です |
| 「このメールアドレスのアカウントはすでに存在します」 | 同じアドレスのアカウントがあるので結び付けませんでした（`409 LOGIN_LINK_REQUIRED`）。その人が元々使っていた方法（パスワードか別のプロバイダー）でログインし、[アカウントを接続](#8-계정-연결과-끊기)します |
| **設定 > ログイン方法**で接続・解除が止められる | ログインから 10 分が過ぎています（`session_too_old`）。ログインし直します |
| IdP から戻ったのに拒否される | コンソールを `CONSOLE_ORIGIN` と違うホスト名で開きました。cookie が別の host に結び付いています |

理由コードの全体は [SSO プロバイダーごとの値と理由コード](/run-server/self-hosting/reference/sso-providers)にあります。ログインが壊れて誰も入れないときは[ログインの復旧](/run-server/self-hosting/recover-sign-in)に従います。

<a id="되돌리기" />
## 元に戻す

| やりたいこと | 方法 |
| --- | --- |
| プロバイダーを一時的に止める | 詳細画面の**オフにする**。ログイン画面から外れ、そのプロバイダーでログインしたセッションはすべて切れます。自分がそのプロバイダーでログインしていれば、自分のセッションも切れます。最後に通ったテストの後にルールを含む設定を変えていなければ、もう一度オンにするときにテストし直す必要はありません |
| オンのプロバイダーの client ID・認証方式・設定ドキュメントを変える | オフにし、変え、テストし、オンにします。名前と**誰が入れるか**のルールはオンのまま変えます |
| client secret を変える | オンのまま**値を変更**。新しい値は差し替え候補として入り、その値でテストログインが通ると使われます。それまでのログインは今の値を使います。候補を取り下げるには、今使っている値を入れ直します |
| プロバイダーをなくす | オフにしてから**削除**。設定と client secret が削除されます。人のアカウントと、そのプロバイダーのアカウントとの接続は残るので、同じ issuer で作り直すと同じ人として入ります |
| パスワードログインを開き直す | **パスワードログイン**の**開く**。パスワードのある人は再びパスワードでログインします |
| IdP で削除した人を外す | werft は IdP での削除を知りません。**メンバー**画面でその人を**無効化**すると、セッションと個人の key が廃止されます |

<a id="보안-참고" />
## セキュリティ上の注意

- client secret は DB の secret ストアに `PLATFORM_SECRET_KEY` で封印して保存します。画面と API は末尾の四文字と変更した時刻だけを返します。ログにも残しません。
- プロバイダーの作成、変更、secret の入力、テスト、オン、オフ、削除、パスワードログインを開くこと・閉じること、緊急管理者の変更、アカウントの接続・解除は、DB の `receipts` テーブルに監査記録を残します。記録の `operation` 名は[監査記録](/run-server/self-hosting/reference/sso-providers#감사-기록)にあります。
- プロバイダーをオフにすると、セッションの期限切れを待たずにそのプロバイダーのセッションが切れます。
- サーバーは IdP の署名鍵（JWKS）をログインのたびに読み直します。IdP が鍵をローテーションしたり削除したりすると、次のログインから従います。
- ログインは作成時に確認した endpoint だけを使います。IdP の endpoint が変わったら、プロバイダーをオフにして**設定ドキュメント**の**読み直す**を押します。
- `http` の IdP は、IdP と `CONSOLE_ORIGIN` がどちらも loopback のときだけ受け付けます。運用の設置では secret や code を平文で送りません。
