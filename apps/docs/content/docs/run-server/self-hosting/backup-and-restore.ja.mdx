<a id="무엇을-하게-되나" />
## 作業内容

ComposeのDBとcheckpoint objectをバックアップし、別project・新しい空bucketでpointerのversionを照合します。APIと実際のセッション再開は別の証拠として確認します。

<a id="준비물" />
## 準備

正常な設置、releaseと秘密鍵の別保管、十分な容量、writerを止める保守時間が必要です。バックアップはDB全体とAPI key hashを含むため権限0700、転送・保管時の暗号化を適用します。運用bucketへ復元しません。release bundleは `backup`・`reseed`・`restore-drill` を拒否するため、設置commitのcheckoutで実行します。

<a id="단계" />
## 手順

<a id="1-백업" />
### 1. バックアップする

```bash
scripts/test-ops.sh backup
```

api・scheduler・reconciler・workerを止め、DBとobjectを状態ディレクトリの `backups/backup-<timestamp>` にまとめてサービスを再開します。進行turnは中断され後で回収対象になり得るため先に確認します。失敗した `.failed` や未完成の `.partial` を成功本として使いません。保存が完了してもサービス再開に失敗するとコマンドは失敗します。

毎日利用の少ない時間と各更新直前に実行します。保管例はホスト14日、暗号化外部保管90日です。新しい成功本が26時間ない、non-zero終了、サービス再開失敗のいずれかで通知します。

<a id="2-별도-대상-복원" />
### 2. 別の対象へ復元する

S3は毎回新しい空の訓練bucketを準備します。元bucket、object versionやdelete markerがある対象は拒否されます。

```bash
# Restore a backup into a throwaway project and a new, empty bucket, then verify it
scripts/test-ops.sh restore-drill /var/lib/werft/test-ops/backups/backup-<timestamp> --bucket <drill-bucket> --port-base 25432
```

`--port-base` は訓練サービスの別開始ポートです。他の設置と重ならない値を選びます。LocalStack試験では `--bucket` を省きます。postgresとobject storeを復元し、すべてのcheckpoint pointerをversion単位で照合します。APIは起動しません。月1回と更新後の最初のバックアップで実施します。

バックアップに記録された migration の一覧は、今の checkout と完全に一致する必要があります。古いバックアップも、checkout が知らない migration を含むバックアップも終了コード 3 で拒否します。更新前に取ったバックアップを復元するには、そのバックアップを取った release の `source_commit` を checkout して復元・検証し、migration は別の手順で実行します。

### 3. checkpoint GC

バックアップと重ならない週次予定で先にdry-runします。

```bash
API_CONTAINER='<api-container-id-from-this-installation>'
docker exec -e CHECKPOINT_GC_DRY_RUN=1 "$API_CONTAINER" \
  bun run apps/control-host/src/api/checkpoint-gc.ts
```

API_CONTAINERを今回のstatusとproject labelで特定します。出力の保持・削除対象を確認してから、dry-run用の環境変数を外して実行します。既定Compose projectの他の設置を選ばないでください。Kubernetesはchartの `checkpointGc.schedule` を使います。

<a id="확인" />
## 確認

終了コードとstatus、実際に比較したcheckpoint数・version数・checksum結果を記録します。`nothing was compared` は空の照合で、データ復元の証拠ではありません。従来のLocalStack実行はobject 0・checkpoint 0行でした。AWS S3復元とAPIを起動した実セッション再開は未確認です。別の隔離環境で復元API・workerによる継続を確認する必要があります。

<a id="자주-막히는-곳" />
## よくある問題

対象が元bucketまたは空でなければ停止します。legal holdとretentionでversionを削除できない場合、勝手に保護を外さず対象と保持契約を調べます。出力は `restore-drills/` とhistoryに残ります。

<a id="되돌리기" />
## 元に戻す

訓練ツールは終了時に今回のprojectを片付けます。調査用 `--keep` なら確認後そのprojectだけdownし、volumeは別の保持方針で処理します。訓練bucketを運用と区別し、再利用データがないことを確認して各versionのlegal hold解除 → version/delete marker削除 → 空bucket削除の順で処理します。retentionは迂回せず期限を待ちます。試験のために運用バックアップを消しません。

<a id="kubernetes-설치" />
## Kubernetes 設置

Kubernetes 設置では compose 用のバックアップツールを使いません。AWS の機能が同じ役割を果たします。

- **DB.** RDS の自動バックアップ（point-in-time 復元）と手動スナップショット。
- **checkpoint の object.** S3 の versioning と Object Lock。commit した checkpoint は version で固定され legal hold が掛かっているため、同じ key を上書きまたは削除してもその version は残ります。復元は bucket をコピーせず、同じ bucket の version をそのまま指します。そのため未回収の checkpoint がある間は bucket を変えません。
- **bucket は DB とともに正本です.** [セッションイベントの保管](/run-server/self-hosting/reference/storage#세션-이벤트-보관)が `session-archive/` に移したイベントは、その object が唯一のコピーです。DB だけを戻して bucket を失うと、そのセッションのイベントは読めません。
- **lifecycle 規則.** 期限切れの規則は置きません。checkpoint の object を削除するのは chart の checkpoint GC CronJob（`checkpointGc.schedule`、既定 `0 4 * * 0`）だけです。lifecycle は DB を知らないため、hold が掛かる前の object や GC が hold を外した version を先に削除し、finalize や GC を壊します。`session-archive/` には storage class の移動だけを置き、API がすぐ読める class（`STANDARD_IA`、`ONEZONE_IA`、`GLACIER_IR`、archive tier を有効にしていない `INTELLIGENT_TIERING`）にだけ移します。`GLACIER`・`DEEP_ARCHIVE` に移すと、そのセッションのイベントを読めません。
- **スナップショットと GC.** RDS スナップショットはその時点の pointer を含みます。スナップショットの後に GC が削除した revision をそのスナップショットの pointer が指すことがあるため、スナップショットの保持期間と GC の周期を合わせて決めます。
