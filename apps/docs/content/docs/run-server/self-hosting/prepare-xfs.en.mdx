## What you will do

Place Docker's data-root on XFS prjquota to enforce workspace byte and inode limits. Preserve existing disks, images, and Docker data. The release bundle's `scripts/prepare-xfs.sh` runs everything from the preflight to the final check, and when a step fails it undoes the steps before it.

<a id="준비물" />
## Before you begin

Run this on the Linux server intended for production, after first validating it on a separate test server. You need root access, Docker Engine running under systemd, xfsprogs and rsync, enough space to retain all original data, and a maintenance window. The script is `scripts/prepare-xfs.sh` in the directory where you unpacked the [release bundle](/run-server/self-hosting/single-server#릴리스-번들로-받기). A repository checkout has it at the same path. Docker Desktop does not support this installation path.

Install xfsprogs and rsync with your distribution's package manager. On distributions that use apt:

```bash
sudo apt-get install -y xfsprogs rsync
```

<a id="단계" />
## Steps

<a id="1-현재-상태-확인" />
### 1. Check the current state

```bash
findmnt -no FSTYPE,OPTIONS -T "$(docker info -f '{{.DockerRootDir}}')"
P="quota-probe-$(date +%s)"; docker volume create --driver local --opt size=64m "$P" && docker volume rm "$P"
```

If XFS and prjquota are already active and the probe succeeds, skip the rest of this page. In that state the script also exits without changing anything. If the quota probe fails, do not deploy until you resolve the cause.

<a id="2-dry-run으로-사전-검사" />
### 2. Run the preflight with --dry-run

Run it from the bundle directory.

```bash
sudo bash scripts/prepare-xfs.sh --dry-run
```

A dry run performs only the preflight and prints the steps it would run. It does not change the host. The preflight checks that:

- It runs as root and the commands it needs, such as `mkfs.xfs`, `rsync`, and `findmnt`, are present.
- Docker runs under systemd with live-restore off and its data-root at `/var/lib/docker` (with live-restore on, containers keep writing after Docker stops, so the script refuses), and that path is neither a symlink nor a mount point.
- `/var/lib/docker.xfs.img`, `/var/lib/docker.old`, and `/etc/fstab.before-prepare-xfs` do not exist, and `/etc/fstab` has no `/var/lib/docker` entry. `findmnt --verify` finds no errors in the current `/etc/fstab`.
- `/var/lib` has free space for the full image size.
- The kernel supports XFS, and a temporary 512M image can be trial-mounted with loop and prjquota. The trial image is removed after the check.

If any check fails, the script prints the reason and `nothing was changed`, and exits with code 1. A server without loop devices or XFS support (such as a container-type server) stops here, before Docker is stopped.

<a id="3-디스크-준비-실행" />
### 3. Prepare the disk

```bash
sudo bash scripts/prepare-xfs.sh
```

The script runs the same preflight again, then in order: stops Docker, moves `/var/lib/docker` to `/var/lib/docker.old`, creates the 60G sparse image `/var/lib/docker.xfs.img` and runs `mkfs.xfs`, mounts it with `loop,prjquota`, copies the original data (`rsync -aHAX`), backs up `/etc/fstab` to `/etc/fstab.before-prepare-xfs`, adds the entry below and runs `findmnt --verify`, starts Docker, and checks the data-root, the mount, and the quota probe.

```text
/var/lib/docker.xfs.img /var/lib/docker xfs loop,prjquota 0 0
```

The script appends this entry to `/etc/fstab` itself, so there is nothing to edit by hand. The `findmnt --verify` in this step can exit 0 and still print two warnings; both are expected. `non-bind mount source /var/lib/docker.xfs.img is a directory or regular file` only says the loop mount source is a regular file. `your fstab has been modified, but systemd still uses the old version` appears because the script runs `systemctl daemon-reload` right after.

Change the image size with `--size`. The value is in whole GB (for example `--size 100G`). 60G is the ceiling for volumes and container logs under `/var/lib/docker`. Docker 29 keeps images and container layers in `/var/lib/containerd`, so they land outside the XFS image (usually on the root disk). Check that free space separately. The XFS image is a sparse file, but the host must have that much free space.

When a step fails, the script undoes the steps before it in reverse: it restores fstab from the backup, unmounts, removes the mount point and image it created, moves the original back to `/var/lib/docker`, and starts Docker again. If Docker already started on the new image, what it wrote is in the image, so the script keeps the image and prints its path.

| Exit code | Meaning |
| --- | --- |
| 0 | Prepared, or already prepared and nothing changed |
| 1 | The preflight refused. Nothing changed |
| 2 | Invalid arguments |
| 3 | A step failed and everything was undone. Docker runs on the original data-root again |
| 4 | A step failed and part of the undo failed too. The output describes what is left |

<a id="확인" />
## Verify

The script ends by checking the data-root, the mount options, and the quota probe. Rerun the commands from step 1 to see `xfs`/`prjquota` and a successful probe yourself. Check free space with `df -h`, `df -i`, and `xfs_quota -x -c 'report -p'`.

<a id="자주-막히는-곳" />
## Troubleshooting

- A refusal with `already exists` means an earlier run or manual work left that path. Inspect its contents. Do not resize or reformat an existing image or `/var/lib/docker.old` to reuse it.
- A refusal with `the trial XFS loop mount` means this host cannot use loop devices or XFS project quotas. Use another server, or plan a migration onto a separate XFS disk for the Docker data-root.
- With exit code 4 and the data-root not back in place, the script leaves Docker stopped. Starting Docker in that state uses an empty data-root, so first clean up what the output lists, following [Roll back](#되돌리기), then start it.

<a id="되돌리기" />
## Roll back

Containers, volumes, and data created after restarting Docker on the new XFS are absent from `/var/lib/docker.old`. Returning to the original directory loses those changes. Preserve new data separately first and decide what to restore. Sparse images do not shrink automatically when data is deleted; monitor free space on the host filesystem too.

Stop Docker and its socket. If the new XFS is mounted, confirm no containers are using it before unmounting. Revert the added fstab entry against `/etc/fstab.before-prepare-xfs`, which the script left. `/var/lib/docker.old` is the original. Confirm the original path is empty, restore the original directory, and start Docker. Do not delete the new image or original data; confirm the previous container and volume inventory matches.

For an installation that originally had a data directory, after unmounting and restoring fstab, remove only the empty mount point with `sudo rmdir /var/lib/docker`, then restore it with `sudo mv /var/lib/docker.old /var/lib/docker`. If rmdir fails, investigate without deleting its contents. Do not perform this move on a fresh installation that had no original directory.
