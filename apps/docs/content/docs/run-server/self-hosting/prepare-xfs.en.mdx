## What you will do

Place Docker's data-root on XFS prjquota to enforce workspace byte and inode limits. Preserve existing disks, images, and Docker data. The release bundle's `scripts/prepare-xfs.sh` runs everything from the preflight to the final check, and when a step fails it undoes the steps before it.

<a id="준비물" />
## Before you begin

Run this on the Linux server intended for production, after first validating it on a separate test server. You need root access, Docker Engine running under systemd, xfsprogs and rsync, enough space to retain all original data, and a maintenance window. The script is `scripts/prepare-xfs.sh` in the directory where you unpacked the [release bundle](/run-server/self-hosting/single-server#릴리스-번들로-받기). A repository checkout has it at the same path. Docker Desktop does not support this installation path.

Install xfsprogs and rsync with your distribution's package manager. On distributions that use apt:

```bash
sudo apt-get install -y xfsprogs rsync
```

<a id="단계" />
## Steps

<a id="1-현재-상태-확인" />
### 1. Check the current state

```bash
findmnt -no FSTYPE,OPTIONS -T "$(docker info -f '{{.DockerRootDir}}')"
P="quota-probe-$(date +%s)"; docker volume create --driver local --opt size=64m "$P" && docker volume rm "$P"
```

If XFS and prjquota are already active and the probe succeeds, skip the rest of this page. In that state the script also exits without changing anything. If the quota probe fails, do not deploy until you resolve the cause.

<a id="2-dry-run으로-사전-검사" />
### 2. Run the preflight with --dry-run

Run it from the bundle directory.

```bash
sudo bash scripts/prepare-xfs.sh --dry-run
```

A dry run performs only the preflight and prints the steps it would run. It does not change the host. The preflight checks that:

- It runs as root and the commands it needs, such as `mkfs.xfs`, `rsync`, and `findmnt`, are present.
- Docker runs under systemd with live-restore off and its data-root at `/var/lib/docker` (with live-restore on, containers keep writing after Docker stops, so the script refuses), and that path is neither a symlink nor a mount point.
- `/var/lib/docker.xfs.img`, `/var/lib/docker.old`, and `/etc/fstab.before-prepare-xfs` do not exist, and `/etc/fstab` has no `/var/lib/docker` entry. `findmnt --verify` finds no errors in the current `/etc/fstab`.
- `/var/lib` has free space for the full image size.
- The kernel supports XFS, and a temporary 512M image can be trial-mounted with loop and prjquota. The trial image is removed after the check.

If any check fails, the script prints the reason and `nothing was changed`, and exits with code 1. A server without loop devices or XFS support (such as a container-type server) stops here, before Docker is stopped.

<a id="3-디스크-준비-실행" />
### 3. Prepare the disk

```bash
sudo bash scripts/prepare-xfs.sh
```

The script runs the same preflight again, then in order: stops Docker, moves `/var/lib/docker` to `/var/lib/docker.old`, creates the 60G sparse image `/var/lib/docker.xfs.img` and runs `mkfs.xfs`, mounts it with `loop,prjquota`, copies the original data (`rsync -aHAX`), backs up `/etc/fstab` to `/etc/fstab.before-prepare-xfs`, adds the entry below and runs `findmnt --verify`, starts Docker, and checks the data-root, the mount, and the quota probe.

```text
/var/lib/docker.xfs.img /var/lib/docker xfs loop,prjquota 0 0
```

The script appends this entry to `/etc/fstab` itself, so there is nothing to edit by hand. The `findmnt --verify` in this step can exit 0 and still print two warnings; both are expected. `non-bind mount source /var/lib/docker.xfs.img is a directory or regular file` only says the loop mount source is a regular file. `your fstab has been modified, but systemd still uses the old version` appears because systemd has not yet reloaded the modified fstab; the script runs `systemctl daemon-reload` immediately afterward.

Change the image size with `--size`. The value is in whole GB (for example `--size 100G`). 60G is the combined ceiling that volumes and container logs under `/var/lib/docker` share. Filesystem metadata also takes space, so usable data room is smaller. On a fresh Docker 29 or later install that uses the containerd image store (the default), images and container layers go to `/var/lib/containerd`, outside the XFS image (usually on the root disk). Check that free space separately. The XFS image is a sparse file, but the host must have that much free space.

When a step fails, the script undoes the steps before it in reverse: it restores fstab from the backup, unmounts, removes the mount point and image it created, moves the original back to `/var/lib/docker`, and starts Docker again. If Docker already started on the new image, what it wrote is in the image, so the script keeps the image and prints its path.

| Exit code | Meaning |
| --- | --- |
| 0 | Prepared, or already prepared and nothing changed |
| 1 | The preflight refused. Nothing changed |
| 2 | Invalid arguments |
| 3 | A step failed and everything was undone. Docker runs on the original data-root again |
| 4 | A step failed and part of the undo failed too. The output describes what is left |

<a id="확인" />
## Verify

The script ends by checking the data-root, the mount options, and the quota probe. Rerun the commands from step 1 to see `xfs`/`prjquota` and a successful probe yourself. Check free space with `df -h`, `df -i`, and `xfs_quota -x -c 'report -p'`.

<a id="xfs-project-quota를-직접-켜기" />
## Turn on the XFS project quota yourself

If you already have an XFS disk or partition dedicated to the Docker data-root, turn on the mount option instead of running the script. The conditions are:

- The filesystem at the path that `docker info -f '{{.DockerRootDir}}'` reports is XFS. Other filesystems, such as ext4, do not pass Werft's quota check.
- That filesystem is mounted with the `prjquota` option (`pquota` means the same).

First find the mount point, device, and filesystem that hold the data-root, and the UUID of that device. The mount point can be a parent directory of the data-root. If the filesystem is not `xfs`, stop here.

```bash
DATA="$(docker info -f '{{.DockerRootDir}}')"
findmnt -no TARGET,SOURCE,FSTYPE -T "$DATA"
sudo blkid -s UUID -o value "$(findmnt -no SOURCE -T "$DATA")"
```

Quota options take effect only at the first mount, and `mount -o remount` does not turn them on. So change the configuration and then reboot. Every running container stops, so do this in a maintenance window. A LocalStack test installation loses its checkpoint objects on a reboot. Before changing anything, run `backup --stop` as in the planned restart steps of [Try with LocalStack](/run-server/self-hosting/try-localstack). Go on only after the command has succeeded and you have seen the backup directory it made; if it fails, change nothing and do not reboot. After the reboot use `reseed`, not `start`.

If the mount point is the root filesystem (`/`), the fstab option alone does not turn the quota on. Add `rootflags=prjquota` to the kernel boot arguments (add to the value if `rootflags` is already there), reboot, and then [check that it is on](#켜졌는지-확인하기). How to change boot arguments differs between distributions. Write down the current arguments before you change them. If the host does not boot with the new ones, boot once with the old arguments from the boot menu and then revert the setting. The fstab steps below are only for a mount point other than the root.

Back up `/etc/fstab` before you edit it for the first time. If the backup fails, do not edit.

```bash
sudo cp -n -p /etc/fstab /etc/fstab.before-prjquota
```

If there is already an entry for that mount point, do not add a line; add `prjquota` to that entry's options. If that entry does not point to the device (UUID) you found above, do not edit it; stop and find out why. If there is no entry, add one line of the following shape. Use the UUID printed above, and put the mount point you found above in place of `/var/lib/docker`.

```text
UUID=<filesystem-uuid> /var/lib/docker xfs defaults,prjquota 0 0
```

Reboot only when `findmnt --verify` shows no errors. If it shows errors, fix them right away or restore the backup.

```bash
sudo findmnt --verify && sudo reboot
```

After the reboot, run the first command above again to see that the mount point and the device UUID are the same as before, and use the check below to see `prjquota` among the options. If the boot stops because of fstab, restore the backup from the recovery console.

<a id="켜졌는지-확인하기" />
## Check that it is on

```bash
DATA="$(docker info -f '{{.DockerRootDir}}')"
findmnt -no TARGET,FSTYPE,OPTIONS -T "$DATA"
sudo xfs_quota -x -c 'state -p' "$(findmnt -no TARGET -T "$DATA")"
P="quota-probe-$(date +%s)-$$"; docker volume create --driver local --opt size=64m "$P" && docker volume rm "$P"
```

`findmnt` must show the filesystem `xfs` with `prjquota` among the options. In the Project quota section of `xfs_quota`, both Accounting and Enforcement must be `ON`. The last line checks that Docker accepts a volume with the `size` option: it creates and removes a volume under a new name, and succeeds when it prints the name twice. `quota size requested but no quota support` means the quota is still off.

<a id="werft가-quota를-알아내는-방법" />
## How Werft finds out about the quota

This section is about Docker installations. On Kubernetes the scheduler does not check a quota; see [Storage and limits](/run-server/self-hosting/reference/storage) for the limits there.

With `EXECUTION_WORKSPACE_QUOTA=on`, the scheduler does not decide from the mount table or fstab. It asks the Docker Engine API to create a probe volume (its name starts with `ap-quota-probe-`) with the `local` driver's `size` option. A daemon that refuses with `no quota support` fails the check. When the volume is created, a helper container runs from the worker image (capabilities `SYS_ADMIN` and `MKNOD`). The helper reads `/proc/self/mountinfo` to see that the volume is on XFS, confirms with `xfs_io` that the volume has a project of its own, sets an inode limit with `xfs_quota`, and reads it back with `xfs_quota` and `stat -f`. After the check it tries to remove the probe volume. A later check tries again to remove one that was left behind, once it is old. `preflight` and `deploy` of `scripts/test-ops.sh` also create a probe volume with the same `size` option.

When the check fails, the scheduler launches no worker and ends in failure. **It does not switch to measurement on its own.** Measurement holds the limit only when the operator sets `EXECUTION_WORKSPACE_QUOTA=off`. Then the scheduler skips the probe, each worker measures its workspace when a turn starts and while it runs (the periodic measurement runs at most once a minute), and stops a turn whose usage grows during the turn and passes the limit. A workspace can briefly pass the limit between two measurements. In a single-server installation, `scripts/test-ops.sh` accepts `off` only for the LocalStack test installation. The local Compose stack of a repository checkout is `off` when no value is given.

The quota note on the General screen of workspace settings and `detail.no_disk_quota` in `/readyz` do not come from a disk check. They show whether the `EXECUTION_WORKSPACE_QUOTA` value the api received is `off`. After preparing the disk, change the value to `on` and apply it to the api and the scheduler again. In a single-server installation, edit the env file and run `scripts/test-ops.sh start`. If you rebooted a LocalStack test installation, do not use `start`: edit the env file, and `reseed` brings the api and the scheduler up with the new value. A workspace created under `off` does not start as it is under `on`, so follow [Migrate workspaces](/run-server/self-hosting/migrate-workspaces).

## Troubleshooting

- A refusal with `already exists` means an earlier run or manual work left that path. Inspect its contents. Do not resize or reformat an existing image or `/var/lib/docker.old` to reuse it.
- If a rerun after an undo is refused because `/var/lib/docker.xfs.img` or `/etc/fstab.before-prepare-xfs` already exists, the undo left it behind. When Docker had already run on the new image, the script keeps the image too. Confirm the image holds no data you need, and only after the unmount, the fstab restore and `daemon-reload` are done and `/var/lib/docker` is the original again, remove them with `sudo rm -f /var/lib/docker.xfs.img /etc/fstab.before-prepare-xfs`. If `/var/lib/docker.old` still exists it is the original: restore it first and do not delete it.
- A refusal with `the trial XFS loop mount` means this host cannot use loop devices or XFS project quotas. Use another server, or plan a migration onto a separate XFS disk for the Docker data-root.
- With exit code 4 and the data-root not back in place, the script leaves Docker stopped. Starting Docker in that state uses an empty data-root, so first clean up what the output lists, following [Roll back](#되돌리기), then start it.

<a id="되돌리기" />
## Roll back

Containers, volumes, and data created after restarting Docker on the new XFS are absent from `/var/lib/docker.old`. Returning to the original directory loses those changes. Preserve new data separately first and decide what to restore. Sparse images do not shrink automatically when data is deleted; monitor free space on the host filesystem too.

Stop Docker and its socket. If the new XFS is mounted, confirm no containers are using it before unmounting. Revert the added fstab entry against `/etc/fstab.before-prepare-xfs`, which the script left, then run `sudo systemctl daemon-reload` so systemd rereads the restored fstab. `/var/lib/docker.old` is the original. Confirm the original path is empty, restore the original directory, and start Docker. Do not delete the new image or original data; confirm the previous container and volume inventory matches.

For an installation that originally had a data directory, after unmounting and restoring fstab, remove only the empty mount point with `sudo rmdir /var/lib/docker`, then restore it with `sudo mv /var/lib/docker.old /var/lib/docker`. If rmdir fails, investigate without deleting its contents. Do not perform this move on a fresh installation that had no original directory.
