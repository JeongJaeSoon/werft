## 무엇을 하게 되나

게시 Helm chart로 운영 서버를 설치한다. PostgreSQL과 영속 S3 호환 bucket은 따로 준비한다. chart 설치 성공과 세션 데이터 복원 성공을 구분한다.

## 준비물

| 항목 | 요구 |
| --- | --- |
| 클러스터 | Kubernetes. NetworkPolicy를 강제하는 CNI가 필요하다. 강제하지 않으면 worker 격리가 없다 |
| 도구 | `helm` 3, `kubectl`, `curl` |
| PostgreSQL | 16. 클러스터 안에서 닿는 주소 |
| S3 호환 object store | bucket 하나. 기본 보호 모드 `locked`는 versioning, Object Lock, 기본 암호화 SSE-S3(`AES256`)가 켜진 bucket을 요구한다. 아니면 api가 기동을 거부한다 |
| 외부 | `ghcr.io`에서 chart와 이미지를 받을 수 있다. 패키지는 로그인 없이 받는다 |

chart와 패키지의 선택 방법은 [배포 패키지 계약](/run-server/self-hosting/reference/packages)을 따른다. AWS 이외 endpoint는 `config.aws.endpointUrl`와 credential allowlist를 함께 맞추고 보호 계약을 확인한다.

chart는 PostgreSQL, object store, Secret 값을 만들지 않는다. worker Pod도 만들지 않는다. scheduler가 세션마다 만든다. 게시 이미지는 `linux/amd64`와 `linux/arm64`를 담은 index이므로 노드가 자기 아키텍처를 받는다.

Git 서버도 chart가 만들지 않는다. 설정 문서의 저장소 URL은 worker가 egress proxy로 닿을 수 있어야 한다. kind의 시험 Git 서버는 운영 저장소가 아니다.

아래 예시는 namespace와 release가 모두 `werft`인 설치다. 실행 전에 `kubectl config current-context`와 `KUBECONFIG`가 이번 설치의 클러스터를 고르는지 확인한다. `helm`은 `KUBECONFIG`(없으면 `~/.kube/config`)를 읽는다. k3s에 들어 있는 `kubectl`은 k3s의 설정 파일을 따로 읽으므로, `kubectl`이 되어도 `helm`은 클러스터를 찾지 못할 수 있다. k3s에서는 `export KUBECONFIG=/etc/rancher/k3s/k3s.yaml`로 지정한다. 이 파일은 기본으로 root만 읽으므로 root 셸에서 실행한다. 다른 설치는 모든 `-n`·`--namespace`·release 이름과 `deploy/werft-*`·`svc/werft-*`를 실제 fullname으로 바꾼다. release 이름에 `werft`가 없으면 fullname은 `<release>-werft`다.

[checkpoint bucket](/run-server/self-hosting/prepare-checkpoint-bucket)과 [workspace 저장소 계약](/run-server/self-hosting/reference/storage)을 먼저 확인한다. 설치 id는 backend가 받는 **32자 이하 소문자 DNS label**이어야 한다. chart가 더 넓게 허용해도 이 제약을 따른다. 원격 bootstrap 전 [접속 경로](/run-server/self-hosting/access)를 준비한다.

## 단계

### 1. 정확한 chart 버전 선택

```bash
VERSION='<published-chart-version>'
helm show chart oci://ghcr.io/jeongjaesoon/werft --version "$VERSION"
helm show values oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" | sed -n '/^images:/,/^$/p'
```

`images` 아래에 `controlHost`·`egressProxy`의 `digest`와 `workers` 목록이 나오면 된다. 목록에는 Claude worker와 Codex worker 두 항목이 있고, 각 세션은 자기 엔진의 이미지로 뜬다. 이 값은 chart에 들어 있으므로 설치별 values에 다시 적지 않는다. 적으면 다음 chart의 값을 계속 덮는다. Helm은 목록을 합치지 않고 통째로 바꾸므로, values에 적은 `images.workers`에는 다음 chart의 이미지가 들어가지 않는다. 이미지 하나만 배포하려면 values에 `images.workers: []`와 그 이미지의 `images.worker`(repository·digest·runtime)를 적는다. 값은 같은 chart의 `files/release-images.json`에서 얻는다. 이 설치의 업그레이드는 [Kubernetes 업그레이드](/run-server/self-hosting/upgrade-kubernetes)의 단일 이미지 절차를 따른다.

### 2. namespace와 Secret

Secret은 키마다 파일 하나인 디렉터리(`0700`, 파일 이름이 키)에서 만든다. 값이 명령줄과 셸 history에 남지 않는다.

| 키 | 값 |
| --- | --- |
| `DATABASE_URL` | PostgreSQL 연결 URL |
| `EGRESS_AUTHORIZER_TOKEN` | 무작위 값. api와 egress proxy가 같은 값을 쓴다 |
| `PLATFORM_SECRET_KEY` | `openssl rand -hex 32`의 64자 hex. 저장한 자격 증명을 봉인한다. 없으면 Pod가 뜨지 않는다 |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | object store key. IRSA로 서명하려면 두 키를 빼고 values에 `secrets.objectStoreKeys: false`와 `serviceAccounts.api.annotations`를 둔다 |

모델 key는 Secret에 두지 않는다. 설치 뒤 콘솔의 **설정 > 에이전트 연결 > 모델 연결 > 연결 추가**에서 넣고, DB에 `PLATFORM_SECRET_KEY`로 암호화돼 저장된다.

```bash
kubectl create namespace werft
kubectl -n werft create secret generic werft --from-file=<secret-dir>
```

Secret 디렉터리는 0700, 파일은 운영자만 읽을 수 있게 둔다.

### 3. 설치별 values

설치별 값은 `values-<installation>.yaml` 하나에 둔다. 최소한 checkpoint bucket과 worker가 bucket에 닿는 경로가 들어간다.

```yaml
installationId: werft-main
config:
  checkpoints:
    bucket: <bucket>
  egress:
    credentialAllowlist: "api.anthropic.com:443,registry.npmjs.org:443,rubygems.org:443,proxy.golang.org:443,sum.golang.org:443,github.com:443,<bucket>.s3.<region>.amazonaws.com:443"
```

`credentialAllowlist`는 기본값을 통째로 바꾼다. 기본 목록(provider와 패키지 registry)을 모두 다시 적고, 저장소 호스트(`github.com:443`, 다른 Git 호스트를 쓰면 그 호스트도)와 bucket 호스트를 이어 적는다.

`config.aws.region`의 기본값은 `ap-northeast-1`이다. 다른 리전의 bucket이면 바꾼다. 연결, 저장소, MCP 서버, 상한은 values에 없다. 설치한 뒤 웹 콘솔에서 더한다. `bun run settings:k8s import`를 쓰는 대안은 설치 버전의 저장소 checkout과 호스트 Bun·kubectl이 필요하다. 기본값과 설명은 `helm show values`에 있다.

`config.egress.credentialAllowlist` 값은 기본값을 통째로 대체하므로 GitHub·checkpoint bucket host를 넣을 때 provider와 패키지 registry 등 필요한 항목을 모두 다시 적는다. API와 proxy가 같은 credential 두 목록을 읽는다.

다른 설치와 겹치지 않는 `installationId`를 같은 파일에 둔다. `images.*`의 digest는 게시 chart의 값을 유지한다. DB·S3·Secret·CNI가 준비됐는지 확인한 뒤 진행한다.

### 4. 설치와 rollout

```bash
helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  --namespace werft -f values-<installation>.yaml --timeout 10m
```

`helm`이 `Kubernetes cluster unreachable: Get "http://localhost:8080/version"`으로 끝나면 `helm`이 클러스터 설정을 읽지 못한 것이다. 준비물에 적은 대로 `KUBECONFIG`를 지정하고 같은 명령을 다시 돌린다.

migrate Job이 먼저 schema를 올리고, 끝나면 api, egress proxy, reconciler, scheduler, slack이 한꺼번에 적용된다. 첫 설치가 이미지 경로나 pull 권한 오류로 실패하면 값을 고치고 같은 명령을 다시 돌린다.

```bash
kubectl -n werft get job werft-migrate
for d in api egress-proxy reconciler scheduler slack; do
  kubectl -n werft rollout status deploy/werft-$d --timeout=600s
done
```

values에 `slack.enabled: false`를 둔 설치는 반복문에서 `slack`을 뺀다. release 이름에 `werft`가 들어가지 않으면 리소스 이름은 `<release>-werft-…`가 된다.

첫 설치가 실패하면 값을 고치고 같은 명령을 다시 실행한다. Deployment까지 생긴 실패에서 worker 이미지를 바꿨다면 업그레이드 검사 규칙이 적용된다. 세션이 없다면 [Kubernetes 제거](/run-server/self-hosting/remove-kubernetes)로 설치를 정리한 뒤 다시 시작한다.

첫 세션은 worker Pod가 뜰 노드가 worker 이미지를 받는 동안 늦다. 이미지는 수백 MB다(0.4.0의 Claude worker는 약 395 MB). worker Pod는 노드에 이미 있는 이미지를 다시 받지 않으므로 미리 받아 둘 수 있다. 아래 첫 명령은 이 chart의 worker 이미지 주소(Claude worker, Codex worker)를 한 줄에 하나씩 적는다. worker를 띄울 노드마다 에이전트가 쓰는 엔진의 주소를 `<worker-image>` 자리에 넣어 받는다.

```bash
helm show values oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
  | sed -n 's/.*"repository":"\([^"]*\)","digest":"\([^"]*\)".*/\1@\2/p'
sudo crictl pull '<worker-image>'
```

k3s 노드에서는 `sudo k3s crictl pull '<worker-image>'`로 받는다. values에 `images.registry`를 둔 설치는 각 주소 앞에 `<registry>/`를 붙인다.

## 확인

```bash
kubectl -n werft port-forward svc/werft-api 13000:3000 &
PF=$!
trap 'kill "$PF" 2>/dev/null || true' EXIT INT TERM
READY=0
for attempt in $(seq 1 30); do
  if curl --max-time 2 -fsS -o /dev/null http://127.0.0.1:13000/readyz; then READY=1; break; fi
  sleep 1
done
if [ "$READY" != 1 ]; then
  kill "$PF" 2>/dev/null || true
  trap - EXIT INT TERM
  false
else
  curl --max-time 10 -fsS -w '\n%{http_code}\n' http://127.0.0.1:13000/readyz
  curl --max-time 10 -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:13000/docs
  kill "$PF" 2>/dev/null || true
  trap - EXIT INT TERM
fi
```

ready 본문과 200, docs 200을 확인한다. 30번 안에 ready가 되지 않으면 이 셸이 띄운 port-forward PID를 정리하고 실패로 남긴다. 실제 사용자 경로에서는 [접속 경로 검사](/run-server/self-hosting/access)도 수행한다. 이 확인은 빈 설치의 준비 상태이며 worker 실행·checkpoint 복원을 증명하지 않는다.

## 자주 막히는 곳

첫날에는 설치 직후·1시간 뒤·업무 종료 전에 `kubectl -n werft get job,deploy,pods,pvc`와 api·scheduler·reconciler 로그, 각 `--health`, 디스크·inode·PVC 여유를 확인한다. 백업 실패 알림·checkpoint GC 일정·key 폐기 연락 경로·provider 비용 한도를 점검한다. release와 namespace가 예시와 다르면 모든 명령을 해당 설치 값으로 바꾼다.

NetworkPolicy를 강제하지 않는 CNI에는 worker 격리가 없다. Secret 키 누락, 잘못된 installationId, S3 보호 설정 오류, image pull 실패를 Pod와 Job 로그에서 구분한다. fixture chart의 render 성공은 게시 chart의 설치 성공과 다르다.

노드를 다시 켠 뒤에는 api가 준비되기까지 몇 분 걸릴 수 있다. PostgreSQL이 같은 노드에서 함께 다시 뜨는 구성에서, api Pod가 2분 넘게 준비되지 않다가 startup probe(5초 간격 24번, 약 2분)에 재시작된 뒤에야 준비된 일이 있다. 그동안 `kubectl rollout status`는 재시작 전 상태를 보고 성공으로 끝날 수 있다. 준비됐는지는 [확인](#확인)의 블록으로 `/readyz`를 직접 본다. 30번 안에 준비되지 않으면 몇 분 뒤 다시 돌리고, `kubectl -n werft get pods`로 api Pod의 상태와 `RESTARTS`를, `kubectl -n werft logs deploy/werft-api`로 로그를 함께 본다.

## 되돌리기

이전 revision으로 자동 rollback하지 않는다. 첫 설치 실패는 이 namespace의 리소스를 확인한 뒤 [제거](/run-server/self-hosting/remove-kubernetes)를 따른다. PVC와 bucket의 미수거 checkpoint는 보존한다.
