<a id="계약" />
## 契約

ストレージごとの上限と回収条件の正本です。サイズ変更は[容量の計画と変更](/run-server/self-hosting/capacity)、エラー後の判断は[停止したセッションの復旧](/run-server/self-hosting/recover-sessions)に従います。

<a id="backend별-workspace" />
## backend 別の workspace

| 項目 | 単一サーバー | Kubernetes |
| --- | --- | --- |
| 保存先 | セッションごとの Docker `local` volume。Docker データルートの XFS | セッションごとに PVC 一つ（`werft-ws-<installationId>-<sessionId>`）を worker の `/workspace` に mount します。`ReadWriteOnce`、`Filesystem`。`/tmp` と HOME はメモリ emptyDir で、hostPath は使いません |
| 容量上限 | `EXECUTION_WORKSPACE_QUOTA_MB`、既定 4096MiB（最小 1024） | PVC の `requests.storage`、helm の `worker.workspace.quotaMb`、既定 4096MiB（最小 1024）。実際の強制は StorageClass が決めます |
| inode 上限 | `EXECUTION_WORKSPACE_QUOTA_INODES`、既定 1,000,000 | **ありません。** Werft も chart も設定せず、ファイルシステムの既定値に従います（ext4 は作成時に個数が決まります） |
| 強制主体 | XFS の `prjquota`（カーネル）。scheduler preflight が確認します | CSI ドライバーとファイルシステム。Werft は PVC 容量と workspace 使用量を読みますが、実際の強制を検証する preflight はありません |
| 超過時 | worker の書き込みが `ENOSPC`。上限を設定できなければ scheduler が起動しません | StorageClass が容量を強制すれば `ENOSPC`。強制しなければ上限がないのと同じです。PVC 外のノードディスク使用量（主にログ）が `worker.ephemeralStorageMb`（既定 1024MiB、requests=limits）を超えると kubelet が Pod を evict します |
| 運用者の設定値 | Docker データルートのファイルシステムとサイズ、上記二つの上限 | `worker.storageClass`（空ならクラスタ既定）、`worker.workspace.quotaMb`、`worker.workspace.enforcedByStorage`、`worker.ephemeralStorageMb`、worker ノードのファイルシステムサイズ |
| 確認コマンド | `findmnt -no FSTYPE,OPTIONS -T "$(docker info -f '{{.DockerRootDir}}')"`、`xfs_quota -x -c 'report -p'` | 下記 |

```bash
kubectl get storageclass
kubectl -n werft get pvc -l app.kubernetes.io/part-of=werft,werft.installation=<installationId> \
  -o custom-columns=NAME:.metadata.name,REQUEST:.spec.resources.requests.storage,CAPACITY:.status.capacity.storage
kubectl -n werft exec <worker-pod> -- df -h /workspace
kubectl -n werft exec <worker-pod> -- df -i /workspace
```

`kubectl get storageclass` で、使う StorageClass の provisioner が容量を強制する volume を作るか確認します（例えば EBS gp3 では要求サイズがそのままブロックデバイスのサイズです）。PVC の `REQUEST` は Werft の要求値、`CAPACITY` は provisioner が作成したサイズです。`df -h` の総量はファイルシステムの overhead により異なる場合があるため、一致するかでは判断しません。確認するのは、`CAPACITY` が `REQUEST` 以上であることと、同じ StorageClass の試験 PVC に `REQUEST` を超えて書くと `ENOSPC` になることです。`df -i` で inode 総数を確認します。これら Kubernetes コマンド、容量強制、AZ 再接続は実行確認していません。値はコードと chart に基づきます。

- **PVC は必須です。** worker Pod の workspace volume は PVC だけで、emptyDir や hostPath に変える設定はありません。セッションの PVC は Pod と独立して存続し、Pod が置き換わっても同名の PVC に再接続します。scheduler がセッションごとに Pod と PVC を作成します。
- **StorageClass による容量の強制は Werft は検証しません。** コードは `requests.storage` を要求し、その値を `werft.workspace-size` annotation に記録して設定と比較します。PVC の `status.capacity` を読み worker に渡し、worker は workspace 使用量とファイルシステムの総量・inode を観測します。この観測は実際の強制の検証ではありません。強制の有無は CSI ドライバーとファイルシステムにより異なるため、設置前にインフラ側へ確認します。
- kind の既定 StorageClass（local-path 系）は PVC サイズを強制しないことが知られています。kind で `Bound` になっても上限が設定されたとは限りません。
- **既知の制限。** inode 上限がなく、容量上限は StorageClass に委ねられています。上限を強制しない StorageClass を選んでも chart は拒否しません。この制限を解消するコード変更はこのページの範囲外です。

EBS のような zonal PVC は AZ に結び付きます。ノード交換や Kubernetes 更新後、worker が同じ AZ の利用可能なノードで PVC に再接続することを設置環境で確認します。

Kubernetes の `worker.workspace.quotaMb` を変えると、既存 PVC の `werft.workspace-size` annotation と異なるため、そのセッションの launch が拒否されます。進行中のセッションがないときに新規セッション用の値を変更します。サイズ変更のために既存 PVC を削除しないでください。

`worker.workspace.enforcedByStorage: true`（既定 `false`）は、**この設置の全 workspace PVC（既存を含む）**で保存先が要求バイト数をハードに強制するという運用者の宣言です。`worker.storageClass` が空ならクラスタ既定値なので、各 PVC が実際に強制することを運用者が確認します。Werft は確認しません。宣言自体が保存先に上限を設定するわけではありません。

宣言経路では、ファイルシステム総量が要求の 0.95〜1.05 倍、PVC capacity が要求以上、mount point が `/` 以外の専用書き込み可能 mount（`rw` あり、`ro` なし）の場合、worker はバイトを `hard`、inode を `unknown` と判定します（`storage_declaration_and_capacity`）。mount・ファイルシステム証拠や capacity がなければ `unknown` です。他の宣言条件が不足すると `unknown`/`storage_enforcement_unverified` となり、共有ファイルシステム・inode 総数 0・要求の 1.5 倍を超えるファイルシステムは既存の `soft` 判定を維持します。サイズと mount の条件はヒューリスティックであり強制検証ではありません。宣言と判定根拠は `workspace_limit_mode` ログの evidence に残ります。

PVC がまだ bind されていないか、scheduler に PVC の `get` 権限がないと capacity は分かりません。共有ファイルシステムなど既存の `soft` 判定に該当せず mount・ファイルシステム証拠があっても、capacity がなければ宣言だけでは引き上げず `unknown`（`storage_capacity_unavailable`）のままです。

宣言を変えても PVC サイズ・名前・annotation と isolation stamp は変わらず、既存 Pod の置換や resume 拒否は起きません。実行中 Pod の env はそのままで、新しく作る Pod だけが新しい宣言を受け取ります。

<a id="transcript-상한" />
## transcript 上限

一つの checkpoint に含む transcript（root と全 subagent の合計）は 512MiB 以下、一つの part は 16MiB 以下でなければなりません。三箇所で同じ値を検査します。

1. worker が checkpoint を upload する前（`captureTranscripts`、manifest の upload・commit 前）。
2. API の finalize が part を読む前。この判定が基準です。
3. restore が part を取得する前（`#checkManifest`）。

サイズは compaction 後も残る JSONL 全体です。エンジン（Claude Code CLI）は resume 時に最後の compaction より前を読み直しませんが、プラットフォームはファイル全体を保存・復元します。そのため上限はファイル全体のサイズに適用します。

<a id="80-경고" />
### 80% 警告

- commit 済み checkpoint の transcript が初めて上限の 80%（409.6MiB）以上になると、SSE の `system` イベント（`transcript_near_limit`）を一度送り、セッション詳細の `attention` を `TRANSCRIPT_LIMIT` にします。実行は止めません。

<a id="상한을-넘으면" />
### 上限を超えた場合

- worker の事前検査（workspace upload 前）または finalize（part 読み取り前）が、`transcript_too_large`（一つの part が超過した場合は `transcript_part_too_large`）をセッションの `durability.checkpoint_pending_reason` に記録します。初回記録時に SSE の `system` イベント（`transcript_limit_reached`）を一度送ります。
- 上限を超えた turn は実行どおり `completed` で終了しますが、その turn の checkpoint は commit されません。
- 以後の新規メッセージは 409 `CHECKPOINT_UNAVAILABLE` で拒否され、キューの turn も実行されません。継続するには新しいセッションを作るか、recovery 経路の `start_fresh` を使います。close も 409 `CHECKPOINT_UNAVAILABLE` です。terminate 後に recovery close で閉じます。
- interrupt した turn は異なります。その turn の checkpoint が拒否されると、turn は `outcome_unknown`（`interrupt_checkpoint_unavailable`）で終わり、セッションは `recovery_required` へ移ります。
- 最後に commit した checkpoint が復元地点として残ります。上限を超えた一つの turn には checkpoint がなく、worker 交代後はその turn の context を引き継げません（セッション詳細の attention は `CONTEXT_GAP`）。

## 成果物（`out/`）の索引上限

worker は checkpoint ごとに作業ディレクトリの `out/` 配下の通常ファイルを git 状態に関係なく索引化して manifest の `outputs` に入れ、ファイルごとに object を一つ upload します。上限は worker の既定の出力上限です。

| 値 | 既定値 | 超過時 |
|---|---|---|
| ファイル一つの `maxFileBytes` | 64MiB | そのファイルは `{path, bytes, omitted: "too_large"}` だけを記録し、upload しません |
| checkpoint 一つの upload 合計 `maxTotalBytes` | 256MiB | 合計を超過させるファイルから `too_large` になります |
| ファイル数 `maxFiles` | 1,000 | パス順で 1,000 個より後のファイルを一覧から除外します。publish ログの `outputs_dropped` に件数を記録します |

- 索引上限を超えても checkpoint は失敗しません。git bundle 上限（256MiB）と workspace quota はそのままなので、git が追跡する、またはリポジトリなしのセッションが bundle に含める大きな `out/` ファイルは、別途そちらの上限に達します。git が無視しない untracked の `out/` ファイルも、復元用 untracked object としてはそのまま upload します。索引で `too_large` でも同様です。
- manifest 上限（object 20,000 個、8MiB）も checkpoint を失敗させません。成果物は復元用 object が残した個数まで一覧に入れ、超過分は `outputs_dropped` に数えます。一覧によって manifest が 8MiB を超えると、その checkpoint は `outputs` なしで upload し、publish ログの `outputs_refused` に理由を記録します。どちらの場合も除外されたファイルの object は upload 済みで、どの manifest からも参照されず、次の checkpoint でそのファイルを再 upload します。
- ファイルは一度に一つずつメモリへ読みます。worker メモリに追加されるのは、一つのファイル上限（64MiB）までです。
- symlink、通常ファイルでないもの、`.git` や UTF-8 以外の名前など manifest が受け付けない名前は一覧に入りません。`out` 自体が symlink なら一覧は空です。
- 同じ digest は一度だけ upload します。直前の checkpoint が upload した同じ digest はその object を参照し、再 upload しません。
- object の場所は `sessions/<id>/checkpoints/<revision>/<attempt>/<publish>/outputs/<sha256>` です。control plane が finalize でサイズと digest を確認して version を hold します。checkpoint GC は保持する checkpoint が参照する成果物 object を削除しません。

## Docker quota と回収

セッションごとに `werft-ws-<installationId>-<sessionId>-<suffix>` volume 一つを `/workspace` に接続します。この volume は generation を超えて存続します。コンテナが交代してもセッションの作業ツリーを維持するためです。そのため**コンテナを削除する `terminate` は volume に触れず**、回収は pass の ④ 段階で別途実行します。

volume が消えても、セッションは最後に commit した checkpoint から継続します。残るものと失うものは [workspace volume 消失時に残るもの](#workspace-volume을-잃었을-때)を参照してください。

volume は現在、backend が `POST /volumes/create` で**明示的に**作成します。mount spec に名前だけを書くと、Docker が label も上限もない volume を自動作成するためです。作成時に `werft.managed`・`.installation`・`.session-id`・`.workspace-quota` label を付け、GC は名前を解析せず、この label だけを参照します。

**volume 名は一度限りです。** `local` ドライバーは、過去に quota を設定した名前を再作成すると、`Options.size` をそのまま返しながら実際の project quota は設定しません。xfs+prjquota（Docker 27.5.1）の再現条件では、最初に作った名前はコンテナ内の `df` 総量が設定値（64MiB）ですが、同名を削除・再作成すると `Options.size` が同じでも `df` はファイルシステム全体（8GiB）を示します。Engine API では両者を区別できないため、セッションの workspace は名前から導出せず、ランダムな接尾辞を付けて作成し、**label で検索します。** GC や運用者が volume を削除しても、次は新しい名前になり上限が再設定されます。一つのセッションに workspace が二つ見つかった場合、どちらが作業ツリーかは判断せず報告だけします。preflight probe も同じ理由で毎回新しい名前を使います。以前の実行が残した probe は label で回収しますが、作成から 10 分と `EXECUTION_DOCKER_REQUEST_TIMEOUT_SEC` の 20 倍のうち長い方を過ぎたものだけを削除します。preflight は pass lock の外で実行されるため、それより新しい probe は並行する別の preflight（ループと並行した単独 `--once`、二つの scheduler）が使用中かもしれません。

CPU・メモリ・PID・tmpfs と同じく、`/workspace` にも上限があります。`EXECUTION_WORKSPACE_QUOTA_MB`（既定 4096）が `local` ドライバーの `size` driver option として上限を設定します。ただしこのオプションは**daemon のストレージが project quota に対応する場合だけ**（xfs + `prjquota`）機能し、それ以外では daemon が create を `400 quota size requested but no quota support` で拒否します。scheduler は pass 前に probe volume を一つ作って機能を確認し（`verifyWorkspaceQuota`）、対応しない daemon では**何も起動せず終了します。** probe は volume 一つの作成と CAP_SYS_ADMIN helper の起動を伴うため、毎 pass は繰り返しません。監督ループの pass は probe に合格すると、backend 設定全体（`DOCKER_HOST`・`EXECUTION_*` など）の hash を status file の隣の `<SCHEDULER_STATUS_FILE>.quota-verified` に記録します。以後の pass は hash が同じなら probe を省略します。監督ループは起動時にこのファイルを削除します。そのためループの再起動（コンテナ再起動、連続失敗後の再起動）後は、最初の pass が再確認します。失敗した probe は記録しないため、次の pass が再確認します。ループ外で単独実行する pass（`main.ts scheduler --once`）はこの記録を書かず、信頼せず、毎回 probe します。ループは記録先を `SCHEDULER_QUOTA_PREFLIGHT_MARKER` として自分の pass だけに渡します。黙って無制限になる経路はありません。カーネルの quota なしで動かすには `EXECUTION_WORKSPACE_QUOTA=off` を明示する必要があり、その場合は scheduler の毎 pass で警告が 1 件残ります。worker はカーネルの quota の代わりに自分の作業領域を測り、測るのは 1 分に 1 回までです。`EXECUTION_WORKSPACE_QUOTA_MB` か `EXECUTION_WORKSPACE_QUOTA_INODES` を超えた turn は `WORKSPACE_ENFORCE` に関係なく止まり、セッションは残ります。二つの測定の間は一時的に上限を超えることがあります。Compose の設置は同じ値を api にも渡します。api は起動時に警告を残し、`/readyz` 本文の `detail.no_disk_quota` とコンソール上部の帯でこの状態を示します。`on`・`off` 以外（`false`、`0`、`no`）は誤記として拒否します。

**quota の最小値は 1024 MiB です。** これより小さい `EXECUTION_WORKSPACE_QUOTA_MB` は起動時に拒否します。checkpoint 復元中、workspace volume を一時的にこれだけ使うためです。復元は root を空にしてから次の順で進みます。表の記号は次のとおりです。

- B：bundle の鎖の合計。control plane 上限は 256 MiB です。
- U：untracked ファイル。capture 上限は 256 MiB です。
- W：workspace の `.git` が取得した object。おおよそ B です。
- I：instructions commit から到達できる object。W 以下です。
- T：checkout した作業ツリーと index。

| 段階 | 同時に占有するもの | 最大 |
| --- | --- | --- |
| ダウンロード | bundle ファイル B、U | 512 MiB |
| staging | bundle ファイル B、staged リポジトリ ≈B、U | ≈768 MiB |
| workspace fetch | staged リポジトリ ≈B、W、U（bundle ファイルは staging 直後に削除） | ≈768 MiB |
| staged リポジトリの縮小 | W、I、U（staged リポジトリを先に削除） | ≤768 MiB |
| checkout 後、セッション全体 | W、I、T、U | 2B + T + U |

checkout 前の固定コストは bundle 上限の 2 倍 + untracked 上限、つまり 768 MiB です。1024 MiB はそこに pack index と余裕を加えた値です。incremental thin pack を埋める delta base のコピーもこの余裕に含みます。checkout 後の T はセッションの作業ツリーそのもので、上限はありません。そのため最小値はセッションによらない checkout 前のコストだけを保証します。checkout 後の W + I + T + U は、同じ quota 内で capture した際にそのセッションが使っていた量に近くなります。capture 時は workspace の `.git`、作業ツリー、untracked、scratch リポジトリの snapshot object、bundle ファイル（≤B）が共存していました。I は B 以下です。quota を下げてから新しい volume に復元する場合は保証対象外で、checkout 中に ENOSPC で失敗する場合があります。

既存 workspace を再利用する fresh fetch（checkpoint なしで再開する reuse）は、復元と異なり root を空にしません。worker は origin 全体を bare mirror として取得し、そこから branch をコピーします。mirror は `.git/werft-fetch-*` 配下に作り、fetch 完了後に削除します。`/tmp` と HOME は tmpfs でコンテナのメモリを使うためです。表の記号に加え、M は mirror のディスク使用量の最大値です。origin リポジトリの pack 全体に index・ref と、取得中の一時 pack ファイルが加わります。Δ は workspace の `.git` に新たに入る object です。下の最大値はこの推定を足したものです。

| 段階 | 同時に占有するもの | 最大 |
| --- | --- | --- |
| mirror clone とローカル fetch | 既存 W、I、T、U + mirror M + Δ | セッション使用量 + M + Δ |
| fetch 後 | W + Δ、I、T、U（mirror は削除） | セッション使用量 + Δ |

M に上限はありません。reuse の成功には M 分の quota 余裕が必要で、不足すると fetch が ENOSPC で失敗します。最初の clone（`clone`・`recreate`）は mirror なしで root に直接取得するため、W + T だけを使います。worker が途中で終了して残した scratch（fetch・capture・publish の `.git/werft-<purpose>-XXXXXX`）は、次の reuse が fetch 前に削除します。`werft-checkpoint` は残します。checkout が別の場所の object を借りる場合（`objects/info/alternates`、`commondir`、リンクの `objects`）、その参照先の可能性があるため削除しません。

復元後の `.git/werft-checkpoint/checkpoint.git` には、instructions commit から到達できる object（I）だけが残ります。エンジンがその commit を prune しても、次の capture が bundle を作れるようにするためのリポジトリです。それ以降の commit、未 commit 変更の snapshot、鎖の以前の snapshot は残しません。ただし instructions commit が HEAD と同じ場合、I は commit 済み履歴全体です。エンジンが commit していないセッションが該当し、その場合に減るのは snapshot 分だけです。

この縮小には代償があります。次の incremental capture は、鎖の tip のうち現存するものだけを除外対象にします。以前の base bundle にしかない snapshot commit は残っていません。最後の bundle の snapshot も、workspace の `.git` に参照なしで入っているだけです。通常の `git gc` はこれを 2 週間削除しませんが、エンジンが `git gc --prune=now` を実行すると消えます。その場合、残った tip（履歴に残る HEAD commit、instructions commit）を基準に bundle を作ります。結果として bundle が大きくなったり、full bundle に戻ったりする場合がありますが、正しさは維持されます。full bundle が上限を超えるリポジトリは、いずれにせよ鎖が 32 個または上限に達して再開するときにも拒否されます。

**inode 上限も同じ project に設定します。** byte 上限だけでは、数百万個の空ファイルで inode を使い切る経路が残ります。xfs は inode を project の block 使用量に含めないため、4GiB 内でも起こせます。その場合、同じ daemon の他のセッションや Postgres がファイルを作れなくなります。`local` ドライバーには inode オプションがなく、`o=loop` でセッションごとにファイルシステムを作る経路も使えません。ドライバーは `mount(8)` ではなく mount syscall を呼ぶためです（`data: loop: invalid argument`）。そのため Docker が `size` で作った xfs project に、こちらで `ihard`・`isoft`（`EXECUTION_WORKSPACE_QUOTA_INODES`、既定 1,000,000）を直接設定します。

- 設定するのは短時間動く helper コンテナです。`CapDrop ALL` + `CapAdd SYS_ADMIN, MKNOD`、`NetworkMode none`、read-only rootfs で、privileged ではありません。
- helper は volume の project id を読みます。project 0（= project なし）なら拒否します。0 に上限を設定するとファイルシステム全体を制限するためです。
- helper は mount 元の block device ノードを自分専用の `/dev` に `mknod` で作り、`xfs_quota` を呼びます。
- `xfs_quota` は失敗しても 0 で終了します。そのため成功は quota 報告の hard・soft limit と statfs の `f_files` を読むことだけで判断します。
- Docker の `SetQuota` は BHARD/BSOFT だけを書くため、この値を上書きしません。
- イメージは scheduler の `WORKER_IMAGE` です。worker イメージには `xfsprogs` が含まれます。launch ごとに別のイメージを選ばせません。CAP_SYS_ADMIN を与えるイメージは catalog ではなく運用者が決めます。

適用時点は四つです。

- preflight probe（`verifyWorkspaceQuota`、ループ起動後の最初の合格まで、および設定変更時だけ）：設定できなければ byte 上限と同じ規則で起動を拒否します。opt-out も同じ `EXECUTION_WORKSPACE_QUOTA=off` 一つだけです。
- 毎 launch の `ensureWorkspaceVolume`：新規・既存の両 volume が対象です。project id は daemon 再起動後に再利用され得るため cache しません。再設定は冪等です。
- 交代前の `assertReplaceable`：上限を設定できない volume なら、既存 worker を終了する前に交代を拒否します。
- `migrate-workspace` のコピー前：上限よりファイルが多いツリーはコピーが失敗し、原本が残ります。

inode 上限は in-place で変更できるため、volume label（`workspace-quota`）には入れません。inode 上限なしで作った volume も拒否せず、次の launch で上限を設定します。代わりに `isolationStampFor` の fingerprint に含め、`ISOLATION_CONTRACT` を 7 に上げます。このバージョンより前に rollback した host は、これらの worker を newer と判断して触れません。そのため上限の追加・変更で実行中 worker は stale として交代し、交代経路の ensure が上限を設定します。

Docker Desktop はカーネル自体が XFS quota なしでビルドされているため（`XFS (loopN): quota support not available in this kernel`）、ローカルでは `off` が事実上唯一の選択肢です。GitHub Actions runner の daemon も data root が ext4 なので同様です。そのため実際の上限強制は、CI の `workspace-quota` job が xfs + prjquota の loop ファイルを data root に使う daemon を別途起動して確認します。

一つの volume に上限を設定するだけでは不十分です。Docker はイメージが宣言する `VOLUME` パスごとに**書き込み可能な匿名 volume**を自動接続し、そこには上限も label もありません。そのため launch 前にイメージを調べ、`/workspace` 以外の `VOLUME` 宣言があれば拒否し（`ImageVolumeError`）、コンテナ削除時には `v=true` で匿名 volume も削除します（named volume の workspace には影響しません）。未 pull のイメージの取得は 404 なのでそのままにし、create が同じ 404 を返すようにします。

検査したものと実際に起動するものも食い違い得ます。タグは可変なので、コンテナは**検査したイメージの id**（`sha256:…`）で作成し、volume は create 直後、start 前にもう一度確認します。その間に `docker volume prune` が走ると、Docker が mount 用に label も上限もない volume を新しく作るためです。不一致なら、まだ何も実行していないコンテナを削除して失敗させます。

quota preflight が失敗したら、**何も起動しませんが、回収は一度実行します。** probe も少しディスクを使うため、既に満杯の daemon は preflight から失敗しますが、まさにそのとき終了したセッションの workspace を回収する必要があります。そのまま終了すると回収できなくなります。このとき動くのは pass ではなく `reclaimWorkspaces` で、同じ advisory lock の下で ④ 段階だけを実行します。slot limit 0 の pass では不十分です。新規予約だけを止めても、消えたコンテナの再作成や stale コンテナの交代は実行されるためです。回収後は元のエラーを再度 throw し、non-zero で終了します。

volume の quota label が現在の設定と異なる場合（quota なし、または別の byte 上限で作成した volume）は、起動を拒否します（`WorkspaceQuotaError`）。volume の byte quota は後から変更できず（inode 上限は前述のとおり in-place で変更できます）、変更のために削除するとそのセッションの作業ツリーを失います。作業ツリーを維持して新しい契約へ移すには、[既存 workspace の移行](/run-server/self-hosting/migrate-workspaces)手順を使います。以前の設定に戻す方法もあります。同じ理由で quota 設定は `werft.isolation` fingerprint にも含めます。含めなければ、起動済みのコンテナが以前の上限を保持したまま動き続けます。

この拒否は**実行中の worker を終了する前に**行う必要があります。fingerprint が変わると stale 判定 → `terminate` → 再作成の順になりますが、再作成が volume によって拒否されると、そのセッションには worker も戻る手段もなくなります。そのため `inspect` は stale を報告する前に、そのセッションの volume を読み取り専用で確認し、利用できなければ stale ではなく例外を返します。コンテナは以前の上限のまま動き続け、pass は `reconcileFailed` で non-zero となり、運用者が volume を移すまで続きます。方法は [既存 workspace の移行](/run-server/self-hosting/migrate-workspaces)を参照してください。inode 上限はこの読み取り専用確認ではなく、交代直前の `assertReplaceable` が実際に設定し、設定できなければ既存 worker を終了する前に交代を拒否します。

④ 段階の GC は fail-safe に動作します。**先に volume を列挙し、その後 DB に問い合わせます。** 逆にすると二つの呼び出しの間に作成されたセッションの volume を削除してしまいます。保持条件は、session row があり admission state が `closed` でない、または生きている execution row があることです。`stopped` は例外で、下記の期限規則に従います。session id label がない、session id の形式でない、まだコンテナが参照している（409）、別の設置環境の volume は、すべて**残してログだけを記録します。** `EXECUTION_WORKSPACE_GC_MIN_AGE_SEC`（既定 3600）より新しい volume は候補にしません。volume はコンテナより先に作られるため、その間に回収すると進行中の launch を壊します。**判断して残した場合と、失敗して残った場合は exit code が異なります。** mount 中（409）や別環境のため残した volume は正常状態なので exit code を変えません（`workspacesUnresolved`）。一覧を読めない、DB が応答しない（`workspaceScanFailed`）、削除呼び出しが throw する（`workspacesFailed`）場合は、誰にも確認されずディスクが増える状態なので pass は non-zero で終了します。

**`stopped` セッションの workspace は期限切れになります。** stop 後、owner が Web コンソールの **設定 > ワークスペース > 実行の上限**「停止したセッションの作業領域」で決めた時間（既定 86400 秒、一日。0–315360000 秒）を過ぎると回収候補になります。scheduler は回収のたびにこの値を DB から読みます。以前の版の `EXECUTION_WORKSPACE_STOPPED_TTL_SEC` は migrate が一度だけ移し、scheduler は読みません。基準時刻は `sessions.updated_at` です。stop 遷移が記録し、回収 claim と完了記録は変更しません。既に `stopped` のセッションに新しい terminate が受理されると更新され、その時点から TTL を数え直します。ただし terminate は workspace を保持する手段ではありません。既に回収 claim を取得していれば、回収はそのまま進みます。workspace が必要なら resume します。claim と直列化するのは resume だけです。slot を保持する launch が残っていれば候補ではありません。停止した workspace は設定 TTL まで保持し、期限後は回収候補と判定します。`0` は次の pass ですぐ回収する意味です。

resume は commit 済み checkpoint がある場合だけ受理し、worker は claim に restore pointer があれば checkpoint から workspace を復元します（root を空にしてから埋め直します）。そのため TTL を過ぎた stopped セッションの volume は cache にすぎません。逆に**checkpoint がない stopped セッションは resume できず、その volume だけに残る作業は TTL 後に消えます。** 必要な作業は TTL 内に volume から直接取り出してください。

**`paused` セッションの workspace も期限切れになります。** pause 後、同じ画面の「一時停止したセッションの作業領域」で決めた時間（既定 86400 秒、一日。0–315360000 秒、以前の版の `EXECUTION_WORKSPACE_PAUSED_TTL_SEC`）を過ぎると回収候補になります。承認待ちで park されたセッション（`pause_reason: awaiting_input`）も同じです。基準時刻は `sessions.paused_at` です。セッションが `paused` に入る書き込みが記録し、`paused` を離れると消去します。ほかの書き込み、回収 claim、完了記録は変更しません。この値ができる前（migration `0273_paused_at` より前）から `paused` だったセッションは、アップグレード後に回収 pass がそのセッションを初めて見た時刻から数えます。`0` は次の pass ですぐ回収する意味です。回収するのは、resume が受理する checkpoint があるセッションだけです。checkpoint pointer がない、`checkpoint_pending_reason` が妨げる、start_fresh が退役させた checkpoint である、legacy pod binding である場合は残します。slot を保持する launch があれば候補でないのは `stopped` と同じです。

回収された `paused` セッションを resume すると（人の resume でも、parked 要求への回答による自動 resume でも）、新しい workspace に checkpoint を復元します。復元はもともと古いツリーを消してから埋めるため、通常は何も失いません。ただし**復元が失敗したときに volume で救う道はなくなります。** これまでは checkpoint の確認（manifest の欠落・破損、イメージ組み合わせの不一致など）で復元が失敗すると volume が残り、その後の start_fresh がリポジトリなしセッションのファイルをそのまま使いました。回収されたセッションでは start_fresh は空の作業ディレクトリから始まります。作業ディレクトリは cache であり、checkpoint（S3）と DB が原本だという原則に従っています。paused volume を長く残すには画面でその時間を増やします。

二つの時間のどちらかを読めないとき（移せなかった env 値、DB 障害）、scheduler は `stopped`・`paused` セッションの workspace を新たに回収しません。終了したセッションの workspace と、前の pass が終えられなかった claim は回収を続けます。画面で値を保存すると、次の pass から期限をまた数えます。

回収と resume は DB で直列化します。volume 一覧で候補が見つかると、pass はセッション row を resume と同じ順序（launch → session）で lock し、条件を再確認してから **claim**（`sessions.workspace_reclaim_id`・`workspace_reclaim_workspace_id`）を記録して commit します。その後 volume を削除し、同じ claim id で結果を記録します。

* 削除済みまたは既に存在しなければ claim を消し、`workspace_reclaimed_at` を記録します。
* mount 中（409）または別の設置環境のものなら claim だけを解除します。
* 削除呼び出しが throw した場合（timeout を含む）は claim を残します。volume が削除されたか不明なためです。次の pass は volume 一覧とは別に、未完了 claim から先に再処理します。削除済み volume は一覧に再び現れないためです。

claim が残る間、resume は **503 `BACKEND_UNAVAILABLE`（`retryable: true`）** で拒否します。このとき receipt も idempotency 記録も残さないため、同じ要求を再送すれば回収後に正常処理されます。`paused` セッションでは、resume を始めうるほかの要求も同じ 503 で拒否します。parked 要求への回答（回答は保存しません）と、既に終わった turn の interrupt です。期限を過ぎた parked 要求の期限切れ処理も回収が終わるまで待ち、その後の pass が期限切れを記録してグループを続けます。逆に resume が先に commit すると、セッションが `stopped` や `paused` を離れるため（`stopped` からは `active`、`paused` からは `resuming`）claim は拒否され、次の launch が volume をそのまま使います。再開成功時に `workspace_reclaimed_at` は消去します。

<a id="공통-object-store-보호" />
## 共通の object store 保護

既定の保護モード `locked` は versioning、Object Lock、SSE-S3（`AES256`）を要求します。checkpoint の object version は legal hold で保護します。既定 retention と object version を期限切れにする lifecycle は設定しません。復元には DB ポインターが指す正確な version が必要です。`/readyz` の準備状態だけで、そのデータが保持されたと判断しないでください。

AWS での作成と最小権限は [bucket の準備](/run-server/self-hosting/prepare-checkpoint-bucket)、バックアップと別の対象での照合は[復元訓練](/run-server/self-hosting/backup-and-restore)に従います。

| 会話ターンの記録（`conversation_turns`） | PostgreSQL | 無期限。会話、話題、依頼者、決定と理由、エージェントが書いた答え（本文）、出典（Slack メッセージの場所と入力受付の行の id。読み取りツールが読んだメッセージも入ります）、リリース id、Slack のインストールを持ちます。チャンネルのメッセージの本文はありません。Web 入力の行はその入力の本文を持ち（種類 `web_input`、状態 `received`、決定なし）、ターンの数には数えません。このリリースには人のメッセージで会話ターンを動かす経路がありません。運用者のコマンドで動かしたターンは依頼者の種類 `operator` で残ります。上限（モデル呼び出し 8 回、ツール呼び出し 12 回、2 分）に達して決定なしで終わったターンは、どの上限だったかと、その上限を誰が守ったか（ランタイム自身の数え `runner`、サーバーの錠 `server`）を持ちます | [管理者削除](#대화-기록의-관리자-삭제)が会話単位で削除します（Web 入力の行は残ります） | なし |
| 会話ターンの許可（`conversation_turn_permits`） | PostgreSQL | ターンと同じ。動いているターン 1 つに 1 行で、ランタイムが provider へのリクエストごとに送るトークンの hash（トークン自体は持ちません）、1 リクエストが使えるモデル・出力上限・リクエストの大きさ、ターンのアカウントを選んだ root、最後に拒否された理由（予算・同時呼び出しの上限・1 ターンの呼び出し数の上限）、読み取りツールの呼び出し数（上限を超えて拒否された呼び出しも含む）とスレッド読み取り数を持ちます。ランタイムがターンを受け取ると、許可の期限はその lease の終わりまで縮みます。予約はこの行ではなく、リクエストごとに会話呼び出しの台帳に別に取ります | そのターンが削除されるときに一緒に削除されます | なし |
| チャンネル要約（`channel_summaries`、`channel_summary_lines`、`channel_summary_line_sources`、`channel_summary_versions`） | PostgreSQL | 現在のバージョンは無期限。古いバージョンは過去 7 日のうちに一度でも現在のバージョンだったものだけが残り、戻せるのもそのバージョンだけです。行にはエージェントが書いた文と書いたエージェント、出典の行には Slack メッセージの場所（team、チャンネル、ts）・入力受付の行の id・話者・読んだ本文の編集時刻だけがあり、Slack メッセージの本文はありません。入力受付の行がもうないメッセージ（例: エージェントが関わったメッセージ）は、場所から作った id と `unknown` の話者で残し、話者を推測しません。行は M1 が判断バッファのまとまりを判断するときに一緒に出す一行です（shadow でも書きます）。判断したメッセージを 40 文字を超えてそのまま写した行は書きません。行の文が合わせて 4,608 バイト（約 1.5k トークン）を超えると、その行を書いたエージェントが判断モデルで古い行を一行にまとめます（チャンネルごとに 10 分に 1 回まで、エージェントのチーム予算）。まとめた行の出典はまとめられた行の出典をすべて合わせたもので、まとめる前のバージョンは履歴に残ります | reconciler が 7 日を過ぎた古いバージョンと、そのバージョンにしかない行を削除します。出典のメッセージが削除されると、slack ロールがその行をすべてのバージョンから削除します。出典のメッセージが編集されると、編集前の本文から作った行だけを削除し、編集後の本文から作った行は残します。チャンネル削除イベント（`channel_deleted`・`group_deleted`）が届くと、そのチャンネルの要約をすべてのバージョンと一緒に削除します。どのエージェントの削除イベントでも先に届いた後は、その時点で進行中だった判断も行を書きません。アーカイブと `channel_not_found` では削除しません。[管理者削除](#대화-기록의-관리자-삭제)はそのチャンネルの要約を履歴ごと削除します | なし |
| Slack メッセージの削除・編集の印（`deleted_sources`、`edited_sources`） | PostgreSQL | 作ってから 70 分。メッセージの場所（team、チャンネル、ts）、時刻、印の理由（Slack での削除 `slack_deleted`、管理者削除 `admin_deleted`）だけで、本文はありません。そのメッセージの入力受付の行か関与記録、またはそれを出典に持つターン・会話ターン・outbox の行・チャンネル要約の行があれば残ります | reconciler が削除します | なし |
| API key、利用者・メンバー・招待・連携アカウント | PostgreSQL | 無期限 | なし。key の失効と連携解除は記録を残すだけです | なし |
| 保存した秘密値 | PostgreSQL（master key で暗号化） | 無期限 | 人がその接続や App を削除したときだけ | なし |
| transcript と checkpoint の object | bucket の `sessions/<id>/` | pointer とその親 3 個、開いている push リクエストが固定した revision | [checkpoint GC](/run-server/self-hosting/backup-and-restore#3-checkpoint-gc) だけが削除します | Helm `checkpointGc.*`、compose `CHECKPOINT_GC_DRY_RUN` |
| 保管したセッションイベント | bucket の `session-archive/` | 無期限 | なし | なし |
| 作業領域の volume | Docker volume、Kubernetes PVC | 停止したセッションは 24 時間、一時停止したセッションは 24 時間 | scheduler が回収します。セッションは最後の checkpoint から再開します | コンソールの実行上限「停止したセッションの作業領域」・「一時停止したセッションの作業領域」 |
| プロセスの stdout ログ | compose は json-file、それ以外は設置の log driver | compose のサービスはコンテナごとに 50 MB のファイル 5 個。scheduler が起動した worker コンテナは Docker daemon の既定値 | ローテーション | compose の `x-logging`、worker コンテナとそれ以外は Docker daemon・ノード・collector の設定 |
| まだ精算されていない provider 呼び出しの使用量予約 | PostgreSQL | 使用量の報告が来るまで。課金されなかったとして解放された呼び出しは 7 日。解放されていない呼び出しは経過時間では削除しません | API と reconciler | なし |

- 内容（プロンプト、回答、ツールの入出力）が残るのは、turn の入力原文、セッションイベント、transcript、保管したイベントです。保存前のマスキングは[ログとイベントのマスキング](/run-server/self-hosting/explanation/isolation#로그와-이벤트의-가림)にあります。入力原文（`turns.message`）と transcript はマスキングしません。transcript はセッションを再開するときエンジンにそのまま返す原本なので、イベントでマスキングした値も transcript には残ることがあります。
- 解放されていない使用量予約は、セッションのコスト上限の判定に加算され続けます。報告が失われた呼び出しのコストを見落とさないためです。lease が切れても報告がなければ、reconciler が `Provider exchange reservation expired unsettled` 警告を一度残します。まだ流れている呼び出しでも出ることがあるため、警告だけでコストが漏れたと判断しません。
- トレースは既定ではエクスポートしません。有効にする方法は[トレースのエクスポート](/run-server/self-hosting/reference/configuration#트레이스-내보내기)にあります。

## 会話記録の管理者削除

ワークスペースの管理者（owner・admin）が求めたときに、チャンネル会話ひとつの記録を削除する運用者コマンドです。API route はありません。API コンテナーでコマンドを実行できる運用者が実行します。まず `--dry-run` で削除する行数を確かめます。

```bash
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/conversation-records.ts delete --conversation <conversation-id> --by admin@example.com --dry-run
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/conversation-records.ts delete --conversation <conversation-id> --by admin@example.com
```

- **会話 id。** エージェントとチャンネルで `conversations` 表から探します: `SELECT id FROM conversations WHERE agent_id = '<agent-id>' AND channel_id = '<channel-id>';`
- **削除するもの。** その会話のエージェントがそのチャンネルに残した関与記録、そのチャンネルの要約（すべてのバージョンの履歴を含む）、その会話の会話ターンの記録、その会話の判断バッファに入ったメッセージ。動いていた会話ターンは終わっても結果を書きません。そのターンのモデル呼び出しの台帳の行は残り、ターンを指さなくなります。チャンネル要約はチャンネルごとに一つなので、同じチャンネルの他のエージェントも同じ要約を失います。
- **残るもの。** セッション、ターンと入力の原文、入力受付の行、Web 入力の本文を持つ会話ターンの行、セッションイベント、transcript、checkpoint、receipt。会話の行も残り、最後に削除した時刻と削除した管理者を持ちます。
- **止まるセッション。** 削除する前に、記録が指すメッセージのうち、どのターンの入力でもないものに削除の印（`admin_deleted`）を付けます。そのメッセージを出典に持つセッションは、Slack でメッセージが削除されたときと同じように止まり（`SOURCE_DELETED`）、まだ送っていない答えは出ません。同じチャンネルの他のセッションと、自分の入力だけを持つセッションはそのまま動きます。Slack のメッセージはそのまま残ります。
- **`--by`。** その会話のワークスペースで無効化されていない owner か admin のアドレスです。削除した人として会話の行と receipt に残ります。そうでなければ何も削除せず `not_admin` で終わります。DM の会話は `dm_not_supported` で拒否します。
- **出力。** stdout に JSON 一行です。`outcome`（`deleted`、削除するものがなければ `unchanged`、`--dry-run` なら `dry_run`）、`conversation_id`、削除した行数（`engagements`、`summary_lines`、`buffered`、`turns`）、新しく付けた印の数（`marked`）、止めたセッションの id（`sessions_stopped`）。終了コードは 0 完了、1 予期しないエラー、2 使い方、3 存在しない会話、4 拒否です。
- **もう一度呼ぶ。** 結果は同じです。削除するものがなければ何も書かず `unchanged` です。前の実行が削除の後、セッションを止める前に途切れていたら、もう一度呼んだときにそのセッションを止めます。
- **監査。** 削除したものがあれば、監査ログに receipt `delete_conversation_records` が一行残ります。行為者は `--by` の人、対象はその会話、結果は削除した行数です。

## 終わりのわからない予算予約の解消

lease(5 分)以内に使用量の報告が来ず、終わりのわからない呼び出し(`unknown_at`)の予約は、遅れた報告が来るまで口座に押さえられたままです。たまって口座やエージェントが止まったら、運用者がこのコマンドで確認して解消します。API route はありません。API コンテナでコマンドを実行できる運用者が、組織の管理者(owner・admin)を `--by` に指定して実行します。セッションの呼び出しと会話呼び出し(会話ターンの呼び出しを含む)を同じコマンドで扱います。

終わったターンの予約は reconciler が自分で精算します。三つの条件がすべて満たされたときです: ターンが終わった(セッションのターンは `cancelled`・`failed`、会話ターンは `decided`・`no_decision`・`voided_by_delete`)、呼び出しの lease が切れた、呼び出しを開いてから provider 呼び出しの最大時間(1 時間)が過ぎた。セッションの呼び出しは自分のターンを記録しないので、その attempt に終わっていないか結果のわからない(`outcome_unknown`)ターンがあれば待ち、呼び出しを開いた時刻の前後 5 分にかかるその attempt のターンがすべて `cancelled`・`failed` でなければなりません。押さえた分を返すのではなく、使ったものとして確定し `resolution: "estimated"` と記録します。それ以外の行(決定を待つ `outcome_unknown` のターン、ターンのない判断・要約の呼び出し)はこのコマンドで解消します。

```bash
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/budget-unknown.ts list --limit 20
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/budget-unknown.ts resolve --account <budget-account-id> --by admin@example.com --dry-run
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/budget-unknown.ts resolve --call <call-id> --by admin@example.com
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/budget-unknown.ts resolve --call <call-id> --by admin@example.com --refund --reason "provider never billed"
```

- **`list`。** 終わりのわからない予約を最も多く押さえている口座と、すべての口座の合計を、reconciler のログ(`Budget reservations of unknown end held`・`... reported`)と同じ名前、同じ数で出します(`accounts` の `unknown_count`・`held_cost_usd`・`held_tokens`、`total`)。`lines` は予約ごとの行で、印の古いものから並びます。呼び出し id(`call_id`)、種類(`call_kind`: `session`・`conversation`、どちらの台帳にも行がなければ `unlinked`)、口座とその月、押さえている金額、セッション id またはエージェント・会話ターンの id です。`--account` で一つの口座の行だけを見て、`--limit`(既定 100、最大 1000)で数を決めます。何も書きません。
- **`resolve`。** `--call`(複数回指定できます)で選んだ予約を解消するか、`--account` でその口座の古いものから `--limit` 件(既定・最大 100)を解消します。一回に 100 件までで、残りがあればもう一度実行します。予約ごとに別々にコミットします。
  - 既定では押さえた分を使ったものとして確定します(`resolution: "spent"`)。終わりのわからない呼び出しを少なく課金しないためです。`--refund` は 0 に戻し(`refunded`)、`--reason` が必要です。理由のない `--refund` は終了コード 2 で拒否し、何も変えません。
  - どちらでも口座の予約から外れ、その呼び出しは進行中として数えなくなります。会話呼び出しは状態が `resolved` になって同時呼び出しの上限から外れ、セッションの呼び出しは台帳の行が解放されます。その口座とエージェントはすぐに新しい呼び出しを受けます。
  - 終わりのわからない予約でない行(精算済み、または lease が更新された行)は `not_unknown` として残し、触りません。存在しない id は `not_found` です。
  - `--dry-run` は解消する行と金額(`would_resolve`)だけを出し、何も書きません。
- **`--by`。** 選んだ予約が属するすべてのワークスペースで無効化されていない owner か admin のアドレスです。一つでも違えば何も書かず `not_admin`(終了コード 4)で終わります。実行中にロールを失うと、その場で止まり、`stopped_at` に止まった呼び出し id を出します(終了コード 4)。
- **監査。** 解消した予約ごとに receipt `resolve_unknown_budget` が一行、その予約を解消するトランザクションの中で残ります。行為者は `--by` の人、対象は口座の持ち主(人かチーム、口座がなければワークスペース)で、結果に呼び出し、口座とその月、確定した側(`resolution`)、理由(`reason`)、押さえていた金額と課金した金額、実行 id(`run_id`)が入ります。時刻は receipt の `created_at` です。 reconciler が推定で精算した行も同じ receipt を残します。行為者はなく、`by` は `reconciler`、`resolution` は `estimated`、`reason` と `run_id` は null です。
- **遅れた報告。** 解消した後に報告が来ても予約を開き直しません。実際の値と解消時に課金した値の差を、調整行(`budget_adjustments`)一つとして元の予約の口座に加えます。少なく使った報告は差を返し、多く使った報告と `--refund` で解消した行の報告は追加で課金します。調整は元の予約の月に付くので、月が変わった後に来ても今月の使用額は変わりません。調整行は元の予約の呼び出し id をキーに一度だけできます。同じ報告がもう一度来ても重ねて書きません。
- **出力。** stdout に JSON 一行です。`resolve` は `outcome`(`resolved`、解消したものがなければ `unchanged`、`--dry-run` なら `dry_run`、`not_admin`)、`run_id`、`resolution`、解消した数 `resolved`、行ごとの結果 `lines` を出します。終了コードは 0 完了(解消するものがないときも)、1 予期しないエラー、2 使い方、4 拒否です。

## セッションイベントの保管

長く休止したセッションのイベント行を checkpoint bucket に移す週次の job です。イベント以外の行は変えず、API は移した後も同じ応答を返します。

- **設定.** owner がコンソールの設定 > ワークスペース > 実行上限「セッション記録の保管」で決めます。休止期間は既定 180 日で、0 なら無効、それ以外は 30〜3650 日です。処理は「数えるだけ」（既定）と「実際に移す」から選びます。「数えるだけ」なら、移すセッション・イベント・バイトの数だけをログ（`Session archive completed`）に残します。
- **対象.** 最後の活動が休止期間より古いセッションです。実行中の turn、回答を待つ承認・質問、開いている push リクエストがあるセッションは飛ばします。移している間にセッションが再び動けば、そのセッションはそのままにします。
- **書き方.** イベント 1000 個または 8 MiB ごとに `session-archive/<session id>/` の下へ JSONL.gz の object を一つ create-only で書き、legal hold を掛け、読み直して照合した後にだけ DB の行を削除します。`locked` 保護モードでだけ動きます。worker はこの key を読むことも書くこともできません。
- **読み取り.** イベント一覧 API、SSE と `Last-Event-ID`、セッション一覧の最後のイベント時刻は、保管した範囲もそのまま反映します。API が object を読むため、保管したセッションは API に checkpoint object store が設定されているときだけ読めます。
- **日程.** compose では `maintenance` サービスが checkpoint GC の後に週 1 回実行します（`MAINTENANCE_INTERVAL_SEC`、既定 604800 秒）。すぐに一度実行するには `docker compose exec maintenance bun run apps/control-host/src/api/session-archive.ts` を使います。Kubernetes では CronJob（`sessionArchive.schedule`、既定 `0 5 * * 0`）が実行します。
- **元に戻す.** `bun run apps/control-host/src/api/session-archive.ts restore <session id>` が、そのセッションのイベントを同じ id で DB に戻します。object は hold が掛かったまま残ります。まだ対象なら次の pass が再び移すため、DB に置き続けるには先に休止期間を延ばすか 0 で無効にします。
- **設定を読めないとき.** 保存した値を読めなければ、job は何も移さず `Session archive refused: its settings cannot be read` を残して 1 で終わります。画面で値を保存し直すと解除されます。
- **バックアップ.** 保管した object はそのイベントの唯一のコピーです。bucket は DB とともに正本なので、両方を守ります（[Kubernetes 設置](/run-server/self-hosting/backup-and-restore#kubernetes-설치)）。

## workspace volume を失ったとき

セッションを続ける正本は volume ではなく checkpoint です。worker は turn が終わるたびに作業ディレクトリとエンジンの会話を checkpoint として object store に上げ、DB の pointer がその revision を指します。volume がなくなったセッションを resume すると、scheduler が空の volume を新しく作って worker を起動し、worker が pointer の checkpoint を復元して会話を続けます。

- **残るもの.** 最後に commit した checkpoint までです。どの turn まで含むかは、セッション詳細の `checkpoint_revision` と `durability.last_checkpointed_turn_id` で確認します。これが `durability.last_completed_turn_id` と同じなら、最後に完了した turn まで含みます。
- **失うもの.** 最後の checkpoint の後の作業、`.gitignore`・`.git/info/exclude` に一致する追跡されていないファイル（ビルド結果、依存関係、ignore された `.env`）、作業ディレクトリの外の状態（tmpfs HOME の `git config --global` など）です。すでに追跡しているファイルは ignore 規則に一致しても checkpoint に入ります。残す必要のある成果物は ignore されないパス（例: `out/`）に書きます。
