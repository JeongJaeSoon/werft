## Contract

`WERFT_API_KEY` and `WERFT_BASE_URL` configure SDK callers, not the server. See [SDK client configuration](/getting-started/client).

This reference covers formats, requirements, and when settings apply. Read [Compose upgrades](/run-server/self-hosting/upgrade-compose) and [Kubernetes upgrades](/run-server/self-hosting/upgrade-kubernetes) first for activation and rollback gates.

<a id="설치-상한" />
## Installation limits

API and scheduler refuse startup if the value below is missing or has an invalid format. They log all problems on one line using the same parser. Code has no default; Compose `x-installation-limits` and the chart's `config.limits` provide a local default. Running API readyz repeats the same validation as its config check. The session limits on waiting messages, kept input, cost, and tokens, and the turn time and provider retries, are not env but [execution limits set on the web](#웹에서-정하는-실행-한도).

| Variable | Meaning | When exceeded |
|---|---|---|
| `EXECUTION_SLOT_LIMIT` | Concurrent workers holding slots. 0 accepts input but launches nothing | Input remains accepted as queued |

<a id="api-설정" />
## API settings

At startup, API reads these through one parser. Unset values use defaults; invalid configured values (including empty strings) never silently fall back. API/scheduler/reconciler/worker numeric settings and installation limits share this rule. Missing required settings return `X is required`; invalid values describe the expected range, such as `X must be a positive integer`, without echoing the value, which could be a misplaced secret. All problems appear in one `Refusing to start: API settings are invalid` log line; startup stops. Running readyz repeats config validation.

| Variable | Default | Allowed range |
|---|---|---|
| `HEARTBEAT_TTL_SEC` | 30 | Greater than 12, at most 86400. Workers relinquish leases 10 seconds early (WORKER_LEASE_SAFETY_MARGIN_SEC) and heartbeat every 2 seconds (WORKER_HEARTBEAT_INTERVAL_SEC). A TTL at or below their sum loses attempts around their first heartbeat. Launchers do not pass these two worker settings, so validation uses defaults. A heartbeat answered 403 ends the worker at once. One answered 404 is sent again after 1 second, then at every heartbeat interval (2 seconds), and the worker ends if none is accepted by the time it relinquishes the lease (9–10 resends with the defaults). While resending, the worker sends no other gateway call and uploads no checkpoint; it goes on once a heartbeat is accepted |
| `SSE_MAX_STREAMS` · `SSE_MAX_STREAMS_PER_OWNER` · `SSE_REPLAY_MAX_BYTES` | 256 · 8 · 1 MiB | Positive integers |
| `LOG_LEVEL` | `info` | debug/info/warn/error, case-insensitive; empty means info. Scheduler/reconciler loops and egress-proxy reject invalid values by the same rule. Workers inherit scheduler's value |
| `WEB_DIST_DIR` | Unset (no console); control-host image: `/app/apps/web/dist` | Absolute path containing index.html, the apps/web build output |
| `LOGIN_ACCOUNT_FAILURE_LIMIT` · `LOGIN_ACCOUNT_FAILURE_WINDOW_SEC` | 5 · 900 | Count 1–1,000,000, window 1–86400 seconds. Failed passwords per email, and their window |
| `LOGIN_IP_FAILURE_LIMIT` · `LOGIN_IP_FAILURE_WINDOW_SEC` | 20 · 900 | Same ranges. Failed passwords per client network (one IPv4 address, or an IPv6 /64), and their window |
| `AUTH_IP_REQUEST_LIMIT` · `AUTH_IP_REQUEST_WINDOW_SEC` | 30 · 60 | Same ranges. Requests per network to the sign-in routes that take a token (setup link, invite, password reset, sign-in provider), successful ones included |
| `CLIENT_IP_HEADER` | Unset (the socket peer address) | The one header the proxy in front writes the client address to (letters, digits, `-`). Behind Cloudflare Tunnel: `CF-Connecting-IP` |

Every API replica counts sign-in attempts in one database table. A window runs a fixed length from its first attempt, and emails and addresses are kept only as HMACs. Signing in with the right password clears that email's failures. When an account locks, each live workspace it belongs to gets one `lock_login` receipt per window. An unknown email or a network that locks leaves one `Login locked` warning log line instead, and answers the same as a known email. Without `CLIENT_IP_HEADER` the socket peer address is counted. Behind a tunnel or proxy that address is private or loopback and stands for every user, so the network windows are skipped (one warning the first time) and only the email window applies. With the header set, only its last entry is trusted: set it only where the proxy in front always overwrites that header.

Every /v1 response logs `api.request.completed`: Hono route_template without actual ids, method, status, duration_ms including auth/routing, operation=api_request, outcome, reason_code, and request_id in log context. Bodies/credentials/provider keys are excluded. Terminate also logs `Terminate control transaction completed` under the same request_id, with millisecond pool checkout, binding/launch/session locks, individual SQL, commit/rollback, and total control-transaction timing. Join the logs by request_id to diagnose acceptance latency.

Immediate terminate of an already absent execution, or scheduler/reconciler confirmation of absence, emits control.result with operation=terminate, receipt control_id, outcome, reason_code, and effect_ms from durable acceptance to confirmation (equal to duration_ms). Overdue receipts first emit outcome=unknown/reason_code=deadline_exceeded; later confirmed absence upgrades the receipt and adds outcome=succeeded/reason_code=execution_gone.

WEB_DIST_DIR enables same-origin console serving. GET/HEAD outside /v1 and /internal serve files or index.html SPA fallback, allowing /login and /bootstrap refreshes. No fallback applies under /v1 or /internal; authenticated /v1/nope returns JSON 404 NOT_FOUND. Hashed /assets/ files cache immutable; missing assets return 404, not a page. index.html uses no-cache and CSP `script-src 'self'`, prohibiting inline scripts. control-host's web build stage builds apps/web and retains only dist; no separate web image exists. For local web-only work, `bun run --cwd apps/web dev` uses Vite and proxies /v1 to VITE_API_TARGET (default `http://127.0.0.1:3000`).

AUTH_MODE=none cannot coexist with EGRESS_AUTHORIZER_PORT. An enabled authorizer means workers reach API through proxy; none would let worker code impersonate arbitrary owners via X-Owner-Id, so startup refuses. Readiness validates AUTH_MODE itself (none|api-key).

Workers also cross-check startup settings. Missing WORKER_PROVIDER_MAX_RETRIES fails: this installation limit has no code default and scheduler always passes the value pinned to the launch. WORKER_NEXT_INPUT_WAIT_SEC must be below WORKER_REQUEST_TIMEOUT_SEC or every long poll times out. Scheduler/reconciler treat empty DATABASE_URL as unset and fall back to QUEUE_DATABASE_URL.

API/slack read current/previous runtime combinations through WORKER_IMAGE_RUNTIME/WORKER_IMAGE_PREVIOUS_RUNTIME. Copy runtime from images.yml worker digest JSON rather than typing it (`{"engine":…,"sdkVersion":…,"cliVersion":…,"profileDigestScheme":…}`). The engine is `claude` or `codex`; other names fail rendering with `images.worker.runtime.engine must be one of: claude, codex`. Custom images lack that JSON; extract with the same command:

```bash
docker run --rm -i --network none --entrypoint bun <worker-image> \
  run apps/worker/src/image-runtime.ts <<<'{}' | jq -c 'del(.profiles)'
```

**One worker image holds one engine.** `apps/worker/Dockerfile` picks it with the build argument `WORKER_RUNTIME`. Empty builds the Claude image; `--build-arg WORKER_RUNTIME=codex_app_server` builds the Codex image (the build log prints `codex-cli 0.167.0`, and any other version fails the build). CI builds the Codex image as its own image, `werft-worker-codex`. A deployment that runs Codex points `WORKER_IMAGE` (the chart's `images.worker`) at that image and sets the `runtime` read with the command above (`engine` is `codex`). The local stack builds the same image with the `infra/compose.codex-worker.yml` overlay. A deployment whose Codex sessions call the real OpenAI Responses API also adds `api.openai.com:443` to the proxy's `EGRESS_CREDENTIAL_ALLOWLIST`. The Codex engine has no budget of its own. The session cost and token limits (`SESSION_COST_LIMIT_USD`, `SESSION_TOKEN_LIMIT`) are enforced by the worker gateway on every provider call from the stored usage, and a session past a limit gets `403 BUDGET_EXCEEDED` on its next call. Limit of this: usage reaches the gateway through the proxy's report. A report lost after its retries (1s, 5s, 15s) leaves the stored cost low, and that session's later provider calls are then stopped only by the proxy's in-process gate (one process, lost on restart). The limit is therefore a soft one that relies on the stored usage. After a lost report, with several proxies or a restart, the overshoot has no bound. Even with every report delivered, one long response, parallel calls, and a call sent while a report is still in flight can pass the limit (the Claude engine's budget is also checked only after a call completes). Closing this with durable usage records is follow-up work.

**Each session runs on an image of its own engine.** The scheduler takes the engine from the session spec's runtime kind (`claude_agent_sdk` is claude, `codex_app_server` is codex) and picks among that engine's images only, by the rules below. A worker likewise claims only sessions of its own engine. When no image of the engine is listed, a session without a checkpoint waits without taking a slot (`waiting_for_engine_count` in the scheduler log), and one with a checkpoint stops before launch as `recovery_required` (attention `RESTORE_FAILED`, reason `incompatible_checkpoint`). One deployment can therefore run Claude and Codex agents together: list both engines' images in the image list (`WORKER_IMAGES`, below), at most two per engine. Give a two-engine list only once the scheduler, API, and Slack roles all run this version; an older version refuses the list and does not start. To roll back, first shrink the list to one engine. The upgrade check (`upgrade-check`) judges each engine on its own, and an upgrade that drops every image of one engine lists that engine's open sessions for approval ([an upgrade that drops an engine](/run-server/self-hosting/upgrade-kubernetes#3-검사-결과와-예외)).

**The sandbox of Codex auto mode.** A Codex session in `auto` mode runs the commands the model calls inside Codex's bubblewrap sandbox. Writes reach only the working directory, and the network is open. The sandbox is on by default. Before an `auto` session starts, the worker runs `true` once through `codex sandbox`. If that fails, the session does not start and stops (`recovery_required`); its reason carries bubblewrap's error line. The failure shows in this check at once, so no session sits waiting. `auto` never runs outside the sandbox. The other permission modes run whatever the sandbox's state.

bubblewrap uses namespace syscalls that Docker's default seccomp (Kubernetes's `RuntimeDefault`) blocks. So the scheduler puts the Werft seccomp profile on the containers of Codex images only. The profile is Docker's default one plus `clone`, `unshare`, `mount`, `umount2` and `pivot_root` (`scripts/codex-seccomp-profile.ts`). A Codex image is one whose declared runtime has the `engine` `codex`. An image with no declared runtime starts under the default seccomp, so its `auto` sessions are refused. A compose stack running Codex also needs `WORKER_IMAGE_RUNTIME`, read with the command above, for the profile to apply.

- **Docker backend.** The profile is passed with each container. Nothing is placed on the host.
- **Kubernetes.** Codex worker containers get the `Localhost` profile `werft/codex-sandbox.json`, a path under the kubelet's seccomp directory. The path is fixed: the chart refuses to render with `codexSandbox.localhostProfile` set. The Pod-level profile stays `RuntimeDefault`. A Pod that gets this profile also gets a required nodeAffinity on the node label `werft.codex-seccomp-profile=installed`. So it is placed only on a labelled node, and it waits `Pending` while no such node exists or has room. With `codexSandbox.provider=installer`, the chart's installer DaemonSet writes that one file to `<kubeletDir>/seccomp/werft/codex-sandbox.json` on the worker nodes, then puts this label on its own node. By default it is placed by `worker.nodeSelector` and `worker.tolerations`. The init container that writes the file has no capabilities and no API token, mounts only that directory writable, and keeps its root file system read-only. The container that sets the label does not run as root and mounts that directory read-only. Its ServiceAccount gets Node `patch` through a ClusterRole. RBAC cannot narrow that to "its own node", so a ValidatingAdmissionPolicy in the chart holds each request to the node the Pod runs on, and to setting this one label to this value. The policy needs Kubernetes 1.30 or later. The container that sets the label first sends a dry-run request that sets another value, and sets the label only after the policy refuses it. If it sees no refusal within about two minutes, it fails without changing anything and restarts. The label stays when the installer DaemonSet or the chart is removed, because the file stays on the node too. On a labelled node without the file (say, after the node's disk was wiped), the Codex worker container is not created (`CreateContainerError`). The scheduler counts that error, when seccomp caused it, as a failed launch as soon as it sees it. It deletes the Pod and launches again after a backoff; if the installer DaemonSet writes the file meanwhile, or the Pod lands on another node, the session goes on. At the launch failure limit (5 by default) it gives up the launch and frees the slot. The reason names the node, the profile path and the installer DaemonSet.

**Who provides the sandbox.** The chart's `codexSandbox.provider` is `disabled` (the default), `installer` or `external`. `installer` is the DaemonSet above and creates cluster-scoped objects (a ClusterRole, a ClusterRoleBinding, a ValidatingAdmissionPolicy and its binding). The default (`disabled`) and `external` create no cluster-scoped object, so an installer holding namespace permissions alone can run `helm install`. `disabled` means there is no Codex sandbox. The scheduler takes the value as `CODEX_SANDBOX_PROVIDER` and refuses a Codex image's worker before its Pod is created. That input's receipt fails at once with `CODEX_SANDBOX_NOT_INSTALLED`, the session returns to `idle`, and no launch failure is counted. The console, the Slack thread and the log ask to turn `codexSandbox.provider` to `installer`, or to have a cluster administrator install the sandbox first. Before anything fails, the console's agent screen shows a one-line warning to the admins of an agent that runs on the Codex engine (an OpenAI Responses API connection). Turning the agent on is not blocked. With `external` and no labelled node, the Pod waits `Pending`, and after 15 minutes the `NO_CAPACITY` reason adds a line to check the node label. The old `codexSandbox.installer.enabled` is gone; setting it stops the render and points to `codexSandbox.provider`.

**Placing the profile without the installer DaemonSet.** A cluster that ships profiles through the Security Profiles Operator or its node images sets `codexSandbox.provider=external`. The chart then creates neither the Node permission nor the admission policy. On every node Codex workers may run on, the operator does two things. First, put the chart's `files/codex-sandbox-seccomp.json` at `<kubeletDir>/seccomp/werft/codex-sandbox.json`. Then label only the nodes that hold the file:

```bash
kubectl label node <node> werft.codex-seccomp-profile=installed
```

Codex Pods are not placed on a node without the label, and stay `Pending` while no node has it. Before taking the file off a node, take the label off first (`kubectl label node <node> werft.codex-seccomp-profile-`). To remove the label everywhere after uninstalling the chart, pass `--all` instead of `<node>`. The commands for each node and what to do when upgrading the chart are in [Prepare nodes for the Codex sandbox](/run-server/self-hosting/prepare-codex-sandbox).

**Hosts with AppArmor on.** Docker's `docker-default` and containerd's default AppArmor profile both block `mount`. So on a host with AppArmor on (the default on Ubuntu and Debian), bubblewrap fails with `bwrap: Failed to make / slave: Permission denied` even under the seccomp profile, and `auto` sessions are refused. `kernel.apparmor_restrict_unprivileged_userns=1`, on since Ubuntu 23.10, blocks it even with AppArmor lifted (`unconfined`): `bwrap: setting up uid map: Permission denied`. The least that worked on Ubuntu 24.04 with Docker 28 is an AppArmor profile on the Codex container that is `docker-default` plus three rules: `userns,`, `mount,` and `pivot_root,`. It works whatever the sysctl says. Werft does not yet put an AppArmor profile of its own on Codex containers, so for now such hosts cannot use `auto`. The other permission modes work there.

**Turning the sandbox off.** Helm takes `codexSandbox.enabled=false`; compose takes `CODEX_SANDBOX=disabled` on the scheduler. Turning it off turns `auto` mode off with it. Codex containers start under the default seccomp, and no installer DaemonSet is made. `auto` sessions are refused before they start (`recovery_required`), with a reason naming this value. The other permission modes run as before. Use it to run Codex without `auto` on a cluster whose nodes cannot hold the profile. The off state also shows as a warning in the scheduler and worker startup logs. Changing the value changes the isolation stamp, so running workers are replaced.

**Kernel patches.** With the sandbox on, Codex containers can use user namespaces and mounts. A kernel flaw on that path can become a container escape. Apply kernel security updates promptly on nodes that run Codex sessions.

**Switching engines.** With the single-image settings, setting `WORKER_IMAGE` to the new engine's image and `WORKER_IMAGE_PREVIOUS` to the current one keeps the old engine's sessions starting on the previous image, with or without a checkpoint, while the new engine's sessions start on the new image. To replace the `WORKER_IMAGE` of a running deployment with another engine's image, follow the upgrade check (`upgrade-check`) as it is: the new configuration's `WORKER_IMAGE_PREVIOUS` must be the image deployed now, and every session the check reports as unresumable (not only a different checkpoint engine, but also a mismatched SDK or CLI version or digest scheme, or an unrecorded runtime) must be approved in `upgrade.approvedSessions` as exactly the list the check prints. Checkpoints do not move between engines, so the previous (old-engine) image can only be emptied once the sessions running on it have ended.

With neither runtime, no runtime reading or pin preservation applies. Previous-only or unreadable values reject startup. When configured, releases made with the previous image and their sessions keep running. A release pins the runtime version its image shipped when it was made, so a release whose version neither the current nor the previous image ships takes no new session; release that agent again.

Set the following only to send GitHub Packages bot tokens to another host, such as GHES/test registries. URLs must be http(s) without userinfo/query/fragment, or startup fails. Hosts must also be in proxy EGRESS_CREDENTIAL_ALLOWLIST, or EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST for private addresses. The API sends the token check only to the host:port of `GITHUB_PACKAGES_API_URL` and follows no redirect. The default (`https://api.github.com`) is called only when it resolves to a public address; a URL you set may be plain http or private. A name that resolves to a metadata or link-local address is refused either way.

| Variable | Default | Meaning |
|---|---|---|
| `GITHUB_PACKAGES_API_URL` | `https://api.github.com` | Queries token scopes (GET /user) |
| `GITHUB_PACKAGES_NPM_URL` | `https://npm.pkg.github.com` | github-npm upstream |
| `GITHUB_PACKAGES_RUBYGEMS_URL` | `https://rubygems.pkg.github.com` | github-rubygems upstream |

## Execution limits set on the web

An owner saves these under **Settings > Workspace > Execution limits**, not in env (`PATCH /v1/installation-config`). They are one for the whole installation; a save applies at once on that API and within 10 seconds on other replicas and on the scheduler, slack, and metrics roles. With nothing saved, the default applies. No role reads the old env; migrate carries it in once at upgrade ([Execution limits moved to the web](/run-server/self-hosting/upgrade-compose#웹으로-옮긴-실행-한도)).

| Field on the screen (old env) | Default | Meaning and allowed range | When exceeded |
|---|---|---|---|
| Human answers (`PENDING_REQUEST_TTL_SEC`) | 1800 | Integer 1–604800 seconds. Lifetime of approval/question requests. Workers wait this long after registration; a request already registered keeps the wait it was given. Until the gateway registers a request, the worker waits 30 minutes. The turn time includes waits and still bounds them | The unanswered request closes |
| Turn time (`MAX_TURN_SECONDS`) | 3600 | Integer 1–604800 seconds. Turn wall-clock limit including approval waits, passed as `WORKER_MAX_TURN_SEC` | `failed(turn_timeout)`, or `outcome_unknown(turn_timeout)` if engine does not respond |
| Model request retries (`PROVIDER_MAX_RETRIES`) | 2 | Integer 0–10. Retries for failed provider requests, passed through `WORKER_PROVIDER_MAX_RETRIES` to SDK `CLAUDE_CODE_MAX_RETRIES`. 0 ends the turn on first failure | `failed(api_error)`; turn result retains api_error_status/provider_error/last_retry_status |
| Session cost (`SESSION_COST_LIMIT_USD`) | 25 | USD above 0, at most 1000000. Estimated cumulative session cost: proxy-metered provider usage converted through platform prices | No new turn dispatch; session attention.code=BUDGET_EXCEEDED; worker releases slot. Input still accepted as queued |
| Session tokens (`SESSION_TOKEN_LIMIT`) | 0 (no limit) | Integer 0–9007199254740991. Cumulative provider tokens from the same calls, independent of prices | Same as session cost. Shared budgetExceeded returns BUDGET_EXCEEDED for whichever limit is reached first; attention.reason names only reached limits |
| Waiting messages (`QUEUED_INPUT_LIMIT_PER_SESSION`) | 20 | Integer 1–100000. Queued turns allowed per session | `429 RATE_LIMITED`, `retryable:true`, `Retry-After: 5` |
| Kept input (`STORAGE_LIMIT_BYTES`) | 1073741824 (1 GiB) | Integer 1–9007199254740991 bytes. Installation-wide retained input-message UTF-8 bytes, excluding events/checkpoint objects/worker disk (workspace quotas cover disk) | `413 STORAGE_LIMIT_EXCEEDED`, `retryable:false` |
| Workspace size (`WORKSPACE_ENFORCE`) | `warn` | `warn`, `fail`, or `off`: what a worker does when its workspace outgrows its quota. A worker takes the value at its claim, so one already running keeps the value it was given | `warn` only logs `worker.turn.workspace_quota_exceeded`, `fail` stops the turn that outgrew it, `off` does not measure. Workers of a Docker installation with `EXECUTION_WORKSPACE_QUOTA=off` run as `fail` whatever this says |
| Session event archive: idle before archiving (`SESSION_ARCHIVE_AFTER_DAYS`) | 180 | 0 (off), or a whole number of days from 30 to 3650. The archive job moves the events of sessions idle longer than this into bucket objects, and reads the value from the database on each run ([session event archive](/run-server/self-hosting/reference/storage#세션-이벤트-보관)) | Not applicable |
| Session event archive: what the archive job does (`SESSION_ARCHIVE_DRY_RUN`) | Count only (`true`) | Count only, or move the events. Counting only logs what it would move. The screen says so when, by the API's object store settings, the installation cannot archive | Not applicable |
| Stopped sessions' workspaces (`EXECUTION_WORKSPACE_STOPPED_TTL_SEC`) | 86400 (a day) | A whole number from 0 to 315360000 seconds (3650 days). How long a `stopped` session's workspace (Docker volume, Kubernetes PVC) is kept from the stop. 0 reclaims it on the next reclaim. The scheduler reads it from the database on each reclaim ([worker workspaces](/run-server/self-hosting/reference/storage)) | The scheduler reclaims the workspace; the next resume restores from the checkpoint |
| Paused sessions' workspaces (`EXECUTION_WORKSPACE_PAUSED_TTL_SEC`) | 86400 (a day) | A whole number from 0 to 315360000 seconds (3650 days). How long a `paused` session's workspace is kept from the pause, for a session with a checkpoint a resume accepts | As for stopped sessions |

The scheduler reads the turn time and model request retries each pass and pins them to every launch that pass reserves; the worker starts with the pinned values. After a change, of the workers started with other values, an idle one stops at once and one in a turn finishes that turn under its values and then stops. The session's next launch gets the new values ([changing the turn time and retries](/run-server/self-hosting/explanation/isolation#turn-시간과-재시도를-바꿀-때)).

**With no usable value.** A key holding an env value that could not be carried in (out of range), or a saved value this release does not accept, is blocked. It never runs on a default. Only what reads that key is refused; the screen shows a notice on that field, and saving a value lifts it. Settings that cannot be read for over 60 seconds (a database outage) do the same to every key.

- Human answers: registering a new permission request or question is refused `503 BACKEND_UNAVAILABLE` (`retryable:true`). The worker sends it again.
- Session cost, tokens, waiting messages, kept input: creating a session and taking a message are refused `503 BACKEND_UNAVAILABLE`. A request already taken, sent again with the same `Idempotency-Key`, still gets its stored answer. `GET /v1/limits` and `GET /v1/sessions/{id}/usage`, which show these four values and the turn time and retries, also answer `503` while any of them is blocked. Session cost and tokens stop more besides. The scheduler skips only its launches (log `Launches skipped: the session limits cannot be read`) and goes on with kills and workspace reclaim. A worker's claim, next input, provider-call open, and finalize get `503` (retried). Reopening a provider call already open, and the answer of a finalize already committed, still go through. Metrics leave the launch-queue gauges (`werft_launch_queue_*`) without samples.
- Workspace size: a worker's claim gets `503`, so no session starts.
- Turn time, model request retries: the scheduler reserves no new launch (log `Launches skipped: the worker limits cannot be read`). A launch reserved before the values were pinned is not rebuilt; its resource is kept as it is (log `Launch held: the worker limits it would start with cannot be read`). Pinned launches and running workers go on with their values, and kills and workspace reclaim go on too.
- Stopped and paused sessions' workspaces: while either is blocked, the scheduler reclaims no new `stopped` or `paused` session's workspace (log `Workspace TTLs cannot be read; keeping every stopped and paused session's workspace`). Closed sessions' workspaces, and reclaims an earlier pass left unfinished, still go, and launches go on.

**The cost and token limits also hold each provider call.** Before the egress proxy sends a billed provider call (Messages, Responses), it opens the call with the API. The API adds the reserves of the session's unfinished calls and this call's reserve to the session's spend so far. When the sum reaches a limit, it refuses with `403 BUDGET_EXCEEDED`, and the proxy does not send the call to the provider. A reserve counts the request's bytes as input tokens at the dearest cache-write rate (2× for Claude, 2.5× for OpenAI), and the request's whole output cap as output (32,768 tokens for a Responses request without a cap). One `claude-sonnet-5` or `gpt-5.5` call reserves roughly $1–2.

- A session stops one call's reserve before its limit. With a session cost limit below one call's reserve, the first call is refused.
- A lowered limit holds a running session from its next provider call. A raised one reaches a running worker at its next claim (the worker takes its remaining budget at the claim, as the SDK's `maxBudgetUsd`).
- The cost a session records is the usage the provider reported, not the reserve. A call whose usage report finally failed goes on counting its reserve.
- When the API cannot open a call within 5 seconds, the proxy does not send it and answers `503`. The engine retries.
- The limits are estimates. One long answer can go up to its call's reserve. A Responses request without an output cap can exceed it by whatever it reasons past 32,768 tokens.

## Scheduler, worker container, and egress settings

Scheduler reads these to create workers. Unset values use defaults; invalid formats reject startup. User, HOME/workspace paths, tmpfs sizes, credential port, and stop timeout enter werft.isolation ([isolation](/run-server/self-hosting/explanation/isolation)); changing them replaces running workers. CPU/memory/PID limits apply next launch.

WORKER_MEMORY_MB is chosen with MAX_TRANSCRIPT_BYTES; see [capacity](/run-server/self-hosting/capacity) for node counts and changes.

Scheduler receives current WORKER_IMAGE/WORKER_IMAGE_RUNTIME and previous WORKER_IMAGE_PREVIOUS/WORKER_IMAGE_PREVIOUS_RUNTIME, using API-equivalent runtimes. Previous image/runtime must be set together; one alone fails. Without current runtime every launch uses current image. Otherwise, match each checkpoint engine/SDK/CLI/profile digest scheme to current/previous, preferring current when both match. New sessions, checkpoint-free sessions, and old unrecorded checkpoints use the newest image of the session's engine (current, or previous when only previous runs that engine); with no image of that engine they wait without a slot. No match stops before launch as recovery_required (incompatible_checkpoint), with checkpoint_restore_failed detected_at: "launch". retry_restore is available.

**Image list (`WORKER_IMAGES`).** One JSON array can give the images instead of the four values above. Each entry is `{"image": "<repository>@sha256:<digest>", "runtime": {…}, "released_at": "2026-11-10T00:00:00Z"}`, newest first within each engine. Each engine's first unretracted entry is the image that engine's new sessions start on; the rest resume checkpoints sealed on their combination, chosen by the rules above. Copy `runtime` from images.yml, and make `released_at` strictly decrease in the array's order among entries of the same engine (equal or reversed times fail startup). Entries of different engines are not compared, so two engines may share a release time. A tag reference, the same digest twice, an unknown field, or more than two unretracted images of one engine also fail startup, as does setting `WORKER_IMAGES` beside the four values above. The scheduler, API, and slack role read the same value, and the workspace quota helper runs from the first unretracted entry's image. The upgrade check (`upgrade-check`) judges a list too ([Pre-upgrade check](/run-server/self-hosting/upgrade-kubernetes#업그레이드-전-검사)). The chart renders `WORKER_IMAGES` from `images.workers`, a list of `{repository, digest, runtime, releasedAt}` entries, newest first. The digest and runtime of `images.worker` and `images.workerPrevious` must then stay empty. A packaged chart defaults `images.workers` to its release's Claude and Codex images. To give one image through `images.worker`, set `images.workers: []` beside it. Helm replaces a list as a whole instead of merging it into the default, so a list in your values never gets the images of a later chart. A list that fails startup above fails rendering too, and `releasedAt` must be an RFC 3339 time with seconds and at most three fractional digits. The compose stack does not use a list: its scheduler always has `WORKER_IMAGE`, so setting `WORKER_IMAGES` stops it from starting. A compose stack that runs both engines uses the single values: the Codex image in `WORKER_IMAGE`, the Claude image in `WORKER_IMAGE_PREVIOUS`, and each runtime read from its built image with the command above. `infra/compose.two-engines.yml` gives the order (build both images, read the runtimes, start the stack). Given the two images without their runtimes, the scheduler does not start.

**Retraction (`retracted`).** When an image must not run any more, such as for a vulnerability no rebuild can fix, keep its entry in the list with `"retracted": true` (in the chart, `images.workers[].retracted: true`). No session launches on a retracted image. A checkpoint sealed on it resumes on an unretracted image of the same engine, SDK, and CLI (a fixed build) when the list has one. When a session whose previous launch ran a retracted image moves to another image, reserving that launch records a `worker_image_replaced` event on the session (the images before and after, reason `retracted`) and, if the session has a Slack thread, posts a notice there. Without one, the session stops before launch in `recovery_required`, and its `RESTORE_FAILED` attention reads reason `runtime_retired`. List a fixed image and retry with `retry_restore`, go on without the checkpoint with `start_fresh`, or close the session. A launch already up on a retracted image is not left there either. One no worker has bound yet is torn down and given back unbuilt, and its session chooses an image again. One whose worker is running is torn down once its open turn ends (the same drain as `stale_isolation`; past the maximum turn length plus a finalize grace it is not waited on). That session too chooses an image on its next launch, and stops as above when none is left. A launch reserved before images were stored is left as it is once a worker has bound, since nothing says what it runs. The scheduler logs this replacement as `Execution resource runs a retracted worker image`, and records it under the reason `stale_isolation` (so a scheduler rolled back to one that does not know another value still reads it). An image only removed from the list, not retracted, is not torn down this way. A launch reserved on it is rebuilt on that image, as stored, when it has to be rebuilt before a worker binds it (it is given back unbuilt instead when the list has no unretracted image of its engine, or when it cannot be told apart from a retracted image), and a launch whose worker has bound keeps running. To stop launching on an image, retract it instead of removing it. The image limit counts unretracted images only, and a list with every image retracted still starts: nothing launches (a launch on an image no longer listed is not built again either), no workspace quota probe runs, sessions with a checkpoint stop as `runtime_retired`, and the scheduler logs one error when it starts. The same holds for one engine's sessions when every image of that engine alone is retracted. Its sessions with no checkpoint that wait for a launch show the `NO_WORKER_IMAGE` attention (reason `runtime_retired`), which clears once an unretracted image of that engine is listed. The upgrade check does not count a retracted image as one that restores checkpoints.

A worker image built before the profile removal cannot read the control-host answers of the profile removal release, so it is outside the support window. In the upgrade to that release, the upgrade check can make `WORKER_IMAGE_PREVIOUS` that image, but no session launches on it ([Upgrade order of the profile removal release](/run-server/self-hosting/upgrade-compose#프로필-제거-릴리스의-업그레이드-순서)).

Workers report actual image runtime at claim. Mismatch causes API LAUNCH_FAILED with reason_code worker_image_mismatch and records refusal for that image/configuration. Further launches for it wait; scheduler logs images_refused as error and exits 1. Correcting image configuration (changed values) restores launches next pass. Sessions themselves do not become failed.

Deploy API first, then scheduler WORKER_IMAGE: new workers send claim image_runtime, rejected by old APIs. The upgrade to the profile removal release is an exception: change both together in one upgrade ([Upgrade order of the profile removal release](/run-server/self-hosting/upgrade-compose#프로필-제거-릴리스의-업그레이드-순서)).

## Kubernetes env and values

EXECUTION_BACKEND selects local_docker (default, also when empty) or kubernetes; other values reject startup with an error naming the value. Kubernetes ignores Docker settings (DOCKER_HOST, EXECUTION_DOCKER_*, EXECUTION_WORKSPACE_QUOTA) and socket, and skips Docker egress-isolation/quota preflights. Chart NetworkPolicy provides isolation; the workspace requests PVC size, while actual enforcement depends on storage. Fixed stop/request timeouts are 120s + 30s, requiring SCHEDULER_PASS_TIMEOUT_SEC >150. migrate-workspace is local_docker-only.

On readOnlyRootFilesystem Pods, status files need writable directories. Default /tmp/scheduler-status.json and /tmp/reconciler-status.json work with /tmp emptyDir. Override paths with SCHEDULER_STATUS_FILE/RECONCILER_STATUS_FILE. Loops write adjacent `<status file>.<pid>.tmp` then rename; scheduler also stores .quota-verified nearby. The whole directory, not just the file, must be writable.

Shared env matches Docker: WORKER_IMAGE, WORKER_GATEWAY_URL, EXECUTION_EGRESS_PROXY_URL, EXECUTION_EGRESS_CREDENTIAL_PORT, EXECUTION_INSTALLATION_ID, EXECUTION_WORKSPACE_QUOTA_MB, EXECUTION_WORKSPACE_GC_MIN_AGE_SEC, S3_BUCKET, AWS_REGION. Kubernetes adds constraints:

- WORKER_IMAGE must be `repository@sha256:<digest>`.
- EXECUTION_INSTALLATION_ID must be a lowercase DNS label, at most 32 characters.

Kubernetes-only settings:

`EXECUTION_WORKSPACE_ENFORCED_BY_STORAGE` defaults to `false` when unset and accepts only exact `true`/`false`. Empty values, whitespace, uppercase, `1`/`0`, and `on`/`off` reject startup without exposing the original value. Helm generates it from `worker.workspace.enforcedByStorage` (default `false`): an operator declaration that storage hard-enforces requested bytes for every workspace PVC in this installation, including existing PVCs. With an empty StorageClass, the cluster default applies and operators must verify enforcement for each PVC. Werft does not verify it. Only the declaration path passing the heuristics of a dedicated writable mount (not `/`, `rw` present, `ro` absent), filesystem size 0.95–1.05 times the request, and PVC capacity at least the request yields bytes `hard`/inodes `unknown`. See [Storage and limits](/run-server/self-hosting/reference/storage). Changing the declaration leaves PVCs, the isolation stamp, and existing Pod env unchanged; only new Pods receive the new value.

## Usage and cost metering

- Credential routes meter session cost. Proxy reads usage from 2xx /v1/messages responses, JSON or SSE, and reports POST /usage to authorizer when responses finish/disconnect. count_tokens/error responses do not count.
  - Incomplete usage is estimated conservatively. Streams ending before message_stop count each delivered content character as one output token and each delivered web-search result block as one search. Unreadable JSON (truncated, over 8 MiB, or invalid JSON) uses request estimation: 1 request byte/input token and full max_tokens/output. Proxy logs Provider usage estimated; ledger estimated=true.
  - API converts through prices to USD, rounds up to micro-dollars, writes one provider_usage row/exchange and adds session cost in the same transaction, keeping ledger/session totals aligned.
  - Engine calls and tool calls made directly with engine tokens are metered equally.
  - Proxy assigns exchange ids. Failed authorizer reports retry after 1, 5, and 15 seconds; ids count once. Final failure logs Provider usage went unreported and leaves that exchange uncounted.
- SDK turn-end total_cost_usd increments appear only in turn result cost_usd, not session cost. Engine maxBudgetUsd still uses SDK values. Pre-proxy-metering sessions retain costs previously accumulated from SDK values.
- Platform code owns prices by model: input/output/cache write (5-minute 1.25×, 1-hour 2×)/cache read. Each entry records the day it was checked against the [official prices](https://platform.claude.com/docs/en/about-claude/pricing). New models/prices require release updates.
  - Fast prices are the model's standard prices times its fast multiplier. They currently cover Fable 5.2/Mythos 5.2 ($16/$80), Opus 5.5 ($8/$40), and Opus 5/Opus 4.8 ($10/$50). Cache multipliers apply to fast prices. speed uses response usage.speed, then request speed, then standard.
  - For a model the Claude table names, a `fast` response without a fast multiplier or an unknown speed value is priced at the model's own rates (long-prompt rates included) times the largest multiplier either table has (now 6x, OpenAI's Ultrafast). This is how the OpenAI table prices a tier its entry does not list; the ledger records priced_by=table.
  - Models neither table names use per-item highest rates across both tables. Authorizer warns Provider usage priced at the fallback rate; ledger priced_by=fallback. When a model the Claude table does not name is priced at the highest rates, it may be an OpenAI call: a model neither table names, or an OpenAI model past 272K input tokens whose table has no long-context rates. Then, when the speed is not `standard`, the highest rates are multiplied by the largest multiplier the OpenAI table has for that tier: 2.5x for `fast`, 6x for any other tier. A model the OpenAI table names keeps its own entry's multiplier when that is larger (6x for a tier its entry does not list). At any speed a cache write is counted at 1.25x the input rate, a long-lived one at 2.5x (OpenAI's 12-hour write). A model the Claude table names uses its own fast multiplier or the largest multiplier above, and Claude's cache write multipliers, instead.
  - OpenAI models are priced from a separate OpenAI table. Each entry records the day it was checked against the [official prices](https://developers.openai.com/api/docs/pricing). A speed tier multiplies the model's standard rates. `fast` is 2x for most models and 2.5x for `gpt-5.5`. Ultrafast (`ultrafast`) exists only for `gpt-6-astra` and `gpt-6.1-sol`, at 6x. A tier the model's entry does not list is counted at the largest multiplier the table knows (6x), whatever its name. Pro models (`gpt-5.5-pro`, `gpt-5.4-pro`, `gpt-5.2-pro`, `gpt-5-pro`, `o3-pro`) have no cache discount, so a cache read is counted at the input rate. Pro rates are not part of the highest rates above. Only a Pro model's call past 272K input tokens, when the table has no long-context rates for it, is counted at the highest Pro rates.
  - Response usage.server_tool_use web searches add $0.01 each ($10/1,000). Web fetch has no charge beyond tokens. Code execution is excluded: free with web search/fetch, otherwise billed by container time with organizational free allowances, not invocation count. All three counts and speed are recorded in provider_usage.
  - Models from 4.6 onward apply 1.1× to every token price (fast/cache included) for inference_geo: "us", excluding web-search fees. Geo follows response usage.inference_geo, then request inference_geo, then unknown (workspace may default to us). Non-global/us values use the model's own prices times the largest geo multiplier (1.1×), priced_by=table; a model neither table names uses highest prices ×1.1. Ledger records inference_geo. Old APIs reject this new field with 400, causing unreported exchanges. Update API including migration before proxy ([Compose order](/run-server/self-hosting/upgrade-compose#2-api--proxy--worker-순서), [Kubernetes order](/run-server/self-hosting/upgrade-kubernetes#1-대상-chart와-제어-영역-우선-교체)). New API accepts old reports without it.
  - Pre-4.6 models (Opus 4.5/4, Sonnet 4.5/4, Haiku 4.5) do not support inference_geo and use standard prices regardless of geo. Their window is 200K without published long-context rates; input+cache write+cache read over 200K uses highest prices, priced_by=fallback, times the speed multiplier above when the speed is not standard. Models 4.6 onward use standard prices for the full 1M, except Haiku 5.5: a prompt (input+cache write+cache read) over 100K pays its higher prices on every part ($0.50/$2.50, cache read $0.05).
  - Batch is irrelevant: credential routes do not expose /v1/messages/batches.
- Token limits sum input_tokens + cache_creation_input_tokens + cache_read_input_tokens + output_tokens from each provider_usage row into sessions.provider_tokens through an INSERT trigger in the same transaction. This includes calls from pre-0127 APIs during rollout/rollback. Cache reads count as model-processed tokens; estimates count as estimated. The migration backfills provider_usage totals, but cannot recover tokens from older SDK-cost-only sessions. Totals saturate at 2^53-1 (Number.MAX_SAFE_INTEGER, migration 0129). Numeric trigger arithmetic prevents oversized tokens from rolling back usage/cost writes.
  - SDK has no token-budget option; in-turn enforcement relies on egress rejection/reauthorization below. Calls opened after reaching limits are rejected and turns finish failed(budget_exceeded); later turns are blocked with BUDGET_EXCEEDED. Proxy uses Messages error format with message starting BUDGET_EXCEEDED:, but does not determine reason from text. Engine reports the 403 as api_error; exchanges cut by reauthorization also remain api_error if retries are exhausted (PROVIDER_MAX_RETRIES=0). Finalize converts api_error to budget_exceeded and receipt BUDGET_EXCEEDED if the session is already over budget, clearing provider_error diagnostics. A 403 below limits remains api_error.
- Cost/token limits are judged after calls finish. Concurrent open calls may all pass authorization; active turns can exceed limits.
- Authorizer rejects provider egress tokens at or above cumulative cost/token limits with 403 BUDGET_EXCEEDED. New exchanges fail immediately; open exchanges disconnect at the next reauthorization (every 30 seconds). Repository/object-store routes remain available.

## Trace export [#트레이스-내보내기]

Only the API reads these settings. Export is off by default: with none of the keys set, it creates no spans and sends nothing. When it is on, the `trace_id` and `span_id` in logs are filled inside an active span. Any collector that accepts OTLP/HTTP (protobuf) works. Example collectors are in [Observability](/observability).

| Key | Default | Meaning |
|---|---|---|
| `OTEL_TRACES_EXPORTER` | `none` | `none` or `otlp` |
| `OTEL_EXPORTER_OTLP_ENDPOINT` / `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | None | Collector address. The first gets `/v1/traces` appended; the second is used as is. With `otlp` and neither set, the API does not start |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | `http/protobuf` | Only this value is accepted |
| `OTEL_EXPORTER_OTLP_HEADERS` / `OTEL_EXPORTER_OTLP_TRACES_HEADERS` | None | `key=value,key=value` (values percent-encoded, printable ASCII only). For the same name, the second wins. A malformed value stops startup. These are secrets: give them only through an env file. Values never appear in logs or error messages |
| `OTEL_SERVICE_NAME` | `werft-api` | Service name |
| `OTEL_TRACES_SAMPLER` / `OTEL_TRACES_SAMPLER_ARG` | `always_on` / `1.0` | `always_on`, `always_off`, `traceidratio` (ratio 0 to 1) |
| `TRACE_TENANT_HEADER` | None | `<header name>: <value template>`. `{workspace_id}` in the template is replaced with the workspace id and the header is added to every batch |

| `TRACE_CONTENT_MODE` / `TRACE_CONTENT_MAX_BYTES` | `full` / `32768` | Whether prompts, answers and tool input/output go on spans (`full` or `metadata`), and the byte limit of one content attribute. One value applies to the whole installation |
| `TRACE_INGEST_PORT` / `TRACE_INGEST_MAX_REQUEST_BYTES` / `TRACE_INGEST_MAX_BYTES_PER_MIN` / `TRACE_MAX_BYTES_PER_TRACE` / `TRACE_FENCED_GRACE_SEC` | `4319` / 4 MiB / 32 MiB / 20 MiB / `300` | Port and limits of the ingest listener. A value of 0, a negative value or a non-number stops startup with the key named |

The format of `TRACE_TENANT_HEADERS_FILE` follows. The values are secrets, so keep the file out of the repository.

```json
{ "<workspace_id>": { "<header name>": "<secret value>" } }
```

**Minimal configuration.** Give the api these values. Prompts, answers and tool input/output travel as span attributes (`gen_ai.*`), so no log store is needed.

```bash
OTEL_TRACES_EXPORTER=otlp
OTEL_EXPORTER_OTLP_ENDPOINT=https://otel-collector.example.com:4318
TRACE_INGEST_URL=http://api:4319
EGRESS_PRIVATE_ALLOWLIST=api:3200,host.docker.internal:3200,api:4319
```

- **Compose.** Put the values in the shell that starts compose or in `.env`; they reach the api container under the same names. Workers reach the ingest listener through the egress proxy, so add `api:<TRACE_INGEST_PORT>` to the `EGRESS_PRIVATE_ALLOWLIST` default `api:3200,host.docker.internal:3200`.
- **Kubernetes.** Give the keys in `api.extraEnv`. The Service and NetworkPolicy need the port too, so change it only with `config.tracing.ingestPort` (default `4319`) and do not set `TRACE_INGEST_PORT`. `TRACE_INGEST_URL` is `http://<api Service name>:4319`, and set `config.egress.privateAllowlist` to `<api Service name>-internal:3200,<api Service name>:4319`.
- Workers never call the collector. If the collector host is in `EGRESS_PRIVATE_ALLOWLIST` or `EGRESS_ALLOWLIST`, the api logs a warning at startup. `OTEL_*` keys are not passed to workers or the engine.

**On the collector side.**

- Set the collector's per-trace size limit above `TRACE_MAX_BYTES_PER_TRACE`. A smaller limit makes the collector drop large traces.
- Without a tenant header, traces of every workspace land in one place. Let only operators see the backend's screens.
- With `TRACE_CONTENT_MODE=full`, prompts, answers and tool input/output reach the collector. Use `metadata` to keep them out.

**Spans.** Each `/v1/**` request starts a new root span `{METHOD} {route_template}` (for example `POST /v1/sessions/:id/turns`). A `traceparent` sent by the client is kept only as a link, not as the parent, and its sampled flag is not followed. Health and metrics paths have no spans. A turn's spans belong to a separate trace set by the session and turn number (root `werft.turn`), linked to the span of the request that queued the turn and to the previous turn's root. A worker gateway call becomes a child span in that turn trace only when it carries that trace's `traceparent`; other gateway calls (heartbeats, long polls and the like) have no spans.

## Session title generation [#세션-제목-생성]

When a session is created without `title`, the first message cut at 80 characters becomes the title. When the first turn ends `completed`, the API asks once for a short title from that turn's message and answer, and replaces it.

| Variable | Default | Allowed values |
|---|---|---|
| `SESSION_TITLE_EGRESS_URL` | compose `http://egress-proxy:3129` | Address of the egress proxy's credential route. Empty turns the feature off. Sessions on a Codex connection (`openai_responses`) get no model-made title and keep the one made from the first message |

- The call uses the session's connection and model through the provider route, so its cost goes into the first turn's usage and the session limits. The proxy sends only requests to `/v1/messages` with the session's model and `max_tokens` 64 or less.
- The API sends only to this URL's host:port (metadata and link-local addresses are refused), follows no redirect, and gives up after 25 seconds.
- A title the user gave, or one changed with `PATCH /v1/sessions/{id}`, is never overwritten. If the call fails or the answer is empty, the first-message title stays.

## Conversation runtime [#대화-런타임]

The conversation runtime is one process: the worker image started on its conversation entry point (`apps/worker/src/conversation/main.ts`). It runs the conversation turns of every agent in the installation. It is off by default and turned on only in test stacks. A turn starts in one of two ways: an operator runs `bun run apps/control-host/src/api/conversation-turn.ts` in the api container, or, while the agent's conversation rollout is `on`, someone mentions the agent in a Slack channel or sends it a DM. No API can set rollout `on` yet.

- A mention becomes one turn of its thread (the post itself when it is a top-level post). The requester and the budget root are the person who mentioned the agent, as the api recorded them through their linked account; a name written in the message is never used. The model's instruction is that person's message alone, and the topic's records go in as data. The same post's events arriving again make no second turn. When the decision is to reply (`reply`), a slack role pass posts the answer once in that thread; for a top-level post, in that post's thread. The channel and thread come from the turn's record, never from a channel the model wrote. The answer goes under the agent's name and ends with a small grey line, `AI agent · Werft · Requested by <name>` (the requester's Werft name, left out when it cannot be read). If a source message of the turn is deleted before the send, the answer is not sent. When the turn ends in a reply, a new task or a handoff to an open task, one 👀 goes on the mention (staying quiet and no decision put none). An app without `reactions:write` puts none, and the answer still goes out. When the turn ends in a new task (`spawn_task`), a slack role pass opens one task session whose parent is that conversation and ties it to the thread. The task's request is the mention as the server received it; the goal and done condition the model wrote stay its interpretation only. `task.spawn` is judged again then, on the Slack subject the mention was judged on. A refusal sends a line only the requester sees, and when that line cannot be sent, a line with no reason goes in the thread. With 3 open tasks in the conversation or 10 for the agent, no task is opened and the thread is told why, as it is when the model picks a repository the agent cannot use. An opened task gets no extra answer, and nothing the model wrote is posted. If a source message is deleted before the judgment, there is no task and no line. The queue keeps that turn's input alone, sealed, until the task is settled, at most 1 hour; after that it is cleared and the task is recorded as failed. When it ends in a handoff to an open task (`route_to_task`), a pass of the slack role puts the mention as the server received it into that task as an input. No task is made, and a running task takes it after its current turn. The target is checked again: it must be an open task of the same conversation (the same channel), and the poster must have `session.submit` on it. The poster is the input's requester. A task of another conversation, or a closed one, is not handed to, and the thread gets one line with no reason. Without the right, the requester alone gets one line, or the thread gets one when that cannot be sent. Handed on from another thread, that thread points at the task and gets one line, "Continuing in the original thread ↗", with a link to the task's thread; it gets another only when the task it points at changes. The task's reports go to its own thread alone. A further mention in that thread is judged by the conversation again. The handed input and the line carry every source of the turn, and do not go out once one of them is deleted. A source deleted before the check hands nothing and says nothing. The queue keeps the input to hand for an hour at most. Mention turns do not count toward M1's hourly judgments per channel.
- While the conversation rollout is `on`, every other post under the agent's name ends with the same line: task reports, failure notices, approval and question cards and their redraws, refusals, the welcome, the channel notice, push and pull request results, model notices and progress messages. `Requested by <name>` is added only to a post that is a turn's result or request: the task report, that turn's failure notice and budget refusal, a card, and a push or pull request result. The name is the Werft name of whoever sent the turn (for a push, whoever requested it), left out when it cannot be read. Web and API inputs shown under a person's name and the 👀 have no line, and neither do the answers only a button's presser sees. The line follows the rollout at the time of the send; `off` and `shadow` add none.
- While the turn runs, the slack role sets the thread's status to "processing". However the turn ends, a pass of the slack role ends the turn and sets the status back to `active` once: a decision, no decision, a limit, a failure, a refused budget, a turn nobody took, or the time limit. A turn the queue has not ended is ended as out of time when its permit ends (the 30 seconds to be taken, then the lease). When a newer turn of the same thread is running, the status is left as it is. A status Slack did not take is sent again by the next pass. When the pass sending it stops partway, a pass after the pass time limit sends it.
- Even with rollout `on`, a mention is dropped, with no turn, when the channel listens to nothing (`off`), the agent is inactive, or the channel is archived or waiting for approval, and when the post is longer than a turn's input may be (16,000 characters). A mention in a thread with a bound task goes to that task's session as before. Under `off` and `shadow`, a mention opens a session as before.
- A DM becomes a turn as a mention does. One DM post becomes one turn of its thread (the post itself when it is a top-level post), in that person's DM conversation. Each top-level DM post is a topic of its own, so one person's DMs are never gathered into one session or one topic. The requester and the budget root are the person who sent the DM. When the agent is inactive or its DMs are switched off, a DM is dropped with no turn. A post in a DM thread with a bound task goes to that task's session as before. Under `off` and `shadow`, a DM opens a session as before. The app subscribes to no `assistant_thread_started` event; DMs arrive through `message.im` alone.

- The runtime holds no provider key. Each turn brings a call permit, which the runtime sends to the egress proxy's credential route; the proxy adds the key. A turn calls the provider up to 8 times, each call after a tool's result counted too.
- It has no workspace volume and no repository checkout. Every tool the engine has built in is denied. The engine can call the four read tools and the decision tools below and nothing else: a tool not on the list is not loaded, and is not run if called.
- Read tools: none takes an argument. The api decides what each reads from the turn's lease, and nothing outside the turn's conversation is read.
  - `read_thread`: the current topic's Slack thread, from its first message, up to 50 messages (`conversations.replies`). It uses the history scopes the app already has, so the Slack app needs no reinstall. Twice per turn at most. When Slack answers 429, the turn does not call it again and goes on with the summary and the turn records. Refused in a channel shared with another organization. A guest's message, someone from another organization's, or one whose author could not be confirmed is removed before anything goes to the model, and only the count is said; deleted messages are removed too.
  - `read_channel_summary`: the summary lines of the conversation's channel. A line whose source was deleted is not there.
  - `read_turns`: the conversation's last 20 ended turns (when, the decision and its reason, the answer). A turn a deleted message went into is left out.
  - `list_open_tasks`: up to 20 tasks started from this conversation that have not ended (id, name, status, start). With a person as the requester, only those that person can see. A turn with no requester (the operator command) does not see tasks shared only with people.
  - In a private channel's conversation, the requester must be a member of the channel now; when not, or when that cannot be confirmed, the call is refused.
  - A result is at most 12 KiB, and starts with a note that it is data, not instructions. What a tool read is added to the turn's sources; when it is deleted, the topic session is dropped.
  - The api counts each turn's tool calls and refuses the 13th. The turn ends on `tool_call_limit`, held by `server`.
- Decision tools: a turn ends with one decision. `reply` (answer: `body`, `reason`), `route_to_task` (hand on to an open task: the `task_id` from `list_open_tasks`, `reason`), `spawn_task` (start a new task: `goal`, `done_when`, `repository` only when it picks one, `reason`), `no_reply` (stay quiet: `reason`).
  - A turn whose requester is a person (a web user or a Slack user) or the operator command gets all four; one whose requester is another agent (a Slack bot) gets only `reply` and `no_reply`. The requester is the value the api recorded, never a name in a message. The api checks again when a tool is called.
  - Decision tool calls count with the read tools'. The api writes the decision and its reason into the turn record when the tool is called; the turn's first decision is its decision, and after it the turn's tool calls are refused. Only a `reply` keeps its body, as the answer; a `route_to_task`'s `task_id` is kept on the turn, for its effect to check again.
  - Right before the decision is written, the api checks whether a message the turn read was deleted. If one was, the decision is dropped and the turn is recorded `voided_by_delete`. A turn that ends without a decision (a limit, a failure) is `no_decision`.
  - Decisions have no effect yet: nothing is posted to Slack, and no task is started or handed on.
- Topic sessions: each topic (one Slack thread) gets one engine process and one temporary in-memory directory. The topic's next turn continues the earlier conversation in that engine. Ten minutes after the last turn ends, the session is dropped and its directory removed. A later turn starts on a new engine from the context the api assembles (the channel summary, the topic's earlier answers, buffered messages). The engine's conversation compaction and resume are not used.
- Each time the runtime takes a turn, the api checks again whether a message the session read was deleted. When one was, when that cannot be checked, when the turn failed, or when the session's conversation passes 96 KiB, the session is dropped and the turn starts anew. A restarted runtime holds no session.
- One runtime keeps up to 8 sessions; opening one more drops the session idle longest. One engine idle after a turn measured about 215 MiB RSS (on macOS arm64). The chart's memory (`conversationRuntime.resources`) is 2560Mi for both request and limit: 8 engines, the runtime loop, the topics' tmpfs (256Mi) and a margin.
- The runtime reaches the egress proxy and nothing else, with no DNS. It asks the API for the next turn through the forward proxy, and nothing connects to the runtime.
- To turn it on: with compose, lay `infra/compose.conversation-runtime.yml` over the stack. With Helm, set `conversationRuntime.enabled: true` and put `CONVERSATION_RUNTIME_TOKEN` in the Secret. It runs one replica.
- Turns are queued in the memory of one API process for now. Restarting the API drops the queued turns. With more than one API replica, the operator command is refused with `no_runtime` on a replica the runtime is not asking. One turn of a topic runs at a time: the next waits in the queue until the one before it ends, and its time to be taken (30 seconds) counts again from that end. What decides whether a session goes on is kept in the same process's memory too.

| Variable | Read by | Default | Allowed values |
|---|---|---|---|
| `CONVERSATION_RUNTIME_TOKEN` | api, conversation runtime (same value) | none | At least 32 characters. The bearer that opens the runtime's four routes (`/internal/conversation-runtime/next-turn`, `/internal/conversation-runtime/turn-result`, `/internal/conversation-runtime/read-tool`, `/internal/conversation-runtime/decision-tool`) and nothing else; on any other `/internal` route it gets 403. Without it the api serves none of the four routes nor the operator command, and the runtime refuses to start. With Helm, the Secret key of the same name |
| `CONVERSATION_RUNTIME_TOKEN_PREVIOUS` | api | none | A bearer being rotated out, accepted beside the new one. Put the old value here and the new one in `CONVERSATION_RUNTIME_TOKEN`, restart the api and the runtime, then remove this value |
| `CONVERSATION_TURN_DISPATCH` | api | `false` | The switch that sends people's messages to conversation turns. Leave it off. While turns are queued in memory, the api refuses to start with it on |
| `CONVERSATION_TURN_SOCKET` | api | `/tmp/werft-conversation-turns.sock` | The unix socket path where the operator command hands the api a turn. Reachable only inside the same container |
| `CONVERSATION_TOPICS_DIR` | conversation runtime | `/conversation` in compose and the chart | The tmpfs path the per-topic temporary directories are made under. Required |
| `CONVERSATION_STATUS_FILE` | conversation runtime | `/tmp/conversation-runtime-status.json` | The file where the runtime records when it last reached the api. The healthcheck (`main.ts --health`) reads it; staler than 200 seconds is unhealthy |

## Settings document import and export [#설정-문서-가져오기내보내기]

Model connections and repositories are database rows. Manage them one by one in the console, or put them in and take them out with one **settings document**. The migrate step of the first deploy puts the document into an empty installation once; later deploys do not read it. To add from a document after that, import it with the commands below.

- **Format.** `{"version": 1, "connections": {…}, "repositories": {…}}`. A document whose `mcp_servers` field is not empty is refused whole with `400 BAD_REQUEST` (`reason_code: invalid_document`), and the error shows only the server's name and a note that the installation catalog MCP is gone. An empty field (`{}`) or a document without it is taken, and export leaves the field out. Write credentials as `"auth": {"stored": true}` and enter the values in the console after the import. A row without a value is `needs_value`, and sessions that use it do not run. Export gives only `{"stored": true, "last4": "…"}`, never the value. The master key is not in the document. `value_env` and `secret_id` references and a top-level `profiles` are refused.
- **Import only adds.** Each entry is `add` (new row), `unchanged` (same row), `inactive` (same id as a disabled row) or `needs_value`. The same id with different content, or the same GitHub repository under another id, is `conflicts`, and then nothing is written. Rows are never changed or deleted.
- **Compose.** `bun run settings export > settings.json` writes the document to stdout and `digest sha256:…` to stderr. Check an import first with `bun run settings import --document - --dry-run < settings.json`, then run it again without `--dry-run`. The command runs inside the api container, so pass a host file as `-` (stdin). A refusal exits 1.
- **Kubernetes.** `settings:k8s`, as in `bun run settings:k8s export`, runs the same CLI inside the api Pod.
- **API.** `GET /v1/installation/settings/export` returns `{document, digest}`, and `POST /v1/installation/settings/import?dry_run=true` returns the verdicts. Only a signed-in session of the installation owner can call them; an API key gets `403`. A conflict is `409 REVISION_CONFLICT` and a malformed document is `400 BAD_REQUEST`.
- **Installations that ran on a file catalog.** The ways to import a file catalog from before v0.1.0 (`settings import|seed --from-dir`, migrate's `/legacy-config` mount and `PLATFORM_LEGACY_CONFIG_DIR`) are gone. An installation still on a file catalog first upgrades to a release before this one, which moves its settings into the database, and then upgrades. `PLATFORM_CONFIG_DIR` and `SESSION_CATALOG_JSON` are not read, so the api starts with either still set; remove them to tidy up.
- **Installation catalog MCP.** The remote MCP servers an installation owner added in the console or with the settings document's `mcp_servers` are removed by migration `0304_retire_catalog_mcp`. It deletes the catalog rows, their stored values and agents' catalog choices, and the migrate log `db.migrate.notice` records how many servers it removed and their names. They are not moved to workspace MCP servers: write down the names of servers you still need before upgrading, then after upgrading register them as workspace MCP servers (Settings > Agent connections > **MCP servers**) and choose them on the agent's access tab. A new registration cannot use the names `github`, `browser` or `memory` (an existing workspace `memory` server stays), and a name only has to be unique within its workspace, so register a catalog `memory` server under another name. When the API starts, an agent draft that names a catalog server is moved to a new version without that server (`capabilities.mcp`), the `tool_policy.per_tool` entries of its tools, and the `credential_ref` it used (`forbidden` and the card's other names stay). When any are moved, the log `Drafts naming a retired catalog MCP server reconciled` records how many. Existing releases are not changed and can be activated again. Sessions of older releases run without that server, and they still start after the credential name that server used is unbound. The session shows one line, once, saying the retired catalog MCP `<name>` was skipped. Checkpoints taken with that server are still restored. A session that already holds 16 restore alternatives may fail to restore the checkpoint of its oldest alternative; the API log then records a `claim.retired_catalog_restore_dropped` warning with the session id. During a rolling deploy the database refuses an old replica's catalog writes (import, console, saving a card that names a catalog server), so do not change the catalog while upgrading.
- **Rollback floor.** A database where an import wrote a repository row with `auth_kind` `github_app_explicit` is not rolled back to an older image that does not know `auth_kind`. That image reads the row as a console GitHub App repository.
