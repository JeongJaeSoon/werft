## 契約

`WERFT_API_KEY` と `WERFT_BASE_URL` はサーバーではなく SDK 呼び出し側の設定です。[SDK クライアント設定](/getting-started/client)に従います。

設定値の形式、必須性、反映時点を調べるための文書です。実行前の有効化・rollback ゲートは、先に [Compose アップグレード](/run-server/self-hosting/upgrade-compose)と [Kubernetes アップグレード](/run-server/self-hosting/upgrade-kubernetes)を読みます。

<a id="설치-상한" />
## 設置上限

API と scheduler は、下記の値がない、または形式が不正な場合、問題を一行にすべて記録し起動しません。両プロセスは同じ parser を使います。コードに既定値はなく、compose の `x-installation-limits` と chart の `config.limits` がローカル既定値を渡します。起動済み API の `/readyz` も同じ検証を `config` チェックで再実行します。セッションの待機メッセージ・入力の保管・費用・トークンの上限と、turn 時間・provider 再試行は env ではなく [Web で決める実行の上限](#웹에서-정하는-실행-한도) です。

| 変数 | 意味 | 超過時 |
|---|---|---|
| `EXECUTION_SLOT_LIMIT` | 同時に slot を保持する worker 数。0 なら受付だけ行い、何も起動しません | 入力は拒否せず `queued` にします |

<a id="api-설정" />
## API 設定

API は設置上限以外に次の値を起動時に一つの parser で読みます。未設定なら既定値を使います。設定した値が不正なら（空文字を含む）、既定値には戻りません。数値設定は API・scheduler・reconciler・worker と設置上限がすべてこの規則に従います。既定値のない値は未設定なら `X is required`、不正なら `X must be a positive integer` のように期待する範囲を示して拒否します。受け取った値自体は書きません。ログに残り、別の変数へ誤入力した秘密かもしれないためです。`Refusing to start: API settings are invalid` の一行に全問題を記録して起動しません。起動済み API の `/readyz` も同じ検証を `config` チェックで再実行します。

| 変数 | 既定値 | 許可範囲 |
|---|---|---|
| `HEARTBEAT_TTL_SEC` | 30 | 15 超、86400 以下。worker は lease 終了の 10 秒前に lease を手放し（`WORKER_LEASE_SAFETY_MARGIN_SEC`）、5 秒ごとに heartbeat を送ります（`WORKER_HEARTBEAT_INTERVAL_SEC`）。両値の合計以下なら、attempt は最初の heartbeat 頃に lease を失います。launcher は worker の両値を渡さないため、既定値で判定します |
| `SSE_MAX_STREAMS`・`SSE_MAX_STREAMS_PER_OWNER`・`SSE_REPLAY_MAX_BYTES` | 256・8・1 MiB | 正の整数 |
| `LOG_LEVEL` | `info` | `debug`・`info`・`warn`・`error`（大文字・小文字不問、空値は `info`）。scheduler・reconciler loop と egress-proxy も同じ規則で起動を拒否します。worker は scheduler の値を受け取ります |
| `WEB_DIST_DIR` | なし（Web コンソールを配信しない）。control-host イメージは `/app/apps/web/dist` | `index.html` のある絶対パス。Web コンソール（`apps/web`）のビルド結果です |

すべての `/v1` 応答は `api.request.completed` を記録します。実 id を含まない Hono の `route_template`、`method`、`status`、認証と route 処理を含む `duration_ms`、`operation=api_request`、`outcome`、`reason_code` があり、`request_id` は log context にあります。request body・credential・provider key は含めません。terminate 要求は同じ `request_id` の `Terminate control transaction completed` も記録し、pool checkout、binding・launch・session lock、各 SQL、commit または rollback、control transaction 全体の millisecond 計測を含みます。デプロイ環境で受理遅延を調べるときは、両ログを `request_id` で結び、遅い段階を特定します。

terminate が既に消えた execution で即完了する、または scheduler/reconciler が execution 不在を確認すると、`control.result` が `operation=terminate`、receipt id の `control_id`、`outcome`、`reason_code`、durable 受理から確認までの `effect_ms`（`duration_ms` と同じ）を記録します。期限超過 receipt は先に `outcome=unknown`・`reason_code=deadline_exceeded` を記録し、後に execution 不在を確認して receipt を成功へ上げると、`outcome=succeeded`・`reason_code=execution_gone` の結果を追加します。

`WEB_DIST_DIR` があれば API が同一 origin で Web コンソールを配信します。`/v1`・`/internal` 外の GET・HEAD はそのディレクトリのファイルを返し、なければ `index.html` を返します（SPA fallback）。そのため `/login`・`/bootstrap` を再読込しても画面が開きます。`/v1`・`/internal` 配下は fallback しません。認証済みの `/v1/nope` は JSON の `404 NOT_FOUND` です。`/assets/` 配下のファイル名には content hash があるため `immutable` で cache し、存在しない asset にはページではなく 404 を返します。`index.html` は `no-cache` で、inline script を許可しない CSP（`script-src 'self'`）を付けます。control-host イメージは `web` build stage で `apps/web` をビルドし、`dist/` だけを含みます。別の web イメージはありません。ローカルで Web だけ変更するなら `bun run --cwd apps/web dev`（Vite、`/v1` を `VITE_API_TARGET`、既定 `http://127.0.0.1:3000` へ proxy）を使います。

`AUTH_MODE=none` は egress authorizer（`EGRESS_AUTHORIZER_PORT`）と併用できません。authorizer が有効なら worker が proxy 経由でこの API に到達することを意味します。`none` では worker 内のコードが `X-Owner-Id` で任意の owner を名乗れるため、起動を拒否します。`AUTH_MODE` 自体（`none`|`api-key`）は readiness が判定します。

worker も起動時に交差検査します。`WORKER_PROVIDER_MAX_RETRIES` がなければ起動しません。コード既定値のない設置上限で、scheduler が launch に固定された値を常に渡します。`WORKER_NEXT_INPUT_WAIT_SEC` が `WORKER_REQUEST_TIMEOUT_SEC` 以上でも起動しません。その設定ではすべての long poll が request timeout で切れるためです。scheduler と reconciler は空の `DATABASE_URL` を未設定と見なし、`QUEUE_DATABASE_URL` を使います。

API と slack role は `WORKER_IMAGE_RUNTIME`・`WORKER_IMAGE_PREVIOUS_RUNTIME` から現在・直前の worker イメージの runtime の組み合わせを読みます。手入力せず、images.yml が出力した worker digest JSON の `runtime` をそのまま入れます（`{"engine":…,"sdkVersion":…,"cliVersion":…,"profileDigestScheme":…}`）。`engine` は `claude` と `codex` で、chart は他の名前を render 時に `images.worker.runtime.engine must be one of: claude, codex` として拒否します。自前イメージにはその JSON がないため、images.yml と同じコマンドでイメージから読みます。

```bash
docker run --rm -i --network none --entrypoint bun <worker-image> \
  run apps/worker/src/image-runtime.ts <<<'{}' | jq -c 'del(.profiles)'
```

**worker イメージ一つが載せるエンジンは一つです。** `apps/worker/Dockerfile` はビルド引数 `WORKER_RUNTIME` でエンジンを選びます。空なら Claude イメージ、`--build-arg WORKER_RUNTIME=codex_app_server` を渡すと Codex イメージです（ビルドログに `codex-cli 0.167.0` が出力され、別のバージョンならビルドは失敗します）。CI は Codex イメージを `werft-worker-codex` という別イメージとして作ります。Codex を使うデプロイは `WORKER_IMAGE`（chart では `images.worker`）をそのイメージにし、上のコマンドで読んだ `runtime`（`engine` は `codex`）を合わせて設定します。ローカルスタックは `infra/compose.codex-worker.yml` オーバーレイで同じイメージをビルドします。Codex セッションが実際の OpenAI Responses API を呼ぶデプロイでは、proxy の `EGRESS_CREDENTIAL_ALLOWLIST` に `api.openai.com:443` も加えます。Codex エンジンには独自の予算がありません。セッションのコスト・トークン上限（`SESSION_COST_LIMIT_USD`、`SESSION_TOKEN_LIMIT`）は、worker gateway がプロバイダー呼び出しのたびに保存済みの使用量で執行し、上限を超えたセッションの次の呼び出しは `403 BUDGET_EXCEEDED` で止まります。制約: 使用量は proxy の報告で gateway に届きます。報告が再試行（1 秒・5 秒・15 秒）の末に失われると保存コストが低いままになり、そのセッションの以後の呼び出しは proxy プロセス内の遮断（プロセス単位で、再起動で消えます）でしか止まりません。したがってこの上限は、保存済みの使用量に依存するソフトな上限です。報告が失われた後に proxy が複数ある、または再起動すると、超過額に上限はありません。報告がすべて届いても、1 回の長い応答、並列呼び出し、報告が遅れている間に送る次の呼び出しは上限を超えることがあります（Claude エンジンの予算も完了した呼び出しの後に検査されます）。永続的な使用量記録でこの穴を塞ぐのは後続の作業です。

**セッションは自分のエンジンのイメージで起動します。** scheduler はセッション spec の runtime kind からエンジンを決め（`claude_agent_sdk` は claude、`codex_app_server` は codex）、そのエンジンのイメージの中からだけ下の規則でイメージを選びます。worker も自分のエンジンのセッションだけを claim します。そのエンジンのイメージが一つもないと、checkpoint のないセッションは slot を使わずに待ち（scheduler ログの `waiting_for_engine_count`）、checkpoint のあるセッションは launch 前に `recovery_required` で止まります（attention `RESTORE_FAILED`、reason `incompatible_checkpoint`）。そのため一つのデプロイで Claude と Codex のエージェントを一緒に動かせます。二つのエンジンのイメージはイメージ一覧（`WORKER_IMAGES`、下記）にエンジンごとに最大二つずつ書きます。二つのエンジンの一覧は、scheduler・API・Slack role をすべてこのバージョンに上げてから渡します。古いバージョンはその一覧を拒否して起動しません。戻すときは、先に一覧を一つのエンジンに減らしてから戻します。アップグレード検査（`upgrade-check`）はエンジンごとに判定し、一つのエンジンのイメージをすべて外すアップグレードはそのエンジンの開いたセッションを承認一覧に載せます（[エンジンを外す upgrade](/run-server/self-hosting/upgrade-kubernetes#3-검사-결과와-예외)）。

**Codex auto モードのサンドボックス。** Codex セッションの `auto` モードは、モデルが呼ぶコマンドを Codex の bubblewrap サンドボックスの中で実行します。書き込めるのは作業ディレクトリだけで、ネットワークは開いています。サンドボックスは既定で有効です。worker は `auto` セッションを始める前に、`codex sandbox` で `true` を一度実行します。失敗するとセッションは始まらずに止まり（`recovery_required`）、理由に bubblewrap のエラー1行が残ります。失敗はこの確認ですぐに分かるため、セッションが止まったまま待ち続けることはありません。`auto` はサンドボックスの外では動きません。ほかの権限モードはサンドボックスの状態に関係なく動きます。

bubblewrap は、Docker の既定の seccomp（Kubernetes の `RuntimeDefault`）が塞ぐ namespace の syscall を使います。そこで scheduler は、Codex イメージのコンテナにだけ Werft の seccomp プロファイルを付けます。このプロファイルは Docker の既定プロファイルに `clone`・`unshare`・`mount`・`umount2`・`pivot_root` を加えたものです（`scripts/codex-seccomp-profile.ts`）。Codex イメージとは、宣言された runtime の `engine` が `codex` のイメージです。runtime を宣言していないイメージは既定の seccomp で起動するため、`auto` セッションは拒否されます。Codex を動かす compose スタックも、上のコマンドで読んだ `WORKER_IMAGE_RUNTIME` を渡さないとプロファイルが付きません。

- **Docker backend。** プロファイルをコンテナごとに直接渡します。ホストに置くファイルはありません。
- **Kubernetes。** Codex worker コンテナに `Localhost` プロファイル `werft/codex-sandbox.json` を付けます。kubelet の seccomp ディレクトリからのパスで、変えられる値ではありません。chart に `codexSandbox.localhostProfile` を渡すとレンダリングが拒否されます。Pod 単位のプロファイルは `RuntimeDefault` のままです。このプロファイルを付ける Pod には、ノードラベル `werft.codex-seccomp-profile=installed` を求める nodeAffinity（required）も付きます。そのため、ラベルの付いたノードにだけ配置され、そうしたノードがないか空きがない間は `Pending` で待ちます。chart のインストーラー DaemonSet（`codexSandbox.installer`）が、worker ノードの `<kubeletDir>/seccomp/werft/codex-sandbox.json` にそのファイル1つを書き、そのあと自分のノードにこのラベルを付けます。配置は既定で `worker.nodeSelector`・`worker.tolerations` に従います。ファイルを書く init コンテナは capability も API トークンも持たず、そのディレクトリだけを書き込み可能でマウントし、ルートファイルシステムは読み取り専用です。ラベルを付けるコンテナは root ではなく、そのディレクトリを読み取り専用でマウントします。このコンテナの ServiceAccount は ClusterRole で Node の `patch` 権限を受けます。RBAC では「自分のノード」に範囲を絞れないため、chart の ValidatingAdmissionPolicy が、リクエストをその Pod が動くノードと、このラベル1つをこの値で付ける変更に限ります。このポリシーには Kubernetes 1.30 以上が必要です。ラベルを付けるコンテナは、まず別の値にする dry-run リクエストを送り、ポリシーがそれを拒否するのを確かめてからラベルを付けます。約2分のうちに拒否が見えなければ、何も変えずに失敗して再起動します。ラベルは、インストーラー DaemonSet や chart を消しても外しません。ファイルもノードに残るからです。ラベルがあるのにファイルのないノード（ノードのディスクを消した場合など）では Codex worker コンテナが作られません（`CreateContainerError`）。scheduler は、seccomp プロファイルが原因のこのエラーを見るとすぐに launch の失敗として数えます。Pod を消し、backoff の後にもう一度起動します。その間にインストーラー DaemonSet がファイルを書くか、Pod が別のノードで起動すれば、セッションは続きます。launch の失敗上限（既定5回）に達すると launch をあきらめ、スロットを返します。理由にはノード名、プロファイルのパス、インストーラー DaemonSet が残ります。

**インストーラー DaemonSet なしでプロファイルを置くには。** Security Profiles Operator やノードイメージでプロファイルを配るクラスターは、`codexSandbox.installer.enabled=false` で DaemonSet を無効にします。このとき chart は Node の権限も admission ポリシーも作りません。運用者は、Codex worker が動くノードごとに2つのことを自分で行います。まず chart の `files/codex-sandbox-seccomp.json` を `<kubeletDir>/seccomp/werft/codex-sandbox.json` に置きます。次に、ファイルを置いたノードにだけラベルを付けます。

```bash
kubectl label node <node> werft.codex-seccomp-profile=installed
```

ラベルのないノードには Codex Pod が配置されず、ラベルの付いたノードが1つもなければ `Pending` のままです。ノードからファイルを取り除くときは、先にラベルを外します（`kubectl label node <node> werft.codex-seccomp-profile-`）。chart を消したあとラベルをすべて外すには、同じコマンドに `<node>` の代わりに `--all` を渡します。

**AppArmor が有効なホスト。** Docker の `docker-default` と containerd の既定の AppArmor プロファイルは、どちらも `mount` を塞ぎます。そのため AppArmor が有効なホスト（Ubuntu・Debian の既定）では、seccomp プロファイルがあっても bubblewrap が `bwrap: Failed to make / slave: Permission denied` で失敗し、`auto` セッションは拒否されます。Ubuntu 23.10 から有効な `kernel.apparmor_restrict_unprivileged_userns=1` は、AppArmor を外しても（`unconfined`）`bwrap: setting up uid map: Permission denied` で塞ぎます。Ubuntu 24.04 と Docker 28 で確かめた最小の条件は、Codex コンテナに `docker-default` へ `userns,`・`mount,`・`pivot_root,` の3つの規則を加えた AppArmor プロファイルを付けることです。この条件は sysctl の値に関係なく通ります。Werft はまだ Codex コンテナに独自の AppArmor プロファイルを付けません。そのため、こうしたホストではいま `auto` を使えません。ほかの権限モードは使えます。

**サンドボックスを無効にするには。** Helm は `codexSandbox.enabled=false`、compose は scheduler の `CODEX_SANDBOX=disabled` を渡します。無効にすると `auto` モードも一緒に無効になります。Codex コンテナは既定の seccomp で起動し、インストーラー DaemonSet は作られません。`auto` セッションは始まる前に拒否され（`recovery_required`）、理由にこの値が残ります。ほかの権限モードはそのまま動きます。ノードにプロファイルを置けないクラスターで、Codex を `auto` なしで使うときにこの値を使います。無効な状態は、scheduler と worker の起動ログの警告でも分かります。値を変えると隔離 stamp が変わり、実行中の worker は置き換えられます。

**カーネルのパッチ。** サンドボックスを有効にすると、Codex コンテナの中で user namespace と mount が使えます。その経路のカーネルの脆弱性はコンテナからの脱出につながりえます。Codex セッションが動くノードには、カーネルのセキュリティ更新をすぐに適用します。

**エンジンを切り替えるには。** 単一イメージの設定で `WORKER_IMAGE` を新しいエンジンのイメージに、`WORKER_IMAGE_PREVIOUS` をいまのイメージにすると、旧エンジンのセッションは checkpoint がなくても直前イメージで起動し、新しいエンジンのセッションは新しいイメージで起動します。稼働中のデプロイの `WORKER_IMAGE` を別のエンジンのイメージに置き換えるには、アップグレード検査（`upgrade-check`）の規則にそのまま従います。新しい設定の `WORKER_IMAGE_PREVIOUS` はいま配備されているイメージでなければならず、検査が再開できないと出力するセッション（checkpoint のエンジンが違うものだけでなく、SDK・CLI のバージョンや digest 方式が合わないもの、ランタイムが記録されていないものも含む）は、出力された一覧そのものを `upgrade.approvedSessions` で承認します。checkpoint はエンジン間で移せないため、切り替え後は直前イメージ（旧エンジン）で動くセッションが終わってから直前イメージを空にできます。

両方なければ runtime の組み合わせを読まず、下記 pin 維持も適用しません。`WORKER_IMAGE_PREVIOUS_RUNTIME` だけがある、または値を読めなければ起動しません。設定すると、直前のイメージのバージョンで作ったリリースとそのセッションも動き続けます。リリースは作成時にイメージが載せていたランタイムのバージョンを固定するので、現在・直前のどちらのイメージも載せていないバージョンのリリースは新規セッションを受け付けません。そのエージェントはリリースし直します。

GitHub Packages bot tokenを別の host に送る必要がある場合だけ、次を設定します。GitHub Enterprise Server や試験用の偽 registry が該当します。値は http(s) URL で、userinfo・query・fragment があると API は起動しません。registry host は proxy の `EGRESS_CREDENTIAL_ALLOWLIST`（プライベートアドレスなら `EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST`）にも必要です。API は token の確認を `GITHUB_PACKAGES_API_URL` の host:port にだけ送り、redirect はたどりません。既定値（`https://api.github.com`）は公開アドレスに解決されるときだけ呼び、自分で設定した URL は http やプライベートアドレスでも構いません。メタデータ・link-local アドレスに解決される名前はどちらでも拒否します。

| 変数 | 既定値 | 意味 |
|---|---|---|
| `GITHUB_PACKAGES_API_URL` | `https://api.github.com` | 登録 token の scope を問い合わせる先（`GET /user`） |
| `GITHUB_PACKAGES_NPM_URL` | `https://npm.pkg.github.com` | `github-npm` route の upstream |
| `GITHUB_PACKAGES_RUBYGEMS_URL` | `https://rubygems.pkg.github.com` | `github-rubygems` route の upstream |

## Web で決める実行の上限

次の値は env ではなく、owner が **設定 > ワークスペース > 実行の上限** で保存します（`PATCH /v1/installation-config`）。インストール全体で一つで、保存するとその API はすぐに、ほかの replica と scheduler・slack・metrics role は 10 秒以内に従います。保存した値がなければ既定値を使います。どの role も以前の env を読みません。migrate がアップグレード時に一度だけ移します（[Web に移した実行の上限](/run-server/self-hosting/upgrade-compose#웹으로-옮긴-실행-한도)）。

| 画面の欄（以前の env） | 既定値 | 意味と許可範囲 | 超過時 |
|---|---|---|---|
| 人の応答（`PENDING_REQUEST_TTL_SEC`） | 1800 | 整数 1–604800 秒。承認・質問要求を受け付ける期間です。登録済み要求は worker がこの時間待ち、すでに登録された要求は変えた値に従いません。gateway が登録するまでは worker が 30 分待ちます。turn の時間に待ち時間も含むため、待機はその上限を超えません | 答えのない要求を閉じます |
| ターンの時間（`MAX_TURN_SECONDS`） | 3600 | 整数 1–604800 秒。一つの turn の実時間上限で、承認待ちも含みます。worker env の `WORKER_MAX_TURN_SEC` に渡します | turn は `failed(turn_timeout)`。エンジンが応答しなければ `outcome_unknown(turn_timeout)` |
| モデル呼び出しの再試行（`PROVIDER_MAX_RETRIES`） | 2 | 整数 0–10。失敗した provider 要求の再送回数。worker env の `WORKER_PROVIDER_MAX_RETRIES` を経由して SDK の `CLAUDE_CODE_MAX_RETRIES` に渡します。0 なら最初の失敗で turn が終わります | turn は `failed(api_error)`。turn 詳細の `result` に `api_error_status`・`provider_error`・`last_retry_status` が残ります |
| セッションの費用（`SESSION_COST_LIMIT_USD`） | 25 | 0 より大きく 1000000 以下の USD。セッション累積費用（egress proxy が計測した provider 呼び出し別 usage をプラットフォーム価格表で換算した合計、推定値） | 新 turn を dispatch しません。セッション詳細に `attention.code=BUDGET_EXCEEDED` が出て worker は slot を返します。入力は引き続き `queued` で受け付けます |
| セッションのトークン（`SESSION_TOKEN_LIMIT`） | 0（上限なし） | 整数 0–9007199254740991。セッション累積 provider token 数。費用上限と同じ呼び出しを単価によらず数えます | セッションの費用と同じです。両上限は同じ判定（`budgetExceeded`）を通り、どちらが先に達しても `BUDGET_EXCEEDED` です。`attention.reason` は達した上限だけを記します |
| 待機メッセージ（`QUEUED_INPUT_LIMIT_PER_SESSION`） | 20 | 整数 1–100000。一つのセッションが蓄積できる `queued` turn 数 | `429 RATE_LIMITED`、`retryable:true`、`Retry-After: 5` |
| 入力の保管（`STORAGE_LIMIT_BYTES`） | 1073741824（1 GiB） | 整数 1–9007199254740991 bytes。環境全体が保持する入力 message の UTF-8 bytes。event・checkpoint object・worker ディスクは数えません（ディスクは workspace quota が担当） | `413 STORAGE_LIMIT_EXCEEDED`、`retryable:false` |
| 作業領域の容量（`WORKSPACE_ENFORCE`） | `warn` | `warn`・`fail`・`off`。worker の workspace が quota を超えたときの動作です。worker は claim 時に値を受けるため、すでに動いている worker は受けた値を使い続けます | `warn` はログ `worker.turn.workspace_quota_exceeded` だけを残し、`fail` は超えた turn を止め、`off` は測りません |
| セッション記録の保管: 保管までの未使用期間（`SESSION_ARCHIVE_AFTER_DAYS`） | 180 | 0（無効）か、整数 30–3650 日。最後の活動がこれより古いセッションのイベントを、保管ジョブが bucket の object に移します。ジョブは実行のたびに DB から読みます（[セッションイベントの保管](/run-server/self-hosting/reference/storage#세션-이벤트-보관)） | 該当なし |
| セッション記録の保管: 保管ジョブの動作（`SESSION_ARCHIVE_DRY_RUN`） | 数えるだけ（`true`） | 数えるだけ・実際に移す。数えるだけなら、移す数をログに残すだけです。API の object store の設定から見て保管できないインストールなら、画面がそう知らせます | 該当なし |
| 停止したセッションの作業領域（`EXECUTION_WORKSPACE_STOPPED_TTL_SEC`） | 86400（1 日） | 整数 0–315360000 秒（3650 日）。`stopped` セッションの workspace（Docker volume、Kubernetes PVC）を stop から残しておく時間です。0 なら次の回収ですぐ回収します。scheduler は回収のたびに DB から読みます（[worker の作業領域](/run-server/self-hosting/reference/storage)） | scheduler が workspace を回収し、次の resume は checkpoint から復元します |
| 一時停止したセッションの作業領域（`EXECUTION_WORKSPACE_PAUSED_TTL_SEC`） | 86400（1 日） | 整数 0–315360000 秒（3650 日）。resume が受け付ける checkpoint のある `paused` セッションの workspace を、pause から残しておく時間です | 停止したセッションと同じ |

ターンの時間・モデル呼び出しの再試行は scheduler が pass ごとに読み、その pass が予約する launch に固定します。worker は固定された値で起動します。値を変えると、別の値で起動した worker のうち待機中のものはすぐに終了し、turn 中のものは受け取った値でその turn を終えてから終了します。セッションの次の launch が新しい値を受け取ります（[turn 時間と再試行を変えるとき](/run-server/self-hosting/explanation/isolation#turn-시간과-재시도를-바꿀-때)）。

**使える値がないとき。** 移せなかった env 値（範囲外）や、このリリースが受け付けない保存値のあるキーは止まります。既定値では動きません。そのキーを読む処理だけが拒否され、画面はその欄に案内を出し、値を保存すると解けます。設定を 60 秒を超えて読めないとき（DB 障害）も、すべてのキーが同じです。

- 人の応答: 新しい権限リクエスト・質問の登録が `503 BACKEND_UNAVAILABLE`（`retryable:true`）で拒否されます。worker が再送します。
- セッションの費用・トークン・待機メッセージ・入力の保管: セッション作成とメッセージの受付が `503 BACKEND_UNAVAILABLE` で拒否されます。すでに受け付けた要求を同じ `Idempotency-Key` で送り直すと、保存した応答をそのまま受けます。この四つの値とターンの時間・再試行を見せる `GET /v1/limits` と `GET /v1/sessions/{id}/usage` も、どれか一つが止まると `503` です。セッションの費用・トークンはほかにも止めます。scheduler は launch だけを飛ばし（ログ `Launches skipped: the session limits cannot be read`）、終了と workspace の回収は続けます。worker の claim・次の入力・provider 呼び出しの開始・finalize は `503`（再試行）を受けます。すでに開いた provider 呼び出しを開き直すことと、すでに確定した finalize の応答はそのまま通ります。metrics は launch 待ち行列の gauge（`werft_launch_queue_*`）を空にします。
- 作業領域の容量: worker の claim が `503` を受け、セッションが始まりません。
- ターンの時間・モデル呼び出しの再試行: scheduler は新しい launch を予約しません（ログ `Launches skipped: the worker limits cannot be read`）。値が固定される前に予約された launch は作り直さず、いまの資源をそのまま残します（ログ `Launch held: the worker limits it would start with cannot be read`）。値が固定された launch と起動中の worker はその値で動き続け、終了と workspace の回収も続けます。
- 停止・一時停止したセッションの作業領域: どちらか一つでも止まると、scheduler は `stopped`・`paused` セッションの workspace を新たに回収しません（ログ `Workspace TTLs cannot be read; keeping every stopped and paused session's workspace`）。終了したセッションの workspace と、前の回収が終えられなかったものは回収を続け、launch もそのまま行います。

**コストとトークンの上限は provider 呼び出し一つずつにもかかります。** egress proxy は課金される provider 呼び出し(Messages、Responses)を送る前に、API でその呼び出しを開きます。API はセッションの累計コスト・トークンに、まだ終わっていない呼び出しの予約と今回の呼び出しの予約を足します。その合計が上限に届くと `403 BUDGET_EXCEEDED` で拒否し、proxy はその呼び出しを provider に送りません。予約は要求のバイト数を入力トークンとみなして最も高い cache write 単価(Claude は 2 倍、OpenAI は 2.5 倍)で数え、出力は要求の出力上限すべて(上限のない Responses 要求は 32,768 トークン)で数えます。`claude-sonnet-5` や `gpt-5.5` の呼び出し一つでおよそ 1〜2 ドルです。

- セッションは上限より呼び出し一つの予約分だけ早く止まります。セッションの費用上限が呼び出し一つの予約より小さいと、最初の呼び出しから拒否されます。
- 下げた上限は実行中のセッションの次の provider 呼び出しからかかります。上げた上限は、実行中の worker には次の claim で届きます（worker は claim 時に残りの予算を SDK の `maxBudgetUsd` として受けるためです）。
- セッションに記録されるコストは予約ではなく、provider が報告した使用量です。使用量の報告が最後まで失敗した呼び出しは、その予約を数え続けます。
- API が 5 秒以内に呼び出しを開けないと、proxy は呼び出しを送らず `503` で答えます。エンジンは再試行します。
- 上限は推定です。長い応答一つはその呼び出しの予約まで行くことがあります。出力上限のない Responses 要求は、32,768 トークンを超えて推論した分だけ上回ることがあります。

## scheduler・worker コンテナ・egress 設定

scheduler が worker コンテナ作成時に読む値です。未設定は既定値、不正な形式では起動しません。user、HOME・workspace パス、tmpfs サイズ、credential ポート、stop timeout は `werft.isolation` fingerprint に含まれます（[実行基盤と worker の隔離](/run-server/self-hosting/explanation/isolation)）。変更すると実行中 worker が交代します。CPU・メモリ・PID 上限は次の launch から適用します。

`WORKER_MEMORY_MB` は transcript 上限（`MAX_TRANSCRIPT_BYTES`）と合わせて決めた値です。両者の関係、ノードごとのセッション数、変更方法は[容量管理](/run-server/self-hosting/capacity)を参照してください。

scheduler は `WORKER_IMAGE`・`WORKER_IMAGE_RUNTIME` で現在のイメージ、`WORKER_IMAGE_PREVIOUS`・`WORKER_IMAGE_PREVIOUS_RUNTIME` で直前リリースのイメージを受け取ります。runtime 値は API と同じです（上記 API 設定）。直前イメージは両値を設定する必要があり、一つだけでは起動しません。`WORKER_IMAGE_RUNTIME` がなければ、すべての launch は `WORKER_IMAGE` で起動します。設定すると launch ごとに、セッションの checkpoint ポインターに記録された組み合わせ（engine・SDK・CLI・profile digest scheme）と合うイメージを選び、両方合えば現在のイメージを使います。新規セッション、checkpoint がないセッション、組み合わせ未記録の古い checkpoint は、セッションのエンジンの最も新しいイメージ（現在のイメージ、そのエンジンを動かすのが直前イメージだけなら直前イメージ）で起動します。そのエンジンのイメージがなければ slot を使わずに待ちます。どちらとも合わなければ worker を起動せず、`recovery_required`（`incompatible_checkpoint`）で停止し、セッションイベント `checkpoint_restore_failed` に `detected_at: "launch"` が残ります。`retry_restore` で再試行できます。

**イメージ一覧（`WORKER_IMAGES`）。** 上の四つの値の代わりに、JSON 配列一つでイメージを渡すこともできます。要素は `{"image": "<repository>@sha256:<digest>", "runtime": {…}, "released_at": "2026-11-10T00:00:00Z"}` で、エンジンごとに最も新しいイメージから書きます。エンジンごとに撤回されていない最初の要素がそのエンジンの新規セッションのイメージで、残りはその組み合わせで封印された checkpoint を再開します。選び方は上と同じです。`runtime` は images.yml の値をそのまま入れ、`released_at` は同じエンジンの要素同士で配列の順に厳密に減っていく必要があります（同じか逆順なら起動しません）。エンジンの違う要素同士は順序と時刻を比べないため、二つのエンジンを同じ時刻で出せます。タグ参照、同じ digest の重複、未知のフィールド、一つのエンジンに撤回されていないイメージが三つ以上の一覧も起動しません。`WORKER_IMAGES` と上の四つの値を一緒に設定しても起動しません。scheduler・API・slack role が同じ値を読み、workspace quota helper は撤回されていない最初の要素のイメージで起動します。アップグレード検査（`upgrade-check`）は一覧も判断します（[アップグレード前の検査](/run-server/self-hosting/upgrade-kubernetes#업그레이드-전-검사)）。chart では `images.workers` に `{repository, digest, runtime, releasedAt}` の要素を最も新しいイメージから書くと、`WORKER_IMAGES` を render します。このとき `images.worker` と `images.workerPrevious` の digest・runtime は空にします。公開 chart は既定値として、そのリリースの Claude・Codex の二つのイメージを `images.workers` に含みます。`images.worker` でイメージを一つだけ渡すには、`images.workers: []` を一緒に書きます。Helm は一覧を既定値と統合せず丸ごと置き換えるため、values に書いた一覧には次の chart のイメージが入りません。上で起動しない一覧は chart も render しません。`releasedAt` は秒まで書いた RFC 3339 の時刻にし、小数秒は三桁までにします。compose スタックは一覧を使いません。その scheduler は常に `WORKER_IMAGE` を持つため、`WORKER_IMAGES` を設定すると起動しません。二つのエンジンを一緒に動かす compose スタックは単一の値で渡します。`WORKER_IMAGE` に Codex イメージ、`WORKER_IMAGE_PREVIOUS` に Claude イメージを置き、二つの runtime はビルドした各イメージから上のコマンドで読みます。`infra/compose.two-engines.yml` がその順序（二つのイメージのビルド → runtime の取り出し → スタックの起動）を書いています。runtime なしで二つのイメージだけを渡すと scheduler は起動しません。

**撤回（`retracted`）。** 再ビルドで直せない脆弱性のように、イメージをもう使ってはいけないときは、その要素に `"retracted": true` を付けて一覧に残します（chart では `images.workers[].retracted: true`）。撤回したイメージではどのセッションも起動しません。そのイメージで封印された checkpoint は、エンジン・SDK・CLI が同じ撤回されていないイメージ（修正ビルド）が一覧にあれば、そのイメージで再開します。直前の launch が撤回したイメージだったセッションが別のイメージに移ると、その launch を予約するときにセッションの記録に `worker_image_replaced` イベント（移る前と後のイメージ、reason `retracted`）が残り、セッションを作った人に Slack DM が届きます。なければ、セッションは launch 前に `recovery_required` で止まり、attention `RESTORE_FAILED` の reason が `runtime_retired` になります。修正イメージを入れてから `retry_restore` で再試行するか、`start_fresh` で checkpoint なしで続けるか、閉じます。撤回したイメージですでに動いている launch もそのままにはしません。まだ worker が付いていない launch は作り直さずに落として返し、セッションにイメージを選び直させます。worker が付いて動いている launch は、進行中の turn が終わるのを待ってから落とします（`stale_isolation` と同じ drain です。turn の最大時間に仕上げの猶予を足した時間を過ぎると、それ以上は待ちません）。そのセッションも次の launch でイメージを選び直し、選べるイメージがなければ上と同じく止まります。イメージを記録する前に予約された launch に worker が付いているときは、何を動かしているか分からないのでそのままにします。この入れ替えは scheduler のログに `Execution resource runs a retracted worker image` として残り、入れ替えの記録の理由は `stale_isolation` と同じです（その値を知らない以前の scheduler にロールバックしても読めるように）。撤回せずに一覧から外しただけのイメージは、このようには落としません。そのイメージで予約された launch は、worker が付く前に作り直すとき、保存されたとおりそのイメージで作り直し（そのエンジンの撤回されていないイメージが一覧にないとき、またはそのイメージが撤回されたイメージと同じか確かめられないときは、作り直さずに戻します）、worker が付いた launch はそのまま動きます。そのイメージでもう起動しないようにするには、外さずに撤回します。数の上限は撤回されていないイメージだけに適用され、すべてのイメージを撤回した一覧でも起動します。このときはどのセッションも launch せず（一覧から外れたイメージの launch も作り直しません）、workspace quota の検査も行わず、checkpoint があるセッションは `runtime_retired` で止まり、scheduler は起動時にエラーログを一度残します。一つのエンジンのイメージだけがすべて撤回された場合も、そのエンジンのセッションには同じことが起きます。checkpoint がなく launch を待つそのエンジンのセッションは attention `NO_WORKER_IMAGE`（reason `runtime_retired`）を示し、そのエンジンの撤回されていないイメージを入れると消えます。アップグレード検査は、撤回したイメージを checkpoint を復元するイメージとして数えません。

プロファイル削除前にビルドした worker イメージは、プロファイル削除リリースの control-host の応答を読めないため、サポート範囲に入りません。そのリリースへの upgrade では、アップグレード検査のために `WORKER_IMAGE_PREVIOUS` がそのイメージになることがありますが、そのイメージで起動するセッションはありません（[プロファイル削除リリースのアップグレード順序](/run-server/self-hosting/upgrade-compose#프로필-제거-릴리스의-업그레이드-순서)）。

worker は claim 時に、実際に自分のイメージに含む組み合わせを送ります。設定値と違えば API が claim を拒否し（`LAUNCH_FAILED`、`reason_code` は `worker_image_mismatch`）、その設定値に対してそのイメージを拒否したと記録します。以後、そのイメージで起動するセッションは launch されず待機し、scheduler pass は `images_refused` を error ログに残して exit 1 で終了します。イメージ設定を修正すると（値が変わると）、次の pass から launch を再開します。セッション自体は失敗に変わりません。

デプロイ順序：新 worker は claim に `image_runtime` を含めます。このフィールドを知らない以前の API は拒否するため、API を先に更新し、その後 scheduler の `WORKER_IMAGE` を新イメージに変えます。プロファイル削除リリースへの更新は例外で、両方を一つの upgrade で一緒に変えます（[プロファイル削除リリースのアップグレード順序](/run-server/self-hosting/upgrade-compose#프로필-제거-릴리스의-업그레이드-순서)）。

| `EXECUTION_DOCKER_COMMAND` | なし | イメージ entrypoint の代わりに実行するコマンド（空白で分割）。試験用です |
| `DOCKER_HOST` | `unix:///var/run/docker.sock` | Docker daemon アドレス |
| `DOCKER_API_VERSION` | `v1.44` | 要求に使う Engine API バージョン |
| `EXECUTION_EGRESS_CREDENTIAL_PORT` | 3129 | proxy credential route のポート。proxy の `EGRESS_CREDENTIAL_PORT` と一致し、`EXECUTION_EGRESS_PROXY_URL` のポートとは異なる必要があります |

`EXECUTION_DOCKER_NETWORK`・`EXECUTION_DOCKER_NETWORK_ALLOWLIST` はもう読みません。値があれば起動を拒否します。

egress-proxy と API の authorizer listener は次の値を読みます。一覧変数は既定値に追加せず、全体を置き換えます。GitHub・bucket host を追加するときは provider・パッケージ registry など必要な項目をすべて再記入します。公開 credential 一覧（`EGRESS_CREDENTIAL_ALLOWLIST`）は proxy と API で同じ値にします。private 一覧（`EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST`）は proxy の拒否基準であり、API はコンソール警告だけに使います。private 一覧も一致を推奨しますが強制はなく、core・local-model layer の role 別既定値も異なります。

| `EGRESS_CREDENTIAL_PORT` | 3129 | 個別 key なし | credential route ポート |

| `EGRESS_ALLOWLIST` | 空一覧 | `config.egress.allowlist` | forward public 宛先のカンマ区切り `host:port`。credential・redirect 一覧との重複禁止 |

compose の三つのポートと二つの内部 URL は、`infra/compose.core.yml` 冒頭の `x-egress-ports` 一箇所で定めます。proxy の `EGRESS_PROXY_PORT`・`EGRESS_CREDENTIAL_PORT`・`EGRESS_AUTHORIZER_URL`、api の `EGRESS_AUTHORIZER_PORT`、scheduler の `EXECUTION_EGRESS_PROXY_URL`・`EXECUTION_EGRESS_CREDENTIAL_PORT` はすべてその anchor を使います。ポート変更時は同じ block の listener と URL の対を同時に変更します。テストが `docker compose config` の結果で二つの URL のポートと三つの listener が一致することを確認します。

API コンテナのメモリは checkpoint bundle 検証によって決まります。検証は同時に二つまで動き、各検証では git fetch と index-pack がそれぞれ `CHECKPOINT_GIT_MEMORY_MB` のアドレス空間上限の下で同時に動きます。両値は一緒に変更します。上限だけを上げると OOM killer が終了対象を決めることになります。計算は `infra/compose.core.yml` の api サービスのコメントにあります。

| 変数 | 既定値 | 意味 |
|---|---|---|
| `API_MEMORY_MB` | 7168 | compose api コンテナの `mem_limit`（MiB） |
| `CHECKPOINT_GIT_MEMORY_MB` | 1536 | bundle 検証の git 一プロセスのアドレス空間上限（MiB）。512 未満なら起動拒否 |

compose の Postgres は `POSTGRES_USER`（`postgres`）・`POSTGRES_PASSWORD`（`dev`）・`POSTGRES_DB`（`sessions`）で作り、すべてのサービスが同じ値で DSN を作ります。

worker は次も env から読みますが、scheduler が渡さないため運用ではコード既定値に固定です。`WORKER_ANSWER_POLL_SEC`（1）、`WORKER_ATTACH_FETCH_TIMEOUT_SEC`（300、セッション途中で追加した一つのリポジトリの取得時間）、`WORKER_ATTACH_FETCH_MAX_MB`（2048、そのリポジトリの scratch mirror サイズ）、`WORKER_CLAIM_TIMEOUT_SEC`（60）、`WORKER_DRAIN_TIMEOUT_SEC`（100、stop 猶予内に短縮）、`WORKER_HEARTBEAT_INTERVAL_SEC`（5）、`WORKER_IDLE_TIMEOUT_SEC`（1800）、`WORKER_LEASE_SAFETY_MARGIN_SEC`（10）、`WORKER_NEXT_INPUT_RETRY_SEC`（60）、`WORKER_NEXT_INPUT_WAIT_SEC`（20）、`WORKER_REQUEST_TIMEOUT_SEC`（30）、`WORKER_STARTUP_TIMEOUT_SEC`（3600）、`WORKER_CLAUDE_CONFIG_DIR`（`$HOME/.claude`）。

## 監督ループ

| 設定 | 既定値 | 意味 |
|---|---|---|
| `RECONCILER_INTERVAL_SEC` | 10 | pass 終了から次の pass までの待ち時間 |
| `RECONCILER_PASS_TIMEOUT_SEC` | 60 | 超過した pass を SIGTERM、その 10 秒後に SIGKILL で終了し失敗に数えます。DB 停止時の pass が pool timeout で自ら終わる約 45 秒より大きくします |
| `RECONCILER_MAX_CONSECUTIVE_FAILURES` | 3 | この回数連続で pass が失敗すると loop が exit 1 となり、`restart: unless-stopped` が再起動します。それ未満なら次の pass がすぐ再試行になります |
| `RECONCILER_HEALTH_STALE_SEC` | 90 | 最後に完了した pass が失敗、進行中 pass が期限超過、この時間内に成功 pass がない場合に healthcheck が unhealthy となります。成功直後に止まった pass も制限時間で即 unhealthy になります。`RECONCILER_INTERVAL_SEC + RECONCILER_PASS_TIMEOUT_SEC` より大きくないと起動しません |
| `RECONCILER_STATUS_FILE` | `/tmp/reconciler-status.json` | loop が pass ごとに更新する状態（`lastSuccessAt`・`lastDegradedAt`・`lastFailureAt`・`lastFailureReason`・`consecutiveFailures`・`lastPassDurationMs`、進行中 pass の `passDeadlineAt`）。healthcheck が読みます |
| `RECONCILER_BATCH_SIZE` | 100 | pass の各段階（orphan・lease・interrupt 回収、期限超過 interrupt・terminate receipt の `unknown` 確定、入力待ち通知、provider 呼び出し台帳の精算確認・期限切れ警告・整理）で一度に処理する row 数上限。残りは次の pass が処理します。scheduler の terminate 期限 sweep は読まず、毎 pass 固定上限 100 件ずつ処理します |

| scheduler 設定 | 既定値 | 制約 |
| --- | --- | --- |
| `SCHEDULER_INTERVAL_SEC` | 5 | pass 終了後の待機 |
| `SCHEDULER_PASS_TIMEOUT_SEC` | 180 | Docker stop+request timeout より大きいこと。Kubernetes は 150 秒超 |
| `SCHEDULER_MAX_CONSECUTIVE_FAILURES` | 3 | 連続失敗後に loop 終了 |
| `SCHEDULER_HEALTH_STALE_SEC` | 200 | interval+timeout より大きいこと |
| `SCHEDULER_STATUS_FILE` | `/tmp/scheduler-status.json` | ディレクトリ全体が書き込み可能なこと |

compose は `RECONCILER_STATUS_FILE`、`SCHEDULER_STATUS_FILE`、`RECONCILER_DRY_RUN` を渡しません。状態確認には各 status file と `--health` を使います。reconciler dry-run は[復旧作業](/run-server/self-hosting/recover-sessions)で直接一度実行します。`HEARTBEAT_TTL_SEC` は API だけが読み、reconciler に設定すると起動拒否します。

<a id="kubernetes-env와-values" />
## Kubernetes env と values

scheduler は `EXECUTION_BACKEND` で backend を選びます。値は `local_docker`（既定、空も同じ）と `kubernetes` の二つで、他の値ならその値を記したエラーで起動を拒否します。`kubernetes` では Docker 設定（`DOCKER_HOST`、`EXECUTION_DOCKER_*`、`EXECUTION_WORKSPACE_QUOTA`）を読まず、Docker socket も使いません。Docker 専用 preflight の egress proxy 隔離確認と workspace quota probe も実行しません。kubernetes の worker 隔離は chart の NetworkPolicy が担当し、workspace は PVC サイズを要求しますが実際の強制は保存先に依存します。停止・要求 timeout は固定値（120s + 30s）なので、`SCHEDULER_PASS_TIMEOUT_SEC` は 150 より大きくなければなりません。`migrate-workspace` は Docker volume 移行ツールのため `local_docker` だけで動きます。

readOnlyRootFilesystem の Pod では、status file を書き込み可能なパスに置きます。既定の `/tmp/scheduler-status.json`・`/tmp/reconciler-status.json` は、`/tmp` に emptyDir を mount すれば使えます。別パスなら `SCHEDULER_STATUS_FILE`・`RECONCILER_STATUS_FILE` で変更します。loop は status file と同じディレクトリに一時ファイル（`<status file>.<pid>.tmp`）を書いてから rename します。scheduler は隣に `.quota-verified` 記録も置きます。そのため一つのファイルだけでなくディレクトリ全体が書き込み可能でなければなりません。

共有 env（`WORKER_IMAGE`、`WORKER_GATEWAY_URL`、`EXECUTION_EGRESS_PROXY_URL`、`EXECUTION_EGRESS_CREDENTIAL_PORT`、`EXECUTION_INSTALLATION_ID`、`EXECUTION_WORKSPACE_QUOTA_MB`、`EXECUTION_WORKSPACE_GC_MIN_AGE_SEC`、`S3_BUCKET`、`AWS_REGION`）は Docker backend と同じです。kubernetes モードでは次の二つに追加制約があります。

- `WORKER_IMAGE` は `repository@sha256:<digest>` 形式でなければなりません。
- `EXECUTION_INSTALLATION_ID` は 32 文字以下の小文字 DNS label でなければなりません。

kubernetes モードだけで読む設定は次のとおりです。

`EXECUTION_WORKSPACE_ENFORCED_BY_STORAGE` は未設定なら `false` で、正確な `true`/`false` のみ受け付けます。空値・空白・大文字・`1`/`0`・`on`/`off` は元の値を出さないエラーで起動を拒否します。Helm の `worker.workspace.enforcedByStorage`（既定 `false`）から生成し、この設置の全 workspace PVC（既存を含む）で保存先が要求バイト数をハードに強制するという運用者の宣言です。StorageClass が空ならクラスタ既定値なので、各 PVC の強制を運用者が確認します。Werft は検証しません。専用書き込み可能 mount（`/` 以外、`rw` あり、`ro` なし）、ファイルシステム総量が要求の 0.95〜1.05 倍、PVC capacity が要求以上というヒューリスティックを満たした宣言経路だけがバイト `hard`/inode `unknown` になります。[ストレージと上限](/run-server/self-hosting/reference/storage)に従います。宣言を変えても PVC・isolation stamp・既存 Pod の env は変わらず、新しい Pod だけが新しい値を受け取ります。

| 変数 | 意味 |
| --- | --- |
| `EXECUTION_K8S_NAMESPACE` | worker Pod・Secret・PVC を配置する namespace。既定は scheduler 自身の namespace です。クラスタ外で実行する場合は必須です |
| `EXECUTION_K8S_WORKER_SERVICE_ACCOUNT` | worker Pod の ServiceAccount。token は常に mount しません |
| `EXECUTION_K8S_STORAGE_CLASS` | workspace PVC の StorageClass。空ならクラスタ既定値です |
| `EXECUTION_K8S_IMAGE_PULL_SECRETS` | 任意。カンマ区切りの Secret 名 |
| `EXECUTION_K8S_WORKER_NODE_SELECTOR` | 任意。JSON object |
| `EXECUTION_K8S_WORKER_TOLERATIONS` | 任意。JSON array |
| `EXECUTION_K8S_WORKER_EPHEMERAL_STORAGE_MB` | worker コンテナの ephemeral-storage requests・limits（MiB）。既定 1024。超過すると kubelet が Pod を evict します |

失敗した worker の終了理由とログ tail（最後の 8 KiB）は、scheduler ログの `Execution resource failed; log tail kept` 行に残ります。ログのマスキング規則は tail を行単位で隠します。秘密の形をした値は、その値がまたがる行だけを隠します。`input:` のような断片は、その行から最後までを隠します。それより前の行は残ります（URL の login はその部分だけ隠します）。保存先と保持期間は、リポジトリの Kubernetes 実行アダプターの README（終了理由とログ tail 節）にあります。

<a id="probe" />
## probe の設定

| コンポーネント | readiness | liveness | startup |
| --- | --- | --- | --- |
| api | `GET /readyz` | `GET /healthz` | `GET /healthz`（5 秒 × 24） |
| scheduler | `bun run apps/control-host/src/main.ts scheduler --health` | 同じ | 同じ。失敗許容回数は `(intervalSec + passTimeoutSec + 39) / 10` |
| reconciler | `bun run apps/control-host/src/main.ts reconciler --health` | 同じ | scheduler と同じ式 |
| slack | `bun run apps/control-host/src/main.ts slack --health` | 同じ | scheduler と同じ式 |
| egress-proxy | `bun run /app/src/healthcheck.ts` | 同じ | なし |

`/healthz` は HTTP を受け付けるかだけを見て DB を確認しません。そのため liveness に使い、DB・schema・設定を見る `/readyz` は readiness だけに使います。DB が一時的に切れても api Pod は再起動せず、トラフィックから外れるだけです。`/livez` はありません。scheduler・reconciler・slack の `--health` は loop が書く status file を読み、直前 pass が失敗または期限超過した、あるいは `SCHEDULER_HEALTH_STALE_SEC`・`RECONCILER_HEALTH_STALE_SEC`・`SLACK_ROLE_HEALTH_STALE_SEC` 内に完了 pass がなければ失敗します。startup probe は最初の pass の完了を待ちます。

| `DATABASE_URL` | api、scheduler、reconciler、slack、migrate、checkpoint GC、metrics、upgrade-check Job、session archive CronJob |

| `AWS_ACCESS_KEY_ID`、`AWS_SECRET_ACCESS_KEY` | api、checkpoint GC、session archive CronJob。`secrets.objectStoreKeys: true` の場合だけ。`false` なら AWS 既定 credential chain（IRSA）で署名します |
| `PLATFORM_SECRET_KEY` | api、slack。必須。64 文字 hex の master key。コンソールに保存した資格情報を封印します。Secret にないと Pod は起動しません |

master key は `PLATFORM_SECRET_KEY` の代わりに、key を入れたファイルのパスを `PLATFORM_SECRET_KEY_FILE` で渡せます（compose secret のようにマウントしたファイル。末尾の改行一つは無視します）。両方あるときは同じ key でなければならず、違うと api と slack の役割は起動を拒否します（`master_key_mismatch`）。どちらもないか、ファイルを読めなければ `master_key_missing` です。コンテナ内で運用者コマンドを実行するときは、そのコマンドの環境にもどちらかが必要です。entrypoint がサーバープロセスにだけ key を渡す構成では、`docker compose exec` で起動したコマンドは key を受け取れないため、サービスの env に `PLATFORM_SECRET_KEY_FILE` を置きます。

モデル接続・MCP サーバー・リポジトリの GitHub App key は、Secret や環境変数では渡しません。コンソール（または credential API）で入れ、`PLATFORM_SECRET_KEY` で暗号化して DB に保存されます。`secrets.catalogEnv` と `config.aws.secretsManagerEndpointUrl` はなくなり、values に残っているとレンダリングが失敗します。`secrets.bootstrapToken` もなくなり、残っているとレンダリングが失敗します。最初の owner は、api Pod で `bun run apps/control-host/src/api/setup-link.ts` が出力する一回限りの設定リンクで作ります。リンクは DB にあるため、replica の数に関係なく使えます。

## 使用量と費用の計測

- セッション費用は credential route が計測します。proxy は 2xx の `/v1/messages` 応答（JSON・SSE 両方）から usage を読みます。応答の完了または切断時に authorizer listener の `POST /usage` へ報告します。`count_tokens` とエラー応答は数えません。
  - 応答に usage が揃わなければ多めに推定します。`message_stop` 前に切れた stream は、転送した content の一文字を一 token として output に含め、転送した web search 結果ブロック一つを検索一回と数えます。usage を読めない JSON 応答（切断、8 MiB 超、JSON 以外）は要求から数えます。要求 1 byte を input token 一つ、`max_tokens` を output 全量とします。このような呼び出しは proxy が `Provider usage estimated` 警告を記録し、ledger に `estimated=true` と記します。
  - API は価格表で USD を求め、micro-dollar 単位に切り上げます。その額を `provider_usage` に一交換一行で記録し、同じ transaction でセッション費用に加算します。そのため ledger 合計とセッション費用は一致します。
  - engine の呼び出しも、ツールが engine の token で直接呼び出したものも同じように数えます。
  - 報告には proxy が交換ごとに作る id が付きます。authorizer が応答できなければ 1・5・15 秒後に再送し、同じ id は一度だけ数えます。最後まで報告できなければ proxy が `Provider usage went unreported` エラーログを残し、その交換は計測されません。
- turn 終了時に SDK が返す `total_cost_usd` の増分は turn 結果（`cost_usd`）だけに残し、セッション費用には加算しません。engine の turn 別 `maxBudgetUsd` は引き続き SDK 値で判定します。proxy 計測導入前のセッションは、それまで SDK 値を加算した費用を引き継ぎます。
- 価格表はプラットフォームコードが管理します。model id 別に input、output、cache write（5 分は 1.25 倍、1 時間は 2 倍）、cache read の単価を設定します。項目ごとに[公式単価](https://platform.claude.com/docs/en/about-claude/pricing)を確認した日付があります。モデル追加や価格変更時はリリースと一緒に修正します。
  - fast mode はモデルの標準単価に fast 倍率を掛けて数えます。現在は Fable 5.2・Mythos 5.2（$16/$80）、Opus 5.5（$8/$40）、Opus 5・Opus 4.8（$10/$50）だけです。cache 倍率は fast 単価にそのまま掛けます。speed は応答の `usage.speed`、なければ要求の `speed` に従い、両方なければ `standard` です。
  - Claude の表にあるモデルの `fast` 応答に fast 倍率がない場合や、speed が定義名以外の値の場合は、モデル自身の単価（長い prompt の単価を含む）に両表を通じた最大の倍率（現在 6 倍、OpenAI の Ultrafast）を掛けて数えます。OpenAI の表が項目にない段階を数える方法と同じで、ledger には `priced_by=table` と記します。
  - どちらの表にもないモデルは、項目ごとに両表を通じた最高単価で数えます。authorizer が `Provider usage priced at the fallback rate` 警告を記録し、ledger には `priced_by=fallback` と記します。Claude の表に名前がないモデルが最高単価で数えられる場合、OpenAI の呼び出しである可能性があります。どちらの表にもないモデルと、長いコンテキストの単価が表にない OpenAI モデルの 272K 超の呼び出しが該当します。このとき speed が `standard` でなければ、最高単価に OpenAI の表がその段階に持つ最大の倍率を掛けます。`fast` は 2.5 倍、それ以外の段階は 6 倍です。OpenAI の表に名前があるモデルは、自分の項目の倍率のほうが大きければその倍率を使います（項目にない段階は 6 倍）。cache write は speed にかかわらず input 単価の 1.25 倍、長く保持する write は 2.5 倍（OpenAI の 12 時間 write）で数えます。Claude の表に名前があるモデルは、この倍率の代わりに自分の fast 倍率か上の最大の倍率と、Claude の cache write 倍率を使います。
  - OpenAI モデルは別に置いた OpenAI の単価表で数えます。項目ごとに[公式単価](https://developers.openai.com/api/docs/pricing)を確認した日付があります。speed 段階はモデルの標準単価に倍率を掛けます。`fast` はほとんどのモデルで 2 倍、`gpt-5.5` は 2.5 倍です。Ultrafast（`ultrafast`）は `gpt-6-astra` と `gpt-6.1-sol` にだけあり 6 倍です。モデルの項目にない段階は、名前にかかわらず表が知る最大の倍率（6 倍）で数えます。Pro モデル（`gpt-5.5-pro`、`gpt-5.4-pro`、`gpt-5.2-pro`、`gpt-5-pro`、`o3-pro`）は cache 割引がないため、cache read も input 単価で数えます。Pro の単価は上の最高単価に含めません。長いコンテキストの単価が表にない Pro モデルの 272K 超の呼び出しだけを Pro の最高単価で数えます。
  - 応答の `usage.server_tool_use` の web search 一回ごとに $0.01（1,000 回 $10）を加算します。web fetch は token 以外の料金がありません。code execution は加算しません。web search・web fetch と併用すれば無料で、それ以外では呼び出し数でなくコンテナ時間で課金され、組織の無料時間もあるためです。三つの回数と speed は ledger（`provider_usage`）に記録します。
  - 4.6 以降のモデルが US 限定推論（`inference_geo: "us"`）の場合、token 単価すべて（fast・cache を含む）に 1.1 倍を掛けます。web search 料金には掛けません。geo は応答の `usage.inference_geo`、なければ要求の `inference_geo` に従い、両方なければ `unknown` です。workspace の既定値が `us` の場合があるためです。`global`・`us` 以外はモデル自身の単価に最大の geo 倍率（1.1 倍）を掛けて数えます（`priced_by=table`）。どちらの表にもないモデルは最高単価の 1.1 倍です。geo は ledger の `inference_geo` に記録します。これを知らない以前の API はフィールド付き報告を `400` で拒否し、proxy はその交換を計測できません（`Provider usage went unreported`）。そのため API（migration 含む）を egress proxy より先に更新します。順序は [Compose アップグレード](/run-server/self-hosting/upgrade-compose#2-api--proxy--worker-순서)と [Kubernetes アップグレード](/run-server/self-hosting/upgrade-kubernetes#1-대상-chart와-제어-영역-우선-교체)に従います。新 API はこのフィールドがない以前の proxy の報告も受け付けます。
  - 4.6 より前のモデル（Opus 4.5・4、Sonnet 4.5・4、Haiku 4.5）は `inference_geo` を受け付けないため geo によらず標準単価です。window は 200K で、公開された long-context 単価がありません。そのため input・cache write・cache read 合計が 200K を超える呼び出しは最高単価で数えます（`priced_by=fallback`）。speed が `standard` でなければ、さらに上の speed 倍率を掛けます。4.6 以降は 1M 全体が標準単価です。Haiku 5.5 だけは prompt（input・cache write・cache read の合計）が 100K を超えると、すべての部分を高い単価（$0.50/$2.50、cache read $0.05）で数えます。
  - batch は credential route が `/v1/messages/batches` を開かないため対象外です。
- トークン上限は、`provider_usage` 一行の `input_tokens + cache_creation_input_tokens + cache_read_input_tokens + output_tokens` を `sessions.provider_tokens` に加算して数えます。`provider_usage` の insert trigger が同じ transaction で加算するため、rollout 中や rollback 後に 0127 より前の API が記録した呼び出しも取りこぼしません。cache read もモデルが処理した token なので数えます。多めに推定した報告は推定値のまま足します。累計を追加した migration は既存セッションを `provider_usage` 合計で埋めます。それ以前に SDK 値だけで費用を数えたセッションの token は補えません。累計は 2^53-1（`Number.MAX_SAFE_INTEGER`）で止まります（migration 0129）。trigger は numeric で加算するため、異常に大きな token 値でもエラーで usage 記録や費用を rollback しません。
  - SDK に token 予算オプションはありません。そのため turn 中の token 上限は下記の egress 拒否と再認可だけが担当します。上限到達後に開いた Messages 呼び出しは拒否され、turn は `failed(budget_exceeded)` で終了し、次の turn から `BUDGET_EXCEEDED` で dispatch されません。proxy は authorizer の `BUDGET_EXCEEDED` 拒否を Messages エラー形式（`message` が `BUDGET_EXCEEDED:` で始まる）で伝えます。理由はこの文言からは決めません。engine はこの 403 を `api_error` として報告し、再認可で切れた交換も再試行がなければ（`PROVIDER_MAX_RETRIES=0`）、切れた接続のまま `api_error` と報告します。finalize は `api_error` で終了した turn のセッションが既に上限を超えていれば、理由を `budget_exceeded`、receipt エラーを `BUDGET_EXCEEDED` と記録し、engine の provider 診断（`provider_error`）を消去します。上限未満で発生した 403 は `api_error` のままです。
- 費用・token 上限は呼び出し完了後に判定します。同時に開く呼び出しがすべて認可を通過する場合があり、進行中の turn は上限を超え得ます。
- 累積費用または token が上限以上のセッションの provider egress token は、authorizer が 403 `BUDGET_EXCEEDED` で拒否します。新 provider 交換は即座に拒否し、既存交換は次の再認可（30 秒周期）で切断します。repository・object store route は拒否しません。

## トレースのエクスポート [#트레이스-내보내기]

API だけが読む設定です。既定はオフで、キーを一つも設定しなければ span を作らず、何も送りません。オンにすると、ログの `trace_id`・`span_id` がアクティブな span の中で記録されます。collector は OTLP/HTTP（protobuf）を受け取れるものなら何でも使えます。サンプル collector は[観測](/observability)にあります。

| キー | 既定値 | 意味 |
|---|---|---|
| `OTEL_TRACES_EXPORTER` | `none` | `none` または `otlp` |
| `OTEL_EXPORTER_OTLP_ENDPOINT` / `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | なし | collector のアドレス。前者は末尾に `/v1/traces` を付け、後者はそのまま使います。`otlp` なのにどちらもなければ起動しません |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | `http/protobuf` | この値だけを受け付けます |
| `OTEL_EXPORTER_OTLP_HEADERS` / `OTEL_EXPORTER_OTLP_TRACES_HEADERS` | なし | `キー=値,キー=値`（値はパーセントエンコード、印字可能な ASCII のみ）。同じ名前なら後者が優先されます。形式が誤っていれば起動しません。秘密情報なので env ファイルでだけ渡し、値はログやエラーメッセージに出ません |
| `OTEL_SERVICE_NAME` | `werft-api` | サービス名 |
| `OTEL_TRACES_SAMPLER` / `OTEL_TRACES_SAMPLER_ARG` | `always_on` / `1.0` | `always_on`、`always_off`、`traceidratio`（比率 0〜1） |
| `TRACE_TENANT_HEADER` | なし | `<ヘッダー名>: <値テンプレート>`。テンプレートの `{workspace_id}` をワークスペース id に置き換え、batch ごとに付けます |
| `TRACE_INSTALL_TENANT` | なし | ワークスペースのない span のテナント値 |
| `TRACE_TENANT_HEADERS_FILE` | なし | ワークスペースごとのヘッダーを書いた JSON ファイル。mode 600 でなければ起動しません。同じヘッダー名なら、このファイルが `TRACE_TENANT_HEADER` と `OTEL_EXPORTER_OTLP_HEADERS` より優先されます |
| `TRACE_INGEST_URL` | なし | worker が span を送る API の ingest アドレス（`http`・`https`）。`otlp` なのになければ起動しません |
| `TRACE_CONTENT_MODE` / `TRACE_CONTENT_MAX_BYTES` | `full` / `32768` | プロンプト・回答・ツールの入出力を span に載せるか（`full`・`metadata`）と、内容属性一つのバイト上限。設置全体に一つだけ適用されます |
| `TRACE_INGEST_PORT` / `TRACE_INGEST_MAX_REQUEST_BYTES` / `TRACE_INGEST_MAX_BYTES_PER_MIN` / `TRACE_MAX_BYTES_PER_TRACE` / `TRACE_FENCED_GRACE_SEC` | `4319` / 4 MiB / 32 MiB / 20 MiB / `300` | ingest listener のポートと上限。0・負の値・数値でない値なら、キー名を示して起動しません |

`TRACE_TENANT_HEADERS_FILE` の形式です。値は秘密情報なので、リポジトリに置きません。

```json
{ "<workspace_id>": { "<header name>": "<secret value>" } }
```

**有効にする最小設定.** 次の値を api の env に渡します。プロンプト・回答・ツールの入出力は span 属性（`gen_ai.*`）に載るため、ログストアは別途要りません。

```bash
OTEL_TRACES_EXPORTER=otlp
OTEL_EXPORTER_OTLP_ENDPOINT=https://otel-collector.example.com:4318
TRACE_INGEST_URL=http://api:4319
EGRESS_PRIVATE_ALLOWLIST=api:3000,host.docker.internal:3000,api:4319
```

- **Compose.** 上の値を compose を起動するシェルか `.env` に置くと、同じ名前で api コンテナに渡ります。worker が ingest に向かう経路も egress proxy を通るため、`EGRESS_PRIVATE_ALLOWLIST` の既定値 `api:3000,host.docker.internal:3000` に `api:<TRACE_INGEST_PORT>` を加えます。
- **Kubernetes.** キーは `api.extraEnv` に渡します。ポートは Service と NetworkPolicy も知る必要があるため、`config.tracing.ingestPort`（既定 `4319`）でだけ変え、`TRACE_INGEST_PORT` は渡しません。`TRACE_INGEST_URL` は `http://<api Service 名>:4319` で、`config.egress.privateAllowlist` を `<api Service 名>:3000,<api Service 名>:4319` に指定します。
- worker は collector に直接接続しません。collector の host を `EGRESS_PRIVATE_ALLOWLIST` や `EGRESS_ALLOWLIST` に入れると、api が起動時に警告を残します。`OTEL_*` キーは worker とエンジンに渡りません。

**collector 側の条件.**

- トレース一つのサイズ上限を `TRACE_MAX_BYTES_PER_TRACE` より大きくします。小さいと collector が大きなトレースを捨てます。
- テナントヘッダーを設定しない設置では、すべてのワークスペースのトレースが一か所に集まります。収集バックエンドの画面は運用者だけが見られるようにします。
- `TRACE_CONTENT_MODE=full` なら、プロンプト・回答・ツールの入出力が collector に送られます。送らないなら `metadata` にします。

**span.** `/v1/**` リクエストごとに `{METHOD} {route_template}` span（例: `POST /v1/sessions/:id/turns`）が新しい root として作られます。クライアントが送った `traceparent` は親ではなく link としてだけ残り、その sampled フラグには従いません。ヘルス・メトリクスのパスには span がありません。turn の span はセッションと turn 番号で決まる別のトレース（root `werft.turn`）に付き、turn をキューに入れたリクエストの span と前の turn の root とは link でつながります。worker gateway の呼び出しは、その turn トレースの `traceparent` を載せたときだけその下の子 span になり、それ以外の gateway 呼び出し（heartbeat、long poll など）には span がありません。

## セッションタイトルの生成 [#세션-제목-생성]

セッション作成時に `title` がなければ、最初のメッセージを 80 文字で切った値がタイトルになります。最初の turn が `completed` で終わると、API がその turn のメッセージと回答から短いタイトルを一度だけ取得して置き換えます。

| 変数 | 既定値 | 許容範囲 |
|---|---|---|
| `SESSION_TITLE_EGRESS_URL` | compose `http://egress-proxy:3129` | egress proxy の credential route のアドレス。空にするとこの機能はオフになります。Codex 接続（`openai_responses`）のセッションはモデルでタイトルを作らず、最初のメッセージから作ったタイトルをそのまま残します |

- 呼び出しはセッションの接続とモデルで provider route を通るため、費用は最初の turn の usage とセッション上限に入ります。proxy は `/v1/messages`、セッションのモデル、`max_tokens` 64 以下のリクエストだけを送ります。
- API はこの URL の host:port にだけ送り（メタデータ・link-local アドレスは拒否）、redirect には従わず、25 秒で打ち切ります。
- 利用者が付けたタイトルや `PATCH /v1/sessions/{id}` で変えたタイトルは上書きしません。呼び出しが失敗するか回答が空なら、最初のメッセージのタイトルが残ります。

## 設定文書のインポートとエクスポート [#설정-문서-가져오기내보내기]

モデル接続・リポジトリは DB の行です。コンソールで一つずつ扱うか、**設定文書** 一つで入れて取り出します。初回デプロイの migrate は空の設置にだけ文書を一度入れ、その後のデプロイは文書を読みません。その後に文書から追加するには、次のコマンドでインポートします。

- **形式.** `{"version": 1, "connections": {…}, "repositories": {…}}`。`mcp_servers` 欄が空でない文書は文書全体を `400 BAD_REQUEST`（`reason_code: invalid_document`）で拒否し、エラーにはそのサーバー名と「設置カタログ MCP はなくなった」という案内だけが出ます。空の欄（`{}`）や欄のない文書は受け付け、エクスポートはその欄を書きません。資格情報は `"auth": {"stored": true}` と書き、値はインポート後にコンソールで入れます。値のない行は `needs_value` で、その行を使うセッションは動きません。エクスポートは `{"stored": true, "last4": "…"}` だけを出し、値は出しません。master key は文書に入りません。`value_env`・`secret_id` の参照と最上位の `profiles` は拒否します。
- **インポートは追加だけを行います.** 項目ごとに `add`（新しい行）、`unchanged`（同じ行）、`inactive`（使用停止した行と同じ id）、`needs_value` に分けます。同じ id で内容が違うか、同じ GitHub リポジトリを別の id で書くと `conflicts` で、その場合は何も書きません。行を変更・削除することはありません。
- **Compose.** `bun run settings export > settings.json` は文書を stdout に、`digest sha256:…` を stderr に出します。インポートは `bun run settings import --document - --dry-run < settings.json` で先に確認し、`--dry-run` を外してもう一度実行します。コマンドは api コンテナの中で動くため、ホストのファイルは `-`（stdin）で渡します。拒否されると 1 で終わります。
- **Kubernetes.** `bun run settings:k8s export` のように、`settings:k8s` が api Pod の中で同じ CLI を実行します。
- **API.** `GET /v1/installation/settings/export` は `{document, digest}` を、`POST /v1/installation/settings/import?dry_run=true` は判定結果を返します。設置 owner のログインセッションだけが呼び出せ、API key は `403` です。衝突は `409 REVISION_CONFLICT`、誤った文書は `400 BAD_REQUEST` です。
- **ファイルカタログで動いていた設置.** `PLATFORM_CONFIG_DIR`・`SESSION_CATALOG_JSON` は読まず、値が残っていると api は起動を拒否します。上げる前に二つの値を env から消し、Compose では古い設定ディレクトリを `PLATFORM_LEGACY_CONFIG_DIR` で渡します（`/legacy-config` に読み取り専用でマウントされます）。`platform.yaml` はインポートしないため、master key は上げる前に同じ値で `PLATFORM_SECRET_KEY` に移します。値が違うと保存した資格情報を読めません。master key なしで動いていた設置は先に新しい key を入れます。なければ api と slack の役割は起動を拒否します。migrate がそのディレクトリを一度インポートし、その後はディレクトリと `PLATFORM_LEGACY_CONFIG_DIR` を消してかまいません。手でインポートするときは `bun run settings import --from-dir <dir>` を使います。ディレクトリからのインポート（migrate と `--from-dir`）ではリポジトリだけが例外で、認証の種類が同じで内容が違うリポジトリと、すでに行がある GitHub リポジトリの別名は `conflicts` ではなく `kept` とし、DB の行をそのまま使います。
- **設置カタログ MCP.** 設置 owner がコンソールや設定文書の `mcp_servers` で追加していたリモート MCP サーバーは、migration `0304_retire_catalog_mcp` が削除します。カタログの行、その保存値、エージェントのカタログ選択が消え、migrate ログ `db.migrate.notice` に削除したサーバーの数と名前が残ります。ワークスペース MCP サーバーへは移さないため、使い続けるサーバーは上げる前に名前を控え、上げた後にワークスペース MCP サーバー（設定 > エージェント接続 > **MCP サーバー**）として登録し、エージェントのアクセスタブで選びます。新しく登録する名前に `github`・`browser`・`memory` は使えず（`memory` は既存のワークスペースサーバーならそのまま残ります）、名前はワークスペース内で重ならなければかまいません。そのためカタログの `memory` サーバーは別の名前で登録します。API の起動時、カタログサーバーを書いたエージェントの下書きは、そのサーバー（`capabilities.mcp`）、そのサーバーのツールの `tool_policy.per_tool` 項目、そのサーバーが使っていた `credential_ref` を除いた新しいバージョンに移されます（`forbidden` とカードの他の名前は残ります）。移したものがあれば `Drafts naming a retired catalog MCP server reconciled` ログにその数が残ります。既存の release は変わらず、再び有効化できます。古い release のセッションはそのサーバーなしで動き、そのサーバーが使っていた credential 名の紐付けを外しても開始します。セッションには「なくなったカタログ MCP `<名前>` はスキップ」という一行が一度残ります。そのサーバーを入れて撮った checkpoint も復元されます。ただし復元候補が 16 個埋まったセッションは、最も古い候補一つの checkpoint を復元できないことがあり、そのとき API ログに `claim.retired_catalog_restore_dropped` 警告がセッション id とともに残ります。rolling deploy 中に古い replica がカタログに書き込むと（インポート、コンソール、カタログサーバーを書いたカードの保存）DB が拒否するため、上げている間はカタログを変えません。
- **戻せる下限.** インポートで `auth_kind` が `github_app_explicit` のリポジトリ行を書いた DB は、`auth_kind` を知らない古いイメージに戻しません。古いイメージはその行をコンソールの GitHub App リポジトリとして読みます。
