## Contract

This is the source of truth for storage limits and reclamation conditions. For resizing, see [Capacity planning](/run-server/self-hosting/capacity); for post-failure decisions, see [Session recovery](/run-server/self-hosting/recover-sessions).

## Workspaces by backend

| Item | Single server | Kubernetes |
| --- | --- | --- |
| Location | Docker `local` volume per session, on Docker data-root XFS | One PVC/session (`werft-ws-<installationId>-<sessionId>`), mounted at worker `/workspace`; `ReadWriteOnce`, `Filesystem`. `/tmp` and HOME are memory emptyDir; no hostPath |
| Capacity limit | `EXECUTION_WORKSPACE_QUOTA_MB`, default 4096MiB, minimum 1024 | PVC `requests.storage`, Helm `worker.workspace.quotaMb`, default 4096MiB, minimum 1024. Actual enforcement depends on StorageClass |
| Inode limit | `EXECUTION_WORKSPACE_QUOTA_INODES`, default 1,000,000 | **None.** Neither Werft nor chart sets it. Filesystem defaults apply (ext4 fixes inode counts at creation) |
| Enforcement | Kernel XFS `prjquota`, checked by scheduler preflight | CSI driver and filesystem. Werft reads PVC capacity and workspace usage, but has no preflight that verifies actual enforcement |
| When exceeded | Worker writes get `ENOSPC`. Scheduler cannot start without enforceable limits | `ENOSPC` if StorageClass enforces capacity; otherwise effectively unlimited. If node disk usage outside the PVC (primarily logs) exceeds `worker.ephemeralStorageMb` (default 1024 MiB, requests=limits), kubelet evicts the Pod |
| Operator settings | Docker data-root filesystem/size and both limits above | `worker.storageClass` (empty uses cluster default), `worker.workspace.quotaMb`, `worker.workspace.enforcedByStorage`, `worker.ephemeralStorageMb`, worker-node filesystem size |
| Checks | `findmnt -no FSTYPE,OPTIONS -T "$(docker info -f '{{.DockerRootDir}}')"`, `xfs_quota -x -c 'report -p'` | Below |

```bash
kubectl get storageclass
kubectl -n werft get pvc -l app.kubernetes.io/part-of=werft,werft.installation=<installationId> \
  -o custom-columns=NAME:.metadata.name,REQUEST:.spec.resources.requests.storage,CAPACITY:.status.capacity.storage
kubectl -n werft exec <worker-pod> -- df -h /workspace
kubectl -n werft exec <worker-pod> -- df -i /workspace
```

Use `kubectl get storageclass` to check whether the chosen provisioner creates capacity-enforcing volumes (EBS gp3, for example, creates a block device of the requested size). PVC `REQUEST` is Werft's request; `CAPACITY` is provisioned size. Filesystem overhead can change `df -h` totals, so do not require exact equality. Verify `CAPACITY` is at least `REQUEST` and that a test PVC using the same StorageClass returns `ENOSPC` when writes exceed `REQUEST`. Check inode totals with `df -i`. These Kubernetes commands, capacity enforcement, and AZ reattachment have not been verified by execution. Values come from the code and the chart.

- **PVCs are mandatory.** Worker workspace volumes are always PVCs, with no emptyDir/hostPath option. Session PVCs outlive Pods and reattach under the same name after replacement. The scheduler creates Pods and PVCs per session.
- **Werft does not verify StorageClass hard enforcement.** It requests `requests.storage`, records it in `werft.workspace-size`, and compares configuration. It reads PVC `status.capacity` and passes it to the worker, which observes workspace usage and filesystem totals/inodes. These observations do not verify enforcement. Confirm CSI/filesystem enforcement with infrastructure operators before installation.
- kind's default local-path-style StorageClass is known not to enforce PVC size. Bound status does not establish a hard limit.
- **Known limits:** no inode limit; capacity enforcement is delegated to StorageClass. The chart does not reject non-enforcing classes. Code changes addressing this are outside this page's scope.

Zonal PVCs such as EBS are bound to an AZ. After node replacement or Kubernetes upgrades, verify workers reattach on available nodes in the same AZ.

Changing `worker.workspace.quotaMb` makes existing PVC `werft.workspace-size` annotations differ and rejects those sessions' launches. Change it for new sessions when none are active. Do not delete existing PVCs to resize them.

`worker.workspace.enforcedByStorage: true` (default `false`) is an operator declaration that storage hard-enforces requested bytes for **every workspace PVC in this installation, including existing PVCs**. With an empty `worker.storageClass`, the cluster default applies: operators must verify actual enforcement for each PVC. Werft does not verify it. The declaration does not impose a storage limit.

In the declaration path, the worker classifies bytes as `hard` and inodes as `unknown` when filesystem total size is 0.95–1.05 times the request, PVC capacity is at least the request, and a dedicated writable mount has a mount point other than `/` (`rw` present, `ro` absent): `storage_declaration_and_capacity`. Missing mount/filesystem evidence or capacity yields `unknown`. Other unmet declaration conditions yield `unknown`/`storage_enforcement_unverified`; shared filesystems, zero total inodes, and filesystems over 1.5 times the request retain their existing `soft` classification. These size/mount checks are heuristics, not enforcement verification. The declaration and classification evidence appear in the `workspace_limit_mode` log's evidence.

If a PVC is not yet bound or the scheduler lacks PVC `get` permission, its capacity is unavailable. Even with mount/filesystem evidence and no existing `soft` classification such as a shared filesystem, missing capacity keeps the result `unknown` (`storage_capacity_unavailable`); the declaration cannot replace that evidence.

Changing the declaration leaves PVC size/name/annotations and the isolation stamp unchanged, so it neither replaces existing Pods nor rejects resume. Running Pods keep their env; only newly created Pods receive the new declaration.

<a id="transcript-상한" />
## Transcript limits

Total transcript size in one checkpoint (root and every subagent) must not exceed 512MiB; each part must not exceed 16MiB. Three checks use the same values:

1. Worker capture before checkpoint upload (`captureTranscripts`, before manifest upload/commit).
2. API finalize before reading parts; this is authoritative.
3. Restore before downloading parts (`#checkManifest`).

Size means the entire JSONL remaining after compaction. Claude Code CLI resume skips content before the last compaction, but the platform stores/restores entire files, so limits apply to the full size.

<a id="80-경고" />
### 80% warning

- The first committed checkpoint reaching 80% (409.6MiB) emits one SSE `system` event (`transcript_near_limit`) and sets session `attention` to `TRANSCRIPT_LIMIT`. It does not block execution.

<a id="상한을-넘으면" />
### Exceeding the limit

- Worker prechecks (before workspace upload) or finalize (before reading parts) set `durability.checkpoint_pending_reason` to `transcript_too_large` (or `transcript_part_too_large` for one oversized part). The first occurrence emits one SSE `system` `transcript_limit_reached` event.
- The oversized turn still finishes `completed` as executed, but its checkpoint does not commit.
- New messages then return 409 `CHECKPOINT_UNAVAILABLE`; queued turns do not execute. Start a new session or use recovery `start_fresh`. close also returns 409 `CHECKPOINT_UNAVAILABLE`; terminate, then use recovery close.
- Interrupted turns differ: rejected checkpoints make the turn `outcome_unknown` (`interrupt_checkpoint_unavailable`) and the session `recovery_required`.
- The last committed checkpoint remains the restoration point. The oversized turn lacks a checkpoint, so its context cannot continue after worker replacement (session attention `CONTEXT_GAP`).

## Output (`out/`) index limits

At each checkpoint, workers index regular files under working-directory `out/` regardless of git status, add manifest `outputs`, and upload one object/file. Limits are the worker's default output limits.

| Value | Default | When exceeded |
|---|---|---|
| Per-file `maxFileBytes` | 64MiB | Records only `{path, bytes, omitted: "too_large"}`, without upload |
| Per-checkpoint upload total `maxTotalBytes` | 256MiB | Files that would exceed the total become `too_large` |
| File count `maxFiles` | 1,000 | Files after the first 1,000 in path order are omitted; publish logs record their count in `outputs_dropped` |

- Index limits do not fail checkpoints. Git bundle limits (256MiB) and workspace quotas still apply; large `out/` files tracked by git or bundled in repository-free sessions can hit those separately. Untracked, nonignored `out/` files still upload as restoration untracked objects even if indexed as `too_large`.
- Manifest limits (20,000 objects, 8MiB) also do not fail checkpoints. Outputs fit only in the object slots left by restoration objects; excess files count as `outputs_dropped`. If the output list pushes the manifest beyond 8MiB, it uploads without `outputs` and logs `outputs_refused`. In both cases omitted file objects were already uploaded and have no manifest reference; the next checkpoint uploads them again.
- Files are read into memory one at a time, adding at most the per-file limit (64MiB) to worker memory.
- Symlinks, nonregular files, and invalid manifest names (such as `.git` or non-UTF-8 names) are excluded. If `out` itself is a symlink, the list is empty.
- Each digest uploads once. A matching digest from the previous checkpoint reuses that object.
- Objects live at `sessions/<id>/checkpoints/<revision>/<attempt>/<publish>/outputs/<sha256>`. Control-plane finalize verifies size/digest and holds the version. Checkpoint GC retains output objects referenced by retained checkpoints.

## Docker quotas and reclamation

Each session mounts one `werft-ws-<installationId>-<sessionId>-<suffix>` volume at `/workspace`. It survives generations so replacing containers preserves the working tree. **Container `terminate` does not touch the volume**; pass stage ④ reclaims it separately.

If the volume disappears, the session continues from its last committed checkpoint. See [what remains after losing a workspace volume](#workspace-volume을-잃었을-때) for retained and lost data.

The backend now creates volumes **explicitly** with `POST /volumes/create`. Merely naming a volume in a mount spec lets Docker create it without labels or limits. Creation sets the `werft.managed`, `.installation`, `.session-id`, and `.workspace-quota` labels. GC reads these labels instead of parsing names.

**Volume names are single-use.** Recreating a name previously assigned a quota makes the `local` driver return the same `Options.size` without enforcing the actual project quota. Under reproduced xfs+prjquota conditions (Docker 27.5.1), the container's `df` total showed the configured 64 MiB on first creation. After deleting and recreating the same name, `df` showed the entire 8 GiB filesystem despite identical `Options.size`. Engine API cannot distinguish them. Workspace names therefore use random suffixes and are **looked up by labels**, not derived from session ids. A volume deleted by GC/operators gets a new name next time and regains enforcement. Multiple workspaces for one session are reported without guessing which is authoritative. Preflight probes also use fresh names. Leftover labeled probes are reclaimed only after the longer of 10 minutes or 20 times `EXECUTION_DOCKER_REQUEST_TIMEOUT_SEC`: preflight runs outside the pass lock, so younger probes may belong to concurrent preflights (standalone `--once` or another scheduler).

Like CPU/memory/PID/tmpfs, `/workspace` has a limit too. `EXECUTION_WORKSPACE_QUOTA_MB` (default 4096) sets the local driver's `size` option. This works **only with project-quota-capable daemon storage** (xfs+`prjquota`); otherwise creation returns `400 quota size requested but no quota support`. Scheduler `verifyWorkspaceQuota` creates a probe before passes and **launches nothing on unsupported daemons**. The probe creates a volume and CAP_SYS_ADMIN helper, so it is not repeated every pass. After success, supervised passes store a hash of all backend configuration (`DOCKER_HOST`/`EXECUTION_*`, etc.) in `<SCHEDULER_STATUS_FILE>.quota-verified`; matching hashes skip probes. The supervisor deletes this marker on startup, ensuring rechecks after restarts, including consecutive-failure restarts. Failed probes write no marker and retry next pass. Standalone `main.ts scheduler --once` neither writes nor trusts it and always probes. The supervisor passes `SCHEDULER_QUOTA_PREFLIGHT_MARKER` only to its own passes. There is no silent unlimited fallback: explicitly set `EXECUTION_WORKSPACE_QUOTA=off` to accept unlimited storage, producing 1 warning per scheduler pass. Values other than `on`/`off`, including `false`, `0`, and `no`, are rejected as typos.

**Minimum quota is 1024 MiB.** Smaller `EXECUTION_WORKSPACE_QUOTA_MB` values fail startup because restoration temporarily needs this workspace space. Restoration clears root first. Symbols:

- B: bundle-chain total, control-plane limit 256 MiB.
- U: untracked files, capture limit 256 MiB.
- W: objects fetched into workspace `.git`, approximately B.
- I: objects reachable from the instructions commit, at most W.
- T: checked-out working tree and index.

| Stage | Concurrent storage | Maximum |
| --- | --- | --- |
| Download | Bundle files B, U | 512 MiB |
| Staging | Bundle files B, staged repository ≈B, U | ≈768 MiB |
| Workspace fetch | Staged repository ≈B, W, U (bundle files deleted immediately after staging) | ≈768 MiB |
| Shrink staged repository | W, I, U (staged repository deleted first) | ≤768 MiB |
| After checkout, throughout session | W, I, T, U | 2B + T + U |

Fixed pre-checkout cost is twice the bundle limit plus untracked limit: 768 MiB. 1024 MiB adds pack indexes and headroom, including delta base copies used to complete incremental thin packs. T is the session working tree and unbounded, so the minimum guarantees only session-independent pre-checkout cost. After checkout, W + I + T + U approximates the same session's capture-time quota usage. Capture held workspace `.git`, working tree, untracked files, snapshot objects in scratch storage, and bundle files (≤B). I is at most B. Restoring to a new volume after lowering quota is outside this guarantee and can fail with ENOSPC during checkout.

Fresh fetch reusing an existing workspace without checkpoints does not clear root. The worker clones the entire origin into a bare mirror, copies the branch, then deletes the mirror. Mirrors live under `.git/werft-fetch-*` because `/tmp` and HOME are memory-backed tmpfs. M below is maximum mirror disk usage: origin packs plus indexes/refs and temporary packs during download. Δ is newly fetched workspace `.git` objects.

| Stage | Concurrent storage | Maximum |
| --- | --- | --- |
| Mirror clone and local fetch | Existing W, I, T, U + mirror M + Δ | Session usage + M + Δ |
| After fetch | W + Δ, I, T, U (mirror deleted) | Session usage + Δ |

M is unbounded. Reuse needs M of quota headroom; otherwise fetch fails ENOSPC. Initial clone (`clone`/`recreate`) goes directly into root without a mirror and uses W + T. A later reuse deletes scratch left by dead workers before fetching (fetch/capture/publish `.git/werft-<purpose>-XXXXXX`), retaining `werft-checkpoint`. If checkout borrows external objects (`objects/info/alternates`, `commondir`, symlinked `objects`), scratch may be their source and is not deleted.

After restoration, `.git/werft-checkpoint/checkpoint.git` retains only I, objects reachable from the instructions commit, so future capture can bundle it even if the engine prunes that commit. Later commits, uncommitted-change snapshots, and earlier chain snapshots are not retained. If instructions equals HEAD, I includes all committed history, as in sessions without engine commits; only snapshot storage shrinks then.

The tradeoff: subsequent incremental capture excludes only chain tips still present. Old-base-only snapshot commits are gone; the last bundle's snapshot remains unreferenced in workspace `.git`. Normal `git gc` retains it for 2 weeks, but `git gc --prune=now` can remove it. Bundles then use remaining tips (historical HEAD/instructions), potentially growing or becoming full bundles without affecting correctness. Repositories whose full bundle exceeds limits would also be rejected when the chain restarts at 32 bundles or its size limit.

**Inode limits apply to the same project.** Byte limits alone permit millions of empty files to exhaust inodes even within 4GiB: xfs does not charge inodes to project block usage. Other sessions and Postgres on the daemon can then fail to create files. The local driver lacks inode options, and per-session filesystems through `o=loop` are unavailable because it calls the mount syscall, not `mount(8)` (`data: loop: invalid argument`). Werft directly sets `ihard`/`isoft` (`EXECUTION_WORKSPACE_QUOTA_INODES`, default 1,000,000) on the xfs project created by Docker `size`.

- A short-lived helper container applies limits with `CapDrop ALL` + `CapAdd SYS_ADMIN, MKNOD`, `NetworkMode none`, read-only rootfs; it is not privileged.
- It reads the project id and rejects project 0 (= none), since limiting 0 would limit the whole filesystem.
- It creates the mount source's block device node in its private `/dev` with `mknod`, then runs `xfs_quota`.
- `xfs_quota` exits 0 even on failure; success is determined only from reported hard/soft limits and statfs `f_files`.
- Docker `SetQuota` writes only BHARD/BSOFT and does not overwrite these.
- The image is scheduler `WORKER_IMAGE`, which includes `xfsprogs`. Launches cannot choose another helper image. Operators, not catalogs, select the CAP_SYS_ADMIN image.

Limits apply at four points:

- Preflight `verifyWorkspaceQuota`: until first success after supervisor startup, and on configuration changes. Failure rejects startup like byte quotas; the sole opt-out is `EXECUTION_WORKSPACE_QUOTA=off`.
- Every launch's `ensureWorkspaceVolume`, new and existing volumes alike. Project ids can be reused after daemon restart, so are not cached; reapplying is idempotent.
- Pre-replacement `assertReplaceable`: failure rejects replacement before stopping the existing worker.
- Before `migrate-workspace` copying: excessive file counts fail copying and preserve the source.

Inode limits change in place, so are absent from the volume `workspace-quota` label. Volumes created without them remain accepted and receive them next launch. They do enter `isolationStampFor`, with `ISOLATION_CONTRACT` raised to 7. Older hosts after rollback treat these workers as newer and leave them alone. New/changed limits make running workers stale and replacement ensure applies them.

Docker Desktop kernels lack XFS quota support (`XFS (loopN): quota support not available in this kernel`), leaving `off` effectively the only local option. GitHub Actions runner daemons use ext4 data roots too. CI `workspace-quota` therefore starts a separate daemon on an xfs+prjquota loop-file data root to test enforcement.

Per-volume quotas alone are insufficient: Docker attaches **writable anonymous volumes** for image-declared `VOLUME` paths without labels or quotas. Before launch, images declaring any `VOLUME` beyond `/workspace` are rejected (`ImageVolumeError`). Container deletion uses `v=true` to remove anonymous volumes without affecting named workspace volumes. Unpulled images return 404 on inspection; creation is allowed to return that same 404.

To prevent tag races, containers use the **inspected image id** (`sha256:…`). Volumes are checked again immediately after create and before start: an intervening `docker volume prune` can make Docker implicitly recreate unlabeled, unlimited volumes. A mismatch deletes the not-yet-started container and fails.

Failed quota preflight **launches nothing but runs reclamation once**. Probes need some space, so full daemons can fail preflight exactly when finished workspaces need reclamation. Exiting immediately would prevent cleanup forever. This is `reclaimWorkspaces`, not a pass: only stage ④ under the same advisory lock. A zero-slot pass is insufficient because it still recreates missing containers and replaces stale ones. After reclamation, rethrow the original error and exit nonzero.

A volume quota label differing from configuration (made with no quota or another byte limit) rejects startup with `WorkspaceQuotaError`. Byte quotas cannot change later (inodes can, as above); deleting a volume destroys its working tree. Preserve the tree through [workspace migration](/run-server/self-hosting/migrate-workspaces), or restore previous settings. Quotas also enter `werft.isolation` so existing workers cannot indefinitely retain old limits.

Rejection must happen **before killing a running worker**. Otherwise stale → terminate → recreate could fail at the volume, stranding the session. `inspect` checks the volume read-only before reporting stale; unusable volumes raise an exception instead. The worker continues at its old limit while passes report nonzero `reconcileFailed` until [migration](/run-server/self-hosting/migrate-workspaces). Inode enforcement is tested by `assertReplaceable` immediately before replacement, rejecting failure before stopping the worker.

Stage ④ GC is fail-safe: **list volumes before querying the database**. Reversing this could delete a session volume created between calls. Retain volumes with a nonclosed session row or live execution row; `stopped` has the expiry exception below. Missing/invalid session-id labels, mounted volumes (409), and other installations' volumes are **retained and logged**. Volumes younger than `EXECUTION_WORKSPACE_GC_MIN_AGE_SEC` (default 3600) are never candidates, protecting launches between volume and container creation. **Intentional retention and failures have different exit codes.** Mounted/foreign volumes are normal (`workspacesUnresolved`) and do not change exit code. Listing/database failures (`workspaceScanFailed`) or deletion exceptions (`workspacesFailed`) cause a nonzero pass because disk can otherwise grow unobserved.

**Stopped workspaces expire.** After the time the owner sets in the web console under **Settings > Workspace > Execution limits**, "Stopped sessions' workspaces" (default 86400 seconds, one day; 0 to 315360000 seconds), measured from `sessions.updated_at`, they become candidates. The scheduler reads it from the database on each reclaim. Migrate carries an earlier release's `EXECUTION_WORKSPACE_STOPPED_TTL_SEC` in once; the scheduler does not read it. Stop transitions update that time; reclamation claims/completion do not. A new accepted terminate on an already stopped session resets it, but terminate is not a retention mechanism: existing reclamation claims continue. Resume alone serializes with claims. A launch holding a slot prevents candidacy. `0` means reclaim next pass.

Resume requires a committed checkpoint; workers with restore pointers clear root and restore from it. Expired stopped volumes are therefore caches. **Stopped sessions without checkpoints cannot resume, and work existing only on their volumes disappears after TTL.** Extract required work directly before expiry.

**Paused workspaces expire too.** After the time set on the same screen under "Paused sessions' workspaces" (default 86400 seconds, one day; 0 to 315360000 seconds; an earlier release's `EXECUTION_WORKSPACE_PAUSED_TTL_SEC`), measured from `sessions.paused_at`, they become candidates. Sessions parked on an approval wait (`pause_reason: awaiting_input`) follow the same rule. The write that moves a session into `paused` sets that time, and leaving `paused` clears it; other writes, reclamation claims and completion do not change it. A session already paused before it existed (before migration `0273_paused_at`) counts from the first reclamation pass after the upgrade that sees it. `0` means reclaim next pass. Only a session whose resume would accept its checkpoint is reclaimed: no checkpoint pointer, a blocking `checkpoint_pending_reason`, a checkpoint retired by start_fresh, or a legacy pod binding keeps the volume. As for `stopped`, a launch holding a slot prevents candidacy.

Resuming a reclaimed paused session (a person's resume, or the automatic resume of an answer to a parked request) restores its checkpoint onto a new workspace. A restore clears the old tree first anyway, so normally nothing is lost. **But a failed restore can no longer fall back on the volume.** Until now, when a restore failed its checks (missing or damaged manifest, mismatched image combination, and the like) the volume was left, and a later start_fresh kept the files of a session without a repository. On a reclaimed session, start_fresh starts from an empty working directory. This follows the rule that the working directory is a cache and the checkpoint (S3) and the database are the record. Raise that time on the screen to keep paused volumes longer.

While either time cannot be read (an env value that could not be carried in, a database outage), the scheduler reclaims no new `stopped` or `paused` session's workspace. Closed sessions' workspaces, and claims an earlier pass left unfinished, are still reclaimed. Once a value is saved on the screen, expiry is counted again from the next pass.

Reclamation and resume serialize in the database. After identifying a volume candidate, the pass locks launch → session in the same order as resume, rechecks conditions, records a **claim** (`sessions.workspace_reclaim_id`/`workspace_reclaim_workspace_id`), and commits. It then deletes the volume and records results under the same claim id.

* Deleted/already absent: clear claim, set `workspace_reclaimed_at`.
* Mounted (409)/foreign: clear only the claim.
* Deletion exceptions, including timeout: retain the claim because deletion is uncertain. Next pass processes unfinished claims independently of volume listings, since deleted volumes no longer appear.

While claimed, resume returns **503 `BACKEND_UNAVAILABLE` (`retryable: true`)** without receipt/idempotency records; retry the same request after completion. On a `paused` session, the other requests that can start a resume get the same 503: an answer to a parked request (the answer is not kept) and an interrupt of a turn that already ended. Expiring parked requests past their deadline also waits until the reclamation settles; a later pass then records the expiry and carries the group on. If resume commits first, the session leaves `stopped` or `paused` (to `active` from `stopped`, to `resuming` from `paused`), preventing the claim; the next launch uses the volume. Successful resumption clears `workspace_reclaimed_at`.

<a id="공통-object-store-보호" />
## Shared object store protection

Default `locked` protection requires versioning, Object Lock, and SSE-S3 (`AES256`). Checkpoint object versions are protected by legal holds. Do not configure default retention or object-version-expiring lifecycles. Restoration needs exact versions referenced by database pointers. `/readyz` alone does not establish data retention.

For AWS creation/minimum permissions, see [Bucket preparation](/run-server/self-hosting/prepare-checkpoint-bucket); for backup and separate-destination comparison, see [Restoration drills](/run-server/self-hosting/backup-and-restore).

## Retention by data

The platform never deletes sessions. There is no API that deletes one, and the rows that belong to a session stay after it is closed. Only the items with a period in the table below are deleted when the period runs out.

| Data | Where | Kept | Deleted | Change it |
| --- | --- | --- | --- | --- |
| Sessions, turns and their input text, receipts, tool call records, push requests and pull request records, the usage ledger | PostgreSQL | Indefinitely | Never. Close only changes the state | No setting |
| Session events | PostgreSQL; after a long idle period, `session-archive/` in the bucket | Indefinitely | Database rows leave only after the [session event archive](#세션-이벤트-보관) moved them to the bucket | "Session record archive" in the console's execution limits |
| Plain variable values a session copied | PostgreSQL | Until the session closes. For a session not closed, 30 days after the copy | At once on close; after 30 days the reconciler deletes them. The next claim of a session past 30 days is refused, so start a new one | No setting |
| Authorization decision records | PostgreSQL | 90 days by default (30 to 3650 days) | The reconciler deletes rows past the period | The owner calls `POST /v1/workspaces/{id}/audit-retention` |
| Sign-in sessions | PostgreSQL | 14 days, the latest 10 per user | On the next sign-in, or by the reconciler 30 days after expiry | No setting |
| Slack private channel member lists (`slack_channel_member_cache`, Slack user ids and read times only) | PostgreSQL | 5 minutes | Unused after 5 minutes and deleted by the reconciler. A channel's list is dropped at once when someone joins or leaves it or the bot leaves it, and an install's lists when the app install is revoked | No setting |
| Slack install state | PostgreSQL | 600 seconds | When used, or when a new link is made | No setting |
| Event body (payload) in the Slack event inbox | PostgreSQL | Until processed. An event that failed processing, 7 days after it was received. An event dropped on arrival is stored without its body; one dropped during processing loses it then | The slack role clears it as soon as processing ends; the reconciler clears a failed event's after 7 days. The row (event type, status, drop reason, attempts) stays. Rows processed before migration 0308 still hold their body | No setting |
| Input rows of Slack messages and web inputs (`conversation_inputs`) | PostgreSQL | Indefinitely. A Slack message's row has only where the message was (team, channel, ts), its number in the topic, the requester and the turn it became, never its text. A web input's row has its number, the requester, the client's message key and its text, and once it is shown in Slack, that post's place (team, channel, ts) as its alias (no route records web inputs yet) | None | No setting |
| Slack messages held in the judgment buffer (`conversation_inputs` rows with `buffer_expires_at`) | PostgreSQL | 10 minutes from when it was held. Where the message was, its number in the topic, its poster's Slack id and its text. Made only in a `free` channel of an agent whose conversation layer switch is `shadow` or `on`. Removed at once when the message is deleted in Slack, the channel is archived or deleted, the bot leaves it, the binding is turned `off` or the agent is archived; an edit only replaces the text | The reconciler removes the row whole; the [admin delete](#대화-기록의-관리자-삭제) also removes them one conversation at a time | No setting |
| Engagement rows of Slack posts an agent took part in (`conversation_engagements`) | PostgreSQL | Indefinitely. Only the agent, where the post was (team, channel, ts), the kind (mention, reply, bound to a task) and the session the post went into; no text, thread or link | The [admin delete](#대화-기록의-관리자-삭제) removes them one conversation at a time | No setting |
| Channel summaries (`channel_summaries`, `channel_summary_lines`, `channel_summary_line_sources`) | PostgreSQL | Indefinitely, with each version's history. A line keeps the agent's own words and which agent wrote them; a source row keeps only where the Slack message was (team, channel, ts), the input row's id and the speaker, never the message's text. Nothing in this release writes a summary yet | When a source message is deleted or edited, the slack role removes its lines from every version; the [admin delete](#대화-기록의-관리자-삭제) removes the channel's summary with its history | No setting |
| Marks of deleted and edited Slack messages (`deleted_sources`, `edited_sources`) | PostgreSQL | 70 minutes from when the mark was made. Only where the message was (team, channel, ts), when, and why it was made (a Slack delete `slack_deleted`, an admin delete `admin_deleted`), never its text. Kept while the message has an input row or an engagement row, or a turn, outbox row or channel summary line has it among its sources | The reconciler removes it | No setting |
| API keys, users, members, invites, linked accounts | PostgreSQL | Indefinitely | Never. Revoking a key or unlinking leaves a record | No setting |
| Stored secrets | PostgreSQL (encrypted with the master key) | Indefinitely | Only when a person deletes that connection or App | No setting |
| Transcript and checkpoint objects | `sessions/<id>/` in the bucket | The pointer and its 3 parents, and revisions pinned by open push requests | Only [checkpoint GC](/run-server/self-hosting/backup-and-restore#3-checkpoint-gc) deletes them | Helm `checkpointGc.*`, compose `CHECKPOINT_GC_DRY_RUN` |
| Archived session events | `session-archive/` in the bucket | Indefinitely | Never | No setting |
| Workspace volumes | Docker volume, Kubernetes PVC | 24 hours for a stopped session, 24 hours for a paused session | The scheduler reclaims them. The session reopens from its last checkpoint | "Stopped session workspace" and "Paused session workspace" in the console's execution limits |
| Process stdout logs | compose json-file; otherwise the installation's log driver | compose services keep 5 files of 50 MB per container. Worker containers the scheduler starts follow the Docker daemon defaults | Rotation | compose `x-logging`; for worker containers and elsewhere, Docker daemon, node and collector settings |
| Usage reservations of provider calls not yet settled | PostgreSQL | Until the usage report arrives. A call released as not billed: 7 days. An unreleased call is never deleted by age | The API and the reconciler | None |

- Content (prompts, answers, tool input/output) stays in turn input text, session events, transcripts and archived events. Masking before storage is in [Masking in logs and events](/run-server/self-hosting/explanation/isolation#로그와-이벤트의-가림). Input text (`turns.message`) and transcripts are not masked. A transcript is the original handed back to the engine when the session reopens, so a value masked in events can remain in the transcript.
- An unreleased usage reservation keeps counting toward the session cost limit, so the cost of a call whose report was lost is not missed. If no report has come when the lease runs out, the reconciler logs `Provider exchange reservation expired unsettled` once. A call still streaming can also cause it, so the warning alone does not mean a cost was lost.
- Traces are not exported by default. How to turn them on is in [Trace export](/run-server/self-hosting/reference/configuration#트레이스-내보내기).

## Admin delete of conversation records

An operator command that deletes the records of one channel conversation when a workspace manager (owner or admin) asks. There is no API route: an operator who can run commands in the API container runs it. Look at the counts with `--dry-run` first.

```bash
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/conversation-records.ts delete --conversation <conversation-id> --by admin@example.com --dry-run
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/conversation-records.ts delete --conversation <conversation-id> --by admin@example.com
```

- **Conversation id.** Find it in the `conversations` table by agent and channel: `SELECT id FROM conversations WHERE agent_id = '<agent-id>' AND channel_id = '<channel-id>';`
- **What goes.** The engagement rows the conversation's agent left in the channel, the channel's summary with the history of every version, and the messages held in the conversation's judgment buffer. A channel has one summary, so the other agents of the channel lose it too.
- **What stays.** Sessions, turns and their input text, input rows, session events, transcripts, checkpoints and receipts. The conversation row stays too, and keeps when it was last deleted and by which admin.
- **Sessions that stop.** Before anything goes, each message the records name that is no turn's input gets a delete mark (`admin_deleted`). A session with such a message among its sources stops as it does when Slack deletes the message (`SOURCE_DELETED`), and its answers not yet sent do not go out. Other sessions of the channel, and sessions that hold only their own input, go on. The message stays in Slack.
- **`--by`.** The address of an owner or admin of the conversation's workspace who is not disabled. It is kept on the conversation row and the receipt as who deleted. Otherwise nothing is deleted and the outcome is `not_admin`. A DM conversation is refused with `dm_not_supported`.
- **Output.** One line of JSON on stdout: `outcome` (`deleted`, `unchanged` when nothing was left, `dry_run` with `--dry-run`), `conversation_id`, the rows removed (`engagements`, `summary_lines`, `buffered`), the marks newly made (`marked`) and the ids of the sessions stopped (`sessions_stopped`). Exit codes: 0 done, 1 unexpected error, 2 usage, 3 no such conversation, 4 refused.
- **Running it again.** The result is the same. With nothing left it writes nothing and says `unchanged`. If an earlier run stopped after deleting but before stopping a session, running it again stops that session.
- **Audit.** When something was deleted, one receipt `delete_conversation_records` is in the audit log: the `--by` person as its actor, the conversation as its target and the rows removed as its result.

## Session event archive

A weekly job moves the event rows of long-idle sessions to the checkpoint bucket. It changes no rows other than events, and the API gives the same responses after the move.

- **Settings.** The owner sets them in the console under Settings > Workspace > Execution limits, "Session record archive". The idle period is 180 days by default, 0 turns it off, and otherwise it is 30 to 3650 days. Choose between "Count only" (default) and "Move". With "Count only", only the numbers of sessions, events and bytes to move are logged (`Session archive completed`).
- **Targets.** Sessions whose last activity is older than the idle period. Sessions with a running turn, an approval or question waiting for an answer, or an open push request are skipped. If a session becomes active during the move, it is left as is.
- **How it writes.** For every 1000 events or 8 MiB it writes one JSONL.gz object under `session-archive/<session id>/` create-only, puts a legal hold on it, reads it back to compare, and only then deletes the database rows. It runs only in `locked` protection mode. Workers can neither read nor write these keys.
- **Reading.** The event list API, SSE with `Last-Event-ID`, and the last event time in the session list reflect archived ranges as before. The API reads the objects, so an archived session can be read only when the API has a checkpoint object store configured.
- **Schedule.** In compose, the `maintenance` service runs it once a week after checkpoint GC (`MAINTENANCE_INTERVAL_SEC`, default 604800 seconds). To run it once now, use `docker compose exec maintenance bun run apps/control-host/src/api/session-archive.ts`. In Kubernetes, a CronJob (`sessionArchive.schedule`, default `0 5 * * 0`) runs it.
- **Undo.** `bun run apps/control-host/src/api/session-archive.ts restore <session id>` puts that session's events back into the database with the same ids. The objects stay with their holds. If the session is still a target, the next pass moves it again, so to keep it in the database, raise the idle period first or turn it off with 0.
- **When the settings cannot be read.** If the stored values cannot be read, the job moves nothing, logs `Session archive refused: its settings cannot be read` and exits 1. Saving the values again in the console clears it.
- **Backup.** An archived object is the only copy of those events. The bucket is canonical together with the database, so protect both ([Kubernetes installations](/run-server/self-hosting/backup-and-restore#kubernetes-설치)).

## When a workspace volume is lost

What carries a session on is the checkpoint, not the volume. At the end of every turn the worker uploads the working directory and the engine conversation to the object store as a checkpoint, and the pointer in the database points to that revision. When a session whose volume is gone resumes, the scheduler creates a new empty volume and starts a worker, and the worker restores the pointer's checkpoint and continues the conversation.

- **What remains.** Everything up to the last committed checkpoint. Which turn it covers is in `checkpoint_revision` and `durability.last_checkpointed_turn_id` on the session detail. When it equals `durability.last_completed_turn_id`, the last completed turn is included.
- **What is lost.** Work after the last checkpoint, untracked files matched by `.gitignore` or `.git/info/exclude` (build output, dependencies, an ignored `.env`), and state outside the working directory (such as `git config --global` in the tmpfs HOME). Files already tracked go into the checkpoint even when an ignore rule matches them. Write outputs you need to keep to a path that is not ignored (for example `out/`).
