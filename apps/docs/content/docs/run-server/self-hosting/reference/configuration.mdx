## 계약

`WERFT_API_KEY`와 `WERFT_BASE_URL`은 서버 설정이 아니라 SDK 호출자의 설정이다. [SDK 클라이언트 설정](/getting-started/client)을 따른다.

설정값의 형식·필수성·반영 시점을 찾는 문서다. 실행 전 활성화·롤백 게이트는 [Compose 업그레이드](/run-server/self-hosting/upgrade-compose)와 [Kubernetes 업그레이드](/run-server/self-hosting/upgrade-kubernetes)를 먼저 읽는다.

## 설치 상한

API와 scheduler는 아래 값이 없거나 형식이 틀리면 문제를 한 줄에 모두 로그로 남기고 기동하지 않는다. 두 프로세스는 같은 parser를 쓴다. 코드에 기본값이 없고, compose의 `x-installation-limits` 블록과 chart의 `config.limits`가 로컬 기본값을 준다. 떠 있는 API의 `/readyz`는 같은 검증을 `config` 체크로 다시 수행한다. 세션의 대기 메시지·입력 보관·비용·토큰 상한과 turn 시간·provider 재시도는 env가 아니라 [웹에서 정하는 실행 한도](#웹에서-정하는-실행-한도)다.

| 변수 | 의미 | 넘었을 때 |
|---|---|---|
| `EXECUTION_SLOT_LIMIT` | 동시에 슬롯을 잡는 worker 수. 0이면 접수만 받고 아무것도 띄우지 않는다 | 입력은 거부하지 않고 `queued`로 둔다 |

## API 설정

API는 설치 상한 말고도 아래 값을 기동 때 한 parser로 읽는다. 설정하지 않으면 기본값을 쓴다. 설정했는데 틀린 값이면(빈 문자열 포함) 기본값으로 돌아가지 않는다. 숫자 설정은 API·scheduler·reconciler·worker와 설치 상한이 모두 이 규칙을 따른다. 기본값이 없는 값은 설정하지 않으면 `X is required`로, 틀린 값은 `X must be a positive integer`처럼 기대한 범위를 적어 거부한다. 받은 값은 적지 않는다. 로그에 남고, 다른 변수에 잘못 넣은 비밀일 수 있어서다. 이때 `Refusing to start: API settings are invalid` 한 줄에 문제를 모두 남기고 기동하지 않는다. 떠 있는 API의 `/readyz`도 같은 검증을 `config` 체크로 다시 수행한다.

| 변수 | 기본값 | 허용 범위 |
|---|---|---|
| `HEARTBEAT_TTL_SEC` | 30 | 12 초과 86400 이하. worker는 lease가 끝나기 10초 전에 lease를 내려놓고(`WORKER_LEASE_SAFETY_MARGIN_SEC`), 2초마다 heartbeat를 보낸다(`WORKER_HEARTBEAT_INTERVAL_SEC`). 두 값의 합 이하이면 attempt가 첫 heartbeat 무렵 lease를 잃는다. launcher는 두 worker 값을 넘기지 않으므로 기본값을 기준으로 판정한다. heartbeat가 403을 받으면 worker는 바로 끝난다. 404를 받으면 1초 뒤에, 그다음부터는 heartbeat 간격(2초)마다 다시 보내고, lease를 내려놓는 시각까지 받아들여지지 않으면 끝난다(기본값에서는 다시 보내기 9–10회). 다시 보내는 동안 worker는 gateway의 다른 호출과 checkpoint 올리기를 보내지 않고, heartbeat가 받아들여지면 이어서 보낸다 |
| `SSE_MAX_STREAMS` · `SSE_MAX_STREAMS_PER_OWNER` · `SSE_REPLAY_MAX_BYTES` | 256 · 8 · 1 MiB | 양의 정수 |
| `LOG_LEVEL` | `info` | `debug`·`info`·`warn`·`error`(대소문자 무관, 빈 값은 `info`). scheduler·reconciler loop와 egress-proxy도 같은 규칙으로 기동을 거부한다. worker는 scheduler의 값을 받는다 |
| `WEB_DIST_DIR` | 없음(웹 콘솔을 서빙하지 않음). control-host 이미지는 `/app/apps/web/dist` | `index.html`이 있는 절대 경로. 웹 콘솔(`apps/web`)의 빌드 결과다 |
| `LOGIN_ACCOUNT_FAILURE_LIMIT` · `LOGIN_ACCOUNT_FAILURE_WINDOW_SEC` | 5 · 900 | 횟수는 1 이상 1,000,000 이하, 창은 1 이상 86400초 이하. 이메일 하나의 비밀번호 실패 수와 그 창 |
| `LOGIN_IP_FAILURE_LIMIT` · `LOGIN_IP_FAILURE_WINDOW_SEC` | 20 · 900 | 같은 범위. 클라이언트 네트워크 하나(IPv4는 주소 하나, IPv6는 /64)의 비밀번호 실패 수와 그 창 |
| `AUTH_IP_REQUEST_LIMIT` · `AUTH_IP_REQUEST_WINDOW_SEC` | 30 · 60 | 같은 범위. token을 받는 로그인 route(setup link, 초대, 비밀번호 재설정, 로그인 provider)에 네트워크 하나가 보내는 요청 수와 그 창. 성공한 요청도 센다 |
| `CLIENT_IP_HEADER` | 없음(소켓 peer 주소로 센다) | 앞단 proxy가 클라이언트 주소를 쓰는 헤더 이름 하나(영문·숫자·`-`). Cloudflare Tunnel 뒤라면 `CF-Connecting-IP` |

로그인 시도는 모든 API replica가 DB 표 하나에서 함께 센다. 창은 첫 시도부터 정해진 길이만큼이고, 이메일과 주소는 원문 없이 HMAC으로만 남는다. 맞는 비밀번호로 들어오면 그 이메일의 실패 수는 지워진다. 계정이 잠기는 순간 그 계정이 속한 살아 있는 workspace마다 `lock_login` receipt가 창당 하나 남는다. 없는 이메일이나 네트워크가 잠기면 `Login locked` 경고 로그 한 줄만 남고, 응답은 있는 이메일과 같다. `CLIENT_IP_HEADER`가 없으면 소켓 peer 주소로 센다. 터널이나 proxy 뒤에서는 그 주소가 사설·loopback 주소라 모든 사용자가 한 주소로 보인다. 그래서 그때는 네트워크 창을 건너뛰고(처음 건너뛸 때 경고 한 줄) 이메일 창만 적용한다. 헤더를 정하면 그 헤더의 마지막 항목만 믿는다. 앞단 proxy가 그 헤더를 늘 덮어쓰는 구성에서만 정한다.

모든 `/v1` 응답은 `api.request.completed`를 남긴다. 실제 id가 없는 Hono `route_template`, `method`, `status`, 인증과 route 처리를 포함한 `duration_ms`, `operation=api_request`, `outcome`, `reason_code`가 있고 `request_id`는 log context에 있다. request body·credential·provider key는 넣지 않는다. terminate 요청은 같은 `request_id`의 `Terminate control transaction completed`도 남기며, 여기에는 pool checkout, binding·launch·session lock, 각 SQL, commit 또는 rollback, control transaction 전체의 millisecond 계측이 들어간다. 배포 환경에서 수락 지연을 조사할 때는 두 로그를 `request_id`로 묶어 어느 단계가 느렸는지 판단한다.

terminate가 이미 사라진 execution에서 즉시 끝나거나 scheduler/reconciler가 execution 부재를 확인하면 `control.result`가 `operation=terminate`, receipt id인 `control_id`, `outcome`, `reason_code`, durable 수락부터 확인까지의 `effect_ms`(`duration_ms`와 같음)를 남긴다. 기한을 넘긴 receipt는 먼저 `outcome=unknown`·`reason_code=deadline_exceeded`를 남기며, 이후 execution 부재를 확인해 receipt를 성공으로 올리면 `outcome=succeeded`·`reason_code=execution_gone` 결과를 추가로 남긴다.

`WEB_DIST_DIR`가 있으면 API가 웹 콘솔을 같은 origin에서 서빙한다. `/v1`·`/internal` 밖의 GET·HEAD는 그 디렉터리의 파일을 돌려주고, 파일이 없으면 `index.html`을 돌려준다(SPA fallback). 그래서 `/login`·`/bootstrap`을 새로고침해도 화면이 열린다. `/v1`·`/internal` 아래는 fallback하지 않는다. 인증된 `/v1/nope`는 JSON `404 NOT_FOUND`다. `/assets/` 아래 파일은 content hash가 붙은 이름이라 `immutable`로 캐시하고, 없는 asset은 페이지 대신 404를 준다. `index.html`은 `no-cache`이며 inline script를 허용하지 않는 CSP(`script-src 'self'`)를 붙인다. control-host 이미지는 `web` build stage에서 `apps/web`을 빌드하고 `dist/`만 담는다. 별도 web 이미지는 없다. 로컬에서 웹만 고칠 때는 `bun run --cwd apps/web dev`(Vite, `/v1`을 `VITE_API_TARGET` 기본 `http://127.0.0.1:3000`으로 proxy)를 쓴다.

`AUTH_MODE=none`은 egress authorizer(`EGRESS_AUTHORIZER_PORT`)와 함께 쓸 수 없다. authorizer가 켜져 있다는 것은 worker가 proxy를 거쳐 이 API에 닿는다는 뜻이다. `none` 모드에서는 worker 안의 코드가 `X-Owner-Id`로 아무 owner나 행세할 수 있으므로 기동을 거부한다. `AUTH_MODE` 값 자체(`none`|`api-key`)는 readiness가 판정한다.

worker도 기동 때 교차 검사를 한다. `WORKER_PROVIDER_MAX_RETRIES`가 없으면 기동하지 않는다. 코드 기본값이 없는 설치 한도이고, scheduler가 launch에 고정된 값을 항상 넘긴다. `WORKER_NEXT_INPUT_WAIT_SEC`가 `WORKER_REQUEST_TIMEOUT_SEC` 이상이어도 기동하지 않는다. 그 설정에서는 모든 long poll이 요청 timeout에 잘린다. scheduler와 reconciler는 빈 `DATABASE_URL`을 설정하지 않은 것으로 보고 `QUEUE_DATABASE_URL`을 쓴다.

API와 slack role은 `WORKER_IMAGE_RUNTIME`과 `WORKER_IMAGE_PREVIOUS_RUNTIME`으로 현재·직전 worker 이미지의 런타임 조합을 읽는다. 값은 손으로 적지 않고, images.yml이 남긴 worker digest JSON의 `runtime` 필드를 그대로 넣는다(`{"engine":…,"sdkVersion":…,"cliVersion":…,"profileDigestScheme":…}`). `engine`은 `claude`와 `codex`이고, chart는 다른 이름을 렌더링 때 `images.worker.runtime.engine must be one of: claude, codex`로 거절한다. 직접 빌드한 이미지에는 그 JSON이 없다. images.yml과 같은 명령으로 이미지에서 읽는다.

```bash
docker run --rm -i --network none --entrypoint bun <worker-image> \
  run apps/worker/src/image-runtime.ts <<<'{}' | jq -c 'del(.profiles)'
```

**worker 이미지 하나는 엔진 하나를 담는다.** `apps/worker/Dockerfile`은 빌드 인자 `WORKER_RUNTIME`으로 엔진을 고른다. 비워 두면 Claude 이미지이고, `--build-arg WORKER_RUNTIME=codex_app_server`를 주면 Codex 이미지다(빌드 로그에 `codex-cli 0.167.0`이 찍히고, 다른 버전이면 빌드가 실패한다). CI는 Codex 이미지를 `werft-worker-codex`라는 별도 이미지로 만든다. Codex를 쓰는 배포는 `WORKER_IMAGE`(chart는 `images.worker`)를 그 이미지로 두고 위 명령으로 읽은 `runtime`(`engine`은 `codex`)을 함께 넣는다. 로컬 스택은 `infra/compose.codex-worker.yml` 오버레이로 같은 이미지를 빌드한다. Codex 세션이 OpenAI Responses API를 부르는 배포는 proxy의 `EGRESS_CREDENTIAL_ALLOWLIST`에 `api.openai.com:443`도 넣는다. Codex 엔진에는 자체 예산이 없다. 세션 비용·토큰 한도(`SESSION_COST_LIMIT_USD`, `SESSION_TOKEN_LIMIT`)는 worker gateway가 provider 호출마다 저장된 사용량으로 집행하고, 한도를 넘은 세션의 다음 호출은 `403 BUDGET_EXCEEDED`로 막힌다. 한계: 사용량은 proxy의 보고로 gateway에 닿는다. 보고가 재시도(1s·5s·15s) 끝에 유실되면 저장된 비용이 낮게 남고, 그 세션의 이후 provider 호출은 proxy 프로세스 안의 차단(프로세스 하나 단위, 재시작하면 사라진다)으로만 막힌다. 그래서 이 한도는 저장된 사용량에 기대는 소프트 한도다. 보고가 유실된 뒤 proxy가 여러 개이거나 재시작하면 초과액에 상한이 없다. 보고가 정상이어도 한 번의 긴 응답, 병렬 호출, 보고가 늦는 동안 나가는 다음 호출은 한도를 넘을 수 있다(Claude 엔진의 예산도 완료된 호출 뒤에 검사한다). 영속적인 사용량 기록으로 이 구멍을 닫는 일은 후속 작업이다.

**세션은 자기 엔진의 이미지로 뜬다.** scheduler는 세션 spec의 runtime kind로 엔진을 정하고(`claude_agent_sdk`는 claude, `codex_app_server`는 codex), 그 엔진의 이미지 가운데서만 아래 규칙으로 이미지를 고른다. worker도 자기 엔진의 세션만 claim한다. 그 엔진의 이미지가 하나도 없으면 체크포인트가 없는 세션은 slot을 쓰지 않고 기다리고(scheduler 로그의 `waiting_for_engine_count`), 체크포인트가 있는 세션은 launch 전에 `recovery_required`로 멈춘다(attention `RESTORE_FAILED`, reason `incompatible_checkpoint`). 그래서 한 배포가 Claude와 Codex 에이전트를 함께 돌릴 수 있다. 두 엔진의 이미지는 이미지 목록(`WORKER_IMAGES`, 아래)에 엔진마다 최대 둘씩 적는다. 두 엔진 목록은 scheduler·API·Slack role을 모두 이 버전으로 올린 뒤에 준다. 옛 버전은 그 목록을 거부해 기동하지 않는다. 되돌릴 때는 먼저 목록을 엔진 하나로 줄인 뒤 되돌린다. 업그레이드 검사(`upgrade-check`)는 엔진마다 따로 판정하고, 한 엔진의 이미지를 모두 빼는 업그레이드는 그 엔진의 열린 세션을 승인 목록에 올린다([엔진을 빼는 upgrade](/run-server/self-hosting/upgrade-kubernetes#3-검사-결과와-예외)).

**Codex auto 모드의 샌드박스.** Codex 세션의 `auto` 모드는 모델이 부르는 명령을 Codex의 bubblewrap 샌드박스 안에서 돌린다. 쓰기는 작업 디렉터리에만 되고, 네트워크는 열려 있다. 샌드박스는 기본으로 켜져 있다. worker는 `auto` 세션을 시작하기 전에 `codex sandbox`로 `true`를 한 번 돌려 본다. 실패하면 세션을 시작하지 않고 멈추며(`recovery_required`), 이유에 bubblewrap의 오류 한 줄이 남는다. 실패는 이 확인에서 바로 드러나므로, 세션이 멈춘 채 기다리지 않는다. `auto`는 샌드박스 밖에서는 돌지 않는다. 다른 권한 모드는 샌드박스와 상관없이 돈다.

bubblewrap은 Docker 기본 seccomp(Kubernetes의 `RuntimeDefault`)가 막는 namespace syscall을 쓴다. 그래서 scheduler는 Codex 이미지의 컨테이너에만 Werft seccomp 프로필을 건다. 이 프로필은 Docker 기본 프로필에 `clone`·`unshare`·`mount`·`umount2`·`pivot_root`를 더한 것이다(`scripts/codex-seccomp-profile.ts`). Codex 이미지는 선언된 runtime의 `engine`이 `codex`인 이미지다. runtime을 선언하지 않은 이미지는 기본 seccomp로 뜨므로 `auto` 세션이 거절된다. compose의 Codex 스택도 위 명령으로 읽은 `WORKER_IMAGE_RUNTIME`을 넣어야 프로필이 걸린다.

- **Docker backend.** 프로필을 컨테이너마다 직접 넘긴다. 노드에 따로 둘 파일은 없다.
- **Kubernetes.** Codex worker 컨테이너에 `Localhost` 프로필 `werft/codex-sandbox.json`을 건다. kubelet의 seccomp 디렉터리 기준 경로이고, 바꿀 수 있는 값이 아니다. chart에 `codexSandbox.localhostProfile`을 주면 렌더링이 거절된다. Pod 단위 프로필은 그대로 `RuntimeDefault`다. 이 프로필을 거는 Pod에는 노드 라벨 `werft.codex-seccomp-profile=installed`를 요구하는 nodeAffinity(required)도 붙는다. 그래서 라벨이 붙은 노드에만 배치되고, 그런 노드가 없거나 자리가 없으면 Pod는 `Pending`으로 기다린다. `codexSandbox.provider=installer`이면 chart의 설치 DaemonSet이 worker 노드의 `<kubeletDir>/seccomp/werft/codex-sandbox.json`에 그 파일 하나를 쓰고, 그다음 자기 노드에 이 라벨을 붙인다. 노드 배치는 기본으로 `worker.nodeSelector`·`worker.tolerations`를 따른다. 파일을 쓰는 init 컨테이너는 capability 없이 그 디렉터리 하나만 쓰기로 마운트하고, 루트 파일 시스템은 읽기 전용이며, API 토큰이 없다. 라벨을 붙이는 컨테이너는 root가 아니고 그 디렉터리를 읽기로만 마운트한다. 이 컨테이너의 ServiceAccount는 ClusterRole로 Node `patch` 권한을 받는다. RBAC은 "자기 노드"로 범위를 좁힐 수 없으므로, chart의 ValidatingAdmissionPolicy가 요청을 그 Pod가 도는 노드로, 그리고 이 라벨 하나를 이 값으로 붙이는 변경으로 제한한다. 이 정책에는 Kubernetes 1.30 이상이 필요하다. 라벨을 붙이는 컨테이너는 먼저 다른 값으로 바꾸는 dry-run 요청을 보내고, 정책이 그 요청을 거절하는 것을 본 뒤에야 라벨을 붙인다. 약 2분 안에 거절을 보지 못하면 아무것도 바꾸지 않고 실패해 다시 시작한다. 라벨은 설치 DaemonSet이 지워지거나 chart를 지워도 떼지 않는다. 파일도 노드에 그대로 남기 때문이다. 라벨이 붙었는데 파일이 없는 노드(노드 디스크를 지운 경우 등)에서는 Codex worker 컨테이너가 만들어지지 않는다(`CreateContainerError`). scheduler는 seccomp 프로필 때문에 생긴 이 오류를 보는 즉시 launch 실패로 센다. Pod를 지우고, backoff 뒤 다시 띄운다. 그 사이 설치 DaemonSet이 파일을 쓰거나 Pod가 다른 노드에 뜨면 세션이 이어진다. launch 실패 한도(기본 5회)에 이르면 launch를 포기하고 슬롯을 돌려준다. 이유에는 노드 이름, 프로필 경로, 설치 DaemonSet이 남는다.

**누가 sandbox를 두는가.** chart의 `codexSandbox.provider`는 `disabled`(기본), `installer`, `external` 중 하나다. `installer`는 위 DaemonSet이고 cluster 범위 리소스(ClusterRole, ClusterRoleBinding, ValidatingAdmissionPolicy와 binding)를 만든다. 기본(`disabled`)과 `external`은 cluster 범위 리소스를 하나도 만들지 않으므로, namespace 권한만 받은 설치자도 `helm install`을 할 수 있다. `disabled`는 Codex sandbox가 없다는 뜻이다. scheduler는 `CODEX_SANDBOX_PROVIDER`로 이 값을 받아, Codex 이미지의 worker를 Pod를 만들기 전에 거절한다. 그 입력의 접수는 곧바로 `CODEX_SANDBOX_NOT_INSTALLED`로 실패하고, 세션은 `idle`로 돌아가며, launch 실패로 세지 않는다. 콘솔, Slack 스레드, 로그가 "`codexSandbox.provider`를 `installer`로 켜거나 cluster 관리자가 sandbox를 먼저 설치해 달라"고 알린다. 실패하기 전에도 콘솔의 에이전트 화면은 Codex 엔진으로 도는 에이전트(OpenAI Responses API 연결)의 관리자에게 경고 한 줄을 보인다. 에이전트를 켜는 일은 막지 않는다. `external`에서 라벨 붙은 노드가 없으면 Pod는 `Pending`으로 기다리고, 15분 뒤 `NO_CAPACITY`의 이유에 노드 라벨을 확인하라는 말이 더해진다. 예전 `codexSandbox.installer.enabled`는 없어졌고, 쓰면 render가 `codexSandbox.provider`로 옮기라고 알리며 멈춘다.

**설치 DaemonSet 없이 프로필을 두는 방법.** Security Profiles Operator나 노드 이미지로 프로필을 배포하는 클러스터는 `codexSandbox.provider=external`로 둔다. 그러면 chart는 Node 권한도 admission 정책도 만들지 않는다. 운영자는 Codex worker가 뜰 노드마다 두 가지를 직접 한다. 먼저 chart의 `files/codex-sandbox-seccomp.json`을 `<kubeletDir>/seccomp/werft/codex-sandbox.json`에 둔다. 그다음 파일을 둔 노드에만 라벨을 붙인다.

```bash
kubectl label node <node> werft.codex-seccomp-profile=installed
```

라벨이 없으면 Codex Pod는 그 노드에 배치되지 않고, 라벨을 붙인 노드가 하나도 없으면 `Pending`으로 남는다. 노드에서 파일을 치울 때는 라벨을 먼저 뗀다(`kubectl label node <node> werft.codex-seccomp-profile-`). chart를 지운 뒤 라벨을 모두 떼려면 같은 명령에 `<node>` 대신 `--all`을 준다. 노드마다 할 명령과 chart를 올릴 때 할 일은 [Codex sandbox 노드 준비](/run-server/self-hosting/prepare-codex-sandbox)에 있다.

**AppArmor가 켜진 호스트.** Docker의 `docker-default`와 containerd의 기본 AppArmor 프로필은 `mount`를 막는다. 그래서 AppArmor가 켜진 호스트(Ubuntu·Debian의 기본값)에서는 seccomp 프로필이 있어도 bubblewrap이 `bwrap: Failed to make / slave: Permission denied`로 실패하고, `auto` 세션은 거절된다. Ubuntu 23.10부터 켜진 `kernel.apparmor_restrict_unprivileged_userns=1`은 AppArmor를 풀어도(`unconfined`) `bwrap: setting up uid map: Permission denied`로 막는다. Ubuntu 24.04와 Docker 28에서 확인한 최소 조건은 Codex 컨테이너에 `docker-default`에 `userns,`·`mount,`·`pivot_root,` 세 규칙을 더한 AppArmor 프로필을 거는 것이다. 이 조건은 sysctl 값과 상관없이 통한다. Werft는 아직 Codex 컨테이너에 AppArmor 프로필을 따로 걸지 않는다. 그래서 이런 호스트에서는 지금 `auto`를 쓸 수 없다. 다른 권한 모드는 쓸 수 있다.

**샌드박스를 끄는 방법.** Helm은 `codexSandbox.enabled=false`, compose는 scheduler의 `CODEX_SANDBOX=disabled`를 준다. 끄면 `auto` 모드도 함께 꺼진다. Codex 컨테이너는 기본 seccomp로 뜨고, 설치 DaemonSet은 만들어지지 않는다. `auto` 세션은 시작 전에 거절되고(`recovery_required`), 이유에 이 값이 남는다. 다른 권한 모드는 그대로 돈다. 노드에 프로필을 둘 수 없는 클러스터에서 Codex를 `auto` 없이 쓸 때 이 값을 쓴다. 끈 상태는 scheduler와 worker의 기동 로그 경고로도 드러난다. 값을 바꾸면 격리 stamp가 달라져 실행 중인 worker가 교체된다.

**커널 패치.** 샌드박스를 켜면 Codex 컨테이너 안에서 user namespace와 mount를 쓸 수 있다. 그 경로의 커널 취약점은 컨테이너 탈출로 이어질 수 있다. Codex 세션이 도는 노드에는 커널 보안 업데이트를 바로 적용한다.

**엔진을 바꾸는 방법.** 단일 env에서 `WORKER_IMAGE`를 새 엔진의 이미지로, `WORKER_IMAGE_PREVIOUS`를 지금 이미지로 두면 옛 엔진의 세션은 체크포인트가 없어도 직전 이미지로 뜨고, 새 엔진의 세션은 새 이미지로 뜬다. 이미 도는 배포의 `WORKER_IMAGE`를 다른 엔진의 이미지로 바꾸려면 업그레이드 검사(`upgrade-check`)의 규칙을 그대로 따른다. 새 설정의 `WORKER_IMAGE_PREVIOUS`가 지금 배포된 이미지여야 하고, 검사가 이어 받을 수 없다고 출력하는 세션(엔진이 다른 체크포인트뿐 아니라 SDK·CLI 버전이나 digest 방식이 맞지 않는 것, 런타임이 기록되지 않은 것도 포함한다)은 모두 `upgrade.approvedSessions`에 정확히 그 출력 목록으로 승인해야 한다. 체크포인트는 엔진 사이에서 옮길 수 없으므로, 전환 뒤에는 직전 이미지(옛 엔진)로 도는 세션이 끝나야 직전 이미지를 비울 수 있다.

둘 다 없으면 런타임 조합을 읽지 않으므로 아래 pin 유지도 적용되지 않는다. `WORKER_IMAGE_PREVIOUS_RUNTIME`만 있거나 값을 읽을 수 없으면 기동하지 않는다. 설정하면 직전 이미지 버전으로 만든 release와 그 세션도 계속 돈다. release는 만들 때 이미지가 싣던 런타임 버전을 고정하므로, 현재·직전 이미지 어느 쪽도 싣지 않는 버전의 release는 새 세션을 받지 않는다. 그 에이전트는 다시 release한다.

GitHub Packages bot token을 다른 host로 보내야 할 때만 아래 값을 둔다. GitHub Enterprise Server나 테스트용 가짜 레지스트리가 그런 경우다. 값은 http(s) URL이고 userinfo·query·fragment가 있으면 API가 기동하지 않는다. 레지스트리 host는 proxy의 `EGRESS_CREDENTIAL_ALLOWLIST`(사설 주소면 `EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST`)에도 있어야 한다. API는 token 확인을 `GITHUB_PACKAGES_API_URL`의 host:port에만 보내고 redirect는 따라가지 않는다. 기본값(`https://api.github.com`)은 공인 주소로 풀릴 때만 부르고, 직접 정한 주소는 http이거나 사설 주소여도 된다. 메타데이터·link-local 주소로 풀리는 이름은 어느 쪽이든 거절한다.

| 변수 | 기본값 | 의미 |
|---|---|---|
| `GITHUB_PACKAGES_API_URL` | `https://api.github.com` | 등록하는 token의 scope를 묻는 곳(`GET /user`) |
| `GITHUB_PACKAGES_NPM_URL` | `https://npm.pkg.github.com` | `github-npm` route의 upstream |
| `GITHUB_PACKAGES_RUBYGEMS_URL` | `https://rubygems.pkg.github.com` | `github-rubygems` route의 upstream |

## 웹에서 정하는 실행 한도

아래 값은 env가 아니라 owner가 **설정 > 워크스페이스 > 실행 한도**에서 저장한다(`PATCH /v1/installation-config`). 설치 전체에 하나이고, 저장하면 그 API는 바로, 다른 replica와 scheduler·slack·metrics role은 10초 안에 따른다. 저장한 값이 없으면 기본값을 쓴다. 어느 role도 옛 env를 읽지 않는다. migrate가 업그레이드 때 한 번만 옮겨 담는다([웹으로 옮긴 실행 한도](/run-server/self-hosting/upgrade-compose#웹으로-옮긴-실행-한도)).

| 화면의 칸 (옛 env) | 기본값 | 의미와 허용 범위 | 넘었을 때 |
|---|---|---|---|
| 사람 응답 (`PENDING_REQUEST_TTL_SEC`) | 1800 | 정수 1–604800초. 승인·질문 요청을 받는 기간이다. 등록된 요청은 worker가 이 값만큼 기다리고, 이미 등록된 요청은 바꾼 값을 따르지 않는다. gateway가 등록하기 전까지는 worker가 30분 기다린다. turn 시간에는 대기 시간도 들어가므로, 대기는 그 상한을 넘지 못한다 | 답이 없는 요청을 닫는다 |
| 턴 시간 (`MAX_TURN_SECONDS`) | 3600 | 정수 1–604800초. turn 하나의 벽시계 상한이고 승인 대기도 포함한다. worker env `WORKER_MAX_TURN_SEC`로 전달된다 | turn `failed(turn_timeout)`. 엔진이 응답하지 않으면 `outcome_unknown(turn_timeout)` |
| 모델 요청 재시도 (`PROVIDER_MAX_RETRIES`) | 2 | 정수 0–10. 실패한 provider 요청을 다시 보내는 횟수. worker env `WORKER_PROVIDER_MAX_RETRIES`를 거쳐 SDK `CLAUDE_CODE_MAX_RETRIES`로 전달된다. 0이면 첫 실패에서 turn이 끝난다 | turn `failed(api_error)`. turn 상세 `result`에 `api_error_status`·`provider_error`·`last_retry_status`가 남는다 |
| 세션 비용 (`SESSION_COST_LIMIT_USD`) | 25 | 0보다 크고 1000000 이하인 USD. 세션 누적 비용(egress proxy가 계측한 provider 호출별 usage를 플랫폼 가격표로 환산한 합, 추정치) | 새 turn을 dispatch하지 않는다. 세션 상세 `attention.code=BUDGET_EXCEEDED`가 뜨고 worker는 슬롯을 반납한다. 입력은 계속 `queued`로 받는다 |
| 세션 토큰 (`SESSION_TOKEN_LIMIT`) | 0 (상한 없음) | 정수 0–9007199254740991. 세션 누적 provider token 수. 비용 상한과 같은 호출을 세되 단가와 무관하다 | 세션 비용과 같다. 두 상한은 같은 판정(`budgetExceeded`)을 지나며 어느 쪽이 먼저 닿아도 `BUDGET_EXCEEDED`다. `attention.reason`은 닿은 상한만 적는다 |
| 대기 메시지 (`QUEUED_INPUT_LIMIT_PER_SESSION`) | 20 | 정수 1–100000. 세션 하나가 쌓아 둘 수 있는 `queued` turn 수 | `429 RATE_LIMITED`, `retryable:true`, `Retry-After: 5` |
| 입력 보관 (`STORAGE_LIMIT_BYTES`) | 1073741824 (1 GiB) | 정수 1–9007199254740991 bytes. 설치 전체가 보존하는 입력 message의 UTF-8 bytes. event·checkpoint object·worker 디스크는 세지 않는다(디스크는 workspace quota가 맡는다) | `413 STORAGE_LIMIT_EXCEEDED`, `retryable:false` |
| 작업 공간 용량 (`WORKSPACE_ENFORCE`) | `warn` | `warn`·`fail`·`off`. worker의 workspace가 quota를 넘었을 때 할 일이다. worker는 claim할 때 값을 받으므로, 이미 돌고 있는 worker는 받은 값을 계속 쓴다 | `warn`은 로그 `worker.turn.workspace_quota_exceeded`만 남기고, `fail`은 넘은 turn을 멈추며, `off`는 재지 않는다. `EXECUTION_WORKSPACE_QUOTA=off`인 Docker 설치의 worker는 이 값과 상관없이 `fail`로 돈다 |

| 세션 기록 보관: 보관 작업이 할 일 (`SESSION_ARCHIVE_DRY_RUN`) | 세기만 함 (`true`) | 세기만 함·실제로 옮김. 세기만 하면 옮길 수만 로그에 남긴다. 화면은 API의 object store 설정으로 보아 보관할 수 없는 설치이면 그렇다고 알린다 | 해당 없음 |
| 멈춘 세션의 작업 공간 (`EXECUTION_WORKSPACE_STOPPED_TTL_SEC`) | 86400 (하루) | 정수 0–315360000초(3650일). `stopped` 세션의 workspace(Docker volume, Kubernetes PVC)를 stop한 때부터 남겨 두는 시간이다. 0이면 다음 회수 때 바로 회수한다. scheduler가 회수할 때마다 DB에서 읽는다([worker 작업 공간](/run-server/self-hosting/reference/storage)) | scheduler가 workspace를 회수하고, 다음 resume은 checkpoint에서 복원한다 |
| 일시 정지한 세션의 작업 공간 (`EXECUTION_WORKSPACE_PAUSED_TTL_SEC`) | 86400 (하루) | 정수 0–315360000초(3650일). resume이 받아들일 checkpoint가 있는 `paused` 세션의 workspace를 pause한 때부터 남겨 두는 시간이다 | 멈춘 세션과 같다 |

단가 미상 토큰 상한(`unknown_price_session_token_limit`)은 같은 화면에서 저장하고 옛 env가 없다. 기본값은 5000000이고, 정수 1–9007199254740991을 받는다. 0으로 끌 수 없다. 한 세션에서 단가 미상으로 표시된 호출의 토큰과 단가 미상 모델로 열려 있는 예약의 토큰을 더한 값이 이 값 이상이면, 그 세션의 다음 모델 호출을 `BUDGET_EXCEEDED`로 거절한다. 단가 미상 호출에는 금액을 붙이지 않아 비용 상한이 그 호출을 세지 못하므로, 가격과 무관한 토큰 수로 막는 것이다(아래 "사용량과 비용 계측"). 단가 미상 모델을 부르는 첫 호출도 그 예약의 추정 토큰으로 걸릴 수 있다. 단가 미상으로 표시된 호출도, 단가 미상 모델로 열려 있거나 지금 여는 예약도 없는 세션은 이 값으로 거절되지 않는다. 요청한 모델의 단가를 알아도 답이 단가 미상 모델을 대면 그 호출은 단가 미상으로 표시된다. 새 turn의 dispatch는 이 값으로 막지 않으므로, 상한에 닿은 세션의 turn은 시작한 뒤 첫 호출에서 실패한다. 판정은 호출을 열 때 하므로, 이미 열려 있던 호출의 답이 단가 미상 모델을 대면 그 호출들의 토큰만큼 상한을 넘을 수 있다.

세션 밖의 대화 호출(채널 판정, 채널 요약 접기)과 대화 턴의 호출도 같은 값으로 막는다. 이쪽은 세션이 아니라 호출이 잡히는 예산 계정(사람이나 팀)의 한 달(UTC)로 센다. 계정 없이 잡히는 호출(팀이 없는 에이전트의 호출)은 에이전트의 한 달로 센다. 그 달의 단가 미상 토큰이 이 값에 닿으면 그 계정(또는 에이전트)의 대화 호출은 단가를 아는 모델의 것까지 다음 달 1일(UTC)까지 거절되고, 대화 턴은 `BUDGET_EXCEEDED`로 끝난다. 잡혀 있던 단가 미상 호출이 쓰이지 않고 풀리면 그만큼 자리가 돌아와, 그 달 안에서도 다시 열릴 수 있다. 단가 미상 호출을 한 번도 하지 않은 계정은 이 값으로 거절되지 않는다. 과금 없음(`billing: none`) 연결의 호출은 세지 않는다.

턴 시간·모델 요청 재시도는 scheduler가 pass마다 읽어, 그 pass가 예약하는 launch에 고정한다. worker는 고정된 값으로 뜬다. 값을 바꾸면 다른 값으로 뜬 worker 가운데 쉬고 있는 것은 바로 내려가고, turn을 돌고 있는 것은 받은 값으로 그 turn을 마친 뒤 내려간다. 세션의 다음 launch가 새 값을 받는다([turn 시간과 재시도를 바꿀 때](/run-server/self-hosting/explanation/isolation#turn-시간과-재시도를-바꿀-때)).

**쓸 수 있는 값이 없을 때.** 옮겨 오지 못한 env 값(범위 밖)이나 이 릴리스가 받지 않는 저장값이 있는 키는 막힌다. 기본값으로 돌지 않는다. 그 키를 읽는 일만 거절되고, 화면은 그 칸에 안내를 보이며, 값을 저장하면 풀린다. 설정을 60초 넘게 읽지 못할 때(DB 장애)도 모든 키가 같다.

- 사람 응답: 새 권한 요청·질문의 등록이 `503 BACKEND_UNAVAILABLE`(`retryable:true`)로 거절된다. worker가 다시 보낸다.
- 세션 비용·토큰·대기 메시지·입력 보관: 세션 생성과 메시지 접수가 `503 BACKEND_UNAVAILABLE`로 거절된다. 이미 받은 요청을 같은 `Idempotency-Key`로 다시 보내면 저장된 응답을 그대로 받는다. 이 네 값과 턴 시간·재시도를 보여 주는 `GET /v1/limits`와 `GET /v1/sessions/{id}/usage`도 그중 하나가 막히면 `503`이다. 세션 비용·토큰은 그 밖에도 막는다. scheduler는 launch만 건너뛰고(로그 `Launches skipped: the session limits cannot be read`) 종료·workspace 회수는 계속한다. worker의 claim·다음 입력·provider 호출 열기·finalize는 `503`(재시도)을 받는다. 이미 연 provider 호출을 다시 여는 것과 이미 끝난 finalize의 답은 그대로 받는다. metrics는 launch 대기열 gauge(`werft_launch_queue_*`)를 비운다.
- 작업 공간 용량: worker의 claim이 `503`을 받아 세션이 시작되지 않는다.
- 턴 시간·모델 요청 재시도: scheduler가 새 launch를 예약하지 않는다(로그 `Launches skipped: the worker limits cannot be read`). 값이 고정되기 전에 예약된 launch는 다시 만들지 않고 지금 자원을 둔다(로그 `Launch held: the worker limits it would start with cannot be read`). 값이 고정된 launch와 떠 있는 worker는 그 값으로 계속 돌고, 종료·workspace 회수도 계속한다.
- 멈춘·일시 정지한 세션의 작업 공간: 둘 중 하나라도 막히면 scheduler는 `stopped`·`paused` 세션의 workspace를 새로 회수하지 않는다(로그 `Workspace TTLs cannot be read; keeping every stopped and paused session's workspace`). 끝난 세션의 workspace와 앞선 회수가 마치지 못한 것은 계속 회수하고, launch도 그대로 한다.

**비용·토큰 상한은 provider 호출 하나하나에도 걸린다.** egress proxy는 과금되는 provider 호출(Messages, Responses)을 보내기 전에 API에 그 호출을 연다. API는 세션의 누적 비용·토큰에, 아직 끝나지 않은 호출들의 예약과 이번 호출의 예약을 더한다. 그 합이 상한에 닿으면 `403 BUDGET_EXCEEDED`로 거절하고, proxy는 그 호출을 provider로 보내지 않는다. 예약은 요청 바이트 수를 입력 token으로 보고 가장 비싼 cache write 단가(Claude 2배, OpenAI 2.5배)로 매기고, 출력은 요청의 출력 상한 전체(Responses 요청에 상한이 없으면 32,768 token)로 매긴다. `claude-sonnet-5`나 `gpt-5.5` 호출 하나에 대략 1–2달러다.

- 세션은 상한보다 호출 하나의 예약만큼 일찍 멈춘다. 세션 비용 한도가 호출 하나의 예약보다 작으면 첫 호출부터 거절된다.
- 내린 한도는 실행 중인 세션의 다음 provider 호출부터 걸린다. 올린 한도는 실행 중인 worker에는 다음 claim에서 닿는다(worker가 claim 때 남은 예산을 SDK `maxBudgetUsd`로 받기 때문이다).
- 세션에 기록되는 비용은 예약이 아니라 provider가 알린 사용량이다. 사용량 보고가 끝내 실패한 호출은 그 예약을 계속 센다.
- API가 5초 안에 호출을 열지 못하면 proxy는 호출을 보내지 않고 `503`으로 답한다. 엔진은 다시 시도한다.
- 상한은 추정이다. 긴 응답 하나는 그 호출의 예약까지 갈 수 있다. Responses 요청에 출력 상한이 없으면 32,768 token보다 많이 추론한 만큼 넘을 수 있다.

## scheduler·worker 컨테이너·egress 설정

scheduler가 worker 컨테이너를 만들 때 읽는 값이다. 없으면 기본값을 쓰고, 형식이 틀리면 기동하지 않는다. user, HOME·workspace 경로, tmpfs 크기, credential 포트, stop timeout은 `werft.isolation` 지문에 들어간다([실행 기반과 worker 격리](/run-server/self-hosting/explanation/isolation)). 그래서 바꾸면 실행 중인 worker가 교체된다. CPU·메모리·PID 한도는 다음 launch부터 적용된다.

`WORKER_MEMORY_MB`는 transcript 상한(`MAX_TRANSCRIPT_BYTES`)과 함께 정한 값이다. 둘의 관계, 노드당 세션 수, 바꾸는 방법은 [용량 관리](/run-server/self-hosting/capacity)에 있다.

scheduler는 `WORKER_IMAGE`와 `WORKER_IMAGE_RUNTIME`으로 현재 이미지를, `WORKER_IMAGE_PREVIOUS`와 `WORKER_IMAGE_PREVIOUS_RUNTIME`으로 직전 릴리스 이미지를 받는다. 런타임 값은 API와 같은 값이다(위 API 설정). 직전 이미지는 두 값을 함께 설정하고, 하나만 있으면 기동하지 않는다. `WORKER_IMAGE_RUNTIME`이 없으면 모든 launch가 `WORKER_IMAGE`로 뜬다. 설정하면 launch마다 세션의 checkpoint 포인터가 기록한 조합(engine·SDK·CLI·profile digest scheme)과 같은 이미지를 고르고, 둘 다 맞으면 현재 이미지를 쓴다. 새 세션, checkpoint가 없는 세션, 조합을 기록하지 않은 옛 checkpoint는 세션 엔진의 가장 새 이미지(현재 이미지, 그 엔진을 직전 이미지만 돌리면 직전 이미지)로 뜬다. 그 엔진의 이미지가 없으면 slot을 쓰지 않고 기다린다. 어느 이미지와도 맞지 않는 세션은 worker를 띄우지 않고 `recovery_required`(`incompatible_checkpoint`)로 멈추며, 세션 이벤트 `checkpoint_restore_failed`에 `detected_at: "launch"`가 남는다. `retry_restore`로 다시 시도할 수 있다.

**이미지 목록(`WORKER_IMAGES`).** 위 네 값 대신 JSON 배열 하나로 이미지를 줄 수도 있다. 원소는 `{"image": "<repository>@sha256:<digest>", "runtime": {…}, "released_at": "2026-11-10T00:00:00Z"}`이고, 엔진마다 가장 새 이미지부터 적는다. 엔진마다 철회되지 않은 첫 원소가 그 엔진의 새 세션 이미지이고, 나머지는 그 조합으로 봉인된 checkpoint를 이어 받는다. 고르는 규칙은 위와 같다. `runtime`은 images.yml의 값을 그대로 넣고, `released_at`은 같은 엔진의 원소끼리 배열 순서대로 엄격히 줄어야 한다(같거나 거꾸로면 기동하지 않는다). 엔진이 다른 원소끼리는 순서와 시각을 보지 않아, 두 엔진을 같은 시각으로 낼 수 있다. 태그 참조, 같은 digest 두 번, 모르는 필드, 한 엔진에 철회되지 않은 이미지가 셋 이상인 목록도 기동하지 않는다. `WORKER_IMAGES`와 위 네 값을 함께 주면 기동하지 않는다. scheduler·API·slack role이 같은 값을 읽고, workspace quota helper는 철회되지 않은 첫 원소의 이미지로 뜬다. 업그레이드 검사(`upgrade-check`)는 목록도 판단한다([업그레이드 전 검사](/run-server/self-hosting/upgrade-kubernetes#업그레이드-전-검사)). chart에서는 `images.workers`에 `{repository, digest, runtime, releasedAt}` 원소를 가장 새 이미지부터 적으면 `WORKER_IMAGES`를 렌더링한다. 이때 `images.worker`와 `images.workerPrevious`의 digest·runtime은 비워 둔다. 게시 chart는 기본값으로 그 릴리스의 Claude·Codex 두 이미지를 `images.workers`에 담는다. `images.worker`로 이미지 하나만 주려면 `images.workers: []`를 함께 적는다. Helm은 목록을 기본값과 합치지 않고 통째로 바꾸므로, values에 적은 목록에는 다음 chart의 이미지가 들어가지 않는다. 위에서 기동하지 않는 목록은 chart도 렌더링하지 않는다. `releasedAt`은 초까지 적은 RFC 3339 시각이어야 하고, 소수 초는 세 자리까지 쓴다. compose 스택은 목록을 쓰지 않는다. 그 scheduler는 늘 `WORKER_IMAGE`를 가지므로 `WORKER_IMAGES`를 주면 기동하지 않는다. 두 엔진을 함께 돌리는 compose 스택은 단일 env로 준다. `WORKER_IMAGE`에 Codex 이미지, `WORKER_IMAGE_PREVIOUS`에 Claude 이미지를 두고, 두 runtime은 빌드한 각 이미지에서 위 명령으로 읽는다. `infra/compose.two-engines.yml`이 그 순서(두 이미지 빌드 → runtime 추출 → 스택 시작)를 적는다. runtime 없이 두 이미지만 주면 scheduler가 기동하지 않는다.

**철회(`retracted`).** 다시 빌드할 수 없는 취약점처럼 이미지를 더 쓰면 안 될 때는 그 원소에 `"retracted": true`를 붙여 목록에 남긴다(chart에서는 `images.workers[].retracted: true`). 철회된 이미지로는 어떤 세션도 띄우지 않는다. 그 이미지로 봉인된 checkpoint는 엔진·SDK·CLI가 같은 철회되지 않은 이미지(수정 빌드)가 목록에 있으면 그 이미지로 재개한다. 직전 launch가 철회된 이미지였던 세션이 다른 이미지로 옮기면, 그 launch를 예약할 때 세션 기록에 `worker_image_replaced` 이벤트(옮기기 전과 후의 이미지, reason `retracted`)가 남고, 세션에 Slack 스레드가 있으면 그 스레드에 안내가 올라간다. 없으면 세션은 launch 전에 `recovery_required`로 멈추고, attention `RESTORE_FAILED`의 reason이 `runtime_retired`가 된다. 수정 이미지를 넣은 뒤 `retry_restore`로 다시 시도하거나, `start_fresh`로 checkpoint 없이 이어 가거나, 닫는다. 철회된 이미지로 이미 떠 있는 launch도 그대로 두지 않는다. 아직 worker가 붙지 않은 launch는 다시 만들지 않고 내려 돌려보내, 세션이 이미지를 다시 고르게 한다. worker가 붙어 실행 중인 launch는 진행 중인 turn이 끝나기를 기다린 뒤 내린다(`stale_isolation`과 같은 drain이다. turn 최대 시간에 마무리 여유를 더한 시간이 지나면 더 기다리지 않는다). 그 세션도 다음 launch에서 이미지를 다시 고르고, 고를 이미지가 없으면 위처럼 멈춘다. 이미지를 기록하기 전에 예약된 launch에 worker가 붙어 있으면, 무엇을 돌리는지 알 수 없어 그대로 둔다. 이 교체는 scheduler 로그에 `Execution resource runs a retracted worker image`로 남고, 교체 기록의 사유는 `stale_isolation`과 같다(그 값을 모르는 이전 scheduler로 롤백해도 읽히도록). 철회하지 않고 목록에서 빼기만 한 이미지는 이렇게 내리지 않는다. 그 이미지로 예약된 launch는 worker가 붙기 전에 다시 만들 때 저장된 대로 그 이미지로 다시 만들고(그 엔진의 철회되지 않은 이미지가 목록에 없거나, 그 이미지가 철회된 이미지와 같은지 확인하지 못하면 다시 만들지 않고 돌려보낸다), worker가 붙은 launch는 그대로 돈다. 그 이미지로 더는 띄우지 않으려면 빼지 말고 철회한다. 개수 제한은 철회되지 않은 이미지에만 적용되고, 모든 이미지가 철회된 목록도 기동한다. 이때는 어떤 세션도 launch하지 않고(목록에서 빠진 이미지의 launch도 다시 만들지 않는다), workspace quota 검사도 하지 않으며, checkpoint가 있는 세션은 `runtime_retired`로 멈추며, scheduler가 기동할 때 오류 로그를 한 번 남긴다. 한 엔진의 이미지만 모두 철회돼도 그 엔진의 세션에는 같은 일이 일어난다. checkpoint가 없어 launch를 기다리는 그 엔진의 세션은 attention `NO_WORKER_IMAGE`(reason `runtime_retired`)를 보이고, 그 엔진의 철회되지 않은 이미지를 넣으면 사라진다. 업그레이드 검사는 철회된 이미지를 복원 이미지로 세지 않는다.

프로필 제거 전에 빌드한 worker 이미지는 프로필 제거 릴리스의 control-host 응답을 읽지 못하므로 지원 창에 들지 않는다. 그 릴리스로 올리는 upgrade에서는 업그레이드 검사 때문에 `WORKER_IMAGE_PREVIOUS`가 그 이미지일 수 있지만, 그 이미지로 뜨는 세션은 없다([프로필 제거 릴리스의 업그레이드 순서](/run-server/self-hosting/upgrade-compose#프로필-제거-릴리스의-업그레이드-순서)).

worker는 claim 때 자기 이미지가 실제로 싣는 조합을 보낸다. 설정한 조합과 다르면 API가 claim을 거절하고(`LAUNCH_FAILED`, `reason_code` `worker_image_mismatch`), 그 이미지를 그 설정값에 대해 거부한 것으로 기록한다. 이후 그 이미지로 뜰 세션은 launch되지 않고 기다리며, scheduler pass는 `images_refused`를 error 로그로 남기고 exit 1로 끝난다. 이미지 설정을 바로잡으면(값이 달라지면) 다음 pass부터 다시 launch한다. 세션 자체는 실패로 바뀌지 않는다.

배포 순서: 새 worker는 claim에 `image_runtime`을 싣는다. 이 필드를 모르는 옛 API는 요청을 거절하므로, API를 먼저 올린 뒤 scheduler의 `WORKER_IMAGE`를 새 이미지로 바꾼다. 프로필 제거 릴리스로 올릴 때는 예외로, 둘을 한 upgrade로 함께 바꾼다([프로필 제거 릴리스의 업그레이드 순서](/run-server/self-hosting/upgrade-compose#프로필-제거-릴리스의-업그레이드-순서)).

egress-proxy와 API의 authorizer listener는 아래 값을 읽는다. 목록 변수는 기본값에 덧붙이지 않고 기본값을 통째로 대체한다. GitHub·bucket host를 넣을 때 provider와 패키지 registry 등 필요한 항목을 모두 다시 적는다. 공개 credential 목록(`EGRESS_CREDENTIAL_ALLOWLIST`)은 proxy와 API에서 같은 값으로 맞춘다. private 목록(`EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST`)은 proxy가 거절하는 기준이다. API에서는 워크스페이스 MCP 서버를 http로 등록하고 사설 주소로 부를 수 있는 host를 정하고, 콘솔 경고에도 쓴다. private 목록도 같게 두기를 권장하지만 강제되지는 않으며 core·local-model 레이어의 역할별 기본값도 다르다. API는 두 credential 목록을 proxy와 같은 방식으로 기동 때 한 번 읽는다. 대소문자, host 끝의 점, IPv6 주소의 대괄호는 구별하지 않고, 두 목록에 모두 있는 host는 공개 목록 쪽으로 친다. proxy가 기동을 거절하는 항목(포트가 없거나 1~65535의 정수가 아닌 항목)은 아무것도 허용하지 않는다. 모델 연결의 콘솔 경고가 이 결과를 쓴다. 워크스페이스 MCP 서버 등록은 이 공개 목록을 요구하지 않는다. https 이름의 풀린 주소가 모두 공개 주소이면 공개 목록에 그 host를 추가하지 않아도 등록되고 호출된다([격리 설명](/run-server/self-hosting/explanation/isolation)).

| `CHECKPOINT_GIT_MEMORY_MB` | 1536 | bundle 검증 git 프로세스 하나의 주소 공간 상한(MiB). 512 미만이면 기동을 거부한다 |

compose의 Postgres는 `POSTGRES_USER`(`postgres`)·`POSTGRES_PASSWORD`(`dev`)·`POSTGRES_DB`(`sessions`)로 만들고, 모든 서비스가 같은 값으로 DSN을 만든다.

worker는 아래 값도 env로 읽는다. 하지만 scheduler가 넘기지 않으므로 운영에서는 코드 기본값으로 고정이다. `WORKER_ANSWER_POLL_SEC`(1), `WORKER_ATTACH_FETCH_TIMEOUT_SEC`(300, 세션 도중 붙인 저장소 하나를 받아 오는 시간), `WORKER_ATTACH_FETCH_MAX_MB`(2048, 그 저장소를 받은 scratch mirror의 크기), `WORKER_CLAIM_TIMEOUT_SEC`(60), `WORKER_DRAIN_TIMEOUT_SEC`(100, stop 유예 안으로 줄어든다), `WORKER_HEARTBEAT_INTERVAL_SEC`(2), `WORKER_LEASE_SAFETY_MARGIN_SEC`(10), `WORKER_NEXT_INPUT_RETRY_SEC`(60), `WORKER_NEXT_INPUT_WAIT_SEC`(20), `WORKER_REQUEST_TIMEOUT_SEC`(30), `WORKER_STARTUP_TIMEOUT_SEC`(3600), `WORKER_CLAUDE_CONFIG_DIR`(`$HOME/.claude`).

## 감독 루프

| 설정 | 기본 | 의미 |
|---|---|---|
| `RECONCILER_INTERVAL_SEC` | 10 | pass가 끝난 뒤 다음 pass까지 쉬는 시간 |
| `RECONCILER_PASS_TIMEOUT_SEC` | 60 | 이 시간을 넘긴 pass는 SIGTERM, 10초 뒤 SIGKILL로 끝내고 실패로 센다. DB가 멈춘 pass가 pool timeout으로 스스로 끝나는 약 45초보다 크게 둔다 |
| `RECONCILER_MAX_CONSECUTIVE_FAILURES` | 3 | 실패 pass가 이만큼 이어지면 루프가 exit 1 하고 `restart: unless-stopped`가 재시작한다. 그보다 적으면 다음 pass가 곧 재시도다 |
| `RECONCILER_HEALTH_STALE_SEC` | 90 | healthcheck는 마지막으로 끝난 pass가 실패했거나, 진행 중인 pass가 제한 시간을 넘겼거나, 이 시간 동안 성공한 pass가 없으면 unhealthy다. 성공 직후 멈춘 pass도 제한 시간에서 바로 unhealthy가 된다. `RECONCILER_INTERVAL_SEC + RECONCILER_PASS_TIMEOUT_SEC`보다 커야 기동한다 |
| `RECONCILER_STATUS_FILE` | `/tmp/reconciler-status.json` | 루프가 pass마다 갱신하는 상태(`lastSuccessAt`·`lastDegradedAt`·`lastFailureAt`·`lastFailureReason`·`consecutiveFailures`·`lastPassDurationMs`, 진행 중인 pass의 `passDeadlineAt`). healthcheck가 읽는다 |
| `RECONCILER_BATCH_SIZE` | 100 | pass의 각 단계(orphan·lease·interrupt 회수, 기한을 넘긴 interrupt·terminate receipt의 `unknown` 마감, 입력 대기 알림, provider 호출 장부의 정산 확인·만료 경고·정리)가 한 번에 처리하는 row 수 상한. 남은 row는 다음 pass가 처리한다. scheduler의 terminate 기한 sweep은 이 값을 읽지 않고 pass마다 고정 상한 100개씩 처리한다 |

| scheduler 설정 | 기본 | 제약 |
| --- | --- | --- |
| `SCHEDULER_INTERVAL_SEC` | 5 | pass 종료 뒤 대기 |
| `SCHEDULER_PASS_TIMEOUT_SEC` | 180 | Docker stop+request timeout보다 큼. Kubernetes는 150초 초과 |
| `SCHEDULER_MAX_CONSECUTIVE_FAILURES` | 3 | 연속 실패 뒤 loop 종료 |
| `SCHEDULER_HEALTH_STALE_SEC` | 200 | interval+timeout보다 큼 |
| `SCHEDULER_STATUS_FILE` | `/tmp/scheduler-status.json` | 디렉터리 전체가 쓰기 가능해야 함 |

compose는 `RECONCILER_STATUS_FILE`, `SCHEDULER_STATUS_FILE`, `RECONCILER_DRY_RUN`을 전달하지 않는다. 상태 확인은 각 status file과 `--health`를 사용한다. reconciler dry-run은 [복구 작업](/run-server/self-hosting/recover-sessions)에서 직접 1회 실행한다. `HEARTBEAT_TTL_SEC`는 API만 읽으며 reconciler에 넣으면 기동을 거부한다.

## Kubernetes env와 values

scheduler는 `EXECUTION_BACKEND`로 backend를 고른다. 값은 `local_docker`(기본값, 비워 둬도 같다)와 `kubernetes` 둘이고, 그 밖의 값이면 그 값을 적은 오류로 기동을 거부한다. `kubernetes`이면 Docker 설정(`DOCKER_HOST`, `EXECUTION_DOCKER_*`, `EXECUTION_WORKSPACE_QUOTA`)을 읽지 않고 Docker socket도 쓰지 않는다. Docker 전용 preflight인 egress proxy 격리 확인과 workspace quota probe도 돌지 않는다. kubernetes에서 worker 격리는 chart의 NetworkPolicy가 맡고, workspace는 PVC 크기를 요청하지만 실제 상한 강제는 저장소에 달려 있다. 정지·요청 timeout은 고정값(120s + 30s)이어서 `SCHEDULER_PASS_TIMEOUT_SEC`는 150보다 커야 한다. `migrate-workspace`는 Docker volume을 옮기는 도구라서 `local_docker`에서만 돈다.

readOnlyRootFilesystem인 Pod에서는 status file을 쓰기 가능한 경로에 둔다. 기본 경로 `/tmp/scheduler-status.json`·`/tmp/reconciler-status.json`은 `/tmp`에 emptyDir를 마운트하면 그대로 쓸 수 있다. 다른 경로라면 `SCHEDULER_STATUS_FILE`·`RECONCILER_STATUS_FILE`로 바꾼다. 루프는 status file과 같은 디렉터리에 임시 파일(`<status file>.<pid>.tmp`)을 쓴 뒤 rename한다. scheduler는 그 옆에 `.quota-verified` 기록도 둔다. 그래서 파일 하나가 아니라 디렉터리 전체가 쓰기 가능해야 한다.

공유 env(`WORKER_IMAGE`, `WORKER_GATEWAY_URL`, `EXECUTION_EGRESS_PROXY_URL`, `EXECUTION_EGRESS_CREDENTIAL_PORT`, `EXECUTION_INSTALLATION_ID`, `EXECUTION_WORKSPACE_QUOTA_MB`, `EXECUTION_WORKSPACE_GC_MIN_AGE_SEC`, `S3_BUCKET`, `AWS_REGION`)는 Docker backend와 같다. kubernetes 모드에서는 다음 두 값에 제약이 더 붙는다.

- `WORKER_IMAGE`는 `repository@sha256:<digest>` 형식이어야 한다.
- `EXECUTION_INSTALLATION_ID`는 32자 이하의 소문자 DNS label이어야 한다.

kubernetes 모드에서만 읽는 설정은 다음과 같다.

`EXECUTION_WORKSPACE_ENFORCED_BY_STORAGE`는 미설정이면 `false`이며 정확히 `true`/`false`만 받는다. 빈 값·공백·대문자·`1`/`0`·`on`/`off`는 원본 값을 노출하지 않는 오류로 기동을 거부한다. Helm의 `worker.workspace.enforcedByStorage`(기본 `false`)에서 생성하며, 이 설치의 모든 workspace PVC(기존 것 포함)에 저장소가 요청 바이트를 하드로 강제한다는 운영자 선언이다. StorageClass가 비면 클러스터 기본값이므로 각 PVC의 강제를 운영자가 확인한다. Werft는 검증하지 않는다. 전용 쓰기 가능 마운트(`/` 아님, `rw` 있고 `ro` 없음), 파일시스템 총량이 요청의 0.95~1.05배, PVC capacity가 요청 이상이라는 휴리스틱을 통과한 선언 경로만 바이트 `hard`/inode `unknown`으로 판별한다. [저장소와 상한](/run-server/self-hosting/reference/storage)을 따른다. 선언 변경은 PVC·isolation stamp·기존 Pod env를 바꾸지 않고 새 Pod만 새 값을 받는다.

| 변수 | 뜻 |
| --- | --- |
| `EXECUTION_K8S_NAMESPACE` | worker Pod·Secret·PVC를 두는 namespace. 기본값은 scheduler 자신의 namespace다. 클러스터 밖에서 돌리면 반드시 줘야 한다. |
| `EXECUTION_K8S_WORKER_SERVICE_ACCOUNT` | worker Pod의 ServiceAccount. token은 늘 마운트하지 않는다. |
| `EXECUTION_K8S_STORAGE_CLASS` | workspace PVC의 StorageClass. 비우면 클러스터 기본값을 쓴다. |
| `EXECUTION_K8S_IMAGE_PULL_SECRETS` | 선택. 쉼표로 구분한 Secret 이름. |
| `EXECUTION_K8S_WORKER_NODE_SELECTOR` | 선택. JSON object. |
| `EXECUTION_K8S_WORKER_TOLERATIONS` | 선택. JSON array. |
| `EXECUTION_K8S_WORKER_EPHEMERAL_STORAGE_MB` | worker 컨테이너의 ephemeral-storage requests·limits(MiB). 기본 1024. 넘으면 kubelet이 Pod를 evict한다. |
| `SCHEDULER_NODE_CAPACITY_CHECK` | 선택. `true`면 scheduler가 시작할 때 worker 둘을 받지 못하는 노드마다 경고 로그를 남긴다. 미설정이면 `false`이며 `true`/`false` 밖의 값은 기동을 거부한다. Node를 읽을 권한이 필요하다. 켜면 Codex sandbox Pod가 자리를 기다릴 때 내릴 worker도 노드 라벨로 고른다. |

실패한 worker의 종료 사유와 로그 tail(마지막 8 KiB)은 scheduler 로그의 `Execution resource failed; log tail kept` 줄에 남는다. 로그 마스킹 규칙은 tail을 줄 단위로 가린다. 비밀 모양의 값은 그 값이 걸친 줄만 가린다. `input:` 같은 조각은 그 줄부터 끝까지 가린다. 그 앞의 줄은 남는다(URL login은 그 부분만 가린다). worker가 lease를 잃어 끝났으면 같은 줄의 `cause`가 `worker.ownership.lost`이고, heartbeat가 거절된 상태 코드와 오류 코드가 `heartbeat_status`·`heartbeat_code`에 남는다. 저장 위치와 보존 기간은 저장소의 Kubernetes 실행 어댑터 README(종료 사유와 로그 tail 절)에 있다.

Helm chart(`deploy/helm/werft`, 설치 절차는 [Kubernetes 설치 (Helm chart)](/run-server/self-hosting/kubernetes))로 설치하면 위 env를 직접 적지 않는다. chart가 values에서 만든다.

| --- | --- | --- |

| `EXECUTION_K8S_WORKER_SERVICE_ACCOUNT` | 없음 | chart가 만든 `<fullname>-worker`. token은 마운트하지 않는다 |

| `WORKER_CPUS`, `WORKER_MEMORY_MB` | `worker.cpus`, `worker.memoryMb` | |

| `EXECUTION_K8S_WORKER_EPHEMERAL_STORAGE_MB` | `worker.ephemeralStorageMb` | 기본 1024 |
| `SCHEDULER_NODE_CAPACITY_CHECK` | `scheduler.nodeCapacityCheck.enabled` | 기본 `false`. 켜면 chart가 Node를 읽기만 하는 ClusterRole을 scheduler에 만든다. [설치 때 노드 크기 경고](/run-server/self-hosting/capacity#설치-때-노드-크기-경고선택) |

| `PLATFORM_ALLOW_UNATTENDED_PERMISSIONS`(slack) | `api.extraEnv` | slack은 api와 같은 카탈로그를 읽으므로 api의 값을 따른다. `slack.extraEnv`에 적으면 그 값이 이긴다 |
| `SLACK_ROLE_CLOSE_LINKS`(slack) | `slack.extraEnv` | 기본 `true`. 닫힌 세션의 Slack 스레드 연결을 마지막 보고 줄을 넣은 뒤 닫고, 같은 스레드의 다음 멘션은 새 세션이 된다. `false`면 닫힌 세션의 스레드가 연결을 그대로 붙든다 |
| `SLACK_ROLE_TASK_REPLY_WAIT_SEC`(slack) | `slack.extraEnv` | 기본 30. 대화 rollout이 `on`일 때, 열린 작업의 스레드에 멘션 없이 단 답글이 M1 판단을 기다리는 초다. 판단 중에는 그 스레드의 이벤트와 채널 전체에 걸린 이벤트(멤버·이름·보관)를 미루고, 채널의 다른 스레드는 계속 처리한다. 다만 그런 채널 전체 이벤트가 채널 줄 맨 앞에 서면 다른 스레드도 그 뒤에서 기다린다. 이 시간이 지나면 판단 실패로 보고 답글을 작업의 세션에 보낸다(세션이 `paused`·`stopped`면 지금처럼 받지 않는다). 이 시간 뒤에 난 판단은 기록만 남고 답글을 작업에서 떼지 못한다. 실제로 넣는 시점은 다시 보는 간격(2초), slack 역할·M1 판단 pass의 주기, 줄에 밀린 이벤트만큼 더 늦을 수 있다. `0`이면 기다리지 않는다 |

어느 Deployment에나 `extraEnv`로 env를 더할 수 있다. Secret에서 오는 값(`DATABASE_URL`, `EGRESS_AUTHORIZER_TOKEN`, AWS key, 카탈로그 credential)은 [Kubernetes 설치 (Helm chart)의 준비 절](/run-server/self-hosting/kubernetes)의 표에 있다.

## probe

| 구성요소 | readiness | liveness | startup |
| --- | --- | --- | --- |
| api | `GET /readyz` | `GET /healthz` | `GET /healthz`(5초 × 24) |
| scheduler | `bun run apps/control-host/src/main.ts scheduler --health` | 같음 | 같음. 실패 허용 횟수는 `(intervalSec + passTimeoutSec + 39) / 10` |
| reconciler | `bun run apps/control-host/src/main.ts reconciler --health` | 같음 | scheduler와 같은 식 |
| slack | `bun run apps/control-host/src/main.ts slack --health` | 같음 | scheduler와 같은 식 |
| egress-proxy | `bun run /app/src/healthcheck.ts` | 같음 | 없음 |

`/healthz`는 HTTP를 받는지만 보고 DB를 보지 않는다. 그래서 liveness에 쓰고, DB·schema·설정을 보는 `/readyz`는 readiness에만 쓴다. DB가 잠시 끊겨도 api Pod는 재시작되지 않고 트래픽에서만 빠진다. `/livez`는 없다. scheduler·reconciler·slack의 `--health`는 loop가 쓰는 status file을 읽고, 직전 pass가 실패했거나 기한을 넘겼거나, `SCHEDULER_HEALTH_STALE_SEC`·`RECONCILER_HEALTH_STALE_SEC`·`SLACK_ROLE_HEALTH_STALE_SEC` 안에 끝난 pass가 없으면 실패한다. startup probe는 첫 pass가 끝날 때까지 기다린다.

| `EGRESS_AUTHORIZER_TOKEN` | api, egress-proxy(같은 값) |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | api, checkpoint GC, session archive CronJob. `secrets.objectStoreKeys: true`일 때만. `false`면 AWS 기본 credential chain(IRSA)으로 서명한다 |
| `PLATFORM_SECRET_KEY` | api, slack. 필수. 64자 hex master key. 콘솔에서 저장한 자격 증명을 봉인한다. Secret에 없으면 Pod가 뜨지 않는다 |

master key는 `PLATFORM_SECRET_KEY` 대신, 키를 담은 파일의 경로를 `PLATFORM_SECRET_KEY_FILE`로 줄 수 있다(compose secret처럼 마운트한 파일, 끝의 줄바꿈 하나는 무시한다). 둘 중 하나만 둔다. 둘 다 있으면 같은 키여야 하고, 다르면 api와 slack 역할이 기동을 거부한다(`master_key_mismatch`). 둘 다 없거나 파일을 읽지 못하면 `master_key_missing`이다. 컨테이너 안에서 운영자 명령을 돌릴 때는 그 명령의 환경에도 둘 중 하나가 있어야 한다. entrypoint가 서버 프로세스에만 키를 넘기는 구성에서는 `docker compose exec`로 띄운 명령이 키를 받지 못하므로, 서비스 env에 `PLATFORM_SECRET_KEY_FILE`을 둔다. 로컬 스택의 `scripts/local.sh up`은 api가 `PLATFORM_SECRET_KEY_FILE`을 받으면 키를 만들지 않고 `PLATFORM_SECRET_KEY`를 빈 값으로 넘긴다. `infra/compose.local.yml`의 개발용 기본 키는 셸에 이 변수가 아예 없을 때만 들어가므로, `local.sh` 없이 `docker compose`로 띄울 때는 셸에 `PLATFORM_SECRET_KEY=`(빈 값)를 둔다.

모델 연결·MCP 서버·저장소 GitHub App key는 Secret이나 환경 변수로 주지 않는다. 콘솔(또는 credential API)에서 넣고 DB에 `PLATFORM_SECRET_KEY`로 암호화돼 저장된다. `secrets.catalogEnv`와 `config.aws.secretsManagerEndpointUrl`은 없어졌고, values에 남아 있으면 렌더링이 실패한다. `secrets.bootstrapToken`도 없어졌고, 남아 있으면 렌더링이 실패한다. 첫 owner는 api Pod에서 `bun run apps/control-host/src/main.ts admin bootstrap-owner --email <owner-email> --out <file>`이 파일에 쓰는 일회용 설정 링크로 만든다. 링크는 DB에 있으므로 replica 수와 관계없이 통한다.

| 값 | 무엇을 바꾸나 |
|---|---|
| `images.registry`, `images.*.digest` | ECR host와 그 이미지의 digest |
| `secrets.objectStoreKeys: false`, `serviceAccounts.api.annotations` | 정적 AWS key 대신 IRSA. api, checkpoint GC, session archive CronJob이 api ServiceAccount의 이 role로 S3에 서명한다. scheduler와 worker는 S3 권한이 없다 |
| `secrets.externalSecret` | External Secrets Operator가 Secrets Manager의 `remoteKey`(JSON, 위 Secret 키 전부. IRSA면 AWS key 둘은 뺀다)로 Secret을 쓴다. 운영자 CRD가 필요하다 |
| `ingress` | ALB Ingress. `scheme`은 `internal`이다(위). `healthcheck-path: /readyz`, SSE를 위해 idle timeout 300초. 공개 경로(`/v1`·`/docs`·`/healthz`·`/readyz`)만 route하고 `/internal`과 authorizer(3100)는 열지 않는다 |
| `ingress.console.enabled` | 기본 `false`. 켜면 웹 콘솔 `/`와 `/internal` 404 규칙을 더한다. 켜는 조건은 [접속 경로](/run-server/self-hosting/access) |
| `config.egress.credentialAllowlist` | 값이 기본값을 통째로 대체하므로 GitHub·checkpoint bucket host를 넣을 때 provider와 패키지 registry 등 필요한 항목을 모두 다시 적는다. worker의 checkpoint upload·restore가 credential route로 나간다 |
| `worker.storageClass`, `worker.nodeSelector`, `worker.tolerations` | worker 전용 node group과 workspace PVC의 StorageClass(gp3) |
| `networkPolicy.enabled` | VPC CNI의 network policy agent가 켜져 있어야 효력이 있다 |

정적 S3 key를 써야 하면 `secrets.objectStoreKeys: true`로 두고 Secret에 AWS key 둘을 넣는다. 둘 다 있으면 정적 key가 IRSA보다 우선한다.

## 사용량과 비용 계측

- 세션 비용은 credential route가 센다. proxy는 2xx `/v1/messages` 응답(JSON과 SSE 모두)에서 usage를 읽는다. 응답이 끝나거나 끊기면 authorizer listener의 `POST /usage`로 보고한다. `count_tokens`와 오류 응답은 세지 않는다.
  - 응답이 usage를 다 말하지 않으면 많게 추정한다. `message_stop` 전에 끊긴 stream은 전달한 content 한 글자를 token 하나로 쳐서 output에 넣고, 전달한 web search 결과 블록 하나를 검색 한 번으로 친다. usage를 읽지 못한 JSON 응답(끊김, 8 MiB 초과, JSON 아님)은 요청으로 센다. 요청 1 byte를 input token 하나로, `max_tokens`를 output 전부로 본다. 이런 호출은 proxy가 `Provider usage estimated` 경고를 남기고 ledger에 `estimated=true`로 적힌다.
  - API는 가격표로 USD를 구해 micro-dollar 단위로 올림한다. 그 금액을 `provider_usage`에 교환 하나당 한 줄로 쓰고, 같은 트랜잭션에서 세션 비용에 더한다. 그래서 ledger 합과 세션 비용이 맞는다.
  - engine의 호출과 도구가 engine의 token으로 직접 부른 호출을 똑같이 센다.
  - 보고에는 proxy가 교환마다 만든 id가 붙는다. authorizer가 답하지 못하면 1·5·15초 뒤에 다시 보내고, 같은 id는 한 번만 센다. 끝내 보고하지 못하면 proxy가 `Provider usage went unreported` 오류 로그를 남기고 그 교환은 세지 않는다.
- turn 종료 때 SDK가 알려 준 `total_cost_usd` 증분은 turn 결과(`cost_usd`)에만 남고 세션 비용에는 더하지 않는다. engine의 turn별 `maxBudgetUsd`는 그대로 SDK 값으로 판정한다. proxy 계측 전에 만든 세션은 그때까지 SDK 값을 더한 비용을 이어받는다.
- 가격표는 플랫폼 코드가 소유한다. 모델 id별로 input, output, cache write(5분 1.25배, 1시간 2배), cache read 단가를 둔다. 항목마다 [공식 단가](https://platform.claude.com/docs/en/about-claude/pricing)를 확인한 날짜가 있다. 모델이 추가되거나 가격이 바뀌면 릴리스와 함께 고친다.
  - fast mode는 모델의 표준 단가에 fast 배수를 곱해 센다. 지금은 Fable 5.2·Mythos 5.2($16/$80), Opus 5.5($8/$40), Opus 5·Opus 4.8($10/$50)만 있다. cache 배수는 fast 단가 위에 그대로 곱한다. speed는 응답의 `usage.speed`를 따르고, 응답이 말하지 않으면 요청의 `speed`를 따른다. 둘 다 없으면 `standard`다.
  - Claude 표에 있는 모델의 `fast` 응답에 fast 배수가 없거나 speed가 이름이 아닌 값이면, 모델 자기 단가(긴 prompt 단가 포함)에 두 표를 통틀어 가장 큰 배수(지금 6배, OpenAI의 Ultrafast)를 곱해 센다. OpenAI 표가 항목에 없는 단계를 세는 방식과 같고, ledger에는 `priced_by=table`로 적힌다.
  - 어느 표에도 없는 모델은 릴리스에 담긴 LiteLLM 단가 snapshot에서 이름을 찾는다. 있으면 그 단가로 세고 ledger에 `priced_by=litellm`으로 적는다. snapshot은 실행 중에 받아 오지 않는다. 거기에도 없으면 단가 미상이고, 그 호출에는 금액을 붙이지 않는다. 다른 모델의 단가(최고 단가 포함)를 대신 쓰지 않고, 세션 비용·비용 상한·예산 계정에 아무것도 더하지 않는다. authorizer가 `Provider usage has no known price` 경고를 남기고, ledger에는 `priced_by=unknown`, `cost_usd=0`으로 적힌다. 이 0은 금액이 없다는 표시이지 0달러라는 뜻이 아니다(이 값이 생기기 전의 릴리스는 이런 호출을 최고 단가로 세고 `fallback`으로 적었다. 그 행은 그대로 남는다). 표가 이름을 아는 모델이 자기 항목의 범위를 벗어난 호출(4.6 이전 Claude 모델의 200K 초과, 긴 문맥 단가가 표에 없는 OpenAI 모델의 272K 초과)도 snapshot을 보지 않고 단가 미상이다. 요청한 모델과 답이 말한 모델이 다르고 둘 다 단가를 알면 둘 가운데 비싼 쪽으로 센다. 둘 중 하나라도 단가 미상이면 그 호출은 단가 미상이고 금액이 없다. 단가 미상 호출의 토큰은 세션마다 따로 더해 [단가 미상 토큰 상한](#웹에서-정하는-실행-한도)으로 막는다. 호출을 열 때의 예약도 같은 규칙을 따른다. 단가 미상 모델의 예약은 금액을 잡지 않고 토큰만 센다. 요청한 모델의 단가를 알면 그 금액으로 예약하고, 답이 단가 미상 모델을 대면 정산 때 금액 없이 예약을 돌려준다. snapshot의 단가로 세는 모델은 OpenAI 호출일 수 있다. 그래서 speed가 `standard`가 아니면 그 단가에 OpenAI 표가 그 단계에 둔 가장 큰 배수를 곱한다. `fast`는 2.5배, 그 밖의 단계는 6배다. snapshot이 cache write 단가를 주지 않으면 input 단가의 1.25배, 오래 유지하는 write는 2.5배(OpenAI의 12시간 write)로 센다. Claude 표에 이름이 있는 모델은 이 배수 대신 자기 fast 배수나 위의 가장 큰 배수, 그리고 Claude의 cache write 배수를 쓴다.
  - OpenAI 모델은 따로 둔 OpenAI 단가표로 센다. 항목마다 [공식 단가](https://developers.openai.com/api/docs/pricing)를 확인한 날짜가 있다. speed 단계는 모델의 표준 단가에 배수를 곱한다. `fast`는 대부분 2배이고 `gpt-5.5`는 2.5배다. Ultrafast(`ultrafast`)는 `gpt-6-astra`와 `gpt-6.1-sol`에만 있고 6배다. 모델의 항목에 없는 단계는 이름과 상관없이 표가 아는 가장 큰 배수(6배)로 센다. Pro 모델(`gpt-5.5-pro`, `gpt-5.4-pro`, `gpt-5.2-pro`, `gpt-5-pro`, `o3-pro`)은 cache 할인이 없어 cache read도 input 단가로 센다. 긴 문맥 단가가 표에 없는 모델(Pro 모델 포함)의 272K 초과 호출은 단가 미상이다.
  - 응답 `usage.server_tool_use`의 web search 한 번마다 $0.01(1,000회 $10)을 더한다. web fetch는 token 말고 요금이 없다. code execution은 더하지 않는다. web search·web fetch와 함께 쓰면 요금이 없고, 아니면 호출 수가 아니라 컨테이너 시간으로 과금되며 조직 무료 시간이 있기 때문이다. 세 횟수와 speed는 ledger(`provider_usage`)에 함께 적힌다.
  - 4.6 이후 모델은 US 전용 추론(`inference_geo: "us"`)이면 token 단가 전부(fast·cache 포함)에 1.1배를 곱한다. web search 요금에는 곱하지 않는다. geo는 응답의 `usage.inference_geo`를 따르고, 응답이 말하지 않으면 요청의 `inference_geo`를 따른다. 둘 다 없으면 `unknown`이다. workspace 기본값이 `us`일 수 있어서다. `global`과 `us`가 아닌 값은 모델 자기 단가에 가장 큰 geo 배수(1.1배)를 곱해 센다(`priced_by=table`). snapshot의 단가로 세는 모델에도 같은 geo 배수를 곱한다. geo는 ledger에 `inference_geo`로 적힌다. `inference_geo`를 모르는 옛 API는 이 필드가 붙은 보고를 `400`으로 거절하고, proxy는 그 교환을 세지 못한다(`Provider usage went unreported`). 그래서 API(migration 포함)를 egress proxy보다 먼저 올려야 한다. 실행 순서는 [Compose 업그레이드](/run-server/self-hosting/upgrade-compose#2-api--proxy--worker-순서)와 [Kubernetes 업그레이드](/run-server/self-hosting/upgrade-kubernetes#1-대상-chart와-제어-영역-우선-교체)를 따른다. 새 API는 이 필드가 없는 옛 proxy의 보고도 받는다.
  - 4.6 이전 모델(Opus 4.5·4, Sonnet 4.5·4, Haiku 4.5)은 `inference_geo`를 받지 않으므로 geo와 상관없이 표준 단가로 센다. 이 모델들의 창은 200K이고 공개된 long-context 단가가 없다. 그래서 input·cache write·cache read 합이 200K를 넘는 호출은 단가 미상이고 금액이 없다(`priced_by=unknown`). 4.6 이후 모델은 1M 전체가 표준 단가다. Haiku 5.5만 prompt(input·cache write·cache read 합)가 100K를 넘으면 모든 부분을 더 높은 단가($0.50/$2.50, cache read $0.05)로 센다.
  - batch는 credential route가 `/v1/messages/batches`를 열지 않아서 해당이 없다.
- 토큰 상한은 `provider_usage` 한 줄의 `input_tokens + cache_creation_input_tokens + cache_read_input_tokens + output_tokens`를 `sessions.provider_tokens`에 더해 센다. 더하는 일은 `provider_usage` insert trigger가 같은 트랜잭션에서 한다. 그래서 rollout 중이나 롤백 뒤에 0127 이전 API가 기록한 호출도 빠지지 않는다. cache read도 모델이 처리한 token이라 센다. 많게 추정한 보고는 추정치 그대로 더한다. 이 누계를 더한 migration은 기존 세션의 값을 `provider_usage` 합으로 채운다. 그 전에 SDK 값으로만 비용을 셌던 세션의 token은 채울 수 없다. 누계는 2^53-1(`Number.MAX_SAFE_INTEGER`)에서 멈춘다(migration 0129). trigger는 numeric으로 더하므로 비정상적으로 큰 token 값이 와도 오류로 usage 기록과 비용을 되돌리지 않는다.
  - SDK에는 token 예산 옵션이 없다. 그래서 turn 도중의 토큰 상한은 아래 egress 거절과 재인가만 맡는다. 상한에 닿은 뒤 열린 Messages 호출은 거절되어 turn이 `failed(budget_exceeded)`로 끝나고, 다음 turn부터는 `BUDGET_EXCEEDED`로 dispatch되지 않는다. proxy는 authorizer의 `BUDGET_EXCEEDED` 거절을 Messages 오류 형식(`message`가 `BUDGET_EXCEEDED:`로 시작)으로 전한다. 사유는 이 문구로 정하지 않는다. 엔진은 이 403을 `api_error`로 보고하고, 재인가에서 끊긴 교환도 재시도가 남지 않았으면(`PROVIDER_MAX_RETRIES=0`) 끊긴 연결 그대로 `api_error`로 보고한다. finalize는 `api_error`로 끝난 turn의 세션이 이미 상한을 넘었으면 사유를 `budget_exceeded`로, receipt 오류를 `BUDGET_EXCEEDED`로 기록하고, 엔진의 provider 진단(`provider_error`)은 비운다. 상한 아래에서 난 403은 `api_error`로 남는다.
- 비용 상한과 토큰 상한은 호출이 끝난 뒤에 판정한다. 동시에 열린 호출은 모두 인가를 통과할 수 있고, 진행 중인 turn은 상한을 넘을 수 있다.
- 누적 비용이나 누적 token이 상한 이상인 세션의 provider egress token은 authorizer가 403 `BUDGET_EXCEEDED`로 거절한다. 새 provider 교환은 곧바로 거절되고, 이미 열린 교환은 다음 재인가(30초 주기)에서 끊긴다. repository·object store route는 거절하지 않는다.

## 트레이스 내보내기

API만 읽는 설정이다. 기본은 꺼짐이고, 키를 하나도 주지 않으면 span을 만들지도 보내지도 않는다. 켜면 로그의 `trace_id`·`span_id`가 활성 span 안에서 찍힌다. 수집기는 OTLP/HTTP(protobuf)를 받으면 어느 것이든 된다. 예제 수집기는 [관측](/observability)에 있다.

| 키 | 기본값 | 뜻 |
|---|---|---|
| `OTEL_TRACES_EXPORTER` | `none` | `none` 또는 `otlp` |
| `OTEL_EXPORTER_OTLP_ENDPOINT` / `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | 없음 | 수집기 주소. 앞의 것은 뒤에 `/v1/traces`를 붙이고, 뒤의 것은 그대로 쓴다. `otlp`인데 둘 다 없으면 기동하지 않는다 |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | `http/protobuf` | 이 값만 받는다 |
| `OTEL_EXPORTER_OTLP_HEADERS` / `OTEL_EXPORTER_OTLP_TRACES_HEADERS` | 없음 | `키=값,키=값`(값은 퍼센트 인코딩, 출력 가능한 ASCII만). 같은 이름이면 뒤의 것이 이긴다. 모양이 틀리면 기동하지 않는다. 비밀이므로 env 파일로만 주고, 값은 로그와 오류 메시지에 나오지 않는다 |
| `OTEL_SERVICE_NAME` | `werft-api` | 서비스 이름 |
| `OTEL_TRACES_SAMPLER` / `OTEL_TRACES_SAMPLER_ARG` | `always_on` / `1.0` | `always_on`, `always_off`, `traceidratio`(비율 0~1) |
| `TRACE_TENANT_HEADER` | 없음 | `<헤더 이름>: <값 틀>`. 값 틀의 `{workspace_id}`를 워크스페이스 id로 바꿔 batch마다 붙인다 |
| `TRACE_INSTALL_TENANT` | 없음 | 워크스페이스가 없는 span의 테넌트 값 |
| `TRACE_TENANT_HEADERS_FILE` | 없음 | 워크스페이스별 헤더를 담은 JSON 파일. mode 600이 아니면 기동하지 않는다. 같은 헤더 이름이면 이 파일이 `TRACE_TENANT_HEADER`와 `OTEL_EXPORTER_OTLP_HEADERS`를 이긴다 |
| `TRACE_INGEST_URL` | 없음 | worker가 span을 보내는 API의 ingest 주소(`http`·`https`). `otlp`인데 없으면 기동하지 않는다 |
| `TRACE_CONTENT_MODE` / `TRACE_CONTENT_MAX_BYTES` | `full` / `32768` | 프롬프트·답변·도구 입출력을 span에 싣는지(`full`·`metadata`)와 내용 속성 하나의 바이트 상한. 설치 전체에 하나만 적용된다 |
| `TRACE_INGEST_PORT` / `TRACE_INGEST_MAX_REQUEST_BYTES` / `TRACE_INGEST_MAX_BYTES_PER_MIN` / `TRACE_MAX_BYTES_PER_TRACE` / `TRACE_FENCED_GRACE_SEC` | `4319` / 4 MiB / 32 MiB / 20 MiB / `300` | ingest listener의 포트와 상한. 0·음수·숫자가 아닌 값이면 키 이름을 밝히고 기동하지 않는다 |

`TRACE_TENANT_HEADERS_FILE`의 형식이다. 값은 비밀이므로 저장소에 두지 않는다.

```json
{ "<workspace_id>": { "<header name>": "<secret value>" } }
```

**켜는 최소 설정.** 아래 값을 api의 env에 준다. 프롬프트·답변·도구 입출력은 span 속성(`gen_ai.*`)에 실리므로 로그 저장소가 따로 필요 없다.

```bash
OTEL_TRACES_EXPORTER=otlp
OTEL_EXPORTER_OTLP_ENDPOINT=https://otel-collector.example.com:4318
TRACE_INGEST_URL=http://api:4319
EGRESS_PRIVATE_ALLOWLIST=api:3200,host.docker.internal:3200,api:4319
```

- **Compose.** 위 값을 compose를 띄우는 셸이나 `.env`에 두면 api 컨테이너에 같은 이름으로 넘어간다. worker가 ingest로 가는 길도 egress proxy를 지나므로 `EGRESS_PRIVATE_ALLOWLIST`의 기본값 `api:3200,host.docker.internal:3200`에 `api:<TRACE_INGEST_PORT>`를 더한다.
- **Kubernetes.** 키는 `api.extraEnv`에 준다. 포트는 Service와 NetworkPolicy도 알아야 하므로 `config.tracing.ingestPort`(기본 `4319`)로만 바꾸고 `TRACE_INGEST_PORT`는 주지 않는다. `TRACE_INGEST_URL`은 `http://<api Service 이름>:4319`이고, `config.egress.privateAllowlist`를 `<api Service 이름>-internal:3200,<api Service 이름>:4319`로 지정한다.
- worker는 수집기로 직접 가지 않는다. 수집기 host를 `EGRESS_PRIVATE_ALLOWLIST`나 `EGRESS_ALLOWLIST`에 넣으면 api가 기동할 때 경고를 남긴다. `OTEL_*` 키는 worker와 엔진에 넘어가지 않는다.

**수집기 쪽 조건.**

- 트레이스 하나의 크기 상한을 `TRACE_MAX_BYTES_PER_TRACE`보다 크게 둔다. 작으면 수집기가 큰 트레이스를 버린다.
- 테넌트 헤더를 정하지 않은 설치에서는 모든 워크스페이스의 트레이스가 한곳에 모인다. 수집 백엔드의 화면은 운영자만 보게 한다.
- `TRACE_CONTENT_MODE=full`이면 프롬프트·답변·도구 입출력이 수집기로 간다. 내보내지 않으려면 `metadata`로 둔다.

**span.** `/v1/**` 요청마다 `{METHOD} {route_template}` span(예: `POST /v1/sessions/:id/turns`)이 새 root로 생긴다. 클라이언트가 보낸 `traceparent`는 부모가 아니라 link로만 남고, 그 sampled 플래그는 따르지 않는다. 헬스·지표 경로에는 span이 없다. turn의 span은 세션과 turn 번호로 정한 별도 트레이스(root `werft.turn`)에 달리고, turn을 큐에 넣은 요청의 span과 앞 turn의 root는 link로 이어진다. worker gateway 호출은 그 turn 트레이스의 `traceparent`를 실었을 때만 그 아래 자식 span이 되고, 그 밖의 gateway 호출(heartbeat, long poll 등)에는 span이 없다.

## 세션 제목 생성

세션을 만들 때 `title`이 없으면 첫 메시지를 80자에서 자른 값이 제목이 된다. 첫 turn이 `completed`로 끝나면 API가 그 turn의 메시지와 답으로 짧은 제목을 한 번 받아 바꾼다.

| 변수 | 기본값 | 허용 범위 |
|---|---|---|
| `SESSION_TITLE_EGRESS_URL` | compose `http://egress-proxy:3129` | egress proxy의 credential route 주소. 비우면 이 기능이 꺼진다. Codex 연결(`openai_responses`)의 세션은 모델로 제목을 만들지 않고 첫 메시지에서 만든 제목을 그대로 둔다 |

- 호출은 세션의 연결과 모델로 provider route를 지나므로, 비용은 첫 turn의 usage와 세션 상한에 들어간다. proxy는 `/v1/messages`, 세션의 모델, `max_tokens` 64 이하인 요청만 보낸다.
- API는 이 URL의 host:port에만 보내고(메타데이터·link-local 주소는 거절), redirect는 따라가지 않으며 25초 뒤 끊는다.
- 사용자가 준 제목이나 `PATCH /v1/sessions/{id}`로 바꾼 제목은 덮어쓰지 않는다. 호출이 실패하거나 답이 비면 첫 메시지 제목이 남는다.

## 대화 런타임

대화 런타임은 worker 이미지를 대화용 진입점(`apps/worker/src/conversation/main.ts`)으로 띄운 process 하나다. 설치 안 모든 에이전트의 대화 턴을 함께 돌린다. 기본은 꺼져 있고, 시험 스택에서만 켠다. 턴은 두 길로 시작한다. 하나는 운영자가 api 컨테이너에서 `bun run apps/control-host/src/api/conversation-turn.ts`를 돌리는 것이다. 다른 하나는 에이전트의 대화 rollout이 `on`일 때 Slack 채널에서 그 에이전트를 멘션하거나 그 에이전트에게 DM을 보내는 것이다. rollout `on`은 아직 API로 고를 수 없다.

- 멘션 하나가 그 스레드(맨 위 글이면 그 글)의 턴 하나가 된다. 요청자와 예산 root는 멘션한 사람이다. api가 연결된 계정으로 기록한 사람이며, 글에 적힌 이름은 쓰지 않는다. 모델의 지시는 그 사람의 이번 글뿐이고, 주제의 기록은 자료로 따로 싣는다. 같은 글의 이벤트가 다시 와도 턴은 하나다. 결정이 답하기(`reply`)면 slack 역할의 pass가 그 답을 그 스레드에 한 번 올린다. 맨 위 글을 멘션했으면 그 글의 스레드다. 보낼 채널과 스레드는 턴 기록에서 정하고, 모델이 적은 채널은 쓰지 않는다. 답은 에이전트 이름으로 가고, 끝에 작은 회색 줄 `AI 에이전트 · Werft · <이름> 님 요청`이 붙는다(이름은 요청자의 Werft 이름이고, 읽지 못하면 뺀다). 보내기 전에 그 턴의 출처 글이 지워지면 답은 나가지 않는다. 답하기·새 작업 만들기·열린 작업에 넘기기로 끝나면 그 멘션 글에 👀 하나를 단다(조용히 있기와 결정 없음에는 달지 않는다). 앱에 `reactions:write`가 없으면 달지 않고 답은 그대로 나간다. 새 작업 만들기(`spawn_task`)로 끝나면 slack 역할의 pass가 그 대화를 부모로 하는 작업 세션을 하나 열고 그 스레드에 묶는다. 작업의 요청 원문은 서버가 받은 그 멘션 글이고, 모델이 적은 목표와 완료 조건은 해석으로만 남는다. 이때 멘션을 판정한 Slack 주체로 `task.spawn`을 다시 판정한다. 거절되면 요청자에게만 보이는 한 줄을 보내고, 그 줄을 보내지 못하면 스레드에 이유 없는 한 줄을 올린다. 대화 하나에 열린 작업이 3개, 에이전트 하나에 10개면 새 작업을 열지 않고 그 이유를 스레드에 올린다. 에이전트가 쓸 수 없는 저장소를 고른 경우도 그렇다. 작업이 열리면 따로 답하지 않고, 모델이 쓴 글도 올리지 않는다. 판정 전에 출처 글이 지워지면 작업도 줄도 없다. 큐는 이 턴의 입력만 봉인해 작업이 정해질 때까지, 길어야 1시간 둔다. 그 뒤에는 지우고 작업은 실패로 기록한다. 열린 작업에 넘기기(`route_to_task`)로 끝나면 slack 역할의 pass가 서버가 받은 그 멘션 글을 그 작업의 입력으로 넣는다. 새 작업은 만들지 않고, 작업이 실행 중이면 그 뒤에 줄을 선다. 대상은 다시 확인한다: 같은 대화(같은 채널)의 열린 작업이어야 하고, 글쓴이가 그 작업에 `session.submit` 권한이 있어야 한다. 넘긴 입력의 요청자는 글쓴이다. 다른 대화의 작업이거나 닫힌 작업이면 넘기지 않고 스레드에 이유 없는 한 줄을 올린다. 권한이 없으면 요청자에게만 보이는 한 줄을 보내고, 보내지 못하면 스레드에 한 줄을 올린다. 다른 스레드에서 넘겼으면 그 스레드는 그 작업을 가리키게 되고, 거기에 "원래 스레드에서 이어서 할게요 ↗"와 원래 스레드 링크 한 줄을 단다. 가리키는 작업이 바뀔 때만 다시 단다. 작업 보고는 작업의 스레드에만 간다. 그 스레드에 또 멘션이 오면 대화가 다시 판단한다. 넘긴 입력과 안내 줄은 턴의 출처를 모두 실어, 그중 하나가 지워지면 나가지 않는다. 판정 전에 출처 글이 지워지면 넘기지도 말하지도 않는다. 넘길 입력은 큐가 길어야 1시간 둔다. 멘션 턴은 M1의 채널당 시간 판단 수에 세지 않는다.
- 대화 rollout이 `on`이면 에이전트 이름으로 올라가는 다른 글도 같은 줄로 끝난다(작업 보고, 실패 안내, 승인·질문 카드와 그것을 다시 그린 글, 거절 안내, 환영 글, 채널 고지, push·PR 결과, 모델 안내, 진행 메시지). `<이름> 님 요청`은 한 턴의 결과나 요청인 글에만 붙는다. 작업 보고, 그 턴의 실패 안내와 예산 거절 안내, 카드, push·PR 결과다. 이름은 그 턴을 보낸(push는 요청한) 사람의 Werft 이름이고, 읽지 못하면 뺀다. 사람의 이름으로 올라가는 웹·API 입력과 👀에는 붙지 않는다. 버튼을 누른 사람에게만 보이는 답에도 붙지 않는다. 줄은 보낼 때의 rollout을 따르고, `off`·`shadow`에서는 붙지 않는다.
- 턴이 도는 동안 slack 역할이 그 스레드의 상태를 "처리 중"으로 둔다. 턴이 어떻게 끝나든 slack 역할의 pass가 턴을 끝내고 상태를 `active`로 한 번 되돌린다. 결정, 결정 없음, 상한, 실패, 예산 거절, 아무도 가져가지 않은 턴, 시간 초과가 모두 그렇다. 큐가 끝내지 않은 턴은 permit이 끝나는 때(가져갈 시간 30초와 lease)에 시간 초과로 끝낸다. 같은 스레드에 더 새로운 턴이 돌고 있으면 상태는 그대로 둔다. 앞 턴의 `active`를 보내는 사이에 새 턴이 쓰였으면 "처리 중"을 다시 보낸다. 관리자가 턴이 도는 중에 대화 기록을 지우면 그 스레드를 `active`로 되돌린다. 이 두 경우는 보낼 때 그 스레드의 턴을 다시 읽어, 아직 도는 턴이 있으면 "처리 중", 없으면 `active`를 보낸다. Slack이 받지 않은 되돌리기는 다음 pass가 다시 보낸다. 보내던 pass가 도중에 멈추면 pass 시간 제한이 지난 뒤의 pass가 보낸다.
- rollout `on`이어도 채널의 듣기 설정이 `off`이거나, 에이전트가 비활성이거나, 채널이 보관되었거나 승인을 기다리면 멘션은 턴이 되지 않고 버려진다. 글이 턴 입력의 한도(16,000자)보다 길 때도 그렇다. 작업이 묶인 스레드의 멘션은 지금처럼 그 작업 세션으로 간다. `off`와 `shadow`에서는 멘션이 지금처럼 세션을 연다.
- DM도 멘션처럼 턴이 된다. DM 글 하나가 그 스레드(맨 위 글이면 그 글)의 턴 하나가 되고, 그 사람의 DM 대화에 속한다. 맨 위 DM 글마다 주제가 따로 생기므로, 한 사람의 DM 전체가 한 세션이나 한 주제로 묶이지 않는다. 요청자와 예산 root는 DM을 보낸 사람이다. 에이전트가 비활성이거나 DM 설정이 꺼져 있으면 DM은 턴이 되지 않고 버려진다. 작업이 묶인 DM 스레드의 글은 지금처럼 그 작업 세션으로 간다. `off`와 `shadow`에서는 DM이 지금처럼 세션을 연다. Slack의 `assistant_thread_started` 이벤트는 구독하지 않으며, DM은 `message.im`만으로 받는다.

- 런타임은 provider 키를 갖지 않는다. 턴마다 호출 허가를 받아 egress proxy의 credential route로 보내고, proxy가 키를 붙인다. 한 턴은 provider를 8번까지 부른다. 도구 결과를 받은 뒤의 호출도 하나씩 센다.
- workspace volume과 저장소 checkout이 없다. 엔진의 내장 도구는 모두 막는다. 엔진이 부를 수 있는 것은 아래 읽기 도구 넷과 결정 도구뿐이다. 목록에 없는 도구는 엔진에 실리지 않고, 불러도 실행되지 않는다.
- 읽기 도구: 인자를 받지 않는다. 무엇을 읽을지는 api가 턴의 lease로 정한다. 그 턴의 대화 밖은 읽지 않는다.
  - `read_thread`: 지금 주제의 Slack 스레드를 첫 글부터 50개까지 읽는다(`conversations.replies`). 앱이 이미 가진 history 범위를 쓰므로 Slack 앱을 다시 설치하지 않아도 된다. 한 턴에 2번까지다. Slack이 429로 답하면 그 턴에서는 다시 부르지 않고, 턴은 요약과 턴 기록으로 이어 간다. 다른 조직과 공유한 채널에서는 거절된다. 게스트, 다른 조직 사람, 작성자를 확인하지 못한 글은 모델에 가기 전에 빼고 뺀 수만 알린다. 지워진 글도 뺀다.
  - `read_channel_summary`: 대화 채널의 요약 줄. 출처 글이 지워진 줄은 없다.
  - `read_turns`: 이 대화의 끝난 턴 20개(끝난 때, 결정과 이유, 답). 지워진 글이 들어간 턴은 뺀다.
  - `list_open_tasks`: 이 대화에서 시작해 아직 끝나지 않은 작업 20개(id, 이름, 상태, 시작 시각). 요청자가 사람이면 그 사람이 볼 수 있는 작업만 보인다. 요청자가 없는 턴(운영자 명령)은 사람에게만 공유한 작업을 보지 못한다.
  - 비공개 채널의 대화에서는 요청자가 지금 그 채널의 구성원이어야 한다. 아니거나 확인하지 못하면 거절된다.
  - 결과는 12 KiB까지이고, 지시가 아니라 데이터라는 문구가 앞에 붙는다. 읽은 글은 그 턴의 출처에 더해지고, 그 글이 지워지면 주제 세션을 버린다.
  - api는 턴마다 도구 호출을 세어 13번째를 거절한다. 그 턴은 `tool_call_limit`으로 끝나고, 지킨 쪽은 `server`로 남는다.
- 결정 도구: 턴은 결정 하나로 끝난다. `reply`(답하기: `body`, `reason`), `route_to_task`(열린 작업에 넘기기: `list_open_tasks`가 준 `task_id`, `reason`), `spawn_task`(새 작업 만들기: `goal`, `done_when`, 고를 때만 `repository`, `reason`), `no_reply`(조용히 있기: `reason`).
  - 요청자가 사람(웹 사용자, Slack 사용자)이거나 운영자 명령이면 넷 모두를, 다른 에이전트(Slack bot)이면 `reply`와 `no_reply`만 엔진에 싣는다. 요청자는 api가 기록한 값이고, 글 본문에 적힌 이름은 쓰지 않는다. api는 도구를 부를 때 다시 검사한다.
  - 결정 도구 호출도 읽기 도구와 함께 센다. api는 도구가 불린 그때 턴 기록에 결정과 이유를 쓴다. 턴의 첫 결정이 그 턴의 결정이고, 그 뒤의 도구 호출은 거절한다. 답의 본문은 `reply`의 것만 남는다. `route_to_task`의 `task_id`는 효과가 다시 확인하도록 턴에 남는다.
  - 결정을 쓰기 직전에 그 턴이 읽은 글이 지워졌는지 다시 본다. 지워졌으면 결정을 버리고 `voided_by_delete`로 남긴다. 결정 없이 끝난 턴(상한, 오류)은 `no_decision`이다.
  - 아직 결정은 효과가 없다. Slack에 올리지 않고, 작업을 만들거나 넘기지 않는다.
- 주제 세션: 주제(Slack 스레드 하나)마다 엔진 process 하나와 메모리 안 임시 디렉터리 하나를 둔다. 같은 주제의 다음 턴은 그 엔진에서 앞 대화를 이어 쓴다. 마지막 턴이 끝나고 10분 쉬면 세션을 버리고 디렉터리를 지운다. 그 뒤의 턴은 api가 조립한 맥락(채널 요약, 그 주제의 앞 답, 버퍼의 글)으로 새 엔진에서 시작한다. 엔진의 대화 압축과 이어 하기(resume)는 쓰지 않는다.
- api는 런타임이 턴을 가져갈 때마다 그 세션이 읽은 글이 지워졌는지 다시 본다. 지워졌거나 확인하지 못하면, 또 턴이 실패했거나 세션의 대화가 96 KiB를 넘으면 세션을 버리고 새로 시작한다. 런타임을 다시 띄우면 살아 있던 세션은 없다.
- 런타임 하나는 세션을 8개까지 둔다. 하나 더 열면 가장 오래 쉰 세션을 버린다. 한 턴을 마치고 쉬는 엔진 하나는 RSS 약 215 MiB다(macOS arm64에서 잰 값). chart의 메모리(`conversationRuntime.resources`)는 request와 limit 모두 2560Mi다. 엔진 8개, 런타임 loop, 주제 디렉터리 tmpfs(256Mi)와 여유를 더한 값이다.
- 런타임은 egress proxy만 만난다. DNS도 쓰지 않는다. API에는 forward proxy를 거쳐 다음 턴을 물어 오고, 런타임으로 들어오는 연결은 없다.
- 켜는 법: compose는 `infra/compose.conversation-runtime.yml`을 스택 위에 얹는다. Helm은 `conversationRuntime.enabled: true`로 두고 Secret에 `CONVERSATION_RUNTIME_TOKEN`을 넣는다. replica는 1이다.
- 턴은 지금 API process 하나의 메모리에 줄 선다. API를 다시 띄우면 줄 선 턴이 없어진다. API replica가 둘 이상이면, 런타임이 묻고 있지 않은 replica에서 돌린 운영자 명령은 `no_runtime`으로 거절된다. 같은 주제의 턴은 한 번에 하나만 돈다. 앞 턴이 끝날 때까지 다음 턴은 줄에서 기다리고, 받을 수 있는 시간(30초)은 앞 턴이 끝난 때부터 다시 센다. 세션을 이어 쓸지 판정하는 기록도 같은 process의 메모리에 있다.

| 변수 | 읽는 곳 | 기본값 | 허용 범위 |
|---|---|---|---|
| `CONVERSATION_RUNTIME_TOKEN` | api, 대화 런타임(같은 값) | 없음 | 최소 32자. 런타임의 네 route(`/internal/conversation-runtime/next-turn`, `/internal/conversation-runtime/turn-result`, `/internal/conversation-runtime/read-tool`, `/internal/conversation-runtime/decision-tool`)만 여는 bearer다. 다른 `/internal` route에 내면 403이다. api에 없으면 네 route와 운영자 명령이 꺼지고, 런타임에 없으면 런타임이 기동을 거부한다. ## 설정 문서 가져오기·내보내기

모델 연결·저장소는 DB 행이다. 콘솔에서 하나씩 다루거나 **설정 문서** 하나로 넣고 꺼낸다. 첫 배포의 migrate는 빈 설치에만 문서를 한 번 넣고, 그 뒤 배포는 문서를 읽지 않는다. 그 뒤에 문서로 더하려면 아래 명령으로 가져온다.

- **형식.** `{"version": 1, "connections": {…}, "repositories": {…}}`. `mcp_servers` 칸이 비어 있지 않은 문서는 문서 전체를 `400 BAD_REQUEST`(`reason_code: invalid_document`)로 거절하고, 오류에는 그 서버 이름과 "설치 카탈로그 MCP는 없어졌다" 안내만 보인다. 빈 칸(`{}`)이나 칸이 없는 문서는 받고, 내보내기는 그 칸을 쓰지 않는다. 자격 증명은 `"auth": {"stored": true}`로 적고, 값은 가져온 뒤 콘솔에서 넣는다. 값이 없는 행은 `needs_value`이고, 그 행을 쓰는 세션은 돌지 않는다. 내보내면 `{"stored": true, "last4": "…"}`만 나오고 값은 나오지 않는다. master key는 문서에 들어가지 않는다. `value_env`·`secret_id` 참조와 최상위 `profiles`는 거절한다.
- **가져오기는 더하기만 한다.** 항목마다 `add`(새 행), `unchanged`(같은 행), `inactive`(사용 중지한 행과 같은 id), `needs_value`로 나눈다. 같은 id인데 내용이 다르거나 같은 GitHub 저장소를 다른 id로 적으면 `conflicts`이고, 그러면 아무것도 쓰지 않는다. 행을 고치거나 지우지 않는다.
- **Compose.** `bun run settings export > settings.json`은 문서를 stdout에, `digest sha256:…`을 stderr에 낸다. 가져오기는 `bun run settings import --document - --dry-run < settings.json`으로 먼저 보고, `--dry-run`을 빼고 다시 돌린다. 명령은 api 컨테이너 안에서 돌므로 host의 파일은 `-`(stdin)로 넘긴다. 거절되면 1로 끝난다.
- **Kubernetes.** `bun run settings:k8s export`처럼 `settings:k8s`가 api Pod 안에서 같은 CLI를 돌린다.
- **API.** `GET /v1/installation/settings/export`는 `{document, digest}`를, `POST /v1/installation/settings/import?dry_run=true`는 판정 결과를 준다. 설치 owner의 로그인 세션만 부를 수 있고 API key는 `403`이다. 충돌은 `409 REVISION_CONFLICT`, 틀린 문서는 `400 BAD_REQUEST`다.
- **파일 카탈로그로 돌던 설치.** v0.1.0보다 앞선 파일 카탈로그를 가져오는 경로(`settings import|seed --from-dir`, migrate의 `/legacy-config` 마운트와 `PLATFORM_LEGACY_CONFIG_DIR`)는 없어졌다. 아직 파일 카탈로그로 도는 설치는 이 판보다 앞선 release로 먼저 올려 설정을 DB로 옮긴 뒤 올린다. `PLATFORM_CONFIG_DIR`·`SESSION_CATALOG_JSON`은 읽지 않으므로 남아 있어도 api가 뜬다. 정리하려면 지운다.
- **설치 카탈로그 MCP.** 설치 owner가 콘솔이나 설정 문서의 `mcp_servers`로 더하던 원격 MCP 서버는 migration `0304_retire_catalog_mcp`가 지운다. 카탈로그 행, 그 저장값, 에이전트의 카탈로그 선택이 지워지고, migrate 로그 `db.migrate.notice`에 지운 서버의 수와 이름이 남는다. 워크스페이스 MCP 서버로 옮기지 않으므로, 계속 쓸 서버는 올리기 전에 이름을 적어 두고 올린 뒤 워크스페이스 MCP 서버(설정 > 에이전트 연결 > **MCP 서버**)로 등록해 에이전트의 접근 탭에서 고른다. 새로 등록하는 이름으로 `github`·`browser`·`memory`는 쓸 수 없고(`memory`는 이미 있는 워크스페이스 서버면 그대로 둔다), 이름은 워크스페이스 안에서만 겹치지 않으면 된다. 그래서 카탈로그의 `memory` 서버는 다른 이름으로 등록한다. API가 시작할 때 카탈로그 서버를 적은 에이전트 초안은 그 서버(`capabilities.mcp`), 그 서버 도구의 `tool_policy.per_tool` 항목, 그 서버가 쓰던 `credential_ref`를 뺀 새 버전으로 옮겨진다(`forbidden`과 카드의 다른 이름은 남는다). 옮긴 것이 있으면 `Drafts naming a retired catalog MCP server reconciled` 로그에 그 수가 남는다. 이미 있는 release는 바뀌지 않고 다시 활성화할 수 있다. 옛 release의 세션은 그 서버 없이 돌고, 그 서버가 쓰던 credential 이름의 묶음을 풀어도 시작된다. 세션에는 "없어진 카탈로그 MCP `<이름>`은 건너뜀" 한 줄이 한 번 남는다. 그 서버를 넣고 찍은 checkpoint도 복원된다. 다만 복원 대안이 16개 찬 세션은 가장 오래된 대안 하나의 checkpoint를 복원하지 못할 수 있고, 그러면 API 로그에 `claim.retired_catalog_restore_dropped` 경고가 세션 id와 함께 남는다. rolling deploy 중 옛 replica가 카탈로그를 쓰면(가져오기·콘솔·카탈로그를 적은 카드 저장) DB가 거절하므로, 올리는 동안 카탈로그를 바꾸지 않는다.
- **되돌리기 하한.** 가져오기로 `auth_kind`가 `github_app_explicit`인 저장소 행을 쓴 DB는 `auth_kind`를 모르는 옛 이미지로 되돌리지 않는다. 옛 이미지는 그 행을 콘솔 GitHub App 저장소로 읽는다.
