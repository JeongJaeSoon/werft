## 作業内容

バックアップと互換性検査を経て、Compose 環境を新しい release へ更新します。checkpoint を失う承認は、影響セッションを正確に確認してからだけ行います。

<a id="준비물" />
## 準備

[変更履歴](https://github.com/JeongJaeSoon/werft/blob/main/CHANGELOG.md)で対象バージョンの運用者向け作業を先に読みます。

現在・対象の source commit、release 入力、settings digest、イメージ digest が必要です。直近の成功バックアップと復元訓練を確認し、利用者に停止を知らせます。

先に[共通の実行前ゲート](#실행-전-게이트)を確認します。

<a id="단계" />
## 手順

<a id="1-대상-입력과-백업" />
### 1. 対象入力とバックアップ

[パッケージ契約](/run-server/self-hosting/reference/packages)から対象タグを選び、[設置時の release 生成](/run-server/self-hosting/single-server#3-release-입력-생성)と同じ方法で checkout 外に release-new.json を作ります。生成前に対象 source commit を checkout し、`bun install --frozen-lockfile` を実行します。release の `source_commit` はこの checkout の HEAD でなければなりません。先に[バックアップ](/run-server/self-hosting/backup-and-restore)を実行します。

<a id="2-api--proxy--worker-순서" />
### 2. API → proxy → worker の順序

protocol または[実行前ゲート](#실행-전-게이트)のフィールドに変更があれば、全イメージを一度に変えません。先に新 source commit を checkout して依存関係をインストールし、対象 release の control_host だけを新イメージに変え、worker・egress_proxy は現在のままにした中間 release ファイルを作ります。同じ settings digest・source_commit 条件を守ります。中間 release で upgrade し、API が ready で全 API インスタンスが新バージョンになったことを確認します。

次に egress proxy と worker を対象 digest に変えた最終 release で upgrade します。これにより API より先に proxy・worker が新フィールドを送ることを防ぎます。test-ops 環境は中間・最終 release 入力をそれぞれ `scripts/test-ops.sh upgrade` で適用します。

プロファイル削除リリースへ更新するときは、この順序に従いません。中間 release なしで最終 release へ直接更新します。以前の worker が新しい control-host の応答を読めないためです（[プロファイル削除リリースのアップグレード順序](#프로필-제거-릴리스의-업그레이드-순서)）。

<a id="3-upgrade와-영향-세션" />
### 3. upgrade と影響セッション

手順 1 で対象 source commit・digest から作った `release-new.json` で `upgrade` を実行します。worker イメージが変われば新イメージで現在の checkpoint を検査し、非互換セッションがあれば終了コード 3 で拒否します。影響セッション id は `$TEST_OPS_STATE_DIR/upgrade-<timestamp>.sessions` に記録します。一覧を確認して利用者へ知らせ、正確にその id を含むファイルで `scripts/test-ops.sh upgrade release-new.json --approve-sessions approved.txt` を再実行します。一つでも違えば拒否し、続行時は状態ディレクトリに承認記録を残します。非互換セッションを `start_fresh` で復旧すると以前の checkpoint の context を失います。影響セッションがなければ承認なしで進みます。

upgrade 直前に一度[バックアップ](/run-server/self-hosting/backup-and-restore)を取ります。戻す操作も以前の release ファイルでの `upgrade` であり、worker イメージが再び変わるため同じ規則を適用します。

新 release 起動前に upgrade が停止した場合（例：scheduler の quota 検査失敗）、環境は停止したままで、状態ディレクトリに `pending.json` が残ります。この状態では `status`、`reset`、`pending.json` と同内容の release ファイルを使う `upgrade` だけを許可し、以前の release へ戻す `upgrade` を含む他のコマンドは拒否します。原因を直し、同じ対象 release ファイルで `upgrade` を再実行すると解消します。

upgrade ではなく `compose down` やホスト再起動で停止しただけなら、`upgrade`・`deploy` ではなく `scripts/test-ops.sh start` で同じ volume を使って再起動します（[停止](/run-server/self-hosting/stop-compose)）。`pending.json` があれば `start` は拒否します。

```bash
scripts/test-ops.sh upgrade release-new.json
```

`release-new.json` と承認ファイルは checkout 外の実際の絶対パスで渡します。対象 checkout の HEAD は release の source_commit と一致する必要があります。

<a id="확인" />
## 確認

status の適用 release、サービス health、ready を確認します。既存セッションを新 worker で再開し、context、最終 checkpoint、turn 完了を照合します。メトリクス名が変われば Datadog 定義・クエリ・フィルターと Prometheus ルールを新名に変更し、実際の series を確認します。

上書きした CSS 名も変更履歴の運用者作業と照合し、新名に変えます。以前のメトリクス・CSS 名に alias があるとは考えないでください。

<a id="자주-막히는-곳" />
## よくある問題

pending.json が残ると start と以前の release への upgrade は拒否されます。原因を直し、pending と同じ対象 release で再 upgrade します。影響セッション一覧が変わったら以前の承認ファイルは再利用しません。start_fresh は以前の context を破棄します。

<a id="되돌리기" />
## 元に戻す

以前の release の適用も、upgrade 検査と[実行前ゲート](#실행-전-게이트)の rollback 下限に従います。新 schema・checkpoint を知らないビルドへ、単にイメージタグだけを戻さないでください。新 release がまだ起動していない pending 失敗では以前の release は拒否されるため、同じ対象で復旧します。

## 実行前ゲート

アップグレードの前に、デプロイ済みのバージョンと対象バージョンの間の[変更履歴](https://github.com/JeongJaeSoon/werft/blob/main/CHANGELOG.md)をすべて読みます。その間のリリースの手順が下の[リリースごとの作業](#릴리스별-작업)にあれば、その手順にも従います。デプロイ時は [release manifest](/run-server/self-hosting/reference/packages#릴리스-manifest-읽기) の commit と三つの digest をあわせて確認します。

現在のロールバック下限は `v0.2.0` です。このリリースの migration `0270` がプロファイルのデータを消すため、それより前のイメージには戻しません([プロファイル削除のロールバック下限](#프로필-제거의-롤백-하한))。その後に変更履歴が戻せないと書いたリリースがあれば、そのリリースが下限です。下限より前に戻す必要があれば、アップグレード前のバックアップから DB を復元します。rollback を考える前に影響セッションを読み取り SQL で数え、データを失わずに roll-forward できるかを先に判断します。

新 control-host・直前 worker の組み合わせはデプロイ前に試験環境で確認します。セッションの turn 1 完了 → worker 削除 → checkpoint から turn 2 完了を確認し、API の worker 要求に 400 BAD_REQUEST がない必要があります。空環境の ready 200 で代替しません。まず turn 1 の完了を見ます。直前の worker が新しい control-host の応答を読めない場合、API は 200 を返し、worker は起動直後に終了するため、400 がないことだけではこの失敗を捕まえられません。プロファイル削除リリースはこの組み合わせをサポートしません。そのリリースへ更新するときは、新しい control-host と新しい worker で turn 1 の完了を確認します（[プロファイル削除リリースのアップグレード順序](#프로필-제거-릴리스의-업그레이드-순서)）。

<a id="compose-전용-checkpoint-검사" />
### Compose 専用 checkpoint 検査

単一サーバー（compose）の upgrade 検査で worker イメージが変わると、新イメージの engine・SDK・CLI・profile digest で各現在 checkpoint の restore plan を計算します。四値がすべて同じで互換のセッションは承認なしで継続し、`INCOMPATIBLE_CHECKPOINT` のものだけ利用者に知らせ、正確な一覧を承認してもらいます。検査を完走できない、または他の検証失敗が混在する場合は、未回収 checkpoint のある全セッションを影響一覧にする fail-closed 動作で、ログに残します。writer 停止後も同じ検査を繰り返します。非互換セッションに `start_fresh` を選ぶと以前の checkpoint の context を破棄します。Kubernetes（helm）の pre-upgrade hook はイメージを実行せず、ポインターの組み合わせで同じ判定をします（[Kubernetes アップグレードの 3. 検査結果と例外 — アップグレード前検査](/run-server/self-hosting/upgrade-kubernetes#3-검사-결과와-예외)）。

worker イメージが変わると、upgrade は変更前イメージを直前イメージとして残します（upgrade スクリプトの状態ディレクトリの `previous-worker`）。scheduler はセッションごとに checkpoint ポインターの組み合わせ（engine・SDK・CLI・profile digest scheme）に合うイメージを現在・直前から選び、両方合えば現在を使います（[設定レファレンスの scheduler・worker コンテナ・egress 設定](/run-server/self-hosting/reference/configuration)）。そのためゲートは、新イメージで復元できず直前イメージでも復元できないセッションだけを影響一覧に入れます。新・直前いずれかの検査が fail-closed なら、新イメージ基準の一覧をそのまま使います。同じ組み合わせで再ビルドしたイメージなら scheduler は新イメージで起動するため、新イメージで復元可能と確認できないセッションは、直前で復元できても一覧から外しません。どちらかが自分の組み合わせを出力できない以前のイメージなら（組み合わせを出力する機能がないビルド）、直前イメージを使わず、ゲートも新イメージ基準の一覧を維持します。サポート範囲は一リリースです。もう一度更新すると、それより前のイメージに残るセッションは再び影響一覧に入ります。プロファイル削除リリースでは、直前のイメージで起動するセッションはありません（[プロファイル削除リリースのアップグレード順序](#프로필-제거-릴리스의-업그레이드-순서)）。

<a id="runtime-버전의-공통-준비" />
### runtime バージョンの共通準備

SDK を上げるリリースでは、イメージが載せるランタイムのバージョンが変わります。リリースは作成時にイメージが載せていたランタイムのバージョンを固定し、セッションはそのリリースのバージョンで動きます。現在・直前のどちらのイメージも載せていないバージョンのリリースでは新規セッションが `UNSUPPORTED_CAPABILITY` で拒否されるので、そのエージェントをリリースし直します。チェックポイントはこの判定とは関係なく、作成したビルドと同じエンジン・SDK・CLI の組み合わせのイメージでのみ再開します。Kubernetes（helm）設置の戻し方と注意点は [Kubernetes のアップグレード § 戻す](/run-server/self-hosting/upgrade-kubernetes#되돌리기) にあります。

<a id="릴리스별-작업" />
## リリースごとの作業

変更履歴が指すリリースごとの手順です。デプロイ済みのバージョンと対象バージョンの間のリリースの節だけに従います。

<a id="프로필-제거의-롤백-하한" />
### プロファイル削除の rollback 下限

実行プロファイルを削除したリリースでは、migration `0270_remove_profiles` がプロファイルの表と列を削除し、プロファイルで作ったリリースとそのセッション、セッションに付く記録（turn・イベント・checkpoint 行など、45 表）を削除します。セッションを持たない `slack_outbox` の行（ウェルカム通知など）は残ります。使用量の表では、セッションに付く `provider_usage` だけが空になり、`agent_usage` は残ります。エージェントとカードのバージョン、チーム、キー、設置の設定は残ります。以後すべてのセッションはリリースが固定した spec（接続・モデル・ランタイム・ツール）で動き、エージェントは接続を選んでリリースし直すと動きます。接続には、エージェントが選ぶモデル一覧（`models`）が必要で、一覧にないモデルでは release を作れません。`0270` は一覧が空の接続にだけ、その接続に対応していたプロファイルのモデルを入れます。対応していたプロファイルがなければ一覧は空のまま残り、一覧がすでにあった接続には何も足しません。アップグレード後、接続ごとにエージェントが使うモデルがすべて一覧にあるかを確認し、足りないモデルを入れます。設定文書では、最上位の `profiles` キーとリポジトリ項目の `profiles` を削除します。最上位のキーがあると `settings import`（CLI と API）が文書を拒否します。リポジトリ項目の `profiles` は CLI が捨てますが、API は拒否します。**このリリースより前のビルドへは rollback できません。** 戻すには、アップグレード前のバックアップから DB を復元します。

<a id="프로필-제거-릴리스의-업그레이드-순서" />
### プロファイル削除リリースのアップグレード順序

プロファイル削除リリースへは、control-host と worker のイメージを一つの upgrade で一緒に更新します。このリリースの control-host は `bootstrap-claim` の応答から `runtime.profile_id` と `profile_fingerprint` を外しました。プロファイル削除前にビルドした worker（`v0.1.3` を含む）は、この二つのフィールドを必須として読みます。そのため、その worker は応答を受け取るとすぐに `POST /bootstrap-claim answered a body this worker cannot read` を残して exit 1 で終了します。セッションは三回 launch された後、`recovery_required`（`STARTUP_FAILED`、`execution_gone`）で停止します。API はこの要求に 200 を返すため、API ログで worker 要求の 400 を探してもこの失敗は分かりません。セッションの turn 1 が完了するかで分かります。

- このリリースでは、上の [2. API → proxy → worker の順序](#2-api--proxy--worker-순서)の中間 release と、[Kubernetes アップグレードの手順 1](/run-server/self-hosting/upgrade-kubernetes#1-대상-chart와-제어-영역-우선-교체)を行いません。新しい control-host と以前の worker が一緒に動く間は、新しいセッションが一つも起動しないためです。Compose は最終 release へ直接 `upgrade` し、Kubernetes は手順 2 のコマンドで直接更新します。
- プロファイル削除前にビルドした worker イメージは、このリリースのサポート範囲に入りません。そのようなイメージを `images.workerPrevious` にわざわざ入れません。ただし Kubernetes の[アップグレード前検査](/run-server/self-hosting/upgrade-kubernetes#3-검사-결과와-예외)は、worker イメージが変わる upgrade では `images.workerPrevious` が現在デプロイ済みのイメージであることを要求し、承認でも続行できません。そのため、この upgrade には手順 2 のスクリプトが作った `worker-previous.json`（現在デプロイ済みの worker イメージ）をそのまま渡します。Compose の `upgrade` が残す `previous-worker` ファイルも同じです。そのイメージで起動するセッションはありません。`0270` がセッションを空にし、新しいセッションは常に現在のイメージで起動し、その後の checkpoint は現在のイメージが残すためです。次に worker イメージを変える upgrade で、直前のイメージはこのリリースのイメージに変わります。
- 更新後、新しいセッション一つが turn 1 を完了するかを確認します。

<a id="지운-slack-연결-env" />
### 削除した Slack 連携の環境変数

このリリースから、API と slack ロールは `SLACK_OIDC_REDIRECT_URI`・`SLACK_OIDC_CLIENT_ID`・`SLACK_OIDC_CLIENT_SECRET` を読みません。Slack アカウント連携のリダイレクトは、`CONSOLE_ORIGIN` に固定パス `/settings/linked-accounts/slack` を付けて計算します。client ID と secret は、ワークスペースごとに 設定 > ワークスペース > 連携 > Slack で作った link アプリのものだけを使います。

- アップグレードの前に、API と slack ロールに `CONSOLE_ORIGIN` があるか確認します。以前のリリースは、`CONSOLE_ORIGIN` がないと `SLACK_OIDC_REDIRECT_URI` の origin を代わりに使いました。このリリースでは、その場合 Slack アカウント連携が `503` になり、Slack アプリを作れず、保存したイベントの入口アドレス(下記)もなければイベント購読も登録されません(`events_url_unset`)。
- 三つの値を削除します。Compose は `infra/compose.core.yml` がもう渡さないので、インストールの env ファイルから行を消すだけです。Kubernetes は `api.extraEnv` と `slack.extraEnv` から削除します。値が残っていると、API は起動時に `Ignored removed settings: <名前>` の警告を一度だけ出します。値は出力せず、動作にも使いません。
- このリリースは以前のビルドに戻せないため([プロファイル削除の rollback 下限](#프로필-제거의-롤백-하한))、ロールバックのために残しておく行はありません。

<a id="웹으로-옮긴-slack-이벤트-입구-주소" />
### Web に移した Slack イベントの入口アドレス

このリリースから、API は `SLACK_EVENTS_PUBLIC_URL` を読みません。イベントの入口をコンソールと別にする場合は、owner が **設定 > 連携 > Slack** の「イベントの入口アドレス」に query・fragment・アカウント情報のない https アドレスを保存します(`PUT /v1/slack-settings`、監査記録 `update_slack_settings`)。空のままなら `CONSOLE_ORIGIN` から計算したアドレスを使います。保存の前に、画面が計算したアドレスと Slack に送る URL を表示します。この値はインストール全体で一つです。

- migration `0278_slack_settings` が `slack_settings` テーブルを追加します。新しい API が初めて起動したときにこのテーブルが空で、API コンテナーに `SLACK_EVENTS_PUBLIC_URL` が実際に渡されていれば、その値を一度だけ移し、値を含まない警告を出します。移した記録は作成者のない監査記録(`by: "env_import"`)として残ります。Compose の `infra/compose.core.yml` はこの値を API に渡さないので、インストール側の overlay や `api.extraEnv`(Kubernetes)で自分で渡していた場合にだけ移されます。それ以外はアップグレード後に画面で保存します。
- 移したあと env の行を削除します。残っていると、起動のたびに `Ignored removed settings: SLACK_EVENTS_PUBLIC_URL` の警告が出ます。https でない値や query のある値は移さず、その旨を警告します。以前のリリースと違い、起動は止まりません。
- 保存したアドレスを変えても、作成済みのアプリにはすぐには送りません。エージェントの Slack タブで「再確認」を押すか、`slack-app finalize` を実行します。
- ロールバックするときも `slack_settings` テーブルは削除しません。以前のビルドはこのテーブルを読みません。

<a id="slack-채널-이벤트와-manifest-다시-보내기" />
### Slack チャンネルのイベントと manifest の送り直し

アップグレードしたあと、エージェントごとにコンソールの Slack タブで「再確認」を一度押すか、API コンテナーで `bun run apps/control-host/src/api/slack-app.ts finalize --agent <agent_id>` を一度実行します。そうして初めて、作成済みのアプリがチャンネルの削除・アーカイブ・名前変更のイベントを受け取ります。実行しないと、削除されたチャンネルの処理は投稿やチャンネルの照会が `channel_not_found` を受けたときにしか動きません。送り直した manifest がインストールにない scope を求めると、「再確認」の案内とコマンドの `warnings`(`reinstall_required`)がアプリの再インストールを求めます。

<a id="웹으로-옮긴-실행-한도" />
### Web に移した実行の上限

インストール全体の実行の上限、セッション記録の保管、作業領域の保持の設定、あわせて十二個は、env ではなく owner が **設定 > ワークスペース > 実行の上限** で保存します(`GET`・`PATCH /v1/installation-config`、監査記録 `update_installation_config`)。どの role も下の env を読みません。保存するとその API はすぐに、ほかの replica と scheduler・slack・metrics role は 10 秒以内に従います。すでに待っているリクエストは最初に受けた時間のままです。turn 時間とモデル呼び出しの再試行は保存後に予約する launch から適用され、別の値で起動した worker は現在の turn を終えてから終了します([turn 時間と再試行を変えるとき](/run-server/self-hosting/explanation/isolation#turn-시간과-재시도를-바꿀-때))。セッション記録の保管の二つの値は保管ジョブが実行のたびに、作業領域の保持の二つの値は scheduler が workspace を回収するたびに読みます。範囲と既定値は [Web で決める実行の上限](/run-server/self-hosting/reference/configuration#웹에서-정하는-실행-한도) にあります。

| 画面の項目 | 移す env |
|---|---|
| 人の応答 | `PENDING_REQUEST_TTL_SEC` |
| セッションの費用 | `SESSION_COST_LIMIT_USD` |
| セッションのトークン | `SESSION_TOKEN_LIMIT` |
| 待機メッセージ | `QUEUED_INPUT_LIMIT_PER_SESSION` |
| 入力の保管 | `STORAGE_LIMIT_BYTES` |
| 作業領域の容量 | `WORKSPACE_ENFORCE` |
| ターンの時間 | `MAX_TURN_SECONDS` |
| モデル呼び出しの再試行 | `PROVIDER_MAX_RETRIES` |
| セッション記録の保管: 保管までの未使用期間 | `SESSION_ARCHIVE_AFTER_DAYS` |
| セッション記録の保管: 保管ジョブの動作 | `SESSION_ARCHIVE_DRY_RUN` |
| 停止したセッションの作業領域 | `EXECUTION_WORKSPACE_STOPPED_TTL_SEC` |
| 一時停止したセッションの作業領域 | `EXECUTION_WORKSPACE_PAUSED_TTL_SEC` |

- migration `0281_installation_config` が、キーごとに一行の `installation_config` テーブルを追加します。続いて migrate が、どの role よりも先に値を移します。保存した値のないキーに env の値が渡されていれば一度だけ移し、値を含まない `note: <env> was carried into Settings > Workspace > Execution limits and is no longer read; remove it` を出します。ワークスペースがあれば作成者のない監査記録(`by: "env_import"`)を残します。空の値は設定していないものとみなします。
- `infra/compose.core.yml` は十二個の env をホストの env か `.env` から受け取り、migrate にだけ渡します。以前のリリースどおり `.env` に書いた値はそのまま移ります。api・scheduler・maintenance に overlay で渡していた値は移らないので、アップグレード前に `.env` へ移すか、アップグレード後に画面で保存します。何も設定していなければ既定値を使います。既定値は以前の compose の既定値と同じです(turn 時間 3600 秒、再試行 2 回、保管まで 180 日、数えるだけ、作業領域の保持はそれぞれ 86400 秒)。作業領域の保持時間を読めない間(止まったキー、DB 障害)、scheduler は止まらず、`stopped`・`paused` セッションの workspace だけを新たに回収しません。移した turn 時間と再試行が起動中の worker の値と同じなら、その worker はアップグレード後も動き続けます。
- 移したあと env の行を削除します。残っていると、migrate が動くたびに `note: Ignored removed settings: <env>` が出ます。保存済みの値を env が変えることはありません。
- 範囲外の値は移しません(`note: <env> was not carried in`)。以前のリリースと違い起動は止まらず、既定値でも動きません。そのキーは画面で値を保存するまで止まります。保存した値がこのバージョンの範囲外でも同じです。止まったキーを読む処理だけが拒否され、画面はその欄に案内を出します。何が拒否されるかは [Web で決める実行の上限](/run-server/self-hosting/reference/configuration#웹에서-정하는-실행-한도) の「使える値がないとき」にあります。たとえばセッションの費用が止まると、新しいセッションとメッセージは `503 BACKEND_UNAVAILABLE` で拒否され、scheduler は launch を飛ばします。
- worker は `QUESTION_TIMEOUT_SEC` を読みません。launcher が渡したことのない値なので、動作は同じです(gateway が登録するまで 30 分)。
- ロールバックするときも `installation_config` テーブルは削除しません。以前のビルドはこのテーブルを読まずに env を読みます(なければ compose の既定値)。画面で変えた値をロールバックしたビルドでも使うには、その値を `.env` に戻します。

### 設定文書は空のインストールに一度だけ入る

このリリースから、migrate は設定文書(`SETTINGS_DOCUMENT`、test-ops では `PLATFORM_SETTINGS_DOCUMENT`)を、空のインストールにだけ一度入れます(`settings seed`)。その後、接続・リポジトリ・MCP サーバーはコンソール(設定 > エージェント接続)で変更します。文書を直して再デプロイしても取り込まれません。

- migration `0282_settings_seed_decided` が `settings_generation.seed_decided_at` 列を追加します。アップグレード後、設定文書を受け取った最初の migrate がこの時刻を記録します。`SETTINGS_DOCUMENT` がなければ migrate は seed を実行しないため、時刻もログも残りません。接続や MCP サーバーがすでにあるインストール(使用停止したものを含む)は何も取り込まず、時刻だけを記録します。リポジトリ行だけがあるインストールは空とみなし、一度入れます。
- 取り込まないとき、migrate のログに値を含まない一行が出ます: `note: the settings document <ファイル> (SETTINGS_DOCUMENT) not imported: the installation already holds settings. It seeds an empty installation only; change settings in the console`。時刻を記録した後は `the automatic seed ran on <時刻>` と表示されます。この行は失敗ではありません。
- 文書の内容を意図して入れ直すときは、owner が手で `settings import` を実行します。このコマンドは変わっていません。
- test-ops の `upgrade` は、変わった文書を取り込まず、DB と比較もしません。文書の digest が変わると `upgrade: the settings document changed; it is not imported into a deployed installation, so change settings in the console` を記録します。`deploy` の確認はそのままです。
- ロールバックすると、以前のリリースの migrate がデプロイのたびに文書を再び取り込みます。コンソールで変えた項目が文書の同じ id と異なると、その取り込みが拒否されて migrate が失敗し、API が起動しません。ロールバックの前に、そうした項目を文書から外すか、コンソールの値に合わせます。`seed_decided_at` 列は削除しません。以前のビルドはこの列を読みません。

<a id="env로-가리키던-자격-증명은-db로-한-번-옮긴다" />
### env で指していた資格情報は DB へ一度移す

このリリースから api は設定の `value_env`（接続、自分の GitHub App を書いたリポジトリ、MCP サーバー）を env から読みません。設定を読むときにその値を DB に封印し、その行の保存値として一度移します。`secret_id` はそのままです。

- migration `0285_credential_carried_auth` が `provider_connections`・`catalog_repositories`・`mcp_servers` に `carried_auth` 列を、`catalog_repositories` に `carried_binding` 列を追加し、明示的な App のリポジトリも保存値を持てるよう `catalog_repositories_credential_check` を変えます。`push_requests`・`worker_credentials` には INSERT trigger（`…_carried_binding`）を付けます。
- アップグレード後、移した行ごとに api のログに `<kind>:<id> took its credential from <名前> into the database and no longer reads it; remove <名前>` が一度出ます。そのあと env からその名前を外せます。値はログにも receipt にも出ません。receipt `set_settings_credential` には変数名と `by: env_import` だけが残ります。
- 最初のワークスペースがない間（bootstrap 前）はそれまで env から読み、ワークスペースができたあと最初の設定読み込み（10 秒以内）で移します。
- env に値がない行は外され、警告が一度出ます: `<kind>:<id> names <名前>, which the API does not have, so it is left out. …`。変数を入れて api を再起動します。接続ならコンソールの「画面でキーを入れる」でもできます。
- 実行経路が拒否する値（8 バイトより短いキーや前後の空白・制御文字を含むキー、RSA 秘密鍵 PEM でない App のキー）と 8 文字より短いキー（保存値は末尾の四文字を表示します）は移しません。その行は外され、`<kind>:<id> is left out and not carried into the database: <理由>. Correct <名前> and restart the API` が一度出ます。理由には変数名だけが出ます。
- 明示的な App のリポジトリを移すと資格情報の参照が変わり、リポジトリの binding も変わります。同じトランザクションで、そのリポジトリの古い binding をそのまま持つ push 要求と実行中のセッションのリポジトリトークンを新しい binding に移します。そのため、移す前の push からも PR を開いてマージでき、実行中のセッションもトークンを受け取り直せます。移した行数はログ（`… (N push requests and M worker credentials moved to its new binding)`）と receipt の `rebound` に残ります。まだ移したことを読んでいない replica（10 秒ごとに読み直します）や以前のビルドがそのあと古い binding で書く行は、DB が書き込む時点で新しい binding にします（上の trigger）。ロールバックの SQL が `carried_binding` を空にすると、trigger は何も変えません。移すトランザクションは二つの表をロックするため、その間 push 要求と worker トークンを書く要求は待ちます。5 秒以内にロックできなければ移さず、次の読み込みでやり直します。移したあと、その App のキーは `POST /v1/installation/settings/repositories/{id}/credential`（owner・admin、RSA 秘密鍵 PEM）で変えます。env を変えても読みません。
- **このリリースへ上げるときは、api を一つに減らすか、以前の replica をすべて止めてから新しいビルドを起動します。** replica はそれぞれ 10 秒ごとに設定を読み直すため、まだ移したことを読んでいない replica がその間に、移した push 要求を `catalog_changed` で失敗させたり、実行中のセッションのトークン再発行を拒否したりすることがあります。Compose の api は一つなので、そのまま上げます。Helm は [Kubernetes のアップグレード](/run-server/self-hosting/upgrade-kubernetes)の手順 1 に従います。そうして失敗した push は、もう一度要求すれば新しい binding で push されます。
- 移したあと古い文書を手で `settings import` すると、移した項目は同じ id で内容が違うため `conflicts` で止まります。その項目を文書から外すか、`settings export` で受け取った文書を使います。
- URL リポジトリ（`auth` が `basic`・`bearer`）は実行に使われないので移しません。
- ロールバック: 以前のビルドは接続・MCP サーバーの保存値は読みますが、明示的な App のリポジトリの保存値は拒否し、そのリポジトリは `invalid` として外れます。ロールバックはこの順序で行います。
  1. このリリースの api replica をすべて止めます。一つでも動いていると、次の設定読み込み（10 秒以内）で戻した行をまた移します。
  2. 下の SQL を一つのトランザクションで実行します。行の env 参照を戻し、移したときに変えた push 要求と worker トークンの binding も古い値に戻します。
  3. それらの変数を api の env に戻し、以前のビルドを起動します。移したあとコンソールでキーを変えていたら env の値に戻るので、env に新しい値を入れます。

  `carried_auth`・`carried_binding` 列と封印した値は残します。

```sql
BEGIN;
UPDATE push_requests p SET repository_binding = r.carried_binding->>'from' FROM catalog_repositories r WHERE r.carried_binding IS NOT NULL AND p.repository_binding = r.carried_binding->>'to';
UPDATE worker_credentials w SET binding = r.carried_binding->>'from' FROM catalog_repositories r WHERE r.carried_binding IS NOT NULL AND w.purpose = 'repository' AND w.binding = r.carried_binding->>'to';
UPDATE provider_connections SET definition = jsonb_set(definition, '{auth}', carried_auth), credential_source = 'external', carried_auth = NULL WHERE carried_auth IS NOT NULL;
UPDATE catalog_repositories SET auth = carried_auth, credential_source = 'external', carried_auth = NULL, carried_binding = NULL, version = version + 1 WHERE carried_auth IS NOT NULL;
UPDATE mcp_servers SET auth = carried_auth, credential_source = 'external', carried_auth = NULL WHERE carried_auth IS NOT NULL;
COMMIT;
```

<a id="외부-자격-증명-출처를-없앤-릴리스" />
### 外部の資格情報の出所をなくしたリリース

このリリースから、モデル接続、MCP サーバー、リポジトリの GitHub App key は DB に保存された値だけを使います。設定の `value_env`（api の env）と `secret_id`（AWS Secrets Manager）はなくなり、api は Secrets Manager をどこでも使いません。値はコンソール（設定 > モデル接続・MCP サーバー）か、owner のセッションの `POST /v1/installation/settings/{connections|mcp-servers|repositories}/{id}/credential` で入れ、`PLATFORM_SECRET_KEY` で暗号化して DB に保存されます。リポジトリの App key は Web の画面がなく、この API でだけ入れます（GitHub App の RSA 秘密鍵 PEM）。`PLATFORM_SECRET_KEY`、`DATABASE_URL`、`EGRESS_AUTHORIZER_TOKEN`、object store の key、すでに DB に保存される Slack・IdP の秘密、リポジトリの `auth` `none` はそのままです。

- アップグレードの前に、env か Secrets Manager を指すモデル接続ごとに、今のリリースのコンソールの**画面でキーを入れる**でキーを入れておきます。そうすればアップグレード後もその接続のセッションは止まりません。アップグレード後に入れてもかまいません。MCP サーバーとリポジトリの App key は今のリリースでは移す方法がないので、アップグレード直後に入れます（下記）。
- 使用を停止した接続や MCP サーバーが env か Secrets Manager を指していると、アップグレード後は再び有効にできません。コンソールは停止した行にキーを受け付けず、キーのない行を有効にしません。その接続を使い続けるなら、アップグレード前に有効にして**画面でキーを入れる**でキーを入れます。MCP サーバーはアップグレード前に有効にしておき、アップグレード後にキーを入れます。そうしなかった場合は、アップグレード後に新しい id で接続やサーバーを作ります。id は再利用しません。
- migration `0288_remove_external_credentials` は、env か Secrets Manager を指していた行を値のない保存型の行に変えます。その行はキーが入るまで `needs_value`（画面では**値が必要**）で、その行を使うセッションは動きません。接続は**API キーを設定**、MCP サーバーは**値を変える**、リポジトリの App key は上の API で入れます。古い `auth` は `carried_auth` に記録としてだけ残り、読まれません。明示的な App のリポジトリは binding が変わるため、同じ migration がそのリポジトリの worker 資格情報の binding を新しい値に移します。push リクエストの binding はそのリポジトリの App key を入れたときに移すため、それまでは上げる前に作った push から PR を開けません。以前の api replica が受け取ったキーでは push は移らないので、リポジトリの App key はすべての api が新しいビルドになってから入れます（先に入れたならもう一度入れます）。
- 設定文書の `value_env`・`secret_id` の項目は `"stored": true` に変えてから import します。残っていると `settings import`（API、CLI）が 400 `invalid_document` で拒否し、CLI はそのフィールド名をエラーに出します。
- アップグレード後、接続が指していたキーの変数（例: `ANTHROPIC_API_KEY`）と `AWS_ENDPOINT_URL_SECRETS_MANAGER` を api の env から消します。api はこれらを読みません。Helm は [Kubernetes のアップグレード](/run-server/self-hosting/upgrade-kubernetes)に従います。
- コンソールで作る接続と MCP サーバーは、キーがあるときだけ保存されます。Web は 8 文字以上入れるまで保存ボタンを押せないようにし、API はキーがない、8 バイトより短い、制御文字や前後の空白を含むときに 400 で拒否し、DB は値なしでコンソールから作った行を同じトランザクションで拒否します。外部の出所の接続を保存型に変えていたコンソールの「画面でキーを入れる」ボタンと `POST …/connections/{id}/convert` の経路はなくなりました。
- 上の 0285 のロールバック SQL は、このリリースの後では使えません。`credential_source` は `stored` だけを許します。

<a id="쓰지-않는-표-셋을-지운-릴리스" />
### 使っていない三つの表を削除したリリース

migration `0305_drop_unused_tables` が `catalog_authority`・`owner_workspace_map`・`push_continuations` の表を行ごと削除する。`v0.1.0` 以降、前の二つの表を読み書きしたリリースはなく、`push_continuations` を使った最後のリリースは `v0.1.1` である。そのため、サポート期間内のイメージに戻しても影響はない。

- 表に行が残っている場合がある。`catalog_authority` には設定ファイルのカタログ時代に有効にした revision の一行、`owner_workspace_map` には運用者が手で入れた owner とワークスペースの対応、`push_continuations` には `v0.1.1` 以前が作った続きのターンの記録が残っている場合がある。行があれば、migrate のログ `db.migrate.notice` に表ごとの削除した行数が残る(`0305: dropped rows: …`)。行の値はログに残らない。
- その行が必要なら、上げる前にバックアップする。0305 より下にスキーマを戻しても行は戻らない。

<a id="slack-글의-관여-기록을-남기는-릴리스" />
### Slack の投稿への関与を記録するリリース

migration `0323_conversation_engagements` が関与記録の表 `conversation_engagements` を追加する。slack ロールはメンション・DM・紐づいたスレッドの投稿をこれまでどおりセッションのターンにし、入力受付の行を記録する同じ transaction で、エージェントがその投稿に関与したことを一行記録する。上げるときにすることはなく、Slack とセッションの動作も変わらない。

- 関与記録に残るのはエージェント、投稿の場所(team、チャンネル、ts)、種類、その投稿が入ったセッションだけで、本文・スレッドの ts・Slack のリンクは残らない。スレッドはセッションの link が持つ。
- 種類は、セッションを開いた投稿が `mention`(メンションか DM)、メンションのないトップレベルの投稿で開いたセッションなら `reply`、すでに開いているセッションに入った投稿が `bound`(メンションがあっても `bound`)。
- 一つの投稿が二つのイベントで届いても、処理し直しても、エージェントごとに一行。ターンにならなかった投稿(拒否・無視)は記録しない。既存のセッションは埋めない。
- 関与記録がある投稿の削除・編集の印は、70 分を過ぎても reconciler が消さない。
- 新しい表を作るだけなので、サポート期間内のイメージに戻してもよい。その間の投稿には関与記録ができない。

<a id="세션에-부모-대화를-채우는-릴리스" />
### セッションに親の会話を埋めるリリース

migration `0320_session_parent_conversation` が `sessions.parent_conversation_id`(nullable、`conversations` への外部キー)を追加する。外部キーは `NOT VALID` で追加してから別に検証するので、表を長くロックしない。上げるときにすることはなく、Slack・Web・セッション API の動作も変わらない。

- 新しい Slack セッションは作るときに親の会話を受ける。チャンネルのスレッドのセッションはそのチャンネルのメインの会話、DM のセッションはその人の DM の会話になる。link のないセッション(Web の「新しいセッション」、セッション API)は空のままになる。
- 既存のセッションは、api が起動するたびに動く整理がまとめて埋める。閉じた link や廃止された link のセッションも埋める。セッションごとに空のときだけ埋めるので、何度起動しても、複数の api が同時に起動しても結果は同じで、途中で止まれば次の起動が残りから続ける。
- DM のセッションの人はそのセッションを開いた人で(新しいセッションが作るときに選ぶ人と同じ)、いないかワークスペースのメンバーでなければ link を作った人になる。どちらもいなければ親は空のままで、そのセッションは link のないセッションと同じに動く。その数は理由ごとにログ `Linked DM sessions left without a parent conversation`(`no_person`・`no_membership`)に残る。その人がまたメンバーになれば次の起動が埋める。
- 埋めた数はログ `Parent conversations filled` に残る。埋められなかったセッションはセッション id とともに警告として残り、次の起動でもう一度試す。
- サポート期間内のイメージに戻してもよい。その間に作った Slack セッションは親なしでできて、また上げると起動時に埋まる。

### 終わりのわからない呼び出しを示し、エージェント自身の仕事を先に止めるリリース

migration `0332_unknown_budget_end` が `budget_reservations` と `conversation_calls` に、終わりのわからない呼び出しを示す列 `unknown_at`(nullable)を追加し、reconciler が読む部分インデックスを二つ作る。上げるときにすることはない。予算の上限がないインストールでは、人、key、エージェントの呼び出しはこれまでどおり動く。

- 使われた provider 呼び出しに lease(5 分)以内に使用量の報告が来なければ、reconciler がその予約の `unknown_at` を書く。状態は `reserved`(会話呼び出しは `in_flight`)のままである。予約は解放せず、上限の計算では使ったものとして数え続ける。遅れて報告が来れば実際の値で精算し、予約を外す。lease がまた更新されるか呼び出しが解放されれば印を消す。セッションの呼び出しとセッションのない呼び出し(会話呼び出し)が同じ規則に従う。
- reconciler は終わりのわからない予約の多い口座からバッチの大きさまで、その数と押さえている金額を `warn` ログ `Budget reservations of unknown end held`(`unknown_count`、`held_cost_usd`、`held_tokens`)に、すべての口座の合計をログ `Budget reservations of unknown end reported` に残す。ログ `Provider exchange ledger reconciled` と `Conversation call reservations reconciled` に `unknown_count` が加わる。このリリースには押さえられた予約を運用者が解放するコマンドはない。
- 上限のある予算口座では、人も key もいない実行(root の種類 `none`)の予約は上限の 80% で拒否される。人の依頼と key、Slack ボットの依頼は 100% まで動き、100% ではすべて拒否される。上限のない口座には 80% の判定はかからない。
- 状態の値と CHECK は変わらず、インデックスは `CONCURRENTLY` で作る。サポート期間内のイメージに戻してもよい。古いイメージは `unknown_at` を無視し、予約を `reserved` として精算する。

### 削除された Slack メッセージにかかる返信とターンを止めるリリース

migration `0329_slack_outbox_voided_by_delete` が `slack_outbox` の状態に `voided_by_delete` を、その行がどのターンのものかを示す列 `sources_turn` を追加する。上げるときにすることはない。削除されたメッセージのないスレッドのメンションと返信、Web・API のセッションの動作は変わらない。

- メッセージの編集は何も止めない。
- 削除されたメッセージからはセッションもターンも作らない。そのメッセージのメンションと、前のメッセージが削除されたスレッドの次の投稿が対象である。Slack には案内を投稿せず、slack ロールが `warn` ログ `Slack input refused by the session`(`code` `SOURCE_DELETED`)を残す。
- そのようなセッションに Web や API からメッセージを送ると、新たに 409 `SOURCE_DELETED` で拒否される。このリリースはセッションを止めない。
- CHECK は `NOT VALID` で追加し別の文で検証するので、書き込みを長く止めない。サポート期間内のイメージに戻してもよい。古いイメージは `voided_by_delete` の行を読まず、送りもしない。

### セッションのない呼び出しの予約表を作るリリース

migration `0328_conversation_calls` が、セッションのない provider 呼び出し(会話呼び出し)の表 `conversation_calls` を追加する。このリリースには会話呼び出しを出す経路がないので、表は空のままである。上げるときにすることはない。

- 会話呼び出しは、トークンを出す前に、誰の依頼か(root)で選んだ予算口座にその呼び出しの最大コストを予約する。最大コストは、リクエスト本文のバイト上限を入力トークン、`max_tokens` を出力トークンとして数える。口座に収まらなければ、トークンも表の行も作られない。
- トークンはハッシュだけを保存し、egress proxy を通る Messages 呼び出し一回に結び付く。その呼び出しのパス、モデル、`max_tokens`、本文バイト上限を超えるリクエストは proxy が拒否する。同じトークンの二回目の呼び出しも拒否する。
- 使われた呼び出しは proxy の使用量報告で口座に精算される。セッションの使用量(`provider_usage`)には書かない。
- 2 分以内に使われなかったトークンの予約は reconciler が解放し、ログ `Conversation call reservations reconciled`(`released_count`)を残す。使われたのに報告が来ない呼び出しの予約は解放しない。
- セッションのタイトル付け呼び出しと、実行中のターンがないセッションの呼び出しは、そのセッションを作った最初のターンの口座で押さえるようになる。上限のない設置では今までどおり動く。上限を入れると、超えたタイトル付け呼び出しは拒否され、最初のメッセージから切ったタイトルが残る。
- egress proxy が provider の許可リクエストにヘッダー `x-werft-exchange-id` を付ける。前の API はこのヘッダーを無視する。会話呼び出しのトークンはこのヘッダーがあるときだけ許可されるので、api と egress proxy を一緒に上げる。
- 表を追加するだけなので、サポート期間内のイメージに戻してもよい。

### 人に直接届く Slack 投稿を止めるリリース

migration `0309_slack_outbox_channel` が `slack_outbox` に CHECK `slack_outbox_channel_check` を加える。Slack のユーザー id(`U…`、Enterprise Grid では `W…`)を channel に持つ行は、モデルの案内(`model_notice`)だけが入れられる。エージェントが人との DM を先に開かないための防御である。これまでどのリリースもそのような行を書いていないので、通常はすることはない。

- そのような行が残っていると、migrate のログ `db.migrate.notice` にその数が残り(`0309: … slack_outbox rows name a Slack user as their channel`)、migrate は `VALIDATE CONSTRAINT` で止まる。そのときも制約は `NOT VALID` のまま残り、新しい行を拒む。上げる前に次のクエリで確かめられる。

```sql
SELECT kind, status, count(*) FROM slack_outbox
WHERE channel_id ~ '^[UW]' AND kind <> 'model_notice'
GROUP BY 1, 2;
```

- 見つかった行は送ってはならない行である。削除してから migrate をもう一度実行する。どの文も再実行してよい。
- 送る側もそのような行を Slack に送らず、`failed`(`error_code` `user_channel`)で終える。
- 以前のイメージもそのような行を書かないので、制約を残したまま戻してもよい。

### 呼び出しをターンの予算アカウントに課金するリリース

このリリースから、provider 呼び出しの open はセッション上限と一緒に予算アカウントでもその呼び出しを押さえる。アカウントは、実行中のターンが誰の依頼か(root)で選ぶ。migration `0322_budget_root_slack_bot` は台帳の root の種類に `slack_bot` を加える(`provider_exchanges.budget_root_kind` と `budget_reservations.root_kind` の CHECK を置き換える)。することはない。

- 上限を決めていないインストール(`budget_limits` の行がない)では、人・キー・Slack ボットのターンはこれまでどおり動く。台帳には呼び出しごとに root の種類とアカウントが残る。誰も頼んでいないエージェント自身の仕事(root `none`)は上限がなければ拒否されるが、このリリースにはそのようなターンを作る経路はない(push のフォローアップターンは前のターンの依頼者を引き継ぐ)。
- アカウントの選び方: 人のターンと、その後の継続ターン・push のフォローアップターンはその人のアカウント(`user`)だ。個人キーのターンはキーを作った人のアカウント(`key`)、人のいないキーのターンはエージェントを管理するチームのアカウント(`key`)、許可した Slack ボットのターンもそのチームのアカウント(`slack_bot`)だ。チームがアーカイブされていれば、アカウントなしで root の種類だけが残る。
- 依頼者を読めないターン(依頼者の記録がない古いターンなど)、セッションのタイトル付けの呼び出し、実行中のターンがない呼び出し(ターンの間など)、ワークスペースのないセッションはアカウントを押さえず、セッション上限だけを見る。これまでと同じだ。
- `budget_limits` に上限を入れると、そのアカウントで超える呼び出しはセッション上限を超えたときと同じ `BUDGET_EXCEEDED` で拒否される。アカウントが拒否したターンは provider のエラーで終わり(Claude Code エンジンでは `api_error`)、セッションの注意表示(`BUDGET_EXCEEDED`)はセッション上限にだけ出る。アカウントの拒否かどうかは下のログの `turn_id` でつなぐ。このリリースには上限を決める画面も API もない。
- 拒否された open ごとに API は `info` ログ `Provider exchange refused for the budget` を残す。項目は `session_id`、`attempt_id`、`turn_id`(実行中のターン)、`refused_by`(`session` か `account`)、`budget_root_kind`、`budget_account_id` だ。
- CHECK は値を広げるだけなので、サポート期間内のイメージに戻してもよい。すでに開いている呼び出しは、最初の open が選んだアカウント(またはセッション上限だけ)で終わる。
- タイトル付けの呼び出しは、egress proxy が open にヘッダーで知らせる。api だけがこのリリースで egress proxy が以前のリリースのあいだは、タイトル付けの呼び出しも実行中のターンのアカウントで押さえられる。上限を決めていないインストールでは違いはなく、二つを一緒に上げればよい。

### 台帳に予算アカウントの列を加えるリリース

migration `0318_provider_exchange_budget` が provider 呼び出しの台帳 `provider_exchanges` に nullable の列を二つ加える。`budget_root_kind`(その呼び出しを課金した root の種類 `user`・`key`・`none`)と `budget_account_id`(その呼び出しを一緒に押さえた予算アカウント)だ。することはない。

- このリリースではどの呼び出しもアカウントを渡さないので、二つの列は空のままで、セッションのコスト上限とトークン上限はこれまでどおり動く。台帳がアカウントとセッション上限を一度に押さえるコードは入るが、呼び出し経路につなぐのは後のリリースだ。
- 列を加えるだけなので、サポート期間内のイメージに戻してもよい。

### 予算アカウントの表を加えるリリース

migration `0314_budget_accounts` が空の表を三つ作る。`budget_limits`(組織全体の一人あたりの既定の上限、人ごとの上限、エージェントチームの上限)、`budget_accounts`(人・チームのアカウントが月ごとに使った分と予約した分。月は UTC で区切る)、`budget_reservations`(呼び出しごとの予約と精算の記録)だ。することはない。

- このリリースでは、どの呼び出しもこれらの表を読み書きしない。セッションのコスト上限とトークン上限はこれまでどおりで、上限を決める画面・API・運用者コマンドもまだない。
- 新しい表を作るだけなので、サポート期間内のイメージに戻してもよい。

### Slack メッセージの編集・削除の印

migration `0312_slack_source_marks` が新しいテーブル `deleted_sources` と `edited_sources` を作る。このリリースから、Slack でメッセージを削除または編集したイベント（`message_deleted`、返信のあるメッセージを削除したときに届く墓標の `message_changed`、人が編集した `message_changed`）を捨てずに、そのメッセージの場所（team、チャンネル、ts）と時刻だけを印として残す。メッセージの本文とイベントの原文はどこにも保存せず、inbox の行は原文なしで `processed` になる。特にやることはない。

- 今は Werft がそのメッセージを指す記録を持たないため、すべての印は作ってから 70 分（判断バッファの 10 分と 1 時間）を過ぎると reconciler が消す。ログ `Unknown Slack source marks purged` に消した数が残る。保持期間は[データごとの保持](/run-server/self-hosting/reference/storage#데이터별-보존)にある。
- 捨てた理由 `message_subtype` で集計していたクエリは、編集・削除イベントがなくなった分だけ数が減る。リンクのプレビューのように人が編集していない `message_changed` は今までどおり捨てる。
- テーブルを足すだけなので、サポート期間内のイメージに戻してもよい。前のイメージはこのテーブルを使わず、編集・削除イベントをまた捨てる。

### Slack スレッドの link 履歴の列を加えたリリース

migration `0313_session_link_history` が `session_links` に `closed_at`・`closed_reason` 列と、閉じていない link だけを見る部分 unique 二つ(`session_links_open_surface_ref_uniq`、`session_links_open_session_uniq`)を加え、`slack_outbox` に `session_link_id` 列を加える。このリリースのコードは新しい列をまだ読み書きしないので、することはなく動作も変わらない。既存の行はすべて閉じていない link のまま残る。

- 古い unique 二つ(`session_links_surface_ref_key`、`session_links_session_uniq`)はそのまま残る。後のリリースが削除する。
- インデックスは `CONCURRENTLY` で作り、CHECK と外部キーは `NOT VALID` で加えてから別に検証する。そのため検証とインデックスの作成のあいだ書き込みを止めない(列と制約を加えるときだけ短くロックを取る)。
- どの文も再実行してよい。インデックスの作成が途中で切れたら migrate をもう一度実行する。残った INVALID インデックスを削除して作り直す。
- 以前のイメージは新しい列なしで書き、古い unique で重なりを判定するので、そのまま動く。サポート期間内のイメージへ戻してもよい。

### mock Slack の環境変数名

mock Slack 試験スタック(`infra/compose.mock-slack.yml`)が使っていた `SLACK_API_URL`・`SLACK_OIDC_ISSUER` は `MOCK_SLACK_API_URL`・`MOCK_SLACK_OIDC_ISSUER` に変わりました。古い名前は読まず、残っていれば `Ignored removed settings` の警告に名前が出ます。新しい名前に値があると、アドレスに関係なく起動時に `Mock Slack override in use: <名前>` の警告を一行出します。運用設定にはどちらの名前も置きません。

### 成果判定の接続とロールバック

`openai_decisions` 接続(成果判定器 Luna 用)を作った後にこの種類を知らないビルドへ戻すと、そのビルドの 設定 > エージェント接続 > モデル接続 の一覧と `GET /v1/installation/settings/connections` が、ほかの接続も含めて失敗します。使用停止した接続も一覧で読まれるため、使用停止では解消しません。エージェントの実行と release はその接続を飛ばすので影響はありません。戻す前に DB でその接続の行を削除します。

```sql
DELETE FROM provider_connections WHERE definition->>'kind' = 'openai_decisions';
```

保存したキーの値は残ります。判定設定に保存した接続 id も残り、戻したビルドでは Luna ルールを判定しません。再度アップグレードした後、接続を作り直して判定設定で選びます。アップグレード前の DB バックアップから復元して戻す場合は、追加の作業はありません。
