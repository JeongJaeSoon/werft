## 作業内容

ノート PC の隔離した kind クラスタで chart と API の準備状態を試験し、最後に削除します。この PostgreSQL・LocalStack は運用データの保存先ではありません。

<a id="준비물" />
## 準備

Docker、kind、Helm 3、kubectl が必要です。手順 1 の harness は git、Bun 1.3.14 とリポジトリ checkout も使います。手順 2 の公開 chart 試験は checkout の代わりに `curl`、`openssl` と [chart 試験用の DB と object store の準備](/run-server/self-hosting/try-chart-dependencies#준비물)を使います。設置・削除するクラスタ名と registry ポートが他の作業と重複しないことを確認します。NetworkPolicy を強制する kind バージョンを使います。

<a id="단계" />
## 手順

<a id="1-checkout의-시험-harness" />
### 1. checkout の試験 harness

```bash
git clone https://github.com/JeongJaeSoon/werft.git
cd werft
CLUSTER_NAME=werft-try REGISTRY_PORT=15001 deploy/kind/up.sh
export KUBECONFIG=~/.cache/werft/kind/werft-try/kubeconfig
```

スクリプトは cluster、registry、イメージ、namespace、DB、LocalStack、Secret、chart を準備し、rollout と ready/docs を確認します。生成された kubeconfig だけを使います。`EXTRA_VALUES` で環境ごとの値を上書きできますが、harness の worker イメージの `--set` 値は変わりません。

<a id="2-게시-chart를-직접-시험하는-경우" />
### 2. 公開 chart を直接試験する場合

harness の代わりに公開 chart を試験する場合、リポジトリ checkout は不要です。別の kind クラスタを作成し、そのクラスタだけを指す kubeconfig を使います。

```bash
kind create cluster --name werft-try --kubeconfig "$HOME/.kube/werft-try"
export KUBECONFIG="$HOME/.kube/werft-try"
kubectl config current-context
```

最後のコマンドが `kind-werft-try` を出力することを確認します。続けて同じシェルで [chart 試験用の DB と object store](/run-server/self-hosting/try-chart-dependencies)の手順 1〜4 に従います。そのページが依存サービスの manifest、Secret、最小の values を本文で示し、手順 4 で公開 chart を設置します。LocalStack の初期化スクリプトはその manifest の ConfigMap `localstack-init` に入っており、リリースバンドル（`werft-test-ops-<tag>.tar.gz`）の `infra/localstack/init/10-create-resources.sh` と同じ bucket を作ります。

最初の owner は、下の[最初の owner を作る](#첫-owner-만들기)で作ります。リンクは DB にあるため、2 個の replica のどちらに届いても使えます。モデル key は Secret に入れません。key は最初の owner がコンソールで入力して DB に保存する値だけで、この試験では key を入れません。実運用の資格情報をこの試験に入れないでください。

<a id="확인" />
## 確認

```bash
kubectl -n werft get job werft-migrate
for d in api egress-proxy reconciler scheduler; do
  kubectl -n werft rollout status deploy/werft-$d --timeout=600s
done
```

```bash
kubectl -n werft port-forward svc/werft-api 13000:3000 &
PF=$!
trap 'kill "$PF" 2>/dev/null || true' EXIT INT TERM
READY=0
for attempt in $(seq 1 30); do
  if curl --max-time 2 -fsS -o /dev/null http://127.0.0.1:13000/readyz; then READY=1; break; fi
  sleep 1
done
if [ "$READY" != 1 ]; then
  kill "$PF" 2>/dev/null || true
  trap - EXIT INT TERM
  false
else
  STATUS=0
  curl --max-time 10 -fsS -w '\n%{http_code}\n' http://127.0.0.1:13000/readyz || STATUS=1
  curl --max-time 10 -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:13000/docs || STATUS=1
  kill "$PF" 2>/dev/null || true
  trap - EXIT INT TERM
  [ "$STATUS" = 0 ]
fi
```

ready 200 と docs 200 は空の設置環境の準備状態です。セッションと worker Pod を起動し、checkpoint 復元まで確認した結果ではありません。kind の PVC Bound だけで byte 上限の強制を証明することはできません。

<a id="자주-막히는-곳" />
<a id="첫-owner-만들기" />
### 最初の owner を作る

上のブロックは最後に port-forward を止めます。リンクは port-forward のアドレスで開くので、先に port-forward をもう一度起動し、api が応答するまで待ちます。

```bash
kubectl -n werft port-forward svc/werft-api 13000:3000 &
PF=$!
until curl --max-time 2 -fsS -o /dev/null http://127.0.0.1:13000/readyz; do sleep 1; done
```

そのシェルで、[最初の owner を作る](/run-server/self-hosting/users-and-keys#1-첫-owner-만들기)の Kubernetes のコマンドでリンクのファイルを受け取ります。`accept_url` が `null` なら `http://127.0.0.1:13000` の後ろに `accept_path` を付けて開き、コマンドに渡したメールアドレスで owner を作ります。終わったら `kill "$PF"` で port-forward を止め、リンクのファイルを削除します。

## よくある問題

直接設置で Secret の必須 key が欠けると Pod は起動しません。公開 chart を取得できない場合、fixture のレンダリングで成功扱いにせず、その公開パッケージの設置失敗として記録します。クラスタ外の DB・S3 アドレスと試験依存サービスのアドレスを混在させないでください。

<a id="되돌리기" />
## 元に戻す

harness で作成した場合：

```bash
CLUSTER_NAME=werft-try deploy/kind/up.sh down
```

直接作成した `werft-try` クラスタは `kind delete cluster --name werft-try --kubeconfig "$HOME/.kube/werft-try"` で削除します。失敗時も今回の試験クラスタだけを整理し、他の context のリソースには触れません。
