## 무엇을 하게 되나

Linux 시험 서버에 LocalStack을 쓰는 Compose 설치를 만든다. object가 호스트·Docker 재시작에서 사라질 수 있는 비영속 시험 경로다.

## 준비물

| 항목 | 요구 |
| --- | --- |
| 운영체제 | Linux. `x86_64`와 `arm64` 모두 된다 |
| Docker Engine | 28 이상 |
| Docker Compose | 2.24.6 이상 |
| 디스크 | Docker 데이터 루트가 XFS이고 `prjquota`로 mount돼 있다. `preflight`가 quota probe로 이것을 검사하고, 아니면 멈춘다. ext4 서버는 [XFS 디스크 준비](/run-server/self-hosting/prepare-xfs)를 먼저 끝낸다. Docker Desktop에서는 쓸 수 없다 |
| 시간 | NTP 동기화. 재부팅 뒤 Docker가 자동으로 시작한다 |
| 도구 | checkout 설치는 `git`, `jq`, `curl`, `openssl`, Bun 1.3.14, Docker Buildx 플러그인. 릴리스 번들 설치는 `jq`, `curl`, `openssl`, `sha256sum`, `tar`(gzip 지원). 둘 다 Docker daemon에 접근할 수 있는 계정 |
| 외부 | `ghcr.io`와 Docker Hub에서 이미지를 받을 수 있다. 패키지는 로그인 없이 받는다. 세션은 `api.anthropic.com`과 `github.com`에 나간다 |

설치 방법은 [단일 서버 설치](/run-server/self-hosting/single-server)와 같이 둘이다. 저장소 checkout은 모든 게시 태그에 쓸 수 있고, `v*` 릴리스는 번들로 checkout과 호스트 Bun 없이 설치할 수 있다. 어느 쪽이든 compose 파일과 `scripts/test-ops.sh`를 받은 디렉터리에서 읽고, 이미지는 빌드하지 않는다.

운영 데이터와 분리된 Linux 서버에서 [XFS 준비](/run-server/self-hosting/prepare-xfs)를 먼저 끝낸다. 시험 전용 project·설치 id·포트·상태/비밀 디렉터리를 선택한다. test-ops의 기본 project 이름은 `werft-test-ops`이며 `TEST_OPS_PROJECT`로 바꾼다. 다음 예시의 기본 경로가 기존 설치에 쓰이면 다른 경로와 `TEST_OPS_*` 값을 지정한다.

## 단계

### 1. 이미지와 소스

```bash
TAG='<published-image-tag>'
SOURCE_REF='<matching-source-commit-or-release-tag>'
for app in control-host worker egress-proxy; do
  echo "$app $(docker buildx imagetools inspect "ghcr.io/jeongjaesoon/werft-$app:$TAG" --format '{{.Manifest.Digest}}')"
done
```

```bash
git clone https://github.com/JeongJaeSoon/werft.git
cd werft
git checkout "$SOURCE_REF"
bun install --frozen-lockfile
```

세 이미지가 모두 digest를 돌려주고 같은 source commit을 checkout했는지 확인한다.

`v*` 릴리스를 checkout 없이 설치할 때는 위 두 블록 대신 [단일 서버의 릴리스 번들 받기](/run-server/self-hosting/single-server#릴리스-번들로-받기)를 따른다. 이후 단계는 번들 디렉터리에서 실행한다. 번들은 `backup`과 `reseed`를 거부하므로, 아래 "자주 막히는 곳"의 계획 재시작 절차는 같은 env 파일과 상태 디렉터리를 두고 그 릴리스의 `source_commit`을 checkout한 저장소에서 실행한다.

### 2. 시험 설정

비밀 값은 저장소 밖의 env 파일 `/etc/werft/test-ops.env`에만 둔다. 다음 블록은 설정 디렉터리와 상태 디렉터리를 운영자 소유로 만들고, `init-config`로 예시 파일에서 이 파일을 새로 만든다. 파일은 운영자만 읽을 수 있는 `0600`으로 생기고, 무작위 비밀 값은 화면에 나오지 않는다. 파일이 이미 있으면 덮어쓰지 않고 거부한다. `<console-origin>`에는 브라우저가 여는 콘솔의 origin을 넣는다. SSH tunnel이면 `http://127.0.0.1:<터널 포트>`다.

```bash
sudo install -d -m 755 -o "$USER" /etc/werft
sudo install -d -m 700 -o "$USER" /var/lib/werft/test-ops
TEST_OPS_OBJECT_STORE=localstack scripts/test-ops.sh init-config --console-origin '<console-origin>'
```

`init-config: wrote /etc/werft/test-ops.env`로 시작하는 줄이 나와야 한다. 인자와 채우는 값은 [단일 서버 설치의 2단계](/run-server/self-hosting/single-server#2-비밀과-설정-문서)와 같고, S3 인자 대신 `--localstack-port`로 LocalStack의 호스트 포트를 바꿀 수 있다. 예시 값인 `EXECUTION_INSTALLATION_ID=test-ops`, `PLATFORM_SETTINGS_DOCUMENT=/etc/werft/settings.json`, `EXECUTION_WORKSPACE_QUOTA=on`, private credential allowlist `localstack:4566`을 그대로 쓰고, AWS key·region·bucket 변수는 비워 둔다.

env 파일을 직접 쓰려면 `infra/test-ops.env.example`을 `/etc/werft/test-ops.env`에 운영자 소유 `0600`으로 복사하고 편집기로 다음을 채운다.

| 변수 | 값 |
| --- | --- |
| `POSTGRES_PASSWORD` | 무작위 값. 영문, 숫자, `.` `_` `~` `-`만 쓴다 |
| `EGRESS_AUTHORIZER_TOKEN` | 32자 이상 무작위 값 |
| `PLATFORM_SECRET_KEY` | `openssl rand -hex 32`의 64자 hex. 잃으면 저장한 자격 증명을 읽지 못한다 |

`CONSOLE_ORIGIN`은 직접 추가한다. `EXECUTION_INSTALLATION_ID=test-ops`, `PLATFORM_SETTINGS_DOCUMENT=/etc/werft/settings.json`, `EXECUTION_WORKSPACE_QUOTA=on`을 사용한다. credential allowlist는 `api.anthropic.com:443,github.com:443`, private credential allowlist는 `localstack:4566`이다. AWS key·region·bucket 변수는 예시처럼 비워 둔다. LocalStack은 고정 시험 key와 `claude-sessions` bucket을 사용한다.

설정 문서는 `/etc/werft/settings.json`에 둔다. 세션이 쓸 GitHub 저장소를 적는다. 첫 `deploy`가 빈 설치에 한 번 넣고, 그 뒤로는 문서를 고쳐도 들어가지 않으니 설정은 콘솔에서 바꾼다. 비밀이 없다. 저장소 URL만 실제 값으로 바꾼다. 예시는 공개 저장소 기준이다. 저장소 항목에는 `"auth": { "kind": "github_app" }`가 있어야 한다. 없으면 `preflight`가 문서 전체를 거절해 설치를 막는다. 비공개 저장소는 그 저장소에 GitHub App을 설치한다([GitHub](/integrations/github)).

migrate 컨테이너가 읽어야 하므로 파일은 `0644`로 둔다. 빈 파일을 먼저 만들고 편집기로 아래 내용을 채운다.

```bash
sudo install -m 644 -o "$USER" /dev/null /etc/werft/settings.json
```

```json
{
  "version": 1,
  "connections": {},
  "repositories": {
    "sample-app": {
      "url": "https://github.com/<owner>/<repo>.git",
      "branch": "main",
      "auth": { "kind": "github_app" }
    }
  }
}
```

### 3. release 입력과 설치

release 생성은 [단일 서버의 3단계](/run-server/self-hosting/single-server#3-release-입력-생성)와 같다. 번들로 받았다면 그 단계의 번들용 `manifest` 명령을 쓴다. 생성 위치는 checkout 밖의 `/var/lib/werft/test-ops/release.json`으로 한다. 이 단계는 S3용 preflight를 실행하지 않고 다음을 사용한다.

```bash
TEST_OPS_OBJECT_STORE=localstack scripts/test-ops.sh preflight /var/lib/werft/test-ops/release.json
TEST_OPS_OBJECT_STORE=localstack scripts/test-ops.sh deploy /var/lib/werft/test-ops/release.json
```

quota 검사와 서비스 health가 성공해야 한다. 모델 key는 설치 뒤 콘솔에 넣는다.

## 확인

`scripts/test-ops.sh status`, ready 본문과 200, docs 200을 확인한다. [첫 owner와 key](/run-server/self-hosting/users-and-keys)에서 인증을 확인한다. 운영 AWS S3 권한과 데이터가 있는 복원은 이 시험으로 증명하지 않는다.

## 자주 막히는 곳

첫 `deploy`가 실패하면 시작된 컨테이너는 남아 있고 `current.json`이 없어 `stop`을 쓸 수 없다. 실패 로그에서 quota·네트워크·Secret 등 원인을 확인하고, 이번 설치의 project 이름을 확인한 뒤 다음처럼 내린다. `-v`는 붙이지 않는다.

```bash
PROJECT='<this-installation-project>'
printf '%s\n' '{"services":{"x":{"image":"alpine:3"}},"networks":{"default":{}}}' \
  | docker compose --project-name "$PROJECT" -f - down --remove-orphans
```

원인을 고친 뒤 같은 release 파일과 같은 환경으로 `deploy`를 다시 실행한다. 이미 성공한 설치를 다시 시작할 때는 `start`를 쓴다.

`preflight`가 `path(s) the containers mount cannot be read by the user their container runs as`로 멈추면 적힌 경로를 괄호 안의 컨테이너 사용자가 읽지 못한다. postgres(uid 999)와 migrate(uid 1000)는 호스트 사용자로 돌지 않으므로, 제한적인 umask(`077`, `027`)에서 받은 checkout이나 번들, 또는 다른 사용자가 읽지 못하게 둔 설정 문서에서 생긴다. checkout이나 번들 디렉터리에 `chmod -R o+rX`, 설정 문서에 `chmod o+r`를 실행하거나 umask `022`에서 다시 받는다. postgres volume을 이미 초기화한 설치는 초기 SQL을 다시 읽지 않으므로, 지금까지 드러나지 않았더라도 이 검사가 있는 버전의 `upgrade`·`start`에서 처음 멈출 수 있다.

업그레이드가 LocalStack 컨테이너를 다시 만들면 object를 잃을 수 있다. `status`가 미수거 checkpoint 0개임을 확인하지 못하면 업그레이드를 미룬다. API 기동 실패와 `pending.json`이 겹치면 `reseed`도 거부되며, `reset`은 모든 데이터를 버린다. `backup --stop`은 이 차단을 해제하지 않는다.

LocalStack은 컨테이너가 다시 시작하면(호스트 재부팅, Docker 재시작, 컨테이너 재생성) 메모리의 object를 잃는다. bucket은 시작할 때마다 다시 만들어지지만 비어 있다. 이 시험 설치의 API는 그 상태에서 기동을 거부하지 않고, DB에 남은 미수거 checkpoint를 포기한 뒤 뜬다. 예고 없는 재부팅 뒤에 따로 할 일은 없고, `reset`을 쓰지 않는다.

- owner, key, 설정, 세션 목록은 남는다.
- 잃은 checkpoint가 복원 지점이던 세션은 닫힌 것을 빼고 `recovery_required`가 된다. 이전 맥락 없이 이어 갈지(`start_fresh`) 닫을지(`close`) 정한다([API 가이드](/reference/api-guide)의 복구 결정).
- API 로그에 `The object store came back empty`로 시작하는 경고 한 줄이 세션 수와 id를 남긴다.
- `/readyz`는 200 그대로이고, 본문의 `detail.checkpoints_forgotten_on_boot`에 그 세션 수를 적는다.

LocalStack 컨테이너만 따로 다시 시작하지 않는다. API가 떠 있는 동안에는 정리하지 않기 때문이다. 그 사이 새 checkpoint가 쓰이면 bucket이 비어 있지 않게 되어 다음 시작에서도 정리하지 않고, object를 잃은 세션은 복원할 때 실패한다. 그렇게 됐다면 바로 `scripts/test-ops.sh stop` 뒤 `start`로 설치 전체를 다시 시작한다.

`v0.4.0` 이하 릴리스는 정리하지 않는다. 그 API는 로그에 `Checkpoint bucket claude-sessions holds no object version`을 남기고 기동을 거부한다. 미리 `backup --stop`을 해 두지 않았다면 `reset`만 남는다. 자동 재시작과 수동 start의 조건은 [Compose 수명주기](/run-server/self-hosting/stop-compose)를 따른다.

세션의 맥락을 지키려면 계획 재시작 전에 백업하고 writer를 중지한다. 재시작 뒤에는 `start`가 아니라 `reseed`를 쓴다. `start`는 API를 빈 bucket으로 띄워 checkpoint를 포기하게 하고, 그 뒤에는 object를 되돌려도 포기한 checkpoint가 돌아오지 않는다.

```bash
# Back up, leave the writers stopped, restart the host, then restore the objects
scripts/test-ops.sh backup --stop
sudo reboot
scripts/test-ops.sh reseed /var/lib/werft/test-ops/backups/backup-<timestamp>
```

`reseed`는 원본 project/bucket/checksum과 빈 bucket, 마지막 백업 이후 checkpoint 변화가 없음을 검사한다. 조건을 만족하지 않으면 거부한다. object를 잃고 API 기동 실패와 pending upgrade가 남은 상태에서는 `reseed`가 거부된다. `backup --stop`으로 남긴 백업이 있어도 이 차단은 풀리지 않는다. 이 상태에서 `reset`을 고르면 DB·세션·checkpoint를 버리며, 일반적인 재부팅의 복구 명령으로 사용하지 않는다.

## 되돌리기

[Compose 중지·제거](/run-server/self-hosting/stop-compose)를 따른다. 성공한 설치는 `scripts/test-ops.sh stop`으로 이번 project를 내리고 volume을 보존한다. 첫 deploy 실패는 위의 명시 project와 stdin compose model을 쓰는 정리 절차를 따른다. checkpoint가 없는 시험이라는 이유로 운영 bucket이나 다른 설치를 정리하지 않는다. reset은 삭제 범위를 확인한 별도 선택이다.
