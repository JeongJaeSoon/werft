## 作業内容

いま設置するリリースは、[GitHub Releases](https://github.com/JeongJaeSoon/werft/releases/latest) で Latest と表示された `v*` リリースです。既定の設置方法は、そのリリースに添付されたバンドルで checkout なしに設置することです([リリースバンドルを取得する](#릴리스-번들로-받기))。手順 1 の最初のコマンドがそのタグを読みます。

一台の Linux に公開イメージを digest で固定して設置し、`/readyz` と `/docs` の応答を確認します。永続 AWS S3 を使います。この Compose 経路は独自 endpoint を指定できません。他の S3 互換 endpoint が必要なら [Kubernetes 設置](/run-server/self-hosting/kubernetes)に従います。高可用性が必要なら [Kubernetes](/run-server/self-hosting/kubernetes)を選びます。

<a id="준비물" />
## 準備

| 項目 | 要件 |
| --- | --- |
| OS | Linux。`x86_64` と `arm64` の両方に対応します |
| Docker Engine | 28 以上 |
| Docker Compose | 2.24.6 以上 |
| ディスク | Docker データルートが XFS で、`prjquota` 付きで mount されていること。`preflight` が quota probe でこれを確認し、満たさなければ止まります。ext4 サーバーでは先に [XFS ディスクの準備](/run-server/self-hosting/prepare-xfs)を完了します。Docker Desktop では使えません |
| 時刻 | NTP 同期。再起動後に Docker が自動起動すること |
| ツール | リリースバンドル設置では `jq`、`curl`、`openssl`、`sha256sum`、`tar`(gzip 対応)。checkout 設置では `git`、`jq`、`curl`、`openssl`、Bun 1.3.14、Docker Buildx プラグイン。どちらも Docker daemon にアクセスできるアカウント |
| object store | 永続 AWS S3 bucket。Compose test-ops は AWS S3 のみに対応し、独自 endpoint は指定できません。[bucket の準備](/run-server/self-hosting/prepare-checkpoint-bucket)で保護契約と権限を確認します |
| 外部 | `ghcr.io` と Docker Hub からイメージを取得できること。パッケージはログイン不要です。セッションは `api.anthropic.com` と `github.com` にアクセスします |

設置方法は二つです。既定は `v*` リリースの GitHub Release に添付されたバンドル(`werft-test-ops-<tag>.tar.gz`)で、checkout とホストの Bun なしに設置します。リポジトリ checkout はすべての公開タグ(`main-<12>`、`v<version>`)に使えます。どちらでも compose ファイルと `scripts/test-ops.sh` は取得したディレクトリから読み、イメージはビルドしません。バンドルは `upgrade`、`backup`、`reseed`、`restore-drill` を拒否します。これらは同じ env ファイルと状態ディレクトリのまま、そのリリースの `source_commit` を checkout したリポジトリで実行します。

- まず [XFS ディスク](/run-server/self-hosting/prepare-xfs)と [checkpoint bucket](/run-server/self-hosting/prepare-checkpoint-bucket)を準備します。
- リモート bootstrap 前に[アクセス経路](/run-server/self-hosting/access)を決めます。
- 設置環境ごとに別の project、設置 id、秘密ファイル、状態ディレクトリを使います。

## 手順

<a id="1-버전과-소스-고정" />
### 1. バージョンとソースの固定

現在の設定文書・モデル接続・秘密 key 契約に対応する公開タグを、変更履歴と照合して選びます。既定は [GitHub Releases](https://github.com/JeongJaeSoon/werft/releases) で Latest と表示されたリリースです。次のコマンドがそのタグを読みます。別の `v*` リリースを使うときは、`TAG` にそのタグを直接入れます。

```bash
TAG="$(curl -fsSL https://api.github.com/repos/JeongJaeSoon/werft/releases/latest | jq -er .tag_name)"
echo "$TAG"
```

`v` で始まるタグが出力される必要があります。空行が出たら取得に失敗しています。一緒に出た `curl` のエラーを確認し、再実行するか、選んだタグを `TAG` に直接入れます。

<a id="릴리스-번들로-받기" />
#### リリースバンドルを取得する

既定の設置方法です。`TAG` を決めたシェルで実行します。checkout とホストの Bun は不要です。

```bash
BASE="https://github.com/JeongJaeSoon/werft/releases/download/$TAG"
mkdir -p "$HOME/werft-releases/$TAG"
cd "$HOME/werft-releases/$TAG"
curl -fsSLO "$BASE/werft-test-ops-$TAG.tar.gz"
curl -fsSLO "$BASE/werft-test-ops-$TAG.tar.gz.sha256"
sha256sum -c "werft-test-ops-$TAG.tar.gz.sha256"
tar -xzf "werft-test-ops-$TAG.tar.gz"
cd "werft-test-ops-$TAG"
```

`sha256sum` が `OK` を出力する必要があります。sha256 はダウンロード中の破損だけを検出し、出所は証明しないため、この GitHub Release のアドレスから取得したファイルだけを使います。以降の手順の `infra/` と `scripts/` のパスはこのディレクトリが基準です。バンドルにはそのリリースの `release-manifest.json` が入っているため、手順 3 でイメージ digest を別に調べません。

<a id="저장소-checkout으로-받기" />
#### リポジトリ checkout を取得する

`main-<12>` のようにバンドルのない公開タグを設置するとき、またはリポジトリ checkout で設置するときは、バンドルのブロックの代わりに次の二つのブロックを実行します。次の二つの placeholder を、[パッケージ契約](/run-server/self-hosting/reference/packages)で得た実際のタグと、同じソース commit に置き換えます。イメージの main タグは Git タグではないため、checkout 値と同じとは考えないでください。

```bash
TAG='<published-image-tag>'
SOURCE_REF='<matching-source-commit-or-release-tag>'
for app in control-host worker egress-proxy; do
  echo "$app $(docker buildx imagetools inspect "ghcr.io/jeongjaesoon/werft-$app:$TAG" --format '{{.Manifest.Digest}}')"
done
```

三つのイメージ取得がすべて成功し、digest が返ってから進みます。

```bash
git clone https://github.com/JeongJaeSoon/werft.git
cd werft
git checkout "$SOURCE_REF"
bun install --frozen-lockfile
```

checkout は選んだ release の commit で、依存関係のインストールが成功している必要があります。release ファイルは checkout 外に保存し、clean checkout 条件を維持します。

<a id="2-비밀과-설정-문서" />
### 2. 秘密情報と設定文書

秘密の値はリポジトリ外の env ファイル `/etc/werft/test-ops.env` だけに置きます。`init-config` が取得したディレクトリの例のファイルからこのファイルを新しく作り、ランダムな秘密の値と引数で受け取った値を入れます。ファイルは運用者だけが読める `0600` で作られ、値は画面に表示されません。ファイルがすでにあれば上書きせずに拒否します。以降のコマンドは group や other に権限がある env ファイルを拒否します。

先に設定ディレクトリと状態ディレクトリを運用者の所有にします。

```bash
sudo install -d -m 755 -o "$USER" /etc/werft
sudo install -d -m 700 -o "$USER" /var/lib/werft/test-ops
```

bucket の API 資格情報はコマンドライン引数では受け取らず、このシェルの環境変数 `AWS_ACCESS_KEY_ID` と `AWS_SECRET_ACCESS_KEY` から読みます。シェルの履歴に残らないよう `read -s` で入力して export します。placeholder は下の表の値に置き換えます。

```bash
read -rs -p 'AWS_ACCESS_KEY_ID: ' AWS_ACCESS_KEY_ID; echo
read -rs -p 'AWS_SECRET_ACCESS_KEY: ' AWS_SECRET_ACCESS_KEY; echo
export AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY
TEST_OPS_OBJECT_STORE=s3 scripts/test-ops.sh init-config \
  --console-origin '<console-origin>' --aws-region '<region>' --s3-bucket '<bucket>'
unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY
```

`init-config: wrote /etc/werft/test-ops.env` で始まる行が出力されるはずです。拒否されると `error:` の行に理由が出て、ファイルは作られません。

| 引数 | 値 |
| --- | --- |
| `--console-origin` | 必須。ブラウザが開くコンソールの origin で、`CONSOLE_ORIGIN` になります。形式は `https://host[:port]` で、パスと末尾の `/` は付けません。SSH tunnel で開くなら `http://127.0.0.1:<tunnel port>` を指定します。http は `127.0.0.1`、`localhost`、`[::1]` でだけ受け付けます。この値がないと、コンソールから GitHub App を作る「GitHub で作成」ボタンが無効になり、Slack アカウント連携のリダイレクトと Slack のイベントアドレスを計算できないため Slack 連携が無効になり、[SSO ログイン](/run-server/self-hosting/sso)のプロバイダーも作成できません |
| `--aws-region`、`--s3-bucket` | S3 の設置では必須。準備した AWS bucket の region と名前で、`AWS_REGION`、`S3_BUCKET` になります。credential allowlist に `<bucket>.s3.<region>.amazonaws.com:443`（ドットを含む bucket 名では `s3.<region>.amazonaws.com:443`）を加え、private credential allowlist を空にします |
| `--installation-id` | 任意。既定値は `test-ops`。同じ Docker daemon の他の設置と重複しない id。`local` はローカルスタックの id なので使えません。デプロイ後に変更しません |
| `--settings-document` | 任意。既定値は `/etc/werft/settings.json`。下の設定文書の絶対パス |
| `--api-port`、`--postgres-port` | 任意。下のポートの表の `TEST_OPS_API_PORT`、`TEST_OPS_POSTGRES_PORT` になります |

`init-config` は `POSTGRES_PASSWORD`（32 文字 hex）、`EGRESS_AUTHORIZER_TOKEN`（48 文字 hex）、`PLATFORM_SECRET_KEY`（64 文字 hex）をランダムな値で埋めます。`EXECUTION_WORKSPACE_QUOTA=on` と provider・Git host の credential allowlist は例の値のままです。`CONSOLE_ORIGIN` とポートは `deploy` の前に決めます。最初の `deploy` がこの値でコンテナを作ります。設置後に変えるには、env ファイルを直して `scripts/test-ops.sh start` で同じ release を再適用します。バンドルでも checkout でもこのコマンドを使い、`upgrade` は要りません。実行中の環境でも、`start` は変わった値を受け取る api・scheduler・reconciler とその依存サービスのコンテナだけを作り直し、volume と記録された release はそのまま残します。`start: done` の行が出れば反映されています。

env ファイルを自分で書くには、取得したディレクトリの `infra/test-ops.env.example` を運用者所有の `0600` で `/etc/werft/test-ops.env` にコピーし、エディターで次を設定します。

| 変数 | 値 |
| --- | --- |
| `POSTGRES_PASSWORD` | ランダムな値。英字、数字、`.` `_` `~` `-` だけを使います |
| `EGRESS_AUTHORIZER_TOKEN` | 32 文字以上のランダムな値 |
| `PLATFORM_SECRET_KEY` | `openssl rand -hex 32` の 64 文字 hex。失うと保存した資格情報を読めなくなります。この設置はキーをこの変数で受け取るため、キーをファイルで渡す `PLATFORM_SECRET_KEY_FILE` は一緒に置きません。両方あってキーが違うと api と slack は起動しません |
| `CONSOLE_ORIGIN` | `--console-origin` と同じ値。env の例にはこの行がないため、自分で追加します |

例の LocalStack 値を運用 S3 の値に変更します。秘密をコマンドラインやログへ出力しないでください。

| 変数 | 運用環境の値 |
| --- | --- |
| `EXECUTION_INSTALLATION_ID` | 他の環境と重複しない id。デプロイ後に変更しません |
| `PLATFORM_SETTINGS_DOCUMENT` | `/etc/werft/settings.json` |
| `EXECUTION_WORKSPACE_QUOTA` | `on` |
| `AWS_REGION`、`S3_BUCKET` | 準備した AWS bucket の region と名前。独自 endpoint は未対応です |
| `AWS_ACCESS_KEY_ID`、`AWS_SECRET_ACCESS_KEY` | bucket の最小権限の API 資格情報 |
| `EGRESS_CREDENTIAL_ALLOWLIST` | provider・Git host と `<bucket>.s3.<region>.amazonaws.com:443`。ドットを含む bucket 名では `s3.<region>.amazonaws.com:443` |
| `EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST` | 空の値。`localstack:4566` を削除します |

ホストのポートがすでに使われている場合は、`init-config` のポート引数で渡すか、env ファイルに次を入れます。値を指定しなければ既定値を使い、どの値でも `127.0.0.1` にだけ開きます。

| 変数 | 既定値 | 値 |
| --- | --- | --- |
| `TEST_OPS_API_PORT` | `3000` | API と Web コンソールのホストポート。1〜65535 |
| `TEST_OPS_POSTGRES_PORT` | `5432` | postgres のホストポート。1〜65535 |
| `TEST_OPS_LOCALSTACK_PORT` | `4566` | [LocalStack の試用設置](/run-server/self-hosting/try-localstack)のホストポート。1〜65535。S3 の設置では無視します |
| `TEST_OPS_API_URL` | `http://127.0.0.1:<TEST_OPS_API_PORT>` | `deploy`・`upgrade`・`status` が `/readyz` を確認するアドレス。ホストの前にプロキシを置くときだけ入れます。形式は `scheme://host[:port]` で、パスと末尾の `/` は付けません |

`preflight` は範囲外のポート、二つのサービスが同じポートを使う値、形式の誤った URL を拒否します。設置後にポートを変えるには、env ファイルを直して `scripts/test-ops.sh start` で同じ release を再適用します。トンネルと `curl` のポートも合わせて変えます。`TEST_OPS_LOCALSTACK_PORT` を変えると LocalStack コンテナが作り直されて object がすべて消えるため、`preflight` は実行中のポートと違う値を拒否します。`scripts/test-ops.sh backup --stop` でバックアップし、env ファイルを直してから、そのバックアップで `reseed` を呼びます。

env ファイルを `/etc/werft/test-ops.env` 以外の場所に置く場合は、スクリプトを呼ぶたびに `TEST_OPS_ENV_FILE` にそのパスを渡します。

モデル key は設置後にコンソールのモデル接続で入力するため、`ANTHROPIC_API_KEY` は空のままにします。ただし `v0.1.0` タグでは compose がこれを必須とし、空のままだと `preflight` が exit 1 で終わるため、env ファイルにモデル key (または後でコンソールで差し替える仮の値) を入れます。`PLATFORM_SECRET_KEY` を失うと保存した資格情報を読めなくなるため、別途安全にバックアップします。

設定文書は `/etc/werft/settings.json` に置き、セッションが使う GitHub リポジトリを書きます。最初の `deploy` が空のインストールに一度だけ入れ、その後は文書を直しても取り込まれないため、設定はコンソールで変更します。秘密情報は含みません。リポジトリ URL だけを実際の値に変更します。例は公開リポジトリ用です。リポジトリ項目には `"auth": { "kind": "github_app" }` が必要です。なければ `preflight` が文書全体を拒否し、設置を止めます。非公開リポジトリは、そのリポジトリに GitHub App をインストールします（[GitHub](/integrations/github)）。

migrate コンテナが読む必要があるため、ファイルは `0644` にします。先に空のファイルを作り、エディターで次の内容を入れます。

```bash
sudo install -m 644 -o "$USER" /dev/null /etc/werft/settings.json
```

```json
{
  "version": 1,
  "connections": {},
  "repositories": {
    "sample-app": {
      "url": "https://github.com/<owner>/<repo>.git",
      "branch": "main",
      "auth": { "kind": "github_app" }
    }
  }
}
```

リポジトリ URL は実際に使う公開リポジトリに変更します。非公開リポジトリの GitHub App は[手順 2 の入力一覧の CONSOLE_ORIGIN](#2-비밀과-설정-문서)を準備してから、設置したコンソールで構成します。ファイルは秘密を含まず、migrate が読める必要があります。

<a id="3-release-입력-생성" />
### 3. release 入力の生成

選んだ TAG を保持したシェルで実行します。`DEPLOYMENT_DIR` は取得したディレクトリの外にある環境別ディレクトリです。リリースバンドルで取得した場合は、バンドルのディレクトリで次を実行します。`manifest` は、バンドル内のリリース manifest の commit とイメージ digest に設定文書の digest を加え、release ファイルを作ります。

```bash
DEPLOYMENT_DIR=/var/lib/werft/test-ops
scripts/test-ops.sh manifest release-manifest.json /etc/werft/settings.json > "$DEPLOYMENT_DIR/release.json"
```

手順 4 と `setup-link` も、バンドルのディレクトリで同じコマンドを実行します。バンドルの `preflight` と `deploy` は、このファイルの commit やイメージがバンドルのリリースと違えば拒否します。

リポジトリ checkout で取得した場合は、上のブロックの代わりに checkout で次を実行します。同じ形式のファイルを作ります。

```bash
DEPLOYMENT_DIR=/var/lib/werft/test-ops
SETTINGS_DIGEST="$(bun run scripts/lib/test-ops.ts settings-digest /etc/werft/settings.json)"
digest() { docker buildx imagetools inspect "ghcr.io/jeongjaesoon/werft-$1:$TAG" --format '{{.Manifest.Digest}}'; }
jq -n \
  --arg commit "$(git rev-parse HEAD)" \
  --arg control "ghcr.io/jeongjaesoon/werft-control-host@$(digest control-host)" \
  --arg worker "ghcr.io/jeongjaesoon/werft-worker@$(digest worker)" \
  --arg egress "ghcr.io/jeongjaesoon/werft-egress-proxy@$(digest egress-proxy)" \
  --arg settings "$SETTINGS_DIGEST" \
  '{source_commit: $commit,
    images: {control_host: $control, worker: $worker, egress_proxy: $egress},
    settings_digest: $settings}' > "$DEPLOYMENT_DIR/release.json"
```

三つのイメージ digest がすべて空でないことを確認します。

<a id="4-s3를-명시해-검사설치" />
### 4. S3 を明示して検査・設置

```bash
TEST_OPS_OBJECT_STORE=s3 scripts/test-ops.sh preflight "$DEPLOYMENT_DIR/release.json"
TEST_OPS_OBJECT_STORE=s3 scripts/test-ops.sh deploy "$DEPLOYMENT_DIR/release.json"
```

preflight は bucket の保護設定と scratch version の書き込み・hold・読み取り・hold 解除・削除を検査します。workspace quota probe も先に実行し、deploy 時に scheduler が quota を再度検査します。両方成功し、サービスが healthy になる必要があります。object store 方式は最初の deploy 後に変更できません。

deploy の後で、最初の owner を作る一回限りの設定リンクをファイルとして受け取ります。owner になる人のメールアドレスと、`DEPLOYMENT_DIR` の中でまだ存在しないファイル名を渡します。バンドルのディレクトリの中は test-ops が拒否します（バンドルには SHA256SUMS に載ったファイルだけが必要です）。ファイルは 0600 で作られ、画面にはファイルのパスと期限だけが出ます。

```bash
scripts/test-ops.sh setup-link --email <owner-email> --out "$DEPLOYMENT_DIR/owner-link.json"
```

ファイルの `accept_url`（なければコンソールのアドレスの後ろに `accept_path`）を開き、コマンドに渡したメールアドレスで owner を作ります。ブラウザがない場合の方法とファイルの項目は、[最初の owner と key](/run-server/self-hosting/users-and-keys) にあります。リンクは一度使うとすぐ無効になり、24 時間で期限切れになります。ファイルを失ったり期限が切れたりしたら、新しいファイル名でコマンドを再実行します。新しいリンクが発行され、前のリンクは無効になります。owner ができた後は、リンクもファイルも作らず終了コード 1 で終わります。

<a id="확인" />
## 確認

```bash
scripts/test-ops.sh status
curl --max-time 10 -fsS -w '\n%{http_code}\n' http://127.0.0.1:3000/readyz
curl --max-time 10 -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/docs
```

ready の本文と 200、docs 200、各サービスの healthy を確認します。PostgreSQL は loopback だけで待ち受け、Docker TCP socket は外部から到達できない必要があります。

<a id="자주-막히는-곳" />
## よくある問題

最初の `deploy` が失敗すると、起動したコンテナが残り、`current.json` がないため `stop` は使えません。失敗ログで quota・network・Secret などの原因を確認し、今回の project 名を確認してから次のように停止・削除します。`-v` は付けません。

```bash
PROJECT='<this-installation-project>'
printf '%s\n' '{"services":{"x":{"image":"alpine:3"}},"networks":{"default":{}}}' \
  | docker compose --project-name "$PROJECT" -f - down --remove-orphans
```

原因を直し、同じ release ファイルと同じ環境で `deploy` を再実行します。成功済みの環境を再起動するときは `start` を使います。

`preflight` が `path(s) the containers mount cannot be read by the user their container runs as` で止まった場合、括弧内のコンテナユーザーが表示されたパスを読めません。postgres（uid 999）と migrate（uid 1000）はホストのユーザーとして実行されないため、制限的な umask（`077`、`027`）で作られたリポジトリの checkout やバンドル、または他のユーザーが読めない設定文書が原因です。checkout またはバンドルのディレクトリに `chmod -R o+rX`、設定文書に `chmod o+r` を実行するか、umask `022` で取得し直します。postgres volume が初期化済みの設置は初期 SQL を再度読まないため、これまで問題が出ていなくても、この検査がある版の `upgrade`・`start` で初めて止まることがあります。

quota エラーは [XFS の準備](/run-server/self-hosting/prepare-xfs)、bucket の保護・権限エラーは [bucket の準備](/run-server/self-hosting/prepare-checkpoint-bucket)を確認します。env 権限エラーは[手順 2 のファイル mode](#2-비밀과-설정-문서)、settings digest エラーは[手順 3 の digest・release 入力生成](#3-release-입력-생성)を確認します。最初の deploy が失敗しても、正常デプロイの状態ファイルがあるとは考えないでください。

設定文書のリポジトリ項目に `"auth": {"kind": "github_app"}` がないと、`preflight`・`deploy`・`upgrade` はイメージを取得する前に拒否し、コンテナも `pending.json` もできません。文書を直すと digest が変わるため、release ファイルの `settings_digest` も新しい値に直します。DB に同じ id の行がすでにあると、`auth` を足した項目は内容が違うため `conflicts` で拒否されます。文書からその項目を消すか、新しい id を付けます。この衝突で `upgrade` が `pending.json` を残して止まった場合は、直した release ファイルを `pending.json` にコピーしてから、そのファイルで `upgrade` を再実行します。

```bash
cp "$DEPLOYMENT_DIR/release.json" "$DEPLOYMENT_DIR/pending.json"
TEST_OPS_OBJECT_STORE=s3 scripts/test-ops.sh upgrade "$DEPLOYMENT_DIR/release.json"
```

<a id="되돌리기" />
## 元に戻す

正常な環境は[停止・再起動](/run-server/self-hosting/stop-compose)でデータを保持します。最初の deploy の失敗では、原因とこの project が作ったリソースを先に調べます。reset や volume 削除を既定の後片付けにしないでください。必要なデータがないことを確認した環境だけ、別の削除手順に従います。
