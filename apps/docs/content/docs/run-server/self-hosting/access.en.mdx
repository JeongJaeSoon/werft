## What you will do

Before remote bootstrap, configure an SSH tunnel or a TLS-protected, network-restricted access path, then check the console, API, and SSE. If you connect Slack, also configure a public entrance that opens only the Slack paths.

<a id="준비물" />
## Before you begin

You need an installed server and SSH access, or organizational TLS certificates and a VPN/IP allowlist. Do not expose PostgreSQL or the Docker socket externally. Clients must trust private CAs; do not bypass verification with curl `-k`.

<a id="단계" />
## Steps

### Compose: SSH tunnel

```bash
ssh -N -L 3000:127.0.0.1:3000 <user>@<server>
```

Leave this terminal open and connect to `http://127.0.0.1:3000` from another terminal or browser.

### Compose: TLS reverse proxy

API (default 3000) and PostgreSQL (default 5432) bind only to host loopback. Users enter through an SSH tunnel; operators use PostgreSQL only on the server. Allow only SSH and the selected TLS endpoint through the firewall.

To expose the API through an internal DNS name, put a reverse proxy in front, retaining upstream `127.0.0.1:3000`. Restrict access to VPN ranges or an IP allowlist and terminate TLS at the proxy. Preserve the browser's `Host` when forwarding upstream. The API rejects browser state changes when the `Origin` host differs from `Host`; replacing it with the upstream host breaks console mutations. SSE connections are long-lived: disable `proxy_buffering` and request buffering, and use long read/send timeouts such as 1 hour. Keep PostgreSQL and the Docker socket inside the proxy/firewall boundary on every path. Only the scheduler uses the socket to manage workers; do not enable a host TCP socket.

Use your organization's certificate paths, internal DNS name, and permitted ranges. Explicitly allow loopback if test requests from the same server should work. Match `Host` with browser `Origin` and disable SSE buffering. The console entrance `server` block in [Public entrance](#공개-입구-slack-경로만-열기) below is an example.

<a id="공개-입구-slack-경로만-열기" />
### Public entrance: open only the Slack paths

To receive Slack events and button or modal interactions, Slack needs a public https entrance. Slack calls only two addresses, `POST /v1/slack/events/{agent_id}` and `POST /v1/slack/interactions/{agent_id}`, and both check the agent app's signing secret signature instead of a cookie or API key. The public entrance forwards only these two paths to the api and answers everything else with 404 at the proxy. The OAuth redirects of Slack app install and account linking bring the browser back to the console address (`CONSOLE_ORIGIN`), so do not open them on the public entrance.

Port 3000 of the api serves the console and the `/v1` API. Workers' `/internal` is served on port 3200 alone, and the api answers `/internal` on port 3000 with 404. Compose does not bind port 3200 on the host, and the chart opens it only on a ClusterIP Service inside the cluster. Up to v0.4.0 the api image also serves `/internal` on port 3000, so a tunnel or proxy that publishes all of port 3000 exposes `/internal` to the internet too. Split the public entrance (Slack paths only) and the console entrance (behind a VPN or IP allowlist) onto different DNS names, and block `/internal` on the console entrance as well. Bun turns a backslash into `/`, which slips a path past an `/internal` rule, so whatever the proxy, refuse a path containing `\` or `%5C` with 400.

The example below splits the two entrances with nginx on a Compose server. `<hooks-host>` is the public DNS name, `<console-host>` the host of `CONSOLE_ORIGIN`, and `<allowed-cidr>` the range allowed into the console. Use your organization's certificate paths.

```nginx
# Public entry: only the two request URLs Slack calls reach the API.
server {
    listen 443 ssl;
    server_name <hooks-host>;
    ssl_certificate     <certificate-path>;
    ssl_certificate_key <certificate-key-path>;

    location ~ "^/v1/slack/(events|interactions)/[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$" {
        limit_except POST { deny all; }
        proxy_pass http://127.0.0.1:3000$uri;
        proxy_set_header Host $http_host;
    }

    location / {
        return 404;
    }
}

# Console entry: allowlisted networks only, /internal never forwarded.
server {
    listen 443 ssl;
    server_name <console-host>;
    ssl_certificate     <certificate-path>;
    ssl_certificate_key <certificate-key-path>;

    allow <allowed-cidr>;
    allow 127.0.0.1;
    deny all;

    if ($request_uri ~* "\\\\|%5c") {
        return 400;
    }

    location ^~ /internal {
        return 404;
    }

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $http_host;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_buffering off;
        proxy_request_buffering off;
        proxy_read_timeout 1h;
        proxy_send_timeout 1h;
    }
}
```

- The public entrance's `location` matches only when the path nginx decoded and normalized is one of the two Slack paths followed by an `agent_id` (a lowercase UUID). The api is sent that normalized path (`$uri`), not the original request line, so whatever `..` or backslashes a request mixes in, only a Slack path reaches the api. Everything else gets 404, and a request other than POST gets 403. The query is not forwarded; the addresses Slack is sent have none.
- The console entrance answers `/internal` and everything under it with 404. nginx decodes and normalizes encoded paths such as `/%69nternal/x` and `/x/../internal/x` before choosing a `location`, so those get 404 too. nginx does not treat a backslash as a path separator, but Bun in front of the api turns it into `/`, making `/x/..\internal/x` into `/internal/x`. So a request line with `\` or `%5C` is refused with 400.
- `Host` is passed as `$http_host`, the browser's value with its port. `$host` drops the port, so a console on a port other than 443 would have its changes refused for not matching `Origin`.
- The console entrance carries the event stream (SSE), so it turns buffering off and sets read and send timeouts of 1 hour.

When the public entrance's DNS name differs from the console's, an owner saves `https://<hooks-host>` as the events entrance under **Settings > Integrations > Slack** (`PUT /v1/slack-settings`). A path prefix in the saved address is kept in the URL Slack is sent; the example above does not strip a prefix, so save the host only. Saving sends the new address to every agent app made before, and shows per app whether it was sent and why not. **Send the apps not sent again** retries the ones that were not.

A tunnel (for example Cloudflare Tunnel) as the public entrance follows the same rules. Send only the two Slack paths on the public hostname to `http://127.0.0.1:3000`, let everything else answer 404, and keep the console on another hostname behind access restrictions. Tunnel products normalize paths differently, so after writing the rules run the check below against the public address.

```bash
for p in /v1/slack/events/00000000-0000-0000-0000-000000000000 /v1/auth/login-methods / /internal/x /%69nternal/x /x/../internal/x '/x/..\internal/x'; do
  curl -s --path-as-is -o /dev/null -X POST -w "$p %{http_code} %{content_type}\n" "https://<hooks-host>$p"
done
```

Only the first line is the api's answer (4xx without a signature, `application/json`); every other line is the proxy's 404 (`text/html` from nginx). An `application/json` on any other line means that path reached the api: take the public entrance down and fix the rules. For the console entrance, run the loop in [Verify](#확인) against `<console-host>`. With the nginx example, the two lines with a backslash give 400, the rest 404, and no line is `application/json`.

### Kubernetes: internal ALB

Copy `values-aws.example.yaml` to an installation-specific file, fill placeholders (account id, ARN, host, digest), and layer it over `values.yaml`. Rendering below runs locally; applying its output is **AWS-only**.

**The AWS example assumes an internal ALB.** Its Ingress `scheme` annotation is already `internal`; do not change it to `internet-facing` in your installation file. `render-check` rejects `internet-facing` when rendering the example. After applying, verify the ALB was created in internal subnets (**AWS-only**).

<a id="웹-콘솔과-internal" />
### Web console and `/internal`

api serves the web console on port 3000. With `ingress.console.enabled: true` (default `false`), Ingress routes `/` (Prefix) to the api Service. The api does not serve `/internal` on that port (images up to v0.4.0 do), but the `/` Prefix also matches `/internal`. The chart therefore places an `/internal` (Prefix) rule before `/`, pointing to the fixed-response action (404, `text/plain`) in `alb.ingress.kubernetes.io/actions.block-internal`, rather than api. AWS Load Balancer Controller evaluates longer prefixes first, so the ALB returns 404 for `/internal` and its children. `render-check` verifies ordering, the 404 action, and that other paths reach the api Service's `http` port (3000).

This rule works only on ALB. Other controllers might skip the nonexistent `block-internal` Service and expose `/internal` through `/`, so chart rendering rejects `ingress.className` values other than `alb`. Rendering also rejects `ingress.annotations` entries that can bypass the 404 rule: `alb.ingress.kubernetes.io/` `actions.*`, `conditions.*`, `transforms.*`, `group.*`, and `kubernetes.io/ingress.class`. If the IngressClass's `IngressClassParams` groups this Ingress with another, earlier Ingress rules take precedence. Before enabling the console, confirm the `alb` IngressClass does not force a group (**AWS-only**).

**Enabling conditions.** api routes using percent-decoded paths. ALB path patterns cannot contain `%`, so encoded paths such as `/%69nternal/…` bypass the `/internal` rule and reach api through `/`. api routes to workers only when the undecoded path begins with `/internal`; encoded variants return 404 `NOT_FOUND`. Enable `ingress.console.enabled` only with an api image containing this behavior.

Bun normalizes dot segments (`/x/../internal/…`, `/%2e/internal/…`) and backslashes (`/internal\…`, `/x/..\internal/…`) to `/internal/…` before api receives them, making them indistinguishable there. ALB must block these. ALB normalizes URIs before rule evaluation, but its documentation does not specify the transformations. After enabling the console, send the following requests from the internal network (**AWS-only**). `/%69nternal/x` should return api's 404 (`application/json`); ALB normalization returning `text/plain` 404 is also safe. All other paths should return ALB's 404 (`text/plain`). api `/internal` routes always return `application/json`, regardless of status. A JSON response for a dot-segment or backslash path means ALB forwarded it to api: disable console ingress again. An ALB-generated rejection such as 400 is safe. With an api image that has no `/internal` on port 3000, the api answers such a forwarded path with 404 `NOT_FOUND` and it reaches no worker route. A JSON response still means the ALB rule missed that path, so treat it as above.

```bash
for p in /internal/x /%69nternal/x /x/../internal/x /%2e/internal/x '/internal\x' '/x/..\internal/x'; do
  curl -s --path-as-is -o /dev/null -w "$p %{http_code} %{content_type}\n" "https://<host>$p"
done
```

To enable, add the following to the installation file. Disabling removes both `/` and `/internal` rules while retaining `/v1`, `/docs`, `/healthz`, and `/readyz`.

```yaml
ingress:
  className: alb
  console:
    enabled: true
```

After applying, check from the internal network (**AWS-only**). `curl -s -o /dev/null -w '%{http_code}\n' https://<host>/` should return 200. `curl -si -X POST https://<host>/internal/worker/x` should return 404 with `content-type: text/plain` and no api-added `x-request-id`. api's 404 uses `application/json` and includes `x-request-id`, so status alone cannot prove ALB blocked the request.

```bash
helm lint deploy/helm/werft -f deploy/helm/werft/values-aws.example.yaml   # render only
helm template werft deploy/helm/werft \
  -f deploy/helm/werft/values-aws.example.yaml >/dev/null                          # render only
helm upgrade --install werft deploy/helm/werft \
  --namespace werft -f values-aws-<installation>.yaml --timeout 10m               # requires AWS resources
```

## Verify

```bash
for p in /internal/x /%69nternal/x /x/../internal/x /%2e/internal/x '/internal\x' '/x/..\internal/x'; do
  curl -s --path-as-is -o /dev/null -w "$p %{http_code} %{content_type}\n" "https://<host>$p"
done
```

Check `/readyz`, `/docs`, `/docs/scalar.js`, and the console through the selected path. For an authenticated event stream, use `curl -sSN --max-time 5` to observe content. Distinguish the timeout ending curl from the persistent connection you observed. Requests outside the allowlist must be blocked. Also check login cookies and Origin validation for mutations. Local checks in this document do not prove actual internal DNS, VPN, or AWS ALB paths.

## Troubleshooting

Untrusted TLS certificates make browsers block connections. Replacing Host with the upstream value rejects console mutations. If ALB normalization tests forward internal paths to the API, disable console Ingress immediately.

<a id="되돌리기" />
## Roll back

End the tunnel in its terminal. Restore the reverse proxy changes from backup. Remove the public entrance's `server` block (or tunnel rules); Slack events stop arriving after that. For Kubernetes, restore `ingress.console.enabled` to false in installation values and apply. Confirm `/internal` and the authorizer are not exposed externally.
