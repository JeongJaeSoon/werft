## What you will do

Install published images pinned by digest on one Linux server and check `/readyz` and `/docs`. This uses persistent AWS S3. This Compose path does not accept custom endpoints. For another S3-compatible endpoint, follow [Kubernetes installation](/run-server/self-hosting/kubernetes). Choose [Kubernetes](/run-server/self-hosting/kubernetes) if you need high availability.

<a id="준비물" />
## Before you begin

| Item | Requirement |
| --- | --- |
| Operating system | Linux, both `x86_64` and `arm64` |
| Docker Engine | 28 or later |
| Docker Compose | 2.24.6 or later |
| Disk | Docker data-root on XFS mounted with `prjquota`. `preflight` does not check this. Otherwise the scheduler quota check fails during `deploy` and installation stops. Complete [XFS preparation](/run-server/self-hosting/prepare-xfs) first on ext4 servers. Docker Desktop is unsupported |
| Time | NTP synchronized. Docker starts automatically after reboot |
| Tools | For a checkout installation, `git`, `jq`, `curl`, `openssl`, Bun 1.3.14, and the Docker Buildx plugin. For a release bundle installation, `jq`, `curl`, `openssl`, `sha256sum`, and `tar` (with gzip). Both need an account with Docker daemon access |
| Object store | Persistent AWS S3 bucket. Compose test-ops supports AWS S3 only, without custom endpoints. Check protection and permissions in [Bucket preparation](/run-server/self-hosting/prepare-checkpoint-bucket) |
| External access | Download images from `ghcr.io` and Docker Hub without signing in. Sessions connect to `api.anthropic.com` and `github.com` |

There are two ways to install. A repository checkout works for every published tag (`main-<12>`, `v<version>`). A `v*` release can also be installed from the bundle attached to its GitHub Release (`werft-test-ops-<tag>.tar.gz`), with no checkout and no host Bun. Either way, the Compose files and `scripts/test-ops.sh` are read from the downloaded directory, and no image is built. The bundle refuses `upgrade`, `backup`, `reseed`, and `restore-drill`. Run those from a repository checked out at the release's `source_commit`, with the same env file and state directory.

- Prepare the [XFS disk](/run-server/self-hosting/prepare-xfs) and [checkpoint bucket](/run-server/self-hosting/prepare-checkpoint-bucket) first.
- Choose an [access path](/run-server/self-hosting/access) before remote bootstrap.
- Use a separate project, installation id, secret file, and state directory for every installation.

<a id="단계" />
## Steps

<a id="1-버전과-소스-고정" />
### 1. Pin the version and source

Check the changelog and select a published tag supporting the current settings document, model connection, and secret-key contracts. Replace the two placeholders below with an actual tag and its matching source commit from the [package contract](/run-server/self-hosting/reference/packages). An image main tag is not a Git tag; do not assume it is also the checkout reference.

```bash
TAG='<published-image-tag>'
SOURCE_REF='<matching-source-commit-or-release-tag>'
for app in control-host worker egress-proxy; do
  echo "$app $(docker buildx imagetools inspect "ghcr.io/jeongjaesoon/werft-$app:$TAG" --format '{{.Manifest.Digest}}')"
done
```

Continue only after all three image queries succeed and return digests.

```bash
git clone https://github.com/JeongJaeSoon/werft.git
cd werft
git checkout "$SOURCE_REF"
bun install --frozen-lockfile
```

The checkout must match the selected release commit, and dependency installation must succeed. Store the release file outside the checkout to keep the checkout clean.

<a id="릴리스-번들로-받기" />
#### Get the release bundle

To install a `v*` release without a checkout, run the following instead of the two blocks above. `TAG` is the release tag chosen from the [package contract](/run-server/self-hosting/reference/packages).

```bash
TAG='<release-tag>'
BASE="https://github.com/JeongJaeSoon/werft/releases/download/$TAG"
mkdir -p "$HOME/werft-releases/$TAG"
cd "$HOME/werft-releases/$TAG"
curl -fsSLO "$BASE/werft-test-ops-$TAG.tar.gz"
curl -fsSLO "$BASE/werft-test-ops-$TAG.tar.gz.sha256"
sha256sum -c "werft-test-ops-$TAG.tar.gz.sha256"
tar -xzf "werft-test-ops-$TAG.tar.gz"
cd "werft-test-ops-$TAG"
```

`sha256sum` must print `OK`. The sha256 only catches a damaged download and does not prove where the file came from, so use only files downloaded from this GitHub Release address. The `infra/` and `scripts/` paths in later steps are relative to this directory. The bundle carries the release's `release-manifest.json`, so step 3 does not look up image digests separately.

<a id="2-비밀과-설정-문서" />
### 2. Secrets and settings document

Keep secrets only in an env file outside the repository, readable only by operators. The script rejects group or other permissions.

```bash
sudo mkdir -p /etc/werft
sudo install -m 600 -o "$USER" infra/test-ops.env.example /etc/werft/test-ops.env
sudo install -d -m 700 -o "$USER" /var/lib/werft/test-ops
```

Open `/etc/werft/test-ops.env` in an editor and fill in the following. Tools such as `sed -i` create temporary files and fail with `Permission denied` in `/etc/werft`; use an editor that writes in place.

| Variable | Value |
| --- | --- |
| `POSTGRES_PASSWORD` | Random value using only letters, digits, `.`, `_`, `~`, and `-` |
| `EGRESS_AUTHORIZER_TOKEN` | Random value of at least 32 characters |
| `PLATFORM_SECRET_KEY` | 64-character hex from `openssl rand -hex 32`. Losing it prevents reading stored credentials |
| `BOOTSTRAP_TOKEN` | Leave it commented out. The API generates the first owner's token, and `scripts/test-ops.sh bootstrap-token` shows it once after `deploy` in step 4. For a fixed value, uncomment it and enter a random 32–256-character token; the command then prints no token |
| `CONSOLE_ORIGIN` | The browser console origin (`scheme://host[:port]`) required to create a GitHub App through the console. Without it, the Create on GitHub button is disabled. The Slack account-link redirect and the Slack events address are computed from it too (without it, Slack linking is off). The redirect URI of [SSO sign-in](/run-server/self-hosting/sso) providers is built from it as well; without it, no provider can be created. Add this line yourself; it is absent from the example env file. For an SSH tunnel, use `http://127.0.0.1:<tunnel port>`. To apply additions or changes after installation, reapply the current release with `TEST_OPS_OBJECT_STORE=s3 scripts/test-ops.sh upgrade /var/lib/werft/test-ops/current.json`, rather than `start` |

Replace the example LocalStack values with production S3 values. Do not print secrets in command lines or logs.

| Variable | Production value |
| --- | --- |
| `EXECUTION_INSTALLATION_ID` | An id unique to this installation. Do not change it after deployment |
| `PLATFORM_SETTINGS_DOCUMENT` | `/etc/werft/settings.json` |
| `EXECUTION_WORKSPACE_QUOTA` | `on` |
| `AWS_REGION`, `S3_BUCKET` | Prepared AWS bucket region and name. Custom endpoints are unsupported |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | API credentials with minimum bucket permissions |
| `EGRESS_CREDENTIAL_ALLOWLIST` | Provider/Git hosts plus `<bucket>.s3.<region>.amazonaws.com:443`. For dotted bucket names, use `s3.<region>.amazonaws.com:443` |
| `EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST` | Empty. Remove `localstack:4566` |

Add model keys through console model connections after installation, so the `v0.1.2` tag leaves `ANTHROPIC_API_KEY` empty. On a `v0.1.0` tag checkout, however, compose requires it, and `preflight` exits 1 when it is empty. On that version, put the model key (or a placeholder you will replace later in the console) in the env file. The change that allows an empty value came in with [JeongJaeSoon/werft#1262](https://github.com/JeongJaeSoon/werft/pull/1262), and `v0.1.2` is the first published release that includes it. Back up `PLATFORM_SECRET_KEY` securely and separately: losing it prevents reading stored credentials.

Put the settings document at `/etc/werft/settings.json`, listing the GitHub repositories sessions will use. It contains no secrets. Replace only the repository URL with your actual value; this example assumes a public repository. Every repository entry needs `"auth": { "kind": "github_app" }`. Otherwise import omits it and `preflight` blocks installation. For private repository authentication, see the [API server documentation](https://github.com/JeongJaeSoon/werft/blob/main/docs/operator/api-server.md).

The migrate container must read the file, so use `0644`. Create an empty file, then fill in the following using an editor.

```bash
sudo install -m 644 -o "$USER" /dev/null /etc/werft/settings.json
```

```json
{
  "version": 1,
  "connections": {},
  "repositories": {
    "sample-app": {
      "url": "https://github.com/<owner>/<repo>.git",
      "branch": "main",
      "auth": { "kind": "github_app" }
    }
  },
  "mcp_servers": {}
}
```

Replace the URL with the public repository you will use. For private repositories, prepare [CONSOLE_ORIGIN in the step 2 input table](#2-비밀과-설정-문서), then configure the GitHub App in the installed console. The file contains no secrets and must remain readable by migrate.

<a id="3-release-입력-생성" />
### 3. Generate release input

Run this in the shell retaining the selected TAG. `DEPLOYMENT_DIR` is an installation-specific directory outside the checkout.

```bash
DEPLOYMENT_DIR=/var/lib/werft/test-ops
SETTINGS_DIGEST="$(bun run scripts/lib/test-ops.ts settings-digest /etc/werft/settings.json)"
digest() { docker buildx imagetools inspect "ghcr.io/jeongjaesoon/werft-$1:$TAG" --format '{{.Manifest.Digest}}'; }
jq -n \
  --arg commit "$(git rev-parse HEAD)" \
  --arg control "ghcr.io/jeongjaesoon/werft-control-host@$(digest control-host)" \
  --arg worker "ghcr.io/jeongjaesoon/werft-worker@$(digest worker)" \
  --arg egress "ghcr.io/jeongjaesoon/werft-egress-proxy@$(digest egress-proxy)" \
  --arg settings "$SETTINGS_DIGEST" \
  '{source_commit: $commit,
    images: {control_host: $control, worker: $worker, egress_proxy: $egress},
    settings_digest: $settings}' > "$DEPLOYMENT_DIR/release.json"
```

Confirm all three image digests are nonempty.

If you downloaded the release bundle, run the following in the bundle directory instead of the block above. `manifest` writes a file of the same format from the commit and image digests of the release manifest inside the bundle, plus the settings document's digest.

```bash
DEPLOYMENT_DIR=/var/lib/werft/test-ops
scripts/test-ops.sh manifest release-manifest.json /etc/werft/settings.json > "$DEPLOYMENT_DIR/release.json"
```

Run step 4 and `bootstrap-token` from the bundle directory with the same commands. The bundle's `preflight` and `deploy` refuse the file if its commit or images differ from the bundle's release.

<a id="4-s3를-명시해-검사설치" />
### 4. Explicitly select S3, check, and install

```bash
TEST_OPS_OBJECT_STORE=s3 scripts/test-ops.sh preflight "$DEPLOYMENT_DIR/release.json"
TEST_OPS_OBJECT_STORE=s3 scripts/test-ops.sh deploy "$DEPLOYMENT_DIR/release.json"
```

preflight checks bucket protection and scratch version writes, holds, reads, hold release, and deletion. The scheduler checks quota during deploy. Both must succeed and services must become healthy. The object store mode cannot change after the first deploy.

If the env file sets no `BOOTSTRAP_TOKEN`, get the first owner's token after deploy. It waits in an owner-only file inside the API container, not in the container log, and this command deletes it as it prints it.

```bash
scripts/test-ops.sh bootstrap-token
```

Paste the value into `/bootstrap` ([first owner and keys](/run-server/self-hosting/users-and-keys)). Running the command again prints no token and exits 1. If you missed the value and no owner exists yet, run `scripts/test-ops.sh stop` and `start` to restart the API, which mints a new token (the old one stops working). An installation that already sets `BOOTSTRAP_TOKEN` is unchanged.

<a id="확인" />
## Verify

```bash
scripts/test-ops.sh status
curl --max-time 10 -fsS -w '\n%{http_code}\n' http://127.0.0.1:3000/readyz
curl --max-time 10 -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/docs
```

Check the ready response body and 200, docs 200, and healthy status for each service. PostgreSQL must remain loopback-only, and the Docker TCP socket must be inaccessible externally. The complete production AWS S3 installation and restoration with data have not been verified by execution in this tutorial. An empty LocalStack checkpoint comparison and ready 200 do not substitute for them.

<a id="자주-막히는-곳" />
## Troubleshooting

If the first `deploy` fails, started containers remain and `stop` is unavailable because `current.json` does not exist. Inspect failure logs for quota, network, or Secret issues. Confirm this installation's project name, then bring it down as follows without `-v`.

```bash
PROJECT='<this-installation-project>'
printf '%s\n' '{"services":{"x":{"image":"alpine:3"}},"networks":{"default":{}}}' \
  | docker compose --project-name "$PROJECT" -f - down --remove-orphans
```

Fix the cause, then rerun `deploy` with the same release file and environment. Use `start` to restart an installation that has already succeeded.

If `preflight` stops with `path(s) the containers mount are not readable by other users`, the checkout or bundle was made under a restrictive umask (`077`, `027`). Postgres (uid 999) and migrate (uid 1000) do not run as the host user and cannot read those files. Check the listed paths, then run `chmod -R o+rX` on the checkout or bundle directory and `chmod o+r` on the settings document, or fetch it again under umask `022`. Releases without this check show the same cause only as an unhealthy postgres at `deploy`, with `Permission denied` in the postgres log.

For quota errors, see [XFS preparation](/run-server/self-hosting/prepare-xfs); for bucket protection/permission errors, see [Bucket preparation](/run-server/self-hosting/prepare-checkpoint-bucket). For env permissions, check [step 2 file modes](#2-비밀과-설정-문서); for settings digest errors, check [step 3 digest and release generation](#3-release-입력-생성). A failed first deploy does not imply a successful deployment state file exists.

<a id="되돌리기" />
## Roll back

For a healthy installation, preserve data through [stop and restart](/run-server/self-hosting/stop-compose). After a failed first deploy, inspect the cause and resources this project created first. Do not use reset or volume deletion as default cleanup. Follow a separate removal procedure only after confirming no required data exists.
