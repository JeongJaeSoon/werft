## 作業内容

Linux 試験サーバーに LocalStack を使う Compose 環境を設置します。ホストや Docker の再起動で object が消失する場合がある、非永続の試験経路です。

<a id="준비물" />
## 準備

| 項目 | 要件 |
| --- | --- |
| OS | Linux。`x86_64` と `arm64` の両方に対応します |
| Docker Engine | 28 以上 |
| Docker Compose | 2.24.6 以上 |
| ディスク | Docker データルートが XFS で、`prjquota` 付きで mount されていること。`preflight` が quota probe でこれを確認し、満たさなければ止まります。ext4 サーバーでは先に [XFS ディスクの準備](/run-server/self-hosting/prepare-xfs)を完了します。XFS を用意できないサーバーでは手順 2 の「XFS なしで試験する」に従います。Docker Desktop では使えません |
| 時刻 | NTP 同期。再起動後に Docker が自動起動すること |
| ツール | checkout 設置では `git`、`jq`、`curl`、`openssl`、Bun 1.3.14、Docker Buildx プラグイン。リリースバンドル設置では `jq`、`curl`、`openssl`、`sha256sum`、`tar`(gzip 対応)。どちらも Docker daemon にアクセスできるアカウント |
| 外部 | `ghcr.io` と Docker Hub からイメージを取得できること。パッケージはログイン不要です。セッションは `api.anthropic.com` と `github.com` にアクセスします |

設置方法は[単一サーバー設置](/run-server/self-hosting/single-server)と同じく二つです。リポジトリ checkout はすべての公開タグに使え、`v*` リリースはバンドルで checkout とホストの Bun なしに設置できます。どちらでも compose ファイルと `scripts/test-ops.sh` は取得したディレクトリから読み、イメージはビルドしません。

運用データから分離した Linux サーバーで、先に [XFS の準備](/run-server/self-hosting/prepare-xfs)を完了します。試験専用の project、設置 id、ポート、状態・秘密情報ディレクトリを選びます。test-ops の既定 project 名は `werft-test-ops` で、`TEST_OPS_PROJECT` で変更します。次の例の既定パスが既存環境で使われている場合は、別のパスと `TEST_OPS_*` 値を指定します。

<a id="단계" />
## 手順

<a id="1-이미지와-소스" />
### 1. イメージとソース

```bash
TAG='<published-image-tag>'
SOURCE_REF='<matching-source-commit-or-release-tag>'
for app in control-host worker egress-proxy; do
  echo "$app $(docker buildx imagetools inspect "ghcr.io/jeongjaesoon/werft-$app:$TAG" --format '{{.Manifest.Digest}}')"
done
```

```bash
git clone https://github.com/JeongJaeSoon/werft.git
cd werft
git checkout "$SOURCE_REF"
bun install --frozen-lockfile
```

三つのイメージがすべて digest を返し、同じ source commit を checkout したことを確認します。

`v*` リリースを checkout なしで設置するときは、上の二つのブロックの代わりに[単一サーバーのリリースバンドル取得](/run-server/self-hosting/single-server#릴리스-번들로-받기)に従います。以降の手順はバンドルのディレクトリで実行します。バンドルは `backup` と `reseed` を拒否するため、下の「よくある問題」の計画再起動の手順は、同じ env ファイルと状態ディレクトリのまま、そのリリースの `source_commit` を checkout したリポジトリで実行します。

<a id="2-시험-설정" />
### 2. 試験設定

秘密の値はリポジトリ外の env ファイル `/etc/werft/test-ops.env` だけに置きます。次のブロックは設定ディレクトリと状態ディレクトリを運用者の所有にし、`init-config` で例のファイルからこのファイルを新しく作ります。ファイルは運用者だけが読める `0600` で作られ、ランダムな秘密の値は画面に表示されません。ファイルがすでにあれば上書きせずに拒否します。`<console-origin>` にはブラウザが開くコンソールの origin を入れます。SSH tunnel なら `http://127.0.0.1:<tunnel port>` です。

```bash
sudo install -d -m 755 -o "$USER" /etc/werft
sudo install -d -m 700 -o "$USER" /var/lib/werft/test-ops
TEST_OPS_OBJECT_STORE=localstack scripts/test-ops.sh init-config --console-origin '<console-origin>'
```

`init-config: wrote /etc/werft/test-ops.env` で始まる行が出力されるはずです。引数と埋める値は[単一サーバー設置の 2 番目の手順](/run-server/self-hosting/single-server#2-비밀과-설정-문서)と同じで、S3 の引数の代わりに `--localstack-port` で LocalStack のホストポートを変えられます。例の値の `EXECUTION_INSTALLATION_ID=test-ops`、`PLATFORM_SETTINGS_DOCUMENT=/etc/werft/settings.json`、`EXECUTION_WORKSPACE_QUOTA=on`、private credential allowlist `localstack:4566` をそのまま使い、AWS key・region・bucket 変数は空のままにします。

env ファイルを自分で書くには、`infra/test-ops.env.example` を運用者所有の `0600` で `/etc/werft/test-ops.env` にコピーし、エディターで次を設定します。

| 変数 | 値 |
| --- | --- |
| `POSTGRES_PASSWORD` | ランダムな値。英字、数字、`.` `_` `~` `-` だけを使います |
| `EGRESS_AUTHORIZER_TOKEN` | 32 文字以上のランダムな値 |
| `PLATFORM_SECRET_KEY` | `openssl rand -hex 32` の 64 文字 hex。失うと保存した資格情報を読めなくなります |

`CONSOLE_ORIGIN` は自分で追加します。`EXECUTION_INSTALLATION_ID=test-ops`、`PLATFORM_SETTINGS_DOCUMENT=/etc/werft/settings.json`、`EXECUTION_WORKSPACE_QUOTA=on` を使います。credential allowlist は `api.anthropic.com:443,github.com:443`、private credential allowlist は `localstack:4566` です。AWS key・region・bucket 変数は例のまま空にします。LocalStack は固定の試験 key と `claude-sessions` bucket を使います。

設定文書は `/etc/werft/settings.json` に置き、セッションが使う GitHub リポジトリを書きます。最初の `deploy` が空のインストールに一度だけ入れ、その後は文書を直しても取り込まれないため、設定はコンソールで変更します。秘密情報は含みません。リポジトリ URL だけを実際の値に変更します。例は公開リポジトリ用です。リポジトリ項目には `"auth": { "kind": "github_app" }` が必要です。なければ `preflight` が文書全体を拒否し、設置を止めます。非公開リポジトリは、そのリポジトリに GitHub App をインストールします（[GitHub](/integrations/github)）。

migrate コンテナが読む必要があるため、ファイルは `0644` にします。先に空のファイルを作り、エディターで次の内容を入れます。

```bash
sudo install -m 644 -o "$USER" /dev/null /etc/werft/settings.json
```

```json
{
  "version": 1,
  "connections": {},
  "repositories": {
    "sample-app": {
      "url": "https://github.com/<owner>/<repo>.git",
      "branch": "main",
      "auth": { "kind": "github_app" }
    }
  }
}
```

<a id="xfs-없이-시험하기" />
#### XFS なしで試験する

XFS を用意できないサーバー（コンテナ型サーバー、隔離 VM など）では試験モードで設置します。このモードは運用に使いません。`/etc/werft/test-ops.env` の `EXECUTION_WORKSPACE_QUOTA=on` を `EXECUTION_WORKSPACE_QUOTA=off` に変えます。すると次が変わります。

- `preflight` と `deploy` は quota probe を省きます。`preflight: passed` の行に `no workspace quota (test mode, not for production)` が出ます。
- カーネルの quota がないため、worker が自分の作業領域を測ります。測るのは 1 分に 1 回までです。`EXECUTION_WORKSPACE_QUOTA_MB`（既定 4096）または `EXECUTION_WORKSPACE_QUOTA_INODES`（既定 1,000,000）を超えると、コンソールの作業領域の容量設定（`WORKSPACE_ENFORCE`）に関係なくその turn を止めます。セッションは残るので、ファイルを減らしてから再度依頼します。二つの測定の間は一時的に上限を超えることがあります。
- `/readyz` は 200 のままで、本文の `detail.no_disk_quota` が `true` になります。
- コンソールは owner・admin にすべての画面の上部に「試験モード: ディスク quota なし、運用不可」を表示します。この帯は閉じられません。
- api は起動時に、scheduler は pass ごとにログへ警告を残します。

`off` は LocalStack ストアでだけ受け付けます。`TEST_OPS_OBJECT_STORE=s3` なら `preflight` が `off is for the LocalStack store only` で止まります。

<a id="3-release-입력과-설치" />
### 3. release 入力と設置

release の生成は[単一サーバーの手順 3](/run-server/self-hosting/single-server#3-release-입력-생성)と同じです。バンドルで取得した場合は、その手順のバンドル用 `manifest` コマンドを使います。生成先は checkout 外の `/var/lib/werft/test-ops/release.json` とします。この段階では S3 用 preflight は実行せず、次を使います。

```bash
TEST_OPS_OBJECT_STORE=localstack scripts/test-ops.sh preflight /var/lib/werft/test-ops/release.json
TEST_OPS_OBJECT_STORE=localstack scripts/test-ops.sh deploy /var/lib/werft/test-ops/release.json
```

quota 検査（試験モードでは省きます）とサービス health が成功する必要があります。モデル key は設置後にコンソールへ入力します。

<a id="확인" />
## 確認

`scripts/test-ops.sh status`、ready の本文と 200、docs 200 を確認します。[最初の owner と key](/run-server/self-hosting/users-and-keys)で認証を確認します。この試験では運用 AWS S3 の権限やデータがある状態での復元を証明しません。

<a id="자주-막히는-곳" />
## よくある問題

最初の `deploy` が失敗すると、起動したコンテナが残り、`current.json` がないため `stop` は使えません。失敗ログで quota・network・Secret などの原因を確認し、今回の project 名を確認してから次のように停止・削除します。`-v` は付けません。

```bash
PROJECT='<this-installation-project>'
printf '%s\n' '{"services":{"x":{"image":"alpine:3"}},"networks":{"default":{}}}' \
  | docker compose --project-name "$PROJECT" -f - down --remove-orphans
```

原因を直し、同じ release ファイルと同じ環境で `deploy` を再実行します。成功済みの環境を再起動するときは `start` を使います。

`preflight` が `path(s) the containers mount cannot be read by the user their container runs as` で止まった場合、括弧内のコンテナユーザーが表示されたパスを読めません。postgres（uid 999）と migrate（uid 1000）はホストのユーザーとして実行されないため、制限的な umask（`077`、`027`）で作られたリポジトリの checkout やバンドル、または他のユーザーが読めない設定文書が原因です。checkout またはバンドルのディレクトリに `chmod -R o+rX`、設定文書に `chmod o+r` を実行するか、umask `022` で取得し直します。postgres volume が初期化済みの設置は初期 SQL を再度読まないため、これまで問題が出ていなくても、この検査がある版の `upgrade`・`start` で初めて止まることがあります。

アップグレードで LocalStack コンテナが再作成されると、object を失う場合があります。`status` で未回収 checkpoint が 0 件と確認できなければアップグレードを延期します。API 起動失敗と `pending.json` が重なると `reseed` も拒否され、`reset` は全データを破棄します。`backup --stop` もこの遮断を解除しません。

LocalStack はコンテナが再起動すると（ホストの再起動、Docker の再起動、コンテナの再作成）メモリの object を失います。bucket は起動のたびに作り直されますが、空です。この試験設置の API はその状態でも起動を拒否せず、DB に残った未回収 checkpoint を諦めてから起動します。予告のない再起動の後にすることはなく、`reset` は使いません。

- owner、key、設定、セッション一覧は残ります。
- 失った checkpoint を復元地点としていたセッションは、閉じたものを除いて `recovery_required` になります。以前の文脈なしで続けるか（`start_fresh`）、閉じるか（`close`）を決めます（[API ガイド](/reference/api-guide)の復旧判断）。
- API のログに `The object store came back empty` で始まる警告が 1 行残り、セッション数と id を記録します。
- `/readyz` は 200 のままで、本文の `detail.checkpoints_forgotten_on_boot` にそのセッション数が入ります。
- コンソールは owner・admin に、すべての画面の最上部で「試験インストール: 再起動でセッションN件のコンテキストを失いました」と表示します。そのうちの一人が**閉じる**を押すと全員の画面から消え、`/readyz` の数からも除かれます。セッションは `recovery_required` のままです。

LocalStack のコンテナだけを再起動しないでください。API が整理するのは起動時だけで、動いている間は整理しません。その間に新しい checkpoint が書かれると bucket が空ではなくなり、次の起動でも整理されず、object を失ったセッションは復元時に失敗します。そうなった場合は、すぐに `scripts/test-ops.sh stop` の後 `start` で設置全体を再起動します。

`v0.4.0` 以前のリリースは整理しません。その API はログに `Checkpoint bucket claude-sessions holds no object version` を残して起動を拒否します。事前に `backup --stop` を取っていなければ、残るのは `reset` だけです。自動再起動と手動 start の条件は [Compose のライフサイクル](/run-server/self-hosting/stop-compose)に従います。

セッションの文脈を守るには、計画的な再起動の前にバックアップして writer を停止します。再起動の後は `start` ではなく `reseed` を使います。`start` は API を空の bucket で起動して checkpoint を諦めさせ、その後に object を戻しても諦めた checkpoint は戻りません。

```bash
# Back up, leave the writers stopped, restart the host, then restore the objects
scripts/test-ops.sh backup --stop
sudo reboot
scripts/test-ops.sh reseed /var/lib/werft/test-ops/backups/backup-<timestamp>
```

`reseed` は原本の project・bucket・checksum、空の bucket、最後のバックアップ後に checkpoint の変更がないことを検査します。条件を満たさなければ拒否します。object を失い、API 起動失敗と pending upgrade が残る状態では `reseed` は拒否されます。`backup --stop` のバックアップがあっても遮断は解除されません。この状態で `reset` を選ぶと DB・セッション・checkpoint を破棄します。通常の再起動の復旧コマンドとして使わないでください。

<a id="되돌리기" />
## 元に戻す

[Compose の停止・削除](/run-server/self-hosting/stop-compose)に従います。成功した環境は `scripts/test-ops.sh stop` で今回の project を停止・削除し、volume を保持します。最初の deploy 失敗では、上記の明示的な project と stdin の compose model による後片付け手順に従います。checkpoint がない試験という理由で、運用 bucket や他の環境を整理しないでください。reset は削除範囲を確認したうえで別途選ぶ操作です。
