## What you will do

Back up a Compose installation's database and checkpoint objects, then compare pointer versions in a separate project with a new, empty bucket. Record API verification and actual session resumption as separate evidence.

<a id="준비물" />
## Before you begin

You need a healthy installation, separately stored copies of the current release and secret keys, enough backup space, and a maintenance window to stop writers. Backups include the entire database and API key hashes: restrict access to 0700 and encrypt them in transit and at rest. Do not restore into the production bucket. Release bundles reject `backup`, `reseed`, and `restore-drill`; run them from a checkout of the installation's commit.

<a id="단계" />
## Steps

<a id="1-백업" />
### 1. Back up

```bash
scripts/test-ops.sh backup
```

The command stops api, slack, scheduler, reconciler, maintenance, and workers, bundles the database and objects into `backups/backup-<timestamp>` under the state directory, then restarts services. Check for active turns before starting: they are interrupted and can later be reclaimed. Never use failed (`.failed`) or incomplete (`.partial`) backups as successful ones. The command fails if it cannot restart services, even if the backup itself finished.

Run this daily during a quiet period and immediately before every upgrade. An example retention policy is 14 days on the host and 90 days in an encrypted external store. Alert if no new successful backup exists for 26 hours, the command exits non-zero, or services fail to resume.

<a id="2-별도-대상-복원" />
### 2. Restore to a separate destination

For S3, prepare a new, empty drill bucket every time. The command rejects the source bucket and any destination containing object versions or delete markers.

```bash
# Restore a backup into a throwaway project and a new, empty bucket, then verify it
scripts/test-ops.sh restore-drill /var/lib/werft/test-ops/backups/backup-<timestamp> --bucket <drill-bucket> --port-base 25432
```

`--port-base` sets the drill services' separate starting port. Choose a value that does not overlap other installations. Omit `--bucket` for a LocalStack trial. The drill restores postgres and the object store, then compares every checkpoint pointer by version. It does not start the API. Run it monthly and on the first backup after each upgrade.

The migration list recorded in a backup must match the current checkout exactly. An older backup, or one with a migration the checkout does not know, is refused with exit code 3. To restore a backup taken before an upgrade, check out the `source_commit` of the release it was taken on, restore and verify there, then run the migrations as a separate step.

### 3. Checkpoint GC

Schedule this weekly, without overlapping backups, and start with a dry run.

```bash
API_CONTAINER='<api-container-id-from-this-installation>'
docker exec -e CHECKPOINT_GC_DRY_RUN=1 "$API_CONTAINER" \
  bun run apps/control-host/src/api/checkpoint-gc.ts
```

Identify API_CONTAINER from this installation's status and project label. Review the objects to retain and delete in the output, then run without the dry-run environment variable. Do not select another installation in the default Compose project. Kubernetes uses the chart's `checkpointGc.schedule`.

On a single-server installation, the `maintenance` service runs checkpoint GC once a week (`MAINTENANCE_INTERVAL_SEC`, default 604800 seconds), followed by session archive. Finish the dry-run review above before its first run. To keep the scheduled run a dry run too, add `CHECKPOINT_GC_DRY_RUN=true` to the env file and reapply it with `scripts/test-ops.sh start`. `backup` stops `maintenance` while it runs.

<a id="확인" />
## Verify

Check the backup exit code and status. Keep the drill logs with the actual checkpoint count, version count, and checksum results. `nothing was compared` means the comparison was empty; it does not prove data restoration. Verify that sessions resume with the restored API and workers in a separate, isolated environment.

<a id="자주-막히는-곳" />
## Troubleshooting

Stop if the drill destination is the source or is not empty. If legal holds or retention prevent version deletion, investigate the destination and retention contract instead of removing protection arbitrarily. Drill output is recorded under `restore-drills/` and in history.

<a id="되돌리기" />
## Roll back

The drill tool cleans up its project when it exits. If you used `--keep` for investigation, bring down only that project after checking it, and handle volumes under a separate retention policy. Keep the drill bucket distinct from production. After confirming it contains no data to reuse, release each object version's legal hold, delete versions and delete markers, then delete the empty bucket. Wait for any remaining retention period to expire; do not bypass it. Do not delete production backups for a test.

<a id="kubernetes-설치" />
## Kubernetes installations

Kubernetes installations do not use the compose backup tools. AWS features do the same job.

- **Database.** RDS automated backups (point-in-time restore) and manual snapshots.
- **Checkpoint objects.** S3 versioning and Object Lock. A committed checkpoint is pinned to a version and under a legal hold, so the version survives when the same key is overwritten or deleted. Restoring does not copy the bucket; it points at versions in the same bucket. So do not change buckets while uncollected checkpoints remain.
- **The bucket is canonical together with the database.** Events the [session event archive](/run-server/self-hosting/reference/storage#세션-이벤트-보관) moved to `session-archive/` exist only in those objects. Restoring only the database and losing the bucket leaves those sessions' events unreadable.
- **Lifecycle rules.** Add no expiration rules. Only the chart's checkpoint GC CronJob (`checkpointGc.schedule`, default `0 4 * * 0`) deletes checkpoint objects. A lifecycle rule does not know the database, so it can delete objects before their hold is set, or versions whose hold GC just released, and break finalize or GC. For `session-archive/`, use storage class transitions only, and only to classes the API can read at once (`STANDARD_IA`, `ONEZONE_IA`, `GLACIER_IR`, `INTELLIGENT_TIERING` without archive tiers). Moving to `GLACIER` or `DEEP_ARCHIVE` makes those sessions' events unreadable.
- **Snapshots and GC.** An RDS snapshot holds the pointers of its moment. A snapshot's pointer can point to a revision GC deleted after the snapshot, so set the snapshot retention and the GC schedule together.
