## What you will do

Test the chart and API readiness in an isolated kind cluster on your laptop, then remove it. This PostgreSQL and LocalStack environment is not a production data store.

<a id="준비물" />
## Before you begin

You need Docker, kind, Helm 3, and kubectl. The harness in step 1 also uses git, Bun 1.3.14, and a repository checkout. The published-chart test in step 2 uses `curl`, `openssl`, and the [prerequisites of Test database and object store for the chart](/run-server/self-hosting/try-chart-dependencies#준비물) instead of a checkout. Choose a cluster name and registry port that do not conflict with other work. Use a kind version that enforces NetworkPolicy.

<a id="단계" />
## Steps

<a id="1-checkout의-시험-harness" />
### 1. Use the checkout's test harness

```bash
git clone https://github.com/JeongJaeSoon/werft.git
cd werft
CLUSTER_NAME=werft-try REGISTRY_PORT=15001 deploy/kind/up.sh
export KUBECONFIG=~/.cache/werft/kind/werft-try/kubeconfig
```

The script prepares the cluster, registry, images, namespace, database, LocalStack, Secret, and chart, then checks rollout and ready/docs. Use only the generated kubeconfig. `EXTRA_VALUES` can override installation-specific values, but it cannot change the harness's worker image `--set` values.

<a id="2-게시-chart를-직접-시험하는-경우" />
### 2. Test a published chart directly

Testing a published chart instead of the harness needs no repository checkout. Create a separate kind cluster and use a kubeconfig that points only at it.

```bash
kind create cluster --name werft-try --kubeconfig "$HOME/.kube/werft-try"
export KUBECONFIG="$HOME/.kube/werft-try"
kubectl config current-context
```

The last command must print `kind-werft-try`. Then, in the same shell, follow steps 1 to 4 of [Test database and object store for the chart](/run-server/self-hosting/try-chart-dependencies). That page gives the dependency manifest, the Secret, and minimal values in its text, and step 4 installs the published chart. The LocalStack init script is in that manifest's ConfigMap `localstack-init`, and it creates the same bucket as `infra/localstack/init/10-create-resources.sh` in the release bundle (`werft-test-ops-<tag>.tar.gz`).

The first owner comes from the one-time setup link an api Pod prints (`kubectl -n werft exec deploy/werft-api -- bun run apps/control-host/src/api/setup-link.ts`). If only a path is printed, append it to the port-forward address (`http://127.0.0.1:13000`). The link is kept in the database, so it works on either of the 2 replicas. Do not put a model key in the Secret. A key is only ever a value the first owner enters on the console and that is stored in the database, and this test enters none. Do not put production credentials in this test.

<a id="확인" />
## Verify

```bash
kubectl -n werft get job werft-migrate
for d in api egress-proxy reconciler scheduler; do
  kubectl -n werft rollout status deploy/werft-$d --timeout=600s
done
```

```bash
kubectl -n werft port-forward svc/werft-api 13000:3000 &
PF=$!
trap 'kill "$PF" 2>/dev/null || true' EXIT INT TERM
READY=0
for attempt in $(seq 1 30); do
  if curl --max-time 2 -fsS -o /dev/null http://127.0.0.1:13000/readyz; then READY=1; break; fi
  sleep 1
done
if [ "$READY" != 1 ]; then
  kill "$PF" 2>/dev/null || true
  trap - EXIT INT TERM
  false
else
  curl --max-time 10 -fsS -w '\n%{http_code}\n' http://127.0.0.1:13000/readyz
  curl --max-time 10 -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:13000/docs
  kill "$PF" 2>/dev/null || true
  trap - EXIT INT TERM
fi
```

ready 200 and docs 200 show that an empty installation is ready. They do not establish that a session and worker Pod have been started or that checkpoint restoration works. A Bound PVC on kind does not prove byte-limit enforcement.

<a id="자주-막히는-곳" />
## Troubleshooting

A missing required Secret key prevents Pods from starting in a direct installation. If the published chart cannot be downloaded, record that package installation as failed; do not substitute a successful fixture render. Keep external database/S3 addresses separate from test dependency addresses.

<a id="되돌리기" />
## Roll back

For a harness-created environment:

```bash
CLUSTER_NAME=werft-try deploy/kind/up.sh down
```

Remove a directly created `werft-try` cluster with `kind delete cluster --name werft-try --kubeconfig "$HOME/.kube/werft-try"`. Clean up only this test cluster even after failure; do not touch resources in other contexts.
