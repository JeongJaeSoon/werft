## 무엇을 하게 되나

Linux 한 대에 게시 이미지를 digest로 고정해 설치하고 `/readyz`와 `/docs` 응답을 확인한다. 영속 AWS S3를 사용한다. 이 Compose 경로는 사용자 endpoint를 받지 않는다. 다른 S3 호환 endpoint가 필요하면 [Kubernetes 설치](/run-server/self-hosting/kubernetes)를 따른다. 고가용성이 필요하면 [Kubernetes](/run-server/self-hosting/kubernetes)를 선택한다.

## 준비물

| 항목 | 요구 |
| --- | --- |
| 운영체제 | Linux. `x86_64`와 `arm64` 모두 된다 |
| Docker Engine | 28 이상 |
| Docker Compose | 2.24.6 이상 |
| 디스크 | Docker 데이터 루트가 XFS이고 `prjquota`로 mount돼 있다. `preflight`는 이것을 보지 않는다. 아니면 `deploy`에서 scheduler의 quota 검사가 실패해 설치가 멈춘다. ext4 서버는 [XFS 디스크 준비](/run-server/self-hosting/prepare-xfs)를 먼저 끝낸다. Docker Desktop에서는 쓸 수 없다 |
| 시간 | NTP 동기화. 재부팅 뒤 Docker가 자동으로 시작한다 |
| 도구 | checkout 설치는 `git`, `jq`, `curl`, `openssl`, Bun 1.3.14, Docker Buildx 플러그인. 릴리스 번들 설치는 `jq`, `curl`, `openssl`, `sha256sum`, `tar`(gzip 지원). 둘 다 Docker daemon에 접근할 수 있는 계정 |
| object store | 영속 AWS S3 bucket. Compose test-ops는 AWS S3만 지원하며 사용자 endpoint를 받지 않는다. [bucket 준비](/run-server/self-hosting/prepare-checkpoint-bucket)에서 보호 계약과 권한을 확인한다 |
| 외부 | `ghcr.io`와 Docker Hub에서 이미지를 받을 수 있다. 패키지는 로그인 없이 받는다. 세션은 `api.anthropic.com`과 `github.com`에 나간다 |

설치 방법은 둘이다. 저장소 checkout은 모든 게시 태그(`main-<12>`, `v<버전>`)에 쓸 수 있다. `v*` 릴리스는 GitHub Release에 붙은 번들(`werft-test-ops-<tag>.tar.gz`)로 checkout과 호스트 Bun 없이 설치할 수 있다. 어느 쪽이든 compose 파일과 `scripts/test-ops.sh`를 받은 디렉터리에서 읽고, 이미지는 빌드하지 않는다. 번들은 `upgrade`, `backup`, `reseed`, `restore-drill`을 거부한다. 이 명령은 같은 env 파일과 상태 디렉터리를 두고 그 릴리스의 `source_commit`을 checkout한 저장소에서 실행한다.

- 먼저 [XFS 디스크](/run-server/self-hosting/prepare-xfs)와 [checkpoint bucket](/run-server/self-hosting/prepare-checkpoint-bucket)을 준비한다.
- 원격 bootstrap 전에 [접속 경로](/run-server/self-hosting/access)를 정한다.
- 설치마다 별도 project·설치 id·비밀 파일·상태 디렉터리를 쓴다.

## 단계

### 1. 버전과 소스 고정

현재 설정 문서·모델 연결·비밀키 계약을 지원하는 게시 태그를 변경 기록과 대조해 선택한다. 아래 두 placeholder를 [패키지 계약](/run-server/self-hosting/reference/packages)에서 얻은 실제 태그와 같은 소스 commit으로 바꾼다. 이미지의 main 태그는 Git 태그가 아니므로 checkout 값과 같다고 가정하지 않는다.

```bash
TAG='<published-image-tag>'
SOURCE_REF='<matching-source-commit-or-release-tag>'
for app in control-host worker egress-proxy; do
  echo "$app $(docker buildx imagetools inspect "ghcr.io/jeongjaesoon/werft-$app:$TAG" --format '{{.Manifest.Digest}}')"
done
```

세 이미지 조회가 모두 성공하고 digest가 나온 뒤 진행한다.

```bash
git clone https://github.com/JeongJaeSoon/werft.git
cd werft
git checkout "$SOURCE_REF"
bun install --frozen-lockfile
```

checkout이 선택한 release의 commit이고 의존성 설치가 성공해야 한다. release 파일은 checkout 밖에 저장하여 깨끗한 checkout 조건을 유지한다.

#### 릴리스 번들로 받기

`v*` 릴리스를 checkout 없이 설치할 때는 위 두 블록 대신 다음을 실행한다. `TAG`는 [패키지 계약](/run-server/self-hosting/reference/packages)에서 고른 릴리스 태그다.

```bash
TAG='<release-tag>'
BASE="https://github.com/JeongJaeSoon/werft/releases/download/$TAG"
mkdir -p "$HOME/werft-releases/$TAG"
cd "$HOME/werft-releases/$TAG"
curl -fsSLO "$BASE/werft-test-ops-$TAG.tar.gz"
curl -fsSLO "$BASE/werft-test-ops-$TAG.tar.gz.sha256"
sha256sum -c "werft-test-ops-$TAG.tar.gz.sha256"
tar -xzf "werft-test-ops-$TAG.tar.gz"
cd "werft-test-ops-$TAG"
```

`sha256sum`이 `OK`를 출력해야 한다. sha256은 내려받다 깨진 파일만 잡고 출처는 증명하지 않으므로, 이 GitHub Release 주소에서 받은 파일만 쓴다. 이후 단계의 `infra/`와 `scripts/` 경로는 이 디렉터리 기준이다. 번들에는 그 릴리스의 `release-manifest.json`이 들어 있으므로 이미지 digest는 3단계에서 따로 조회하지 않는다.

### 2. 비밀과 설정 문서

비밀 값은 저장소 밖의 env 파일에만 둔다. 파일은 운영자만 읽을 수 있어야 한다. group이나 other에 권한이 있으면 스크립트가 거부한다.

```bash
sudo mkdir -p /etc/werft
sudo install -m 600 -o "$USER" infra/test-ops.env.example /etc/werft/test-ops.env
sudo install -d -m 700 -o "$USER" /var/lib/werft/test-ops
```

`/etc/werft/test-ops.env`를 편집기로 열어 다음을 채운다. `sed -i`처럼 임시 파일을 만드는 도구는 `/etc/werft`에서 `Permission denied`로 실패하니 제자리에 쓰는 편집기를 쓴다.

| 변수 | 값 |
| --- | --- |
| `POSTGRES_PASSWORD` | 무작위 값. 영문, 숫자, `.` `_` `~` `-`만 쓴다 |
| `EGRESS_AUTHORIZER_TOKEN` | 32자 이상 무작위 값 |
| `PLATFORM_SECRET_KEY` | `openssl rand -hex 32`의 64자 hex. 잃으면 저장한 자격 증명을 읽지 못한다 |
| `CONSOLE_ORIGIN` | 콘솔에서 GitHub App을 만들 때 필요한 브라우저의 콘솔 origin(`scheme://host[:port]`). 없으면 "GitHub에서 만들기" 버튼이 비활성화된다. Slack 계정 연결의 redirect와 Slack 이벤트 주소도 이 값에서 계산한다(없으면 Slack 연결이 꺼진다). [SSO 로그인](/run-server/self-hosting/sso) 공급자의 redirect URI도 이 값에서 만들며, 없으면 공급자를 만들 수 없다. 예시 env 파일에는 이 줄이 없으므로 직접 추가한다. SSH tunnel로 콘솔을 열면 `http://127.0.0.1:<터널 포트>`를 넣는다. 설치 뒤 추가·변경한 값은 `start` 대신 `TEST_OPS_OBJECT_STORE=s3 scripts/test-ops.sh upgrade /var/lib/werft/test-ops/current.json`으로 현재 release를 다시 적용해 반영한다 |

예시의 LocalStack 값을 운영 S3 값으로 바꾼다. 비밀을 명령줄이나 로그에 출력하지 않는다.

| 변수 | 운영 설치 값 |
| --- | --- |
| `EXECUTION_INSTALLATION_ID` | 다른 설치와 겹치지 않는 id. 배포 뒤 변경하지 않는다 |
| `PLATFORM_SETTINGS_DOCUMENT` | `/etc/werft/settings.json` |
| `EXECUTION_WORKSPACE_QUOTA` | `on` |
| `AWS_REGION`, `S3_BUCKET` | 준비한 AWS bucket의 리전과 이름. 사용자 endpoint는 지원하지 않음 |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | bucket 최소 권한의 API 자격 증명 |
| `EGRESS_CREDENTIAL_ALLOWLIST` | provider·Git host와 `<bucket>.s3.<region>.amazonaws.com:443`. 점이 든 bucket 이름은 `s3.<region>.amazonaws.com:443` |
| `EGRESS_CREDENTIAL_PRIVATE_ALLOWLIST` | 빈 값. `localstack:4566`을 제거한다 |

호스트 포트가 이미 쓰이면 env 파일에 다음을 넣는다. 값을 주지 않으면 기본값을 쓰고, 어떤 값이든 `127.0.0.1`에만 열린다.

| 변수 | 기본값 | 값 |
| --- | --- | --- |
| `TEST_OPS_API_PORT` | `3000` | API와 웹 콘솔의 호스트 포트. 1~65535 |
| `TEST_OPS_POSTGRES_PORT` | `5432` | postgres의 호스트 포트. 1~65535 |
| `TEST_OPS_LOCALSTACK_PORT` | `4566` | [LocalStack 시험 설치](/run-server/self-hosting/try-localstack)의 호스트 포트. 1~65535. S3 설치에서는 무시한다 |
| `TEST_OPS_API_URL` | `http://127.0.0.1:<TEST_OPS_API_PORT>` | `deploy`·`upgrade`·`status`가 `/readyz`를 확인하는 주소. 호스트 앞에 프록시를 둘 때만 넣는다. `scheme://host[:port]` 형식이고 경로와 끝의 `/`는 쓰지 않는다 |

`preflight`는 범위 밖 포트, 두 서비스가 같은 포트를 쓰는 값, 형식이 틀린 URL을 거부한다. 설치한 뒤 포트를 바꾸려면 env 파일을 고치고 `TEST_OPS_OBJECT_STORE=s3 scripts/test-ops.sh upgrade /var/lib/werft/test-ops/current.json`으로 같은 release를 다시 적용한다. 터널과 `curl`의 포트도 함께 바꾼다. `TEST_OPS_LOCALSTACK_PORT`를 바꾸면 LocalStack 컨테이너가 다시 만들어져 object가 모두 사라지므로, `preflight`가 실행 중인 포트와 다른 값을 거부한다. `scripts/test-ops.sh backup --stop`으로 백업하고 env 파일을 고친 뒤 그 백업으로 `reseed`를 부른다.

env 파일을 `/etc/werft/test-ops.env`가 아닌 곳에 두면 스크립트를 부를 때마다 `TEST_OPS_ENV_FILE`에 그 경로를 준다.

모델 키는 설치 뒤 콘솔의 모델 연결에서 넣으므로 `v0.1.2` 태그는 `ANTHROPIC_API_KEY`를 비워 둔다. 단, `v0.1.0` 태그 checkout에서는 compose가 이 값을 필수로 요구하여 비어 있으면 `preflight`가 exit 1로 끝난다. 그 버전에서는 env 파일에 모델 키(또는 나중에 콘솔에서 바꿀 자리 값)를 넣는다. 비워도 되는 변경은 [JeongJaeSoon/werft#1262](https://github.com/JeongJaeSoon/werft/pull/1262)에서 들어왔고, `v0.1.2`가 이를 담은 첫 게시 릴리스다. `PLATFORM_SECRET_KEY`를 잃으면 저장한 자격 증명을 읽지 못하므로 별도로 안전하게 백업한다.

설정 문서는 `/etc/werft/settings.json`에 둔다. 세션이 쓸 GitHub 저장소를 적는다. 첫 `deploy`가 빈 설치에 한 번 넣고, 그 뒤로는 문서를 고쳐도 들어가지 않으니 설정은 콘솔에서 바꾼다. 비밀이 없다. 저장소 URL만 실제 값으로 바꾼다. 예시는 공개 저장소 기준이다. 저장소 항목에는 `"auth": { "kind": "github_app" }`가 있어야 한다. 없으면 가져올 때 그 저장소가 빠져 `preflight`가 설치를 막는다. 비공개 저장소는 그 저장소에 GitHub App을 설치한다([GitHub](/integrations/github)).

migrate 컨테이너가 읽어야 하므로 파일은 `0644`로 둔다. 빈 파일을 먼저 만들고 편집기로 아래 내용을 채운다.

```bash
sudo install -m 644 -o "$USER" /dev/null /etc/werft/settings.json
```

```json
{
  "version": 1,
  "connections": {},
  "repositories": {
    "sample-app": {
      "url": "https://github.com/<owner>/<repo>.git",
      "branch": "main",
      "auth": { "kind": "github_app" }
    }
  },
  "mcp_servers": {}
}
```

저장소 URL은 실제 사용할 공개 저장소로 바꾼다. 비공개 저장소의 GitHub App은 [2단계 입력 목록의 CONSOLE_ORIGIN](#2-비밀과-설정-문서)을 준비한 뒤 설치한 콘솔에서 구성한다. 파일은 비밀을 포함하지 않으며 migrate가 읽을 수 있어야 한다.

### 3. release 입력 생성

선택한 TAG를 유지한 셸에서 실행한다. `DEPLOYMENT_DIR`는 checkout 밖의 설치별 디렉터리다.

```bash
DEPLOYMENT_DIR=/var/lib/werft/test-ops
SETTINGS_DIGEST="$(bun run scripts/lib/test-ops.ts settings-digest /etc/werft/settings.json)"
digest() { docker buildx imagetools inspect "ghcr.io/jeongjaesoon/werft-$1:$TAG" --format '{{.Manifest.Digest}}'; }
jq -n \
  --arg commit "$(git rev-parse HEAD)" \
  --arg control "ghcr.io/jeongjaesoon/werft-control-host@$(digest control-host)" \
  --arg worker "ghcr.io/jeongjaesoon/werft-worker@$(digest worker)" \
  --arg egress "ghcr.io/jeongjaesoon/werft-egress-proxy@$(digest egress-proxy)" \
  --arg settings "$SETTINGS_DIGEST" \
  '{source_commit: $commit,
    images: {control_host: $control, worker: $worker, egress_proxy: $egress},
    settings_digest: $settings}' > "$DEPLOYMENT_DIR/release.json"
```

세 이미지 digest가 모두 비어 있지 않은지 확인한다.

릴리스 번들로 받았다면 위 블록 대신 번들 디렉터리에서 다음을 실행한다. `manifest`는 번들 안 릴리스 manifest의 commit과 이미지 digest에 설정 문서의 digest를 더해 같은 형식의 파일을 만든다.

```bash
DEPLOYMENT_DIR=/var/lib/werft/test-ops
scripts/test-ops.sh manifest release-manifest.json /etc/werft/settings.json > "$DEPLOYMENT_DIR/release.json"
```

4단계와 `setup-link`도 번들 디렉터리에서 같은 명령으로 실행한다. 번들의 `preflight`와 `deploy`는 이 파일의 commit이나 이미지가 번들의 릴리스와 다르면 거부한다.

### 4. S3를 명시해 검사·설치

```bash
TEST_OPS_OBJECT_STORE=s3 scripts/test-ops.sh preflight "$DEPLOYMENT_DIR/release.json"
TEST_OPS_OBJECT_STORE=s3 scripts/test-ops.sh deploy "$DEPLOYMENT_DIR/release.json"
```

preflight는 bucket 보호 설정과 scratch version의 쓰기·hold·읽기·hold 해제·삭제를 검사한다. quota는 deploy 때 scheduler가 검사한다. 둘 다 성공하고 서비스가 healthy가 되어야 한다. object store 방식은 첫 deploy 뒤 바꿀 수 없다.

deploy 뒤에 첫 owner를 만드는 일회용 설정 링크를 받는다. 링크는 로그나 파일에 남지 않고, 이 명령이 stdout에 한 번 출력한다.

```bash
scripts/test-ops.sh setup-link
```

출력된 링크를 브라우저로 연다([첫 owner와 key](/run-server/self-hosting/users-and-keys)). 경로만 출력됐으면 콘솔 주소 뒤에 붙인다. 링크는 한 번 쓰면 바로 무효이고 24시간 뒤 만료된다. 놓쳤거나 만료됐으면 명령을 다시 실행한다. 새 링크가 나오고 앞 링크는 무효가 된다. owner가 생긴 뒤에는 링크 없이 종료 코드 1로 끝난다.

## 확인

```bash
scripts/test-ops.sh status
curl --max-time 10 -fsS -w '\n%{http_code}\n' http://127.0.0.1:3000/readyz
curl --max-time 10 -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/docs
```

ready 본문과 200, docs 200, 각 서비스 healthy를 확인한다. PostgreSQL은 loopback에만 있고 Docker TCP socket은 외부에서 닿지 않아야 한다. 운영 AWS S3 설치 전체와 데이터가 있는 복원은 이 튜토리얼에서 실행 확인하지 않았다. LocalStack의 빈 checkpoint 대조와 ready 200으로 이를 대신하지 않는다.

## 자주 막히는 곳

첫 `deploy`가 실패하면 시작된 컨테이너는 남아 있고 `current.json`이 없어 `stop`을 쓸 수 없다. 실패 로그에서 quota·네트워크·Secret 등 원인을 확인하고, 이번 설치의 project 이름을 확인한 뒤 다음처럼 내린다. `-v`는 붙이지 않는다.

```bash
PROJECT='<this-installation-project>'
printf '%s\n' '{"services":{"x":{"image":"alpine:3"}},"networks":{"default":{}}}' \
  | docker compose --project-name "$PROJECT" -f - down --remove-orphans
```

원인을 고친 뒤 같은 release 파일과 같은 환경으로 `deploy`를 다시 실행한다. 이미 성공한 설치를 다시 시작할 때는 `start`를 쓴다.

`preflight`가 `path(s) the containers mount cannot be read by the user their container runs as`로 멈추면 적힌 경로를 괄호 안의 컨테이너 사용자가 읽지 못한다. postgres(uid 999)와 migrate(uid 1000)는 호스트 사용자로 돌지 않으므로, 제한적인 umask(`077`, `027`)에서 받은 checkout이나 번들, 또는 다른 사용자가 읽지 못하게 둔 설정 문서에서 생긴다. checkout이나 번들 디렉터리에 `chmod -R o+rX`, 설정 문서에 `chmod o+r`를 실행하거나 umask `022`에서 다시 받는다. postgres volume을 이미 초기화한 설치는 초기 SQL을 다시 읽지 않으므로, 지금까지 드러나지 않았더라도 이 검사가 있는 버전의 `upgrade`·`start`에서 처음 멈출 수 있다. 이 검사가 없는 이전 릴리스에서는 같은 원인이 `deploy`의 postgres unhealthy(로그의 `Permission denied`)나 migrate 실패로만 드러난다.

quota 오류는 [XFS 준비](/run-server/self-hosting/prepare-xfs), bucket 보호·권한 오류는 [bucket 준비](/run-server/self-hosting/prepare-checkpoint-bucket)를 확인한다. env 권한 오류는 [2단계의 파일 모드](#2-비밀과-설정-문서), settings digest 오류는 [3단계의 digest·release 입력 생성](#3-release-입력-생성)을 확인한다. 첫 deploy가 실패해도 정상 배포의 상태 파일이 있다고 가정하지 않는다.

## 되돌리기

정상 설치는 [중지·재시작](/run-server/self-hosting/stop-compose)으로 데이터를 보존한다. 실패한 첫 deploy는 원인과 이 project가 만든 리소스를 먼저 조사한다. reset이나 volume 삭제를 기본 정리로 사용하지 않는다. 필요한 데이터가 없음을 확인한 설치만 별도 제거 절차를 따른다.
