## What you will do

Create the first owner and workspace, then issue an API key for each user. Distinguish API key revocation from revoking a session's execution grant.

<a id="준비물" />
## Before you begin

Complete [installation](/run-server/self-hosting) and [access configuration](/run-server/self-hosting/access). Only operators receive and handle the setup link.

<a id="1-첫-owner-만들기" />
<a id="단계" />
## Steps

### 1. Create the first owner

The operator gets the first owner's one-time setup link as a file, from a command on the installation. The command is in the api image and takes only the email address of the person who becomes the owner. No password goes in a command argument or an environment variable: whoever opens the link sets it. The link never appears on screen; the screen shows only the file path and the expiry.

On a test-ops single server, write it straight to a new file on the host. `DEPLOYMENT_DIR` is the per-installation directory set in [single-server installation](/run-server/self-hosting/single-server); a path inside the bundle directory is refused.

```bash
scripts/test-ops.sh setup-link --email <owner-email> --out "$DEPLOYMENT_DIR/owner-link.json"
```

On other compose setups, make the file inside the api container, copy it to the host, and delete the container's copy.

```bash
docker compose --profile apps exec -T api \
  bun run apps/control-host/src/main.ts admin bootstrap-owner \
  --email <owner-email> --out /tmp/owner-link.json
(umask 077 && set -C && docker compose --profile apps exec -T api cat /tmp/owner-link.json >owner-link.json)
docker compose --profile apps exec -T api rm -f /tmp/owner-link.json
```

On Kubernetes, first follow [Check the installation's context, namespace and fullname](/run-server/self-hosting/kubernetes#준비물). `werft` below is that example installation name. Pick one Pod first so all three commands reach the same Pod.

```bash
POD="$(kubectl -n werft get pod -l app.kubernetes.io/instance=werft,app.kubernetes.io/component=api -o name | head -n 1)"
kubectl -n werft exec "$POD" -c api -- \
  bun run apps/control-host/src/main.ts admin bootstrap-owner \
  --email <owner-email> --out /tmp/owner-link.json
(umask 077 && set -C && kubectl -n werft exec "$POD" -c api -- cat /tmp/owner-link.json >owner-link.json)
kubectl -n werft exec "$POD" -c api -- rm -f /tmp/owner-link.json
```

The file is created new with mode 0600. If a file of that name exists, the command refuses instead of overwriting it. The file holds, as JSON, the same fields as the [member invite](/members#api-응답) response.

| Field | Contents |
| --- | --- |
| `accept_path` | The path of the setup screen, of the form `/bootstrap#setup=<setup_token>` |
| `accept_url` | `accept_path` appended to `CONSOLE_ORIGIN`. `null` when `CONSOLE_ORIGIN` is not set |
| `expires_at` | When the link expires |

With a browser, open `accept_url` (or `accept_path` appended directly to the console's origin) and enter the owner details and workspace name. Without a browser, take the value after `#setup=` as `setup_token` and send it with the owner details to `POST /v1/auth/bootstrap`. The request body is in the API reference the installation serves (`/docs`). Either way, the email address must be the one given to the command. Any other address is refused with `403`, and the link stays usable. Then sign in at `/login` and delete the link file.

The link stops working once used and expires after 24 hours. Running the command again makes the old link stop working and issues a new one. While an owner exists, the command makes neither a link nor a file and exits 1. Each run leaves one `setup_link_issued` line in the api container's log (`docker compose logs api`, `kubectl logs`). The line holds only the link id, the email address and the expiry, never the token or the link. When the link creates the first workspace, that workspace's first receipt (`bootstrap_owner`) records the link's id and when it was made.

<a id="2-사용자별-key-발급" />
### 2. Issue per-user keys

```bash
KEY="$(scripts/test-ops.sh key create <owner_id> \
  --scopes sessions:read,sessions:write,sessions:approve,sessions:control,sessions:recover)"
```

`<owner_id>` names the owner grouping this key's sessions. Choose a different value for each user. This is separate from web console accounts; do not use a workspace id.

The SDK and HTTP API connect using this server address and key ([SDK installation](/getting-started/install)).

On Kubernetes, use the following command.

First [check the installation's context, namespace, and fullname](/run-server/self-hosting/kubernetes#준비물). The `werft` below is the example installation name.

```bash
kubectl -n werft exec deploy/werft-api -c api -- \
  bun run apps/control-host/src/api/keys.ts create <owner_id> \
  --scopes sessions:read,sessions:write,sessions:approve,sessions:control,sessions:recover
```

The plaintext key appears on stdout only once; stderr reports the key id. Deliver the plaintext securely to the intended user without storing it in public logs. Per-user key owner identifiers are separate from web console accounts. Limit each API key's scopes to the tasks it needs.

<a id="3-폐기-연락과-실행-권한" />
### 3. Revocation contacts and execution grants

Tell users whom to contact to revoke a key. The operator CLI in the checkout provides:

```bash
scripts/test-ops.sh key revoke <key_id>
API_CONTAINER='<api-container-id-from-this-installation>'
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/grants.ts revoke <session_id> --reason <text>
docker exec "$API_CONTAINER" bun run apps/control-host/src/api/grants.ts restore <session_id> --reason <text>
```

Replace API_CONTAINER with the API container id identified from this installation's status and Docker project label. On Kubernetes, prepare a checkout matching the installed version and host Bun and kubectl, then use `keys:k8s` and `grants:k8s`. Both `NAMESPACE` and `RELEASE` default to werft.

| Operation | Effect |
| --- | --- |
| key revoke | Blocks subsequent API authentication with that key. It does not stop sessions already executing |
| grants revoke | Revokes the specified session's execution grant and credentials and requests execution termination |
| grants restore | Restores the execution grant after execution is confirmed absent. It does not revive a revoked API key |

<a id="4-개인-key" />
### 4. Personal keys

A key made with `keys create <owner_id>` is an operator key. It groups sessions under that owner outside the web console's workspace. To let a member see the sessions they made on the web in the same list through the API, make that member a personal key.

```bash
scripts/test-ops.sh key create --workspace <workspace_id> --personal <user_id> \
  --scopes sessions:read,sessions:write
```

- A personal key has only the scopes both the key and its maker's current role allow. Once that person's account or membership is disabled, the next request gets `401`.
- Whatever its scopes, an API key cannot perform management actions (member management, session takeover, key issuance) (`403`). Management actions use a person's sign-in session.
- A personal key or an agent key cannot answer approval requests of sessions that key started (`403`, `reason_code: self_approval`).

<a id="5-멤버-내보내기와-인수" />
### 5. Offboarding members and taking over sessions

An owner or admin calls `POST /v1/members/{user_id}/disable` (body `{}` or `{"reason": "…"}`) from a sign-in session. Only an owner can disable an owner (`403 OWNER_PROTECTED`), you cannot disable yourself (`403 SELF_PROTECTED`), and the last owner cannot be disabled (`409 LAST_OWNER`).

- In one step it disables the membership, revokes all of that person's sign-in sessions and their personal keys in that workspace, and revokes the linked Slack account. Agent keys are not touched.
- Open sessions that person requested wait for takeover. They finish only the running turn, and new messages are refused with `409 TAKEOVER_REQUIRED`. An owner lists them with `GET /v1/takeovers` and takes one over with `POST /v1/sessions/{id}/takeover`, becoming its requester.
- `POST /v1/members/{user_id}/enable` restores only the membership. Revoked sign-in sessions, personal keys and Slack links do not come back, so the person signs in again and gets new keys. Sessions nobody took over yet go back to that person.
- To block the whole account, use `POST /v1/users/{user_id}/disable` and `/enable`. It is allowed only when the target belongs only to workspaces where the caller is an owner or admin.
- There is no sync with an external directory (SCIM). Removing a person from your company SSO is not reflected here, so call this API separately.

<a id="6-감사-기록과-보존-기간" />
### 6. Audit log and retention

Authorization decisions record denials and the allows of management actions, approvals and Slack input in the audit log. Records cannot be changed. A row's `request_id` is the response's `X-Request-Id` and matches the receipt that request left.

- **Reading.** The owner filters by period, kind and person, follows the rows of one request, and exports an NDJSON file under Settings > Workspace > Audit log in the console. The same content is read from a sign-in session with `GET /v1/audit/events` (`limit` default 50, max 200). Admins, members and API keys get `403`.
- **Export.** With `Accept: application/x-ndjson`, every filtered row is sent one per line, and the last line is `{"kind":"end",…}`. Up to 100,000 rows go at once; beyond that, continue with `next_cursor` on the end line. Each API process runs only one per workspace at a time (a second in the same process gets `429`), and it is cut after 10 minutes. A file without the end line is incomplete, so call again with the `cursor` of the last line received.
- **Retention.** 90 days by default. The owner changes it from a sign-in session with `POST /v1/workspaces/{id}/audit-retention` (`{"audit_retention_days": …}`, 30 to 3650). The current value is in `workspace.settings` of `GET /v1/auth/me`. The reconciler deletes decision rows past the period. Receipts are not deleted, but the audit log shows only those inside the retention period.

<a id="7-공유-범위-밖의-세션" />
### 7. Sessions outside the share scope

Even for owners and admins, a session outside its share scope does not appear in lists, details or turns (`404`). Such sessions are handled only through the paths below. The reason (`justification`, up to 1000 characters) is kept in the decision record.

- **Admin list.** `GET /v1/admin/sessions` shows owners and admins the workspace's sessions, newest first, whatever their scope. Entries hold metadata only, such as who made it, the agent release, state and share scope; no messages, titles or summaries.
- **Audit read.** `POST /v1/sessions/{id}/audit-read` (`{"justification": "…"}`) returns the session detail and one page of turns (`cursor`, `limit`), and every read adds one audit record. It only reads, so messages, answers and termination stay `404` afterwards.
- **Admin terminate.** `POST /v1/admin/sessions/{id}/terminate` (`{"expected_revision": …, "justification": "…"}`) lets owners and admins stop a session whatever its scope. The reason becomes the stop reason.
- **Admin recovery.** `POST /v1/admin/sessions/{id}/recovery-decisions` lets only owners decide recovery whatever the scope. The body is the recovery decision of [Session recovery](/run-server/self-hosting/recover-sessions), and its `reason` is the justification.
- **Takeover.** When a departed member's session is outside what the person taking it over can see, send `{"justification": "…"}` to `POST /v1/sessions/{id}/takeover`. Without it the answer is `403` (`reason_code: justification_required`).
- **Taking over a private channel's session.** A `private_channel` session is taken over through the same route by a current member of its channel who may write to it, with no justification asked. An owner or admin outside the channel gets `404`.

<a id="확인" />
## Verify

Reading `/v1/sessions` with each user's key must return a response within its allowed scope; a request without a key must return 401. Revoked keys must fail authentication. Check the grants output receipt and execution state to distinguish acceptance from actual termination.

<a id="자주-막히는-곳" />
## Troubleshooting

If the link opens on "This setup link can't be used", it was already used, is more than 24 hours old, or was replaced by running the command again. While no owner exists, run the command again for a new link. Do not use a workspace id as the CLI owner id.

<a id="되돌리기" />
## Roll back

Do not reset the installation to remove an already-created first owner. Revoke incorrectly issued keys and create new ones with the correct scopes. Restore grants only after the old execution is gone.
