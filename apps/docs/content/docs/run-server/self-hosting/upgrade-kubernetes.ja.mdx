## 作業内容

直前の worker pin とサポート範囲を保持し、アップグレード検査結果を読んでから公開 chart を更新します。

> **最初にすること: Codex サンドボックス。** この chart から `codexSandbox` の既定が変わりました。以前の chart はインストーラー DaemonSet と ClusterRole を既定で作りましたが、今の既定（`codexSandbox.provider: disabled`）はクラスタースコープのリソースを作りません。そのまま上げると helm upgrade が ClusterRole とインストーラー DaemonSet を消し、Codex エージェントの入力は `CODEX_SANDBOX_NOT_INSTALLED` で失敗します。**Codex サンドボックスを使うなら、values に `codexSandbox.provider: installer` を入れてから上げてください。** Security Profiles Operator やノードイメージでプロファイルを置いている環境は `external` を入れます。以前の `codexSandbox.installer.enabled` は使えず、残っていると render が止まります（`installer.enabled=true` は `provider: installer`、`false` は `external`）。

<a id="준비물" />
## 準備

[変更履歴](https://github.com/JeongJaeSoon/werft/blob/main/CHANGELOG.md)で対象バージョンの運用者向け作業を先に読みます。

環境ごとの values、jq・helm・kubectl、現在の deployed revision と worker-previous.json、DB・S3 バックアップが必要です。

[共通の実行前ゲート](/run-server/self-hosting/upgrade-compose#실행-전-게이트)の有効化順序と rollback の下限を先に照合します。Compose 専用の検査コマンドの代わりに、下記の Helm hook と直接検査を使います。

[設置環境の context・namespace・fullname](/run-server/self-hosting/kubernetes#준비물)を確認します。新 control-host・直前 worker の組み合わせは、試験環境で turn 1 完了 → worker Pod 削除 → checkpoint から turn 2 完了、および API の worker 要求に 400 がないことを確認します。まず turn 1 が完了するかを見ます。直前の worker が新しい API の応答を読めない場合、API は 400 を返さず、worker は起動直後に終了し、セッションは `STARTUP_FAILED` で停止します。プロファイル削除リリースはこの組み合わせをサポートしないため、そのリリースへ更新するときは新しい control-host と新しい worker で turn 1 の完了を確認します（[プロファイル削除リリースのアップグレード順序](/run-server/self-hosting/upgrade-compose#프로필-제거-릴리스의-업그레이드-순서)）。

<a id="단계" />
## 手順

<a id="1-대상-chart와-제어-영역-우선-교체" />
### 1. 対象 chart と制御領域を先に更新

`VERSION` は正確な対象 chart バージョンです。`--reuse-values` を使わず、環境ごとの values だけを渡します。protocol・manifest・usage に変更があれば、control-host と worker を同じ upgrade で更新しません。

プロファイル削除リリースへ更新するときは、この手順を行いません。そのリリースの control-host の応答を以前の worker が読めないため、手順 1 と手順 2 の間は新しいセッションが一つも起動しません。手順 2 で control-host と worker を一つの upgrade で一緒に更新します（[プロファイル削除リリースのアップグレード順序](/run-server/self-hosting/upgrade-compose#프로필-제거-릴리스의-업그레이드-순서)）。

env で指していた資格情報を DB へ移すリリース（migration `0285_credential_carried_auth`）へ更新するときは、この手順の前に `kubectl -n werft scale deploy/werft-api --replicas=0` で以前の api をすべて止め、`kubectl -n werft wait --for=delete pod -l app.kubernetes.io/instance=werft,app.kubernetes.io/component=api --timeout=120s` で Pod の終了を待ちます。`kubectl -n werft get pods -l app.kubernetes.io/instance=werft,app.kubernetes.io/component=api -o name` が何も出力しなくなったら、下の `helm upgrade` に `--set api.replicas=1` を加えて実行します。scale は終了を待たず、終了中の api も要求を処理し終えるまで（最大 35 秒）push 実行器を動かします。chart の既定の api replica は複数で、まだ移したことを読んでいない replica が、移した push 要求を `catalog_changed` で失敗させたり、トークン再発行を拒否したりすることがあります。api のログで移した行（`… took its credential from …`）を確かめたあと、手順 2 が replica 数を values のとおりに戻します（[env で指していた資格情報は DB へ一度移す](/run-server/self-hosting/upgrade-compose#env로-가리키던-자격-증명은-db로-한-번-옮긴다)）。

外部の資格情報の出所をなくしたリリース（migration `0288_remove_external_credentials`）へ更新するときは、values から `secrets.catalogEnv` と `config.aws.secretsManagerEndpointUrl` を削除します。残っているとレンダーが止まります（`secrets.catalogEnv is removed: credentials are entered in the console…`、`config.aws.secretsManagerEndpointUrl is removed…`）。Secret のモデル key は api に渡らなくなるため、更新の前にコンソールでそのキーを入れます。停止した行、`needs_value`、設定文書は[外部の資格情報の出所をなくしたリリース](/run-server/self-hosting/upgrade-compose#외부-자격-증명-출처를-없앤-릴리스)に従います。

最初の owner を一回限りの設定リンクで作るリリースへ更新するときは、values から `secrets.bootstrapToken` を、Secret から `BOOTSTRAP_TOKEN` を削除します。残っているとレンダーが止まります（`secrets.bootstrapToken is removed…`）。owner がいる環境では、ほかに変わるものはありません。owner をすべて失ったときの復旧も、同じ設定リンク（[最初の owner を作る](/run-server/self-hosting/users-and-keys#1-첫-owner-만들기)の `admin bootstrap-owner`）で行います。

実行の上限、セッション記録の保管、作業領域の保持の設定、あわせて十二個を Web に移したリリースへ更新するときは、インストールの values をそのまま渡します。values に残った `config.limits` の `QUEUED_INPUT_LIMIT_PER_SESSION`・`STORAGE_LIMIT_BYTES`・`SESSION_COST_LIMIT_USD`・`SESSION_TOKEN_LIMIT`・`MAX_TURN_SECONDS`・`PROVIDER_MAX_RETRIES`、`api.workspaceEnforce` は、migrate Job にだけ入るようになりました。chart の `config.limits` の既定値は `EXECUTION_SLOT_LIMIT` だけです。`api.extraEnv` の同じ名前と `PENDING_REQUEST_TTL_SEC` も migrate Job に入ります。api Pod にもそのまま残りますが、api は読みません。同じ名前が二つあれば `api.extraEnv` が優先します。`MAX_TURN_SECONDS`・`PROVIDER_MAX_RETRIES` だけは、worker を起動していた scheduler が読んでいたとおりに選びます。`scheduler.extraEnv` の同じ名前が `config.limits` より優先し、`api.extraEnv` の二つの名前は移しません。作業領域の保持の `EXECUTION_WORKSPACE_STOPPED_TTL_SEC`・`EXECUTION_WORKSPACE_PAUSED_TTL_SEC` も同じです。`scheduler.extraEnv` に残した値は scheduler Pod にもそのまま入りますが、scheduler は読みません。そこの空文字列は以前の scheduler が起動を拒否していた値なので、移さずにそのキーを止めます。セッション記録の保管の `sessionArchive.afterDays`・`dryRun` は chart の既定値（180、`true`）がなくなり、インストールの values に書いた値だけが `SESSION_ARCHIVE_AFTER_DAYS`・`SESSION_ARCHIVE_DRY_RUN` として migrate Job に入ります。書いておいた `0` と `false` も値として移します。保管の CronJob はこの二つを受け取らず、実行のたびに DB から読みます。以前の chart と違い、範囲外の値でレンダーは止まりません。migrate がそのキーを止めます。Job は `pre-upgrade` hook なので、どの role よりも先に、保存した値のないキーへ一度だけ移します。Job のログで `note: … was carried into Settings > Workspace > Execution limits` の行を確かめたら、values からそのキーを削除します。範囲外の値は移さず、そのキーを止めます（`note: … was not carried in`）。コンソールで値を保存すると解けます。どれも設定していないインストールは、以前の chart と同じ既定値を使います（[Web に移した実行の上限](/run-server/self-hosting/upgrade-compose#웹으로-옮긴-실행-한도)）。

object store の設定を一か所からだけ受け取るリリースへ更新するときは、どの role の `extraEnv`・`config.limits`・`secrets.catalogEnv` に `AWS_` か `CHECKPOINT_OBJECT_` で始まる名前があってもレンダーが止まります（`… must not be set through extraEnv, config.limits or secrets.catalogEnv`）。hook は動かず、Deployment も変わりません。以前の chart は `extraEnv` をその role にだけ入れていました。そのため `api.extraEnv` の値は api でだけ優先し、checkpoint GC・セッション記録の保管の CronJob と scheduler は chart の値で動いていました。値は次のように移します。`S3_BUCKET` → `config.checkpoints.bucket`、`CHECKPOINT_OBJECT_STORE` → `config.checkpoints.objectStore`（`s3`・`disabled`）、`CHECKPOINT_OBJECT_PROTECTION` → `config.checkpoints.protection`、`CHECKPOINT_OBJECT_ENCRYPTION_CHECK` → `config.checkpoints.encryptionCheck`（`enforce`・`warn`）、`AWS_REGION` → `config.aws.region`、`AWS_ENDPOINT_URL` → `config.aws.endpointUrl`、`AWS_ENDPOINT_URL_SECRETS_MANAGER` → `config.aws.secretsManagerEndpointUrl`（外部の資格情報の出所をなくしたリリースからは削除します）、二つの静的キー → `secrets.objectStoreKeys` と Secret の同じ名前。それ以外の `AWS_` の名前（`AWS_ENDPOINT_URL_S3`、`AWS_ROLE_ARN`、`AWS_PROFILE` など）は chart から入れる手段がないので削除します。IRSA role は api ServiceAccount の annotation で与えます。二つの CronJob もその ServiceAccount を使います。名前を移しても Pod が受け取る値が同じなら、作業はそれだけです。

移す前に、以前の chart が動いている間に設定が分かれていなかったかを確かめます。values の `api.extraEnv` に上の名前があり、その値が chart の値（`config.*`、既定値を含む）と違えば、セッション記録の保管 job は api が読まない保存先へイベントを移し、DB の行を削除したかもしれません。保管の記録は object key と version だけを持ち、bucket は持ちません。そのため設定を一つに揃えると、そのイベントはもう読めません。bucket をコピーしても version ID が変わるので代わりになりません。残す値は api の値です。checkpoint は api がその保存先に書きました。`scheduler.extraEnv` の `S3_BUCKET`・`AWS_REGION` が api の値と違っていた場合、揃えるとその値を含む隔離 stamp が変わり、worker が一度ずつ置き換わります（[アップグレードの互換性](/run-server/self-hosting/explanation/compatibility)）。更新の前に次を行います。

1. 保管の CronJob を止めます: `kubectl -n werft patch cronjob werft-session-archive -p '{"spec":{"suspend":true}}'`。`suspend` はすでに作られた Job を止めません。止めたあと、下のコマンドが何も出力しなくなるまで待ちます。この CronJob が作った Job のうち `Complete` でも `Failed` でもないもの（Pod がまだ `Pending` の Job も）を出力します。CronJob の `status.active` は、controller が Job を作った直後に記録できないとその Job が漏れるので使いません。それより前に一覧を取ると、まだ終わっていない Job がその後に保管したセッションが漏れます。

```bash
UID_=$(kubectl -n werft get cronjob werft-session-archive -o jsonpath='{.metadata.uid}')
kubectl -n werft get jobs -o json | jq -r --arg uid "$UID_" '.items[]
  | select(any(.metadata.ownerReferences[]?; .uid == $uid))
  | select(any(.status.conditions[]?; (.type == "Complete" or .type == "Failed") and .status == "True") | not)
  | .metadata.name'
```

2. 運用者の DB クライアントで `SELECT DISTINCT session_id FROM session_event_archives;` を実行し、保管されたセッションを得ます。行がなければ 4 へ進みます。
3. セッションごとに、以前の chart の CronJob から restore Job を作ります。CronJob と同じ保存先の設定で動きます。すべての Job が成功し、ログに `Session archive restored` が出ることを確かめます。その後 `SELECT count(*) FROM session_event_archives;` が `0` であることを確かめます（restore はその行を削除します）。0 でなければ 4 へ進みません。

```bash
kubectl -n werft create job "werft-archive-restore-$N" --from=cronjob/werft-session-archive --dry-run=client -o json \
  | jq --arg id "$SESSION_ID" '.spec.template.spec.containers[0].args += ["restore", $id]' \
  | kubectl -n werft apply -f -
```

4. values の名前を上のとおり移し、この手順の `helm upgrade` を実行します。その後 `kubectl -n werft patch cronjob werft-session-archive -p '{"spec":{"suspend":false}}'` で CronJob を再開します。Helm は `suspend` を扱わないため、更新後も止まったままです。戻したイベントは次の保管の実行が api の保存先へ再び移します。

対象 chart を取得し、手順 2 まで使う二つの関数を定義します。対象リリースの二つの worker イメージの項目は chart の `files/release-images.json` に、次の values ファイルを作るプログラムは `files/next-workers.jq` にあります。

```bash
VERSION=<new-version>
rm -rf target-chart \
  && helm pull oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" --untar --untardir target-chart
# deployed_values: the values of the deployed revision; next_workers <control|final>: the values file
deployed_values() {
  DEPLOYED="$(helm -n werft history werft -o json | jq '[.[] | select(.status == "deployed")] | last.revision')" \
    && helm -n werft get values werft --all --revision "$DEPLOYED" -o json > deployed-values.json
}
next_workers() {
  jq -n -f target-chart/werft/files/next-workers.jq --arg phase "$1" \
    --slurpfile deployed deployed-values.json \
    --slurpfile release target-chart/werft/files/release-images.json \
    --argjson known "$KNOWN"
}
# Drop the runtime the values files before them set, which Helm would merge with the next one
echo '{"images": {"worker": {"runtime": null}}}' > worker-reset.json
echo '{"images": {"workerPrevious": {"runtime": null}}}' > worker-previous-reset.json
```

```bash
KNOWN='{}'
deployed_values && next_workers control > control-phase.json \
  && helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
    --namespace werft -f values-<installation>.yaml \
    -f worker-reset.json -f worker-previous-reset.json -f control-phase.json \
    --set-json 'upgrade.approvedSessions=[]' --timeout 10m \
  && kubectl -n werft rollout status deploy/werft-api --timeout=600s
```

中間 upgrade は新 chart の control-host を適用し、worker・egress proxy は現在のものを維持します。維持するのはイメージです。chart は丸ごと適用されるため、egress proxy の設定（allowlist はその Deployment の env です）は新 chart の値になり、proxy Pod もこの upgrade で起動し直します。`config.egress.privateAllowlist` を自分で設定している環境は、先に [worker gateway を 3200 番ポートへ移したリリース](/run-server/self-hosting/upgrade-compose#worker-gateway를-3200-포트로-옮긴-릴리스)を読みます。migration、**すべての** API の更新、ready を確認してから次に進みます。起動済み worker はイメージ変更だけでは交代せず、次の launch から新イメージを使います。

`next_workers control` はデプロイ済みの worker イメージと egress proxy をそのまま書きます。単一イメージの環境には、デプロイ済みの `images.worker`・`images.workerPrevious` と `images.workers: []` を書きます。公開 chart の既定値は対象リリースの二つのイメージの一覧なので、`images.workers: []` がないとこの upgrade が worker イメージまで変えます。対象 chart の `images.worker.runtime` は空なので、デプロイ済みの runtime はそのまま残り、runtime なしでデプロイした環境は runtime なしのままです。一覧の環境にはデプロイ済みの一覧を書きます（[イメージ一覧の環境の upgrade](#이미지-목록-설치의-upgrade)）。コマンドは `&&` でつながっており、chart を取得できない、またはデプロイ済みの値を読めない場合、`helm upgrade` は実行されません。

ワークスペース MCP サーバーをアドレスで検査するリリースへ更新するときは、手順 1 と手順 2 の間は proxy イメージが現在のものなので、二つの credential 一覧のどちらにもないサーバーを呼ぶセッションの呼び出しが 403 になり、receipt の理由は `egress_proxy_outdated` です。新しい proxy が要求を受け始めれば戻ります。詳しくは [Compose 文書の同じ節](/run-server/self-hosting/upgrade-compose#워크스페이스-mcp-서버를-주소로-검사하는-릴리스)を参照してください。

<a id="2-최종-worker와-proxy-교체" />
### 2. 最終的な worker と proxy の更新

公開 chart は既定値として対象リリースの Claude・Codex の二つのイメージを `images.workers` に含み、`images.worker` と `images.workerPrevious` は空です。単一イメージの環境は、対象リリースの `files/release-images.json` からデプロイするエンジンの項目を `images.worker` として取り出し、`images.workers: []` と一緒に渡します（`worker.json`）。直前のイメージは環境ごとに違い、chart は判断できません。worker digest が変わる upgrade は、対象の `images.workerPrevious` が現在デプロイ済みのイメージでなければ `refused` で止まり、承認でも続行できません（[アップグレード前検査](/run-server/self-hosting/upgrade-kubernetes#3-검사-결과와-예외)）。そのため現在のイメージをファイルに保存して一緒に渡します。プロファイル削除リリースへ更新するときも、このファイルをそのまま渡します。ファイルのイメージ（プロファイル削除前にビルドした worker）はサポート範囲に入りませんが、そのイメージで起動するセッションはありません（[プロファイル削除リリースのアップグレード順序](/run-server/self-hosting/upgrade-compose#프로필-제거-릴리스의-업그레이드-순서)）。

```bash
ENGINE=claude
if deployed_values \
  && CURRENT="$(jq -er '.images.worker.digest' deployed-values.json)" \
  && jq -e --arg e "$ENGINE" '[.[] | select(.runtime.engine == $e)]
      | if length == 1 then {images: {workers: [], worker: (.[0] | {repository, digest, runtime})}}
        else error("the release has no single \($e) image") end' \
    target-chart/werft/files/release-images.json > worker.json \
  && TARGET="$(jq -er '.images.worker.digest' worker.json)"; then
  echo "deployed ${CURRENT}"
  echo "target   ${TARGET}"
  PREVIOUS=worker-previous.json
  if [ "$CURRENT" != "$TARGET" ]; then
    PREVIOUS=worker-previous.next.json
    jq '{images: {workerPrevious: (.images.worker | {repository, digest, runtime})}}' \
      deployed-values.json > "$PREVIOUS"
  fi
  set -- -f values-<installation>.yaml -f worker-reset.json -f worker.json
  if [ -f "$PREVIOUS" ]; then set -- "$@" -f worker-previous-reset.json -f "$PREVIOUS"; fi
  if helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
    --namespace werft "$@" --timeout 10m; then
    if [ "$PREVIOUS" != worker-previous.json ]; then mv "$PREVIOUS" worker-previous.json; fi
  fi
fi
```

`ENGINE` はこの環境がデプロイするエンジンです。Codex worker をデプロイする環境は `ENGINE=codex` にします。そのままにすると worker が Claude イメージに変わり、直前イメージのファイルもデプロイしていないイメージと比較して決まります。`deployed_values` は deployed revision の値を読みます。revision を省くと、失敗した upgrade がある場合、その revision の値、つまり更新候補のイメージが返ります。worker digest が違えば現在のイメージを候補ファイルに書き、upgrade 成功後だけ `worker-previous.json` をそのファイルで置き換えます。失敗した upgrade は保存ファイルを変更しません。digest が同じなら既存ファイルをそのまま渡します。初回設置後、worker が変わらない upgrade にはまだファイルがなくても問題ありません。前のコマンドが一つでも失敗すると `helm upgrade` は実行されません。Helm は values ファイルの runtime を前のファイルの runtime とキーごとに統合します。そのため、イメージのファイルの前にその runtime を空にするファイル（`worker-reset.json`、`worker-previous-reset.json`）を渡します。渡さないと、環境の values に残った前のイメージの `restorableSchemes` などのキーが新しいイメージに付きます。すると新しいイメージが、復元できない checkpoint を復元できると伝えることになります。

- `worker.json` なしで upgrade すると、公開 chart の二つのイメージの一覧が適用されます。values に `images.worker` を書いた環境は render で失敗します（`set images.workers: [] to deploy images.worker alone`）。書いていない環境は一覧の環境に変わり、現在のイメージを直前のイメージとして残しません。現在のイメージの checkpoint を対象一覧のイメージが復元できない場合（エンジン・SDK・CLI が違う、または runtime なしでデプロイしたイメージ）、アップグレード前検査は承認できない `refused` で停止します。
- `worker-previous.json` は設置環境とともに保管し、次の upgrade にも渡します。worker digest が同じ upgrade で省くと、デプロイ済みの直前イメージが失われます。その場合、事前検査はセッションを比較し、対象イメージ（現在、および存在すれば直前）のどちらとも組み合わせが合わない、または組み合わせ未記録のセッションがあれば `refused` で停止します（承認可能）。誤って省いたなら承認せず、ファイルを追加して再実行します。選択セッションがなく `upgrade.approvedSessions` が空なら通過します（前回承認が残っていれば `refused`）。見えないセッションについては下記「検査対象外」を参照してください。同日にマージされた `main` chart は worker digest が同じ場合があります。
- `--reuse-values` は使いません。以前の chart の値を既定にするため、新 chart でもイメージが以前のまま残ります。
- `helm get values --all` 全体を values ファイルとして渡しません。以前の digest が新 chart の値を上書きします。`.images.worker` だけを取り出します。
- `v*` タグで公開した chart も同じ手順です。

最終 upgrade には control-phase.json を渡しません。worker-previous.json は成功後だけ置き換え、以後の upgrade 用にも保持します。承認一覧は毎 upgrade で空にし、新しい affected 一覧を確認します。

<a id="이미지-목록-설치의-upgrade" />
#### イメージ一覧の環境の upgrade

`images.workers` で worker イメージを渡す環境（Claude と Codex を一緒に動かす環境、公開 chart の既定値で設置した環境を含む）は、上の `worker.json` の代わりに `next_workers final` で values ファイルを作ります。単一イメージの環境を初めて一覧に切り替えるときもこの手順を使います。Helm は一覧を統合せず丸ごと置き換えるため、環境の values や前回の upgrade の一覧に新しいリリースのイメージは自動では入りません。リリースごとにこの手順で一覧を作ります。`files/next-workers.jq` と `files/release-images.json` がない chart（この手順ができる前のリリース）では一覧の環境を upgrade しません。

**1 段階目（制御領域）。** 上の手順 1 をそのまま行います。一覧の環境では、`next_workers control` がデプロイ済みの一覧を渡し、`images.worker` と `images.workerPrevious` の digest・runtime を空にします。環境の values が単一の値を書いていても、chart は一覧の横の単一の値を拒否するためです。単一イメージの環境を初めて一覧に切り替えるときは、この段階では単一イメージが維持されます。

**2 段階目（最終の一覧）。** 対象リリースの二つのイメージを、デプロイ済みのイメージに加えます。一覧の環境ではデプロイ済みの一覧が、単一イメージの環境ではデプロイ済みの `images.worker` と（あれば）`images.workerPrevious` がデプロイ済みのイメージです。`worker-previous.json` は渡しません。直前のイメージはデプロイ済みの値から読みます。

```bash
deployed_values && next_workers final > workers.json \
  && helm upgrade --install werft oci://ghcr.io/jeongjaesoon/werft --version "$VERSION" \
    --namespace werft -f values-<installation>.yaml -f workers.json \
    --set-json 'upgrade.approvedSessions=[]' --timeout 10m
```

単一イメージの環境を初めて切り替えるときは、`KNOWN` にデプロイ済みのイメージごとの `releasedAt` を、runtime なしでデプロイしていれば runtime も digest で書きます。デプロイ済みの単一の values の `images.worker.releasedAt` はプログラムが読みません。そのキーは以前の chart の既定値で環境が決めた digest と合わないことがあり、この chart の `images.worker` にはありません。値はデプロイしたリリースの manifest から得ます。`releasedAt` はそのリリースの commit の committer 時刻です。Codex イメージを `images.worker` としてデプロイしているなら、`IMAGE=` の行を `IMAGE=worker-codex RUNTIME=workerCodexRuntime RELEASED=workerCodexReleasedAt` に変えます。`images.workerPrevious` があれば、そのリリースの manifest で同じ項目をもう一つ作って合わせます。

```bash
TAG=<the deployed release, e.g. v0.2.0>
IMAGE=worker RUNTIME=workerRuntime RELEASED=workerReleasedAt
mkdir -p "$TAG" && curl -fsSL -o "$TAG/release-manifest.json" \
  "https://github.com/JeongJaeSoon/werft/releases/download/$TAG/release-manifest.json" \
  && AT="$(curl -fsS "https://api.github.com/repos/JeongJaeSoon/werft/commits/$(jq -r .commit "$TAG/release-manifest.json")" | jq -er .commit.committer.date)" \
  && KNOWN="$(jq -c --arg at "$AT" --arg i "$IMAGE" --arg r "$RUNTIME" --arg t "$RELEASED" '{(.images[$i].digest): {runtime: .[$r], releasedAt: (.[$t] // $at)}}' "$TAG/release-manifest.json")"
```

プログラムは次のように一覧を作ります。

- エンジンごとに `releasedAt` の新しいイメージから書き、撤回されていないイメージを二つまで残します。三つ目からは外れます。外れたイメージを必要とするセッションは[アップグレード前検査](#3-검사-결과와-예외)が判定します。そのイメージで slot を持つ launch の checkpoint を残ったイメージが復元できなければ、承認できない `refused` です。checkpoint だけが残るセッションは affected 一覧に載ります。runtime なしでデプロイした単一イメージで始まった launch には runtime の記録がありません。検査はそうした launch を、デプロイ済みの一覧が同じ digest に宣言した runtime で判定します。一覧に切り替えるときに `KNOWN` に書いた値です。そのため、そのイメージが外れる upgrade（たいてい一覧に切り替えた次の upgrade）も、同じ runtime の再ビルドが対象にあれば、その launch が slot を持ったまま通ります。デプロイ済みの一覧にその digest の runtime がないか、同じ digest の宣言が食い違っていれば、そのイメージ自身しか復元しないとみなし、その launch が slot を手放すまで `refused` です。宣言した runtime がそのイメージが実際に載せる値と違うかどうかは、検査にはわかりません。
- 同じ digest は一度だけ書きます。デプロイ済みのイメージが撤回されていれば、対象リリースが同じ digest を書いても撤回されたままにします。撤回されたイメージは、残したイメージのうち最も古いものより新しいときだけ残します。撤回されていないイメージが一つもないエンジンは、撤回されたイメージをすべて残します（一覧からエンジンが外れるのとは違います）。古い撤回イメージが外れると、その組み合わせの checkpoint は `runtime_retired` ではなく `incompatible_checkpoint` で止まります。
- 次の場合は values ファイルを作らずに失敗します。デプロイ済みのイメージに runtime か `releasedAt` がないとき、対象イメージがデプロイ済みの同じエンジンのどのイメージよりも新しくないとき、同じ digest が別の runtime・時刻・repository で書かれているとき、同じエンジンの二つのイメージが同じ時刻のときです。`releasedAt` は commit 時刻なので、公開の順序と違うことがあります。デプロイ済みのイメージより古い commit に付けたタグの chart と、main が公開済みの commit をタグ push で再ビルドした chart（digest は違い、時刻は同じ）がここで止まります。その場合はより新しいリリースの chart で upgrade します。

コマンドは `&&` でつながっているため、プログラムが失敗すれば `helm upgrade` は実行されません。upgrade が失敗しても、もう一度実行すれば同じ deployed revision から同じファイルができるため、別に保管するファイルはありません。承認一覧は上のとおり毎回空にします。使わないエンジンは `workers.json` からそのエンジンの項目を消して渡してもかまいません。デプロイ済みのイメージにあったエンジンを消すと、その upgrade はエンジンを外す upgrade と判定されます（下の「エンジンを外す upgrade」）。

<a id="3-검사-결과와-예외" />
### 3. 検査結果と例外

<a id="업그레이드-전-검사" />
#### アップグレード前検査

`helm upgrade` は migrate より先に（hook weight -5）、`upgrade-check` Job を対象リリースの api イメージで実行します。Job は未回収 checkpoint のあるセッションごとにポインターの組み合わせを読み、対象の `images.worker`・`images.workerPrevious` のどちらでも再開できないセッションを選びます。組み合わせを記録する前に commit されたポインターも選びます。まだ slot を持つ launch（claim 前を含む）が使うイメージも読みます。worker が claim してまだ slot を持つ launch のセッションも読み、この upgrade で終了する worker を選びます（下の「この upgrade で終了する worker」）。結果は Job ログの JSON 一行です。

```bash
kubectl -n werft logs job/werft-upgrade-check
```

| `verdict` | exit | upgrade | 意味 |
|---|---|---|---|
| `proceed` | 0 | 続行 | `upgrade.approvedSessions` が `affected` の `sessionId` と完全一致します。選択セッションがない場合、worker イメージが同じでデプロイ済みイメージがすべて同じ runtime のまま残る場合、またはデプロイ歴がない場合は、承認一覧が空である必要があります。`worker_ends` で選んだセッションは、worker イメージが同じでも一覧に入ります |
| `refused` | 2 | 停止 | 承認一覧が一つでも異なります（以前の承認が values に残る場合を含む）。worker イメージが同じでも、デプロイ済み直前イメージが対象から外れるか変更されるとセッションを比較します。対象イメージ（現在、および存在すれば直前）のどちらとも組み合わせが合わない、または未記録のセッションが一覧に入ります。または現在デプロイ済みの worker イメージや slot を持つ launch が封印する checkpoint を、対象イメージのどれも復元できません（組み合わせが同じ再ビルドは復元できます。runtime なしでデプロイされたイメージは、同じ digest が対象に必要です。runtime なしで予約された launch は、デプロイ済みの一覧が同じ digest に宣言した runtime で見て、宣言がないか食い違っていれば同じ digest が対象に必要です）。後者は承認で続行できません。撤回した対象イメージは復元するイメージとして数えません。撤回するイメージで launch が slot を持っているときは、組み合わせが同じ修正イメージを一緒に入れるか、その slot が空いてから upgrade します |
| `check_failed` | 1 | 停止 | DB を読めない、イメージの組み合わせが読めないか下表で必要なのにない、デプロイ済み worker イメージが不明な場合です。デプロイ済み worker があるのに `UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS` がない場合も該当します（直前イメージがなければ空値を渡します）。scheduler Deployment がないのに DB にセッションや一部 schema がある場合も同様です。デプロイ済み worker があるのに gateway アドレス `WORKER_GATEWAY_URL`・`UPGRADE_DEPLOYED_WORKER_GATEWAY_URL` のどちらかがない、または URL でない場合も該当します。迂回する設定はありません |

`images.worker.runtime` は初回設置時にはなくてもかまいません。upgrade 時に必要かは、デプロイ状態と対象値によります。

| デプロイ状態 | 対象 | runtime 不在時 |
|---|---|---|
| scheduler Deployment なし、DB が空またはセッションなし（初回設置の再試行） | 任意の worker イメージ、`images.workerPrevious` なし | `proceed` |
| worker イメージ一つ、runtime・直前イメージなし | 同じ worker イメージ、`images.workerPrevious` なし | `proceed` |
| worker イメージ一つ、runtime・直前イメージなし | 異なる worker イメージ | `check_failed`。対象に `images.worker.runtime` と現在のイメージを含む `images.workerPrevious` を設定します |
| runtime または直前イメージあり | `images.worker.runtime` を省いた値 | `check_failed`。組み合わせなしではセッションを検査できません |

runtime の取得方法は[設定レファレンスの API 設定](/run-server/self-hosting/reference/configuration)にあります。最小 values での設置は runtime なしで開始し、初めて worker イメージを変える upgrade で両イメージの runtime を入れます。

`images.worker` を維持し、デプロイ済みの `images.workerPrevious` を外すか変える upgrade はセッションを比較します。対象イメージ（現在、および存在すれば直前）のどちらとも組み合わせが合わない、または未記録のセッションがあれば `refused` となり、その一覧を承認すると通過します。未記録セッションはいずれの場合もイメージ変更 upgrade と同じように選びます。デプロイ済み直前イメージがなかった、または同じ runtime のまま同じならセッションは比較せず、承認一覧が空なら `proceed` です（残った承認は `refused`）。同じ digest でも runtime を変えて書くと、外したイメージと同じようにセッションを比較します。イメージだけ違って組み合わせが同じ再ビルドでは、直前イメージを外しても現在のイメージで再開できるため一覧に入りません。

選んだセッションが再開できなくてもよい場合、その一覧をそのまま values に入れて同じ upgrade を再実行します。承認はセッション状態を変えません。`no_image` で選んだセッションは再開時に worker を起動せず `recovery_required` で止まります。セッションの `attention` が `RESTORE_FAILED`、`incompatible_checkpoint` を示すので、承認したセッションを resume した後はセッションの `admission_state` と `attention` を確認します。`unrecorded` で選んだセッションは新イメージで起動し、復元時の判定で継続するか `recovery_required` で止まります。

```bash
helm upgrade --install ... --set-json 'upgrade.approvedSessions=["<sessionId>", ...]'
```

承認一覧は release values に残ります。次の upgrade ごとに `--set-json 'upgrade.approvedSessions=[]'` で空にし、その upgrade の一覧を読み直して承認します。残った一覧が今回の `affected` と違えば `refused` で止まりますが、同じでサポート範囲の条件も合えばそのまま通過します。

**この upgrade で終了する worker。** worker は作られたときに受け取った gateway アドレス（`WORKER_GATEWAY_URL`）しか知りません。対象リリースの scheduler が worker に渡すアドレスが、現在の scheduler が渡すアドレスと違うと、動いていた worker は upgrade の後に古いアドレスで heartbeat を拒否され、lease を手放して終了します。このとき検査は、worker が claim してまだ slot を持つ launch のセッションをすべて `worker_ends` として選びます。待機中の worker も、turn を実行中の worker も選びます。worker イメージが同じ upgrade でも選びます。アドレスが同じなら選びません。claim 前の launch は選びません。その launch は新しい scheduler が新しいアドレスで作り直します。checkpoint の判定ですでに載ったセッションは、その理由だけで載ります。これらのセッションも同じ承認一覧に入ります。slot が解放された後（セッションを閉じた後、または待機中の worker が停止した後）に再実行すると一覧から外れます。終了してもよい場合は、一覧をそのまま承認します。承認したセッションの worker は upgrade の後に終了します。待機中だった worker のセッションは次の入力で新しい worker で起動し、実行中だった turn は途切れます（[セッションの復旧](/run-server/self-hosting/recover-sessions)）。

**エンジンごとに判定します。** イメージ一覧で Claude と Codex を一緒に動かすインストールのように、デプロイ済みのイメージと対象のイメージに二つ以上のエンジンがあると、上の判定をエンジンごとに行います。対象があるエンジンのイメージを一つでも書けば（撤回したものだけでも）、そのエンジンは残ります。そのエンジンのデプロイ済みの最新イメージが封印する checkpoint を対象のイメージが復元できなければ、承認で通せない `refused` です。エンジンが一つだけのデプロイと、runtime なしでデプロイしたイメージがあるデプロイは、エンジンを分けずにこれまでどおり判定します。

**エンジンを外す upgrade。** 対象があるエンジンのイメージを一つも書かなければ、そのエンジンを外す upgrade です。このとき検査はそのエンジンの最新イメージを保護しません。代わりに、閉じていないそのエンジンのセッションを、checkpoint がなくても `no_engine_image` として選びます。runtime kind をこのホストが知らない、または kind がない開いたセッションも `no_engine_image` です。checkpoint があるセッションは checkpoint の判定が先なので、`no_image` か `unrecorded` として載ります。一つのセッションは一つの理由だけで載ります。そのエンジンの launch が slot を握っていれば（claim 前も含む）、承認で通せない `refused` です。その slot が解放されてから再実行します。承認したセッションは次のようになります。

- checkpoint がないセッションは slot を使わずに待ちます。API では attention `CATALOG_MISMATCH` として見えます。
- 記録された checkpoint があるセッションは launch 前に `recovery_required` で止まります（attention `RESTORE_FAILED`、reason `incompatible_checkpoint`）。
- runtime が記録されていない checkpoint のセッションは待ちます。
- そのエンジンの新しいセッションは、API からも Slack からも作れません（`UNSUPPORTED_CAPABILITY`）。撤回したイメージだけを残したエンジンは外したことにならないので、この拒否は起きません。

エンジンを外すこと自体は、セッションも restore point も消しません。ただし通常の保持規則（checkpoint GC、止まったセッションの workspace TTL など）はそのまま適用されます。

**検査と rollout の間の競合。** 検査は、実行した時点で slot を握っている launch だけを見ます。検査の後 rollout の前に、古い scheduler が外したエンジンの launch を予約することがあります。その worker は新しい control-host で claim するセッションを見つけられずに終了します。scheduler はこの終了を launch 失敗として数えず、その launch を作り直さずに返します（撤回したイメージの launch も同じです）。その後、セッションは上のとおり slot なしで待つか止まります。検査の後に claim してすでに動いている worker は、この設定だけでは止まりません。

**戻し方。** 外したエンジンのセッションをまた動かすには、そのエンジンの撤回していないイメージを一覧に戻す upgrade をします。そのイメージはセッションの runtime バージョンを載せている必要があります。承認一覧は空にします。すると待っていたセッションは次の pass でそのイメージで起動します。`incompatible_checkpoint` で止まったセッションは `retry_restore` で再試行します。

Job は承認一覧を `UPGRADE_APPROVED_SESSIONS`（JSON 配列）、デプロイ済み worker を `UPGRADE_DEPLOYED_WORKER_IMAGE`、デプロイ済み直前イメージを `UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS`（なければ空値）、それぞれの runtime を `UPGRADE_DEPLOYED_WORKER_IMAGE_RUNTIME`・`UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS_RUNTIME` で受け取ります。デプロイ済み scheduler がイメージ一覧（`WORKER_IMAGES`）で動いていれば、その一覧を `UPGRADE_DEPLOYED_WORKER_IMAGES` で受け取ります。chart が現在の scheduler Deployment のこれらの値を `lookup` で読み、名前の前に `UPGRADE_DEPLOYED_` を付けて渡します。現在の scheduler が worker に渡す gateway アドレスも同じ方法で `UPGRADE_DEPLOYED_WORKER_GATEWAY_URL` として渡し、対象の scheduler が渡すアドレスは `WORKER_GATEWAY_URL` として渡します。デプロイ済み runtime がなければ、そのイメージは digest だけで比較します。runtime 表の例外を開けるのは、chart が一緒に渡す `UPGRADE_DEPLOYED_STATE` だけです。`absent` は scheduler Deployment がなく、namespace の `default` ServiceAccount は読めたことを意味します（この経路にはその ServiceAccount の `get` 権限が必要）。`unpinned` は Deployment が runtime・直前イメージなしで動く状態です。`helm template` とクライアント `--dry-run` では `lookup` が何も読まずデプロイ済みの値がすべて空なので、その render で実行した Job は `check_failed` になります。`--dry-run=server` はクラスタを読みますが hook を実行しないため判定の代わりにはなりません。検査は `DATABASE_URL` が今回の DB であることを信頼します。別の空 DB を指すと `absent` 経路が通過します。初回設置（`pre-install`）と `scheduler.enabled: false` では Job を作りません。Job と scheduler に同じイメージを渡すため、`WORKER_IMAGE`・`WORKER_IMAGE_PREVIOUS`・`WORKER_IMAGE_RUNTIME`・`WORKER_IMAGE_PREVIOUS_RUNTIME` は `*.extraEnv`、`config.limits` で渡せません。渡すと render が失敗します。`images.worker` と `images.workerPrevious` で指定します。

**`helm rollback` の前に。** rollback は hook を実行しないため、同じコマンドを api Pod で直接実行します。値は戻す revision のもの（`helm get values --revision <revision>`）を指定します。

```bash
kubectl -n werft exec deploy/werft-api -- env \
  UPGRADE_DEPLOYED_WORKER_IMAGE='<WORKER_IMAGE of the running scheduler>' \
  UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS='<WORKER_IMAGE_PREVIOUS of the running scheduler, empty if none>' \
  UPGRADE_DEPLOYED_WORKER_IMAGE_RUNTIME='<WORKER_IMAGE_RUNTIME of the running scheduler, empty if none>' \
  UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS_RUNTIME='<WORKER_IMAGE_PREVIOUS_RUNTIME of the running scheduler, empty if none>' \
  UPGRADE_DEPLOYED_WORKER_GATEWAY_URL='<WORKER_GATEWAY_URL of the running scheduler>' \
  WORKER_GATEWAY_URL='<WORKER_GATEWAY_URL of the scheduler of the target revision>' \
  WORKER_IMAGE='<worker image of the target revision>' WORKER_IMAGE_RUNTIME='<its runtime JSON>' \
  WORKER_IMAGE_PREVIOUS='<workerPrevious of that revision>' WORKER_IMAGE_PREVIOUS_RUNTIME='<its runtime JSON>' \
  bun run apps/control-host/src/api/upgrade-check.ts
```

二つの gateway アドレスは、scheduler Deployment の `WORKER_GATEWAY_URL` です。戻す revision の値は `helm get manifest --revision <revision>` にあります。二つが違うと、slot を持つ worker のセッションが `worker_ends` として載ります。デプロイ済み scheduler がイメージ一覧で動いている場合は、`UPGRADE_DEPLOYED_WORKER_IMAGE` で始まる四つの値の代わりに、その scheduler の `WORKER_IMAGES` を `UPGRADE_DEPLOYED_WORKER_IMAGES` として渡します。その環境の api Pod も `WORKER_IMAGES` を持つため、単一イメージの revision に戻す検査は `env -u WORKER_IMAGES` でその値を外して実行します。外さないと `WORKER_IMAGES replaces WORKER_IMAGE` で `check_failed` です。戻す revision を runtime なしでデプロイしていた場合、`WORKER_IMAGE_RUNTIME` はそのリリースの manifest の `workerRuntime` から得ます（[イメージ一覧の環境の upgrade](#이미지-목록-설치의-upgrade) の `KNOWN` と同じです）。空にすると `check_failed` です。戻す revision も一覧なら、`WORKER_IMAGE` で始まる四つの値の代わりに、その revision の scheduler が受け取った `WORKER_IMAGES` を渡します（`helm get manifest --revision <revision>` にあります）。

通常の worker イメージを戻す rollback は `refused` です。現在のイメージが新 SDK・CLI を含む場合、戻す revision のどのイメージも現在のイメージが封印する checkpoint を復元できないためです。組み合わせが同じ再ビルドに戻す rollback はセッションを比較します。設定や DB を読めなければ `check_failed` です。現在のイメージで動く worker は rollback 後も終了までその組み合わせの checkpoint を残しますが、検査には見えません。出力の `affected` は検査時点で既に選んだセッションです。roll-forward を優先します。それでも戻すと、再開時に scheduler が組み合わせでイメージを選びます。戻した revision の worker と直前イメージ（存在する場合）のどちらとも合わないセッション（現在のイメージが新 SDK・CLI を含む場合、rollback 中に現在のイメージで checkpoint を残したセッション）は `recovery_required` で止まります。`images.worker` を維持する rollback は、現在デプロイ済み直前イメージが戻す revision にも同じまま含まれれば、承認一覧が空のとき `proceed` です（残った承認は `refused`）。外れるか変われば、このページの upgrade 検査と同じようにセッションを比較します。このコマンドは hook ではなく、rollback を止めてはくれません。`refused` なら `affected` を読み、戻すかを判断します。デプロイ済み worker があるのに `UPGRADE_DEPLOYED_WORKER_IMAGE_PREVIOUS` を省くと `check_failed` です。

**検査対象外。** 単一サーバーの[アップグレード検査](/run-server/self-hosting/upgrade-compose)と異なり、この検査は対象イメージを実行しません。ポインターに記録された組み合わせ（engine・SDK・CLI・profile digest 方式）だけを比較し、実際の profile digest は復元時に判定します。検査後に writer を停止して再検査することもありません。代わりに、現在デプロイ済みの worker イメージと、検査時点で slot を持つ launch が使うイメージが封印する checkpoint を対象イメージが復元できる場合だけ通過するため、その worker が検査後に残す checkpoint は対象のサポート範囲内です。最初の checkpoint 前のセッションも、launch が slot を持っていればここに含まれます。検査後にデプロイ済み scheduler が直前イメージで新しく起動する launch は見えません。そのため直前イメージを外すか変える前は、そのイメージで動く launch がないときに実行します。デプロイ済みイメージでも復元できない古いイメージの worker は、この upgrade のせいで閉じ込められるわけではないため止めません。そのセッションは、ポインターが既にその組み合わせなら一覧に入り、最初の checkpoint 前なら入りません。対象イメージを registry から取得できるかも検査しません。取得できなければ launch 失敗として現れます。`images.worker.runtime` がそのイメージ自身の出力する値かどうかも検査しません。誤っていても upgrade は通過します。engine・SDK・CLI・profile digest 方式のいずれかが worker の claim に書く値と異なると、そのイメージの worker が最初に起動したときに scheduler がイメージを拒否します（[よくある問題](/run-server/self-hosting/upgrade-kubernetes#자주-막히는-곳)）。`restorableSchemes` がそのイメージの実際の復元能力と一致するかは、このときも比較しません。worker が終了する場合のうち、検査が読むのは gateway アドレスが変わる場合だけです。新しい scheduler が、隔離契約（`werft.isolation` label）の変わった worker を実行中の turn の後に停止して作り直す場合と、対象が撤回したイメージで動く worker を turn の後に停止する場合は、`worker_ends` として載りません。

<a id="4-파일-카탈로그-설치에서-오는-경우" />
### 4. ファイル catalog の環境から移行する場合

現在の chart は以前の `catalog` ConfigMap を取り込まず、migrate Job は seed を実行しません。ファイル catalog のままの環境は、まずこのリリースより前の release に上げて設定を DB に移してから上げます([設定文書のインポートとエクスポート](/run-server/self-hosting/reference/configuration#설정-문서-가져오기내보내기))。`api.extraEnv` に残った `PLATFORM_CONFIG_DIR` は読まないため、起動を止めません。整理する場合は削除します。

## 確認

```bash
kubectl -n werft get job werft-migrate
for d in api egress-proxy reconciler scheduler; do
  kubectl -n werft rollout status deploy/werft-$d --timeout=600s
done
```

```bash
kubectl -n werft port-forward svc/werft-api 13000:3000 &
PF=$!
trap 'kill "$PF" 2>/dev/null || true' EXIT INT TERM
READY=0
for attempt in $(seq 1 30); do
  if curl --max-time 2 -fsS -o /dev/null http://127.0.0.1:13000/readyz; then READY=1; break; fi
  sleep 1
done
if [ "$READY" != 1 ]; then
  kill "$PF" 2>/dev/null || true
  trap - EXIT INT TERM
  false
else
  curl --max-time 10 -fsS -w '\n%{http_code}\n' http://127.0.0.1:13000/readyz
  curl --max-time 10 -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:13000/docs
  kill "$PF" 2>/dev/null || true
  trap - EXIT INT TERM
fi
```

Job ログの実際の verdict、rollout、ready 応答を記録します。既存セッションの再開と checkpoint context は別途確認します。メトリクス名が変わる場合は[コレクターとルール](/run-server/self-hosting/collect-metrics#4-기존-규칙-갱신)を更新します。

<a id="자주-막히는-곳" />
## よくある問題

workerPrevious が現在デプロイ済みのイメージでなければ、承認で続行できない refused です。helm get values の revision を省くと、失敗した upgrade の候補値が返る場合があります。lookup のない helm template や client dry-run は実際の upgrade 検査を代替しません。

upgrade 後に新しいセッションが `queued` のままで、scheduler ログに `Worker image refused: a worker on it claimed under another runtime than configured` が出る場合、`images.worker.runtime` がその worker イメージの値ではありません。runtime を再び外す upgrade は `check_failed`（`WORKER_IMAGE_RUNTIME is not set`）で止まります。そのイメージが出力する runtime（[設定リファレンスの API 設定](/run-server/self-hosting/reference/configuration)）を `images.worker.runtime` にそのまま入れ、再度 upgrade します。単一イメージ手順の `worker.json` は、この値を対象リリースの `files/release-images.json` から取ります。待っていたセッションはその後に launch されます。

`refused` や `check_failed` で止まった upgrade も Helm revision を一つ使います。Helm は既定で revision を 10 個だけ残すため、何度も止まると戻したい revision が history から消えます。history から消えた revision には `helm rollback` できず、値を別に保存していても同じです。何度も試す見込みなら `helm upgrade` に大きめの `--history-max` を渡します（`0` は無制限）。

<a id="되돌리기" />
## 元に戻す

```bash
helm -n werft history werft
helm -n werft rollback werft <revision> --wait --timeout 10m
```

rollback は migrate hook を実行しません（`pre-rollback` ではありません）。DB は新 schema に残り、以前のビルドは自分より先の schema でも ready になります（`/readyz` の schema 検査は、自分の migration 一覧が適用済み一覧の先頭部分と一致するかだけを見ます）。[変更履歴](https://github.com/JeongJaeSoon/werft/blob/main/CHANGELOG.md)が戻せないと書いたリリースより前には rollback しません（[実行前ゲート](/run-server/self-hosting/upgrade-compose#실행-전-게이트)）。

リンクした共通の実行前ゲートと直接検査で rollback 可能と確認してからだけ戻します。hook がないため、rollback コマンドが自動検査で止めてはくれません。roll-forward を優先します。

<a id="옛-worker-이미지-지우기" />
## 古い worker イメージを削除する

セッションはイメージではなくランタイムの組み合わせで再開します。そのため registry の古い worker イメージは、以下を順に確認してから削除できます。削除は registry で行い、werft はイメージを削除しません。再ビルドで直せない脆弱性のように、そのイメージでもう起動してはならないときは、削除する前に一覧で[撤回](/run-server/self-hosting/reference/configuration)します。

1. 一覧から外します。一覧の環境（`images.workers`、`WORKER_IMAGES`）では、[イメージ一覧の環境の upgrade](#이미지-목록-설치의-upgrade) のプログラムがエンジンごとに撤回されていないイメージを二つまで残すため、そのエンジンのより新しいリリース二つへ upgrade すれば、そのイメージは自然に外れます。撤回したイメージは、残した撤回されていないイメージのうち最も古いものより古ければ外れ、撤回されていないイメージがないエンジンでは外れません。それより早く外すには、生成した `workers.json` からその要素を削除して渡します。プログラムは配備済みの一覧に対象 chart の `release-images.json` を加えるため、外したイメージは、対象 chart がその digest を含まない限り次の upgrade で戻りません。含む場合は、その upgrade の `workers.json` からも削除します。単一の値の環境では `images.worker` と `images.workerPrevious` のどちらにも置かず、上の手順どおり upgrade します。外したイメージを必要とするセッションがあれば、その upgrade は[アップグレード前検査](#3-검사-결과와-예외)が判定します。それ以降、新しい launch はそのイメージを選びません。同じ組み合わせのイメージが一覧に残らないセッションがどうなるかは、[設定リファレンス](/run-server/self-hosting/reference/configuration)のイメージ一覧を見ます。
2. `werft_sessions_by_worker_image{image="<repository>@sha256:<digest>"}` の series がなくなるまで待ちます。この指標は終わっていないセッションを、最後の launch のイメージ別に数えます（[指標リファレンス](/run-server/self-hosting/reference/metrics)、[指標の収集](/run-server/self-hosting/collect-metrics)）。series があれば、そのイメージで最後に launch したセッションがまだ開いています。休んでいる開いたセッションも series に残るため、そうしたセッションが終わるか、別のイメージで launch し直すまで待ちます。この指標は `stopped` のセッションを数えないため、series がなくても手順 3 を飛ばしません。
3. そのイメージでスロットを持つ launch がないことを DB で確認します。運用者の DB クライアントで下の問い合わせを実行し、行が一つもない必要があります。この行には、scheduler が管理するそのイメージの worker と、worker が付く前に作り直されるときに保存されたイメージ（つまり削除しようとしているイメージ）で作り直される launch の両方が含まれます。スロットは、scheduler がリソースの消えたことを確認してから解放されます。記録から外れ、scheduler が別に片付ける orphan Pod はここに出ません。orphan は作り直されず、ノードがすでに取得したイメージで動くため、registry から削除してもその Pod には影響しません。

```sql
SELECT session_id, generation, claimed_attempt_id IS NOT NULL AS claimed
FROM worker_launches
WHERE image = '<repository>@sha256:<digest>'
  AND slot_released_at IS NULL;
```

三つがすべて満たされたら registry から削除します。削除したあと、そのイメージを一覧に含む Helm revision へ rollback すると、その revision の scheduler がそのイメージで launch するとき、イメージがキャッシュされていないノードでは pull に失敗します（worker Pod は `IfNotPresent` で取得します）。戻せるように残しておく revision が含むイメージは削除しません。
