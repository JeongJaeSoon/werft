A session is a conversation that runs one agent release. It runs on the connection, model, runtime and tools the release pinned, and starts with a repository or without one. When you create a session, the first message is accepted as turn 1, and the scheduler starts a worker container for that session. The scope is `sessions:write`. The SDK examples use the `werft` client made in [Install the SDK](/getting-started/install#create-a-client), and the HTTP API examples use the shell variables `API` (the server address) and `KEY` (the key), and a release id made beforehand in the `WERFT_AGENT_RELEASE_ID` environment variable ([Create](/agents/create)).

In the web console, press "New session with this agent" on the agent's page and send the first message. The session starts on the active release (an agent with GitHub settings starts without a repository, and an older agent with no settings starts on its release's repository), through the same `POST /v1/sessions` with the signed-in person's authority. When the page can tell ahead of time (no active release, paused, no permission and so on), the button is off and the page says why. A refusal known only after sending, such as a missing credential binding, shows its reason in the dialog.

<Callout>
The `GATE-SPEC {…}` messages in the examples are scripts for the fake model of the [development server](/run-server/dev-server). The fake model calls tools and answers exactly as the script says, so the output is always the same. A server started with a real model will not make the same tool calls or print the same output; send it ordinary instructions instead.
</Callout>

## Create

<Tabs groupId="client" persist items={["SDK", "HTTP API"]}>
<Tab>

```ts
const created = await werft.sessions.create({
  agent_release_id: process.env.WERFT_AGENT_RELEASE_ID ?? "",
  repository_id: "sample-app",
  message: 'GATE-SPEC {"id":"start","steps":[],"final":"started"}',
});
console.log(created);
const sessionId = created.session_id;
```

```text
{
  session_id: '…',
  turn_id: '1',
  receipt_id: '…',
  receipt_status: 'accepted',
  status: 'queued'
}
```

</Tab>
<Tab>

```bash
created=$(curl -sS "$API/v1/sessions" \
  -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(uuidgen)" \
  -d "$(jq -nc --arg m 'GATE-SPEC {"id":"start","steps":[],"final":"started"}' \
    '{agent_release_id: env.WERFT_AGENT_RELEASE_ID, repository_id: "sample-app", message: $m}')")
echo "$created" | jq .
SID=$(echo "$created" | jq -r .session_id)
```

```text
{
  "session_id": "…",
  "turn_id": "1",
  "receipt_id": "…",
  "receipt_status": "accepted",
  "status": "queued"
}
```

Reference: [`POST /v1/sessions`](/reference/http-api/sessions/createSession)

</Tab>
</Tabs>

| Field | Required | Description |
| --- | --- | --- |
| `repository_id` | | A repository id from the catalog. When sent, the worker clones it. It must be within the workspace ceiling and the agent's GitHub settings. Omitted, an agent with GitHub settings starts without a repository and attaches only the ones it needs, and an older agent with no settings starts on its release's repository ([Sessions without a repository](/sessions/without-repository)) |
| `message` | Yes | The input of the first turn. Up to 32,768 UTF-8 bytes |
| `model` | | One of the models the release's connection offers. If omitted, the release card's model |
| `title` | | The session's name. If omitted, derived from the first `message` ([Title](#title)) |
| `agent_release_id` | Yes | The agent release the session runs ([Bind to a session](/agents/create#bind-to-a-session)). If its connection was disabled or the model left the connection's list, 409 `RELEASE_SPEC_UNAVAILABLE` |

The response is 201. The request is only accepted; read the result by fetching the turn ([Status and lifecycle](/sessions/lifecycle)).

## Idempotency-Key

Every POST in the session API requires an `Idempotency-Key` header. If you did not receive a response, send it again with **the same key and the same body**. The server runs the command only once. Session creation and messages return the original response as is, and controls such as interrupt return the current state of that receipt. The same key with a different body is 409 `IDEMPOTENCY_CONFLICT`.

The SDK makes one key per call and sends that same key on every retry of the call. To carry on with the same command after restarting the process, make the key yourself and pass it as `idempotencyKey`.

<Tabs groupId="client" persist items={["SDK", "HTTP API"]}>
<Tab>

```ts
const params = {
  agent_release_id: process.env.WERFT_AGENT_RELEASE_ID ?? "",
  repository_id: "sample-app",
  message: 'GATE-SPEC {"id":"retry","steps":[],"final":"once"}',
};
const idempotencyKey = crypto.randomUUID();
const first = await werft.sessions.create(params, { idempotencyKey });
const second = await werft.sessions.create(params, { idempotencyKey });
console.log(first.session_id === second.session_id ? "same session" : "two sessions");
```

```text
same session
```

</Tab>
<Tab>

```bash
IDEM=$(uuidgen)
BODY=$(jq -nc --arg m 'GATE-SPEC {"id":"retry","steps":[],"final":"once"}' \
  '{agent_release_id: env.WERFT_AGENT_RELEASE_ID, repository_id: "sample-app", message: $m}')
first=$(curl -sS "$API/v1/sessions" -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $IDEM" -d "$BODY")
second=$(curl -sS "$API/v1/sessions" -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $IDEM" -d "$BODY")
[ "$(echo "$first" | jq -r .session_id)" = "$(echo "$second" | jq -r .session_id)" ] && echo "same session"
```

```text
same session
```

Without the header the response is 400. Reference: [`POST /v1/sessions`](/reference/http-api/sessions/createSession)

</Tab>
</Tabs>

Use a new key for a new intent. If you send with a new key after a timeout, you may end up with two sessions.

## List

<Tabs groupId="client" persist items={["SDK", "HTTP API"]}>
<Tab>

```ts
const page = await werft.sessions.list({ limit: 5 });
for (const session of page.items) {
  console.log(session.id, session.title, session.status);
}

// for await walks every page.
for await (const session of werft.sessions.list({ status: "idle" })) {
  console.log(session.id);
}
```

`await` gives the first page (`items`, `next_cursor`, `nextPage()`); `for await` gives the items of every page.

</Tab>
<Tab>

```bash
curl -sS "$API/v1/sessions?limit=5" -H "Authorization: Bearer $KEY" | jq -c '.items[] | {id, title, status}'
```

Read the next page by passing the response's `next_cursor` as `cursor`.

Reference: [`GET /v1/sessions`](/reference/http-api/sessions/listSessions)

</Tab>
</Tabs>

Filter with `limit` and `status`. Only the sessions the key can see are returned.

`relation` narrows those further and never widens them. `started` is the sessions you started (for a key, the ones the key or its creator started), `shared` the ones someone else started and shared with you by name or through a team you belong to, and `administered` the sessions of agents you administer, directly or through a team. Someone else's session that the whole workspace sees appears only under `all`, the default. `q` finds sessions whose title contains it, ignoring case, or whose id starts with it. `agent_id` keeps the sessions created with one of that agent's releases, whichever release.

Each item's `agent` (`id`, `name`, `release_version_no`, `release_label`) is the agent and release the session is pinned to. `release_version_no` is the card version that release runs, and `release_label` is the release's name (when it was created, such as `2026-10-30_14:30:28`). It is `null` for a session created without an agent release. `created_by` (`user_id`, `display_name`) is who started the session; for a key's session, the person who created the key. It stays the same after a takeover: the person who took the session over can read it, but it appears under `started` only for the person who started it. `channel` is where the creating request came from (`web`, `api` or `slack`). An older session whose starter or channel the record cannot tell reads `null`. `slack_permalink` is the link to the first message of a session started from Slack ([Original Slack message link](/integrations/slack#original-slack-message-link)). It is `null` for a session created another way or before links were kept.

The SDK has no per-status counts, so read them with the HTTP API. `GET /v1/sessions/counts` returns how many sessions the list would hold per status, read to its last page with the same `relation` and `q`, and their `total`. A session you cannot see is never counted.

```bash
curl -sS "$API/v1/sessions/counts?relation=started" -H "Authorization: Bearer $KEY" | jq -c
```

Reference: [`GET /v1/sessions/counts`](/reference/http-api/sessions/countSessions)

`repository` in the list and the detail is the repository the session was created against. `id` is the catalog key (the same as `repository_id`); `full_name` is a name to show, the repository URL's path without host, credentials, query or `.git` (`owner/name`, or `group/sub/name` on a forge with groups), or the catalog key when the URL does not read that way. `branch` is the branch the worker cloned, not `agent/<session-id>` that a push writes to. All three are recorded when the session is created, so they stay the same when an operator later changes the catalog or removes the repository. A session created without a repository has `repository: null`; a session created before the catalog existed has `id: null`. The repository URL itself is never in a response.

<Tab>

```ts
const session = await werft.sessions.get(sessionId);
console.log(session.repository);
```

```text
{ id: 'sample-app', full_name: 'agent/sample-app', branch: 'main' }
```

</Tab>
<Tab>

```bash
curl -sS "$API/v1/sessions/$SID" -H "Authorization: Bearer $KEY" | jq -c .repository
# {"id":"sample-app","full_name":"agent/sample-app","branch":"main"}
```

## Preview

An agent's admin runs a release alone before publishing it. Add `"preview": true` to the create request for a preview session; it starts even on a release never turned on ([Try it before you publish](/agents/create#try-it-before-you-publish)).

- Only a person signed in to the web console sends it. From an API key or Slack it is 400 `BAD_REQUEST` (`reason_code: preview_web_only`).
- You must manage the release's agent. Someone who cannot see the agent gets the 404 of a release that is not there; someone who sees it but is not its admin gets 403 `FORBIDDEN` (`reason_code: role`).
- The session is seen by its creator alone and its share cannot be widened (409 `REVISION_CONFLICT`, `reason_code: preview_session`). Every request that adds a message, resumes it or answers its pending requests checks again that the sender still manages the agent, else 403 (`reason_code: role`).
- It is a real run, with the same tools and permissions, and its usage and cost are counted. It counts toward no achievement.
- `preview` is `true` in the session list and detail.

## Share scope

Read the share scope to see who can see a session. Anyone who can see the session can read it. The scope is `sessions:read`.

<Tabs groupId="client" persist items={["SDK", "HTTP API"]}>
<Tab>

```ts
const share = await werft.sessions.share(sessionId);
console.log(share.scope, share.revision);
```

```text
workspace 0
```

</Tab>
<Tab>

```bash
curl -sS "$API/v1/sessions/$SID/share" -H "Authorization: Bearer $KEY" | jq -c '{scope, revision}'
# {"scope":"workspace","revision":0}
```

Reference: [`GET /v1/sessions/{id}/share`](/reference/http-api/sessions/getSessionShare)

</Tab>
</Tabs>

`scope` is one of `private` (only the creator), `people` (the people in `user_ids`), `team` (the current members of the teams in `team_ids`), or `workspace` (every member). A session that was never changed is `workspace` with `revision` 0. A session of an agent is seen only by those inside the agent even at `workspace` (agents in a holding team are the exception), and then `audience_limited` is `true` ([Members outside the responsible team](/agents/permissions#members-outside-the-responsible-team)). The console's session screen shows the scope read-only at the end of the line under the title, and with `audience_limited` it reads `Workspace (people outside the responsible team cannot see it)`. `POST /v1/sessions/{id}/share`, which changes the scope, is called only with a web login, so the SDK has no method for it ([`setSessionShare`](/reference/http-api/sessions/setSessionShare)).

A session started in a private Slack channel is `private_channel`: only people who may use its agent and are members of that channel now see it. Its creator loses it on leaving the channel, and a workspace owner or admin outside the channel does not see it either (a justified [audit read](/reference/http-api/admin/auditReadSession) still does). When Slack cannot confirm membership, the session is hidden. An API key, personal or agent, never sees one, even when its owner is a member: it is left out of lists, and every read (detail, turns, events, outputs, pending requests) and every write or approval (messages, answers to pending requests, push requests and their approval or rejection, and every other route under `/v1/sessions/{id}`) answers `404`. A push the agent asks for inside the session is unchanged. When the person who asked for a push (or, with no person behind it, whoever holds the session: its starter, or whoever took it over) leaves the channel, its card reads `The requester left the channel` and any current channel member holding `session.approve` may approve or reject it; the decision record names who decided. The requester who left cannot decide, and on rejoining the usual rule returns. When membership cannot be confirmed, the usual rule applies. Tool permission and question cards work the same way: when the person of the turn that asked (or, with no person there, whoever holds the session) leaves the channel, the card reads `The requester left the channel` and a current channel member holding `session.approve` may answer it; the request's answer record names who answered. The console offers that member its answer buttons too. When a member who took it over presses `Allow for session`, the allow is bound to that member: once they leave the channel, or the requester rejoins and the usual rule returns, the same tool shows the card again. The turn's requester and the account its cost is charged to do not change. Such a session's reports and cards go only to its channel's thread; when they cannot (the bot removed from the channel, say), they go nowhere else. A direct message about the session (its model cut or moved, say) goes only to a current member of the channel, and not at all when membership cannot be confirmed. When its requester is disabled, the session waiting for a takeover is taken over by a current member of the channel who may write to it. The channel sets this scope, so `POST /v1/sessions/{id}/share` answers 409 `REVISION_CONFLICT` (`reason_code: private_channel_session`). The console reads `Current members of the private channel`. Sessions from public channels, DMs, the web and the API are unchanged. Sessions made in a private channel before this scope existed stay visible to the workspace until the operator runs the [move command](/run-server/self-hosting/upgrade-compose#the-release-that-moves-old-private-channel-sessions). When a channel is made private its sessions become `private_channel` too, and when a private channel is made public its sessions become visible to the workspace. A session its creator narrowed to `private` is not widened either way.

A session from a private channel passes the channel's door first even when its scope is not `private_channel` (a `private` session only its creator sees, or one made before that scope existed): it takes a current member of the channel, and then its scope's own rule. So a `private` one is seen by its creator only while they are a member of the channel now, and not after they leave. An API key never sees one, as above: left out of lists, every route `404`. Such a session's share can be changed, but widening it shows it to no one outside the channel. Sessions from public channels, DMs, the web and the API are unchanged.

## Title

A `title` you send is stored with runs of whitespace and line breaks collapsed to one space and the ends trimmed. If that leaves nothing or more than 80 characters (an emoji or a combined character counts as one), the answer is 400. Without one, the title is derived from the first `message` by the same rule, cut to 79 characters and `…` past 80. No model is called, so the same message always gives the same title. A message of only whitespace, and a session created before titles existed, read `title: null`.

The SDK has no rename, so call the HTTP API.

```bash
curl -sS -X PATCH "$API/v1/sessions/$SID" -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' -d '{"title":"결제 테스트 고치기"}' | jq '{id, title}'
```

The session's creator (for a key's session, that key), its agent's admins, and owners and admins rename it. Someone who only sees it through its share gets 403; someone who cannot see it, 404. No Idempotency-Key is needed. A change arrives on the SSE stream as a `status` event carrying `title`. Reference: [`PATCH /v1/sessions/{id}`](/reference/http-api/sessions/updateSession)

## Errors

Server errors arrive in the SDK as `APIError`. Tell them apart with `isApiError(error, code)`; an error whose `retryable` is `true` is resent by the SDK on its own ([Retries and Idempotency-Key](/getting-started/client#retries-and-idempotency-key)).

<Tabs groupId="client" persist items={["SDK", "HTTP API"]}>
<Tab>

```ts
import { isApiError } from "@werft-ai/sdk";

try {
  await werft.sessions.create({
    agent_release_id: process.env.WERFT_AGENT_RELEASE_ID ?? "",
    repository_id: "sample-app",
    model: "claude-opus-9",
    message: "hello",
  });
} catch (error) {
  if (isApiError(error, "UNSUPPORTED_CAPABILITY")) {
    console.log(error.status, error.code, error.retryable, error.message);
  } else throw error;
}
```

```text
422 UNSUPPORTED_CAPABILITY false Model claude-opus-9 is not on the model list of connection fake-messages; name a model the connection offers
```

</Tab>
<Tab>

The error body has the same shape in every API. Resend with the same key only when `retryable` is `true`.

```text
{"error":{"code":"UNSUPPORTED_CAPABILITY","message":"Model claude-opus-9 is not on the model list of connection fake-messages; name a model the connection offers","retryable":false,"request_id":"…","details":null}}
```

Reference: [`POST /v1/sessions`](/reference/http-api/sessions/createSession)

</Tab>
</Tabs>

| Response | Meaning |
| --- | --- |
| 400 | The body does not match the schema, or `Idempotency-Key` is missing |
| 401 | The key is missing, wrong, or revoked |
| 403 | The key lacks `sessions:write` |
| 404 | The release does not exist. A caller outside the agent (for a personal key, its creator) gets the same answer |
| 409 `IDEMPOTENCY_CONFLICT` | The same key with a different body |
| 413 | The message exceeds 32,768 bytes. `STORAGE_LIMIT_EXCEEDED` if the storage limit is exceeded |
| 403 `GITHUB_REFUSED` | The `repository_id` you named is outside the agent's GitHub settings list or the workspace ceiling (`details.reason_code` is `repository_not_allowed`) |
| 422 `UNSUPPORTED_CAPABILITY` | The repository is not in the catalog, the release's connection does not offer the model, or the current worker images do not ship the release's runtime |
| 429 `RATE_LIMITED` | Send again after a short wait |

When execution slots run short, the request is not rejected. The session waits as `queued`.

The SDK's error classes (`APIError`, `ConnectionError`, `TimeoutError`, and others), retry counts, and timeouts are the same for every call, so they are collected in [Client options and errors](/getting-started/client#errors).
