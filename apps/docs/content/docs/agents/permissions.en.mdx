title: "Permissions"
description: The tools an agent can use, human approval, and the people who administer an agent and its credential bindings

An agent's permissions have three layers: the tools and permission mode a release pins, the permission requests that a person answers, and the people who administer the agent and connect credential names.

## Tools: set by the release

A release pins every built-in tool of its connection's runtime (the release response's `effective_tools.tools`). There is no setting that blocks a chosen built-in tool. Whether a tool asks a person before it runs is set by the permission mode below and by the workspace rules built into the platform (the pre-allowed list and the ask list).

A card's `capabilities.forbidden` applies to MCP tools. If an MCP tool the release allows is on that list, the release cannot be created. In a card's `tool_policy`, the default for MCP tools is `ask`.

## Permission mode

The permission mode decides whether a person is asked before a tool runs. There are two modes, `default` and `auto`, and each time a session runs the mode is decided from its connection and model. It appears in `runtime.permission_mode` of the session detail.

| Mode | Behavior |
| --- | --- |
| `default` | Work inside the session workspace runs without asking a person. File writes and edits, every `git` and `gh` command, `sed`, `mkdir`, `touch`, `cp`, `mv` and `rm`, `bun`, `npm`, `pnpm` and `yarn` test, run and install (`npm ci` included), `pytest`, `go test`, `build` and `vet`, `cargo test`, `build` and `check`, `make`, and reads that change nothing (`ls`, `cat`, `grep`, `find` and the like) pass by the engine's allow rules. The engine asks about any other command (`tee`, `curl`, `python` and the like) and about a line it does not read to the end (a file redirect and a heredoc after `&&`, as in `mkdir -p d && cat > d/f <<'EOF'`, a substitution, a pipe), but the platform answers that ask itself by the workspace policy, so it does not become a permission request. The same holds for a file write inside the workspace that the engine asks about (a dot name such as `.vscode/`). Three things create a permission request before running. First, a command on the policy's ask list: `sed -i` and sed's `w`, `git --output` and `--ext-diff` (which write a file or run a program), `git -C` at another repository, `git add -f`, `git worktree`, `gh auth`, a secret file name (`.env`, a key, `.git/config`) on a `cat`, `head`, `tail`, `grep`, `rg`, `cp` or `mv` line, `rg -u` or `--hidden`, which search hidden files, a runner option that points outside the workspace (`--prefix`, `-C`), and the like. Second, a write to a secret, `.git` or `.claude` path. Third, a path outside the workspace (judged on the path after symlinks and `..` are resolved). These three are caught only when they show in the text of the line: a path a variable or a substitution makes, a glob such as `cat .e*`, and a file a script opens get past them. What stops harm is not a permission request but the workspace container isolation, the egress authorizer (push target, token scope) and GitHub branch protection. A Codex connection answers by the same policy. The mode a release runs when its model is not a Claude model |
| `auto` | A model classifier allows or denies each call in place of a person, and denies it when the classifier cannot be reached. Needs no installation setting. It gets the same workspace pre-approvals and ask list as `default`, so the same routine commands (`git` and `gh`, `sed`, writes and `mkdir`, `touch`, `cp`, `mv` and `rm` inside the workspace, reads) run without the classifier, and a call the ask list catches goes to a person, not to the classifier. For a line the engine does not read to the end, the platform answers itself only when the line splits with certainty and every part is a command on the allow list; otherwise it goes to a person (narrower than `default`: the platform does not make a judgment that is the classifier's). The engine drops the allowances for interpreters and script runners (`bun run`, `npm run`, `npx`, `bunx` and the like) when it enters this mode, so the classifier judges those calls. One exception: the built-in GitHub tools for pushing, writing pull requests and reading repositories skip the classifier, and the server decides them (push approval, the release's tool list, the session grant). Reviews and workflows still go through the classifier. The platform adds rules by kind of action. The push, pull request and repository-read items in the allowance below are what the classifier sees only on an older worker that does not get this exception. Allowed: committing in the session's workspace and pushing through the platform's push flow to the session's own work branch (`agent/<session-id>`) in the session's own repository, opening a pull request from that branch and editing the title and body of, commenting on, closing or reopening a pull request the session opened, and listing granted repositories and attaching one to read it. Outside that allowance: pushing to the default branch, a protected branch or a branch the platform did not create, force pushes, merging or approving pull requests, submitting a review, editing, commenting on or closing a pull request the session did not open, pushing to any other repository, including one attached to the session, and secrets. Changing repository settings, branch protection, webhooks, deploy keys or Actions secrets, deleting branches or repositories on GitHub, and merging pull requests lean toward denial by any route |

A session request cannot change the mode. A Claude model runs `auto` and any other model runs `default`. A Claude model is a model on an `anthropic` connection, or, on a `litellm` connection, a model id that starts with `claude-` or `anthropic/claude-` or is exactly `sonnet`, `opus`, `haiku` or `fable` (optionally followed by `[1m]`). An id that merely contains a family name (such as `my-sonnet-proxy`) runs `default`. A Codex connection (`openai_responses`) always runs `default`. No setting chooses the mode, on a connection, an agent or the installation. The mode written on a release is not read, so sessions of a Claude-model release made with `default` before this rule also run `auto`, with no need to make the release again. When a session's model changes (for example, a model dropped from the list moves to the next one), the same rule decides the mode. Auto mode works only on models that support it (see the [auto mode requirements in Claude Code](https://code.claude.com/docs/en/permission-modes#eliminate-prompts-with-auto-mode)). On a current worker, the push and pull request tools do not ask through the engine. A session already running switches to this rule's mode the next time a worker takes it. Push approval is separate from the mode: with push approval on, or the attached-repository push policy on `ask`, even an `auto` agent asks a person before every push to any repository. A value nobody chose reads as no approval. An agent with no saved GitHub settings (a new agent included) and a release with no GitHub settings (such as one made before this setting existed) read push approval as off, and saved settings with no attached-repository push policy (saved before that policy existed) read it as `allow`. So when turning on a repository switch is a new agent's first save in its GitHub tab (a switch saves as soon as it is flipped and also saves these defaults), sessions that start after it push without approval until a person turns approval on. If push approval was turned on and saved first, that value stays. Before that first save its sessions have no GitHub tools. What a person turned on (**Approve before push** on, a policy of `ask` or `deny`) and push approval pinned on a release still apply. Even then a push goes without approval only if the attached-repository push policy (`allow`, `ask` or `deny`) is also `allow`. A `deny` policy blocks the push outright; otherwise a push to any repository follows the stricter of this switch and that policy. To have a person approve pushes, turn the switch on or set the policy to `ask`.

## Approval: only a person does it

Answering permission requests and questions needs the `sessions:approve` scope. The credential held by the agent inside the worker gets 401 on `/v1`, so it cannot approve for itself. An agent key can have `sessions:approve`, but it never approves requests of a session it started. How to answer is described in [Waiting for approval and resuming](/sessions/waiting-and-resume).

Seeing a session does not mean answering for it. Only these people answer its permission requests and questions and approve its pushes and pull requests:

- the person who created the session (for a session an API key created, that key)
- the admins of the session's agent
- the workspace's owners and admins

Someone who only sees the session through its share gets `403 FORBIDDEN` (`reason_code: role`) when they answer; the request stays open and the session stays `needs_input`. A session they cannot see is still `404`. `answerable` in `GET /v1/sessions/{id}/pending-requests` says whether the caller may answer, and when it is `false` the console shows allow and deny disabled, with the reason.

## Agent administrators

The person who creates an agent becomes that agent's administrator. An administrator, even if only a member, can edit the agent's card, create releases, activate, connect credentials, assign administrators, and issue agent keys. You can add a person or a team as an administrator, and for a team, every member of that team is an administrator. Only an owner or admin, who manage teams, can newly add a team. An agent administrator who is a member cannot add a team, but can still remove one and add or remove people.

Every agent has one responsible team, which you can change but not clear. The responsible team's leads (`lead`) administer the agent; its members (`member`) do not. Unless you are an owner or admin, you can choose only a team you belong to. A team that is responsible for an agent cannot be deleted until that agent is archived or moved to another team.

Team roles show on the console's team screen. The member table's **Team role** column tells a **Team lead** (`lead`) from a **Member** (`member`), and **Your teams** shows your own role. Owners and admins pick a role with **Change role** on a member's row and **Save** it (`PATCH /v1/teams/{team_id}/members/{user_id}` `{"role"}`). Deleting a team that is responsible for agents leaves the team in place, and the console names those agents with links (`409 TEAM_MANAGES_AGENTS`). Give each of them another responsible team first.

Who sees what of an agent:

| Who | Information (name, slug, description, responsible team, status, active release) | Reading settings (card, releases, administrators, credential connections, GitHub, Slack) | Changing settings |
| --- | --- | --- | --- |
| Owners and admins | Read | Read | Change |
| Agent administrators (the responsible team's `lead` included) | Read | Read | Change |
| The responsible team's `member` | Read | Read | No (`403`) |
| Any other member | No (missing from lists; reading it is `404`) | No (`404`) | No (`403`) |

<Callout>
The responsible team's `member` finds the agents their team is responsible for with `GET /v1/agents` and `GET /v1/agents/counts`, and reads their settings. The `include=summary` summary (administrators, credential connections) comes only on the agents whose settings the caller reads. A receipt that changed an agent's settings is likewise read only by those who read the settings.
</Callout>

### Members outside the responsible team

Owners, admins, the agent's administrators and its responsible team's members are inside the agent; every other member is outside it. Only those inside use the agent. No setting changes this.

- To a member outside, the agent does not exist, on the web or in Slack. It is missing from lists and counts, reading it is `404`, and starting a session is the same `404` as a release that does not exist. A session shared with them still shows, with its agent hidden.
- When a member outside mentions the agent or sends it a DM in Slack, no session starts; they get a short notice that they lack the right. A Slack user who has not linked a Werft account gets a notice to link one.
- Only those inside see the agent's `workspace`-shared sessions. They are left out of lists, counts, details, events and the usage recent list for members outside. Agents that had no team before a responsible team became required went to a memberless holding team (the server recognizes it even if it is renamed), and their `workspace` sessions stay visible to every member, as before, until the agent moves to the right team. Those sessions' lists and details show the agent's name to every member as plain text, and the session list can be filtered by that agent. The agent's own page stays closed to members outside (`404`).
- A member outside still sees the sessions they started and the ones shared with them or their team (`people`, `team`).
- Changing the responsible team, or leaving it, applies from the next request, to sessions already made too. An open event stream ends at its next check.
- Usage totals (session count, cost, achievement count) stay the same; only the rows of sessions the caller cannot see drop out of the recent achievements list.
- A session shared with `workspace` that members outside cannot see reads `audience_limited: true` in `GET /v1/sessions/{id}/share`.

<Callout>
No workspace setting chooses how far members outside can see and use an agent. The behaviour is always that of `none` and `managing_team`, so agents are hidden from members outside.
</Callout>

This continues with `AID` and `WEB` from [Create](/agents/create).

```bash
curl -sS "$API/v1/agents/$AID/admins" "${WEB[@]}" | jq '{users: [.users[].email], teams}'
```

```text
{
  "users": [
    "owner@example.test"
  ],
  "teams": []
}
```

| Request | What it does |
| --- | --- |
| `POST /v1/agents/{id}/admins` `{"user_id"}` or `{"team_id"}` | Assign an administrator |
| `DELETE /v1/agents/{id}/admins/users/{user_id}`, `…/teams/{team_id}` | Remove |
| `PUT /v1/agents/{id}/managing-team` `{"team_id"}` | Set or change the responsible team |
| `GET /v1/administered-agents` | Agents I administer |
| `DELETE /v1/agents/{id}` | Delete the agent (console: **Settings** → **Danger zone**). It takes no new sessions, and its Slack connection and agent keys are cut in the same request. Past sessions stay readable; afterwards every request for the agent is `404`, and a new agent can take its slug. An API key cannot do it (`403`) |

### Agents with no administrator

An agent has no administrator when no live person administers it: no enabled individual administrator, no enabled member of an administrator team, and no enabled lead of its responsible team. Workspace owners and admins do not count; they are the ones who name a new administrator. An archived agent never counts as having none.

- The agent row's `ownerless` is the judgement now (`true` or `false`). `ownerless_since` is when the platform first saw the agent with no administrator, and turns `null` once someone administers it again. The platform brings it up to date every few seconds.
- `GET /v1/agents?ownerless=true` returns only such agents, and `ownerless` in `GET /v1/agents/counts` is how many there are. Both are read with the same permission as the list.
- The console shows workspace owners and admins an alert and a **No admin** filter above the agent list, and marks such rows **No admin**. The agent page shows a warning with a button to the Admins tab.
- An administrator is named again through the changes that already exist: add a person or a team as administrator, move the responsible team to a team with a lead, or make a member of the responsible team its lead. The first three clear the mark in the same request; a team role change clears it a few seconds later.
- Existing sessions whose requester was disabled stay waiting for a takeover after a new administrator is named. Take them over separately. A takeover and naming an administrator are independent, so either can come first.
- For workspace owners and admins, the detail warning shows how many of this agent's sessions wait for a takeover and lists them, each row linking to that session's detail. If such sessions remain after a new administrator is named, the warning stays with that list. On the session detail, **Take over session** makes you the session's requester. A session not shared with you needs a reason. Through the API, read them with `GET /v1/takeovers?agent_id={id}` and take one over with `POST /v1/sessions/{id}/takeover`. Anyone who may not read the takeover list sees neither the count nor the list.

An agent that still has no administrator 14 days after `ownerless_since` starts no new session. The web, the API, Slack and agent keys all get `409 AGENT_NOT_RUNNABLE` with `details.reason_code` `agent_ownerless`, and a Slack mention or DM gets a short notice. The date in the console warning is that point. Sessions already running are not stopped. Whether anyone administers the agent is checked again when the session is created, so naming an administrator lets new sessions start at once.

## Credential bindings

The card lists only the names of the credentials to use, in `capabilities.credential_refs`. The values live outside Werft (a secret store, a remote MCP server connection). The binding that says this agent may use that name is created separately by an administrator. If any name listed on the card is not bound, activation returns 409 `CREDENTIAL_UNBOUND`.

```bash
curl -sS "$API/v1/agents/$AID/credential-bindings" "${WEB[@]}" -d '{"credential_ref": "notion-token"}' \
  | jq '{credential_ref: .binding.credential_ref, created}'
curl -sS "$API/v1/agents/$AID/credential-bindings" "${WEB[@]}" | jq -c '[.items[].credential_ref]'
```

```text
{
  "credential_ref": "notion-token",
  "created": true
}
["notion-token"]
```

Removing a binding (`DELETE /v1/agents/{id}/credential-bindings/{binding_id}`) does not stop running sessions. It blocks starting with the next session. To block immediately, revoke that credential at the external service.
