エージェントの権限は 3 つの層からなる。リリースが固定したツールと権限モード、人が答える権限リクエスト、そしてエージェントを管理し資格情報の名前をつなぐ人である。

## ツール: リリースが決める

リリースは接続のランタイムが持つ組み込みツールすべてを固定する (リリースのレスポンスの `effective_tools.tools`)。組み込みツールを選んでブロックする設定はない。ツールを実行する前に人へ尋ねるかどうかは、下の権限モードと、プラットフォームに組み込まれた作業スペースのルール (事前許可と確認の一覧) が決める。

カードの `capabilities.forbidden` は MCP ツールに及ぶ。リリースが許可する MCP ツールがその一覧にあると、リリースは作れない。カードの `tool_policy` では MCP ツールの既定値は `ask` である。

## 権限モード

権限モードが、ツールを実行する前に人へ尋ねるかどうかを決める。モードは `default` と `auto` の 2 つで、セッションが動くたびに接続とモデルから決める。セッション詳細の `runtime.permission_mode` に表示される。

| モード | 動作 |
| --- | --- |
| `default` | セッションのワークスペース内の作業は、人に尋ねずに実行する。ファイルの書き込み・編集、`git` と `gh` のコマンド (下の確認一覧の形を除く)、`sed`、`mkdir`・`touch`・`cp`・`mv`・`rm`、`bun`・`npm`・`pnpm`・`yarn` の test・run・install (`npm ci` を含む)、`pytest`、`go test`・`build`・`vet`、`cargo test`・`build`・`check`、`make`、状態を変えない読み取り (`ls`、`cat`、`grep`、`find` など) は、エンジンの許可規則で通る。それ以外のコマンド (`tee`、`curl`、`python` など) と、エンジンが最後まで読めない行 (`mkdir -p d && cat > d/f <<'EOF'` のように `&&` の後にファイルへの redirect と heredoc が続く形、置換、pipe) はエンジンが尋ねるが、プラットフォームがその行を読み、ワークスペースのポリシーが人に残すものが見つからなければ自ら答え、そのときは権限リクエストにならない。エンジンが尋ねるワークスペース内のファイル書き込み (`.vscode/` などの dot 名) も同じである。ポリシーが人に残すものは 3 つである。1 つ目は、ポリシーの確認一覧にあるコマンド: `sed -i` と `sed` の `w`、ファイルを書いたりプログラムを実行したりする `git --output`・`--ext-diff`、別のリポジトリを指す `git -C`、`git add -f`、`git worktree`、`gh auth`、秘密値のファイル名 (`.env`、鍵、`.git/config`) を行に書いた `cat`・`head`・`tail`・`grep`・`rg`・`cp`・`mv`、隠しファイルまで探す `rg -u` や `--hidden`、ワークスペース外を指すランナーのオプション (`--prefix`、`-C`) など。2 つ目は、秘密値・`.git`・`.claude` のパスへの書き込み。3 つ目は、ワークスペース外のパス (symlink は解決した先で判定し、`..` を含むパスは外とみなす)。この 3 つは、プラットフォームが行の文字から読み取れた範囲でだけ捕まえる。逆に、shell がどこにいるかを行から判断できないとき (`cd -` など。移動先が 8 か所を超える行を含む)、ワークスペースのディレクトリ自体が書き込み先のとき (`rm -rf .`)、スクリプトの入れ子が深すぎるとき、確認一覧と照合するには行が長すぎるときは、3 つがなくても尋ねる。変数や置換が作るパス、`cat .e*` のような glob、スクリプトやインタプリタのコードが中で開くファイルは通ってしまう。リリースが Bash やファイルツールを deny 規則で絞っているセッションでは、プラットフォームは答えず、これまでどおり尋ねる。害を止めるのは権限リクエストではなく、ワークスペースのコンテナ分離、egress authorizer (push 先・トークン範囲)、GitHub のブランチ保護である。Codex 接続も、エンジンが尋ねたコマンドとファイル変更に同じポリシーで答える (エンジンに渡す許可規則は Claude より狭い。エンジンがより広い書き込み権限を併せて求めたファイル変更には答えない)。モデルが Claude のモデルでないリリースが動くモードである |
| `auto` | 人の代わりにモデルの分類器が呼び出しごとに許可・拒否を決める。分類器を使えないときは拒否する。インストール設定なしで使える。`default` と同じワークスペースの事前許可と確認一覧を受けるので、同じ日常のコマンド (`git`・`gh`、`sed`、ワークスペース内の書き込みと `mkdir`・`touch`・`cp`・`mv`・`rm`、読み取り) は分類器なしで実行され、確認一覧にかかる呼び出しは分類器ではなく人に回る。エンジンが最後まで読めない行は、確実に分けられ、すべての部分が許可一覧のコマンドであるときだけプラットフォームが自ら答え、それ以外は人に回る (`default` より狭い。分類器が下す判定をプラットフォームが代わりに行うことはない)。ただしエンジンはこのモードに入るとき、インタプリタ・スクリプト実行ツール (`bun run`・`npm run`・`npx`・`bunx` など) の許可を外すので、その呼び出しは分類器が判定する。例外として、組み込みの GitHub ツールのうち push、PR の書き込み、リポジトリの読み取りは分類器を通らず、サーバーが判定する(push 承認、release のツール一覧、セッションの grant)。レビュー送信と workflow は分類器を通る。プラットフォームは分類器に行動単位のルールを加える。下の許可のうち push・PR・リポジトリ読み取りは、この例外を受けられない古い worker でのみ分類器が見るルールである。許可: セッションの作業領域での commit と、プラットフォームの push フローによるセッション自身のリポジトリのセッション専用の作業ブランチ(`agent/<session-id>`)への push、そのブランチから PR を開くことと、このセッションが開いた PR のタイトル・本文の修正・コメント・クローズ・再オープン、許可されたリポジトリの一覧表示と読み取り用の追加。この許可に入らないもの: 既定・保護ブランチやプラットフォームが作っていないブランチへの push、force push、PR のマージ・承認、レビュー送信、このセッションが開いていない PR の修正・コメント・クローズ、ほかのリポジトリ(セッションに付けたものを含む)への push、秘密値。リポジトリ設定・ブランチ保護・webhook・deploy key・Actions secret の変更、GitHub 上のブランチ・リポジトリの削除、PR のマージはどの経路でも拒否寄りに扱う |

モードはセッションのリクエストで変更できない。Claude のモデルなら `auto` で、それ以外は `default` で動く。Claude のモデルとは、`anthropic` 接続のモデル、または `litellm` 接続で `claude-` か `anthropic/claude-` から始まるモデル id、あるいは `sonnet`・`opus`・`haiku`・`fable` (後ろに `[1m]` が付いてもよい) と完全に一致するモデル id である。名前の中に系列名を含むだけの id (`my-sonnet-proxy` など) は `default` になる。Codex の接続 (`openai_responses`) は常に `default` である。モードを選ぶ設定はない (接続にも、エージェントにも、インストール設定にもない)。リリースに記録されたモードは読まない。そのため、この規則より前に `default` で作った Claude モデルのリリースのセッションも `auto` で動き、リリースを作り直す必要はない。セッションのモデルが変わっても (一覧から外したモデルが次の版に移るときなど)、同じ規則で決める。自動モードは、それに対応したモデルでのみ動く ([Claude Code の自動モードの要件](https://code.claude.com/docs/en/permission-modes#eliminate-prompts-with-auto-mode))。push と PR のツールは、最新の worker ではエンジンが尋ねない。すでに動いているセッションは、次に worker がセッションを受け取るときにこの規則のモードに変わる。push 承認はモードとは別である。`auto` モードでも、push 承認がオンか、付けたリポジトリの push ポリシーが `ask` なら、どのリポジトリへの push でも、push のたびに人に尋ねる。人が選んだことのない値は承認なしとして読む。GitHub 設定を保存していないエージェント(新しいエージェントを含む)と GitHub 設定のない release(この設定より前に作った release など)は push 承認をオフとして、添付リポジトリの push ポリシーが空の設定(このポリシーができる前に保存した設定)は `allow` として読む。そのため新しいエージェントは、GitHub タブでリポジトリのスイッチをオンにすることが最初の保存なら(スイッチは切り替えるとすぐ保存され、この既定値も一緒に保存される)、その後に始まるセッションから人が承認をオンにするまで承認なしで push する。push 承認を先にオンにして保存した場合はその値が残る。最初に保存するまでセッションに GitHub ツールがない。人がオンにした値(**push 前の人の承認** オン、ポリシー `ask`・`deny`)と release が固定した push 承認はそのまま従う。オフにしても、承認なしで進むのは、付けたリポジトリの push ポリシー(`allow`・`ask`・`deny`)も `allow` のときだけである。ポリシーが `deny` なら push 自体がブロックされ、それ以外では、どのリポジトリへの push も、このスイッチとそのポリシーのうち厳しいほうに従う。人の承認を受けるには、スイッチをオンにするか、ポリシーを `ask` にする。

## 承認: 人だけが行う

権限リクエストと質問に答えるには `sessions:approve` scope が必要である。worker 内のエージェントが持つ認証情報は `/v1` で 401 になるため、自分で承認することはできない。エージェントキーも `sessions:approve` を持てるが、そのキーで開始したセッションのリクエストは承認できない。答え方は [承認待ちと再開](/sessions/waiting-and-resume) にある。

セッションを見られるからといって、そのセッションのリクエストに答えられるわけではない。権限リクエストと質問に答え、push・PR を承認するのは次の人だけである。

- セッションを作った人(API キーが作ったセッションならそのキー)
- そのセッションのエージェントの管理者
- ワークスペースの owner・admin

共有でセッションを見ているだけの人が答えると `403 FORBIDDEN`(`reason_code: role`)になり、リクエストは開いたまま残ってセッションは `needs_input` のままである。見られないセッションはこれまでどおり `404` である。`GET /v1/sessions/{id}/pending-requests` の `answerable` が、呼び出した人が答えられるかを示す。コンソールは `false` のとき、許可・拒否を理由とともに無効にして表示する。

## エージェント管理者

エージェントを作成した人が、そのエージェントの管理者になる。管理者は member であっても、そのエージェントのカード修正、リリース、有効化、認証情報の紐付け、管理者の指定、エージェントキーの発行を行える。人やチームを管理者として追加でき、チームの場合はそのチームのメンバー全員が管理者になる。チームを新しく追加できるのは、チームを管理する owner・admin だけである。member のエージェント管理者はチームを追加できないが、追加済みのチームを外すことと、人の追加・削除はできる。

エージェントには常に担当チームが一つあり、変えることはできても空にはできない。担当チームのチーム管理者(`lead`)はそのエージェントの管理者で、メンバー(`member`)は管理しない。owner・admin でなければ、自分が所属するチームだけを担当チームに選べる。担当チームに決まったチームは、そのエージェントをアーカイブするか担当チームを移すまで削除できない。

チームのロールはコンソールのチーム画面で見る。メンバー表の **チームのロール** 列が **チーム管理者**(`lead`)と **メンバー**(`member`)を分け、**所属チーム** の一覧にも自分のロールが付く。owner・admin はメンバーの行の **ロールを変更** でロールを選んで **保存** する(`PATCH /v1/teams/{team_id}/members/{user_id}` `{"role"}`)。担当チームになっているチームを削除しようとすると、コンソールは削除せず、そのチームが担当チームのエージェントの名前とリンクを示す(`409 TEAM_MANAGES_AGENTS`)。先に各エージェントの担当チームを変える。

エージェントを見られる範囲は次のとおり。

| 誰が | 情報(名前・slug・説明・担当チーム・状態・有効なリリース) | 設定(カード・リリース・管理者・認証情報の紐付け・GitHub・Slack)の閲覧 | 設定の変更 |
| --- | --- | --- | --- |
| owner・admin | 読める | 読める | 変えられる |
| エージェント管理者(担当チームの `lead` を含む) | 読める | 読める | 変えられる |
| 担当チームの `member` | 読める | 読める | できない(`403`) |
| それ以外の member | 見えない(一覧になく、読むと `404`) | できない(`404`) | できない(`403`) |

<Callout>
担当チームの `member` は `GET /v1/agents`・`GET /v1/agents/counts` で自分のチームが担当するエージェントを探し、設定を読める。`include=summary` の要約(管理者・認証情報の紐付け)は、設定を読めるエージェントにだけ付く。エージェントの設定を変えた receipt も、設定を読める人だけが読める。
</Callout>

### 担当チーム外の member

owner・admin、エージェント管理者、担当チームのメンバーをそのエージェントの内側と呼び、それ以外の member を外側と呼ぶ。エージェントを使えるのは内側だけである。これを変える設定はない。

- 外側の member には、Web でも Slack でもエージェントがないのと同じである。一覧と件数に出ず、読むと `404`、セッションを開始しても、存在しない release と同じ `404` になる。共有されたセッションは見えるが、そのエージェントは隠れる。
- Slack で外側の member がエージェントをメンションしたり DM を送ったりしても、セッションは始まらず、権限がないという短い案内だけが届く。Werft アカウントを連携していない Slack ユーザーには、連携を求める案内が届く。
- エージェントの `workspace` 共有セッションも内側だけが見る。外側の member には一覧・件数・詳細・イベント・使用量の最近の一覧に出ない。担当チームが必須になる前にチームがなかったエージェントは、メンバーのいない保管チーム(名前を変えても、サーバーは保管チームとして認識する)が引き受けた。これらのエージェントの `workspace` セッションは、適切なチームに移すまで以前と同じくすべてのメンバーに見える。そのセッションの一覧・詳細では、エージェント名もすべてのメンバーに文字で表示され、セッション一覧をそのエージェントで絞り込める。エージェントの画面は外側の member には引き続き開かない(`404`)。
- 外側の member でも、自分が開始したセッションと、自分や自分のチームを指定して共有された(`people`・`team`)セッションは引き続き見える。
- 担当チームを変えたときや、メンバーがチームから外れたときは、次のリクエストから作成済みのセッションにも適用される。開いているイベントストリームは次の確認で切れる。
- 使用量の合計(セッション数・費用・成果数)は変わらず、最近の成果一覧から見られないセッションの行だけが抜ける。
- 共有範囲が `workspace` でも外側の member に見えないセッションは、`GET /v1/sessions/{id}/share` の `audience_limited` が `true` になる。

<Callout>
外側の member がエージェントを見て使える範囲を選ぶワークスペース設定はない。動作は常に `none`・`managing_team` と同じで、外側の member にはエージェントが見えない。
</Callout>

[作成](/agents/create)の `AID` と `WEB` を引き続き使う。

```bash
curl -sS "$API/v1/agents/$AID/admins" "${WEB[@]}" | jq '{users: [.users[].email], teams}'
```

```text
{
  "users": [
    "owner@example.test"
  ],
  "teams": []
}
```

| リクエスト | 内容 |
| --- | --- |
| `POST /v1/agents/{id}/admins` `{"user_id"}` または `{"team_id"}` | 管理者の指定 |
| `DELETE /v1/agents/{id}/admins/users/{user_id}`, `…/teams/{team_id}` | 解除 |
| `PUT /v1/agents/{id}/managing-team` `{"team_id"}` | 担当チームの指定・変更 |
| `GET /v1/administered-agents` | 自分が管理しているエージェント |
| `DELETE /v1/agents/{id}` | エージェントを削除する(コンソール: **詳細設定** → **危険な操作**)。新しいセッションを受け付けなくなり、Slack の接続とエージェントキーを同じリクエストで切る。過去のセッションはそのまま読め、以後このエージェントへのリクエストはすべて `404`、slug は新しいエージェントが使える。API キーではできない(`403`) |

### 管理者のいないエージェント

エージェントを管理する有効な人が一人もいないとき、そのエージェントは管理者なしである。個人の管理者、管理者チームのメンバー、担当チームのチーム管理者(`lead`)のうち、無効化されていない人が誰もいない場合だ。ワークスペースの owner・admin は数えない。新しい管理者を決める側だからだ。アーカイブしたエージェントは管理者なしとみなさない。

- エージェント行の `ownerless` が現在の判定である(`true`・`false`)。`ownerless_since` はプラットフォームが管理者なしを最初に見た時刻で、管理者が再びできると `null` になる。プラットフォームは数秒おきにこの値を合わせる。
- `GET /v1/agents?ownerless=true` は管理者のいないエージェントだけを返し、`GET /v1/agents/counts` の `ownerless` はその件数である。どちらも一覧と同じ権限で読む。
- コンソールはワークスペースの owner・admin に、エージェント一覧の上に通知と **管理者なし** フィルターを表示し、行に **管理者なし** の印を付ける。詳細画面は警告と、管理者タブへ移るボタンを表示する。
- 管理者を決め直す方法は既存の変更である。人やチームを管理者に加える、チーム管理者のいるチームに担当チームを変える、担当チームのメンバー一人をチーム管理者にする。最初の三つは同じリクエストで印を消し、チームの役割変更は数秒後に消える。
- 依頼者が無効化された既存のセッションは、管理者を決め直しても引き継ぎ待ちのまま残る。そのセッションは別に引き継ぐ。引き継ぎと管理者の指定は互いに独立していて、どちらを先にしてもよい。
- ワークスペースの owner・admin には、詳細画面の警告がこのエージェントの引き継ぎ待ちセッションの数と一覧を示し、行ごとにそのセッションの詳細へのリンクを置く。管理者を決め直したあとも引き継ぎ待ちのセッションが残っていれば、警告はその一覧として残る。セッション詳細の **セッションを引き継ぐ** で引き継ぐと、自分がそのセッションの依頼者になる。自分に共有されていないセッションは理由を添える必要がある。API では `GET /v1/takeovers?agent_id={id}` で読み、`POST /v1/sessions/{id}/takeover` で引き継ぐ。引き継ぎ一覧を読む権限がない人には、数も一覧も見えない。

`ownerless_since` から 14 日を過ぎても管理者のいないエージェントは、新しいセッションを開始しない。Web・API・Slack・エージェントの key はいずれも `409 AGENT_NOT_RUNNABLE`(`details.reason_code`: `agent_ownerless`)を受け取り、Slack のメンションと DM には短い案内が届く。コンソールの警告の日付がその時点である。すでに動いているセッションは止めない。管理者がいるかはセッションを作るその時点で改めて確かめるので、管理者を決め直せばすぐに新しいセッションを開始できる。

## 認証情報の紐付け

カードには、使う認証情報の名前だけを `capabilities.credential_refs` に書く。値は Werft の外 (secret store、remote MCP server の接続) にある。その名前をこのエージェントが使ってよいという紐付けは、管理者が別途作成する。カードに書かれた名前のうち紐付けられていないものがあると、有効化は 409 `CREDENTIAL_UNBOUND` になる。

```bash
curl -sS "$API/v1/agents/$AID/credential-bindings" "${WEB[@]}" -d '{"credential_ref": "notion-token"}' \
  | jq '{credential_ref: .binding.credential_ref, created}'
curl -sS "$API/v1/agents/$AID/credential-bindings" "${WEB[@]}" | jq -c '[.items[].credential_ref]'
```

```text
{
  "credential_ref": "notion-token",
  "created": true
}
["notion-token"]
```

解除 (`DELETE /v1/agents/{id}/credential-bindings/{binding_id}`) は、動作中のセッションを止めない。次のセッションから遮断される。すぐに遮断するには、外部サービスでその認証情報を失効させる。
