title: "Create"
description: Define an agent, create and activate a release, and bind it to a session
---

An agent is a named definition in a workspace. Name and description are values for people; the definition a run uses is a card (model, tools). Every edit to the card adds a new version. A release binds one version to a provider connection, and the release an agent points to is its active release. A session is always created from a release, and it belongs to that agent.

<Callout type="warn">
Sessions run with the settings their release pinned (connection, model, runtime, built-in tools). What to ask a person about is set by the permission mode and the workspace rules built into the platform. Name and description are not passed to the model; how the agent should work is told by the repository's `AGENTS.md` or `CLAUDE.md`. See [Instructions and description](/agents/instructions-and-roles) and [Permissions](/agents/permissions) for details.
</Callout>

## In the web console

The web console of the local stack is at `http://127.0.0.1:3000/`.

1. The first time only, open the one-time setup link (`/bootstrap#setup=…`) the operator received and create the first owner and workspace. The operator gets the link from a command on the installation while no owner exists (`scripts/test-ops.sh setup-link` on a single-server installation). See [first owner and keys](/run-server/self-hosting/users-and-keys) for details.
2. After logging in, open "Agents" in the left sidebar and click "New agent" at the top right. The "New agent" screen opens with three steps: Name → What it does → Connect channels.
3. In the "Name" step, enter a name. The identifier (slug) is filled in from the name, and you can change it. If you like, write a short introduction for people in "Description (optional)". The model does not see the name or the description. Pick the responsible team and click "Next".
4. In the "What it does" step, choose the model connection and the model, set the reply language, then click "Save and continue". The agent is saved, and its first release is made with that connection and turned on at once. New sessions now start with this release. The model is chosen from the chosen connection's model list. An owner manages connections and their model lists in Settings → Model connections ([Model connections](/run-server/self-hosting/model-connections)). Instructions for how it should work go in the repository's `AGENTS.md` or `CLAUDE.md`.
5. In the "Connect channels" step, add a Slack app with "Create and install Slack app", or click "Do this later". The agent stays on if you leave this step.

Owners, admins, and members can all create agents, and the person who creates one becomes that agent's administrator.

## Through the API

The agents API accepts only the same cookie login as the web console. Calling it with an API key returns 403.

### Log in

```sh
read -rs WERFT_PASSWORD
WERFT_COOKIE=$(curl -sS -o /dev/null -D - "$API/v1/auth/login" \
  -H 'Content-Type: application/json' -H 'X-Requested-With: werft-web' \
  -d "$(jq -nc --arg e 'owner@example.test' --arg p "$WERFT_PASSWORD" '{email: $e, password: $p}')" \
  | sed -n 's/^[Ss]et-[Cc]ookie: \(__Host-werft_session=[^;]*\).*/\1/p')
```

The login cookie has a `__Host-` name and is `Secure`, so curl's cookie jar does not store it over http. Take it from the response headers and send it in a `Cookie` header. Requests that change state need `X-Requested-With: werft-web`.

```bash
WEB=(-H 'Content-Type: application/json' -H 'X-Requested-With: werft-web' -H "Cookie: $WERFT_COOKIE")
curl -sS "$API/v1/auth/me" "${WEB[@]}" | jq '{role: .principal.role, workspace: .workspace.slug}'
```

### Create

An agent must have a responsible team. An owner or admin picks any team from `GET /v1/teams`; anyone else picks a team of their own from `GET /v1/my-teams`. The example below creates a team as the owner and uses it (a team of the same name already there is 409; use that team's `id`).

```bash
TEAM=$(curl -sS "$API/v1/teams" "${WEB[@]}" -d '{"name": "Research"}' | jq -r .team.id)
agent=$(curl -sS "$API/v1/agents" "${WEB[@]}" -d '{
  "slug": "research-bot",
  "name": "Research Bot",
  "description": "Reads the repository and answers questions",
  "managing_team_id": "'"$TEAM"'",
  "card": {
    "model": "claude-sonnet-5",
    "capabilities": { "mcp": null }
  }
}')
AID=$(echo "$agent" | jq -r .agent.id)
VID=$(echo "$agent" | jq -r '.versions[0].id')
echo "$agent" | jq '{slug: .agent.slug, version: .versions[0].version_no, active_release_id: .agent.active_release_id}'
```

```text
{
  "slug": "research-bot",
  "version": 1,
  "active_release_id": null
}
```

If the same workspace already has the same slug, the response is 409 `ALREADY_EXISTS`. Creating an agent alone does not activate anything.

The team in `managing_team_id` becomes the responsible team. Leaving it out is 400 `BAD_REQUEST`, with `{"path": "managing_team_id", "message": "managing_team_id is required"}` in `error.details.issues`. An owner or admin who names a team that does not exist gets 404. Anyone else who names a team they are not in gets 403 (`details.reason_code: team_not_allowed`), even when the team does not exist. So a member who is in no team cannot create an agent. The response's `agent.managing_team_name` is that team's name.

Every agent has one responsible team. `PUT /v1/agents/{id}/managing-team` changes it, and nothing clears it. For agents created before the responsible team was required, the migration filled it in: every agent that had none went to a team with no members named `Unassigned agents`, one per workspace (if a team with that name already exists, an 8-character id follows, as in `Unassigned agents (1a2b3c4d)`). That team is an ordinary team: rename it, or move its agents to another team.

### Create a release

A release binds one version to one provider connection (`connection_id`). If the card's `model` is not on that connection's model list, the response is 422. The release pins the run settings of that moment: the runtime for the connection's kind (at the version the image ships), every built-in tool of that runtime, and the permission mode (`auto` for a Claude model, `default` otherwise; see [Permission mode](/agents/permissions#permission-mode)). A session created with the release runs the card's model unless it names another.

```bash
release=$(curl -sS "$API/v1/agents/$AID/releases" "${WEB[@]}" \
  -d "$(jq -nc --arg v "$VID" '{version_id: $v, connection_id: "fake-messages"}')")
REL=$(echo "$release" | jq -r .release.id)
echo "$release" | jq '{id: .release.id, created, tools: .release.effective_tools.tools}'
```

```text
{
  "id": "sha256:…",
  "created": true,
  "tools": [
    "Read",
    "Write",
    "Edit",
    "…"
  ]
}
```

The release id is a hash of the card, the connection and the pinned run settings. Creating a release again with the same contents returns the same release with `created: false`.

People name a release by its `label`: the second it was created, in Seoul time, as `2026-10-30_14:30:28`. When the same agent gets more than one release in the same second, the second one onward ends in `-2`, `-3`, and so on. The console's release history, the agent's header tag and the session lists use this name. The release id is still the identifier. A card's `version_no` only goes up when the card changes, so releasing the same card on another connection keeps the same version.

The console's release history shows, for each release, what changed against the release the same agent made just before it (allowed repositories, model, tools and MCP, prompt, settings), with who made it and when. Credentials show only as "Changed", never their values. The session screen shows the release the session uses after the agent's name in the line under the title, and marks it when it is not the agent's active release. A session keeps the release it started on, so changed settings apply from new sessions. The session response's `agent.release_is_active` carries that comparison. A session of an archived agent marks the agent's name with an "Archived" badge in the session list and on the session screen; the session response's `agent.archived` carries that state.

### Activate

`expected_revision` is the agent's current `activation_revision`. It starts at `-1`. If someone changed it elsewhere first, the response is 409 `REVISION_CONFLICT`.

```bash
curl -sS "$API/v1/agents/$AID/activate" "${WEB[@]}" \
  -d "$(jq -nc --arg r "$REL" '{release_id: $r, expected_revision: -1}')" \
  | jq '{activation_revision, previous_release_id}'
```

```text
{
  "activation_revision": 0,
  "previous_release_id": null
}
```

A release's `activated_at` is when it was last activated, and `deactivated_at` is when the next activation took its place. The active release has a `deactivated_at` of `null`, and a release that was never activated has both `null`. Both are read from the activation history, so releases activated before these fields existed have them too.

### List and count

```bash
curl -sS "$API/v1/agents?limit=50" "${WEB[@]}" | jq -c '{n: (.items | length), next_cursor}'
curl -sS "$API/v1/agents/counts" "${WEB[@]}" | jq -c
```

```text
{"n":1,"next_cursor":null}
{"counts":{"all":1,"administered":1,"active":1,"draft":0,"inactive":0,"ownerless":0}}
```

The list returns agents oldest first, `limit` at a time (default 50, at most 100). Send the response's `next_cursor` back as `cursor` for the next page; it is `null` on the last one. Without `cursor` you get the first page only. With `q` (up to 200 characters) you get only agents whose name or slug contains it, ignoring case; with `ids`, agent IDs joined by commas (up to 100), you get only those agents. With `connection_id` you get only agents whose active release runs on that connection; an agent with no active release is left out. In every case the next page comes by the same `cursor`. `GET /v1/agents/counts` returns how many agents the list holds read to its end (`all`), how many of them you administer yourself or through a team (`administered`), how many are on through an active release (`active`), how many are drafts, not archived but with no active release yet (`draft`), how many are in neither (`inactive`), and how many no one administers (`ownerless`). Both need the same permission as the list, and API keys are refused. With `ownerless=true` the list returns only the agents no one administers ([Agents with no administrator](/agents/permissions#agents-with-no-administrator)).

Each agent in the list has a `status` and an `activation`. `status` is the state of the agent's record, so a draft that was never switched on is `active` too. Do not use it to tell whether an agent is on. Read `activation` for that: `active` once an active release lets people talk to it, `draft` while it has no active release, and `inactive` otherwise (an agent with an active release that is paused, or an archived one). The three values follow the same rules as `active`, `draft` and `inactive` in `GET /v1/agents/counts`, so those three counts add up to `all`. `activation` may gain values; read a value you do not know as not switched on.

```bash
curl -sS "$API/v1/agents?limit=50" "${WEB[@]}" | jq -c '.items[] | {slug, status, activation}'
```

```text
{"slug":"research-bot","status":"active","activation":"active"}
```

## Try it before you publish

An agent with an active release is **published**; one without is **unpublished**. An unpublished agent is seen only by its admins (direct admins, members of its admin teams, the team leads of its responsible team) and the workspace's owners and admins. Members of its responsible team and of its usage teams do not find it in the list or the counts, and its detail is 404. Once published, it is seen as before.

Send `"activate": false` with a save (`POST /v1/agents`, `PATCH /v1/agents/{id}`) to make the release without turning it on. The response's `release.status` is `saved` and `release_id` names that release. The change stays on the agent's `draft`, and a next save that leaves out the card or the connection goes on from that `draft`, not from the active release. If a newer save landed meanwhile the answer is `superseded`; if the release cannot be made it is `failed` with a reason. Without `activate`, the save turns the release on as before.

```bash
curl -sS "$API/v1/agents/$AID" -X PATCH "${WEB[@]}" -d '{
  "card": { "model": "claude-sonnet-5", "capabilities": { "mcp": null } },
  "connection_id": "fake-messages",
  "activate": false
}' | jq -c '.release | {status, release_id}'
```

```text
{"status":"saved","release_id":"sha256:…"}
```

Try that release in a preview session (`POST /v1/sessions` with `"preview": true`, see [Start a session](/sessions/start#preview)); a release never turned on works too. When you are done, turn it on with [Activate](#activate): that is publishing. Activating the release the `draft` holds clears the `draft`; rolling back to an earlier release leaves it.

## The responsible team in the console

The responsible team is the team an agent belongs to. Its team leads manage the agent; its members see the settings and use it ([Permissions](/agents/permissions#agent-administrators)).

- **New agent**: the first step requires a responsible team. Owners and admins pick from every team, members from the teams they are in. With a single team it is picked for you. A member in no team sees only “You are in no team, so you cannot make an agent. Ask a workspace admin to add you to a team.” and cannot go on.
- **Agent list**: the table shows the name, engine, status, channels and running sessions, not the responsible team. See the responsible team on the Admins tab of the agent's page.
- **Admins tab**: the `Responsible team` group at the top shows the current team's name as a link to the team page. Whoever manages the agent picks a team in `Change` beside it and it applies at once; it cannot be cleared. A responsible team with no team lead is pointed out. The `Agent admins` list below shows people and teams as the same one-line rows, and choosing from the search results adds at once. When the responsible team is also an admin team, its row says that every member is an admin.
- **Responsible team members**: they read every setting on the detail page but get no edit, release or connect buttons, and a notice at the top says they can only read.
- **Outside members**: the agent is not in their list, and opening its detail address shows “Agent not found”, the same as for an agent that does not exist.

## Bind to a session

Put `agent_release_id` in the session create request. The session runs on that release's connection and model. If the connection was disabled or the model left its list, the answer is 409 `RELEASE_SPEC_UNAVAILABLE`; make a new release on another connection or model. Use an agent key of that agent. Issue an agent key in the web console, or with the web login cookie by sending `kind: "agent"` and `agent_id` to `POST /v1/api-keys` ([API key](/api-keys)). The SDK has no method for issuing it. Keep the secret in a variable only.

`repository_id` is optional. If you omit it, an agent with GitHub settings starts without a repository and attaches only what it needs ([Sessions without a repository](/sessions/without-repository)), and an older agent with no settings starts on its release's repository. The example below names `sample-app` directly and starts on that repository.

<Tabs groupId="client" persist items={["SDK", "HTTP API"]}>
<Tab>

```ts
import { Werft } from "@werft-ai/sdk";

// WERFT_API_KEY holds the agent key; WERFT_AGENT_RELEASE_ID the release above.
const agent = new Werft();
const started = await agent.sessions.create({
  repository_id: "sample-app",
  agent_release_id: process.env.WERFT_AGENT_RELEASE_ID ?? "",
  message: 'GATE-SPEC {"id":"agent","steps":[],"final":"hello from research-bot"}',
});
console.log(started.status, started.turn_id);
```

A request from a session made with an agent key is approved by another key or a person ([A separate key for approvals](/getting-started/client#a-separate-key-for-approvals)).

</Tab>
<Tab>

```bash
AGENT_KEY=$(curl -sS "$API/v1/api-keys" "${WEB[@]}" \
  -d "$(jq -nc --arg a "$AID" '{kind: "agent", agent_id: $a, name: "research-bot", scopes: ["sessions:read", "sessions:write"]}')" \
  | jq -r .secret)
curl -sS "$API/v1/sessions" \
  -H "Authorization: Bearer $AGENT_KEY" \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(uuidgen)" \
  -d "$(jq -nc --arg r "$REL" --arg m 'GATE-SPEC {"id":"agent","steps":[],"final":"hello from research-bot"}' \
    '{repository_id: "sample-app", agent_release_id: $r, message: $m}')" \
  | jq '{status, turn_id}'
```

```text
{
  "status": "queued",
  "turn_id": "1"
}
```

Reference: [`POST /v1/sessions`](/reference/http-api/sessions/createSession)

</Tab>
</Tabs>

Sending with a key that is not in the workspace (for example `scripts/local.sh key quickstart …`) returns 404 because the release is not found.
