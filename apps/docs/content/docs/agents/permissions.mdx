에이전트의 권한은 세 층이다. release가 고정한 도구와 권한 모드, 사람이 답하는 권한 요청, 그리고 에이전트를 관리하고 자격 증명 이름을 연결하는 사람.

## 도구: release가 정한다

release는 연결의 런타임이 가진 내장 도구 전부를 고정한다(release 응답의 `effective_tools.tools`). 내장 도구를 골라 막는 설정은 없다. 도구를 실행하기 전에 사람에게 묻는지는 아래 권한 모드와 플랫폼에 들어 있는 작업 공간 규칙(사전 허용과 묻기 목록)이 정한다.

카드의 `capabilities.forbidden`은 MCP 도구에 미친다. release가 허용하는 MCP 도구가 그 목록에 있으면 release를 만들 수 없다. 카드 `tool_policy`의 MCP 도구 기본값은 `ask`다.

## 권한 모드

release가 고정한 `permission_mode`가 도구를 실행하기 전에 사람에게 묻는지 정한다. 세션 상세의 `runtime.permission_mode`에 나온다.

| 모드 | 동작 |
| --- | --- |
| `default` | 세션 작업 공간 안의 파일 쓰기·편집, `git`·`gh` 명령 전체와 `sed`, 작업 공간 안 `mkdir`, `bun`·`npm`·`pnpm`·`yarn`의 test·run은 묻지 않고 실행한다. `&&`·`;`·`\|`로 이은 명령은 각 부분이 이 범위일 때만 통과하고, 한 부분이라도 밖이면 전체가 권한 요청이 된다. 작업 공간 밖 쓰기(symlink와 `..`를 풀어 본 경로 기준), 비밀값·`.git`·`.claude` 경로, `sed -i`, 파일을 쓰거나 프로그램을 돌리는 `git --output`·`--ext-diff`, 다른 저장소를 가리키는 `git -C`, `git add -f`, `gh auth`, `curl` 같은 그 밖의 네트워크 도구는 실행 전에 권한 요청을 만든다. `git`·`gh`는 옵션과 상관없이 묻지 않는다. 막는 것은 권한 요청이 아니라 작업 공간 컨테이너 격리, egress authorizer(push 대상·토큰 범위), GitHub 브랜치 보호다. 상태를 바꾸지 않는 조회(`ls`, `cat`, `grep`, `find` 등)는 엔진이 작업 공간 안에서 묻지 않고 실행한다. 작업 공간 밖 경로나 `find -exec`·`-delete`는 엔진이 묻고, 비밀 파일 이름(`.env`, 키, `.git/config`)을 줄에 적은 `cat`·`head`·`tail`·`grep`·`rg`와 숨김 파일까지 뒤지는 `rg -u`·`--hidden`류는 이 목록이 묻는다(이름만 보므로 `cat .e*`나 `grep -r`은 못 잡는다). Claude 모델이 아닌 release가 도는 모드다 |
| `acceptEdits`, `dontAsk` | Claude Code의 같은 이름 모드로 돌고, `default`와 같은 작업 공간 사전 허용과 승인 목록을 더한다. 이 목록의 비밀값·`.git`·`.claude` 경로는 `acceptEdits`에서도 묻는다 |
| `plan` | Claude Code의 같은 이름 모드로 돈다. 사전 허용은 없다 |
| `auto` | 사람 대신 모델 분류기가 호출마다 허용·거부를 정한다. 분류기를 쓸 수 없으면 거부한다. 설치 설정 없이 쓸 수 있다. `default`와 같은 작업 공간 사전 허용과 묻기 목록을 받으므로, 같은 일상 명령(`git`·`gh`, `sed`, 작업 공간 안 쓰기·`mkdir`, 조회)은 분류기 없이 실행되고, 묻기 목록에 걸린 호출은 분류기가 아니라 사람에게 간다. 다만 엔진은 이 모드에 들어갈 때 인터프리터·스크립트 실행기(`bun run`·`npm run`·`npx`·`bunx` 등)의 허용을 빼므로 그 호출은 분류기가 판정한다. 내장 GitHub 도구 중 push, PR 쓰기, 저장소 읽기는 예외로 분류기를 거치지 않고 서버가 판정한다(push 승인, release의 도구 목록, 세션 grant). 리뷰 제출과 workflow는 분류기를 거친다. 플랫폼이 분류기에 행동 단위 규칙을 더한다. 아래 허용 목록의 push·PR·저장소 읽기는 이 예외를 받지 못하는 옛 worker에서만 분류기가 보는 규칙이다. 허용: 세션 작업 공간의 commit과 플랫폼 push 흐름으로 세션 자기 저장소의 세션 전용 작업 브랜치(`agent/<session-id>`)에 push하기, 그 브랜치에서 PR 열기와 이 세션이 연 PR의 제목·본문 수정·코멘트·닫기·다시 열기, 허용된 저장소 목록 보기와 읽기용으로 붙이기. 이 허용에 들지 않는 것: 기본·보호 브랜치나 플랫폼이 만들지 않은 브랜치 push, force push, PR 머지·승인, 리뷰 제출, 이 세션이 열지 않은 PR의 수정·코멘트·닫기, 다른 저장소(세션에 붙인 저장소 포함) push, 비밀값. 저장소 설정·브랜치 보호·webhook·deploy key·Actions secret 변경, GitHub의 브랜치·저장소 삭제, PR 머지는 어떤 경로로든 거부 쪽으로 둔다 |
| `bypassPermissions` | 판정 없이 모든 호출을 실행한다. 새 release는 이 모드를 고르지 않는다 |

모드는 release에 고정되고 세션 요청으로 바꿀 수 없다. 새 release는 Claude 모델이면 `auto`로, 그 밖에는 `default`로 돈다. Claude 모델은 `anthropic` 연결의 모델이거나, `litellm` 연결에서 `claude-`나 `anthropic/claude-`로 시작하는 모델 id, 또는 `sonnet`·`opus`·`haiku`·`fable`(뒤에 `[1m]`이 붙어도 된다)과 정확히 같은 모델 id다. 이름 안에 계열 이름이 들어 있을 뿐인 id(`my-sonnet-proxy` 등)는 `default`다. Codex 연결(`openai_responses`)은 언제나 `default`다. 모드를 고르는 설정은 없다. 세션의 모델이 바뀌면(모델 목록에서 빠진 모델이 다음 판으로 옮겨 갈 때 등) 이 규칙으로 모드를 다시 정한다. 다만 모델과 상관없이 `default`로 고정된 release(이 규칙 전의 Claude 모델 release 등)는 그대로 둔다. 그런 release는 release를 다시 만들어야 새 세션이 `auto`로 돈다. 자동 모드는 그것을 지원하는 모델에서만 동작한다([Claude Code의 자동 모드 요건](https://code.claude.com/docs/en/permission-modes#eliminate-prompts-with-auto-mode)). push와 PR 도구는 최신 worker에서 `plan`을 뺀 모드에서 엔진이 묻지 않는다(`plan`은 지금처럼 엔진이 묻는다). 이미 도는 세션은 원래 모드로 계속 돈다. push 승인은 모드와 별개다. `auto` 모드여도 push 승인이 켜져 있거나 첨부 저장소 push 정책이 `ask`이면 모든 저장소의 push마다 사람에게 묻는다. 에이전트 GitHub 탭을 처음 저장할 때는 push 승인이 꺼진 채로 시작하지만, GitHub 설정이 없는 release(이 설정 전에 만든 release 등)는 켜진 것으로 읽는다. 승인 없이 자동 push하려면 GitHub 탭에서 **push 전 사람 승인**이 꺼져 있는지 보고 저장한다. 꺼도 승인 없이 가려면 첨부 저장소 push 정책(`allow`·`ask`·`deny`)도 `allow`여야 한다. 정책이 `deny`이면 push 자체가 막히고, 그 밖에는 모든 저장소의 push가 이 스위치와 그 정책 중 더 엄격한 쪽을 따른다. 사람 승인을 받으려면 스위치를 켜거나 정책을 `ask`로 둔다.

## 승인: 사람만 한다

권한 요청과 질문에 답하려면 `sessions:approve` scope가 필요하다. worker 안의 에이전트가 가진 자격은 `/v1`에서 401이라 스스로 승인하지 못한다. 에이전트 key도 `sessions:approve`를 가질 수 있지만, 그 key로 시작한 세션의 요청은 승인하지 못한다. 답하는 방법은 [승인 대기와 재개](/sessions/waiting-and-resume)에 있다.

세션을 볼 수 있다고 그 세션의 요청에 답할 수 있는 것은 아니다. 권한 요청과 질문에 답하고 push·PR을 승인하는 것은 다음 사람만 한다.

- 세션을 만든 사람(API key가 만든 세션이면 그 key)
- 그 세션 에이전트의 관리자
- 워크스페이스 owner·admin

공유로 세션을 보기만 하는 사람이 답하면 `403 FORBIDDEN`(`reason_code: role`)이고, 요청은 열린 채로 남아 세션은 `needs_input`에 머문다. 볼 수 없는 세션은 지금처럼 `404`다. `GET /v1/sessions/{id}/pending-requests`의 `answerable`이 부르는 사람이 답할 수 있는지 알려 주고, 콘솔은 `false`이면 허용·거부를 이유와 함께 비활성으로 보인다.

## 에이전트 관리자

에이전트를 만든 사람이 그 에이전트의 관리자가 된다. 관리자는 member여도 그 에이전트의 카드 수정, release, 활성화, 자격 연결, 관리자 지정, 에이전트 key 발급을 할 수 있다. 사람이나 팀을 관리자로 더할 수 있고, 팀이면 그 팀 구성원 모두가 관리자다. 팀을 새로 더하는 것은 팀을 관리하는 owner·admin만 한다. 에이전트 관리자(member)는 팀을 더할 수 없고, 이미 더해진 팀을 빼거나 사람을 더하고 뺄 수는 있다.

에이전트에는 늘 담당 팀이 하나 있고, 바꿀 수는 있어도 비울 수는 없다. 담당 팀의 팀 관리자(`lead`)는 그 에이전트의 관리자이고, 구성원(`member`)은 관리하지 않는다. owner·admin이 아니면 자기가 속한 팀만 담당 팀으로 고른다. 담당 팀으로 정해진 팀은 그 에이전트를 보관하거나 담당 팀을 옮기기 전에는 지울 수 없다.

팀 역할은 콘솔의 팀 화면에서 본다. 구성원 표의 **팀 역할** 칸이 **팀 관리자**(`lead`)와 **구성원**(`member`)을 나누고, **내가 속한 팀** 목록에도 내 역할이 붙는다. owner·admin은 구성원 줄의 **역할 바꾸기**로 역할을 고르고 **저장**한다(`PATCH /v1/teams/{team_id}/members/{user_id}` `{"role"}`). 담당 팀인 팀을 지우려 하면 콘솔은 삭제하지 않고 그 팀이 담당 팀인 에이전트 이름과 링크를 보인다(`409 TEAM_MANAGES_AGENTS`). 각 에이전트의 담당 팀을 먼저 바꾼다.

에이전트를 보는 범위는 이렇다.

| 누가 | 정보(이름·slug·설명·담당 팀·상태·활성 release) | 설정(카드·release·관리자·자격 연결·GitHub·Slack) 읽기 | 설정 바꾸기 |
| --- | --- | --- | --- |
| owner·admin | 읽는다 | 읽는다 | 바꾼다 |
| 에이전트 관리자(담당 팀 `lead` 포함) | 읽는다 | 읽는다 | 바꾼다 |
| 담당 팀의 `member` | 읽는다 | 읽는다 | 못 한다(`403`) |
| 그 밖의 member | 못 본다(목록에 없고 읽으면 `404`) | 못 한다(`404`) | 못 한다(`403`) |

<Callout>
담당 팀의 `member`는 `GET /v1/agents`·`GET /v1/agents/counts`로 자기 팀이 담당하는 에이전트를 찾고 설정을 읽는다. `include=summary`의 요약(관리자·자격 연결)은 설정을 읽을 수 있는 에이전트에만 붙는다. 에이전트 설정을 바꾼 receipt도 설정을 읽을 수 있는 사람만 읽는다.
</Callout>

### 담당 팀 밖 member

owner·admin, 에이전트 관리자, 담당 팀 구성원을 그 에이전트의 안쪽이라 하고, 그 밖의 member를 바깥쪽이라 한다. 에이전트는 안쪽만 쓴다. 바꾸는 설정은 없다.

- 바깥 member에게 에이전트는 웹에서도 Slack에서도 없는 것과 같다. 목록과 개수에 나오지 않고, 읽으면 `404`, 세션을 시작해도 없는 release와 같은 `404`다. 공유받은 세션은 보이지만 그 세션의 에이전트는 가려진다.
- Slack에서 바깥 member가 에이전트를 멘션하거나 DM을 보내면 세션이 시작되지 않고 권한이 없다는 짧은 안내만 받는다. Werft 계정에 연결하지 않은 Slack 사용자는 계정을 연결하라는 안내를 받는다.
- 에이전트의 `workspace` 공유 세션도 안쪽만 본다. 목록·개수·상세·이벤트·사용량 최근 목록에 바깥 member에게는 나오지 않는다. 담당 팀이 필수가 되기 전에 팀이 없던 에이전트는 구성원 없는 보관 팀(이름을 바꿔도 서버는 보관 팀으로 알아본다)이 맡았고, 이 에이전트들의 `workspace` 세션은 에이전트를 맞는 팀으로 옮기기 전까지 이전처럼 모든 멤버에게 보인다.
- 바깥 member라도 자기가 시작한 세션과, 자기나 자기 팀을 지정해 공유한(`people`·`team`) 세션은 계속 본다.
- 담당 팀을 바꾸거나 구성원이 팀에서 빠지면 다음 요청부터 이미 만든 세션에도 적용된다. 열린 이벤트 스트림은 다음 확인 때 끊긴다.
- 사용량 합계(세션 수·비용·성과 수)는 그대로이고, 최근 성과 목록에서 볼 수 없는 세션의 줄만 빠진다.
- 공유 범위가 `workspace`인데 바깥 member가 못 보는 세션이면 `GET /v1/sessions/{id}/share`의 `audience_limited`가 `true`다.

<Callout>
이전에는 워크스페이스 설정 두 개(`agent_outsider_access`, `agent_outsider_session_visibility`)로 바깥 member가 에이전트를 보고 쓰는 범위를 골랐다. 지금은 그 설정과 `PATCH /v1/workspaces/{id}/agent-access`가 없고, 늘 `none`·`managing_team`처럼 동작한다. 저장해 둔 값은 남아 있지만 읽지 않는다. 그래서 `use`나 `view`로 두었던 워크스페이스에서도 바깥 member에게 에이전트가 보이지 않는다.
</Callout>

| `DELETE /v1/agents/{id}` | 에이전트 삭제(콘솔: **상세 설정** → **위험 구역**). 새 세션을 받지 않고, Slack 연결·에이전트 key를 같은 요청에서 끊는다. 지난 세션은 그대로 읽히고, 그 뒤 이 에이전트의 모든 요청은 `404`, slug는 새 에이전트가 쓸 수 있다. API key로는 못 한다(`403`) |

### 관리자 없는 에이전트

에이전트를 관리할 살아 있는 사람이 한 명도 없으면 그 에이전트는 관리자 없음이다. 개인 관리자, 관리자 팀의 구성원, 담당 팀의 팀 관리자(`lead`) 중 비활성화되지 않은 사람이 아무도 없는 경우다. 워크스페이스 owner·admin은 세지 않는다. 그들은 관리자를 새로 정하는 쪽이다. 보관한 에이전트는 관리자 없음으로 치지 않는다.

- 에이전트 행의 `ownerless`가 지금 판정이다(`true`·`false`). `ownerless_since`는 플랫폼이 관리자 없음을 처음 본 시각이고, 관리자가 다시 생기면 `null`이 된다. 플랫폼은 몇 초 간격으로 이 값을 맞춘다.
- `GET /v1/agents?ownerless=true`는 관리자 없는 에이전트만 주고, `GET /v1/agents/counts`의 `ownerless`는 그 수다. 둘 다 목록과 같은 권한으로 읽는다.
- 콘솔은 워크스페이스 owner·admin에게 에이전트 목록 위에 알림과 **관리자 없음** 필터를 보이고, 행에 **관리자 없음** 표시를 붙인다. 상세 화면은 경고와 함께 관리자 탭으로 가는 버튼을 보인다.
- 관리자를 다시 정하는 방법은 지금 있는 변경이다. 사람이나 팀을 관리자로 더하거나, 팀 관리자가 있는 팀으로 담당 팀을 바꾸거나, 담당 팀 구성원 한 명을 팀 관리자로 바꾼다. 앞의 셋은 같은 요청에서 표시를 지우고, 팀 역할 변경은 몇 초 뒤에 지워진다.
- 요청자가 비활성화된 기존 세션은 관리자를 다시 정해도 그대로 인계 대기에 남는다. 그 세션은 따로 인계한다. 인계와 관리자 지정은 서로 독립이라 어느 순서로 해도 된다.
- 워크스페이스 owner·admin에게는 상세 경고가 이 에이전트의 인계 대기 세션 수와 목록을 보이고, 행마다 그 세션 상세로 가는 링크를 둔다. 관리자를 다시 정한 뒤에도 인계 대기 세션이 남아 있으면 경고는 그 목록으로 남는다. 세션 상세에서 **세션 인계하기**로 인계하면 내가 그 세션의 요청자가 된다. 나에게 공유되지 않은 세션은 사유를 함께 적어야 한다. API로는 `GET /v1/takeovers?agent_id={id}`로 읽고 `POST /v1/sessions/{id}/takeover`로 인계한다. 인계 목록을 읽을 권한이 없는 사람에게는 수도 목록도 보이지 않는다.

`ownerless_since`부터 14일이 지나도록 관리자가 없는 에이전트는 새 세션을 시작하지 않는다. 웹·API·Slack·에이전트 key 모두 `409 AGENT_NOT_RUNNABLE`(`details.reason_code`: `agent_ownerless`)을 받고, Slack 멘션과 DM에는 짧은 안내가 간다. 콘솔 경고의 날짜가 그 시각이다. 이미 돌고 있는 세션은 막지 않는다. 관리자 여부는 세션을 만드는 그 순간에 다시 보므로, 관리자를 다시 정하면 바로 새 세션을 시작할 수 있다.

## 자격 연결

카드는 쓸 자격 증명의 이름만 `capabilities.credential_refs`에 적는다. 값은 Werft 밖(secret store, remote MCP server 연결)에 있다. 그 이름을 이 에이전트가 써도 된다는 연결은 관리자가 따로 만든다. 카드에 적힌 이름 중 연결되지 않은 것이 있으면 활성화가 409 `CREDENTIAL_UNBOUND`다.

```bash
curl -sS "$API/v1/agents/$AID/credential-bindings" "${WEB[@]}" -d '{"credential_ref": "notion-token"}' \
  | jq '{credential_ref: .binding.credential_ref, created}'
curl -sS "$API/v1/agents/$AID/credential-bindings" "${WEB[@]}" | jq -c '[.items[].credential_ref]'
```

```text
{
  "credential_ref": "notion-token",
  "created": true
}
["notion-token"]
```

해제(`DELETE /v1/agents/{id}/credential-bindings/{binding_id}`)는 돌고 있는 세션을 멈추지 않는다. 다음 세션부터 막힌다. 바로 막으려면 외부 서비스에서 그 자격을 폐기한다.
